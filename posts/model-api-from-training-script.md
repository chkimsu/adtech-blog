# 모델 API: 학습 스크립트에서 바뀌는 것은 함수 모양, 동시성, 실패 처리 셋

지훈 씨의 열째 주입니다. 지난주에 분석 팀의 실험용 pCVR 모델을 BentoML 로 띄웠습니다. 이번에는 광고 소재의 품질 점수를 내는 새 모델을 광고를 고르는 경로에 올리게 됐습니다. 이 자리는 모델 호출에 쓸 수 있는 시간이 8ms 라서 BentoML 을 쓰지 않고 추론 서버를 직접 짜기로 했습니다.

지훈 씨는 학습 스크립트를 여러 번 짰습니다. 도커 이미지를 만들어 쿠버네티스에 올렸고, 고친 코드가 CI 검사를 지나는 것도 봤습니다. 그런데 요청을 받아 답하는 서버 코드는 처음부터 짜 본 적이 없었습니다. 선배의 서버 코드를 읽기는 했는데 어디가 어려운 부분인지 감이 없었습니다.

선배에게 물었습니다. 「학습 스크립트는 짤 수 있는데, 서버는 무엇이 다릅니까?」 선배는 이렇게 답했습니다. 「끝나는 대신 기다립니다. 그것 말고 새로 배울 것은 셋뿐입니다. 요청을 받는 함수의 모양, 여러 요청을 동시에 받는 법, 그리고 늦거나 실패했을 때 무엇을 돌려줄지입니다.」

**학습 스크립트를 짤 줄 아는 사람이 API 서버를 처음 짤 때, 새로 배워야 하는 것은 정말 셋뿐일까요?**

모델이 요청을 받아 점수를 돌려주는 서버를 추론 서버라고 부릅니다. 그 서버가 밖에 내놓는 주소와 주고받는 모양의 약속을 API 라고 부릅니다. 이 글은 학습 스크립트와 서버 코드를 나란히 놓고 무엇이 같고 무엇이 다른지를 봅니다. 그리고 「사용자가 많다」는 말이 서버 한 대가 받는 숫자로 어떻게 내려오는지를 셉니다. 이것을 알면 선배의 서버 코드에서 어디를 읽어야 하는지, 서버 대수를 어떻게 세는지, 늦은 요청에 무엇을 돌려줄지가 보입니다.

> **한 줄 요약:** 학습 스크립트와 서버 코드의 차이는 「끝나는가, 기다리는가」입니다. 기다리는 부분은 서버 라이브러리가 대신 하고, 직접 쓰는 것은 요청이 오면 부를 함수 하나입니다. 하루 노출 2억 2,800만 건은 평균 2,639 QPS 이고 피크를 3배로 보면 7,917 QPS 입니다. 요청 하나에 CPU 6ms 가 들면 8코어 서버 한 대가 안전선 60% 에서 800 QPS 를 받아 10대가 필요하고, 장애와 배포 교체 몫 2대를 더해 12대입니다. 피처 조회가 2ms 를 넘기면 기본 피처로 점수를 내서 응답 시간을 12ms 안에 묶습니다.

> **골라 읽는 법** — 절이 아홉 개인 글입니다. 절마다 표 하나나 코드 하나가 있어서 그것만 보고 넘어가도 됩니다.
>
> - 학습 스크립트와 서버 코드의 여섯 가지 차이 → 1절
> - 표준 라이브러리로 API 하나를 띄워 요청 하나를 보내는 코드 → 2절
> - 요청 하나의 12ms 를 어디에 나누나 → 3절
> - 사용자 수에서 서버 대수까지 세는 법 → 4절
> - 늦은 요청에 무엇을 돌려주나 → 5절
> - 트래픽을 받는 세 층과 쿠버네티스 설정의 낱말 → 6~7절
> - 담장 안과 열린 RTB → 8절
> - 이 블로그의 서빙 글 여덟 편을 읽는 순서 → 9절

이 글의 시간과 대수는 전부 설명을 위한 가상 값입니다. 모델 서버 12대, 모델 호출 예산 8ms, 후보 800건을 한 텐서로 넣어 3.0ms 는 [추론 서버](post.html?id=inference-server) 편의 값입니다. 요청 전체 예산 12ms 는 [게이트웨이와 Ingress](post.html?id=gateway-ingress-router) 편이 정한 값입니다. 하루 노출 2억 2,800만 건과 초당 2,639건은 [엔지니어링 기초 트랙](post.html?id=api-basics)의 표준값입니다. 요청 하나의 CPU 시간 6ms 와 피처 조회 2ms 는 이 글에서 새로 둔 가정입니다.

## 1. 학습 스크립트와 서버 코드는 여섯 줄이 다릅니다

**둘 다 모델 파일을 열어 predict 를 부르는 파이썬 프로그램입니다. 다른 것은 언제 시작하고 언제 끝나는가, 입력을 어디서 받고 출력을 어디로 보내는가입니다.**

지훈 씨가 짜 온 학습 스크립트는 한 번 실행되고 끝납니다. 데이터를 읽고, 학습하고, 파일을 저장하고, 종료합니다. 서버 코드는 한 번 실행되고 끝나지 않습니다. 모델 파일을 메모리에 올린 뒤 요청이 올 때마다 predict 를 부르고, 다음 요청을 기다립니다. 아래 표는 둘을 항목마다 나란히 둔 것입니다.

| 항목 | 학습 스크립트, train.py | 추론 서버, serve.py |
|---|---|---|
| 시작 | 명령 한 번으로 실행합니다 | 명령 한 번으로 실행하고, 그 뒤 계속 떠 있습니다 |
| 모델 | 끝에 파일로 저장합니다 | 시작할 때 파일을 열어 메모리에 올려 둡니다 |
| 입력 | 테이블이나 파일 전체를 읽습니다 | 요청 하나가 올 때마다 그 안의 JSON 을 읽습니다 |
| 출력 | 테이블이나 파일에 씁니다 | 응답 JSON 으로 바로 돌려줍니다 |
| 끝 | 다 돌면 종료합니다 | 종료하지 않습니다. 다음 요청을 기다립니다 |
| 새로 쓰는 코드 | 없습니다 | 「이 주소로 요청이 오면 이 함수를 불러라」 하나와, 그 함수의 입력 모양입니다 |

여섯 줄 가운데 다섯은 서버 라이브러리가 맡습니다. 계속 떠 있는 것과 요청을 기다리는 것이 그렇습니다. 요청 본문을 읽어 넘기고, 응답을 보내고, 다음 요청으로 넘어가는 것도 라이브러리의 몫입니다. 표준 라이브러리의 http.server 도 하고, FastAPI 와 uvicorn 도 하고, BentoML 도 합니다. 지훈 씨가 쓰는 것은 마지막 줄입니다. 요청이 오면 부를 함수 하나와 그 함수가 받는 입력의 모양입니다.

그 함수 안의 일은 학습 때와 같습니다. 피처를 모아 텐서를 만들고 predict 를 부릅니다. [추론 서버](post.html?id=inference-server) 편에서 본 입력 변환이 그 자리입니다. 학습 스크립트에서 피처 테이블 한 벌을 텐서로 만들던 코드가, 서버에서는 요청 하나에 실린 후보 800건을 텐서로 만드는 코드가 됩니다. 모양이 같아서 학습 코드를 그대로 옮겨 쓰는 팀이 많습니다.

그래서 처음 짤 때 어려운 것은 모델 쪽이 아닙니다. 「기다리는 부분」을 한 번도 본 적이 없어서 어렵게 느껴질 뿐입니다. 그 부분은 라이브러리가 하니 볼 것이 거의 없습니다. 다음 절에서 그 부분을 포함해 서버 하나를 통째로 띄워 봅니다. 표준 라이브러리만 씁니다.

## 2. 표준 라이브러리만으로 API 하나를 띄워 봅니다

**아래 코드는 모델 하나를 API 로 띄우고, 요청 하나를 보내고, 응답을 받고, 서버를 내립니다. 지훈 씨가 쓰는 것은 핸들러 클래스의 메서드 하나와 predict 함수뿐입니다.**

프레임워크 없이 표준 라이브러리로 짠 이유가 있습니다. 라이브러리가 대신 해 주는 다섯 가지와 직접 쓰는 한 가지가 한 화면에 다 보이기 때문입니다. 실무에서는 FastAPI 나 BentoML 을 쓰지만 하는 일은 같습니다. 가중치와 피처는 설명을 위한 가상 값이고, 피처 스토어 자리에는 딕셔너리를 두었습니다.

```python
# 하는 일: 표준 라이브러리만으로 pCTR 점수 API 를 띄우고, 요청 하나를 보내 응답을 받은 뒤 서버를 내린다.
# 1단계: 모델과 피처를 둔다
# 학습이 남긴 가중치 대신 가상 가중치 셋을 두고, 피처 스토어 대신 딕셔너리를 둔다. predict 는 학습 때 쓰던 함수와 같은 모양이다.
import json, math, threading
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.request import Request, urlopen

WEIGHTS = {"bias": -4.0, "recent_ctr": 20.0, "is_video": 0.3}        # 가상 가중치
FEATURES = {"ad-101": {"recent_ctr": 0.030, "is_video": 1},           # 피처 스토어 대신 둔 표
            "ad-102": {"recent_ctr": 0.012, "is_video": 0},
            "ad-103": {"recent_ctr": 0.051, "is_video": 1}}

def predict(rows):
    scores = []
    for f in rows:
        z = WEIGHTS["bias"] + WEIGHTS["recent_ctr"] * f["recent_ctr"] + WEIGHTS["is_video"] * f["is_video"]
        scores.append(round(1 / (1 + math.exp(-z)), 4))
    return scores

# 2단계: 요청이 오면 부를 함수를 적는다
# 서버 틀은 라이브러리가 준다. 직접 적는 것은 「POST 가 오면 이렇게 답하라」 하나다. 후보 셋을 모아 predict 를 한 번만 부른다.
class ScoreHandler(BaseHTTPRequestHandler):
    def do_POST(self):
        body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        rows = [FEATURES[cid] for cid in body["candidate_ids"]]      # 피처 조회
        scores = predict(rows)                                       # 후보 셋을 한 번에
        reply = json.dumps({"scores": dict(zip(body["candidate_ids"], scores))}).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(reply)))
        self.end_headers()
        self.wfile.write(reply)
    def log_message(self, *args):                                    # 접근 로그는 끈다
        pass

# 3단계: 서버를 띄우고 요청 하나를 보낸다
# 포트 0 은 빈 포트를 하나 고르라는 뜻이다. 서버는 다른 스레드에서 기다리고, 이 스레드가 요청을 보낸다.
server = HTTPServer(("127.0.0.1", 0), ScoreHandler)
threading.Thread(target=server.serve_forever, daemon=True).start()
payload = {"user_id": "u-7", "candidate_ids": ["ad-101", "ad-102", "ad-103"]}
req = Request(f"http://127.0.0.1:{server.server_port}/score", method="POST",
              data=json.dumps(payload).encode(), headers={"Content-Type": "application/json"})
with urlopen(req, timeout=2) as resp:
    print("상태", resp.status, resp.headers["Content-Type"])
    print("응답", resp.read().decode())
server.shutdown()
print("서버를 내렸다. 학습 스크립트였다면 여기까지 오기 전에 이미 끝났다.")

# 출력:
# 3단계 뜻: 요청 하나가 들어와 상태 200 과 점수 셋이 JSON 으로 돌아왔다. 서버는 그 뒤에도 떠 있다가 shutdown 으로 내려간다.
# 상태 200 application/json
# 응답 {"scores": {"ad-101": 0.0431, "ad-102": 0.0228, "ad-103": 0.0642}}
# 서버를 내렸다. 학습 스크립트였다면 여기까지 오기 전에 이미 끝났다.
```

코드를 위에서 아래로 읽으면 요청 하나에 일어나는 일이 보입니다. 서버가 포트에서 기다립니다. 요청 본문이 오면 JSON 으로 읽습니다. 후보 ID 로 피처를 조회합니다. 후보 셋을 모아 predict 를 한 번 부릅니다. 점수를 JSON 으로 돌려줍니다. 그리고 다음 요청을 기다립니다. 이 가운데 지훈 씨가 쓴 줄은 피처 조회, predict 호출, 응답 조립 세 줄입니다.

학습 스크립트와 다른 자리가 셋 보입니다. 첫째, 함수의 모양입니다. 입력이 파일이 아니라 요청 본문이고, 출력이 파일이 아니라 응답입니다. 둘째, 동시성입니다. 이 코드는 요청을 한 번에 하나씩 처리합니다. 요청이 겹치면 뒤의 것이 기다립니다. 실무에서는 프로세스를 여러 개 띄워 나눠 받습니다. 4절에서 그 수를 셉니다. 셋째, 실패 처리입니다. 피처 조회가 늦거나 후보 ID 가 표에 없으면 이 코드는 그대로 멈춥니다. 5절에서 그 자리를 채웁니다.

함수 모양은 반나절이면 익힙니다. 동시성과 실패 처리는 숫자로 정하는 일이라 하루씩 듭니다. 다음 절부터 그 숫자를 셉니다. 먼저 요청 하나에 쓸 수 있는 시간입니다.

## 3. 요청 하나의 12ms 를 어디에 나눕니까

**요청 전체 예산이 12ms 이면 그 안을 구간마다 나눠 적어 둡니다. 모델 호출 8ms, 피처 조회 2ms, 후보 조회 1ms, 게이트웨이와 응답 조립 1ms 입니다. 구간마다 예산이 있어야 어디가 넘겼는지 알 수 있습니다.**

[게이트웨이와 Ingress](post.html?id=gateway-ingress-router) 편에서 입찰 요청 하나의 예산을 12ms 로 정했습니다. 그 12ms 는 서버 코드 한 곳이 다 쓰는 것이 아닙니다. [Ad Serving Flow](post.html?id=ad-serving-flow) 편의 여덟 걸음이 나눠 씁니다. 이 팀의 배분은 아래 표와 같습니다. 모델 호출 8ms 는 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편의 값이고 나머지는 이 글의 가정입니다.

| 구간 | 예산 | 하는 일 | 넘기면 |
|---|---|---|---|
| 게이트웨이 | 0.5ms | 요청을 받아 서버 한 대에 넘깁니다 | 다른 서버로 보냅니다 |
| 후보 조회 | 1ms | 이 사용자에게 보여도 되는 광고 800건을 꺼냅니다 | 어제 만들어 둔 후보 목록을 씁니다 |
| 피처 조회 | 2ms | 사용자 한 줄과 광고 800줄을 피처 스토어에서 가져옵니다 | 기본 피처로 점수를 냅니다 |
| 모델 호출 | 8ms | 후보 800건을 한 텐서로 넣어 점수를 냅니다. 보통 3.0ms 입니다 | 인기도 점수로 순위를 매깁니다 |
| 응답 조립 | 0.5ms | 점수를 JSON 으로 만들어 돌려줍니다 | 넘길 일이 거의 없습니다 |

표의 예산을 더하면 12ms 입니다. 보통 때 실제로 쓰는 시간은 그보다 짧습니다. 모델 호출은 예산이 8ms 인데 보통 3.0ms 에 끝납니다. 남는 5ms 는 느린 요청의 몫입니다. 요청 100건 가운데 99번째로 느린 것이 쓰는 시간을 p99 라고 부르고, 예산은 평균이 아니라 p99 에 맞춥니다. 평균이 멀쩡해 보여도 하루 1,053만 건이 예산을 넘기는 일이 생깁니다. 그 셈은 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편 3절에 있습니다.

「넘기면」 열이 이 표에서 가장 중요합니다. 구간마다 넘겼을 때 무엇을 할지가 적혀 있어야 한 구간이 느려져도 요청 전체가 죽지 않습니다. 피처 조회가 늦으면 기본 피처로 점수를 내고, 모델이 늦으면 인기도 점수로 순위를 매깁니다. 광고가 안 나가는 것보다 덜 정확한 광고가 나가는 쪽이 낫기 때문입니다. 이 결정을 코드로 옮기는 것이 5절입니다.

예산 표가 있으면 서버 코드에서 읽을 자리도 정해집니다. 각 구간이 시작하고 끝나는 자리에 시각을 찍는 줄이 있을 것이고, 그 값이 대시보드의 p99 가 됩니다. 지훈 씨가 선배의 서버 코드에서 처음 찾을 것은 predict 가 아니라 그 시각 찍는 줄입니다. 구간이 어디서 끊기는지가 거기 적혀 있습니다.

## 4. 사용자 수에서 서버 대수까지 셉니다

**「사용자가 많다」는 설계의 입력이 아닙니다. 초당 요청 수가 입력입니다. 하루 노출 2억 2,800만 건은 평균 2,639 QPS 이고 피크는 7,917 QPS 입니다. 그 피크를 8코어 서버가 안전선 60% 로 받으면 10대이고, 예비까지 12대입니다.**

지훈 씨가 가장 걱정한 것이 이 자리였습니다. 사용자 전부의 요청을 자기 서버가 받아야 한다고 생각했기 때문입니다. 셈을 해 보면 그 걱정이 숫자 넷으로 줄어듭니다. 하루 요청 수, 피크 배수, 요청 하나의 CPU 시간, 서버 한 대의 코어 수입니다. 아래 코드가 그 넷에서 서버 대수까지 셉니다. 하루 노출 수는 [엔지니어링 기초 트랙](post.html?id=api-basics)의 표준값이고 나머지는 가정입니다.

```python
# 하는 일: 하루 노출 수에서 피크 초당 요청 수, 동시 요청 수, 서버 대수를 차례로 센다.
# 1단계: 숫자 넷을 둔다
# 하루 노출 2억 2,800만 건은 엔지니어링 기초 트랙의 값이다. 피크는 평균의 3배, 요청 하나의 CPU 시간은 6ms, 요청 하나의 지연은 7ms 로 둔다(가상 값). 서버는 8코어이고 CPU 는 60% 까지만 쓴다.
import math
DAILY, PEAK_RATIO = 228_000_000, 3
CPU_MS, LATENCY_MS = 6.0, 7.0
CORES, SAFE_RATIO = 8, 0.60
# 2단계: 평균과 피크 QPS 를 센다
# 하루는 86,400초다.
avg_qps = DAILY / 86_400
peak_qps = avg_qps * PEAK_RATIO
print(f"평균 {avg_qps:,.0f} QPS, 피크 {peak_qps:,.0f} QPS")
# 3단계: 동시에 처리 중인 요청 수를 센다
# 동시 요청 수 = 초당 요청 수 × 요청 하나의 지연(초). 이 수만큼 워커가 있어야 줄이 안 선다.
concurrent = peak_qps * LATENCY_MS / 1000
print(f"피크에 동시에 처리 중인 요청 {concurrent:.0f}건")
# 4단계: 서버 한 대의 처리량과 대수를 센다
# 코어 하나는 1초에 1,000ms 를 쓴다. 요청 하나가 6ms 면 코어당 초당 요청 수가 나온다. 60% 만 쓰는 이유는 100% 로 돌리면 p99 가 길어지기 때문이다.
per_core = 1000 / CPU_MS
per_server = per_core * CORES * SAFE_RATIO
need = math.ceil(peak_qps / per_server)
print(f"코어당 {per_core:.0f} QPS, 8코어 서버 한 대 {per_server:,.0f} QPS (60% 만 쓸 때)")
print(f"피크를 받는 데 {need}대, 장애와 배포 교체 몫 2대를 더해 {need + 2}대")
print(f"평균 때 서버 한 대가 받는 요청 초당 {avg_qps / (need + 2):.0f}건")

# 출력:
# 2단계 뜻: 하루 2억 2,800만 건은 평균 2,639 QPS 이고 피크는 7,917 QPS 다.
# 평균 2,639 QPS, 피크 7,917 QPS
# 3단계 뜻: 피크에 서버들 안에 동시에 55건이 있다. 12대로 나누면 한 대에 5건이 안 된다.
# 피크에 동시에 처리 중인 요청 55건
# 4단계 뜻: 코어당 167 QPS, 한 대 800 QPS 라 10대가 필요하고 예비 2대를 더해 12대다. 평균 때는 한 대가 초당 220건을 받는다.
# 코어당 167 QPS, 8코어 서버 한 대 800 QPS (60% 만 쓸 때)
# 피크를 받는 데 10대, 장애와 배포 교체 몫 2대를 더해 12대
# 평균 때 서버 한 대가 받는 요청 초당 220건
```

숫자가 어떻게 내려오는지 따라가면 이렇습니다. 하루 2억 2,800만 건을 86,400초로 나누면 평균 2,639 QPS 입니다. 저녁 시간대에 요청이 몰리는 것을 3배로 보면 피크 7,917 QPS 입니다. 요청 하나가 서버 안에 7ms 머물면 피크에 동시에 55건이 서버들 안에 있습니다. 12대로 나누면 서버 한 대에 5건이 안 됩니다. 8코어 서버에 워커 8개를 두면 줄이 서지 않습니다.

서버 대수는 CPU 시간에서 나옵니다. 요청 하나에 CPU 6ms 가 들면 코어 하나가 초당 167건을 처리합니다. 8코어면 1,333건인데 60% 만 쓰기로 하면 800건입니다. 피크 7,917 QPS 를 800 으로 나누면 10대입니다. 한 대가 죽어도 피크를 받아야 하고 배포 중에는 2대씩 빠지니 2대를 더해 12대입니다. [추론 서버](post.html?id=inference-server) 편의 서버 12대와 서버 한 대가 평균 때 받는 초당 220건이 이 셈에서 나온 값입니다.

여기서 결정이 둘 나옵니다. 하나는 서버 대수 12 를 쿠버네티스 설정의 복제본 수에 적는 것입니다. 다른 하나는 요청 하나의 CPU 6ms 를 줄이는 것입니다. 6ms 가 3ms 가 되면 코어당 333건이 되어 서버가 5대로 줄어듭니다. 후보 800건을 하나씩 부르지 않고 한 텐서로 넣는 것이 그 가장 큰 몫입니다. [추론 서버](post.html?id=inference-server) 편 4절이 그 차이를 3.0ms 와 96ms 로 쟀습니다. 사용자가 10배가 되면 이 셈의 첫 줄만 바뀌고, 서버 대수가 10배가 됩니다. 모델 서버가 상태를 들고 있지 않아서 가능한 일입니다.

## 5. 늦은 요청에는 무엇을 돌려줍니까

**피처 조회가 2ms 를 넘기면 기다리지 않고 기본 피처로 점수를 냅니다. 타임아웃이 없으면 요청 10건 중 2건이 12ms 를 넘기고, 타임아웃과 폴백을 넣으면 0건이 되는 대신 2건이 덜 정확한 점수로 나갑니다.**

실패 처리는 두 숫자를 정하는 일입니다. 얼마나 기다릴지와, 기다리기를 멈추면 무엇을 돌려줄지입니다. 기다리는 상한을 타임아웃이라고 부르고, 대신 돌려주는 값을 폴백이라고 부릅니다. 아래 코드는 피처 조회 시간이 들쭉날쭉한 요청 10건으로 두 경우를 견줍니다. 조회 시간은 가상 값이고, 그 가운데 둘은 피처 스토어가 느려진 순간의 값입니다.

```python
# 하는 일: 피처 조회가 늦은 요청에 타임아웃과 폴백을 넣으면 예산을 넘기는 요청 수가 어떻게 바뀌는지 센다.
# 1단계: 요청 10건의 피처 조회 시간을 둔다
# 조회 시간은 가상 값이다. 넷째와 일곱째 요청은 피처 스토어가 느려진 순간에 들어온 것이다. 다른 구간은 게이트웨이 0.5ms, 후보 조회 1ms, 모델 호출 3ms, 응답 조립 0.5ms 로 늘 같다고 둔다.
lookups_ms = [1.1, 0.9, 1.4, 8.2, 1.0, 1.2, 11.0, 1.3, 0.8, 1.1]
OTHER_MS = 0.5 + 1.0 + 3.0 + 0.5
BUDGET_MS, TIMEOUT_MS = 12.0, 2.0
# 2단계: 타임아웃 없이 끝까지 기다린다
# 요청 하나의 시간은 다른 구간 5ms 에 조회 시간을 더한 값이다.
no_timeout = [OTHER_MS + lk for lk in lookups_ms]
over = [t for t in no_timeout if t > BUDGET_MS]
print(f"타임아웃 없이: 가장 느린 요청 {max(no_timeout):.1f}ms, 예산 12ms 를 넘긴 요청 {len(over)}건")
# 3단계: 2ms 에서 끊고 기본 피처로 점수를 낸다
# 조회가 2ms 를 넘기면 그때까지 기다린 2ms 만 쓰고 기본 피처로 모델을 부른다. 그 요청은 점수가 덜 정확하다.
with_timeout = [OTHER_MS + min(lk, TIMEOUT_MS) for lk in lookups_ms]
fallbacks = [lk for lk in lookups_ms if lk > TIMEOUT_MS]
print(f"타임아웃 2ms: 가장 느린 요청 {max(with_timeout):.1f}ms, 예산을 넘긴 요청 {sum(t > BUDGET_MS for t in with_timeout)}건")
print(f"대신 기본 피처로 점수를 낸 요청 {len(fallbacks)}건 (조회에 {fallbacks[0]:.1f}ms, {fallbacks[1]:.1f}ms 걸리던 것)")

# 출력:
# 2단계 뜻: 끝까지 기다리면 느려진 순간의 요청 2건이 예산 12ms 를 넘긴다. 가장 느린 것은 16.0ms 다.
# 타임아웃 없이: 가장 느린 요청 16.0ms, 예산 12ms 를 넘긴 요청 2건
# 3단계 뜻: 2ms 에서 끊으면 가장 느린 요청도 7.0ms 라 넘기는 요청이 0건이다. 대신 2건은 기본 피처로 낸 점수를 받는다.
# 타임아웃 2ms: 가장 느린 요청 7.0ms, 예산을 넘긴 요청 0건
# 대신 기본 피처로 점수를 낸 요청 2건 (조회에 8.2ms, 11.0ms 걸리던 것)
```

타임아웃이 없으면 피처 스토어가 느려진 순간의 요청 2건이 13.2ms 와 16.0ms 가 되어 예산을 넘깁니다. 예산을 넘긴 요청은 게이트웨이가 버리고, 그 사용자는 광고를 보지 못합니다. 타임아웃을 2ms 에 걸면 같은 2건이 7.0ms 에 끝나고 예산을 넘기는 요청은 0건입니다. 대신 그 2건은 그 사용자의 최근 행동 피처 없이 기본 피처로 낸 점수를 받습니다. 덜 정확한 광고가 나갑니다.

이 저울질이 실패 처리의 전부입니다. 광고가 안 나가는 비용과 덜 정확한 광고가 나가는 비용을 견주어 타임아웃 값을 정합니다. 피처 조회의 보통 시간이 1ms 안팎이니 2ms 는 보통 요청을 자르지 않으면서 느려진 순간만 자르는 값입니다. 모델 호출에도 같은 식으로 타임아웃을 걸고, 넘기면 인기도 점수로 순위를 매깁니다. 3절 표의 「넘기면」 열이 코드로 옮겨진 것입니다.

지훈 씨가 서버 코드에서 둘째로 찾을 것이 이 자리입니다. 피처 스토어를 부르는 줄에 타임아웃 값이 있는지, 넘겼을 때 무엇을 돌려주는지입니다. 그 두 줄이 없으면 피처 스토어가 느려지는 날 서버 12대가 전부 예산을 넘깁니다. 한 구간의 지연이 전체의 장애가 되는 것을 막는 줄이 이 두 줄입니다.

## 6. 트래픽은 세 층이 나눠 받습니다

**모델 서버가 사용자 전부의 요청을 혼자 받는 구조는 없습니다. 플랫폼이 요청을 나누고 서버 수를 조절하며, 앞단 서버가 피처를 모으고 모델 서버를 부릅니다. 모델 서버는 받은 배치를 점수로 바꾸는 한 층입니다.**

4절에서 센 12대가 어디에 놓이는지를 보면 지훈 씨가 맡는 범위가 보입니다. 아래 표는 요청이 지나는 세 층과, 층마다 트래픽에서 하는 일, 그리고 모델을 만드는 엔지니어가 그 층에 적어 주어야 하는 것입니다.

| 층 | 트래픽에서 하는 일 | 누가 만들고 운영하나 | 모델 엔지니어가 적어 주는 것 |
|---|---|---|---|
| 플랫폼 | 로드밸런서가 요청을 서버 12대에 나눕니다. 오토스케일이 서버 수를 늘리고 줄입니다. 대시보드와 알람이 붙어 있습니다 | 플랫폼 팀. 쿠버네티스와 게이트웨이 | 서버 한 대가 받는 QPS, 요청 하나의 CPU 와 메모리, 늘리는 기준 |
| 앞단 서버 | 요청을 받아 후보와 피처를 모으고 모델 서버를 부릅니다. 타임아웃과 폴백을 겁니다. 예측 로그를 남깁니다 | 서빙 엔지니어. 작은 팀이면 모델 엔지니어가 같이 | 입력과 출력의 모양, 구간별 예산, 폴백 점수 |
| 모델 서버 | 받은 배치를 점수로 바꿉니다. 상태를 들고 있지 않아 몇 대를 띄워도 같습니다 | 모델 엔지니어 | 요청 하나의 비용, 메모리, 웜업, 부하 시험으로 잰 서버 한 대의 QPS |

모델 엔지니어가 책임지는 것은 셋째 층의 효율과 숫자입니다. 요청 하나의 CPU 를 6ms 에서 3ms 로 줄이고, 모델을 메모리에 한 번만 올리는 일입니다. 그리고 서버 한 대가 몇 QPS 를 받는지 부하 시험으로 재어 첫째 층에 적어 주는 일입니다. 로드밸런서를 만들거나 오토스케일 규칙을 짜거나 클러스터를 운영하는 일은 첫째 층의 몫이고, 회사마다 이미 있습니다.

둘째 층은 팀 크기에 따라 다릅니다. 서빙 엔지니어가 따로 있는 팀은 모델 엔지니어가 입력과 출력의 모양과 폴백 점수만 정합니다. 작은 팀은 모델 엔지니어가 둘째 층의 코드도 씁니다. 지훈 씨의 팀은 둘째 층과 셋째 층이 한 서버 코드 안에 있어서, 선배의 서버 코드에 피처 조회와 타임아웃이 같이 들어 있었습니다. 3절과 5절에서 찾기로 한 줄들이 그 코드의 둘째 층 부분입니다.

이 그림이 있으면 「엄청 잘 설계해야 하는 자리」가 어디인지도 보입니다. 모델 서버는 상태가 없어서 대수를 늘리면 됩니다. 어려운 자리는 여러 서버가 같이 쓰는 것입니다. 피처 스토어와 캐시입니다. 그것은 둘째 층과 첫째 층이 같이 봅니다. [Feature Store](post.html?id=feature-store-serving) 편이 그 자리를 다룹니다.

## 7. 쿠버네티스 설정의 낱말이 곧 서빙 낱말입니다

**지훈 씨가 이미 써 본 쿠버네티스 설정의 값들이 이 글의 숫자와 하나씩 짝이 맞습니다. 복제본 수가 서버 대수이고, HPA 가 오토스케일이고, readiness probe 가 웜업 끝 신호입니다.**

도커 이미지를 만들어 쿠버네티스에 올려 본 사람은 서빙 낱말의 절반을 이미 압니다. 이름이 다를 뿐입니다. 아래 표는 그 짝입니다. 왼쪽은 [Docker 와 CI](post.html?id=container-ci-pipeline) 편과 [쿠버네티스 네트워킹](post.html?id=kubernetes-networking) 편에서 본 것이고, 오른쪽은 이 글의 숫자입니다.

| 이미 아는 것 | 서빙에서의 이름 | 이 글에서 적는 값 |
|---|---|---|
| 도커 이미지 | 모델 서버 한 벌 | 모델 파일 38MB, 서버 코드, 런타임. 학습 이미지와 다른 것은 시작 명령뿐입니다 |
| Deployment 의 replicas | 서버 대수 | 4절의 12 |
| resources 의 cpu | 코어 수 | 4절의 8코어. 코어당 167 QPS 를 곱하면 서버 한 대의 처리량입니다 |
| HPA | 오토스케일 | CPU 60% 를 넘으면 늘립니다. 늘어나는 데 41초가 걸리니 급증은 폴백이 먼저 받습니다 |
| Service 와 Ingress | 로드밸런서 | 요청을 12대에 나눕니다. 6절의 첫째 층입니다 |
| readiness probe | 웜업이 끝났다는 신호 | 모델을 올리고 웜업 200건이 끝나기 전에 요청이 오면 2.5배 느립니다. 그 전에는 트래픽을 받지 않게 하는 장치입니다 |
| liveness probe | 죽은 서버 교체 | 응답이 없으면 서버를 다시 띄웁니다 |
| ConfigMap 과 환경 변수 | 타임아웃과 모델 버전 | 5절의 2ms 와 3절의 8ms, 어느 모델 파일을 읽을지 |
| CI 의 이미지 빌드와 배포 | 모델 배포와 롤백 | 롤백은 이전 이미지 태그로 되돌리는 일입니다 |
| 롤링 업데이트와 카나리 | 새 모델 1% 트래픽 | 새 버전 서버를 일부만 띄워 p99 와 CTR 을 보고 늘립니다 |

readiness probe 가 왜 서빙에서 꼭 필요한지는 [추론 서버](post.html?id=inference-server) 편 3절과 6절에 있습니다. 서버가 뜨고 41초가 지나야 요청을 받을 준비가 되고, 그 전에 열면 폴백이 939건 더 나갑니다. 쿠버네티스 설정의 readinessProbe 한 블록이 그 41초를 지켜 줍니다. HPA 가 서버를 늘릴 때도 새 서버는 같은 41초를 기다립니다. 그래서 트래픽이 갑자기 늘면 오토스케일보다 5절의 폴백이 먼저 받습니다.

롤백도 이미 아는 일입니다. [모델 배포와 롤백](post.html?id=model-deployment-rollback) 편의 1% 로 시작해 15분 안에 되돌리는 순서는 카나리 배포와 이미지 태그 되돌리기로 이루어집니다. 모델 서버에서 새로 생기는 것은 모델 버전과 피처 버전을 짝으로 기록하는 일 하나입니다. 모델만 바꾸고 피처 변환을 안 바꾸면 조용히 틀리는 일이 [Feature Store](post.html?id=feature-store-serving) 편의 주제입니다.

## 8. 무대가 바뀌면 숫자가 어디서 옵니까

**4절의 셈은 두 무대가 같습니다. 다른 것은 첫 줄의 숫자를 누가 주느냐입니다. 담장 안에서는 우리가 요청량을 알고, 열린 RTB 에서는 거래소가 예산과 트래픽을 정합니다.**

### 담장 안에서는 첫 줄을 우리가 적습니다 [무대: 닫힌 생태계]

한 회사가 앱과 서버를 다 가진 담장 안에서는 하루 노출 2억 2,800만 건과 저녁 피크가 우리 로그에 있습니다. 4절의 첫 줄을 어제 값으로 적고 내일을 셉니다. 피처도 회원 ID 로 미리 만들어 두니 피처 조회가 2ms 안에 끝나는 것이 보통입니다. 요청 전체 예산 12ms 도 우리 게이트웨이가 정한 값이라 구간 배분을 우리가 바꿀 수 있습니다. 이 블로그의 저자가 일하는 자리이고, 이 글의 표와 코드는 이 상태를 적은 것입니다.

### 열린 RTB 에서는 첫 줄을 거래소가 정합니다 [무대: 열린 RTB]

열린 RTB 의 입찰 서버는 남의 거래소가 보내는 요청을 받습니다. 요청량은 거래소 사정에 따라 튀어서 피크 배수 3 을 우리가 정할 수 없습니다. 예산도 거래소가 정하고 그 안에 네트워크 왕복이 들어 있어 서버가 쓸 시간이 더 짧습니다. 요청에 실린 것은 회원 ID 가 아니라 쿠키라서 피처를 미리 만들어 둘 수 없고, 피처 조회 대신 그 자리에서 계산하는 몫이 붙습니다. 그래서 같은 셈을 하되 첫 줄은 거래소별 로그의 피크로 적고, 폴백은 더 자주 나갑니다.

| 무엇 | 담장 안 | 열린 RTB |
|---|---|---|
| 하루 요청 수와 피크 | 우리 로그에서 읽습니다 | 거래소별 로그를 합쳐 읽고, 튀는 쪽에 맞춥니다 |
| 요청 전체 예산 | 우리 게이트웨이가 정한 12ms | 거래소마다 다르고 가장 짧은 곳에 맞춥니다 |
| 피처 조회 | 회원 ID 로 미리 만든 값을 2ms 안에 | 쿠키라 그 자리에서 계산하는 몫이 붙습니다 |
| 폴백이 나가는 빈도 | 피처 스토어가 느려진 순간뿐 | 트래픽이 튈 때마다 더 자주 |

## 9. 무엇을 어떤 순서로 읽으면 됩니까

**이 블로그에는 API 와 서빙 글이 여덟 편 있습니다. 모델을 만들던 사람이 서버를 처음 짤 때는 아래 순서가 맞습니다. 요청 하나가 모델을 지나 돌아오는 길만 따라가면 됩니다.**

백엔드 개발자가 API 를 배우는 순서와 다릅니다. HTTP 전체가 아니라 이 글의 세 가지, 함수 모양과 동시성과 실패 처리를 채우는 글부터 읽습니다. 왼쪽 번호가 읽는 순서이고, 오른쪽은 그 글에서 가져갈 것 하나입니다.

| 순서 | 글 | 거기서 가져갈 것 |
|---|---|---|
| 1 | [API 기초](post.html?id=api-basics) | 요청과 응답이 반드시 짝이라는 것, 메서드 다섯, 로그가 남는 두 자리 |
| 2 | [추론 서버](post.html?id=inference-server) | 모델 파일이 서버가 되는 41초, 후보 800건을 한 텐서로 넣는 이유 |
| 3 | [서빙 지연, 처리량과 Grafana](post.html?id=serving-latency-throughput) | latency, throughput, QPS 의 뜻과 p99 를 어디서 재는가 |
| 4 | [API 연동 실무](post.html?id=api-kinds-and-contracts) | 타임아웃과 재시도, 다시 보내기가 가장 비싼 실수인 이유 |
| 5 | [BentoML](post.html?id=bentoml-model-serving) | 서버 기능 일곱 가지 중 넷을 도구가 대신 만들어 주는 것과 그 비용 |
| 6 | [Feature Store](post.html?id=feature-store-serving) | 학습과 서빙이 같은 피처를 보게 하는 법 |
| 7 | [배치 추론과 실시간 추론](post.html?id=batch-vs-realtime-inference) | 요청 안에서 할 일과 미리 해 둘 일을 나누는 기준 |
| 8 | [광고 모델 서빙 아키텍처](post.html?id=model-serving-architecture) | 세 층 전체와 배치 크기가 p99 를 바꾸는 저울질 |

1번에서 3번까지가 이 글의 2절과 3절을 깊게 하는 글입니다. 사흘이면 됩니다. 4번과 5번이 실패 처리와 도구이고, 6번에서 8번이 셋째 층 밖의 그림입니다. 여덟 편을 다 읽은 뒤 2절의 코드를 FastAPI 로 다시 짜고 부하를 걸어 p99 를 보면, 이 글의 숫자가 자기 노트북의 숫자로 바뀝니다.

## 한눈 정리

| 질문 | 한 줄 답 |
|---|---|
| 학습 스크립트와 서버 코드는 무엇이 다른가 | 끝나는가, 기다리는가입니다. 기다리는 부분은 라이브러리가 합니다 |
| 직접 쓰는 것은 | 요청이 오면 부를 함수 하나와 그 입력 모양입니다 |
| 새로 배우는 것은 | 함수 모양, 동시성, 실패 처리 셋입니다 |
| 요청 하나의 예산은 | 12ms. 모델 호출 8, 피처 조회 2, 후보 조회 1, 게이트웨이와 조립 1 |
| 사용자 수는 어떻게 숫자가 되나 | 하루 2억 2,800만 건이 평균 2,639 QPS, 피크 7,917 QPS 입니다 |
| 서버는 몇 대인가 | 요청당 CPU 6ms, 8코어, 60% 로 10대. 예비 2대를 더해 12대 |
| 늦은 요청에는 | 피처 조회 2ms 에서 끊고 기본 피처로 점수를 냅니다 |
| 트래픽은 누가 받나 | 플랫폼, 앞단 서버, 모델 서버 세 층입니다. 모델 서버는 그중 하나 |
| 쿠버네티스 설정과의 짝은 | replicas 가 대수, HPA 가 오토스케일, readiness probe 가 웜업 끝 신호 |

## 헷갈리기 쉬운 점

- **API 서버가 어려운 것이 아니라 「기다리는 부분」을 본 적이 없는 것입니다.** 그 부분은 라이브러리가 하고, 2절 코드에서 지훈 씨가 쓴 줄은 셋입니다.
- **사용자 수는 설계의 입력이 아닙니다.** 초당 요청 수가 입력이고, 그것도 평균이 아니라 피크입니다. 1,000만 사용자가 서버 10여 대로 끝나는 것이 보통의 자릿수입니다.
- **서버 대수를 정하는 것은 지연이 아니라 CPU 시간입니다.** 지연 7ms 는 동시 요청 수를 정하고, CPU 6ms 가 코어당 처리량과 대수를 정합니다.
- **타임아웃은 요청을 버리는 장치가 아닙니다.** 기다리기를 멈추고 폴백으로 답하는 장치입니다. 버리는 쪽은 예산을 넘긴 요청을 받는 게이트웨이입니다.
- **오토스케일은 급증을 받지 못합니다.** 새 서버가 뜨는 데 41초가 걸립니다. 그 41초는 폴백과 남겨 둔 예산이 받습니다.
- **모델 서버를 늘리는 것은 쉽고 피처 스토어를 늘리는 것은 어렵습니다.** 상태가 없는 것과 있는 것의 차이이고, 어려운 쪽은 첫째 층과 둘째 층이 같이 봅니다.
