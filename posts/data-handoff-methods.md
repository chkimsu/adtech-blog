지훈 씨가 여섯째 주에 옆 팀 메시지를 받았습니다. 광고주 리포트 팀이었습니다. "클릭 로그를 우리도 쓰고 싶은데, 어떻게 받을 수 있을까요." 지훈 씨는 답을 쓰기 시작했습니다. "csv 로 뽑아 드릴까요?"

보내기 전에 선배가 봤습니다. "그거 다음 주에도 뽑아 드릴 거예요?" 지훈 씨는 멈췄습니다. 하루치 클릭은 228만 줄입니다. 매주 뽑아서 슬랙으로 보내는 것은 답이 아니었습니다. 그런데 다른 답이 무엇인지 몰랐습니다. 데이터 팀 사람들은 Sqoop 이니 CDC 니 토픽이니 하는 말을 자기들끼리만 했습니다.

**팀에서 팀으로 데이터를 건네는 방법은 몇 가지이고, 어느 것을 골라야 하나요?**

방법은 여덟 가지입니다. 그런데 오가는 것의 모양은 넷뿐입니다. 테이블, 파일, 토픽, API 입니다. 도구 이름은 전부 「이 넷 중 무엇을, 누가, 얼마나 자주 옮기나」의 조합입니다. 이것을 알면 데이터 팀과 같은 말로 이야기할 수 있고, 매주 csv 를 뽑는 일을 안 하게 됩니다.

> **한 줄 요약:** 오가는 모양은 테이블, 파일, 토픽, API 넷입니다. 어디에 어떤 모양으로 있나, 얼마나 자주 새로 와야 하나, 누가 옮기나 세 가지를 답하면 여덟 방법 중 하나로 좁혀집니다.

> **골라 읽는 법** — 절이 10개인 글입니다. 절마다 카드 한 장이 들어 있어 카드만 보고 넘어가도 됩니다.
>
> - 모양 넷과 질문 셋만 → 1절
> - 놓여 있는 것을 옮기는 법 (권한, 배치, CDC, 파일) → 2~5절
> - 흐르는 것과 부르는 것 (토픽, API) → 6~7절
> - 로그를 남기게 하는 법과 결과를 되돌리는 법 → 8~9절
> - 그래서 무엇을 고르나 → 10절

이 글의 팀 이름, 테이블 이름, 시각은 설명을 위한 가상 값입니다. 하루 클릭 228만 건과 한 줄 309 바이트는 이 트랙의 앞 글들과 같은 값입니다. 카드 속 색은 넷입니다. 파랑은 놓여 있는 것(테이블, 파일, DB)이고 벽돌색은 흐르는 것(토픽, 변경 로그)입니다. 먹색은 부르는 것(서비스, API)이고 회색은 옮기는 도구입니다.

## 1. 오가는 모양은 넷, 물을 것은 셋입니다

**데이터는 테이블, 파일, 토픽, API 네 모양 중 하나로 있습니다. 방법 여덟 가지는 이 넷 사이를 옮기는 조합입니다.**

테이블은 창고나 DB 안에 줄과 칸으로 놓인 것입니다. 파일은 저장소 경로에 놓인 것입니다. 토픽은 Kafka 같은 곳에 시간 순서로 흐르는 것입니다. API 는 서비스가 요청을 받아 그때그때 답해 주는 것입니다. 앞의 둘은 놓여 있고, 셋째는 흐르고, 넷째는 부르면 옵니다.

지훈 씨의 클릭 로그는 지금 창고 테이블 `adlog.ad_click` 에 놓여 있습니다. 리포트 팀이 원하는 것도 결국 이 넷 중 하나입니다. 자기 창고의 테이블로 받고 싶은지, 파일로 받고 싶은지, 실시간으로 흘러오길 원하는지, 화면에서 건별로 묻고 싶은지. 그것을 묻지 않고는 방법을 고를 수 없습니다.

| 물을 것 | 답이 정해 주는 것 |
|---|---|
| 지금 어디에 어떤 모양으로 있나 | 테이블이면 권한이나 복사, 파일이면 경로, 토픽이면 구독, API 면 호출 |
| 얼마나 자주 새로 와야 하나 | 하루 한 번이면 배치(권한, 복사, 파일). 분 단위 아래면 흐름(토픽, CDC) |
| 누가 옮기나 | 우리가 당겨 가나, 그쪽이 밀어 주나. 실패했을 때 누가 다시 하나가 여기서 정해집니다 |

세 답을 받으면 아래 여덟 카드 중 하나가 남습니다. 도구 이름은 그 다음에 나옵니다. Sqoop 도 Debezium 도 Airbyte 도 카드 하나에 붙은 도구 이름일 뿐입니다.

## 2. 같은 창고면 권한만 줍니다

**두 팀이 같은 창고를 쓰면 데이터를 옮기지 않습니다. 읽기 권한 한 줄만 줍니다.**

쉽게 말하면 표는 그대로 두고 「이 표를 봐도 됩니다」 하고 허락만 하는 것입니다. 옆 팀이 자기 자리에서 같은 표를 열어 봅니다.

리포트 팀이 지훈 씨 팀과 같은 Hive 창고를 쓴다면 가장 쉬운 답이 있습니다. `adlog.ad_click` 테이블에 리포트 팀 계정의 읽기 권한을 주는 것입니다. 데이터는 그 자리에 있고 권한 한 줄만 갑니다. 복사가 없으니 두 팀이 같은 값을 봅니다. 새로 쌓이는 줄도 바로 보입니다.

## 3. 남의 DB 는 하루 한 번 끌어옵니다

**운영 DB 를 매일 정해진 시각에 통째로 또는 바뀐 행만 복사해 창고에 놓습니다. 어제까지의 값이면 충분할 때 씁니다.**

쉽게 말하면 남의 DB 에 있는 표를 매일 새벽 한 번 우리 창고에 복사해 두는 것입니다. 낮에는 그 복사본을 봅니다.

반대 상황도 있습니다. 지훈 씨 팀이 리포트 팀의 주문 DB 를 받아야 할 때입니다. 주문은 MySQL 에 있고 서비스가 쓰는 DB 라 직접 붙어 무거운 쿼리를 돌릴 수 없습니다. 그래서 매일 03시에 배치 작업이 그 DB 를 읽어 창고 테이블 `dw.orders` 에 씁니다. 카드에서 점이 한 번 몰려 지나가고 다음 주기까지 조용한 것이 배치입니다.

이 일을 오래 해 온 도구가 Sqoop 입니다. 다만 Sqoop 은 2021 년에 Apache 에서 은퇴한 프로젝트입니다. 지금은 Spark 가 JDBC 로 직접 읽거나, Airbyte 나 Fivetran 같은 도구가 같은 일을 합니다. 데이터 팀이 Sqoop 이라고 말하면 「DB 를 배치로 끌어오는 것」으로 들으면 됩니다.

## 4. 바뀐 것만 흘려보내려면 CDC 입니다

**DB 가 남기는 변경 로그를 읽어 토픽으로 보냅니다. 운영 DB 의 지금 상태를 몇 초 뒤에 창고에서 볼 수 있습니다.**

쉽게 말하면 남의 DB 에서 행이 바뀔 때마다 「이 행이 이렇게 바뀌었다」는 알림을 받아 우리 표를 따라 고치는 것입니다.

하루 한 번으로는 모자랄 때가 있습니다. 광고주가 예산을 바꾸면 몇 초 안에 창고에도 반영돼야 하는 경우입니다. 배치 주기를 1분으로 줄이면 운영 DB 가 1분마다 전체를 읽히느라 느려집니다. 다른 길이 있습니다. DB 는 모든 변경을 로그로 남깁니다. MySQL 은 이것을 binlog 라고 부릅니다. 이 로그를 읽어 토픽으로 보내는 것이 CDC 입니다. Change Data Capture 의 머리글자이고, 도구 이름은 Debezium 이 흔합니다.

## 5. 하루 한 번 대량이면 파일입니다

**파일을 저장소에 놓고 경로를 알려 줍니다. 받는 팀은 자기 시간에 읽습니다. 팀 간 전달에서 가장 흔한 방법입니다.**

쉽게 말하면 하루치 데이터를 파일로 저장해 두고 「이 폴더에 있어요」 하고 경로만 알려 주는 것입니다. 받는 팀이 편할 때 가져갑니다.

리포트 팀이 다른 클러스터를 쓴다면 2절의 권한은 쓸 수 없습니다. 이때 가장 흔한 답이 파일입니다. 지훈 씨 팀의 배치 작업이 매일 04시에 어제 클릭 로그를 parquet 파일로 저장소에 씁니다. 경로는 `s3://adlog/ad_click/dt=2026-09-17/` 처럼 날짜가 폴더 이름입니다. 리포트 팀에는 이 경로 하나를 알려 줍니다.

가상 데이터로 크기를 재 보겠습니다. 하루 클릭 228만 건에 한 줄 309 바이트면 약 705 MB 입니다. 파일 하나로 두기에 부담이 없는 크기입니다. parquet 은 열 단위로 압축해서 실제 파일은 이보다 작습니다.

## 6. 실시간이고 받는 팀이 여럿이면 토픽입니다

**토픽에 넣어 두면 여러 팀이 같은 메시지를 각자 속도로 받습니다. 보내는 쪽은 받는 팀이 몇인지 몰라도 됩니다.**

쉽게 말하면 데이터가 생길 때마다 한 줄씩 공용 줄에 넣어 두고, 원하는 팀이 각자 그 줄을 구독해 받는 것입니다. 받는 팀이 늘어도 넣는 쪽은 안 바뀝니다.

리포트 팀만이 아니었습니다. 대시보드 팀은 2초 안에, 예산 소진 확인 팀은 5초 안에 같은 클릭을 받아야 했습니다. 파일로는 안 됩니다. 이때 Kafka 토픽이 답입니다. 지훈 씨 팀의 서비스가 클릭 한 건을 토픽 `ad.click` 에 넣으면, 세 팀이 각자 그 토픽을 구독합니다. 초당 26.4 건이 세 갈래로 나갑니다.

## 7. 건별로 지금 값이 필요하면 API 입니다

**API 는 건 하나를 요청 하나로 묻는 방식입니다. 지금 값을 소량으로 볼 때 맞고, 대량 전달에는 맞지 않습니다.**

쉽게 말하면 필요한 것 하나를 그때그때 「이 광고 지금 상태 알려 줘」 하고 물어서 답을 받는 것입니다. 한 건에 한 번씩 묻습니다.

리포트 화면에서 광고 하나를 누르면 그 광고의 지금 상태가 보여야 합니다. 켜져 있나, 예산이 얼마 남았나. 이것은 어제 파일에 없습니다. 이때는 지훈 씨 팀이 API 를 열어 둡니다. `GET /v1/ads/9931` 을 부르면 지금 상태가 JSON 으로 옵니다. 요청 하나에 답 하나입니다.

## 8. 로그는 파이프라인에 태웁니다

**서비스에서 나오는 행동 기록은 수집기가 토픽으로, 토픽이 창고로 옮깁니다. 서비스 팀은 로그 한 줄만 남기면 됩니다.**

쉽게 말하면 서비스가 무슨 일이 있을 때마다 한 줄씩 기록을 남기면, 그 기록이 자동으로 창고까지 실려 가는 길입니다. 서비스 팀은 한 줄 남기는 것만 합니다.

여덟 방법 중 하나는 방향이 조금 다릅니다. 데이터를 가진 팀이 건네는 것이 아니라, 데이터 팀이 서비스 팀에 「이 로그를 남겨 주세요」라고 요청하는 모양입니다. 지훈 씨의 클릭 로그가 창고에 있는 것도 이 길을 지났기 때문입니다. 웹서버가 남긴 한 줄을 수집기(Filebeat)가 읽어 토픽에 넣고, 토픽에서 창고 테이블로 쌓입니다.

이 길의 특징은 한 번 깔면 계속 흐른다는 것입니다. 새 로그가 필요하면 서비스 팀이 한 줄을 더 남기고, 수집기부터 창고까지는 이미 있는 자리를 그대로 지납니다. 그래서 팀 간 요청서에는 필드 이름과 언제 남기는지만 적혀 있으면 됩니다. 이 길이 어떻게 생겼는지는 [데이터 파이프라인 입문](post.html?id=pipeline-push-and-pull) 편과 [Kafka 로그 파이프라인](post.html?id=kafka-log-pipeline) 편에 있습니다.

## 9. 창고 결과를 서비스로 되돌리려면 reverse ETL 입니다

**분석 결과를 서비스 옆 DB 에 옮겨 두고 서비스가 건별로 읽게 합니다. 창고는 느리고 서비스는 1ms 안에 답해야 하기 때문입니다.**

쉽게 말하면 창고에서 계산한 결과(이 사용자는 어느 그룹인가)를 서비스가 빨리 읽을 수 있는 DB 에 매일 옮겨 두는 것입니다. 서비스는 그 DB 만 봅니다.

마지막 방향은 반대입니다. 데이터 팀이 창고에서 계산한 결과를 서비스 팀이 써야 할 때입니다. 사용자 세그먼트가 예입니다. 창고에서 매일 계산한 `dw.user_segment` 를 광고 서버가 요청마다 읽어야 합니다. 창고에 직접 물으면 수 초가 걸리는데 광고 서버는 1ms 안에 답해야 합니다.

그래서 배치 작업이 매일 결과를 Redis 나 MySQL 같은 서비스 옆 DB 에 옮겨 놓습니다. 광고 서버는 그 DB 를 건별로 읽습니다. 이것을 reverse ETL 이라고 부릅니다. 창고로 들어가는 방향이 ETL 이라서 그 반대라는 뜻입니다. 함정은 낡은 값입니다. 매일 계산하면 서비스는 최대 하루 전 값을 봅니다. 세그먼트처럼 하루 늦어도 괜찮은 것에만 씁니다.

## 10. 그래서 무엇을 고르나

**세 질문의 답을 여덟 카드에 대면 하나가 남습니다. 같은 228만 건도 방법마다 전혀 다른 모양이 됩니다.**

지훈 씨 사례로 돌아가겠습니다. 리포트 팀은 다른 클러스터를 쓰고, 어제까지의 클릭이면 충분하고, 자기들이 읽어 가겠다고 했습니다. 세 답이 5절의 파일을 가리킵니다. 매일 04시 파일을 놓고 경로를 알려 주면 끝입니다. csv 를 매주 뽑는 일은 없습니다.

같은 하루 228만 건을 방법마다 옮겨 보면 크기가 이렇게 다릅니다. 가상 값이고, 한 줄 309 바이트로 계산했습니다.

| 방법 | 하루 228만 건이 이 모양이 됩니다 | 새로 오는 간격 | 누가 옮기나 |
|---|---|---|---|
| 테이블 권한 | 옮기지 않음. 권한 한 줄 | 쌓이는 즉시 | 아무도 |
| DB 배치 | 표 한 번 복사, 약 705 MB | 하루 한 번 | 받는 팀의 배치 |
| CDC | 메시지 228만 개가 종일 흐름 | 몇 초 | 도구(Debezium)가 계속 |
| 파일 | 파일 하나 약 705 MB | 하루 한 번 | 주는 팀이 놓고, 받는 팀이 읽음 |
| 토픽 | 초당 26.4 건이 흐름 | 즉시 | 주는 팀이 넣고, 받는 팀이 구독 |
| API | 요청 228만 번 | 부를 때마다 | 받는 팀이 매번 |
| 로그 파이프라인 | 로그 228만 줄 → 토픽 → 테이블 | 초 단위 | 수집기가 계속 |
| reverse ETL | 결과 표 한 번 복사 | 하루 한 번 | 데이터 팀의 배치 |

표에서 보이는 것이 있습니다. 놓여 있는 것(권한, 배치, 파일, reverse ETL)은 하루 한 번이고, 흐르는 것(CDC, 토픽, 로그)은 초 단위입니다. API 만 「받는 팀이 매번」입니다. 그래서 API 는 전달이 아니라 조회입니다.

슬랙으로 csv 를 보내는 것도 표에 넣을 수 있습니다. 「누가 옮기나」의 답이 사람이고, 「새로 오는 간격」의 답이 「부탁할 때마다」입니다. 한 번은 괜찮습니다. 두 번째 부탁이 오면 이 표의 한 줄로 올릴 때입니다.

## 한눈 정리

| 질문 | 한 줄 답 |
|---|---|
| 데이터를 건네는 방법이 몇 가지인가 | 여덟 가지. 오가는 모양은 테이블, 파일, 토픽, API 넷 |
| 무엇을 먼저 물어야 하나 | 어디에 어떤 모양으로 있나, 얼마나 자주 새로 와야 하나, 누가 옮기나 |
| 같은 창고를 쓰면 | 권한만 줍니다. 데이터는 안 움직입니다 |
| 하루 한 번 대량이면 | 파일을 놓고 경로를 알려 줍니다 |
| 실시간이고 받는 팀이 여럿이면 | 토픽에 넣어 두고 각자 구독합니다 |
| 운영 DB 의 변경을 몇 초 안에 | CDC. 변경 로그를 토픽으로 |
| Sqoop 이 무엇인가 | DB 를 배치로 끌어오던 도구. 2021 년 은퇴. 지금은 Spark JDBC, Airbyte |
| API 로 대량을 받아도 되나 | 안 맞습니다. 228만 건이면 요청 228만 번입니다 |
| 분석 결과를 서비스가 써야 하면 | reverse ETL. 서비스 옆 DB 에 옮겨 두고 건별로 읽게 합니다 |

## 헷갈리기 쉬운 점

- **도구 이름부터 고르지 마세요.** 모양과 주기와 옮기는 쪽을 먼저 정하면 도구는 한두 개로 좁혀집니다.
- **권한을 줄 때 읽기만 주세요.** 지우거나 고치는 권한까지 주면 팀 A 의 테이블이 팀 B 의 손에 흔들립니다.
- **증분 복사는 지워진 행을 모릅니다.** 갱신 시각으로 고르면 삭제는 안 보입니다. 삭제가 중요하면 CDC 입니다.
- **파일은 다 썼다는 표시가 있어야 합니다.** 쓰는 중에 읽으면 반쪽만 읽습니다.
- **토픽은 7일치만 들고 있습니다.** 늦게 온 소비자는 앞을 못 받습니다. 파일과 같이 두는 이유입니다.
- **API 는 조회입니다.** 화면 한 줄에 한 번씩 부르면 화면 하나에 요청 수백 번이 됩니다.
- **reverse ETL 은 하루 전 값입니다.** 그것이 괜찮은 용도에만 씁니다.
- **csv 를 두 번째 부탁받으면** 그때가 여덟 방법 중 하나로 올릴 때입니다.
