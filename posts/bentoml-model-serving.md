지훈 씨의 아홉째 주입니다. 분석 팀이 새 pCVR 예비 모델을 만들어 왔습니다. 아직 광고에 쓸 것은 아니고, 운영자가 쓰는 내부 화면에서 먼저 값을 봐 보자는 것이었습니다. 요청은 초당 마흔 건쯤이라고 했습니다.

지훈 씨는 지난주에 추론 서버를 들여다봤습니다. 모델 파일을 열어 메모리에 올리고, 가짜 요청으로 몸을 푸는 코드가 있었습니다. 준비 신호를 켜고, 후보를 한 텐서로 묶고, 두 버전을 같이 싣는 코드도 거기 다 있었습니다. 그것을 이 작은 모델에도 또 만들어야 하나 싶었습니다.

선배는 다르게 답했습니다. 「그건 BentoML 로 하면 하루면 떠요. 그런데 메인 pCTR 서버는 그걸로 안 해요.」

**같은 회사 안에서 왜 하나는 도구로 띄우고 하나는 직접 짜나요?**

모델 파일 하나를 받아 요청에 답하는 서비스로 만들어 주는 도구를 모델 서빙 프레임워크라고 부릅니다. BentoML 은 그중 파이썬으로 쓰는 것입니다. 이 글은 그 도구가 무엇을 대신해 주고 어디서 안 맞는지를 봅니다. 이것을 알면 새 모델을 띄우자는 말이 나왔을 때 직접 짤지 도구를 쓸지를 예산 숫자로 정할 수 있습니다.

> **한 줄 요약:** 직접 짠 추론 서버에 들어 있던 일곱 가지 중 여섯을 도구가 이미 갖고 있습니다. 코드 1,800줄이 서비스 파일 마흔 줄이 됩니다. 대신 요청을 받는 층이 파이썬이라 고정 비용 1.68ms 가 붙고, 8ms 예산에서 초과율이 3.53% 에서 10.69% 로 세 배가 됩니다. 200ms 예산인 내부 도구에서는 둘 다 0.00% 라 그 차이가 안 보입니다.

> **골라 읽는 법** — 절이 여덟 개인 글입니다. 절마다 카드 한 장이나 표 하나가 들어 있어 그것만 보고 넘어가도 됩니다.
>
> - 직접 짤 때 만들어야 하는 것 일곱 → 1절
> - 도구가 대신하는 것과 서비스 파일 한 장 → 2절
> - 모델을 저장소에 넣고 태그로 꺼내기 → 3절
> - 굳혀서 이미지 한 장으로 → 4절
> - 모아 보내기가 값을 하는 자리 → 5절
> - 8ms 예산에서 파이썬 층의 값 → 6절
> - 어디에 쓰고 어디에 안 쓰나 → 7절
> - 담장 안과 열린 RTB → 8절

이 글의 줄 수, 시간, 크기는 전부 설명을 위한 가상 값입니다. 모델 서버 12대와 모델 호출 예산 8ms, 후보 800건은 [추론 서버](post.html?id=inference-server) 편과 같은 값입니다. 신경망 38MB 와 임베딩 표 27.7GB, 준비 신호 41초도 그 편의 값입니다. 이미지와 검문 이야기는 [Docker 와 CI](post.html?id=container-ci-pipeline) 편에서 이어집니다. 코드는 BentoML 의 모양을 옮긴 것이고, 판이 올라가면서 이름과 옵션이 바뀐 적이 있으니 옮겨 쓰기 전에 그 판의 문서를 봅니다. 카드 속 색은 넷입니다. 파랑은 놓여 있는 것(모델 파일, 저장소, 이미지)이고 벽돌색은 지금 오는 요청과 값을 치르는 자리입니다. 먹색은 서비스와 서버이고 회색은 만드는 작업(굳히기, 묶기)입니다.

## 1. 직접 짠 추론 서버에 들어 있는 것이 일곱입니다

**지난주에 본 추론 서버는 모델을 부르는 코드 한 줄이 아니었습니다. 그 한 줄을 둘러싼 여섯 가지가 더 있었습니다.**

쉽게 말하면 모델에 숫자를 넣어 답을 받는 계산은 코드 몇 줄입니다. 그것을 요청으로 받고, 죽지 않게 지키고, 바꿔 달 수 있게 만드는 일이 나머지 전부입니다.

지훈 씨가 지난주에 읽은 코드를 하는 일로 나눠 적으면 일곱 덩어리입니다. 아래 줄 수는 그 저장소를 세어 본 가상 값입니다.

| 무엇을 하나 | 왜 필요한가 | 줄 수 |
|---|---|---|
| HTTP 로 요청을 받고 답한다 | 앱과 API 서버가 말을 걸 창구 | 220 |
| 모델 파일을 열어 메모리에 올린다 | 매일 새벽 새 파일이 나온다 | 180 |
| 요청에 실린 후보를 한 텐서로 만든다 | 800건을 하나씩 부르면 96ms | 260 |
| 가짜 요청으로 몸을 푼다 | 안 하면 첫 30초가 2.5배 느리다 | 90 |
| 준비 신호를 켠다 | 게이트웨이가 이 신호만 보고 요청을 보낸다 | 70 |
| 두 버전을 같이 싣고 가리키는 곳을 바꾼다 | 되돌리기가 초 단위여야 한다 | 310 |
| 지연과 오류를 재서 내보낸다 | 대시보드와 알람의 재료 | 240 |

일곱을 더하면 1,370줄이고, 여기에 설정과 시험이 붙어 1,800줄쯤 됩니다. 그중 모델을 부르는 계산은 넷째 줄 안쪽의 열몇 줄뿐입니다. 나머지는 모델이 무엇이든 똑같이 필요한 것들입니다.

바로 이 점이 도구가 생긴 이유입니다. 모델마다 다른 것은 가운데 열몇 줄이고, 둘러싼 1,300여 줄은 모델이 바뀌어도 그대로입니다. 새 모델을 하나 띄울 때마다 그것을 다시 짜는 일은 값이 비쌉니다.

## 2. 도구는 그중 여섯을 이미 갖고 있습니다

**BentoML 에 쓰는 것은 클래스 하나입니다. 모델을 어디서 꺼내고 요청이 오면 무엇을 계산할지만 적습니다. 나머지 여섯은 도구가 갖고 있습니다.**

쉽게 말하면 앞 절의 표에서 넷째 줄만 내가 쓰고 나머지 여섯 줄은 도구에 맡기는 것입니다. 내가 쓴 코드는 마흔 줄쯤이 됩니다.

파이썬 파일 하나에 클래스 하나를 두고 표시를 붙입니다. 클래스에 붙이는 표시가 「이것이 서비스다」이고, 함수에 붙이는 표시가 「이 함수가 주소 하나다」입니다. 모양은 이렇습니다.

```python
# service.py — 이 파일 하나가 서비스 하나가 된다.
# 표시(데코레이터) 두 개가 핵심이다. 클래스에 붙은 것이 「이것이 서비스다」,
# 함수에 붙은 것이 「이 함수가 주소 하나다」라는 뜻이다.
import bentoml
import numpy as np

@bentoml.service(
    resources={"cpu": "2"},            # 이 서비스 하나가 쓰는 자원
    traffic={"timeout": 30},           # 이 초를 넘기면 끊는다
)
class PcvrPreview:
    def __init__(self) -> None:
        # 모델 저장소에서 태그로 꺼낸다. 파일 경로를 코드에 안 적는다.
        self.model = bentoml.pytorch.load_model("pcvr_preview:latest")

    @bentoml.api
    def predict(self, feats: np.ndarray) -> np.ndarray:
        """요청에 실려 온 숫자 묶음을 그대로 모델에 넣고 확률을 돌려준다."""
        return self.model(feats).numpy()
```

스물몇 줄입니다. 여기에 없는 것을 세어 보면 도구가 무엇을 하는지가 보입니다. HTTP 를 받는 코드가 없고, 준비 신호를 켜는 코드가 없고, 지연을 재는 코드가 없습니다. 도구가 서비스를 띄울 때 그 셋을 같이 붙입니다. 상태를 묻는 주소와 지표를 내보내는 주소도 같이 생깁니다.

일곱 중 하나는 여전히 내 몫입니다. 후보를 한 텐서로 만드는 일입니다. 요청이 어떤 모양으로 오고 그것을 어떤 숫자 묶음으로 바꿀지는 모델마다 다르기 때문입니다. 도구는 그 함수를 부를 자리만 만들어 줍니다.

## 3. 모델은 저장소에 넣고 태그로 꺼냅니다

**코드에 파일 경로를 적지 않습니다. 모델을 저장소에 넣으면서 이름과 판을 붙이고, 코드는 그 이름으로 꺼냅니다.**

쉽게 말하면 「이 폴더의 이 파일」이라고 적으면 파일이 옮겨질 때마다 코드를 고쳐야 합니다. 이름표를 붙여 두고 이름으로 부르면 파일이 어디 있든 상관없습니다.

학습이 끝나면 모델을 저장소에 넣습니다. 넣을 때 이름을 주면 판이 자동으로 하나 붙습니다.

```text
$ python save_model.py
Model(tag="pcvr_preview:g7k2mqx4a")            저장 완료

$ bentoml models list
 Tag                          Size      Creation Time
 pcvr_preview:g7k2mqx4a       41.2 MiB  2026-10-04 04:12:31
 pcvr_preview:f3n9pqw1b       41.2 MiB  2026-10-03 04:11:58
```

코드가 `pcvr_preview:latest` 라고 적으면 맨 위 줄을 집습니다. 특정 판을 박아 두고 싶으면 `pcvr_preview:f3n9pqw1b` 라고 적습니다. 배포가 나간 뒤 모델만 되돌리고 싶을 때 이 한 줄만 바꾸면 됩니다.

이것이 [모델 버전과 재현](post.html?id=model-versioning-reproducibility) 편의 레지스트리와 겹쳐 보이는데, 담는 것이 다릅니다. 도구의 저장소는 파일과 그 판을 담고, 레지스트리는 그 모델이 어떤 재료로 만들어졌고 지금 상태가 무엇인지를 담습니다. 실무에서는 둘을 같이 씁니다. 레지스트리가 「v417 이 운영이다」라고 말하고, 도구의 저장소가 그 v417 의 파일을 들고 있습니다.

주의할 것이 하나 있습니다. 저장소에 들어가는 것은 모델 파일뿐입니다. 신경망 38MB 는 들어가지만 임베딩 표 27.7GB 는 안 들어갑니다. 그 표는 여전히 임베딩 서비스 한 곳에 있고 서비스가 요청마다 필요한 줄만 가져옵니다. 그 이유는 [추론 서버](post.html?id=inference-server) 편에 있습니다.

결정은 코드에 경로 대신 태그를 적는다입니다. 다음 절은 그 코드와 모델을 한 덩어리로 굳히는 자리입니다.

## 4. 굳히면 이미지 한 장이 됩니다

**서비스 파일과 모델과 라이브러리 목록을 한 묶음으로 굳힌 것을 Bento 라고 부릅니다. 그것을 도커 이미지 한 장으로 바꾸면 앞 편의 배포 길에 그대로 올라갑니다.**

쉽게 말하면 굳히기는 「이 서비스가 돌아가는 데 필요한 것을 전부 한 상자에 담는」 일입니다. 담고 나면 어느 서버에서 열어도 같은 것이 나옵니다.

굳힐 때 무엇을 담을지는 파일 하나에 적습니다.

```yaml
# bentofile.yaml — 무엇을 굳혀 담을지 적는다
service: "service.py:PcvrPreview"      # 어느 파일의 어느 클래스가 서비스인가
include:
  - "service.py"
  - "features.py"                      # 요청을 숫자 묶음으로 바꾸는 코드
python:
  requirements_txt: "./requirements.txt"
models:
  - "pcvr_preview:latest"              # 이 태그의 모델 파일을 같이 담는다
docker:
  python_version: "3.11"
```

명령 두 줄이면 이미지가 나옵니다. 첫 줄이 Bento 를 만들고 둘째 줄이 그것을 도커 이미지로 바꿉니다.

```text
$ bentoml build
Successfully built Bento(tag="pcvr_preview:h4d8rn2xc")

$ bentoml containerize pcvr_preview:h4d8rn2xc
Successfully built docker image "pcvr_preview:h4d8rn2xc"    1.4GB
```

여기서 앞 편과 이어집니다. [Docker 와 CI](post.html?id=container-ci-pipeline) 편에서 본 이미지가 바로 이것입니다. 다만 층의 모양이 조금 다릅니다. 직접 짠 추론 서버의 이미지는 1.1GB 였고 모델 파일이 이미지 밖에 있었습니다. 도구가 만든 이미지는 1.4GB 이고 모델 파일이 안에 들어 있습니다.

이 차이가 뒤에 두 가지를 바꿉니다. 첫째, 모델만 바꾸려 해도 이미지를 다시 만들어야 합니다. 매일 새 모델이 나오는 pCTR 서버라면 매일 이미지가 새로 생깁니다. 둘째, 굳힌 것이 한 덩어리라 재현이 쉽습니다. 그 이미지 하나만 있으면 코드와 모델과 라이브러리가 그때 그대로입니다.

## 5. 모아 보내기는 요청이 작을 때만 값을 합니다

**요청 여럿을 한 묶음으로 모아 모델에 한 번만 넣는 기능이 있습니다. 표시에 옵션 두 개를 주면 켜집니다. 그런데 이 기능이 값을 하는 자리는 좁습니다.**

쉽게 말하면 모아 보내면 건당 계산이 줄어드는 대신 모이기를 기다리는 시간이 붙습니다. 이미 요청 하나가 큰 경우에는 줄어드는 몫이 거의 없고 기다림만 남습니다.

켜는 것은 한 줄입니다. 창 시간과 묶음 최대 크기를 같이 적습니다.

```python
    @bentoml.api(batchable=True, max_batch_size=32, max_latency_ms=2)
    def predict(self, feats: np.ndarray) -> np.ndarray:
        return self.model(feats).numpy()
```

세 경우를 놓고 세어 보겠습니다. 가정은 추론 시간이 고정 0.116ms 에 후보 한 건당 0.0036ms 라는 것이고, 이것은 [추론 서버](post.html?id=inference-server) 편의 값입니다. 요청은 푸아송으로 오고 창 2ms 가 차거나 묶음이 32건이 되면 보냅니다.

```python
# 모아 보내기(요청 여럿을 한 묶음으로 추론)가 언제 값을 하는지 센다.
# 얻는 것은 건당 계산이 줄어드는 몫이고, 치르는 것은 모이기를 기다리는 시간이다.
# 추론 시간 = 고정 0.116ms + 후보 한 건당 0.0036ms (추론 서버 편의 값).
# 요청은 푸아송으로 오고, 창 2ms 가 차거나 묶음이 32건이 되면 보낸다. 전부 가상 값이다.
import random

FIXED, PER = 0.116, 0.0036
WINDOW, MAXB, N = 2.0, 32, 60_000

def run(qps, cand):
    """cand 는 요청 하나에 실려 오는 후보 수. 묶음 크기와 평균 대기를 돌려준다."""
    random.seed(4104)
    lam = qps / 1000.0
    waits, sizes, done = [], [], 0
    while done < N:
        t, n, arrivals = 0.0, 1, [0.0]
        while n < MAXB:
            gap = random.expovariate(lam)
            if t + gap > WINDOW:
                break
            t += gap; n += 1; arrivals.append(t)
        close = t if n == MAXB else WINDOW
        waits += [close - a for a in arrivals]
        sizes.append(n); done += n
    size = sum(sizes) / len(sizes)
    return size, sum(waits) / len(waits)

print('경우 / 묶음 / 대기 / 건당 계산 (혼자 → 모아서) / 판정')
for name, qps, cand in [('내부 도구 40 QPS, 요청에 후보 1건', 40, 1),
                        ('같은 도구 2,000 QPS, 후보 1건', 2000, 1),
                        ('광고 서빙 2,639 QPS, 후보 800건', 2639, 800)]:
    size, wait = run(qps, cand)
    alone = FIXED + PER * cand                      # 혼자 보낼 때 건당
    batched = (FIXED + PER * cand * size) / size    # 묶어 보낼 때 건당
    cut = (1 - batched / alone) * 100
    verdict = '얻는 것이 크다' if cut > 40 else '거의 안 준다' if cut < 10 else '반반이다'
    print(f'  {name}')
    print(f'    묶음 {size:.1f}건, 대기 {wait:.2f}ms, 건당 {alone:.3f} → {batched:.3f}ms '
          f'({cut:.0f}% 절감) — {verdict}')

print('\n요청 하나가 이미 크면 묶어도 건당 계산이 거의 안 준다. 대기만 붙는다')
print('요청 하나가 작고 예산이 넉넉할 때만 모아 보내기가 값을 한다')

# 출력:
# 경우 / 묶음 / 대기 / 건당 계산 (혼자 → 모아서) / 판정
#   내부 도구 40 QPS, 요청에 후보 1건
#     묶음 1.1건, 대기 1.93ms, 건당 0.120 → 0.111ms (7% 절감) — 거의 안 준다
#   같은 도구 2,000 QPS, 후보 1건
#     묶음 5.0건, 대기 1.20ms, 건당 0.120 → 0.027ms (78% 절감) — 얻는 것이 크다
#   광고 서빙 2,639 QPS, 후보 800건
#     묶음 6.3건, 대기 1.16ms, 건당 2.996 → 2.899ms (3% 절감) — 거의 안 준다
#
# 요청 하나가 이미 크면 묶어도 건당 계산이 거의 안 준다. 대기만 붙는다
# 요청 하나가 작고 예산이 넉넉할 때만 모아 보내기가 값을 한다
```

세 줄이 서로 다른 말을 합니다. 첫 줄은 요청이 너무 드물어 묶음이 1.1건입니다. 모을 것이 없는데 창 2ms 를 기다리느라 대기만 1.93ms 붙습니다. 둘째 줄은 요청이 자주 오고 요청 하나가 작아서, 묶으면 건당 계산이 78% 줍니다. 여기가 이 기능이 값을 하는 자리입니다.

셋째 줄이 광고 서빙입니다. 요청 하나에 이미 후보 800건이 실려 있습니다. 여섯 건을 묶으면 후보 4,800건짜리 한 텐서가 됩니다. 고정 비용 0.116ms 를 여섯이 나눠 갖는 것이 전부라 건당 3% 밖에 안 줍니다. 그 3% 를 얻자고 대기 1.16ms 를 치릅니다. 예산이 8ms 인 자리에서 1.16ms 는 15% 입니다.

## 6. 8ms 예산에서는 파이썬 층의 값이 큽니다

**추론 계산은 둘이 같습니다. 다른 것은 요청을 받아 넘겨주는 층입니다. 그 층이 파이썬이면 요청마다 고정 비용이 붙고, 가끔 크게 튑니다.**

쉽게 말하면 도구가 대신해 주는 여섯 가지는 파이썬으로 짜여 있습니다. 그 편함의 값이 요청마다 조금씩 나갑니다. 예산이 넉넉하면 안 보이고 빠듯하면 바로 보입니다.

같은 모델을 두 가지로 서빙했다고 하고 요청 20만 건의 시간을 뽑아 보겠습니다. 추론 계산은 양쪽 모두 평균 2.80ms 로 같게 두고, 앞뒤 층의 고정 비용만 다르게 놓습니다.

```python
# 같은 모델을 두 가지로 서빙했을 때 요청 한 건에 드는 시간을 뽑는다.
# 추론 계산은 둘이 같다. 다른 것은 그 앞뒤에서 HTTP 를 받고 넘겨주는 층이다.
# 직접 짠 서버는 컴파일된 코드가, 도구로 만든 서버는 파이썬이 그 층을 맡는다.
# 수치는 전부 가상 값이고 시드를 고정해 누가 돌려도 같은 값이 나온다.
import random

N = 200_000
INFER_MU, INFER_SD = 2.80, 0.45      # 추론 계산 자체 (후보 800건을 한 텐서로)
JITTER_P, JITTER_MU = 0.15, 3.5      # 가끔 튀는 몫 — 메모리 정리, 다른 요청과 겹침

def draw(fixed, extra_p, extra_mu):
    """앞뒤 층의 고정 비용 + 추론 + 가끔 튀는 몫. extra 는 파이썬 층이 더 자주 겪는 몫이다."""
    t = fixed + max(0.4, random.gauss(INFER_MU, INFER_SD))
    if random.random() < JITTER_P:
        t += random.expovariate(1 / JITTER_MU)
    if random.random() < extra_p:
        t += random.expovariate(1 / extra_mu)
    return t

def stats(name, fixed, extra_p, extra_mu):
    random.seed(4104)
    xs = sorted(draw(fixed, extra_p, extra_mu) for _ in range(N))
    p50, p99 = xs[N // 2], xs[int(N * 0.99)]
    return name, p50, p99, sum(1 for x in xs if x > 8) / N * 100, sum(1 for x in xs if x > 200) / N * 100

rows = [stats('직접 짠 서버', 0.12, 0.0, 1.0),
        stats('도구로 만든 서버', 1.80, 0.09, 6.0)]

print('서버 / p50 / p99 / 8ms 초과 / 200ms 초과')
for n, p50, p99, o8, o200 in rows:
    print(f'  {n}  {p50:.2f}ms  {p99:.2f}ms  {o8:.2f}%  {o200:.2f}%')

print(f'\n8ms 예산: 초과율이 {rows[0][3]:.2f}% 에서 {rows[1][3]:.2f}% 로 {rows[1][3] / rows[0][3]:.1f}배')
print(f'200ms 예산: 둘 다 {rows[1][4]:.2f}% 다. 예산이 넉넉하면 이 차이가 안 보인다')
print(f'파이썬 층이 더하는 고정 비용 {1.80 - 0.12:.2f}ms 는 예산 8ms 의 {(1.80 - 0.12) / 8 * 100:.0f}% 다')

# 출력:
# 서버 / p50 / p99 / 8ms 초과 / 200ms 초과
#   직접 짠 서버  3.01ms  12.64ms  3.53%  0.00%
#   도구로 만든 서버  4.75ms  20.08ms  10.69%  0.00%
#
# 8ms 예산: 초과율이 3.53% 에서 10.69% 로 3.0배
# 200ms 예산: 둘 다 0.00% 다. 예산이 넉넉하면 이 차이가 안 보인다
# 파이썬 층이 더하는 고정 비용 1.68ms 는 예산 8ms 의 21% 다
```

읽을 것은 두 줄입니다. 8ms 예산에서 초과율이 3.53% 와 10.69% 로 세 배 벌어지고, 200ms 예산에서는 둘 다 0.00% 입니다. 같은 도구가 한쪽에서는 안 되고 다른 쪽에서는 아무 문제가 없습니다.

세 배가 나오는 이유는 둘입니다. 고정 비용 1.68ms 가 예산 8ms 의 21% 를 미리 먹고 들어갑니다. 그리고 파이썬은 메모리 정리가 끼어드는 일이 더 잦아 p99 가 12.64ms 에서 20.08ms 로 늘어납니다. 평균은 1.74ms 차이인데 p99 는 7.44ms 차이입니다. 예산을 넘기는 것은 평균이 아니라 꼬리입니다. 이 성질은 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편에서 본 것과 같습니다.

여기서 나오는 결정은 하나입니다. 예산에서 고정 비용이 차지하는 비율을 먼저 재고, 그 비율이 20% 를 넘으면 도구를 쓰지 않습니다. 다음 절이 그 기준을 표로 옮긴 것입니다.

## 7. 그래서 어디에 쓰고 어디에 안 쓰나

**예산과 요청량과 모델 개수 셋이 답을 정합니다. 예산이 넉넉하고 모델이 여럿이면 도구가 이깁니다. 예산이 빠듯하고 모델이 하나면 직접 짠 것이 이깁니다.**

쉽게 말하면 도구는 사람 시간을 아끼고 기계 시간을 조금 더 씁니다. 어느 쪽이 비싼지가 자리마다 다릅니다.

지훈 씨 팀의 모델을 늘어놓고 세 가지를 물어보면 이렇게 나뉩니다. 아래 값은 전부 가상입니다.

| 어디에 쓰나 | 예산 | 요청량 | 모델 개수 | 무엇을 쓰나 |
|---|---|---|---|---|
| 메인 pCTR 서빙 | 8ms | 초당 2,639건 | 하나 | 직접 짠 서버 |
| 운영자 내부 화면의 pCVR 예비 | 200ms | 초당 40건 | 예비 모델 여럿 | 도구 |
| 분석가가 돌리는 배치 채점 | 없음 | 하루 한 번 | 그때마다 다름 | 도구 |
| 광고주 리포트의 예상 전환 | 2초 | 초당 30건 | 둘 | 도구 |
| 후보 추리기의 유저 타워 | 3ms | 초당 2,639건 | 하나 | 직접 짠 서버 |

가운데 세 줄이 도구가 이기는 자리입니다. 셋 다 예산이 밀리초가 아니라 초 단위이거나 아예 없고, 모델이 자주 바뀌거나 여럿입니다. 이런 자리에서 직접 짜면 1,800줄을 모델마다 다시 만들게 됩니다.

위아래 두 줄이 직접 짠 것이 이기는 자리입니다. 예산이 한 자리 밀리초이고 요청량이 크고 모델이 하나입니다. 1,800줄을 한 번 만들어 두면 매일 그 값을 돌려받습니다.

한 가지 덧붙일 것이 있습니다. 둘 중 하나를 고르는 것이 아니라 섞어 쓰는 팀이 많습니다. 새 모델을 도구로 먼저 띄워 값을 보고, 실제로 광고에 나갈 것이 정해지면 그때 직접 짠 서버로 옮깁니다. 지훈 씨 팀이 하려는 것도 이것입니다.

## 8. 무대가 바뀌면 고르는 기준도 바뀝니다

**예산이 정해지는 방식이 무대마다 다릅니다. 담장 안은 우리가 정하고, 열린 RTB 는 거래소가 정합니다. 그래서 도구를 쓸 수 있는 자리의 넓이도 다릅니다.**

쉽게 말하면 예산을 우리가 정할 수 있으면 도구를 쓸 자리를 만들 수도 있습니다. 남이 정해 주면 그 안에서 맞춰야 합니다.

### 담장 안에서는 예산을 우리가 나눠 씁니다 [무대: 닫힌 생태계]

한 회사가 앱과 광고 서버를 다 가진 담장 안에서는 응답 전체에 주어진 시간을 우리가 구간에 나눠 줍니다. 모델 호출에 8ms 를 준 것도 우리 결정입니다. 그래서 어떤 모델은 예산을 넉넉히 받을 수 있습니다.

예를 들어 광고를 고르는 길에 안 걸리는 모델이 있습니다. 운영자 화면의 예비 모델, 광고주 리포트의 예상 전환, 하루 한 번 도는 배치 채점이 그것입니다. 이 셋은 요청이 광고 경매를 지나지 않으므로 예산이 초 단위입니다. 담장 안에서는 이런 자리가 많습니다. 자사 데이터로 만드는 내부 도구가 많기 때문입니다.

지훈 씨의 pCVR 예비 모델이 그 자리입니다. 도구로 하루면 뜨고, 값을 보다가 광고에 쓰기로 정해지면 그때 옮깁니다. 옮길 때 다시 쓰는 것은 앞뒤 층이고 모델과 피처 코드는 그대로 갑니다.

### 열린 RTB 에서는 거래소가 정한 시간 안에 답해야 합니다 [무대: 열린 RTB]

매체와 광고 서버가 다른 회사인 열린 RTB 에서는 입찰 요청에 답하는 시간을 거래소가 정합니다. 흔히 100ms 안쪽이고 그 안에 네트워크 왕복이 들어 있어, 우리 서버가 쓸 수 있는 시간은 더 짧습니다. 늦으면 응답이 버려지고 그 요청은 로그에도 안 남습니다.

그래서 입찰 경로에 있는 모델은 도구로 띄우기 어렵습니다. 고정 비용 1.68ms 가 예산에서 차지하는 비율이 담장 안보다 큽니다. 게다가 거래소마다 시간이 달라 가장 빠듯한 곳에 맞춰야 합니다.

대신 이 무대에도 도구를 쓸 자리가 있습니다. 입찰 경로 밖에서 도는 것들입니다. 광고주에게 보내는 리포트, 소재를 미리 채점해 두는 배치, 세그먼트를 만드는 잡이 그것입니다. 무대가 달라져도 기준은 같습니다. 예산이 밀리초인가 초인가를 먼저 봅니다.

## 헷갈리기 쉬운 점

**도구가 느린 것이 아닙니다.** 추론 계산은 양쪽이 같은 2.80ms 입니다. 다른 것은 요청을 받아 넘겨주는 층이고, 그 층의 값이 1.68ms 입니다. 예산이 200ms 면 그 1.68ms 는 0.8% 라 아무도 못 느낍니다.

**평균이 아니라 꼬리가 예산을 넘깁니다.** 두 서버의 평균 차이는 1.74ms 인데 p99 차이는 7.44ms 입니다. 평균만 보고 「2ms 차이면 괜찮다」고 하면 초과율이 세 배가 된 것을 놓칩니다.

**모아 보내기는 늘 이득이 아닙니다.** 요청 하나에 이미 후보 800건이 실려 있으면 묶어도 건당 3% 밖에 안 줍니다. 그 3% 를 얻자고 대기 1.16ms 를 치릅니다. 요청 하나가 작을 때만 켭니다.

**모델 저장소와 모델 레지스트리는 다른 것입니다.** 도구의 저장소는 파일과 판을 담고, 레지스트리는 재료와 상태를 담습니다. 실무에서는 둘을 같이 씁니다.

**이미지 안에 모델을 담으면 되돌리기가 달라집니다.** 모델만 바꾸려 해도 이미지를 다시 만들어야 합니다. 매일 새 모델이 나오는 서버라면 매일 이미지가 새로 생기고, 앞 편에서 본 되돌리기 한 줄이 이미지 태그 바꾸기가 됩니다.
