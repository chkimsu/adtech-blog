UCB1 이 몇 주째 배너 소재 하나를 두고 같은 답을 냅니다. “이 소재가 제일 낫다.” 소재는 광고로 내보내는 배너 한 장 한 장을 말합니다. UCB1 은 소재마다 노출과 클릭을 세어 두었다가 관측한 평균 클릭률(노출 가운데 클릭된 비율)에 탐색 보너스(적게 보여 준 소재일수록 커지는 가산점)를 더한 점수가 가장 높은 소재를 고르는 알고리즘입니다.

그런데 담당자가 로그를 지면(광고가 실리는 자리)별로 나눠 보니 이상한 점이 있습니다. 뉴스 지면의 오전에는 그 소재가 확실히 1등이 맞지만 커뮤니티 지면의 오전에는 다른 소재가 클릭을 훨씬 더 많이 받고 있었습니다. 시간대를 저녁으로 바꿔 나눠 보면 그 순위가 또 한 번 뒤집힙니다.

UCB1 은 광고가 나가는 곳이 뉴스 지면인지 커뮤니티 지면인지, 지금이 오전인지 저녁인지를 아예 입력으로 받지 않아서 지면과 시간대에 따라 순위가 바뀌는 차이를 볼 방법이 없습니다. 소재마다 노출과 클릭만 세어 전체 평균이 가장 높은 소재 하나를 계속 밀 뿐입니다. 광고가 나가는 순간의 이런 상황 정보, 곧 지면과 시간대와 유저를 컨텍스트(context)라고 부릅니다.

**지면, 시간대, 유저마다 정답이 다르다는 사실을 알고리즘에 알려 주려면 무엇이 필요할까요?**

UCB1 에서 컨텍스트를 점수에 넣는 LinUCB 로, 다시 소재끼리 배운 것을 나눠 쓰는 Hybrid LinUCB 로 이어지는 계보 전체가 이 질문 하나에서 나왔습니다.

> 한 줄 요약: UCB1 은 컨텍스트를 입력으로 받지 않아 '평균적으로 좋은 소재' 하나만 밀어붙입니다. 이 글의 시뮬레이션에서는 컨텍스트마다 UCB1 을 따로 돌리기만 해도 4,000회 동안 받은 클릭이 192회에서 245회로 27.6% 늘었습니다. LinUCB 는 컨텍스트를 점수 계산에 넣어 '이 상황에 맞는 소재'를 고르지만 소재마다 배운 것을 따로 쌓기 때문에 새로 들어온 소재는 매번 처음부터 다시 배웁니다. Hybrid LinUCB 는 배운 것의 일부를 모든 소재가 함께 쓰게 해서 새 소재도 조금은 아는 상태로 출발시킵니다.

## 1. 가데이터: 평균만 보는 UCB1 이 놓치는 조합별 승자

**UCB1 에는 지면과 시간대를 받는 입력이 아예 없어서 상황마다 다른 정답을 전체 평균 하나로 뭉쳐 버립니다.**

조합마다 순위가 뒤집히는 상황을 작은 가데이터(설명을 위해 만든 숫자)로 만들어 보면 평균만 보는 UCB1 이 무엇을 놓치는지 숫자로 보입니다. 소재 A 와 소재 B, 지면 두 종류(뉴스, 커뮤니티), 시간대 두 종류(오전, 저녁)를 가정하면 지면과 시간대의 조합은 4개입니다. 아래 표는 조합마다 두 소재의 진짜 클릭률이 다르다고 놓은 값입니다. 진짜 클릭률은 노출 한 번이 클릭으로 이어질 확률로, 알고리즘도 운영자도 미리 볼 수 없는 가상의 값입니다.

| 지면 | 시간대 | 소재 A | 소재 B | 이 조합의 승자 |
|---|---|---|---|---|
| 뉴스 | 오전 | 8% | 3% | A |
| 뉴스 | 저녁 | 2% | 6% | B |
| 커뮤니티 | 오전 | 3% | 7% | B |
| 커뮤니티 | 저녁 | 6% | 4% | A |
| **전체 평균(UCB1이 보는 값)** | — | 4.75% | **5.0%** | B |

표의 마지막 열에서 위 네 줄을 읽으면 조합의 승자가 A, B, B, A 로 계속 바뀝니다. 지면과 시간대가 달라지면 가장 좋은 소재도 함께 바뀐다는 뜻인데, UCB1 은 표의 위 네 줄을 볼 수 없고 모든 노출을 합쳐 계산한 마지막 줄의 평균만 봅니다.

네 조합의 클릭률을 그대로 평균하면 A 는 8%, 2%, 3%, 6% 의 평균인 4.75%, B 는 3%, 6%, 7%, 4% 의 평균인 5.0% 로 마지막 줄과 같습니다. 이 평균에서는 B 가 A 를 5.0% 대 4.75% 로 근소하게 이기므로 UCB1 은 이 작은 차이를 계속 학습해 결국 어디서나 B 를 밉니다. 그런데 뉴스 오전에서는 실제로 A 가 8% 로 B 의 3% 보다 두 배 이상 높습니다. B 의 3% 는 A 가 받는 8% 의 절반인 4% 에도 못 미치므로, 이 조합 하나만 따져도 B 를 낼 때마다 A 를 냈다면 받았을 클릭의 절반 이상을 놓칩니다.

조합마다 맞는 소재를 골랐다면 평균 클릭률은 각 조합 승자의 클릭률(8, 6, 7, 6%)을 평균한 6.75% 가 됩니다. 어느 한 소재만 계속 미는 경우의 4.75~5.0% 보다 35~42% 높은 값으로, B 만 미는 5.0% 와 비교하면 35%, A 만 미는 4.75% 와 비교하면 42% 높습니다. 컨텍스트를 알 때와 모를 때의 이 격차가 LinUCB 가 있는 까닭의 전부입니다.

## 2. 파이썬으로 측정한 컨텍스트 무시의 대가

**1절에서 말로 설명한 손해를 코드로 재현하려고 컨텍스트를 아예 무시하는 UCB1 과 컨텍스트별로 UCB1 을 따로 돌리는 방식을 4,000회 동안 비교합니다. 받은 누적 클릭은 컨텍스트별 분리 방식이 245회로 컨텍스트 무시 방식의 192회보다 27.6% 많았습니다.**

1절의 6.75% 는 진짜 클릭률을 알고 조합마다 정답을 골랐을 때의 값인데 실제 알고리즘은 진짜 클릭률을 모른 채 노출과 클릭을 세며 배웁니다. 이번에는 두 알고리즘이 직접 배우면서 소재를 고르게 해서 그 손해가 코드에서도 그대로 나오는지 봅니다.

두 방식은 모두 UCB1 그대로이고 통계를 어떻게 나눠 쌓느냐만 다릅니다. 여기서 통계는 소재마다 몇 번 냈는지(코드의 counts)와 클릭을 몇 번 받았는지(코드의 sums)입니다. 컨텍스트 무시 방식은 소재별 통계를 딱 한 세트만 쌓아 (지면, 시간대) 조합을 보지 않습니다. 컨텍스트별 분리 방식은 조합 4개마다 통계를 따로 쌓아 두고 지금 온 조합의 통계만 보고 소재를 고릅니다.

분리 방식에는 행렬의 역행렬 같은 선형대수가 전혀 필요 없습니다. 역행렬은 숫자의 역수에 해당하는 행렬 계산으로, 3절의 LinUCB 점수에 들어갑니다. 분리 방식은 그런 계산 없이 컨텍스트마다 독립된 카운터를 두기만 해도 LinUCB 가 풀려는 문제의 핵심을 그대로 흉내 낼 수 있습니다.

두 방식이 함께 쓰는 `ucb1_pick` 은 아직 한 번도 내지 않은 소재가 있으면 그 소재부터 냅니다. 모든 소재를 한 번 이상 냈다면 관측 평균(sums 를 counts 로 나눈 값)에 탐색 보너스를 더한 값이 가장 큰 소재를 고르는데, 보너스는 그 소재를 낸 횟수가 적을수록 커집니다.

아래 코드는 1절 표와 같은 진짜 클릭률로 두 방식을 4,000회 돌려 누적 클릭을 비교합니다. 루프는 매회 컨텍스트 하나를 무작위로 뽑은 뒤 두 방식이 각자 고른 소재의 클릭 여부를 1절 표의 진짜 클릭률(`TRUE_CTR` 의 0.08 이 표의 8%)을 확률로 삼아 정합니다. `random.seed(3)` 으로 시드(난수의 시작값)를 고정해 두었으므로 그대로 복사해 돌리면 같은 결과가 나옵니다.

```python
# 하는 일: UCB1 을 컨텍스트 무시와 컨텍스트별 분리 두 방식으로 4,000회 돌려 누적 클릭을 비교한다.
import random
import math

random.seed(3)

# 1단계: 컨텍스트 4종의 진짜 클릭률을 둔다
# 1절 표와 같은 '진짜' 클릭률. 지면 2종 x 시간대 2종, 소재 2개.
TRUE_CTR = {
    ("뉴스", "오전"):    {"A": 0.08, "B": 0.03},
    ("뉴스", "저녁"):    {"A": 0.02, "B": 0.06},
    ("커뮤니티", "오전"): {"A": 0.03, "B": 0.07},
    ("커뮤니티", "저녁"): {"A": 0.06, "B": 0.04},
}
CONTEXTS = list(TRUE_CTR)
ARMS = ["A", "B"]
ROUNDS = 4000

# 2단계: UCB1 고르기 함수를 만든다
# 관측 평균에 탐색 보너스를 더한 값이 가장 큰 소재를 고른다.
def ucb1_pick(counts, sums, t):
    unseen = [a for a in ARMS if counts[a] == 0]
    if unseen:
        return unseen[0]
    return max(ARMS, key=lambda a: sums[a] / counts[a] + math.sqrt(2 * math.log(t) / counts[a]))

# 3단계: 두 방식의 통계를 둔다
# 행렬 역행렬 없이 컨텍스트별 카운터 분리만으로 충분하다. 표준 라이브러리만 쓴다.

# (a) 컨텍스트를 무시한다 — 소재별 통계를 딱 하나만 쓴다.
blind_counts = {a: 0 for a in ARMS}
blind_sums = {a: 0 for a in ARMS}
blind_clicks = 0

# (b) 컨텍스트별로 UCB1을 따로 돌린다 — 조합마다 독립된 통계.
sep_counts = {c: {a: 0 for a in ARMS} for c in CONTEXTS}
sep_sums = {c: {a: 0 for a in ARMS} for c in CONTEXTS}
sep_clicks = 0

# 4단계: 4,000회 돌린다
# 매회 컨텍스트 하나가 무작위로 오고, 두 방식이 각자 소재를 고른다.
for _ in range(1, ROUNDS + 1):
    ctx = random.choice(CONTEXTS)

    t_blind = sum(blind_counts.values()) + 1
    arm_b = ucb1_pick(blind_counts, blind_sums, t_blind)
    reward_b = 1 if random.random() < TRUE_CTR[ctx][arm_b] else 0
    blind_counts[arm_b] += 1
    blind_sums[arm_b] += reward_b
    blind_clicks += reward_b

    t_sep = sum(sep_counts[ctx].values()) + 1
    arm_s = ucb1_pick(sep_counts[ctx], sep_sums[ctx], t_sep)
    reward_s = 1 if random.random() < TRUE_CTR[ctx][arm_s] else 0
    sep_counts[ctx][arm_s] += 1
    sep_sums[ctx][arm_s] += reward_s
    sep_clicks += reward_s

# 5단계: 두 방식의 누적 클릭을 찍는다
gain = (sep_clicks / blind_clicks - 1) * 100
print(f"{ROUNDS}회 후 누적 클릭 — 컨텍스트 무시: {blind_clicks}회, 컨텍스트별 분리: {sep_clicks}회")
print(f"분리 방식이 {sep_clicks - blind_clicks}회 더 많음 ({gain:.1f}% 더 많음)")
print(f"컨텍스트 무시 방식의 소재 선택 횟수: {blind_counts}")

# 출력:
# 5단계 뜻: 컨텍스트별로 나누면 클릭이 245회로, 무시할 때의 192회보다 53회(27.6%) 많다. 무시하면 A 와 B 를 1943회와 2057회로 거의 반반 고른다.
# 4000회 후 누적 클릭 — 컨텍스트 무시: 192회, 컨텍스트별 분리: 245회
# 분리 방식이 53회 더 많음 (27.6% 더 많음)
# 컨텍스트 무시 방식의 소재 선택 횟수: {'A': 1943, 'B': 2057}
```

찍힌 첫 줄을 보면 4,000회 뒤 누적 클릭은 컨텍스트별 분리 방식이 245회, 컨텍스트 무시 방식이 192회입니다. 245 에서 192 를 빼면 둘째 줄대로 분리 방식이 53회 더 많습니다. 27.6% 는 코드의 `gain` 계산대로 245 를 192 로 나눈 값에서 1 을 빼고 100 을 곱한 비율입니다. 4,000회 정도의 시뮬레이션에서도 컨텍스트를 반영하는 것 하나로 받는 클릭이 눈에 띄게 달라졌습니다.

더 눈여겨볼 값은 마지막 줄의 소재 선택 횟수입니다. 컨텍스트 무시 방식은 전체 평균의 차이가 4.75% 와 5.0% 로 워낙 작아 4,000번을 겪고도 어느 소재가 나은지 확신하지 못했으므로 A 를 1,943번, B 를 2,057번 골라 거의 반반으로 나눠 썼습니다. 1절에서 말한 「결국 어디서나 B 를 미는」 상태에는 4,000회 안에 아직 이르지 못했습니다. 반면 컨텍스트별로 나누면 조합마다 두 소재의 격차가 훨씬 커서(뉴스 오전은 8% 대 3%) 각 조합의 통계가 훨씬 빨리, 훨씬 자신 있게 정답을 찾습니다.

## 3. 컨텍스트를 점수에 넣는 LinUCB

**LinUCB 는 지면과 시간대 같은 컨텍스트를 숫자 벡터로 바꾼 뒤 소재마다 그 벡터에 어떻게 반응하는지를 따로 학습합니다.**

UCB1 의 점수는 관측 평균에 보너스를 더한 두 숫자로 끝납니다. 지면이나 시간대가 들어갈 입력이 없으니 어떤 상황에서든 소재마다 결과가 하나뿐입니다. LinUCB 는 이 점수에 컨텍스트 벡터 $x$ 를 끼워 넣습니다. $x$ 는 지면(뉴스=0, 커뮤니티=1)과 시간대(오전=0, 저녁=1) 같은 정보를 숫자로 바꿔 한 줄로 늘어놓은 벡터입니다. 이 $x$ 가 들어가면 소재 $a$ 의 점수는 이렇게 바뀝니다.

$$\text{Score}_a = \underbrace{x^T\theta_a}_{\text{이 컨텍스트에서의 예측}} + \underbrace{\alpha\sqrt{x^T A_a^{-1}x}}_{\text{방향별 탐색 보너스}}$$

앞 항은 이 컨텍스트에서의 예측입니다. $\theta_a$ 는 소재 $a$ 가 지금까지 배운 가중치로 「이 소재는 뉴스에서 강하고 저녁엔 약하더라」 같은 패턴이 여기에 쌓입니다. $x^T\theta_a$ 는 $x$ 의 숫자마다 $\theta_a$ 의 같은 자리 가중치를 곱해 모두 더한 값(내적)입니다. 그래서 같은 소재라도 컨텍스트 $x$ 가 바뀌면 예측이 달라집니다.

뒤 항은 방향별 탐색 보너스입니다. $A_a$ 는 소재 $a$ 의 배움이 어느 방향, 다시 말해 어떤 컨텍스트에서 온 데이터였는지를 기록한 행렬이고 $A_a^{-1}$ 은 그 역행렬입니다. $\alpha$ 는 보너스를 얼마나 크게 줄지 정하는 값입니다. $A_a$ 가 왜 필요한지는 7절에서 따로 자세히 보므로, 지금은 「소재마다 컨텍스트에 반응하는 자기만의 작은 모델을 가진다」는 점만 기억하면 됩니다.

소재마다 이런 작은 모델을 두면 1절의 문제가 풀립니다. LinUCB 는 소재 A 와 B 를 평균 하나로 뭉치는 대신 컨텍스트별로 다르게 배우므로 「뉴스에서는 A, 커뮤니티에서는 B」처럼 조합마다 다른 패턴이 남습니다. 2절에서 컨텍스트별로 UCB1 을 나눠 돌려 얻은 27.6% 의 이득이 바로 LinUCB 가 실제로 만들어 내려는 효과입니다.

다만 이 글은 $A_a$ 를 갱신하는 방법, $\alpha$ 를 정하는 기준, 역행렬 계산이 가벼워지는 원리를 다루지 않습니다. 이런 구현 세부는 [Disjoint LinUCB: 광고마다 계수를 따로 배우면 무엇이 달라지나](post.html?id=disjoint-linucb)에 있습니다.

## 4. Disjoint 의 대가 — 소재마다 따로 배울 때 헤매는 신규 소재

**Disjoint LinUCB 는 소재마다 $\theta_a$ 와 $A_a$ 를 따로 가지므로 새로 들어온 소재는 데이터가 0 인 채로 혼자 처음부터 다시 시작합니다.**

3절의 LinUCB 처럼 소재마다 자기만의 모델을 따로 두는 구조를 Disjoint LinUCB 라고 부릅니다. Disjoint 는 「따로 떨어진」이라는 뜻 그대로, 소재 A 가 배운 것과 소재 B 가 배운 것이 서로 전혀 섞이지 않습니다. 소재 A 가 「20대는 오전에 잘 누른다」는 패턴을 확실히 배웠더라도 그 지식은 소재 A 의 $\theta_A$ 안에만 남을 뿐, 소재 B 의 $\theta_B$ 는 여전히 아무것도 모르는 상태입니다.

이 구조는 신규 소재가 들어올 때 실무에서 문제가 됩니다. 오늘 등록된 소재 E 는 노출도 클릭도 아직 0건이라 $A_E$ 는 초기값인 단위행렬(대각선이 1 이고 나머지가 0 인 행렬)이고 $\theta_E$ 도 0 입니다. $\theta_E$ 의 칸이 모두 0 이면 $x$ 의 어느 숫자에 곱해 더해도 0 이 나오므로, 어떤 컨텍스트가 와도 소재 E 의 예측 점수 $x^T\theta_E$ 는 0 입니다. 뉴스든 커뮤니티든, 오전이든 저녁이든 소재 E 의 예측으로는 구분이 되지 않습니다.

물론 데이터가 없는 만큼 보너스 항이 커서 알고리즘은 소재 E 를 탐색해 보라고 점수를 올려 줍니다. 하지만 그 탐색이 쓸모 있는 신호로 바뀌려면 소재 E 자신의 노출과 클릭이 쌓여야 합니다. 다른 소재들이 수천 번 겪은 경험은 소재 E 에게 조금도 전달되지 않습니다.

이렇게 데이터가 없는 새 소재를 처음부터 다시 배워야 하는 문제를 콜드스타트(cold start)라고 부릅니다. 광고 소재가 하루에도 수십~수백 개씩 새로 올라오는 환경이라면 콜드스타트를 소재마다 매번 처음부터 되풀이하는 비용이 만만치 않습니다.

**그렇다면 다른 소재가 이미 배운 것을 새 소재가 조금이라도 물려받을 방법은 없을까요?**

## 5. 배움을 나눠 콜드스타트를 줄이는 Hybrid LinUCB

**Hybrid LinUCB 는 소재마다 따로 배우는 가중치 $\theta_a$ 에 더해 모든 소재가 함께 쓰는 공유 파라미터(학습으로 정해지는 숫자) $\beta$ 를 하나 두어, 새 소재도 다른 소재가 쌓아 둔 학습을 어느 정도 물려받고 시작하게 합니다.**

4절 끝의 물음에 Hybrid LinUCB 는 소재끼리 나눠 쓰는 파라미터로 답합니다. 파라미터는 3절에서 가중치라고 부른 $\theta_a$ 처럼 학습으로 값이 정해지는 숫자입니다. Hybrid LinUCB 에는 소재마다 따로 두는 소재 전용 파라미터 $\theta_a$ 와 모든 소재가 함께 쓰는 공유 파라미터 $\beta$ 가 모두 있어서 점수식에 공통 항이 하나 늘어납니다.

$$\text{Score}_a = \underbrace{z_a^T\beta}_{\text{공통 지식}} + \underbrace{x^T\theta_a}_{\text{개별 지식}} + \text{보너스}_a$$

$z_a$ 는 소재 자체의 특징으로 카테고리(운동화), 브랜드(나이키), 가격대 같은 정보를 담습니다. $\beta$ 는 이 특징들이 클릭에 미치는 영향을 모든 소재의 데이터를 모아서 배우므로, 소재 A 가 클릭을 받을 때마다 $\theta_A$ 뿐 아니라 $\beta$ 도 함께 갱신됩니다. 그래서 「운동화 카테고리는 오전에 반응이 좋다」 같은 패턴은 소재 하나의 것이 아니라 모든 소재의 공통 자산이 됩니다.

이제 신규 소재 E 가 등록되는 순간을 다시 보겠습니다. $\theta_E$ 는 여전히 0 에서 시작하지만 소재 E 에도 $z_E$ = [운동화, 나이키, 신상] 같은 특징은 있습니다. 첫 노출에서 소재 E 의 점수는 $z_E^T\beta + x^T\theta_E + \text{보너스}_E$ 인데 $\theta_E$ 가 0 이라 가운데 항이 0 이 되므로, 점수에는 공통 지식 $z_E^T\beta$ 와 보너스가 남습니다. $z_E$ 를 $\beta$ 에 넣으면 다른 나이키 운동화 소재에서 배운 패턴이 그대로 적용되어 첫 노출부터 그럴듯한 점수가 나옵니다. 소재 E 는 완전히 처음 보는 소재로 취급되지 않고 다른 소재가 쌓아 둔 학습을 어느 정도 물려받고 시작하는데, 실무에서 말하는 콜드스타트 완화가 바로 이렇게 물려받는 동작입니다.

물론 공짜는 아닙니다. Hybrid LinUCB 는 소재별 $\theta_a$, $A_a$ 에 더해 공유 $\beta$ 까지 저장하므로 파라미터가 늘어나며 점수를 계산할 때마다 공통 부분과 개별 부분을 함께 풀어야 합니다. 소재 수가 적고 새 소재도 드물게 들어오는 환경이라면 이 복잡도는 Hybrid 를 쓰지 않아 아낄 수 있는 비용입니다. 반대로 신규 소재가 끊임없이 들어오는 검색광고나 커머스 환경이라면 추가 비용을 감수할 가치가 충분합니다.

## 6. 나란히 놓은 UCB1, Disjoint LinUCB, Hybrid LinUCB

**세 알고리즘은 쓰는 정보가 적은 것부터 UCB1, Disjoint LinUCB, Hybrid LinUCB 순서로 놓이며 뒤로 갈수록 정교해지지만 계산도 무거워집니다.**

1절부터 5절까지 하나씩 본 세 알고리즘을 한 표에 놓으면 무엇을 더 쓰고 그 대가로 무엇을 더 치르는지 한 번에 보입니다. 표의 arm 은 밴딧 알고리즘(선택지 하나를 골라 보고 그 결과로 다음 선택을 고치는 알고리즘)이 고르는 선택지 하나하나로, 이 글에서는 소재입니다. $d$ 는 컨텍스트 벡터 $x$ 에 든 숫자의 개수, $k$ 는 소재 특징 $z_a$ 에 든 숫자의 개수를 뜻합니다.

| 비교 항목 | UCB1 | Disjoint LinUCB | Hybrid LinUCB |
|---|---|---|---|
| 쓰는 정보 | 소재별 평균, 노출 횟수 | 컨텍스트 벡터 + 소재별 가중치 | 컨텍스트 벡터 + 소재별 가중치 + 공유 가중치 |
| 파라미터 수 | 소재당 2개 | 소재당 $d\times d$ 행렬 1개 | 위에 더해 공유 $k\times k$ 행렬 1개 |
| 새 arm 대응 | 몇 번만 보여줘도 곧 따라잡음 | 콜드스타트 — 처음부터 다시 학습 | 공유 파라미터 덕에 첫 노출부터 합리적 |
| 계산 비용 | 덧셈, 나눗셈뿐 | 소재마다 행렬 역산 1회 | 소재 역산 + 공유 역산, 더 무거움 |
| 언제 쓰나 | 소재 수 적고 컨텍스트가 안 중요할 때 | 컨텍스트 있고 소재 구성이 안정적일 때 | 신규 소재가 계속 들어오는 대규모 환경 |

표를 위에서 아래로 읽으면 UCB1 에서 Hybrid LinUCB 까지 이어지는 계보를 따라갈 수 있습니다. 컨텍스트 자체를 쓰지 않는 UCB1 이 가장 가볍습니다. Disjoint LinUCB 는 3절에서 본 대로 컨텍스트를 반영하는 대신 소재마다 행렬을 하나씩 따로 관리해야 합니다. Hybrid LinUCB 는 5절에서 본 대로 콜드스타트 문제를 풀려고 공유 행렬을 하나 더 붙입니다.

세 알고리즘 가운데 무엇이 「제일 좋은 알고리즘」이냐고 묻는다면 질문이 잘못됐습니다. 소재가 서너 개뿐이고 유저 차이도 별 의미가 없다면 UCB1 로 충분해 굳이 행렬을 돌릴 이유가 없습니다. 컨텍스트가 확실히 있고 소재 구성도 잘 바뀌지 않는다면 Disjoint LinUCB 가 딱 맞는 자리입니다. 반면 신규 소재가 하루에도 수십 개씩 들어오는 검색광고나 커머스 지면에서는 콜드스타트 비용이 계산 비용보다 훨씬 큰 부담이라 Hybrid LinUCB 쪽으로 무게가 실립니다.

## 7. 횟수에서 방향으로 넓어진 탐색 보너스

**UCB1 의 보너스와 LinUCB 의 보너스는 「아직 잘 모르는 만큼 여유를 준다」는 같은 직관에서 나옵니다. 모르는 정도를 UCB1 은 본 횟수로 측정하고 LinUCB 는 지금 컨텍스트 방향으로 본 정도로 측정합니다.**

3절에서 미뤄 둔 「$A_a$ 라는 행렬이 왜 필요한가」에 이 절이 답합니다.

이 직관을 가장 단순하게 구현한 알고리즘이 UCB1 입니다. UCB1 은 소재를 몇 번 보여 줬는지 그 숫자 하나로 모르는 정도를 측정하므로 적게 보여 준 소재일수록 여유(보너스)가 커집니다.

LinUCB 는 같은 직관을 컨텍스트에도 적용합니다. 소재를 전체로는 많이 보여 줬어도 지금 들어온 컨텍스트 방향으로는 거의 보여 주지 못했을 수 있는데, LinUCB 의 보너스는 이렇게 컨텍스트 방향별로 모르는 정도를 측정합니다.

두 보너스가 실제로 어떻게 이어지는지는 수식으로 볼 때 가장 깔끔해서 아래 접이 블록에서 이어 봅니다.

:::deep 더 깊이 — 같은 식의 두 모양인 UCB1 의 보너스와 LinUCB 의 보너스
UCB1 의 보너스는 $\sqrt{2\ln t / n_a}$ 로, $t$ 는 지금까지 진행한 전체 횟수이고 $n_a$ 는 소재 $a$ 를 몇 번 보여 줬는지 그 횟수 하나만 담은 그냥 숫자입니다.

LinUCB 의 보너스 $\alpha\sqrt{x^T A_a^{-1} x}$ 는 언뜻 훨씬 복잡해 보이지만 컨텍스트가 없다고 가정하면 UCB1 과 정확히 같은 모양이 나옵니다.

컨텍스트 $x$ 가 늘 1 이라는 상수 하나뿐이라고 해 봅시다. 그러면 $A_a$ 는 $n_a$ 번 관측한 $1^2$ 을 더한 값, 즉 $n_a+1$ 이 됩니다(+1 은 4절의 초기값 단위행렬에서 온 정칙화 항으로, 데이터가 하나도 없어도 역행렬을 구할 수 있게 해 줍니다). 역행렬은 $A_a^{-1} = 1/(n_a+1)$ 이고 $x$ 가 1 이니 $x^T A_a^{-1} x$ 도 같은 값이라 보너스는 $\alpha/\sqrt{n_a+1}$ 로 정리됩니다. UCB1 의 $\sqrt{2\ln t/n_a}$ 와 형태가 사실상 같으며 분자가 $\alpha$ 라는 고정값인지 $\sqrt{2\ln t}$ 라는 서서히 커지는 값인지만 다릅니다.

두 보너스의 차이는 컨텍스트가 실제로 있을 때 보입니다. 그때 $A_a$ 는 $n_a$ 처럼 숫자 하나가 아니라 지금까지 본 컨텍스트 벡터들의 방향까지 함께 쌓은 행렬이므로, $x^T A_a^{-1} x$ 는 「몇 번 봤나」를 넘어 「지금 이 컨텍스트 방향으로 얼마나 봤나」를 측정합니다.

예를 들어 소재 D 가 노출 1,000번을 채웠는데 그 데이터가 전부 '커뮤니티, 저녁' 조합에서만 나왔다고 해 봅시다. 오늘 요청이 '뉴스, 오전'이면 소재 D 는 그 방향의 데이터가 거의 없는 것과 같습니다. $n_a$ 만 보는 UCB1 은 1,000번이라는 횟수만 보고 이 소재를 「이미 많이 안다」고 잘못 판단해 보너스를 작게 주는 반면, LinUCB 는 $x^T A_a^{-1} x$ 가 커져 「이 방향은 아직 낯설다」며 보너스를 제대로 키웁니다.

UCB1 의 $n_a$ 는 이렇게 LinUCB 의 $x^T A_a^{-1} x$ 의 특수한 경우입니다. 컨텍스트가 늘 같다는 가정 아래에서는 LinUCB 의 보너스가 UCB1 의 보너스로 정확히 줄어듭니다. 횟수라는 1차원 기준이 방향까지 담는 다차원 기준으로 넓어졌을 뿐입니다.
:::

## 8. 컨텍스트 피처가 풍부해 LinUCB 류가 힘을 쓰는 닫힌 생태계 [무대: 닫힌 생태계]

**LinUCB 와 Hybrid LinUCB 가 실제로 이득을 보려면 애초에 쓸 만한 컨텍스트 피처(컨텍스트 벡터에 넣는 입력 값)가 있어야 하는데, 로그인 기반으로 유저 정보를 가진 닫힌 생태계가 이 조건을 가장 잘 채웁니다.**

피처(feature)는 모델에 입력으로 넣는 값 하나하나로, 컨텍스트 벡터 $x$ 의 칸 하나가 피처 하나입니다. 네이버, 밴드처럼 로그인 기반의 닫힌 생태계는 유저 정보를 이미 갖고 있어서 나이대, 성별, 과거 클릭 이력, 지금 보는 지면 같은 피처로 광고를 고르는 그 자리에서 컨텍스트 벡터를 만들 수 있습니다. 1절의 지면과 시간대도 바로 이런 피처입니다. LinUCB 의 $\theta_a$ 는 컨텍스트가 이렇게 풍부할 때 비로소 배울 거리가 생깁니다.

컨텍스트 피처가 빈약하면 얘기가 달라집니다. 지면 정보 하나만 있고 유저 정보가 전혀 없다면 LinUCB 든 UCB1 이든 성능 차이가 크지 않은데, 7절의 논리를 뒤집어 보면 $x$ 가 다양하지 않을 때 $A_a^{-1}$ 가 사실상 $n_a$ 와 다를 게 없어지기 때문입니다. 그래서 닫힌 생태계에서도 순서가 있어, 「피처가 몇 개나 있고 얼마나 다양한가」부터 먼저 확인해야 합니다.

Hybrid LinUCB 는 공유 파라미터 $\beta$ 가 의미 있게 학습되도록 소재 피처 $z_a$ 까지 필요로 하므로, 카테고리, 브랜드, 가격대 같은 메타데이터(소재를 설명하는 정보)가 소재마다 정리돼 있어야 합니다. 닫힌 생태계의 광고 플랫폼은 광고주가 소재를 등록하는 단계부터 이 메타데이터가 쌓이므로 대개 이미 갖고 있습니다. 그래서 5절의 콜드스타트 완화가 이론에 그치지 않고 실제로 작동합니다.

## 9. 컨텍스트는 오지만 학습이 느린 열린 RTB [무대: 열린 RTB]

**광고 지면을 실시간 경매로 사고파는 열린 RTB 에서도 입찰 요청마다 컨텍스트는 따라오지만 경매에서 져서 패찰하면 그 컨텍스트에서 어떤 결과가 났을지 아예 볼 수 없습니다.**

열린 RTB(Real-Time Bidding)는 광고 지면이 노출 한 번마다 실시간 경매로 팔리는 시장입니다. DSP(Demand-Side Platform)는 광고주를 대신해 그 경매에 입찰하는 플랫폼입니다. 패찰은 경매에서 져서 노출 기회를 얻지 못한 결과를 말합니다.

DSP 가 받는 입찰 요청에는 매체(지면을 가진 사이트나 앱), 지면, 유저 세그먼트(비슷한 유저를 모은 그룹) 같은 컨텍스트가 대개 요청마다 함께 오므로 LinUCB 의 $x$ 를 채울 재료 자체는 부족하지 않습니다. 문제는 그다음입니다. 입찰에서 이겨야 노출이 나가고 노출이 나가야 클릭 여부를 알 수 있으므로, 패찰하면 이 소재가 통했을지 알 방법이 없고 그 컨텍스트의 데이터 자체가 생기지 않습니다.

이렇게 비어 있는 데이터를 결측이라고 하는데, 이 결측은 4절의 콜드스타트보다 한 겹 더 나쁩니다. 닫힌 생태계에서는 신규 소재라도 노출만 시키면 데이터가 쌓이는 반면 열린 RTB 에서는 노출을 시키고 싶어도 경매에서 계속 질 수 있습니다. 그렇게 지는 동안에는 $A_a$ 가 아예 자라지 않습니다. 인기 있는 세그먼트일수록 경쟁이 치열해 패찰이 잦으므로 그 방향의 데이터는 더디게 쌓입니다. 그 결과 정보가 잘 모이는 세그먼트와 안 모이는 세그먼트의 격차가 벌어지는데, 이 격차는 닫힌 생태계보다 훨씬 큽니다.

게다가 열린 RTB 에서는 캠페인이 시작되고 끝나면서 소재 후보군이 계속 들고 나므로 arm 구성 자체도 자주 바뀝니다. Disjoint 든 Hybrid 든 $\theta_a$ 와 $A_a$ 를 arm 마다 붙여 관리해야 하므로 arm 이 수시로 생기고 사라지면 이 값을 저장하고 정리하는 비용도 함께 늘어납니다. 그래서 열린 RTB 의 컨텍스추얼 밴딧(LinUCB 처럼 컨텍스트를 보고 arm 을 고르는 밴딧 알고리즘)은 알고리즘 선택만으로는 부족합니다. 실무의 절반은 언제 arm 을 등록하고 언제 폐기할지 정하는 운영 규칙이 차지합니다.

## 10. 한눈 정리

표의 숫자는 1절의 가데이터와 2절의 시뮬레이션에서, 식은 3절, 5절, 7절에서 나왔습니다.

| 개념 | 뜻 | 이 글에서 본 숫자 | 핵심 |
|---|---|---|---|
| UCB1의 한계 | 컨텍스트를 아예 못 봄 | 뉴스 오전 A 8% vs B 3%인데 평균은 B가 근소 우위(5.0% vs 4.75%) | 평균적으로 좋은 소재 하나만 계속 민다 |
| 컨텍스트 분리 효과 | 컨텍스트별로 따로 UCB1을 돌림 | 4,000회 후 누적 클릭 192 → 245 (27.6%↑) | 행렬 없이도 LinUCB가 풀려는 문제의 핵심을 흉내 낼 수 있다 |
| LinUCB | 컨텍스트 벡터로 소재별 예측, 보너스 계산 | $x^T\theta_a + \alpha\sqrt{x^T A_a^{-1}x}$ | "이 상황에 맞는 소재"를 고를 수 있게 됨 |
| Disjoint의 한계 | 소재마다 학습이 완전히 분리됨 | 신규 소재는 $\theta_a=0$에서 시작 | 콜드스타트를 매번 처음부터 반복 |
| Hybrid LinUCB | 공유 파라미터 $\beta$로 학습을 나눔 | $z_a^T\beta + x^T\theta_a$ | 새 소재도 첫 노출부터 합리적인 점수 |
| 보너스의 정체 | UCB1은 횟수, LinUCB는 방향 | 컨텍스트가 상수면 $x^TA_a^{-1}x \to 1/(n_a+1)$ | 같은 직관의 1차원 버전과 다차원 버전 |
| 닫힌 생태계 | 컨텍스트 피처가 풍부한 무대 | — | LinUCB류가 실제로 힘을 쓰는 조건 |
| 열린 RTB | 컨텍스트는 오지만 패찰하면 결측 | — | 학습 속도가 세그먼트마다 크게 벌어짐 |

## 11. 헷갈리기 쉬운 점

- **UCB1 이 나쁜 소재를 고르지는 않습니다.** UCB1 은 컨텍스트를 아예 볼 수 없으니 평균적으로 나은 소재 하나를 어디서나 되풀이해 밀 뿐입니다. 1절의 B 도 평균 5.0% 로 A 의 4.75% 보다 나은 소재였습니다.
- **LinUCB 의 $\theta_a$ 는 「정답」이 아니라 「지금까지 배운 추정치」입니다.** 데이터가 적으면 얼마든지 틀릴 수 있어서 점수에 보너스 항이 따로 붙어 있습니다.
- **Disjoint LinUCB 의 「Disjoint」는 알고리즘 이름이 아니라 구조를 가리키는 말입니다.** 소재끼리 배운 것을 전혀 섞지 않는다는 뜻일 뿐 성능이 나쁘다는 뜻은 아닙니다.
- **Hybrid LinUCB 가 언제나 더 좋은 상위 호환은 아닙니다.** 신규 소재가 드문 환경에서는 공유 파라미터를 관리하는 비용만 늘어나므로, 6절의 표대로 컨텍스트가 있고 소재 구성이 안정적인 곳에는 Disjoint LinUCB 가 맞습니다.
- **UCB1 의 $n_a$ 와 LinUCB 의 $x^TA_a^{-1}x$ 는 다른 개념이 아니라 같은 개념의 두 버전입니다.** 컨텍스트가 상수 하나뿐이라고 가정하면 $x^TA_a^{-1}x$ 가 $1/(n_a+1)$ 로 횟수 $n_a$ 만으로 정해지므로 두 버전은 정확히 같은 식이 됩니다(7절).
- **닫힌 생태계와 열린 RTB 모두 LinUCB 류를 쓸 수 있지만 「컨텍스트가 있다」와 「그 컨텍스트로 학습이 잘 된다」는 다른 이야기입니다.** 열린 RTB 는 입찰 요청마다 컨텍스트가 오더라도 패찰한 요청에서는 결과를 볼 수 없어서 학습이 훨씬 느립니다.
