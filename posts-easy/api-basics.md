지훈 씨가 팀에 들어온 첫 주에 이런 말을 들었습니다. "회원가입은 POST 로 보내고, 목록은 GET 으로 받아 오면 돼요."

지훈 씨는 알겠다고 답했는데 다음 날 코드를 보다가 막혔습니다. 검색 기능이 `POST /v1/search` 로 되어 있었는데 그 요청에서 **검색 결과가 돌아오고 있었습니다.** POST 는 뭔가를 고치거나 만드는 것이라고 배웠는데 여기서는 왜 데이터를 받아 오고 있을까요?

**POST 로 보냈는데 왜 데이터가 돌아올까요?**

이 질문 안에는 오해가 두 가지 겹쳐 있습니다. 오해 하나는 POST 라는 이름의 뜻에 있고 다른 하나는 **요청과 응답이 별개**라는 사실을 놓친 데 있습니다. 이 글은 두 오해를 먼저 푼 다음 주소를 짓는 관례, 공개 범위, 로그, 대량 전송까지 처음 API(프로그램끼리 데이터를 주고받으려고 미리 정해 둔 약속)를 다룰 때 필요한 것을 차례로 살펴봅니다.

> **한 줄 요약:** POST 는 서버에 「수정」을 시키는 메서드(요청이 서버에 시키는 일의 종류)가 아니라 「이걸 처리해 주세요」라고 맡기는 메서드입니다. 웹에서 요청과 응답을 주고받는 규칙인 HTTP 에서는 **요청 하나에 응답 하나가 반드시 짝**이라 메서드가 무엇이든 답이 옵니다. 메서드는 내가 서버에 시키는 일이고 응답은 그 일의 결과라서 서로 다른 이야기입니다.

> **골라 읽는 법** — 이 글은 11개 절로 되어 있습니다.
>
> - POST 를 둘러싼 오해 두 가지 → 3, 4절
> - 주소를 짓는 관례와 공개 범위 → 5, 6절
> - 로그에 남길 것과 로그가 남는 곳 → 7, 8절
> - 앱이 센 클릭 수와 서버가 센 클릭 수의 차이 → 9절
> - 100만 줄 같은 대량 데이터 전송 → 10절
> - 광고 클릭 API 하나의 설계 순서 → 11절

이 글에 나오는 숫자는 모두 설명을 위해 지어낸 값입니다. 숫자와 달리 로그 줄과 요청, 응답의 **형식**은 nginx(널리 쓰는 웹 서버 프로그램)와 HTTP 가 실제로 만드는 모양을 그대로 따랐습니다. 글에서 **우리**는 API 를 만들어 다른 쪽이 부를 수 있게 내주는 팀, 지훈 씨가 들어간 팀을 가리킵니다.

## 1. 주고받는 모양을 미리 정해 둔 약속, API

**API 는 「이 주소로 이런 모양으로 물으면 이런 모양으로 답한다」를 미리 맞춰 둔 약속입니다.**

사람은 웹사이트를 화면으로 보지만 프로그램끼리는 화면이 필요 없어 **데이터만** 주고받습니다. 화면 없이 데이터만 오가려면 어떤 모양으로 주고받을지를 양쪽이 미리 정해 둬야 하는데, 그렇게 정해 둔 약속을 API 라고 부릅니다. 그래서 API 를 만들 때는 코드를 짜기 전에 **주고받을 모양부터 정합니다.**

정해야 하는 모양은 요청 쪽 네 조각과 응답 쪽 세 조각으로 나뉩니다. 요청 한 번은 메서드, 주소, 헤더, 본문의 네 조각으로 이루어지며 조각마다 맡는 일은 아래 표와 같습니다.

| 조각 | 무엇인가 | 예 |
|---|---|---|
| 메서드 | 무엇을 시키나 | `GET`, `POST` |
| 주소 | 무엇에 대해 | `/v1/posts/12` |
| 헤더 | 곁들이는 정보 | 누구인지, 본문이 무슨 형식인지 |
| 본문 | 딸려 보내는 데이터 | `{"title": "첫 글"}` |

응답은 **상태 코드**, **헤더**, **본문**의 세 조각입니다. 상태 코드는 서버가 요청을 어떻게 처리했는지 알려 주는 세 자리 숫자입니다. 응답의 헤더와 본문에는 요청 쪽처럼 곁들이는 정보와 돌려주는 데이터가 담깁니다.

이 글 전체에서 되풀이해 쓰는 규칙이 여기서 하나 나옵니다. **요청을 하나 보내면 응답이 하나 오며 예외는 없습니다.** 서버에 돌려줄 데이터가 하나도 없을 때도 「줄 게 없다」는 응답은 옵니다.

그래서 지훈 씨가 본 「POST 로 보냈는데 답이 왔다」는 이상한 일이 아니며 오히려 답이 오지 않는 경우가 고장입니다. POST 로 보낸 요청에 답이 오는 일이 왜 그렇게 헷갈리는지는 4절에서 요청과 응답을 실제 모양 그대로 놓고 다시 봅니다.

## 2. 부르는 쪽에 따른 차이 — client to server 와 server to server

**같은 API 라도 부르는 쪽이 남의 기기인지 우리 서버인지에 따라 지켜야 할 것이 달라집니다.**

사용자의 브라우저나 앱이 우리 서버를 부르는 경우를 **client to server**, 우리 서버가 결제사나 지도 서비스 같은 다른 서버를 부르는 경우를 **server to server** 라고 합니다. 남의 기기에 깔린 코드는 **누구나 뜯어볼 수 있어서** 두 경우에 지켜야 할 것이 달라지는데, 아래 그림의 위쪽이 client to server 이고 아래쪽이 server to server 입니다.

| 물음 | client to server | server to server |
|---|---|---|
| 부르는 코드가 어디 있나 | 남의 브라우저, 기기 | 우리 기계실 |
| 비밀키를 넣을 수 있나 | **안 됩니다** — 뜯으면 보입니다 | 됩니다 |
| 요청값을 믿어도 되나 | 안 됩니다. 전부 다시 검사합니다 | 어느 정도 믿습니다 |
| 호출 횟수 | 사용자 수만큼, 들쭉날쭉 | 우리가 정합니다 |
| 옛 버전을 언제 끌 수 있나 | 앱을 안 지운 사람이 있는 한 못 끕니다 | 양쪽이 합의하면 바로 |

표의 두 번째 줄에 나오는 비밀키는 요청을 보낸 쪽이 누구인지 증명하는 데 쓰는, 남에게 보이면 안 되는 문자열입니다. 그림에 적힌 대로 앱을 뜯으면 그 안에 넣은 키가 그대로 나오므로 client to server 에서는 비밀키를 넣을 수 없습니다.

**실무에서 사고가 가장 자주 나는 줄은 표의 세 번째 줄 「요청값을 믿어도 되나」입니다.** 브라우저가 보낸 `{"price": 0}` 을 서버가 그대로 믿고 주문을 만들면 누군가 요청 속 가격을 0 으로 고쳐 보내는 순간 물건이 공짜로 나갑니다. 화면에서 그런 값을 넣지 못하게 막아 두어도 요청은 화면을 거치지 않고 직접 보낼 수 있으므로 아무것도 보장하지 못합니다. 그래서 표에 적은 대로 client to server 에서는 요청값을 전부 다시 검사합니다.

지훈 씨가 이번 주에 맡을 API 는 앱이 부르는 client to server 라서, 지훈 씨는 그림의 위쪽과 표의 client to server 열에 적힌 것을 모두 지켜야 합니다.

## 3. 메서드 5개가 시키는 일

**메서드는 요청이 그 주소에 무엇을 시키는지 나타냅니다. POST 를 둘러싼 오해의 절반이 이 메서드의 뜻에 있습니다.**

지훈 씨는 POST 를 「무언가를 고치거나 만드는 것」으로 배웠습니다. 그런데 메서드 5개가 각각 무엇을 시키는지 나란히 놓아 보면 「수정」에 가까운 메서드는 POST 가 아니라 따로 있습니다.

| 메서드 | 뜻 | 예 |
|---|---|---|
| `GET` | "주세요" | "글 목록을 주세요" |
| `POST` | **"이걸 처리해 주세요"** | "이 내용으로 글을 새로 써 주세요" |
| `PUT` | "이 자리를 이 내용으로 전부 바꿔 주세요" | 12번 글을 이 내용으로 교체 |
| `PATCH` | "이 자리에서 이 부분만 바꿔 주세요" | 12번 글의 제목만 교체 |
| `DELETE` | "지워 주세요" | "12번 글을 지워 주세요" |

표의 한 줄 설명만으로는 메서드에 따라 서버에서 무엇이 달라지는지 그려지지 않으므로, 아래 데모에서 같은 주소에 메서드만 바꿔 요청을 직접 보내 봅니다. 데모에서는 메서드마다 보낸 요청 원문, 돌아온 응답 원문, 서버 쪽 데이터가 어떻게 달라지는지 보면 됩니다.

**메서드 5개 가운데 「수정」에 가장 가까운 메서드는 `PUT` 과 `PATCH` 입니다.** 표대로 `PUT` 은 그 자리를 보낸 내용으로 전부 바꾸고 `PATCH` 는 그 자리에서 보낸 부분만 바꿉니다. `POST` 는 수정보다 **제출**에 가까워서 서버에 무언가를 넘기며 「알아서 처리해 주세요」라고 맡기는 메서드입니다.

처리를 서버가 알아서 하므로 `POST` 요청이 서버에서 일으키는 일은 상황마다 다릅니다. 같은 `POST` 가 글을 새로 만들기도 하고 로그인을 시켜 주기도 하며 결제를 걸기도 합니다. **세 경우의 공통점은 서버 쪽에서 무슨 일이 일어난다는 점 하나뿐입니다.**

**`GET` 은 반대로 서버에서 아무것도 바꾸지 않아야 합니다.** `GET` 이 이 약속을 지키면 같은 주소를 몇 번 불러도 서버가 그대로이므로 다음 세 가지가 편해집니다.

- 브라우저는 사용자가 누르기 전에 그 주소를 미리 불러 둬도 됩니다.
- 부르는 코드는 요청이 실패하면 그냥 다시 부르면 됩니다.
- 사람은 그 주소를 남에게 그대로 공유해도 됩니다.

`GET /v1/posts/12/delete` 처럼 `GET` 으로 글을 지우는 주소를 만들면 안 되는 까닭도 여기에 있습니다. 검색 로봇(링크를 따라가며 주소를 자동으로 여는 프로그램, 크롤러)은 `GET` 주소를 불러도 서버가 바뀌지 않는다고 보고 주소를 차례로 스캔하므로, 그런 주소가 있으면 검색 로봇이 한 번 스캔하는 것만으로 글이 다 지워집니다.

메서드를 고르는 기준은 이렇게 한 줄로 줄일 수 있습니다. **서버 쪽에서 무언가 바뀌면 `POST`, `PUT`, `PATCH`, `DELETE` 가운데 하나를 쓰고 아무것도 바뀌지 않으면 `GET` 을 씁니다.** 이 한 줄로 대부분의 요청에 쓸 메서드가 정해집니다. 다만 다음 절의 조건이 긴 검색처럼 이 「대부분」에 들지 않는 경우도 있습니다.

## 4. POST 로 보낸 요청과 돌아오는 데이터

**메서드는 내가 서버에 시키는 일이고 응답은 그 일의 결과라서 어떤 메서드로 보냈는지와 무엇이 돌아오는지는 서로 다른 이야기입니다.**

「POST 는 데이터를 보내는 것」이라고 외우면 POST 는 보내기만 하고 받아 오는 데이터는 없다고 생각하게 되는데, 지훈 씨는 바로 이 대목에서 헷갈렸습니다. 하지만 1절에서 본 대로 HTTP 에서는 **요청 하나마다 응답 하나가 반드시 따라오므로** POST 요청에도 응답이 옵니다.

아래 세 블록에 요청 세 가지를 실제로 주고받는 모양 그대로 적었습니다. 블록마다 `HTTP/1.1 200 OK` 처럼 상태 코드가 적힌 줄부터 아래가 받은 응답이고 그 위가 보낸 요청입니다. 요청과 응답 모두 첫 줄 아래의 `Host` 나 `Content-Type` 같은 줄이 헤더이며 본문이 있으면 빈 줄 다음에 옵니다. `Content-Type: application/json` 은 본문이 JSON(중괄호 안에 이름과 값을 적는 데이터 형식)이라고 알려 주는 헤더입니다.

**① 글 목록을 받아 오는 GET — 요청에 본문이 없습니다**

```http
GET /v1/posts?page=2 HTTP/1.1
Host: api.example.com

HTTP/1.1 200 OK
Content-Type: application/json

{"page":2,"items":[{"id":11,"title":"첫 글"},{"id":12,"title":"둘째 글"}]}
```

**② 새 글을 쓰는 POST — 요청에도 응답에도 본문이 있습니다**

```http
POST /v1/posts HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"title":"셋째 글"}

HTTP/1.1 201 Created
Content-Type: application/json

{"id":13,"title":"셋째 글","status":"created"}
```

**③ 조건이 긴 검색 POST — 서버에 아무것도 만들지 않습니다**

```http
POST /v1/search HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"filters":[{"field":"title","value":"글"},{"field":"author","value":"jihun"}]}

HTTP/1.1 200 OK
Content-Type: application/json

{"matched":2,"items":[{"id":11,"title":"첫 글"}]}
```

세 블록에 찍힌 값을 나란히 놓으면 오해가 풀립니다. ①은 `GET` 요청으로 보낸 본문이 없는데도 `200 OK` 응답의 본문에 2쪽(`page=2`)의 글 두 건, 「첫 글」과 「둘째 글」이 들어 있습니다. ②는 제목 「셋째 글」을 본문에 담아 `POST` 로 보냈고 `201 Created` 응답의 본문에 새 글 번호 13, 제목, `"status":"created"` 가 돌아왔으니 서버에 글이 하나 새로 생겼습니다. ③은 검색 조건 두 가지를 본문에 담아 `POST` 로 보냈고 `200 OK` 응답의 본문에 검색 결과가 돌아왔지만 서버에는 아무것도 새로 생기지 않았습니다.

**보낼 때 본문이 있는지, 받을 때 본문이 있는지, 서버에 무언가 생겼는지는 서로 상관없는 세 가지입니다.** ①과 ③은 메서드가 다른데도 둘 다 본문을 받았고 ②와 ③은 같은 `POST` 인데도 서버에 생긴 것이 다르므로, 메서드 하나만 보고 나머지 두 가지를 짐작할 수 없습니다.

③이 바로 지훈 씨가 코드에서 본 `POST /v1/search` 입니다. 아무것도 만들지 않는 검색에 왜 `POST` 를 썼을까요?

**검색 조건이 주소에 다 들어가지 않아서 `POST` 를 씁니다.** `GET` 은 조건을 `?title=글&author=jihun` 처럼 주소 뒤에 붙여 보내는데, 조건이 20개쯤 되거나 값이 길면 주소가 그 길이를 감당하지 못합니다. 서버나 중간 장비(요청이 서버에 닿기 전에 거치는 장비)가 주소 길이를 제한하는 경우도 많습니다. 그래서 ③처럼 조건을 `filters` 목록에 담아 본문으로 보내는 `POST` 요청을 씁니다.

**원칙대로라면 조회는 `GET` 이므로 검색에 `POST` 를 쓰는 일은 원칙에서 벗어납니다.** 다만 주소 길이라는 현실적인 이유로 `POST` 를 쓸 때는 주소에 `search` 처럼 「이 요청은 조회다」라는 표시를 남겨 둡니다. 판단 기준을 하나로 줄이면, 조건이 주소에 들어가면 `GET` 을 쓰고 들어가지 않을 때만 `POST` 로 넘어가되 조회라는 사실이 주소에 보이게 짓습니다.

:::deep 상태 코드 세 자리를 읽는 법

세 자리를 다 외우지 않아도 됩니다. **첫 자리만 알면 대부분의 상태 코드가 읽힙니다.** 상태 코드는 모두 서버가 부르는 쪽에 하는 말이라 첫 자리가 2 인 2xx 는 「됐습니다」, 3xx 는 「다른 데로 가세요」, 4xx 는 「그쪽이 잘못 보냈습니다」, 5xx 는 「제가 처리를 못 했습니다」라는 뜻입니다.

부르는 쪽은 4xx 가 뜨면 자기 요청을 고치고 5xx 가 뜨면 서버 담당자에게 알리므로 **같은 실패라도 할 일이 정반대**입니다. 그래서 실무에서는 무엇보다 4xx 와 5xx 를 먼저 구분합니다.

자주 보는 상태 코드는 아래 표의 7개쯤이고 나머지는 필요할 때 찾아보면 됩니다.

| 코드 | 뜻 | 누가 고치나 |
|---|---|---|
| `200` | 됐습니다 | — |
| `201` | 새로 만들었습니다 | — |
| `400` | 요청 모양이 틀렸습니다 | 부르는 쪽 |
| `401` | 누군지 모르겠습니다 | 부르는 쪽 |
| `403` | 누군지는 알겠는데 권한이 없습니다 | 부르는 쪽 |
| `404` | 그런 것 없습니다 | 부르는 쪽 |
| `500` | 서버에서 오류가 났습니다 | 받는 쪽 |

표에서 `401` 과 `403` 이 헷갈리기 쉬운데, **로그인을 하지 않은 요청에는 서버가 누군지 모르므로 401 을 돌려주고 로그인은 했지만 남의 글을 지우려는 요청에는 누군지는 알아도 권한이 없으므로 403 을 돌려줍니다.**

**`200` 을 보내 놓고 본문에 「실패했습니다」를 담는 일은 절대 하지 않습니다.** 부르는 쪽 코드는 상태 코드만 보고 그 요청을 성공으로 처리하고 감시 도구(오류 건수를 세어 알려 주는 모니터링 프로그램)도 `200` 을 오류로 세지 않으므로, 실패가 어디에도 나타나지 않은 채 조용히 묻힙니다.
:::

## 5. 주소를 짓는 관례

**주소에는 다루는 대상만 넣고 그 대상에 무엇을 할지는 메서드에 맡깁니다.**

주소를 짓는 데 정해진 정답은 없지만 널리 쓰는 관례가 있어 관례만 따라도 처음 보는 사람이 주소를 쉽게 읽습니다.

| 규칙 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 동사를 넣지 않습니다 | `/getPost`, `/createUser` | `GET /posts/12`, `POST /users` |
| 복수형 명사를 씁니다 | `/post/12` | `/posts/12` |
| 소속은 경로로 나타냅니다 | `/comments?postId=12` | `/posts/12/comments` |
| 소문자와 하이픈을 씁니다 | `/userProfile`, `/user_profile` | `/user-profiles` |
| 버전을 앞에 붙입니다 | `/posts` | `/v1/posts` |

**표에서 가장 먼저 지킬 줄은 첫 줄, 주소에 동사를 넣지 않는 규칙입니다.** 메서드가 이미 「무엇을 하라」는 동사 역할을 하므로 주소에 동사를 넣으면 메서드와 뜻이 겹치는데, `POST /createUser` 는 `POST` 와 `create` 로 「만들어라」를 두 번 말합니다. 이렇게 짓다 보면 메서드는 `POST` 인데 주소는 지우라고 말하는 `POST /deleteUser` 같은 주소까지 생깁니다.

반대로 주소를 명사로 지으면 같은 주소에 메서드만 바꿔 여러 일을 시킬 수 있습니다. 글 전체를 뜻하는 `/v1/posts` 에 `GET` 을 붙이면 글 목록을 받고 `POST` 를 붙이면 새 글을 씁니다. 12번 글을 뜻하는 `/v1/posts/12` 에 `PATCH` 를 붙이면 그 글의 일부를 고치고 `DELETE` 를 붙이면 그 글을 지웁니다. 이름 여섯 개를 따로 지어 외우는 것보다 훨씬 쉽습니다. 주소를 이렇게 명사로 짓고 표의 세 번째 줄처럼 소속을 경로로 나타내면 **처음 보는 사람도 `/v1/posts/12/likes` 를 12번 글에 달린 좋아요일 것이라고 짐작할 수 있습니다.**

나중에 응답 모양을 바꿔야 할 때가 오므로 표의 마지막 줄처럼 주소 맨 앞에 `/v1` 같은 버전을 붙입니다. 응답 모양을 바꿀 때 `/v1` 을 살려 둔 채 `/v2` 를 새로 열면 옛 앱은 계속 `/v1` 을 부르고 새 앱만 `/v2` 로 옮겨 갑니다. 2절 표의 마지막 줄에서 본 대로 client to server 는 앱을 안 지운 사람이 있는 한 옛 버전을 끌 수 없는데, 버전 자리가 있으면 옛 버전을 끄지 않고도 새 모양을 열 수 있습니다. 그래서 주소에서 한 번 정하면 되돌리기 가장 어려운 자리는 맨 앞의 버전 자리이며 버전 뒤의 나머지는 나중에 고칠 여지가 있습니다.

## 6. 공개 범위 — 내부용, 파트너용, 공개용

**API 를 연다는 말은 주소를 알려 준다는 뜻이 아니라 누가 부를 수 있는지 등급을 정한다는 뜻입니다.**

한 서버 안에 함께 있는 API 라도 누가 부를 수 있게 할지는 API 마다 다르며 크게 세 등급으로 나눕니다.

| 등급 | 누가 부르나 | 어떻게 막나 | 바꿀 때 |
|---|---|---|---|
| 내부용 | 사내 서버끼리 | 망 자체를 분리 | 양쪽 배포만 맞추면 됩니다 |
| 파트너용 | 계약한 회사 | 회사마다 키를 따로 발급 | 미리 알리고 유예 기간을 둡니다 |
| 공개용 | 아무나 | 가입하면 키를 줍니다 | 함부로 못 바꿉니다 |

**표에서 아래 등급으로 갈수록 API 를 바꾸기 어려워지는데, 등급을 나누는 진짜 이유가 바로 이 차이입니다.** 내부용은 사내 서버끼리만 부르니 오늘 고쳐 오늘 배포(고친 코드를 서버에 올려 실제로 돌게 하는 일)해도 되지만 공개용은 누가 쓰는지도 모르므로 한 번 연 모양을 오래 지켜야 합니다. 그 사이의 파트너용은 계약한 회사에 미리 알리고 유예 기간(옛 모양을 끄기 전에 상대가 옮겨 올 시간)을 둡니다.

그래서 「일단 다 열어 두고 나중에 정리하자」는 실무에서 자주 하는 실수입니다. 열어 둔 API 를 나중에 닫으려면 그 API 를 쓰는 곳을 전부 찾아 설득해야 하므로 **처음에는 좁게 열고 필요할 때 넓히는 편이 언제나 비용이 적게 듭니다.**

등급을 정한 다음에는 세 가지를 더 정합니다.

첫째는 부르는 쪽이 누구인지 확인하는 방법입니다. 내부용은 망 분리(밖에서는 닿지 않는 사내 네트워크에만 API 를 두는 것)로 충분합니다. 파트너용과 공개용은 키나 토큰(부르는 쪽이 누구인지 알리려고 요청에 담는 문자열)을 나눠 줍니다. 키와 토큰 같은 방식이 각각 무엇을 막고 무엇은 못 막는지는 [API 연동 실무](post.html?id=api-kinds-and-contracts) 편에서 다룹니다.

둘째는 한 키가 초당 몇 번까지 부를 수 있는지를 정한 호출 한도(rate limit)입니다. 이 한도를 정해 두지 않으면 한 곳이 실수로 반복 호출을 걸었을 때 같은 서버를 함께 쓰는 다른 모두가 같이 느려집니다.

셋째는 문서로 남길 내용입니다. 주소, 요청 모양, 응답 모양, 오류 목록의 4가지는 최소한 남기는데, 이 문서가 없으면 부르는 쪽이 매번 물어보거나 더 나쁘게는 추측해서 코드를 짭니다.

## 7. 로그 한 줄에 넣을 것과 숨길 것

**서버는 요청 하나가 지나갈 때마다 로그 한 줄을 남깁니다. 그 한 줄에 무엇을 넣고 무엇을 숨길지가 로그 설계의 전부입니다.**

로그는 서버가 받은 요청과 처리 결과를 한 줄씩 적어 두는 기록입니다. 장애가 났을 때 그 요청이 언제 들어왔고 서버가 뭐라고 답했는지를 로그에서 찾지 못하면 원인도 찾지 못합니다. 그렇다고 요청을 받은 그대로 다 남기면 비밀번호와 카드번호까지 로그에 그대로 적힙니다.

아래는 지훈 씨가 로그인 요청 한 건을 받은 그대로 남겨 본 줄입니다.

```json
{"ts":"2026-08-16T10:22:03.114Z","path":"/v1/users/login","body":{"email":"jihun@example.com","password":"hunter2","card":"4111-1111-1111-1234"}}
```

이 줄의 `body` 에는 비밀번호 `hunter2` 와 카드번호가 그대로 찍혀 있습니다. 로그는 보통 여러 사람이 검색할 수 있는 곳에 쌓이므로 이런 줄이 하나만 있어도 사고입니다. 민감한 값을 숨기고 필드를 몇 개 추가해 같은 요청을 다시 남기면 아래처럼 됩니다.

```json
{"ts":"2026-08-16T10:22:03.114Z","request_id":"req-8f21c0","method":"POST","path":"/v1/users/login","status":401,"took_ms":37,"body":{"email":"jihun@example.com","password":"***","card":"***"},"headers":{"Authorization":"***","User-Agent":"app/3.2.1"}}
```

필드는 `"status":401` 처럼 이름과 값의 한 쌍입니다. 둘째 줄에서는 `password`, `card`, 그리고 로그인 정보를 담는 `Authorization` 헤더의 값이 `***` 로 바뀌었고 `request_id`, `method`, `status`, `took_ms`, `headers` 필드가 새로 붙었습니다. `"status":401` 은 서버가 이 로그인 요청에 401(누군지 모르겠습니다)로 답했다는 뜻입니다. `took_ms` 는 서버가 이 요청을 처리하는 데 걸린 시간을 밀리초(ms) 단위로 적은 필드입니다. 새로 붙은 필드마다 정해야 할 것이 하나씩 있는데 그중 꼭 정할 세 가지를 차례로 봅니다.

**첫째, 새 필드 가운데 가장 중요한 필드는 `request_id` 입니다.** `request_id` 는 요청이 들어올 때 하나씩 붙이는 고유한 번호이고 이 줄에서는 `req-8f21c0` 입니다. 서버가 그 요청을 처리하며 남기는 모든 줄에 같은 `request_id` 를 넣어 두면 나중에 `req-8f21c0` 하나로 이 요청과 관련된 줄을 전부 모을 수 있습니다. 이 번호를 응답 헤더에 담아 돌려주면 사용자가 「이 번호로 문의드립니다」라고 말할 수 있어 더 좋습니다.

**둘째, 민감한 값을 숨길 때 필드 자체를 지우지 않고 값만 `***` 로 바꿉니다.** `password` 필드를 아예 지우면 나중에 「이 요청이 비밀번호를 보내긴 했나」를 따질 수 없지만 둘째 줄처럼 `"password":"***"` 로 남겨 두면 비밀번호가 왔다는 사실은 남고 값은 보이지 않습니다. `status` 와 `took_ms` 도 나중에 따져 볼 수 있게 하려고 꼭 넣는데, 상태 코드만 있으면 「성공은 했는데 3초 걸렸다」를 알 수 없기 때문입니다.

**셋째, 모든 요청의 본문을 다 남기면 로그가 원본 데이터보다 커지므로 본문을 남길지는 취향이 아니라 초당 건수로 정합니다.** 초당 수천 건이 들어오는 API 라면 본문은 오류가 났을 때만 남기거나 요청 가운데 일부만 골라 남기는 샘플링을 씁니다.

## 8. 로그가 남는 곳 — 서버가 저절로 남기는 줄과 앱이 보내야 남는 줄

**앱이 보낸 요청 하나는 서버 쪽에 로그 두 줄을 남기는데, 한 줄은 우리가 코드를 짜지 않아도 남고 다른 한 줄은 앱이 본문에 담아 보내 줘야만 남습니다.**

지훈 씨는 앱 팀의 코드를 읽다가 이상한 점을 찾았습니다. 사용자가 광고를 누르면 앱이 `POST /v1/events` 로 「눌렀다」를 보내는데, 그 요청이 서버에 도착하면 서버는 어차피 7절에서 본 것 같은 로그 한 줄을 남깁니다. **서버가 요청을 받기만 해도 기록이 남는데 앱은 왜 굳이 한 번 더 알려 줄까요?**

**서버는 자기에게 온 요청만 알 수 있어서 기기 안에서 일어난 일은 앱이 요청으로 알려 줘야 합니다.** 서버가 한 일은 광고를 내려 준 데까지라, 그 광고가 화면에 실제로 떴는지와 사용자가 그 광고를 눌렀는지는 기기 안에서만 일어나 서버가 알 길이 없습니다. 기기 안에서 일어난 일을 서버 쪽으로 넘기는 수단은 기기가 보내는 요청 하나뿐입니다.

두 줄이 실제로 어떻게 생겼는지 클릭 한 번으로 보겠습니다. 2026년 8월 16일 16시 48분 21초에 사용자가 A앱 메인 상단에 뜬 광고(광고 번호 `9931`)를 눌렀는데, 이 클릭 한 번이 우리 서버에 아래 두 줄을 남겼습니다.

**① 접속 로그(access log): nginx 가 저절로 남기며 우리가 짠 코드는 0줄입니다.**

```
10.2.31.7 - - [16/Aug/2026:16:48:21 +0900] "POST /v1/events HTTP/1.1" 204 0 "-" "AdSDK/3.2.1" 0.002
```

접속 로그는 nginx 같은 웹 서버가 받은 요청마다 한 줄씩 저절로 적는 기록입니다. 이 줄에는 서버에 닿은 시각 `16/Aug/2026:16:48:21 +0900`, 메서드와 주소 `POST /v1/events`, 상태 코드 204(처리는 했고 돌려줄 본문은 없다는 뜻), 요청을 보낸 프로그램의 이름표(User-Agent) `AdSDK/3.2.1`, 처리에 걸린 시간 0.002초처럼 요청이 왔다는 사실만 적혀 있습니다.

**② 이벤트 로그(event log): 앱이 본문에 담아 보내야만 남고 우리 코드가 그 본문을 꺼내 적습니다.**

```json
{"req_id":"r-8f21","event":"click","ad_id":9931,"slot":"main_top","event_ts":1786866501234,"app_ver":"3.2.1"}
```

이벤트 로그는 우리 서버 코드가 요청 본문에서 값을 꺼내 적는 줄이라, 접속 로그에는 없던 무슨 일인지(`"event":"click"`), 어느 광고인지(`ad_id` 9931), 어느 자리인지(`slot` 의 `main_top`, 메인 상단), 언제인지(`event_ts`, 클릭 시각을 밀리초 단위 숫자로 적은 값)가 들어 있습니다.

같은 클릭 한 번을 적었는데도 두 줄에 적힌 내용은 전혀 다릅니다. 다섯 가지 물음으로 나란히 놓으면 아래 표와 같습니다.

| 물음 | ① 접속 로그 | ② 이벤트 로그 |
|---|---|---|
| 누가 남기나 | nginx, 프레임워크가 저절로 | 우리가 코드를 짜야 |
| 무엇이 적히나 | 요청이 왔다는 사실 — 주소, 상태, 걸린 시간 | 본문 내용 — 어느 광고, 어느 자리, 언제 |
| 어느 광고였는지 아나 | 모릅니다. 주소는 전부 `/v1/events` 입니다 | 압니다. `ad_id` 9931 |
| 앱이 본문을 안 담아 보내면 | 그래도 남습니다 | 아무것도 안 남습니다 |
| 어디에 쓰나 | 장애 조사 | 과금, 리포트, 학습 데이터 |

표의 프레임워크(웹 서버 코드를 짤 때 바탕으로 쓰는 라이브러리)도 nginx 처럼 접속 로그를 저절로 남깁니다.

**지훈 씨의 질문에 답하는 줄은 표의 세 번째 줄 「어느 광고였는지 아나」입니다.** 앱이 보낸 클릭 요청이 열 건이면 열 건 모두 주소가 `POST /v1/events` 라서 접속 로그만 보면 열 줄이 똑같이 생겼습니다. 어느 광고를 눌렀는지는 본문에만 있고 본문은 앱이 담아 보내야만 존재하므로, 앱은 요청을 보내기만 하지 않고 어느 광고를 눌렀는지를 본문에 담아 보냅니다.

**웹 지면에서 쓰는 웹 픽셀은 요청 자체가 기록이 되는 가장 분명한 예입니다.** 웹 픽셀은 1×1 크기의 투명 이미지 주소를 부르기만 하는 방식이라 보낼 본문도 없고 돌아온 응답도 쓰지 않습니다. 그 대신 광고 번호를 `/p.gif?ad=9931` 처럼 주소 뒤에 붙이므로, 그 요청이 남긴 접속 로그 한 줄이 그대로 기록이 됩니다.

**클릭은 요청이 트래킹 서버를 지나가게 해서 남기기도 합니다.** 이 방식에서는 사용자가 광고를 눌러도 광고주 페이지로 바로 가지 않고 트래킹 서버(클릭을 기록하는 서버)의 주소를 한 번 거칩니다. 트래킹 서버는 클릭을 적은 다음 사용자를 진짜 광고주 페이지 주소로 넘기는데, 이렇게 다른 주소로 넘겨 보내는 동작을 리디렉션(redirect)이라고 부릅니다. 이 경로 전체는 [광고가 유저에게 도달하는 전체 과정](post.html?id=ad-serving-flow) 편 11절에 있습니다.

**부르는 쪽이 서버라면 사정이 다릅니다.** 서버는 기록을 자기 디스크에 쓰면 되므로 기록을 남기려고 다른 서버를 부를 일이 없지만 브라우저와 앱은 기록을 남길 데가 없어 우리 서버로 보내야 합니다.

부르는 쪽이 남의 기기에 있으면 기기 안에서 일어난 일을 서버에 알릴 방법이 요청으로 보내는 것밖에 없으므로, 지훈 씨가 본 앱 팀의 코드처럼 앱이 굳이 한 번 더 알려 주는 일은 이상한 것이 아니라 **일반적입니다.**

## 9. 앱이 센 클릭 수와 서버가 센 클릭 수의 차이

**8절의 두 줄은 모두 서버에 남는 줄이었지만 이 절에서는 앱 안에 남는 기록과 서버에 남는 기록을 짝지어 봅니다.**

지훈 씨가 앱 팀에 어제 클릭 건수를 묻자 앱 팀은 1,000건이라고 답했는데, 서버 로그에는 985건만 있었습니다. **나머지 15건은 어디로 갔을까요?**

먼저 앱과 서버는 같은 요청을 두고도 측정하는 범위가 다릅니다. 앱은 요청을 보낸 순간부터 응답이 다 올 때까지의 시간을 측정하고 서버는 자기가 요청을 처리한 시간만 측정하므로, 두 시간의 차이는 요청과 응답이 네트워크를 오가는 데 걸린 시간입니다.

그보다 더 중요한 차이가 있습니다. **서버에 도착하지도 못한 요청은 서버 로그에 없습니다.** 요청 하나가 겪을 수 있는 네 가지 상황을 앱 쪽 기록과 서버 쪽 기록으로 나눠 보면 이 차이가 바로 보입니다.

| 상황 | 앱 쪽 기록 | 서버 쪽 기록 | 실제로는 |
|---|---|---|---|
| 정상 | 성공 `200` | `200` 한 줄 | 양쪽이 맞습니다 |
| 서버에서 오류가 났습니다 | 실패 `500` | `500` 한 줄 | 양쪽 다 압니다 |
| 서버가 안 떠 있었습니다 | 연결 실패 | **줄이 없습니다** | 클릭은 있었는데 아무 데도 안 남았습니다 |
| 답이 늦어 앱이 포기했습니다 | 타임아웃 | **`200` 한 줄** | 서버는 저장했는데 앱은 실패로 압니다 |

넷째 줄의 타임아웃은 정해 둔 시간 안에 응답이 오지 않아 앱이 기다리기를 멈춘 경우입니다.

**사라진 15건은 표의 셋째 줄 「서버가 안 떠 있었습니다」에 해당합니다.** 서버가 배포 중이라 잠깐 멈춘 사이에 앱이 보낸 15건은 서버에 닿지 못해 서버 로그에 한 줄도 남지 않았으므로, 앱이 센 1,000건에서 이 15건을 빼면 서버가 센 985건이 나옵니다.

**넷째 줄 「답이 늦어 앱이 포기했습니다」는 반대 방향의 차이를 만듭니다.** 서버는 저장을 끝냈는데 응답이 늦어 앱이 타임아웃으로 실패했다고 알면 앱은 같은 클릭을 다시 보냅니다. 그러면 서버 로그에는 같은 클릭이 두 줄 남습니다.

**결국 서버 로그 하나 안에 셋째 줄 때문에 모자란 클릭(누락)과 넷째 줄 때문에 겹친 클릭(중복)이 함께 있습니다.** 셋째 상황은 서버의 건수를 줄이고 넷째 상황은 늘리므로, 두 상황이 같은 날 섞이면 총계만 보고는 어느 쪽 때문인지 알 수 없습니다.

그래서 앱과 서버 가운데 「어느 쪽이 맞나」를 따지지 않고 **무엇을 측정할 때 어느 쪽 기록을 보는지**를 미리 정해 둡니다. 이 결정은 나중에 정산(광고비와 매출을 확정하는 계산) 회의에서 서로 말이 맞지 않는 일을 막아 줍니다.

**돈과 관련된 숫자는 서버 쪽 기록이 정본(기준으로 삼는 기록)입니다.** 남의 기기가 보낸 숫자는 누군가 고쳐 보낼 수 있으므로(2절 표의 세 번째 줄과 같은 까닭) 과금(광고주에게 광고비를 매기는 일), 정산, 리포트에 쓰는 건수로는 서버가 센 985건을 씁니다.

**반대로 「얼마나 실패했나」는 앱 쪽 기록에서만 보입니다.** 서버는 도착하지 못한 요청을 셀 수 없으므로 1,000건과 985건의 차이인 15건은 앱 쪽 기록에만 남습니다. 그래서 서버 그래프는 평평한데 사용자만 요청이 안 되는 일이 생깁니다.

앱 쪽 기록과 서버 쪽 기록을 같은 요청끼리 연결하려면 양쪽이 같은 요청 번호를 써야 합니다. 앱이 요청 번호를 만들어 `X-Request-Id` 헤더에 담아 보내면 서버는 그 값을 그대로 자기 로그 줄에 적습니다. 이 헤더 없이 온 요청에는 서버가 번호를 만들어 붙입니다. 7절에서 본 `request_id` 가 바로 이 요청 번호입니다.

다만 8절에서 본 것처럼 앱 쪽 기록도 결국 요청으로 보내야 서버에 닿으므로 **앱 쪽 기록을 보내는 전송도 실패할 수 있습니다.** 신호가 끊긴 곳에서는 실패했다는 기록조차 보내지 못하므로 앱은 실패 기록을 모아 두었다가 보낼 수 있을 때 다시 보냅니다.

앱과 서버 사이에 게이트웨이나 프록시(요청을 받아 서버로 넘겨 주는 중간 서버)가 있으면 그 중간 서버도 자기 줄을 남기므로 한 요청의 기록이 3줄이 됩니다. 중간에 무엇이 어디에 끼는지는 [로드밸런서, Ingress, API Gateway](post.html?id=gateway-ingress-router) 편에 있습니다.

## 10. 100만 줄을 API 로 넘기는 방법

**API 로도 대량 데이터를 주고받을 수 있지만 한 번의 요청에 다 담지 않고 나눠 보냅니다.**

클릭 로그 100만 줄을 다른 쪽에 API 로 넘겨야 하는 상황을 생각해 보겠습니다. 아래가 클릭 로그 한 줄이고 한 줄의 크기는 평균 90바이트입니다.

```json
{"click_id":"c-0000001","ts":"2026-08-16T16:48:21Z","ad_id":9931,"user":"u-482913"}
```

한 줄 평균 90바이트짜리가 100만 줄이면 전체는 **86MB** 입니다. 이 86MB 를 몇 줄씩 나눠 보내느냐와 압축을 켜느냐에 따라 요청 하나의 크기가 아래 표처럼 달라집니다.

| 보내는 방법 | 요청 수 | 한 번에 보내는 크기 |
|---|---|---|
| 한 번에 다 | 1 | 86 MB |
| 1,000줄씩 나눠 | 1,000 | 88 KB |
| 10,000줄씩 나눠 | 100 | 879 KB |
| 10,000줄씩 나눠 + gzip | 100 | 131 KB |

표의 둘째 줄과 셋째 줄처럼 100만 줄을 1,000줄씩 나누면 요청이 1,000번, 10,000줄씩 나누면 100번이 됩니다. 이때 요청 하나의 크기는 각각 88KB 와 879KB 입니다. 넷째 줄처럼 gzip(반복되는 글자열을 짧게 줄여 쓰는 압축 방식)을 켜면 요청 하나가 879KB 에서 131KB 로, 원본의 14.9% 크기로 줄어듭니다. 로그는 줄마다 값은 달라도 `click_id`, `ts`, `ad_id` 같은 **키 이름이 100만 번 반복**되는 성질이 있어 gzip 이 그 반복을 없애면 이만큼 작아집니다.

표의 맨 위 줄처럼 86MB 를 요청 하나에 담으면 세 가지 문제가 한꺼번에 생깁니다.

- 받는 쪽은 86MB 를 다 받을 때까지 아무것도 하지 못합니다.
- 전송이 중간에 끊기면 처음부터 다시 보내야 합니다.
- 서버가 86MB 전부를 메모리에 올려야 합니다.

**10,000줄씩 100번으로 나누면 요청 하나가 879KB 라 세 문제가 모두 풀립니다.** 받는 쪽은 879KB 짜리 요청을 하나 받을 때마다 처리를 시작할 수 있습니다. 전송이 끊겨도 끊긴 요청 하나만 다시 보내면 됩니다. 서버가 메모리에 올리는 크기도 요청 하나만큼으로 작아집니다. 여기에 압축까지 켜면 요청 하나는 131KB 가 됩니다.

**그래서 이 표에서는 10,000줄씩 나누고 압축을 켜는 방식을 기본값으로 고릅니다.** 이 기본값에서 벗어나는 경우는 두 가지입니다. 보낼 데이터가 수십 GB 로 아주 크면 요청에 담지 않고 파일로 올려 둔 뒤 그 파일의 위치만 알려 줍니다. 반대로 우리가 데이터를 받아 오는 입장이면 조금씩 나눠 받으면서 다음에 받을 위치(커서)를 응답이 알려 주게 합니다.

**처음에는 잘 떠오르지 않는 방식이 하나 더 있습니다.** 한 달치 정산 자료처럼 만드는 데 몇 분씩 걸리는 자료는 요청을 받은 그 자리에서 응답에 담아 줄 수 없습니다. 그래서 부르는 쪽이 `POST /v1/reports` 로 「만들어 주세요」라고 요청하면 서버는 상태 코드 `202`(받기는 했고 처리는 아직 끝나지 않았다는 뜻)와 접수 번호만 먼저 돌려줍니다. 부르는 쪽은 그 접수 번호로 `GET /v1/reports/{번호}` 를 가끔 불러 확인하다가 자료가 다 만들어졌을 때 받아 갑니다. 이렇게 가끔 불러 확인하는 방식을 폴링(polling)이라고 부릅니다.

받아 올 목록을 서버가 어떻게 나눠 주는지는 [API 연동 실무](post.html?id=api-kinds-and-contracts) 편에서 방식별 성능 비교와 함께 다룹니다.

## 11. 광고 클릭 API 하나의 설계 순서

**앞의 10개 절에서 정한 것이 실제 API 하나에 어떻게 한꺼번에 들어가는지 광고 클릭 API 로 봅니다.**

지훈 씨가 맡은 첫 API 는 사용자가 광고를 클릭하면 그 사실을 서버에 알리는 API 입니다. 앞 절들에서 정한 것을 순서대로 하나씩 적용하면 이 API 하나가 완성됩니다.

**맨 먼저 누가 이 API 를 부르는지 정합니다.** 이 API 는 사용자의 기기에 깔린 앱이 부르는 2절의 client to server 라서 앱에 비밀키를 담을 수 없고 앱이 보낸 값은 서버가 전부 다시 검사합니다. 클릭을 받으면 서버에 기록이 새로 생기므로 3절의 기준대로 메서드는 `POST` 로 정합니다. 주소는 5절의 관례대로 동사를 빼고 `POST /v1/events` 로 짓습니다. 공개 범위는 아무나 부를 수 있게 열되 보낸 값은 믿지 않는 방식을 고릅니다.

**응답을 무엇으로 줄지는 광고에서 특히 따져 볼 문제입니다.** 사용자가 클릭을 눌렀는데 앱 화면이 멈추면 안 되므로 서버는 기록이 다 끝날 때까지 기다리지 않고 10절에서 본 `202` 와 접수 번호만 먼저 답한 다음 실제 저장은 응답을 보낸 뒤에 이어서 합니다. 4절에서 본 「요청 하나에 응답 하나」는 여기서도 그대로라 서버가 저장을 기다리지 않는다고 해서 응답이 없어지지는 않습니다.

**그다음에는 8, 9절에서 본 문제를 처리합니다.** 앱이 보내지 못한 클릭은 서버 로그에 아예 없으므로 앱이 자기 쪽 실패 건수를 따로 세어 보내야 합니다. 이 실패 건수마저 보내지 못하면 그 클릭은 아무 데도 남지 않습니다. 또 클릭 하나마다 요청을 하나씩 보내면 지하철처럼 신호가 약한 곳에서는 요청이 다 실패하므로, 앱은 클릭 몇 개를 모아 두었다가 요청 하나로 한 번에 보내고 그 요청이 실패하면 그 요청만 다시 보냅니다.

**처음 API 를 만들 때도 이 절과 같은 순서를 따릅니다.**

1. 누가 부르는지부터 정합니다.
2. 메서드와 주소를 고릅니다.
3. 응답 모양과 공개 범위를 결정합니다.
4. 마지막에 로그와 대량 처리를 추가합니다.

순서를 뒤집어 코드부터 짜면 대체로 앞의 세 단계를 다시 정하게 됩니다.

이 API 가 받은 클릭 한 건은 서버에 두 줄을 남기는 데서 끝나지 않습니다. 8절에서 남긴 그 두 줄이 그다음 어디로 가는지를 이 트랙의 뒤쪽 글들이 다룹니다.

## 한눈 정리

| 질문 | 한 줄 답 |
|---|---|
| POST 는 수정하라는 뜻인가 | 아닙니다. "이걸 처리해 주세요"입니다. 수정은 PUT, PATCH |
| POST 인데 왜 데이터가 오나 | 요청 하나에 응답 하나가 항상 짝입니다. 메서드와 응답은 별개 |
| 조회인데 POST 를 써도 되나 | 조건이 주소에 안 들어갈 때만. 주소에 `search` 를 남깁니다 |
| GET 으로 데이터를 바꿔도 되나 | 안 됩니다. 검색 로봇이 스캔하는 것만으로 사고가 납니다 |
| client, server 구분이 왜 중요한가 | 남의 기기에는 비밀키를 못 담고 보낸 값을 못 믿습니다 |
| 주소를 어떻게 짓나 | 동사 빼고 복수형 명사. 소속은 경로로, 버전은 앞에 |
| API 를 어디까지 여나 | 내부, 파트너, 공개 세 등급. 좁게 열고 넓히는 쪽이 쌉니다 |
| 로그에 무엇을 남기나 | 요청 번호, 상태, 걸린 시간. 민감한 필드는 값만 `***` |
| 그 로그가 어디에 남나 | 접속 로그는 코드 없이, 이벤트 로그는 앱이 보내야 |
| 앱과 서버 숫자가 다르면 | 돈은 서버 쪽, 실패율은 앱 쪽이 정본입니다 |
| 대량 데이터를 보낼 수 있나 | 나눠 보냅니다. 크면 파일로, 오래 걸리면 접수 번호로 |

## 헷갈리기 쉬운 점

- **POST 를 「데이터를 보내는 것」으로만 외우지 않습니다.** 무엇을 보내는지와 무엇을 받는지는 서로 상관이 없어서 4절의 세 요청은 `GET` 이든 `POST` 든 모두 응답을 받았습니다.
- **`GET` 요청은 서버에서 아무것도 바꾸지 않아야 합니다.** `GET /posts/12/delete` 같은 주소를 만들면 검색 로봇이 그 주소를 한 번 스캔하기만 해도 글이 지워지는 사고가 납니다.
- **주소에는 동사를 넣지 않습니다.** 메서드가 이미 동사 역할을 하므로 `POST /createUser` 는 「만들어라」를 두 번 말합니다.
- **화면에서 막아 두었다고 요청까지 막힌 것은 아닙니다.** 누구든 화면을 거치지 않고 요청만 직접 보낼 수 있으므로 서버가 값을 다시 검사합니다.
- **상태 코드 `200` 의 본문에 실패를 담지 않습니다.** 부르는 쪽 코드도 감시 도구도 상태 코드만 보고 성공으로 세므로 실패가 묻힙니다.
- **`401` 과 `403` 은 다른 상태 코드입니다.** 로그인을 하지 않았으면 401, 로그인은 했지만 권한이 없으면 403 입니다.
- **로그에서 민감한 필드를 지우지 않고 값만 숨깁니다.** 필드를 남겨 두어야 나중에 「그 값을 보내긴 했나」를 따질 수 있습니다.
- **접속 로그만으로 「어느 광고였나」를 찾지 않습니다.** 앱이 보내는 요청의 주소는 전부 `/v1/events` 로 같아서 광고 번호는 이벤트 로그에만 있습니다.
- **서버 로그만 보고 「장애 없음」이라고 판단하지 않습니다.** 서버에 도착하지 못한 요청은 서버 로그에 한 줄도 남지 않습니다.
- **API 를 일단 다 열어 두지 않습니다.** 여는 데는 하루면 되지만 닫는 데는 몇 달이 걸립니다.
