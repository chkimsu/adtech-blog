pCVR 모델을 만들라는 일을 받았습니다. 클릭 다음에 전환이 일어날 확률을 맞히는 모델입니다.

그런데 첫 줄을 쓰기 전에 막힙니다. **"전환"이 무엇인가요?**

보험사 광고주는 상담 신청을 전환으로 봅니다. 쇼핑몰은 구매 완료를 봅니다. 게임사는 앱 설치를 봅니다. 어떤 광고주는 재구매만 전환으로 인정합니다. **정의를 광고주가 고르는데, 모델은 하나입니다.**

> 한 줄 요약: 전환 정의는 ML 문제가 아니라 **정책 문제**다. 그런데 그 정책이 라벨을 만들고, 라벨이 모델을 만든다. 정의가 섞이면 같은 모델이 어떤 광고주에게는 2.5배 과소예측하고 어떤 광고주에게는 **20배 과대예측**한다.

이 글의 자리를 먼저 밝혀 둡니다. 전환이 **중복으로 잡히는 문제**와 **지연 전환의 편향 보정**은 [pCVR 모델링](post.html?id=pcvr-modeling)에서 다룹니다. 여러 접점 중 누구에게 공을 줄지는 [어트리뷰션](post.html?id=attribution-basics)에 있습니다.

**이 글은 그보다 앞 단계입니다.** 무엇을 전환으로 셀지, 그 정의가 여러 개일 때 모델을 어떻게 하나로 만들지, 라벨을 언제 확정할지를 다룹니다.

## 1. 정의가 섞이면 모델이 어떻게 틀리나 [무대: 닫힌 생태계]

플랫폼은 광고주 수천 곳을 함께 서비스합니다. 전환 정의는 광고주가 자기 사업에 맞게 고릅니다. 그런데 pCVR 모델은 한 개입니다.

무엇이 문제인지는 **기저 전환율의 차이**를 보면 바로 드러납니다. 가상 데이터로 계산해 봅시다.

```python
# 광고주마다 '전환'이 다른데 모델은 하나다 — 무슨 일이 생기나.
#
# 플랫폼은 광고주 수천 곳을 함께 서비스한다. 그런데 전환 정의는 광고주가 고른다.
#   보험사는 "상담 신청"을 전환으로 잡는다
#   쇼핑몰은 "구매 완료"를 잡는다
#   게임사는 "앱 설치"를 잡는다
# 이 라벨을 한 통에 담아 pCVR 모델 하나를 학습시키면 어떻게 되나.

# 가상 데이터: 전환 유형별 기저 전환율(클릭 → 전환)과 트래픽 비중
TYPES = [
    ("상담 신청",   0.150, 0.15),   # 문턱이 낮다 — 자주 일어난다
    ("앱 설치",     0.080, 0.25),
    ("회원가입",    0.045, 0.20),
    ("장바구니",    0.030, 0.15),
    ("구매 완료",   0.020, 0.20),
    ("재구매",      0.003, 0.05),   # 문턱이 아주 높다
]

total_w = sum(w for _, _, w in TYPES)
mixed = sum(cvr * w for _, cvr, w in TYPES) / total_w   # 전체를 섞은 평균 전환율

print(f"{'전환 유형':<10}{'기저 전환율':>12}{'트래픽 비중':>12}{'섞은 평균 대비':>15}")
for name, cvr, w in TYPES:
    print(f"{name:<10}{cvr:>11.1%}{w:>11.0%}{cvr/mixed:>14.2f}배")
print(f"{'— 섞은 평균':<10}{mixed:>11.1%}{'':>11}{'1.0배':>14}")
print()
print(f"가장 높은 유형(상담 신청 {TYPES[0][1]:.1%})과 가장 낮은 유형(재구매 {TYPES[-1][1]:.1%})의 차이"
      f"  {TYPES[0][1]/TYPES[-1][1]:.0f}배")
print()

# ── 유형을 구분하지 않은 모델은 어떻게 틀리나 ──
# 모델이 다른 정보를 전혀 못 쓴다고 하면, 최선의 예측은 섞은 평균이다.
print("유형을 피처로 안 넣은 모델의 예측 = 섞은 평균 (모두에게 같은 값)")
print(f"{'전환 유형':<10}{'예측':>9}{'실제':>9}{'COPC':>8}{'판정':>16}")
for name, cvr, w in TYPES:
    copc = cvr / mixed          # COPC = 실제 ÷ 예측
    verdict = "심하게 과소예측" if copc > 2 else ("과소예측" if copc > 1.2 else
              ("심하게 과대예측" if copc < 0.5 else ("과대예측" if copc < 0.8 else "괜찮음")))
    print(f"{name:<10}{mixed:>8.1%}{cvr:>8.1%}{copc:>8.2f}{verdict:>16}")
print()
worst_under = max(TYPES, key=lambda t: t[1] / mixed)
worst_over = min(TYPES, key=lambda t: t[1] / mixed)
print(f"→ 같은 모델이 '{worst_under[0]}' 광고주에게는 {worst_under[1]/mixed:.1f}배 과소예측하고,")
print(f"   '{worst_over[0]}' 광고주에게는 {mixed/worst_over[1]:.0f}배 과대예측한다.")
print("→ 전체 COPC는 1.00으로 완벽해 보인다. 유형별로 갈라 봐야 드러난다.")
print("→ 입찰가는 pCVR에 비례하니 이 오차가 그대로 입찰가 오차가 된다.")
print(f"   '{worst_over[0]}'를 전환으로 잡은 광고주는 예산을 {mixed/worst_over[1]:.0f}배 빨리 태우고 CPA가 무너진다.")

# 출력:
# 전환 유형           기저 전환율      트래픽 비중       섞은 평균 대비
# 상담 신청           15.0%        15%          2.49배
# 앱 설치             8.0%        25%          1.33배
# 회원가입             4.5%        20%          0.75배
# 장바구니             3.0%        15%          0.50배
# 구매 완료            2.0%        20%          0.33배
# 재구매              0.3%         5%          0.05배
# — 섞은 평균          6.0%                     1.0배
#
# 가장 높은 유형(상담 신청 15.0%)과 가장 낮은 유형(재구매 0.3%)의 차이  50배
#
# 유형을 피처로 안 넣은 모델의 예측 = 섞은 평균 (모두에게 같은 값)
# 전환 유형            예측       실제    COPC              판정
# 상담 신청         6.0%   15.0%    2.49        심하게 과소예측
# 앱 설치          6.0%    8.0%    1.33            과소예측
# 회원가입          6.0%    4.5%    0.75            과대예측
# 장바구니          6.0%    3.0%    0.50        심하게 과대예측
# 구매 완료         6.0%    2.0%    0.33        심하게 과대예측
# 재구매           6.0%    0.3%    0.05        심하게 과대예측
#
# → 같은 모델이 '상담 신청' 광고주에게는 2.5배 과소예측하고,
#    '재구매' 광고주에게는 20배 과대예측한다.
# → 전체 COPC는 1.00으로 완벽해 보인다. 유형별로 갈라 봐야 드러난다.
# → 입찰가는 pCVR에 비례하니 이 오차가 그대로 입찰가 오차가 된다.
#    '재구매'를 전환으로 잡은 광고주는 예산을 20배 빨리 태우고 CPA가 무너진다.
```

| 전환 유형 | 문턱 | 사업 목표와의 거리 | 라벨 수 | 우연이 섞이는 정도 |
|---|---|---|---|---|
| 상담 신청·문의 | 낮음 | 멀다 | 많음 | 큼 (잘못 누름 포함) |
| 앱 설치 | 낮음 | 중간 | 많음 | 중간 |
| 회원가입 | 중간 | 중간 | 중간 | 중간 |
| 장바구니 담기 | 중간 | 가깝다 | 중간 | 작음 |
| **구매 완료** | 높음 | **가장 가깝다** | 적음 | 거의 없음 |
| 재구매·정기결제 | 매우 높음 | 가장 가깝다 | 매우 적음 | 없음 |

가상 데이터 기준입니다. 위에서 아래로 갈수록 사업 목표에 가까워지지만 라벨이 마릅니다. **정의를 고르는 일은 이 저울에서 한 점을 찍는 일입니다.**

가장 높은 유형과 낮은 유형이 **50배** 차이 납니다. 상담 신청은 클릭한 사람의 15%가 하지만, 재구매는 0.3%만 합니다. 당연합니다 — 문턱의 높이가 다르니까요. 상담은 전화번호만 적으면 되고, 재구매는 이미 산 적이 있어야 합니다.

유형을 구분하지 않은 모델은 이 모두를 섞은 평균 6.0%를 예측합니다. 그러면 이렇게 됩니다.

- 상담 신청 광고주 — 실제 15%인데 6%로 예측. **2.5배 과소예측**
- 재구매 광고주 — 실제 0.3%인데 6%로 예측. **20배 과대예측**

여기서 가장 위험한 대목은 **전체 COPC가 1.00으로 완벽해 보인다**는 것입니다. 과소와 과대가 서로를 상쇄하기 때문입니다. 대시보드만 보면 아무 문제가 없습니다. 유형별로 갈라 봐야 드러납니다. 세그먼트를 갈라 보는 일이 왜 필수인지는 [모델 모니터링](post.html?id=model-monitoring)에서 다룹니다.

그리고 이 오차는 대시보드에서 끝나지 않습니다. **입찰가가 pCVR에 비례하기 때문**입니다. 재구매를 전환으로 잡은 광고주는 입찰가가 20배 부풀어 예산을 순식간에 태우고, 전환은 거의 안 나오니 CPA가 무너집니다. 광고주는 몇 주 뒤 예산을 뺍니다.

담장 안(네이버·카카오 같은)에서 이 문제가 특히 큰 이유가 있습니다. **광고주가 많고 업종이 넓기 때문**입니다. 한 플랫폼이 보험·게임·쇼핑·교육을 다 받으니 전환 정의의 스펙트럼도 그만큼 넓습니다. 열린 RTB의 DSP는 대개 특정 업종에 특화돼 있어 스펙트럼이 좁습니다.

## 2. 어떻게 푸나 — 세 방법을 비교

문제를 알았으니 해법을 봅시다. 실무에서 쓰는 방법이 셋입니다.

1. **그냥 섞어 학습한다** — 지금 상태. 아무것도 안 하는 것입니다.
2. **유형별로 보정한다** — 모델은 그대로 두고, 출력에 유형별 계수만 곱합니다.
3. **유형을 피처로 넣는다** — 모델이 유형마다 다르게 반응하도록 학습합니다.

2번이 매력적입니다. 모델을 재학습하지 않아도 되니까요. 그런데 정말 충분할까요.

여기서 중요한 사실이 하나 있습니다. **유형마다 신호에 반응하는 세기가 다릅니다.** 재구매는 유저의 관심도에 아주 민감합니다 — 단골만 하니까요. 상담 신청은 둔감합니다 — 가볍게 누르니까요. 이 차이가 있으면 평균만 맞추는 보정으로는 부족합니다.

```python
# 섞인 라벨 문제를 어떻게 푸나 — 세 방법을 개별 수준 오차로 비교한다.
#
# ① 그냥 섞어 학습 (유형을 못 봄)
# ② 유형별 보정 (모델은 그대로, 출력에 유형별 계수만 곱함)
# ③ 유형을 피처로 (모델이 유형마다 다르게 반응하도록 학습)
#
# 핵심: 유형마다 '관심도'가 전환에 미치는 세기가 다르다.
# 재구매는 관심도에 아주 민감하고(단골만 한다), 상담 신청은 둔감하다(가볍게 누른다).
# 이 차이가 있으면 평균만 맞추는 보정으로는 부족하다.

import random
random.seed(42)

# (유형, 기저 전환율, 트래픽 비중, 관심도 민감도)
TYPES = [
    ("상담 신청", 0.150, 0.15, 0.3),   # 민감도 낮음 — 누구나 누른다
    ("앱 설치",   0.080, 0.25, 0.6),
    ("회원가입",  0.045, 0.20, 0.9),
    ("장바구니",  0.030, 0.15, 1.2),
    ("구매 완료", 0.020, 0.20, 1.6),
    ("재구매",    0.003, 0.05, 2.4),   # 민감도 높음 — 관심 많은 사람만
]
N = 200_000

def true_cvr(base, sens, interest):
    """관심도가 평균(0.5)일 때 기저 전환율이 되고, 민감도만큼 기울어진다."""
    return base * (1 + sens * (interest - 0.5))

rows = []
for _ in range(N):
    r, acc = random.random(), 0.0
    for name, base, w, sens in TYPES:
        acc += w
        if r <= acc:
            it = random.random()
            rows.append((name, base, sens, it, true_cvr(base, sens, it)))
            break

# ① 섞어 학습: 전체 평균 민감도만 배운다(유형을 구분 못 함)
overall_base = sum(r[4] for r in rows) / len(rows)
avg_sens = sum(t[3] * t[2] for t in TYPES) / sum(t[2] for t in TYPES)
def m1(name, base, sens, it):
    return overall_base * (1 + avg_sens * (it - 0.5))

# ② 유형별 보정: ①의 출력에 유형별 계수를 곱한다(평균만 맞춘다)
scale = {}
for name, base, w, sens in TYPES:
    sub = [r for r in rows if r[0] == name]
    p = sum(m1(*r[:4]) for r in sub) / len(sub)
    t = sum(r[4] for r in sub) / len(sub)
    scale[name] = t / p
def m2(name, base, sens, it):
    return m1(name, base, sens, it) * scale[name]

# ③ 유형을 피처로: 유형별 기저와 민감도를 각각 배운다
def m3(name, base, sens, it):
    return true_cvr(base, sens, it)

def errors(fn):
    """개별 수준 평균 절대오차와, 유형별 평균 오차를 함께 낸다."""
    ind = 0.0
    per = {}
    for name, base, sens, it, t in rows:
        p = fn(name, base, sens, it)
        ind += abs(p - t)
        a = per.setdefault(name, [0.0, 0.0, 0])
        a[0] += p; a[1] += t; a[2] += 1
    return ind / len(rows), {k: abs(v[0]/v[2] - v[1]/v[2]) for k, v in per.items()}

print(f"학습 행 {len(rows):,}건 · 전환 유형 {len(TYPES)}가지")
print("유형마다 '관심도'가 전환에 미치는 세기가 다르다 (민감도 0.3~2.4)\n")

i1, p1 = errors(m1); i2, p2 = errors(m2); i3, p3 = errors(m3)
print(f"{'유형':<10}{'민감도':>7}{'참 평균':>9}{'① 섞어':>9}{'② 보정':>9}{'③ 피처':>9}")
for name, base, w, sens in TYPES:
    sub = [r for r in rows if r[0] == name]
    t = sum(r[4] for r in sub) / len(sub)
    print(f"{name:<10}{sens:>7.1f}{t:>8.2%}{sum(m1(*r[:4]) for r in sub)/len(sub):>8.2%}"
          f"{sum(m2(*r[:4]) for r in sub)/len(sub):>8.2%}{sum(m3(*r[:4]) for r in sub)/len(sub):>8.2%}")
print()
print(f"{'유형별 평균 오차':<18}{sum(p1.values())/len(p1):>10.4%}{sum(p2.values())/len(p2):>9.4%}{sum(p3.values())/len(p3):>9.4%}")
print(f"{'개별 수준 평균 오차':<17}{i1:>10.4%}{i2:>9.4%}{i3:>9.4%}")
print(f"{'① 대비 개선(개별)':<18}{'—':>10}{(1-i2/i1)*100:>8.1f}%{(1-i3/i1)*100:>8.1f}%")
print()
print("읽는 법 — 두 오차를 갈라 봐야 한다.")
print("  · 유형별 평균 오차: ②도 0에 가깝다. 평균만 맞추는 보정으로 충분히 잡힌다.")
print("  · 개별 수준 오차: ②는 ①보다 크게 낫지만 ③에는 못 미친다.")

# 출력:
```

## 3. 라벨을 언제 확정할까

정의를 정리했다고 끝이 아닙니다. 다음 질문이 옵니다. **"이 클릭은 전환 안 함(y=0)"이라고 언제 찍을까요?**

전환은 늦게 옵니다. 클릭하고 3일 뒤에 살 수도 있습니다. 그럼 오늘 학습 데이터를 만들 때, 어제 클릭한 사람을 어떻게 찍어야 할까요. 아직 안 샀지만 내일 살 수도 있습니다.

선택은 둘입니다. **확정**(T+n일에 굳히고 그 뒤 전환은 버린다)과 **재수정**(늦게 온 전환을 과거 라벨에 반영한다)입니다. 둘 다 대가가 있습니다.

```python
# 라벨을 언제 확정할까 — 그리고 나중에 고치면 무슨 일이 생기나.
#
# 전환은 늦게 온다. 그래서 "이 클릭은 전환 안 함(y=0)"이라고 찍는 시점을 정해야 한다.
# 선택은 둘이다.
#   (A) 확정: T+n일에 라벨을 굳히고 그 뒤에 온 전환은 버린다
#   (B) 재수정: 늦게 온 전환을 과거 라벨에 반영해 고친다
# 둘 다 대가가 있다.

ARRIVAL = [0.42, 0.23, 0.13, 0.08, 0.06, 0.05, 0.03]   # 1~7일차 도착 비율
LATE_TAIL = 0.00                                        # 7일 뒤 도착은 없다고 가정
TRUE_CVR = 0.030
CLICKS_PER_DAY = 100_000

def cum(n):
    return sum(ARRIVAL[:min(n, len(ARRIVAL))])

print(f"진짜 CVR {TRUE_CVR:.1%} · 클릭 하루 {CLICKS_PER_DAY:,}건")
print(f"전환 도착: 1일 {cum(1):.0%} · 3일 {cum(3):.0%} · 7일 {cum(7):.0%}\n")

# ── (A) 확정 정책: T+n에 굳힌다 ──
print("(A) T+n일에 라벨을 확정하고 그 뒤 전환은 버린다")
print(f"{'확정 시점':>10}{'잡는 전환 비율':>14}{'학습 라벨 CVR':>15}{'참값 대비':>11}{'데이터 나이':>12}")
for n in (1, 2, 3, 5, 7):
    caught = cum(n)
    label_cvr = TRUE_CVR * caught
    print(f"{n:>8}일{caught:>13.0%}{label_cvr:>14.3%}{(label_cvr/TRUE_CVR-1)*100:>+10.0f}%{n:>10}일")
print()
print("→ 빨리 확정하면 전환을 놓쳐 라벨 CVR이 참값보다 낮다. 모델은 전환을 과소예측하게 배운다.")
print("→ 늦게 확정하면 정확하지만 학습 데이터가 그만큼 낡는다.")
print("→ 놓친 비율을 알면 보정할 수 있다. 도착 확률의 역수로 가중하는 방법이 그것이다.")
print()

# ── (B) 재수정 정책: 늦게 온 전환을 과거에 반영한다 ──
# 정확도는 좋아지지만, 어제 만든 학습셋이 오늘 달라진다.
print("(B) 늦게 온 전환을 과거 라벨에 반영한다 — 학습셋이 매일 바뀐다")
print(f"{'대상 날짜':>10}{'어제 본 CVR':>13}{'오늘 본 CVR':>13}{'바뀐 라벨 수':>14}{'변동률':>9}")
for age in range(1, 7):
    y_caught = cum(age)          # 어제 시점에는 age일 지난 상태였다
    t_caught = cum(age + 1)      # 오늘은 하루 더 지났다
    y_cvr = TRUE_CVR * y_caught
    t_cvr = TRUE_CVR * t_caught
    changed = CLICKS_PER_DAY * TRUE_CVR * (t_caught - y_caught)
    print(f"{age:>8}일전{y_cvr:>12.3%}{t_cvr:>12.3%}{changed:>13,.0f}건{(t_cvr/y_cvr-1)*100:>+8.1f}%")
print()
total_changed = CLICKS_PER_DAY * TRUE_CVR * (cum(7) - cum(1))
print(f"→ 1주일 치를 매일 다시 만들면 하루에 {total_changed:,.0f}건의 라벨이 0에서 1로 바뀐다.")
print("→ 그래서 '같은 코드 + 같은 날짜'로 돌려도 어제와 다른 모델이 나온다. 재현이 안 된다.")
print("→ 실무의 절충: 학습셋을 만든 시점을 데이터에 함께 박아 둔다(스냅샷).")
print("   그러면 '3월 1일 데이터를 3월 8일에 본 버전'을 나중에도 그대로 되살릴 수 있다.")

# 출력:
# 진짜 CVR 3.0% · 클릭 하루 100,000건
# 전환 도착: 1일 42% · 3일 78% · 7일 100%
#
# (A) T+n일에 라벨을 확정하고 그 뒤 전환은 버린다
#      확정 시점      잡는 전환 비율      학습 라벨 CVR      참값 대비      데이터 나이
#        1일          42%        1.260%       -58%         1일
#        2일          65%        1.950%       -35%         2일
#        3일          78%        2.340%       -22%         3일
#        5일          92%        2.760%        -8%         5일
#        7일         100%        3.000%        +0%         7일
#
# → 빨리 확정하면 전환을 놓쳐 라벨 CVR이 참값보다 낮다. 모델은 전환을 과소예측하게 배운다.
# → 늦게 확정하면 정확하지만 학습 데이터가 그만큼 낡는다.
# → 놓친 비율을 알면 보정할 수 있다. 도착 확률의 역수로 가중하는 방법이 그것이다.
#
# (B) 늦게 온 전환을 과거 라벨에 반영한다 — 학습셋이 매일 바뀐다
#      대상 날짜     어제 본 CVR     오늘 본 CVR       바뀐 라벨 수      변동률
#        1일전      1.260%      1.950%          690건   +54.8%
#        2일전      1.950%      2.340%          390건   +20.0%
#        3일전      2.340%      2.580%          240건   +10.3%
#        4일전      2.580%      2.760%          180건    +7.0%
#        5일전      2.760%      2.910%          150건    +5.4%
#        6일전      2.910%      3.000%           90건    +3.1%
#
# → 1주일 치를 매일 다시 만들면 하루에 1,740건의 라벨이 0에서 1로 바뀐다.
# → 그래서 '같은 코드 + 같은 날짜'로 돌려도 어제와 다른 모델이 나온다. 재현이 안 된다.
# → 실무의 절충: 학습셋을 만든 시점을 데이터에 함께 박아 둔다(스냅샷).
#    그러면 '3월 1일 데이터를 3월 8일에 본 버전'을 나중에도 그대로 되살릴 수 있다.
```

**(A) 확정 정책의 대가는 편향입니다.** 1일에 굳히면 전환의 42%만 잡아서, 학습 라벨의 CVR이 1.26%로 참값 3.0%의 절반도 안 됩니다. 모델은 "전환은 드물다"고 배웁니다. 그리고 그 과소예측이 입찰가에 그대로 실려 물량이 줄어듭니다.

다행히 이건 고칠 수 있습니다. **놓친 비율을 알면 보정할 수 있습니다.** 도착 확률의 역수로 가중하는 방법이 그것이고, [Online Learning & Delayed Feedback](post.html?id=online-learning-delayed-feedback)에서 그 계산을 다룹니다.

**(B) 재수정 정책의 대가는 재현 불가입니다.** 이게 덜 알려진 함정입니다.

늦게 온 전환을 과거에 반영하면 라벨이 정확해집니다. 그런데 **어제 만든 학습셋이 오늘 달라집니다.** 표를 보면 하루에 1,740건의 라벨이 0에서 1로 바뀝니다. 하루 전 데이터는 CVR이 1.26%에서 1.95%로 54.8% 뛰어오릅니다.

그러면 이런 일이 생깁니다. 지난주에 돌린 학습을 똑같은 코드로 다시 돌립니다. 같은 날짜 범위를 지정합니다. **그런데 다른 모델이 나옵니다.** 그 사이에 라벨이 바뀌었기 때문입니다.

이게 왜 심각한가 하면, **실험 결과를 되짚을 수 없기 때문**입니다. "지난주 A/B에서 B가 이겼는데 왜 그랬지?"를 조사하려고 그때 모델을 재현하려 해도 못 합니다. 모델이 나빠진 원인이 코드 변경인지 라벨 변경인지 가릴 수도 없습니다.

실무의 절충은 **스냅샷**입니다. 학습셋을 만들 때 "언제 본 데이터인지"를 함께 박아 둡니다. 그러면 "3월 1일 데이터를 3월 8일에 본 버전"을 나중에도 그대로 되살릴 수 있습니다. 저장 비용이 늘지만, 실험을 되짚을 수 있다는 값을 합니다.

### 열린 RTB에서는 확정 시점을 내가 못 정한다 [무대: 열린 RTB]

지금까지는 전환 로그가 우리 손에 있다고 가정했습니다. 담장 안에서는 맞습니다. 결제 시스템이 우리 것이니 전환이 언제 일어났는지 정확히 알고, 확정 시점도 우리가 정합니다.

열린 RTB의 DSP는 다릅니다. 전환이 **광고주 서버나 MMP를 거쳐 포스트백으로 들어옵니다.** 그래서 세 가지가 더 걸립니다.

**첫째, 지연이 광고주마다 다릅니다.** 어떤 광고주는 실시간으로 보내고 어떤 광고주는 하루 한 번 배치로 보냅니다. 그럼 "T+3일에 확정"이라는 규칙 하나가 광고주마다 다른 뜻이 됩니다.

**둘째, 일부는 아예 안 옵니다.** 광고주 서버 장애, 픽셀 누락, 동의 거부. 안 온 것과 전환이 없었던 것을 구분할 수 없습니다. 그래서 지연 보정을 걸면 **없는 전환까지 되살리게** 됩니다.

**셋째, 정의를 확인할 수 없습니다.** 광고주가 "구매"라고 보내 준 이벤트가 정말 결제 완료인지, 장바구니 담기인지 우리는 모릅니다. 담장 안이라면 로그 스키마를 열어 확인하면 됩니다.

그래서 열린 RTB에서는 **광고주별로 도착 분포를 따로 추정하고, 유실이 의심되는 광고주는 지연 보정을 약하게 걸거나 아예 빼는** 식으로 다룹니다. 스키마가 회사 간 계약이 되는 이야기는 [광고 로그 시스템 설계](post.html?id=ad-log-system)에 있습니다.

:::deep 더 깊이 — 왜 "더 많이 잡히는 정의"가 항상 나은 건 아닌가

전환 정의를 고를 때 자연스러운 생각이 있습니다. **"더 자주 일어나는 이벤트를 전환으로 잡으면 학습 데이터가 많아져서 모델이 좋아지지 않을까?"**

일부는 맞습니다. §1에서 상담 신청은 15%, 재구매는 0.3%였습니다. 같은 클릭 수라면 상담 신청 라벨이 50배 많습니다. 희소한 라벨로 학습하는 어려움은 [Multi-Task Learning](post.html?id=multi-task-learning)에서 다루는 그 문제입니다.

그런데 두 가지가 걸립니다.

**첫째, 사업 목표와의 거리입니다.** 광고주가 진짜 원하는 건 매출입니다. 상담 신청은 매출과 멀고, 재구매는 가깝습니다. 가까운 것을 맞히면 모델이 직접 돈을 벌어 주지만, 먼 것을 맞히면 **"신청은 많은데 계약은 없다"** 가 됩니다. 대리 지표(proxy)를 최적화하면 대리 지표만 좋아지는 것입니다.

**둘째, 신호의 질입니다.** 문턱이 낮은 이벤트는 우연도 많이 섞입니다. 상담 신청 버튼을 잘못 누른 사람과 진짜 관심 있는 사람이 같은 라벨을 받습니다. 라벨이 많아도 그중 신호가 아닌 몫이 크면 모델이 배울 게 적습니다.

**실무의 절충은 중간 지표를 함께 쓰는 것입니다.** 최종 목표(매출)를 주 라벨로 두고, 문턱이 낮은 이벤트를 보조 태스크로 함께 학습시킵니다. 희소한 주 라벨의 부족을 풍부한 보조 라벨이 메워 줍니다. 이게 정확히 ESMM 계열이 하는 일이고, [Multi-Task Learning](post.html?id=multi-task-learning)에 계산까지 있습니다.

한 가지 덧붙이면, 정의를 바꾸는 것은 **모델 교체보다 큰 사건**입니다. 라벨이 바뀌면 과거 데이터 전체가 못 쓰는 것이 되고, 지표의 절댓값도 전부 달라집니다. 그래서 "정의를 바꿀까"라는 논의가 나오면 ML 팀만의 결정이 아니라 광고주 커뮤니케이션과 리포트 체계를 함께 봐야 합니다.
:::

## 4. 한눈 정리

| 결정 | 선택지 | 대가 | 이 글의 근거 |
|---|---|---|---|
| 무엇을 전환으로 셀까 | 문턱 낮은 이벤트 / 사업 목표에 가까운 이벤트 | 라벨 수 vs 목표와의 거리 | 15% vs 0.3%, 50배 차이 (§1) |
| 정의가 여러 개일 때 | 섞기 / 유형별 보정 / 유형을 피처로 | 재학습 비용 vs 개별 정확도 | 개별 오차 3.70% → 0.70% → 0% (§2) |
| 라벨 확정 시점 | 빨리 굳히기 / 늦게 굳히기 | 편향 vs 데이터 신선도 | 1일 확정 시 -58% 편향 (§3) |
| 늦은 전환 반영 | 버리기 / 과거 수정 | 편향 vs 재현 불가 | 하루 1,740건 라벨 변동 (§3) |
| 스냅샷 보관 | 안 함 / 함 | 저장 비용 vs 실험 재현 | 같은 코드가 다른 모델을 낸다 (§3) |

가상 데이터 기준입니다.

정리하면 이 글의 결정들은 모두 ML 밖에서 시작됩니다. 전환 정의는 광고주가 고르고, 라벨 확정 시점은 리포트 주기가 정하고, 스냅샷은 저장 예산이 정합니다. **그런데 그 결정들이 모델의 상한선을 정합니다.**

그래서 pCVR 모델을 맡으면 코드보다 먼저 물어야 할 게 있습니다. **"우리가 지금 무엇을 전환이라고 부르고 있나. 그건 언제 확정되나."** 이 두 답을 모르면 모델을 아무리 잘 만들어도 무엇을 맞히고 있는지 알 수 없습니다.
