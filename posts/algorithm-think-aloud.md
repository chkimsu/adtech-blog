라이브 코딩 면접에서 문제를 받고 15분 동안 아무 말 없이 코드를 썼는데, 다 쓰고 나서 면접관이 「같은 입찰가가 두 번 나오면 어떻게 되나요?」라고 묻습니다. 그 경우는 이미 머릿속에서 생각해 두었지만 말하지 않았으므로 면접관은 알 수 없었고, 중간에 잘못 읽은 자리가 있었다면 면접관이 힌트를 줄 시점도 이미 지나 있습니다.

라이브 코딩은 면접관이 보는 앞에서 정해진 시간 안에 문제를 푸는 형식이고, 면접관이 평가에 쓸 수 있는 것은 화면의 코드와 지원자가 소리 내어 한 말뿐입니다. 그래서 같은 코드를 써도 「왜 이 자료구조를 골랐는지」, 「어떤 입력을 걱정했는지」를 말로 한 사람과 하지 않은 사람은 면접관이 보는 정보의 양이 다릅니다.

**말하며 푸는 것은 무엇을 어떤 순서로 말한다는 뜻일까요?**

이 글은 말하며 풀기(think aloud, 생각하는 과정을 소리 내어 설명하며 푸는 것)를 아홉 단계의 순서로 정리하고, 지어낸 광고 입찰가 문제 하나를 그 순서대로 풀며 단계마다 실제로 할 말을 코드 옆에 적습니다. 순서를 정해 두면 말할 거리를 그때그때 찾지 않아도 되므로, 긴장한 상태에서도 질문과 테스트를 빠뜨리지 않습니다.

> **한 줄 요약:** 문제를 다시 말하고, 입력 크기와 빈 입력과 중복과 돌려줄 모양을 묻고, 느린 풀이와 그 비용을 먼저 말한 뒤 더 나은 풀이와 비용을 말해 동의를 받고, 코드를 쓰며 설명하고, 테스트 입력을 손으로 따라가고, 복잡도와 시간이 더 있으면 할 일을 말합니다. 이 글의 예제에서 n 이 10만이면 모든 쌍을 보는 풀이는 약 50억 번, 해시 풀이는 10만 번을 봅니다.

> **골라 읽는 법** — 절이 아홉 개인 글입니다.
>
> - 아홉 단계의 순서 → 1절
> - 예제 하나를 말하며 처음부터 끝까지 → 2~6절
> - 막혔을 때와 힌트를 받을 때 → 7절
> - 복잡도와 마무리 말 → 8절
> - 영어 면접에서 쓰는 짧은 표현 → 9절

## 1. 말하며 풀기의 아홉 단계

**순서는 다시 말하기, 확인 질문, 느린 풀이와 비용, 더 나은 풀이와 비용, 동의 받기, 말하며 코드 쓰기, 손으로 따라가기, 복잡도, 시간이 더 있으면 할 일입니다.**

순서 없이 말하려고 하면 생각나는 것부터 말하게 되어, 코드를 쓰다가 갑자기 입력 크기를 묻거나 복잡도를 말하지 않은 채 끝나는 일이 생깁니다. 아래 표는 [코딩테스트 풀이 순서](post.html?id=algorithm-solving-steps) 편의 다섯 단계를 「소리 내어 말할 것」 기준으로 다시 나눈 것이라, 혼자 푸는 순서와 같고 말로 하는 자리만 늘었습니다.

| 단계 | 소리 내어 말할 것 | 끝나면 면접관이 아는 것 | UMPIRE 의 이름 |
|---|---|---|---|
| 1. 다시 말하기 | 문제를 자기 말로 한두 문장 | 지원자가 문제를 맞게 읽었는지 | Understand |
| 2. 확인 질문 | 입력 크기, 빈 입력, 중복, 돌려줄 모양 | 지원자가 경계 입력을 떠올렸는지 | Understand |
| 3. 느린 풀이와 비용 | 브루트 포스와 그 시간 복잡도 | 적어도 맞는 풀이 하나는 있다는 것 | Match |
| 4. 더 나은 풀이와 비용 | 자료구조, 접근 방법, 시간과 공간 복잡도 | 무엇을 쓰려는지와 왜 빠른지 | Match, Plan |
| 5. 동의 받기 | 「이 방법으로 짜도 될까요?」 | 방향이 틀렸다면 지금 고칠 수 있다는 것 | Plan |
| 6. 말하며 코드 쓰기 | 지금 쓰는 줄이 계획의 어느 부분인지 | 코드와 계획이 맞는지 | Implement |
| 7. 손으로 따라가기 | 테스트 입력 하나를 변수 값과 함께 한 줄씩 | 코드가 실제로 맞는지 | Review |
| 8. 복잡도 | 시간과 공간 복잡도, 그 까닭 | 지원자가 자기 코드의 비용을 아는지 | Evaluate |
| 9. 시간이 더 있으면 | 더 다룰 입력, 다른 방법의 장단점 | 다음 질문으로 이어 갈 거리 | Evaluate |

UMPIRE 는 CodePath 의 면접 안내서가 쓰는 여섯 단계(Understand, Match, Plan, Implement, Review, Evaluate)이고, 그 안내서는 면접을 대화로 보고 테스트 케이스와 질문으로 요구를 먼저 확인하며 끝에는 장단점과 복잡도를 면접관과 이야기하라고 합니다. Tech Interview Handbook 의 체크리스트도 「바로 코딩에 들어가지 말 것」, 「코딩하면서 무엇을 하려는지 설명할 것」, 「복잡도를 말할 것」을 따로 적어 두었습니다. 다만 면접관이 무엇을 얼마나 중요하게 보는지는 회사와 면접관마다 다르고 공개된 기준이 없으므로, 이 표는 공개 안내서들이 권하는 순서를 정리한 것이지 채점표가 아닙니다.

2절부터 이 순서로 문제 하나를 풉니다. 2절에서 문제를 다시 말하고 질문하고, 3~4절에서 두 풀이의 비용을 말하고 동의를 받고, 5~6절에서 말하며 코드를 쓰고 손으로 따라갑니다.

## 2. 다시 말하기와 확인 질문

**문제를 자기 말로 한 번 다시 말하고, 입력이 얼마나 큰지, 비어 있을 수 있는지, 같은 값이 있는지, 무엇을 어떤 모양으로 돌려줘야 하는지를 묻습니다.**

다시 말하기를 건너뛰면 문제를 잘못 읽은 것을 코드가 다 끝난 뒤에야 알게 되는데, 한두 문장으로 다시 말해 두면 면접관이 그 자리에서 「아니요, 위치가 아니라 값을 돌려주세요」처럼 바로잡을 수 있습니다. 확인 질문도 같아서, 지문에 적혀 있지 않은 것을 가정하고 짜면 그 가정이 틀렸을 때 코드 전체를 고쳐야 합니다.

설명을 위해 문제 하나를 지어냈습니다. 같은 모양의 문제가 LeetCode 에 Two Sum 이라는 이름으로 있지만, 아래 지문과 입찰가와 면접관의 답은 이 글이 만든 가상 데이터입니다.

> **지문(가상):** 광고 지면 하나에 광고 두 개를 함께 싣는데, 두 광고의 입찰가 합이 정확히 `target` 원이어야 합니다. 입찰가 리스트 `bids` 에서 합이 `target` 인 서로 다른 두 광고의 위치를 돌려줍니다.

| 지원자가 하는 말 | 면접관의 답(가상) | 코드에 남는 것 |
|---|---|---|
| 「입찰가 리스트에서 합이 target 인 두 광고를 찾아 위치 두 개를 돌려주는 문제로 이해했습니다. 맞습니까?」 | 맞습니다 | 돌려줄 것은 값이 아니라 위치 |
| 「리스트 길이는 최대 얼마입니까?」 | 10만까지입니다 | 목표는 O(n log n) 이하 |
| 「빈 리스트나 하나뿐인 리스트가 들어올 수 있습니까?」 | 들어올 수 있습니다 | 빈 리스트를 돌려주는 경로 |
| 「같은 입찰가가 두 번 나올 수 있습니까? 같은 광고를 두 번 써도 됩니까?」 | 나올 수 있고, 같은 광고는 두 번 쓰지 않습니다 | 위치가 서로 다른지 확인 |
| 「답이 여럿이면 아무거나 하나입니까? 없으면 무엇을 돌려줍니까?」 | 아무거나 하나, 없으면 빈 리스트입니다 | `return []` |

마지막 칸이 질문의 쓸모입니다. 다섯 질문으로 위치를 돌려준다는 것, 목표 복잡도, 빈 리스트 경로, 같은 광고를 두 번 쓰지 않는 조건, 답이 없을 때의 값이 정해졌고, 이것이 6절에서 돌릴 경계 입력 목록이 됩니다. 질문 수는 정해진 것이 없고, Tech Interview Handbook 은 확인 질문을 적어도 두세 개 하라고 권합니다.

## 3. 느린 풀이와 비용

**곧바로 빠른 풀이를 짜지 말고, 모든 경우를 보는 느린 풀이와 그 비용을 먼저 말합니다. 이 예제에서는 모든 두 입찰의 쌍을 보는 O(n^2) 풀이입니다.**

느린 풀이를 먼저 말하는 까닭은 두 가지입니다. 하나는 「적어도 맞는 답을 내는 방법은 안다」는 것을 면접관에게 먼저 보여 두는 것이고, 다른 하나는 그 풀이의 비용을 숫자로 말해야 「그래서 더 빠른 방법이 필요하다」가 근거를 갖는다는 것입니다. 브루트 포스(brute force)는 가능한 경우를 빠짐없이 다 보는 풀이를 말하고, 이 문제에서는 위치 i 와 그보다 뒤의 위치 j 로 만든 쌍을 모두 더해 보는 것입니다.

```python
# 하는 일: 가상 입찰가 6개에서 브루트 포스로 답을 구하고, n 이 6, 1,000, 10만일 때 두 풀이가 보는 횟수를 비교한다.
# 1단계: 브루트 포스 풀이를 만든다
# 모든 두 입찰의 쌍을 앞에서부터 보고, 합이 target 인 첫 쌍의 위치를 돌려준다. 없으면 빈 리스트다.
def two_sum_brute(bids, target):
    checks = 0
    for i in range(len(bids)):
        for j in range(i + 1, len(bids)):
            checks += 1
            if bids[i] + bids[j] == target:
                return [i, j], checks
    return [], checks

# 2단계: 예제를 돌린다
bids = [300, 800, 500, 1200, 700, 500]   # 가상 입찰가(원)
print(f'브루트 포스 답 {two_sum_brute(bids, 1000)[0]}  본 쌍 {two_sum_brute(bids, 1000)[1]}개')
print(f'답이 없을 때 본 쌍 {two_sum_brute(bids, 99)[1]}개')

# 3단계: n 마다 두 풀이가 보는 횟수를 비교한다
# 답이 없는 최악의 경우 브루트 포스는 쌍 n(n-1)/2 개를 모두 보고, 해시 풀이는 입찰 n 개를 한 번씩 본다.
for n in [6, 1_000, 100_000]:
    print(f'n={n:>7,}  브루트 포스 {n*(n-1)//2:>13,}번  해시 {n:>7,}번')

# 출력:
# 2단계 뜻: 300 과 700 의 쌍 [0, 4] 를 넷째 쌍에서 찾았고, 답이 없으면 쌍 15개를 모두 본다.
# 브루트 포스 답 [0, 4]  본 쌍 4개
# 답이 없을 때 본 쌍 15개
# 3단계 뜻: n 이 10만이면 브루트 포스는 약 50억 번, 해시는 10만 번을 본다.
# n=      6  브루트 포스            15번  해시       6번
# n=  1,000  브루트 포스       499,500번  해시   1,000번
# n=100,000  브루트 포스 4,999,950,000번  해시 100,000번
```

찍힌 숫자가 말할 문장을 정해 줍니다. 입찰가 6개에서 쌍은 6 × 5 ÷ 2 = 15개라 손으로도 금방 보지만, 2절에서 물어 둔 최대 길이 10만을 넣으면 100,000 × 99,999 ÷ 2 = 4,999,950,000 이라 약 50억 번이 되고, 단순 연산 1억 회를 1초로 잡는 어림 기준으로도 50초쯤 걸립니다. 그래서 이 자리에서는 「모든 쌍을 보면 O(n^2) 이고 n 이 10만이면 50억 번쯤이라 너무 느립니다. 더 빠른 방법을 찾아보겠습니다」까지 말하고, 브루트 포스 코드는 화면에 쓰지 않고 말로만 넘어가도 됩니다.

브루트 포스를 실제로 코드로 쓸지는 면접관에게 물어 정합니다. Tech Interview Handbook 은 손으로 푼 방법을 그대로 옮긴 비효율적인 풀이라도 돌아가면 점수를 받을 수 있다고 적고 있어서, 빠른 방법이 떠오르지 않을 때는 느린 풀이를 먼저 완성하는 쪽이 아무것도 없는 것보다 낫습니다. 이 풀이는 6절과 7절에서 빠른 풀이의 답을 맞춰 보는 기준으로도 다시 씁니다.

## 4. 더 나은 풀이와 동의

**「각 입찰의 짝이 될 값 target - bid 를 이미 봤는지」를 딕셔너리로 확인하면 한 번 순회로 끝나고, 시간 O(n), 공간 O(n) 입니다. 이것을 말한 뒤 「이 방법으로 짜도 될까요?」라고 묻습니다.**

브루트 포스가 느린 것은 입찰 하나마다 뒤의 모든 입찰을 다시 보기 때문인데, 짝이 될 값은 `target - bid` 하나로 정해져 있으므로 「그 값이 앞에 있었는가」만 빨리 답할 수 있으면 됩니다. 딕셔너리(해시)는 키가 들어 있는지를 평균 O(1) 에 답하므로, 지금까지 본 입찰가를 키로, 그 위치를 값으로 넣어 두면 입찰마다 한 번 찾고 한 번 넣는 것으로 끝납니다.

말로는 이렇게 합니다. 「입찰을 앞에서부터 한 번 보면서, 지금 입찰의 짝인 target - bid 가 앞에서 본 입찰에 있는지 딕셔너리로 찾겠습니다. 있으면 그 위치와 지금 위치를 돌려주고, 없으면 지금 입찰을 딕셔너리에 넣습니다. 시간은 O(n), 딕셔너리 때문에 공간은 O(n) 입니다.」 이 세 문장에 자료구조(딕셔너리), 접근 방법(한 번 순회), 비용(시간과 공간)이 모두 들어 있어서, 면접관은 코드가 나오기 전에 방향이 맞는지 판단할 수 있습니다.

동의를 받는 질문은 시간을 아끼려는 것입니다. 면접관이 「공간을 O(1) 로 줄일 수 있나요?」라고 되물으면 정렬 뒤 투 포인터로 가는 방법이 있지만 정렬하면 원래 위치를 따로 들고 있어야 한다는 장단점을 지금 이야기하면 되고, 방향을 다 짠 뒤에 바꾸는 것보다 훨씬 적게 고칩니다. 두 방법의 원리와 직접 잰 시간은 [해시와 정렬](post.html?id=algorithm-hash-sort) 편과 [복잡도와 배열 순회](post.html?id=algorithm-complexity-array) 편에 있습니다.

## 5. 코드를 쓰는 동안의 설명

**코드 한 줄을 쓸 때마다 그 줄이 4절에서 말한 계획의 어느 부분인지를 짧게 말합니다. 새로운 설명을 하는 것이 아니라 계획을 코드에 맞춰 짚는 것입니다.**

쓰는 동안 말이 끊기면 면접관은 지원자가 계획대로 가는지, 막혔는지, 다른 생각을 하는지 구분할 수 없습니다. 반대로 줄마다 긴 설명을 붙이면 코드가 늦어지므로, Tech Interview Handbook 의 표현대로 말하면서 설명할 수 있을 정도의 속도로 쓰고, 말은 계획의 낱말(짝, 딕셔너리, 앞에서 본 것)을 그대로 다시 씁니다.

| 지원자가 하는 말 | 그때 쓰는 코드 |
|---|---|
| 「앞에서 본 입찰가와 그 위치를 담을 딕셔너리를 만듭니다.」 | `seen = {}` |
| 「위치와 입찰가를 같이 보면서 앞에서부터 한 번 돕니다.」 | `for i, bid in enumerate(bids):` |
| 「지금 입찰의 짝이 될 값을 구합니다.」 | `need = target - bid` |
| 「짝을 앞에서 봤다면 그 위치와 지금 위치를 돌려줍니다.」 | `if need in seen: return [seen[need], i]` |
| 「짝을 찾은 다음에 자기를 넣습니다. 순서를 바꾸면 자기 자신을 짝으로 찾을 수 있어서입니다.」 | `seen[bid] = i` |
| 「끝까지 못 찾으면, 확인한 대로 빈 리스트를 돌려줍니다.」 | `return []` |

다섯째 줄처럼 「왜 이 순서인가」를 말해 두는 자리가 특히 쓸모 있습니다. 2절에서 면접관이 「같은 광고는 두 번 쓰지 않는다」고 답했으므로, 이 줄의 순서가 그 조건을 지키는 자리라는 것을 말로 이어 주면 면접관은 질문과 코드가 연결되어 있다는 것을 봅니다. 이 순서를 바꾸면 무엇이 틀리는지는 7절에서 실행 결과로 봅니다.

## 6. 손으로 따라가기와 경계 입력

**코드를 다 쓰면 「테스트 입력으로 따라가 보겠습니다」라고 말하고, 예제 하나를 변수 값과 함께 한 줄씩 소리 내어 따라간 뒤 2절에서 정한 경계 입력을 돌립니다.**

따라가기를 건너뛰고 「다 됐습니다」라고 하면 면접관이 대신 테스트를 해야 하고, 그때 버그가 나오면 지원자가 찾은 것이 아니라 면접관이 찾은 것이 됩니다. CodePath 안내서는 이 단계를 「맞아 보이는지 보는 것이 아니라 버그를 찾는다고 생각하고 변수를 따라가는 것」으로 설명합니다.

```python
# 하는 일: 말로 설명한 해시 풀이를 짜고, 가상 입찰가 6개를 한 칸씩 따라가며 찍은 뒤 확인 질문에서 나온 경계 입력을 돌린다.
# 1단계: 해시 풀이를 만든다
# seen 은 지금까지 본 입찰가에서 그 위치로 가는 딕셔너리다. 짝을 먼저 찾고 나서 자기를 넣는다. trace 가 참이면 한 칸씩 찍는다.
def two_sum(bids, target, trace=False):
    seen = {}
    for i, bid in enumerate(bids):
        need = target - bid
        if trace:
            print(f'i={i}  bid={bid:4d}  need={need:4d}  seen={seen}')
        if need in seen:
            return [seen[need], i]
        seen[bid] = i
    return []

# 2단계: 예제를 손 풀이와 같은 순서로 따라간다
bids = [300, 800, 500, 1200, 700, 500]   # 가상 입찰가(원)
print(f'답 {two_sum(bids, 1000, trace=True)}')

# 3단계: 확인 질문에서 나온 경계 입력을 돌린다
# 빈 리스트, 하나뿐인 입력, 같은 값 둘, 답이 없는 입력, 0 이 섞인 입력이다.
cases = [([], 1000), ([1000], 1000), ([500, 500], 1000), ([300, 800], 1000), ([0, 1000], 1000)]
for arr, t in cases:
    print(f'{str(arr):12} target={t}  답 {two_sum(arr, t)}')

# 출력:
# 2단계 뜻: 다섯째 입찰 700 에서 짝 300 을 위치 0 에서 찾아 [0, 4] 를 돌려주고, 여섯째 500 은 보지 않는다.
# i=0  bid= 300  need= 700  seen={}
# i=1  bid= 800  need= 200  seen={300: 0}
# i=2  bid= 500  need= 500  seen={300: 0, 800: 1}
# i=3  bid=1200  need=-200  seen={300: 0, 800: 1, 500: 2}
# i=4  bid= 700  need= 300  seen={300: 0, 800: 1, 500: 2, 1200: 3}
# 답 [0, 4]
# 3단계 뜻: 빈 리스트, 하나뿐인 입력, 답이 없는 입력은 빈 리스트이고, 같은 값 둘과 0 이 섞인 입력은 [0, 1] 이다.
# []           target=1000  답 []
# [1000]       target=1000  답 []
# [500, 500]   target=1000  답 [0, 1]
# [300, 800]   target=1000  답 []
# [0, 1000]    target=1000  답 [0, 1]
```

면접에서는 print 를 넣지 않고 위의 다섯 줄을 말로 합니다. 「i 가 0 이면 bid 300, need 700 이고 seen 이 비어 있으니 300 을 넣습니다. i 가 2 면 bid 500, need 500 인데 seen 에는 300 과 800 뿐이라 없고, 자기를 아직 넣지 않았기 때문에 자기 자신을 찾지도 않습니다. i 가 4 면 bid 700, need 300 이 위치 0 에 있으니 [0, 4] 를 돌려줍니다.」 이 말이 찍힌 줄과 한 칸씩 맞고, 3절의 브루트 포스도 같은 [0, 4] 를 냈습니다.

경계 입력에서는 `[500, 500]` 이 2절의 중복 질문에 답합니다. 첫 500 에서는 seen 이 비어 있어 넣기만 하고, 둘째 500 에서 짝 500 을 위치 0 에서 찾아 [0, 1] 을 돌려주므로 같은 값이 둘이면 서로 다른 두 광고로 맞게 찾습니다. `[1000]` 은 짝 0 이 없어 빈 리스트이고, `[0, 1000]` 은 입찰가 0 도 보통 값처럼 다룬다는 것을 보여 줍니다. 입찰가가 0 일 수 있는지는 2절에서 묻지 않았으므로, 실제 면접이라면 이 자리에서 「0 원 입찰도 있을 수 있다고 보고 넣어 봤습니다」라고 말해 둡니다.

## 7. 막힌 자리와 힌트

**막히면 조용히 고민하지 말고 「무엇을 해 봤고, 어느 입력에서 틀리는지」를 말합니다. 힌트를 받으면 자기 말로 다시 말해 확인한 뒤 계획을 고칩니다.**

말없이 막혀 있으면 면접관은 지원자가 어디까지 생각했는지 몰라서 힌트를 언제 어떤 크기로 줄지 정하기 어렵고, 힌트가 늦게 오면 남은 시간에 코드를 끝내지 못할 수 있습니다. 막힌 자리를 말하는 것은 답을 묻는 것과 다르고, 「이 입력에서 이렇게 틀립니다」까지 말하면 면접관은 작은 힌트만 주어도 됩니다.

예를 들어 5절의 마지막 두 줄 순서를 처음에 반대로 썼다고 해 봅니다. 자기를 먼저 넣고 짝을 찾는 판입니다.

```python
# (앞 블록에 이어서 돌린다.)
# 하는 일: 자기를 먼저 넣고 짝을 찾는 버그 판이 같은 입찰을 두 번 쓰는 것을 찍고, 고친 판을 무작위 입력 300개로 브루트 포스와 비교한다.
import random

# 1단계: 넣는 순서를 바꾼 버그 판을 만든다
# seen 에 자기를 먼저 넣으므로, need 가 자기 값과 같으면 자기 위치를 짝으로 찾는다.
def two_sum_bug(bids, target):
    seen = {}
    for i, bid in enumerate(bids):
        seen[bid] = i
        need = target - bid
        if need in seen:
            return [seen[need], i]
    return []

# 2단계: 막힌 자리를 재현한다
# 입찰가 500 하나와 300 하나에서 합 1000 은 답이 없어야 한다.
print(f'버그 판 {two_sum_bug([500, 300], 1000)}  고친 판 {two_sum([500, 300], 1000)}')

# 3단계: 무작위 입력 300개로 고친 판과 브루트 포스를 비교한다
# 답이 여럿이면 두 풀이가 다른 쌍을 고를 수 있으므로, 답이 있는지와 고른 쌍의 합이 맞는지를 본다.
random.seed(1)
bad = 0
for _ in range(300):
    arr = [random.randint(0, 10) * 100 for _ in range(random.randint(0, 8))]
    t = random.randint(0, 20) * 100
    got = two_sum(arr, t)
    want = two_sum_brute(arr, t)[0]
    ok = (got == [] and want == []) or (got != [] and want != [] and got[0] < got[1] and arr[got[0]] + arr[got[1]] == t)
    if not ok:
        bad += 1
print(f'무작위 300개 중 틀린 답 {bad}개')

# 출력:
# 2단계 뜻: 버그 판은 500 하나를 두 번 써서 [0, 0] 을 내고, 고친 판은 답이 없다고 맞게 답한다.
# 버그 판 [0, 0]  고친 판 []
# 3단계 뜻: 무작위 입력 300개에서 고친 판의 답은 브루트 포스와 하나도 다르지 않다.
# 무작위 300개 중 틀린 답 0개
```

버그 판이 `[500, 300]` 에 [0, 0] 을 낸 것은 500 을 seen 에 먼저 넣은 뒤 짝 500 을 찾았더니 방금 넣은 자기 자신이 나왔기 때문이고, 이 답은 같은 광고를 두 번 쓴 것이라 2절의 조건을 지키지 않습니다. 막혔을 때 하는 말은 이 사실을 그대로 옮기는 것입니다. 「500 과 300 에 target 1000 을 넣으면 [0, 0] 이 나옵니다. 같은 위치가 두 번 나오는 걸 보니 자기 자신을 짝으로 찾는 것 같은데, 넣는 자리를 바꿔야 할지 확인해 보겠습니다.」

힌트를 받을 때는 고맙다고 말하고, 힌트를 자기 말로 한 번 다시 말해서 맞게 알아들었는지 확인한 다음 계획의 어느 줄을 바꾸는지 말합니다. 예를 들어 면접관이 「짝을 찾는 것과 넣는 것 중 무엇을 먼저 하면 좋을까요?」라고 물으면 「짝을 먼저 찾고 넣으면 seen 에는 앞의 입찰만 있어서 자기를 찾지 않겠네요. 두 줄 순서를 바꾸겠습니다」라고 답하고 고친 뒤 같은 입력을 다시 돌립니다. 힌트를 받는 것이 점수에 어떤 영향을 주는지는 면접마다 다르고 공개된 기준이 없지만, 힌트를 받고도 말없이 다른 방향으로 가면 면접관은 힌트가 전달됐는지 알 수 없습니다.

무작위 입력 300개의 비교는 혼자 연습할 때 쓰는 방법입니다. 면접 시간 안에 이런 코드를 다 쓰기는 어렵지만, 연습에서 브루트 포스와 빠른 풀이를 비교해 틀린 답 0개를 확인해 두면 면접에서 「같은 문제를 느린 풀이와 비교해 본 적이 있습니다」처럼 근거를 들어 말할 수 있습니다.

## 8. 복잡도와 마무리 말

**마지막에는 시간과 공간 복잡도를 까닭과 함께 한 번 더 말하고, 시간이 더 있으면 무엇을 더할지 한두 가지를 말합니다.**

복잡도를 4절에서 말했더라도 다 쓴 코드를 보며 다시 말하는 까닭은, 계획과 실제 코드가 같은 비용인지를 확인하는 자리이기 때문입니다. 이 예제에서는 「for 문이 입찰을 한 번씩 보고, 딕셔너리 찾기와 넣기가 평균 O(1) 이라 시간은 O(n) 입니다. 딕셔너리에 최대 n 개가 들어가니 공간은 O(n) 입니다. n 이 10만이면 3절에서 본 대로 10만 번이라 브루트 포스의 약 50억 번보다 훨씬 적습니다」까지 말합니다.

「시간이 더 있으면」은 지금 코드가 다루지 않는 것을 지원자가 알고 있다는 것을 보이는 자리입니다. 이 예제라면 아래 셋 가운데 한두 개를 고릅니다.

| 더 다룰 것 | 말하는 문장 |
|---|---|
| 공간을 줄이는 방법 | 「입력이 정렬되어 있다면 투 포인터로 공간 O(1) 에 할 수 있습니다. 정렬부터 해야 하면 O(n log n) 이고 원래 위치를 따로 들고 있어야 합니다.」 |
| 답을 모두 찾는 경우 | 「쌍을 모두 돌려줘야 한다면 딕셔너리 값을 위치 하나가 아니라 위치 리스트로 바꾸겠습니다.」 |
| 입력 검증 | 「입찰가에 숫자가 아닌 값이 섞일 수 있다면 처음에 확인하고 오류를 내겠습니다.」 |

입력 검증을 오류로 할지 기본값으로 할지의 선택과 요구가 하나씩 늘어나는 추가 질문을 실제로 짜 보는 연습은 [실무형 라이브 코딩](post.html?id=algorithm-practical-live-coding) 편에 있습니다. 이 글의 순서는 그 글의 네 부분 문제에도 그대로 쓰이고, 부분마다 확인 질문, 계획, 따라가기를 짧게 되풀이하면 됩니다.

## 9. 영어 면접 표현

**영어 면접에서는 긴 문장보다 단계마다 정해 둔 짧은 표현 몇 개가 쓰기 쉽습니다. 아래 표는 1절의 순서대로 고른 예이고, 정해진 표준 문구가 아니라 이 글이 고른 평이하고 공손한 표현입니다.**

영어로 말하며 풀 때 막히는 것은 대개 알고리즘이 아니라 다음에 할 말의 첫마디라서, 첫마디만 준비해 두면 나머지는 코드의 이름(dictionary, index, target)으로 채울 수 있습니다. 표의 표현은 짧은 현재형과 「Could you」, 「Does this sound good」 같은 공손한 물음으로 골랐습니다.

| 단계 | 영어 표현 | 한국어 풀이 |
|---|---|---|
| 다시 말하기 | Let me restate the problem to make sure I understand it. | 제가 맞게 이해했는지 문제를 다시 말해 보겠습니다. |
| 확인 질문 | How large can the input be? | 입력이 최대 얼마나 큽니까? |
| 확인 질문 | Can the list be empty, or contain duplicates? | 리스트가 비어 있거나 중복이 있을 수 있습니까? |
| 확인 질문 | Should I return the indices or the values? | 위치를 돌려줍니까, 값을 돌려줍니까? |
| 느린 풀이 | A brute-force approach is to check every pair, which is O(n squared). | 모든 쌍을 보는 브루트 포스는 O(n^2) 입니다. |
| 더 나은 풀이 | I think we can do better with a hash map, in O(n) time. | 해시 맵으로 O(n) 시간에 할 수 있을 것 같습니다. |
| 동의 받기 | Does this approach sound good to you before I start coding? | 코드를 쓰기 전에 이 방법이 괜찮을까요? |
| 말하며 코드 쓰기 | Here I'm storing each value with its index. | 여기서 값마다 위치를 함께 넣습니다. |
| 말하며 코드 쓰기 | I check for the complement before inserting, so I don't use the same element twice. | 같은 원소를 두 번 쓰지 않도록 넣기 전에 짝을 찾습니다. |
| 손으로 따라가기 | Let me walk through an example. | 예제로 따라가 보겠습니다. |
| 손으로 따라가기 | Let me also check some edge cases, like an empty list. | 빈 리스트 같은 경계 입력도 확인하겠습니다. |
| 막혔을 때 | I'm stuck on this part. I tried X, but it fails when the input is Y. | 이 부분에서 막혔습니다. X 를 해 봤는데 입력이 Y 일 때 틀립니다. |
| 막혔을 때 | Could you give me a small hint? | 작은 힌트를 주실 수 있을까요? |
| 힌트 받기 | Thanks. So you mean I should check before inserting, right? | 감사합니다. 넣기 전에 확인하라는 뜻이 맞습니까? |
| 마무리 | The time complexity is O(n) and the space complexity is O(n). | 시간 복잡도는 O(n), 공간 복잡도는 O(n) 입니다. |
| 마무리 | If I had more time, I would handle invalid input. | 시간이 더 있다면 잘못된 입력을 처리하겠습니다. |

complement 는 이 문제에서 `target - bid`, 곧 짝이 될 값을 부르는 영어 낱말이고, Two Sum 풀이를 영어로 설명하는 글에서 자주 보이는 이름입니다. 말이 막히면 표현을 바꾸려 애쓰기보다 「Let me think for a moment.」(잠시 생각해 보겠습니다)라고 말하고 몇 초 생각하는 편이 낫고, 침묵이 길어지기 전에 무엇을 생각하는지 한 문장으로 말하면 됩니다.

## 한눈 정리

| 단계 | 소리 내어 말할 것 | 이 글의 예제에서 |
|---|---|---|
| 1~2. 다시 말하기, 확인 질문 | 문제를 자기 말로, 입력 크기, 빈 입력, 중복, 돌려줄 모양 | 위치를 돌려줌, n 최대 10만, 같은 광고 두 번 금지, 없으면 빈 리스트 |
| 3. 느린 풀이와 비용 | 브루트 포스와 연산 횟수 | 모든 쌍, n 10만이면 4,999,950,000번 |
| 4~5. 더 나은 풀이, 동의 | 자료구조, 방법, 비용, 「짜도 될까요?」 | 딕셔너리로 짝 찾기, 시간 O(n), 공간 O(n) |
| 6. 말하며 코드 쓰기 | 줄마다 계획의 어느 부분인지 | 짝을 먼저 찾고 자기를 넣는 순서의 까닭 |
| 7. 손으로 따라가기 | 변수 값과 함께 한 줄씩, 경계 입력 | 답 [0, 4], 경계 입력 5개 |
| 막혔을 때 | 해 본 것, 틀리는 입력, 힌트 요청 | 버그 판이 [500, 300] 에 [0, 0] |
| 8~9. 복잡도, 시간이 더 있으면 | 까닭과 함께 복잡도, 더 다룰 것 | 투 포인터, 모든 쌍, 입력 검증 |

## 헷갈리기 쉬운 점

- **말하며 풀기는 쉬지 않고 말하라는 뜻이 아닙니다.** 몇 초 생각하는 것은 괜찮고, 그 전에 「잠시 생각해 보겠습니다」라고 말해 두면 면접관이 침묵의 까닭을 압니다. 줄마다 긴 설명을 붙이면 오히려 코드가 늦어집니다.
- **브루트 포스를 말하는 것은 약점이 아닙니다.** 비용을 숫자로 말해야 더 빠른 풀이가 필요한 까닭이 생기고, 공개 안내서들도 느린 풀이부터 이야기하라고 권합니다. 다만 화면에 다 쓸지는 면접관에게 물어 정합니다.
- **동의를 받는 질문은 방향을 맞추는 것입니다.** 방향이 틀렸다면 코드 전에 고치는 것이 가장 적게 고치는 길입니다.
- **손으로 따라가기는 「맞아 보인다」를 확인하는 것이 아닙니다.** 버그를 찾는다고 생각하고 변수 값을 한 줄씩 말하고, 2절에서 정한 경계 입력도 같이 돌립니다.
- **힌트를 받으면 자기 말로 다시 말합니다.** 힌트를 잘못 알아들은 채 다른 방향으로 가면 시간을 두 번 잃고, 면접관은 힌트가 전달됐는지 알 수 없습니다.
- **면접관이 무엇을 얼마나 중요하게 보는지는 정해진 공개 기준이 없습니다.** 이 글의 순서는 공개 안내서들이 권하는 것을 정리한 것이고, 실제 면접의 형식과 규칙은 시작할 때 물어 확인합니다.
