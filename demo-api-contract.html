API 계약 실험실

문서에는 주소와 필드만 적혀 있습니다. 타임아웃·재시도·멱등키·인증은 붙이는 사람이 정합니다. 전환 포스트백 1,000건을 보내 놓고 그 넷을 바꿔 보면, 어느 것이 먼저 리포트를 틀어지게 하는지 보입니다.

먼저 보면 좋아요 요청 경로 시뮬레이터 로그 여섯 층 내려가기
이 데모가 보여주는 것광고주 한 곳의 하루 전환 1,000건을 MMP가 우리 수집 API로 보냅니다. 응답이 돌아오는 길에서 일부가 사라지고, 보낸 쪽은 답을 못 받아 같은 요청을 다시 보냅니다. 스위치 여섯 개를 움직이면 전환 테이블에 몇 줄이 남는지와 어느 계기가 먼저 위험으로 바뀌는지가 같이 움직입니다.
왜 알아야 하나중복으로 쌓인 줄은 에러가 아닙니다. 전부 성공 응답을 받은 건이라 알람이 울릴 자리가 없습니다. 드러나는 곳은 다음 날 리포트의 CPA 한 줄뿐입니다.
    이렇게 해보세요 — 4분
  1. 기본값(server → server · 유실 15% · 재시도 3회 · 멱등키 켬)에서 회차 표를 봅니다. 요청은 1,180건인데 기록은 1,000줄입니다.
  2. 멱등키를 끕니다. 기록이 1,180줄(+18.0%)이 되고 리포트 CPA가 5,000원에서 4,237원으로 내려갑니다.
  3. 재시도를 0으로 내립니다. 중복은 사라지지만 성공률이 85.0%로 떨어집니다. 둘 중 하나만 고를 수는 없다는 뜻입니다.
  4. 호출 방향을 client → server로 바꾸고 인증을 API key로 고릅니다. 시크릿 노출 계기가 위험으로 바뀝니다.

상황 — 광고비 500만 원을 쓴 광고주의 하루 전환은 1,000건입니다. 진짜 CPA는 5,000원입니다.

가정 — 서버는 받은 요청을 항상 기록합니다. 유실은 돌아오는 응답에서만 일어납니다. 유실률은 회차마다 조금씩 올라가고(15.0 → 16.7 → 20.0%), 4회차에는 남은 건이 전부 도착합니다.

커넥션 — 우리 API가 하위(전환 테이블)를 초당 100번 부르고, 커넥션 풀은 200개입니다. 우리가 상위에 약속한 응답 예산은 400ms입니다.

이 데모에서 알게 된 3가지

  1. 재시도는 성공률을 사고 중복을 지불한다 — 재시도를 0으로 두면 중복은 0이지만 보낸 쪽은 150건을 실패로 봅니다. 3으로 올리면 응답은 다 받지만 요청이 1,180건이 됩니다.
  2. 멱등키는 그 지불만 지운다 — 키를 켜도 요청 수는 1,180건 그대로입니다. 달라지는 것은 전환 테이블에 남는 줄뿐입니다. 1,180줄이 1,000줄이 됩니다.
  3. 방향이 인증을 정한다 — client → server에서는 API key·OAuth2·mTLS·HMAC 넷 다 앱 안에 비밀을 둬야 합니다. 남는 답은 사용자 토큰 하나입니다.

현업에서는 이렇게 씁니다

"API 붙여 주세요"를 받으면 문서에 없는 것부터 정합니다. 이 데모의 스위치 여섯 개가 그 목록입니다. 하나씩 값을 넣어 보고 어느 계기가 먼저 움직이는지를 봅니다.

  • 멱등키부터 정합니다: 부르는 쪽이 만들고, 재시도 내내 같은 값을 씁니다. 자연키(주문번호)가 있으면 그것을 쓰고, 없으면 UUID를 한 번만 만들어 재사용합니다. 재시도마다 새로 만들면 키가 없는 것과 같습니다.
  • 타임아웃은 예산을 나눠 잡습니다: 우리가 400ms에 답하기로 했으면 하위 호출의 상한 합이 400ms를 넘으면 안 됩니다. 넘으면 상위가 먼저 끊고, 아래 호출은 아무도 안 기다리는 채로 커넥션을 뭅니다.
  • 인증은 방향을 먼저 봅니다: 앱이 부르는 자리라면 비밀을 둘 곳이 없습니다. 로그인 토큰을 쓰거나, 비밀이 필요한 호출을 우리 서버가 대신하거나, 애초에 비밀이 필요 없게 설계하고 쿼터와 값 검증을 서버에 겁니다.
