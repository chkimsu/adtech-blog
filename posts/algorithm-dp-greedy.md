지훈은 피보나치 수를 재귀로 짰는데, 코드는 두 줄이었고 예제도 맞았다. 그런데 n을 30으로 올리자 0.3초가 걸렸고, 40에서는 아예 끝나지 않았다.

이번에는 자료형 문제가 아니어서, 리스트를 집합으로 바꿀 것도 없고, 정렬할 것도 없었다. 코드는 두 줄뿐인데 그 두 줄이 너무 많이 불렸다.

**같은 계산을 몇 번이나 하고 있을까?**

세어 보면 답이 나온다. 이 글은 그 세는 일에서 출발해 세 가지 도구로 간다. 겹치는 계산을 적어 두는 **동적 계획법**, 아니다 싶으면 되돌아오는 **백트래킹**, 지금 최선만 고르는 **그리디**다. 셋 다 "모든 경우를 다 볼 수는 없다"는 같은 문제에 대한 다른 답이다.

> **한 줄 요약:** 그냥 재귀는 같은 계산을 269만 번 한다. 답을 적어 두기만 하면 59번으로 준다. 적어 둘 것이 없으면 되돌아오며 찾고(백트래킹), 앞만 보고 골라도 되는 문제라면 그냥 고른다(그리디).

> **골라 읽는 법** — 절이 열 개인 글입니다.
>
> - 겹치는 계산을 세고 없애기 → 앞의 세 절
> - 점화식 세우는 순서와 배낭 문제 → 넷째·다섯째 절
> - 백트래킹 → 여섯째·일곱째 절
> - 그리디와 그게 틀리는 자리 → 여덟째·아홉째 절

## 1. 같은 계산을 몇 번이나 하나

**느린 재귀는 대개 같은 값을 여러 번 구한다. 세어 보면 바로 드러난다.**

피보나치는 `f(n) = f(n-1) + f(n-2)` 다. `f(20)` 을 구하려면 `f(19)` 와 `f(18)` 이 필요한데, `f(19)` 를 구하는 도중에도 `f(18)` 이 또 필요하니 이렇게 겹친다.

얼마나 겹치는지는 짐작하지 말고 세면 된다.

```python
import time

부른횟수 = {}

def 그냥(n):
    부른횟수[n] = 부른횟수.get(n, 0) + 1
    if n < 2: return n
    return 그냥(n-1) + 그냥(n-2)

그냥(20)
print("피보나치 20 을 그냥 재귀로 구할 때, 각 n 을 몇 번 불렀나")
for n in (20, 18, 15, 10, 5, 2, 1):
    print(f"  n={n:<4}{부른횟수[n]:>7}번")
print(f"  전부 합치면 {sum(부른횟수.values()):,}번")

print()
print(f"{'n':>5}{'그냥 재귀(ms)':>15}{'부른 횟수':>12}")
for n in (20, 25, 30):
    부른횟수.clear()
    t = time.perf_counter()
    그냥(n)
    ms = (time.perf_counter() - t) * 1000
    print(f"{n:>5}{ms:>15.1f}{sum(부른횟수.values()):>12,}")
```

## 2. 적어 두기 — 위에서 아래로

**한 번 구한 답을 적어 두고, 다시 물으면 적어 둔 것을 준다. 줄 하나면 된다.**

이것을 **메모이제이션**이라 부른다. 이름은 거창한데 하는 일은 딕셔너리에 넣고 빼는 것뿐이다. 앞 편에서 본 해시가 여기서 그대로 쓰인다.

같은 문제를 세 방법으로 풀고 나란히 재 보자.

```python
import time

def 그냥(n):
    if n < 2: return n
    return 그냥(n-1) + 그냥(n-2)

적어둔것 = {}
불린횟수 = [0]
def 적어두기(n):
    불린횟수[0] += 1
    if n < 2: return n
    if n in 적어둔것: return 적어둔것[n]     # 이미 구한 것은 다시 안 구한다
    적어둔것[n] = 적어두기(n-1) + 적어두기(n-2)
    return 적어둔것[n]

def 아래에서(n):
    표 = [0, 1] + [0] * (n - 1)
    for i in range(2, n + 1):
        표[i] = 표[i-1] + 표[i-2]
    return 표[n]

N = 30
print(f"{'방법':<14}{'답':>10}{'시간(ms)':>12}{'부른 횟수':>12}")
t = time.perf_counter(); a = 그냥(N); ms = (time.perf_counter()-t)*1000
print(f"{'그냥 재귀':<14}{a:>10,}{ms:>12.1f}{'2,692,537':>12}")
t = time.perf_counter(); b = 적어두기(N); ms = (time.perf_counter()-t)*1000
print(f"{'적어 두기':<14}{b:>10,}{ms:>12.4f}{불린횟수[0]:>12,}")
t = time.perf_counter(); c = 아래에서(N); ms = (time.perf_counter()-t)*1000
print(f"{'아래에서 쌓기':<13}{c:>10,}{ms:>12.4f}{N-1:>12,}")
print(f"\n세 답이 같나 {a == b == c}")
```

```
방법                     답      시간(ms)       부른 횟수
그냥 재귀            832,040       126.1   2,692,537
적어 두기            832,040      0.0116          59
아래에서 쌓기         832,040      0.0045          29

세 답이 같나 True
```

269만 번이 59번이 됐고, 코드에 더한 것은 `if n in 적어둔것: return 적어둔것[n]` 한 줄이다.

59라는 숫자에도 뜻이 있다. n이 30이니 `f(0)` 부터 `f(30)` 까지 31개를 각각 한 번씩만 진짜로 계산하고, 나머지는 적어 둔 것을 읽었다. **각 값을 한 번씩만 구하면 O(n)이 된다.**

파이썬에는 이것을 자동으로 해 주는 도구가 있다. 함수 위에 `@lru_cache(maxsize=None)` 한 줄을 붙이면 딕셔너리를 직접 안 만들어도 된다. 다만 인자가 리스트처럼 바뀔 수 있는 것이면 안 되는데, 앞 편에서 본 "열쇠로 쓸 수 있는 것" 조건이 그대로 적용되기 때문이다.

## 3. 아래에서 쌓기 — 재귀를 없앤다

**적어 두기는 위에서 아래로 파고들며 채운다. 순서를 뒤집어 작은 것부터 채우면 재귀가 아예 없어진다.**

이것을 **타뷸레이션**이라 하고, 위 코드의 `아래에서` 가 그것이다. `f(2)` 를 구하려면 `f(0)` 과 `f(1)` 이 필요한데 그건 이미 안다. `f(3)` 은 `f(1)`, `f(2)` 가 필요한데 그것도 방금 구했다. 이렇게 작은 것부터 순서대로 채워 올라간다.

둘 다 답은 같지만 성격은 꽤 다르다.

| | 적어 두기 (위에서) | 아래에서 쌓기 |
|---|---|---|
| 모양 | 재귀 + 딕셔너리 | 반복문 + 리스트 |
| 계산하는 범위 | 실제로 필요한 것만 | 0부터 n까지 전부 |
| 재귀 깊이 | n만큼 쌓인다 | 없다 |
| 짜기 | 원래 식을 그대로 옮기면 된다 | 채우는 순서를 정해야 한다 |

**필요한 부분이 전체의 일부뿐이면 적어 두기가 유리하다.** 반대로 어차피 다 필요하고 n이 아주 크면, 재귀 깊이 걱정이 없는 아래에서 쌓기가 안전하다.

위 출력에서 아래에서 쌓기가 29번으로 가장 적었다. 적어 두기의 59번은 같은 값을 두 번씩 물어본 몫이다. 한 번은 계산하려고, 한 번은 적어 둔 것을 읽으려고.

## 4. 점화식 세우는 순서

**동적 계획법에서 어려운 것은 코드가 아니라 "무엇을 표에 적을지" 정하는 일이다.**

피보나치는 문제 자체가 식을 알려 줬지만 실제 문제는 그렇지 않다. 그래도 순서를 정해 두면 헤매지 않는다.

**첫째, 표의 칸 하나가 무엇을 뜻하는지 한 문장으로 적는다.** "표[i] = i번째까지 봤을 때의 최댓값"처럼. 이 문장이 안 나오면 아직 문제를 이해 못 한 것이다.

**둘째, 마지막 선택 하나만 생각한다.** 지금 칸의 답을 구할 때, 바로 앞에서 무슨 선택을 했을 수 있나? 그 선택마다 어느 칸을 봐야 하나? 전체를 다 그리려 하면 막히는데, 마지막 한 걸음만 보면 대체로 풀린다.

**셋째, 시작값을 정한다.** `표[0]` 이 무엇인지, 아무것도 안 골랐을 때 값이 0인지 무한대인지를 정한다. 최솟값을 구하는 문제에서 시작값을 0으로 두면 답이 전부 0이 나온다.

**넷째, 채우는 순서를 확인한다.** `표[i]` 를 구할 때 필요한 칸이 이미 채워져 있어야 한다.

다음 절에서 이 순서를 그대로 밟아 본다.

## 5. 배낭 문제 — 표로 보면 보인다

**무게 한도가 있고 물건마다 무게와 값이 있을 때, 값의 합을 최대로 하는 문제다.**

네 단계를 밟아 보자.

1. **칸의 뜻**: `표[i][w]` = 앞의 i개 물건만 쓰고 무게 한도가 w일 때의 최대값
2. **마지막 선택**: i번째 물건을 넣거나 안 넣거나 둘 중 하나다. 안 넣으면 `표[i-1][w]`, 넣으면 `표[i-1][w-무게] + 값` 이다
3. **시작값**: 물건이 하나도 없으면 값도 0이니 첫 줄은 전부 0
4. **순서**: 위 줄이 있어야 아래 줄을 구하니 물건 순서대로 내려간다

```python
물건 = [("노트북", 3, 9), ("카메라", 2, 6), ("책", 1, 2), ("렌즈", 2, 5)]
한도 = 5

표 = [[0] * (한도 + 1) for _ in range(len(물건) + 1)]

for i, (이름, 무게, 값) in enumerate(물건, 1):
    for w in range(한도 + 1):
        안넣기 = 표[i-1][w]
        넣기 = 표[i-1][w-무게] + 값 if w >= 무게 else -1
        표[i][w] = max(안넣기, 넣기)

print(f"{'':<8}" + "".join(f"{w:>5}" for w in range(한도 + 1)) + "   ← 남은 무게")
print(f"{'없음':<7}" + "".join(f"{x:>5}" for x in 표[0]))
for i, (이름, 무게, 값) in enumerate(물건, 1):
    print(f"{이름:<7}" + "".join(f"{x:>5}" for x in 표[i]) + f"   (무게 {무게} · 값 {값})")

print(f"\n무게 {한도} 까지 담아 얻는 최대값 {표[len(물건)][한도]}")

고른것, w = [], 한도
for i in range(len(물건), 0, -1):
    if 표[i][w] != 표[i-1][w]:          # 값이 달라졌다 = 이 물건을 넣었다
        이름, 무게, 값 = 물건[i-1]
        고른것.append(이름)
        w -= 무게
print("고른 것", 고른것[::-1])
```

```
            0    1    2    3    4    5   ← 남은 무게
없음         0    0    0    0    0    0
노트북        0    0    0    9    9    9   (무게 3 · 값 9)
카메라        0    0    6    9    9   15   (무게 2 · 값 6)
책          0    2    6    9   11   15   (무게 1 · 값 2)
렌즈         0    2    6    9   11   15   (무게 2 · 값 5)

무게 5 까지 담아 얻는 최대값 15
고른 것 ['노트북', '카메라']
```

표를 왼쪽 위에서 오른쪽 아래로 읽어 보자. 노트북 줄에서 무게 3 이전이 전부 0인 것은 무게 3짜리를 넣을 자리가 없기 때문이다. 카메라 줄의 무게 5 칸에서 15가 나온 것은 노트북(3)과 카메라(2)를 둘 다 넣었다는 뜻이다.

렌즈 줄이 책 줄과 완전히 같은 것도 눈여겨보자. **렌즈는 어느 무게에서도 도움이 안 됐다.** 무게 2에 값 5인데, 같은 무게의 카메라가 값 6이라 항상 카메라가 낫다.

마지막 반복문이 **어느 물건을 골랐는지 되짚는** 부분이다. 표만으로는 최대값밖에 모른다. `표[i][w]` 와 `표[i-1][w]` 가 다르면 i번째 물건을 넣었다는 뜻이니, 아래에서 위로 거슬러 올라가며 확인한다. 앞 편의 BFS에서 경로를 되짚던 것과 같은 방법이다.

:::deep 표를 한 줄로 줄이기 — 그리고 방향을 뒤집으면 왜 틀리나

위 표에서 `표[i]` 를 구할 때 보는 것은 `표[i-1]` 뿐이고, 그 위의 줄들은 다시 안 본다. 그러면 줄 하나만 들고 계속 덮어써도 되지 않을까?

된다. 다만 반복문을 **뒤에서 앞으로** 돌려야 한다.

```python
물건 = [("노트북", 3, 9), ("카메라", 2, 6), ("책", 1, 2), ("렌즈", 2, 5)]
한도 = 6

한줄 = [0] * (한도 + 1)
print(f"{'넣은 물건':<8}" + "".join(f"{w:>5}" for w in range(한도 + 1)))
print(f"{'시작':<7}" + "".join(f"{x:>5}" for x in 한줄))
for 이름, 무게, 값 in 물건:
    for w in range(한도, 무게 - 1, -1):        # 뒤에서 앞으로
        한줄[w] = max(한줄[w], 한줄[w-무게] + 값)
    print(f"{이름:<7}" + "".join(f"{x:>5}" for x in 한줄))

print(f"\n최대값 {한줄[한도]} · 들고 있는 칸 {len(한줄)}개 (두 줄짜리 표는 {(len(물건)+1)*(한도+1)}칸)")

# 앞에서 뒤로 돌면 같은 물건을 여러 번 넣게 된다
틀린것 = [0] * (한도 + 1)
for 이름, 무게, 값 in 물건:
    for w in range(무게, 한도 + 1):            # 앞에서 뒤로 — 틀린 방향
        틀린것[w] = max(틀린것[w], 틀린것[w-무게] + 값)
print(f"앞에서 뒤로 돌면 {틀린것[한도]} — 같은 물건을 여러 번 담은 값이라 틀리다")
```

```
넣은 물건       0    1    2    3    4    5    6
시작         0    0    0    0    0    0    0
노트북        0    0    0    9    9    9    9
카메라        0    0    6    9    9   15   15
책          0    2    6    9   11   15   17
렌즈         0    2    6    9   11   15   17

최대값 17 · 들고 있는 칸 7개 (두 줄짜리 표는 35칸)
앞에서 뒤로 돌면 18 — 같은 물건을 여러 번 담은 값이라 틀리다
```

칸이 35개에서 7개로 줄었다. 무게 한도가 십만이고 물건이 천 개면 이 차이가 메모리 초과와 통과를 가른다.

방향이 중요한 이유는 이렇다. `한줄[w]` 를 고칠 때 `한줄[w-무게]` 를 읽는데, 이 값이 **이번 물건을 반영하기 전 값**이어야 한다. 뒤에서 앞으로 돌면 `w-무게` 는 아직 안 건드린 자리라 안전하다. 앞에서 뒤로 돌면 이미 이번 물건을 넣어 고쳐 놓은 값을 다시 읽어서, 같은 물건을 두 번 담게 된다.

재미있는 것은 **앞에서 뒤로 도는 것이 다른 문제의 정답**이라는 점이다. 같은 물건을 몇 개든 담아도 되는 문제라면 그쪽이 맞다. 방향 하나가 "각 물건 한 번씩"과 "무제한"을 가른다.
:::

## 6. 백트래킹 — 아니면 되돌아온다

**표에 적어 둘 만한 겹침이 없으면 결국 다 해 봐야 한다. 다만 아니다 싶은 순간 바로 되돌아온다.**

동적 계획법은 "작은 문제의 답이 겹칠 때" 쓴다. 그런데 겹치지 않는 문제도 많은데, "여덟 개의 퀸을 서로 공격 못 하게 놓아라" 같은 것인데, 이때는 하나씩 놓아 보고 안 되면 물러선다.

이것을 **백트래킹**이라 한다. 앞 편의 DFS와 같은 구조인데, 갈래를 내려갔다가 올라오면서 **상태를 원래대로 되돌린다**는 점이 다르다.

```python
N = 4
답 = []
시도횟수 = [0]

def 놓기(줄, 놓은자리, 로그):
    시도횟수[0] += 1
    if 줄 == N:
        답.append(list(놓은자리)); 로그.append(f"{놓은자리} 완성")
        return
    for 칸 in range(N):
        안전 = all(칸 != c and abs(칸 - c) != 줄 - r for r, c in enumerate(놓은자리))
        if not 안전:
            로그.append(f"{'  '*줄}{줄}줄 {칸}칸 → 막힘, 되돌린다")
            continue
        로그.append(f"{'  '*줄}{줄}줄 {칸}칸 놓음")
        놓은자리.append(칸)
        놓기(줄 + 1, 놓은자리, 로그)
        놓은자리.pop()                      # 되돌린다
로그 = []
놓기(0, [], 로그)
for 줄 in 로그[:16]:
    print(줄)
print("  ...")
print(f"\n답 {답}")
print(f"부른 횟수 {시도횟수[0]}회 · 가지치기 없이 전부 놓으면 {N**N}회")
```

```
0줄 0칸 놓음
  1줄 0칸 → 막힘, 되돌린다
  1줄 1칸 → 막힘, 되돌린다
  1줄 2칸 놓음
    2줄 0칸 → 막힘, 되돌린다
    2줄 1칸 → 막힘, 되돌린다
    2줄 2칸 → 막힘, 되돌린다
    2줄 3칸 → 막힘, 되돌린다
  1줄 3칸 놓음
    2줄 0칸 → 막힘, 되돌린다
    2줄 1칸 놓음
      3줄 0칸 → 막힘, 되돌린다
      3줄 1칸 → 막힘, 되돌린다
      3줄 2칸 → 막힘, 되돌린다
      3줄 3칸 → 막힘, 되돌린다
    2줄 2칸 → 막힘, 되돌린다
  ...

답 [[1, 3, 0, 2], [2, 0, 3, 1]]
부른 횟수 17회 · 가지치기 없이 전부 놓으면 256회
```

`놓은자리.append(칸)` 과 `놓은자리.pop()` 이 짝이다. **내려갈 때 넣고 올라올 때 뺀다.** 이 짝이 백트래킹의 전부이고, `pop()` 을 빼먹으면 위 갈래의 흔적이 옆 갈래로 새어 나가 답이 틀린다.

들여쓰기가 깊어졌다 얕아졌다 하는 것이 되돌아오는 모양이다. 1줄 2칸에 놓았다가 2줄에서 네 칸이 모두 막히자, 다시 1줄로 올라와 3칸을 시도했다.

## 7. 가지치기 — 안 될 갈래는 일찍 버린다

**위 출력의 마지막 줄이 백트래킹의 값어치다. 256가지를 다 보지 않고 17번 만에 끝났다.**

4×4 판에 퀸 넷을 놓는 경우의 수는 각 줄에 네 칸씩이니 4⁴ = 256가지다. 전부 놓고 나서 확인하면 256번인데, 실제로는 17번만 불렸다.

이 차이를 만든 것은 **언제 확인하느냐**다. 다 놓고 확인하면 256번, 한 줄 놓을 때마다 확인하면 17번이다. 1줄에서 이미 막혔으면 그 아래 갈래 열여섯 가지를 통째로 안 본다.

이것을 **가지치기**라 하고, 백트래킹 문제의 성능은 거의 전적으로 여기서 갈린다. **"지금까지의 부분 답이 이미 조건을 어겼나"를 매 단계에서 확인하는 것이 기본형이다.**

한 단계 더 나아간 가지치기도 있다. 최댓값을 찾는 문제에서, 남은 것을 다 최선으로 골라도 지금까지의 최고 기록을 못 넘는다면 그 갈래는 볼 필요가 없다. 이 판단이 정확할수록 빨라진다.

## 8. 그리디 — 지금 최선만 고른다

**앞을 안 보고 지금 가장 좋아 보이는 것만 골라도 답이 되는 문제가 있다.**

회의실이 하나 있고 회의 신청이 여러 개 들어왔다. 겹치지 않게 최대한 많이 잡으려면 어떤 기준으로 골라야 할까? 그럴듯한 기준이 셋 떠오른다.

```python
# (이름, 시작, 끝)
회의 = [("A", 9, 16), ("B", 10, 12), ("C", 11, 13), ("D", 12, 15), ("E", 13, 14), ("F", 15, 17)]

for 기준, 정렬키 in (("시작이 빠른 순", lambda m: m[1]),
                    ("길이가 짧은 순", lambda m: m[2] - m[1]),
                    ("끝이 빠른 순",  lambda m: m[2])):
    잡힌것, 끝난시각 = [], 0
    for 이름, s, e in sorted(회의, key=정렬키):
        if s >= 끝난시각:
            잡힌것.append(이름); 끝난시각 = e
    print(f"{기준:<14}{len(잡힌것)}개  {잡힌것}")

print("\n끝이 빠른 순이 가장 많이 잡는다 — 방을 가장 일찍 비워 주니 뒤에 남는 시간이 가장 많다.")
```

```
시작이 빠른 순      1개  ['A']
길이가 짧은 순      2개  ['E', 'F']
끝이 빠른 순       3개  ['B', 'E', 'F']

끝이 빠른 순이 가장 많이 잡는다 — 방을 가장 일찍 비워 주니 뒤에 남는 시간이 가장 많다.
```

셋 다 그리디인데 결과가 전부 다르다. **그리디에서 어려운 것은 코드가 아니라 기준을 고르는 일이다.**

시작이 빠른 순은 9시부터 16시까지 하는 A 하나에 방을 통째로 내주고 끝났다. 길이가 짧은 순도 가운데 짧은 회의를 먼저 잡느라 앞뒤가 막혔다.

끝이 빠른 순이 답인 이유는 말로 설명된다. **방을 가장 일찍 비워 주는 회의를 잡으면 뒤에 남는 시간이 가장 많다.** 그러니 그 회의를 잡아서 손해 볼 일이 없다. 이런 설명이 되는 기준을 찾았을 때만 그리디를 믿을 수 있다.

## 9. 그리디가 틀리는 자리

**설명이 안 되는 기준을 그럴듯하다는 이유로 쓰면 조용히 틀린다.**

거스름돈 문제가 대표적이다. 동전 종류가 주어지고 금액을 최소 개수의 동전으로 만들어야 한다. 큰 동전부터 쓰는 것이 당연해 보인다.

```python
def 그리디(동전, 금액):
    남은, 쓴것 = 금액, []
    for c in sorted(동전, reverse=True):
        while 남은 >= c:
            남은 -= c; 쓴것.append(c)
    return (쓴것 if 남은 == 0 else None)

def 최적(동전, 금액):
    무한 = float("inf")
    표 = [0] + [무한] * 금액
    고른 = [None] * (금액 + 1)
    for 금 in range(1, 금액 + 1):
        for c in 동전:
            if c <= 금 and 표[금-c] + 1 < 표[금]:
                표[금] = 표[금-c] + 1
                고른[금] = c
    if 표[금액] == 무한: return None
    쓴것, 남은 = [], 금액
    while 남은:
        쓴것.append(고른[남은]); 남은 -= 고른[남은]
    return 쓴것

for 동전, 금액 in (([500, 100, 50, 10], 1260), ([4, 3, 1], 6)):
    g, o = 그리디(동전, 금액), 최적(동전, 금액)
    같나 = "같다" if (g and o and len(g) == len(o)) else "다르다"
    print(f"동전 {동전} · 금액 {금액}")
    print(f"  큰 것부터 (그리디)  {len(g)}개  {g}")
    print(f"  전부 따져 (DP)     {len(o)}개  {o}")
    print(f"  → {같나}\n")
```

```
동전 [500, 100, 50, 10] · 금액 1260
  큰 것부터 (그리디)  6개  [500, 500, 100, 100, 50, 10]
  전부 따져 (DP)     6개  [500, 500, 100, 100, 50, 10]
  → 같다

동전 [4, 3, 1] · 금액 6
  큰 것부터 (그리디)  3개  [4, 1, 1]
  전부 따져 (DP)     2개  [3, 3]
  → 다르다
```

우리가 쓰는 동전에서는 그리디가 맞지만, 동전이 4·3·1이면 틀린다. 6원을 만들 때 4를 먼저 쓰면 남은 2를 1 두 개로 채워야 해서 세 개가 되지만, 3 두 개면 두 개로 끝난다.

**여기가 그리디의 위험한 지점이다.** 오류가 나지 않고, 예제 입력에서도 맞는 답이 나온다. 실제 동전 체계는 대부분 그리디가 맞도록 설계돼 있어서 더욱 그렇다.

그래서 판단 기준을 정해 두는 것이 낫다. **"이 선택이 왜 손해가 아닌지"를 한 문장으로 설명할 수 있으면 그리디를 쓰고, 못 하면 DP를 쓴다.** 8절의 회의실은 설명이 됐고, 거스름돈은 안 된다.

시험장에서 확신이 안 서면 **작은 반례를 손으로 찾아보는 것**이 가장 빠르다. 위의 4·3·1 처럼, 큰 것을 쓰면 어중간한 나머지가 남는 조합을 만들어 보면 된다.

## 10. 어느 것을 언제 쓰나

**"모든 경우를 다 볼 수 없다"에서 출발해 세 갈래로 나뉜다.**

먼저 작은 문제의 답이 **겹치는지** 본다. 같은 계산을 반복하고 있으면 동적 계획법이다. "최대·최소 몇 개", "몇 가지 방법", "최소 비용"이 지문에 있고 선택이 단계별로 이어지면 대체로 여기 든다.

겹치지 않고 **모든 조합을 실제로 만들어야 하면** 백트래킹이다. "가능한 모든 순서", "조건을 만족하는 배치"가 신호다. 이때는 가지치기를 얼마나 일찍 하느냐가 통과 여부를 가른다.

**한 번의 선택이 뒤를 망치지 않는다고 설명할 수 있으면** 그리디다. 설명이 안 되면 쓰지 않는다. 그리디는 가장 빠르지만 가장 위험하다.

입력 크기로도 갈린다. n이 20 언저리면 2ⁿ 이 백만 정도라 완전탐색이 통과한다. n이 수천이면 O(n²) DP까지, n이 십만이면 O(n) 이나 O(n log n)이어야 한다. **문제에 적힌 n이 어느 방법을 허용하는지 먼저 계산하는 것이 첫걸음이다.**

## 한눈 정리

| 상황 | 쓸 것 | 왜 |
|---|---|---|
| 같은 계산이 반복된다 | 적어 두기 | 한 줄로 269만 번이 59번 |
| n이 크고 어차피 다 필요하다 | 아래에서 쌓기 | 재귀 깊이 걱정이 없다 |
| 필요한 부분이 일부뿐이다 | 적어 두기 | 안 쓰는 칸은 안 채운다 |
| 무엇을 골랐는지도 필요하다 | 표를 되짚는다 | 값이 달라진 칸이 고른 자리 |
| 모든 조합을 만들어야 한다 | 백트래킹 | 넣고 부르고 되돌린다 |
| 백트래킹이 느리다 | 가지치기를 위로 올린다 | 위에서 자를수록 많이 지워진다 |
| 선택이 뒤를 안 망친다고 설명된다 | 그리디 | 가장 빠르다 |
| 설명이 안 된다 | DP | 그리디는 조용히 틀린다 |
| n이 20 언저리 | 완전탐색 | 2ⁿ 이 백만 정도 |

## 헷갈리기 쉬운 점

- **표의 칸이 무엇을 뜻하는지 한 문장으로 못 적으면 아직 못 푼 것이다.** 코드부터 짜면 거의 항상 막힌다.
- **시작값을 잘못 두면 답이 통째로 틀린다.** 최솟값 문제에서 `표[0]` 을 0이 아닌 무한으로 두거나 그 반대로 하는 실수가 흔하다.
- **백트래킹에서 `pop()` 을 빼먹으면 옆 갈래로 흔적이 샌다.** 넣기와 되돌리기는 반드시 짝이다.
- **가지치기는 늦게 하면 없는 것과 같다.** 다 만든 뒤 확인하면 256번, 한 단계마다 확인하면 17번이다.
- **그리디는 예제에서 맞아도 틀릴 수 있다.** 동전 4·3·1에서 6원이 그 예다. 오류가 안 나니 더 위험하다.
- **`@lru_cache` 는 인자가 바뀔 수 있으면 못 쓴다.** 리스트를 넘기면 오류가 나니 튜플로 바꿔 넘긴다.
- **적어 두기도 재귀라 깊이 한계가 있다.** n이 아주 크면 아래에서 쌓기로 바꾼다.
