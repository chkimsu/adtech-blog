지훈 씨의 아홉째 주에 분석 팀이 새 pCVR 모델을 실험용으로 만들어 왔습니다. pCVR 은 광고를 클릭한 사람이 구매 같은 전환까지 갈 확률을 예측한 값입니다. 이 모델은 아직 광고에 쓰지 않고 운영자가 쓰는 내부 화면에서 예측값부터 확인할 예정입니다. 그 화면에서 들어올 요청은 초당 40건 정도라고 했습니다.

지훈 씨는 지난주에 팀의 추론 서버 코드를 읽었습니다. 추론 서버는 학습한 모델을 메모리에 올려 두고 요청이 오면 예측값을 계산해 돌려주는 서버입니다. 지훈 씨가 읽은 코드에는 모델 파일을 메모리에 올리는 코드와 서버를 띄운 직후 더미 요청(실제 사용자가 보내지 않은 시험용 요청)을 몇 번 보내는 웜업 코드가 있었습니다. 서버가 요청을 받을 준비가 됐는지 확인하는 검사인 readiness probe 에 답하는 코드, 요청에 담겨 온 후보(점수를 매길 광고)를 텐서(모델에 한 번에 넣는 숫자 배열) 하나로 만드는 코드, 두 모델 버전 사이에서 트래픽을 옮기는 코드도 있었습니다. 지훈 씨는 이 작은 실험용 모델에도 이 코드를 모두 새로 만들어야 하는지 궁금했습니다.

선배는 「그건 BentoML 로 띄우면 하루면 됩니다. 다만 메인 pCTR 서버는 BentoML 을 쓰지 않습니다.」 하고 답했습니다. 메인 pCTR 서버는 광고가 노출됐을 때 클릭될 확률(pCTR)을 예측하는 모델을 올려 두고 광고를 고를 때 쓰는 서버입니다.

**같은 팀에서 왜 어떤 모델은 BentoML 로 띄우고 어떤 모델은 서버를 직접 짤까요?**

BentoML 은 학습이 끝난 모델 파일을 HTTP API 서버로 만들어 주는 파이썬 라이브러리입니다. HTTP API 서버는 HTTP 로 요청을 받아 예측값을 돌려주는 서버입니다. 이렇게 모델을 서버로 띄우는 일을 맡는 도구를 모델 서빙 프레임워크라고 부릅니다. TorchServe, Triton Inference Server, Ray Serve 도 같은 종류입니다.

이 글은 먼저 BentoML 이 추론 서버 코드 가운데 어느 부분을 대신 만들어 주는지 보고 나서 응답 시간이 빠듯한 자리에서는 왜 BentoML 을 쓰지 않는지를 숫자로 확인합니다. 모델 호출에 쓸 수 있는 시간을 지연 예산이라고 부릅니다. 응답 시간이 빠듯한 자리는 메인 pCTR 서빙처럼 지연 예산이 몇 밀리초밖에 안 되는 자리입니다.

> **한 줄 요약:** 직접 짠 추론 서버의 기능 7가지 가운데 요청을 받는 주소인 HTTP 엔드포인트, 모델 로딩, readiness probe, 지연 시간과 오류 수를 내보내는 메트릭 4가지는 BentoML 이 만들어 줍니다. 웜업 몇 줄과 모델마다 다른 입력 변환(요청을 텐서로 바꾸는 코드)은 직접 씁니다. 두 모델 버전 사이의 전환은 도커 이미지(서버 실행에 필요한 코드와 라이브러리를 한데 담은 파일)를 바꿔 배포하는 일이 됩니다. 대신 HTTP 요청을 파이썬 코드가 처리해서 요청마다 약 1.7ms 의 오버헤드(모델 계산 밖에서 더 드는 시간)가 붙습니다. 지연 예산이 8ms 인 메인 pCTR 서빙에서는 8ms 를 넘는 요청이 약 3.5% 에서 약 11% 로 세 배가 되지만 지연 예산이 200ms 인 내부 화면에서는 두 서버 모두 0% 라 차이가 보이지 않습니다.

> **골라 읽는 법** — 이 글의 절은 9개입니다. 절마다 카드 한 장이나 표 하나가 있어서 카드나 표만 보고 넘어가도 됩니다.
>
> - 직접 짠 추론 서버의 기능 7가지와 기능별 줄 수 → 1절
> - BentoML 서비스 파일 하나와 BentoML 이 만들어 주는 기능 4가지 → 2절
> - 모델 저장소, 태그, 모델 레지스트리의 차이 → 3절
> - Bento 빌드와 모델 파일이 든 도커 이미지 → 4절
> - 동적 배칭(요청 여러 개를 모아 한 번에 추론)이 이득인 경우 → 5절
> - 지연 예산 8ms 와 200ms 에서 파이썬 오버헤드의 영향 → 6절
> - 워커(파이썬 프로세스) 수에 따른 처리량과 대기 → 7절
> - BentoML 을 쓰는 곳과 쓰지 않는 곳 → 8절
> - 담장 안과 열린 RTB 에서 지연 예산을 정하는 곳 → 9절

이 글에 나오는 코드 줄 수, 시간, 크기는 모두 설명을 위해 정한 가상 값입니다. 모델 서버 12대, 지연 예산 8ms, 요청 하나에 담겨 오는 후보 800건은 [추론 서버](post.html?id=inference-server) 편과 같은 값입니다. 신경망 38MB, 임베딩 표(ID 하나마다 숫자 여러 개로 된 벡터를 하나씩 적어 둔 표) 27.7GB, 새 서버가 요청을 받을 준비를 마치기까지 걸리는 41초도 그 편에서 가져왔습니다.

글 속 코드는 BentoML 1.2 이후의 API 로 썼습니다. BentoML 은 버전이 올라가면서 이름과 옵션이 바뀐 적이 있으므로 코드를 옮겨 쓰기 전에 지금 쓰는 버전의 문서와 맞는지 확인합니다. 도커 이미지와 그 이미지가 지나는 CI 검사(코드를 올릴 때마다 자동으로 도는 빌드와 테스트)는 [Docker 와 CI](post.html?id=container-ci-pipeline) 편에서 이어집니다.

## 1. 직접 짠 추론 서버의 기능 7가지

**직접 짠 추론 서버의 기능 7가지 가운데 모델마다 코드가 달라지는 기능은 입력 변환 하나뿐입니다. 나머지 6가지는 어떤 모델을 띄워도 거의 같은 코드라서 모델 서빙 프레임워크를 쓰면 모델마다 다시 짜는 수고를 덜 수 있습니다.**

실험용 pCVR 모델에도 서버 코드를 전부 새로 짜야 하는지 알아보려면 지훈 씨가 지난주에 읽은 추론 서버 코드가 어떤 기능으로 이루어졌는지부터 봐야 합니다. 그 코드를 하는 일에 따라 나누면 아래 표처럼 기능 7가지가 나옵니다. 표의 줄 수는 설명을 위해 정한 가상 값입니다.

| 기능 | 하는 일 | 왜 필요한가 | 줄 수 |
|---|---|---|---|
| HTTP 엔드포인트 | 요청을 받아 예측값을 돌려준다 | 앱과 API 서버가 이 URL 로 모델을 호출한다 | 220 |
| 모델 로딩 | 모델 파일을 열어 메모리에 올린다 | 매일 새벽 새 모델 파일이 나온다 | 180 |
| 입력 변환 | 요청에 담긴 후보 800건을 텐서 하나로 만든다 | 800건을 하나씩 호출하면 96ms 가 걸린다 | 260 |
| 웜업(warm-up) | 서버를 띄운 직후 더미 요청을 몇 번 보낸다 | 안 하면 처음 30초 동안 2.5배 느리다 | 90 |
| readiness probe | 「요청 받을 준비 됨」을 알린다 | 게이트웨이는 준비된 서버에만 요청을 보낸다 | 70 |
| 버전 전환 | 두 모델 버전을 함께 띄우고 트래픽을 옮긴다 | 문제가 생기면 몇 초 안에 롤백해야 한다 | 310 |
| 메트릭 | 지연 시간과 오류 수를 내보낸다 | 대시보드와 알람이 이 값을 쓴다 | 240 |

표의 게이트웨이는 요청을 먼저 받아 어느 서버로 보낼지 정하는 앞단 서버입니다. 롤백은 문제가 생긴 새 버전을 이전 버전으로 되돌리는 일입니다.

7가지 기능의 줄 수를 모두 더하면 220 + 180 + 260 + 90 + 70 + 310 + 240 = 1,370줄이고 여기에 설정 파일과 테스트 코드까지 합치면 약 1,800줄이 됩니다.

요청이 어떤 모양으로 오고 그 요청을 어떤 텐서로 바꿀지가 모델마다 다르므로 1,370줄 가운데 입력 변환 260줄은 모델마다 새로 써야 합니다. 반면 나머지 6가지에 해당하는 1,370 - 260 = 1,110줄은 pCTR 모델을 띄우든 pCVR 모델을 띄우든 거의 같은 모양입니다. 모델 서빙 프레임워크는 모델을 새로 띄울 때마다 이 6가지를 다시 짜지 않으려고 쓰는 도구입니다.

카드는 색 4가지로 역할을 나눕니다. 파랑은 저장된 것(모델 파일, 모델 저장소, 이미지), 벽돌색은 들어오는 요청과 비용이 드는 곳, 먹색은 서비스와 서버, 회색은 빌드와 배칭 같은 작업입니다. 첫 카드는 기능 7가지의 줄 수를 막대로 보여 주며 모델마다 달라지는 입력 변환 하나만 벽돌색으로 칠했습니다.

## 2. BentoML 이 만들어 주는 기능 4가지

**BentoML 에서는 파이썬 파일 하나에 클래스 하나만 직접 쓰면 HTTP 엔드포인트, 모델 로딩, readiness probe, 메트릭 4가지를 BentoML 이 만들어 줍니다. 웜업은 그 클래스에 몇 줄을 직접 넣습니다. 버전 전환은 4절에서 볼 이미지 배포로 넘어갑니다.**

선배는 BentoML 로 띄우면 하루면 된다고 했는데, 그 하루가 어디서 나오는지는 직접 써야 하는 코드가 얼마나 남는지를 보면 알 수 있습니다. BentoML 로 실험용 pCVR 모델을 띄울 때 직접 쓰는 서비스 코드는 `service.py` 파일 하나입니다. BentoML 에서는 서비스를 파이썬 클래스 하나로 정의한 다음 그 클래스와 메서드 위에 데코레이터를 붙여 서버에서 맡을 역할을 정합니다. 데코레이터는 함수나 클래스 바로 위에 붙이는 `@...` 줄입니다.

아래 파일에서 클래스 `PcvrPreview` 위의 `@bentoml.service` 는 그 클래스를 서비스 하나로 만듭니다. 메서드 `predict` 위의 `@bentoml.api` 는 그 메서드를 API 엔드포인트(밖에서 호출할 수 있는 URL 하나)로 만듭니다. 이 블록이 서비스 파일 전체입니다.

```python
# 하는 일: service.py 파일 하나로 BentoML 서비스 하나를 만든다.
import bentoml
import numpy as np
import torch
# 1단계: 클래스를 서비스로 만든다
# 클래스에 붙인 @bentoml.service 가 서비스를 만든다.
@bentoml.service(
    resources={"cpu": "2"},            # 이 서비스가 쓰는 CPU
    traffic={"timeout": 30},           # 30초를 넘기는 요청은 끊는다
)
class PcvrPreview:
    def __init__(self) -> None:
        # 모델 저장소에서 태그로 불러온다. 코드에 파일 경로를 적지 않는다.
        self.model = bentoml.pytorch.load_model("pcvr_preview:latest")
# 2단계: 메서드를 API 엔드포인트로 만든다
# 메서드에 붙인 @bentoml.api 가 API 엔드포인트 하나를 만든다.
    @bentoml.api
    def predict(self, feats: np.ndarray) -> np.ndarray:
        """입력 변환을 거친 피처 배열을 모델에 넣고 확률을 돌려준다."""
        with torch.no_grad():
            return self.model(torch.from_numpy(feats)).numpy()
```

주석까지 21줄인 이 파일에는 HTTP 요청을 받는 코드도, 지연 시간을 측정하는 코드도 없습니다. 이 파일에 없는 일을 BentoML 이 맡습니다. 서비스를 띄우면 BentoML 이 `predict` 를 호출하는 엔드포인트를 만들어 주므로 1절의 HTTP 엔드포인트 220줄에 해당하는 코드를 직접 쓰지 않습니다.

`predict` 의 엔드포인트 말고도 엔드포인트 몇 개가 같이 생깁니다. 서버가 요청을 받을 준비가 됐는지 알리는 `/readyz`, 서버 프로세스가 살아 있는지 알리는 `/livez`, 지연 시간 같은 메트릭을 내보내는 `/metrics` 입니다. 1절의 readiness probe 70줄이 하던 일은 `/readyz` 가 맡습니다. 준비됐다고 답할 조건을 바꾸고 싶으면 서비스 클래스에 `__is_ready__` 메서드를 직접 씁니다.

`__init__` 은 클래스의 객체가 만들어질 때 한 번 실행되는 메서드입니다. 1절의 모델 로딩 180줄은 이 `__init__` 안의 `bentoml.pytorch.load_model("pcvr_preview:latest")` 한 줄로 줄어듭니다.

1절의 나머지 3가지 가운데 웜업은 BentoML 이 자동으로 해 주지 않으므로 모델을 불러온 다음 더미 입력으로 모델을 몇 번 호출하는 코드를 `__init__` 이나 시작 훅(`@bentoml.on_startup`)에 직접 넣습니다. 시작 훅은 서비스가 시작될 때 실행되는 메서드로, 메서드 위에 이 데코레이터를 붙여 지정합니다. 두 모델 버전 사이에서 트래픽을 옮기는 버전 전환은 BentoML 라이브러리에 없습니다. BentoML 에서는 모델 파일이 이미지 안에 들어가서 모델 버전을 바꾸는 일이 새 이미지를 배포하는 일이 됩니다. 이 배포 과정은 4절에서 봅니다.

입력 변환은 요청의 모양과 바꿀 텐서의 모양이 모델마다 다르므로 BentoML 을 써도 계속 직접 씁니다. BentoML 은 그 코드를 호출할 자리만 만들어 줍니다. 아래 카드는 서비스 파일 하나에 적는 것을 왼쪽에, BentoML 이 만들어 주는 것을 오른쪽에 나눠 보여 줍니다.

## 3. 모델 저장소와 태그

**학습이 끝난 모델을 BentoML 의 모델 저장소(Model Store)에 넣으면 이름과 버전이 붙습니다. 서비스 코드는 파일 경로 대신 이 이름과 버전으로 모델을 불러옵니다.**

코드에 파일 경로를 적어 두면 모델 파일이 다른 곳으로 옮겨질 때마다 코드도 고쳐야 하므로, 2절의 `__init__` 은 모델을 경로가 아니라 이름과 버전을 이은 `pcvr_preview:latest` 로 불러왔습니다. 이렇게 부르면 파일이 어디에 있든 코드를 고칠 일이 없습니다.

모델 저장소는 BentoML 이 모델 파일과 그 버전을 담아 두는 곳입니다. 학습이 끝난 모델을 이름 하나와 함께 저장소에 넣으면 버전이 자동으로 하나 붙습니다. 이름과 버전을 콜론으로 이은 `이름:버전` 을 태그라고 부릅니다. 아래는 모델을 저장소에 넣는 스크립트 `save_model.py` 를 돌린 출력과 저장소에 든 모델 목록을 보는 `bentoml models list` 의 출력입니다.

```text
$ python save_model.py
Model(tag="pcvr_preview:g7k2mqx4a")            저장 완료

$ bentoml models list
 Tag                          Module           Size      Creation Time
 pcvr_preview:g7k2mqx4a       bentoml.pytorch  41.2 MiB  2026-10-04 04:12:31
 pcvr_preview:f3n9pqw1b       bentoml.pytorch  41.2 MiB  2026-10-03 04:11:58
```

`save_model.py` 가 찍은 `pcvr_preview:g7k2mqx4a` 에서 콜론 앞의 `pcvr_preview` 는 넣을 때 준 이름이고 콜론 뒤의 `g7k2mqx4a` 는 저장소가 붙인 버전입니다. 목록에는 같은 이름의 버전 2개가 들어 있습니다. 하나는 2026-10-04 04:12:31 에 만든 `g7k2mqx4a` 이고 다른 하나는 그 전날 04:11:58 에 만든 `f3n9pqw1b` 입니다. 크기는 둘 다 41.2 MiB 입니다.

2절 코드처럼 `pcvr_preview:latest` 라고 적으면 이 가운데 가장 최근 버전인 `g7k2mqx4a` 를 불러옵니다. 특정 버전에 고정하려면 `pcvr_preview:f3n9pqw1b` 처럼 버전까지 적습니다. 모델 파일이 이미지 안에 들어가기 때문에 모델만 이전 버전으로 되돌릴 때도 이 태그 한 줄을 바꾼 뒤 다시 빌드합니다. 모델이 이미지에 들어가는 과정은 4절에서 봅니다.

모델 저장소를 [모델 버전과 재현](post.html?id=model-versioning-reproducibility) 편의 모델 레지스트리와 같은 것으로 보기 쉽지만 두 곳은 담는 것이 다릅니다. 모델 저장소에는 모델 파일과 그 버전이 들어 있는 반면 레지스트리에는 그 모델을 어떤 데이터와 코드로 만들었는지와 지금 어떤 상태인지가 기록됩니다. 실무에서는 두 곳을 함께 씁니다. 레지스트리가 「v417 이 운영 중이다」라고 기록해 두면 그 v417 의 파일은 모델 저장소에 들어 있는 식입니다.

다만 모델 저장소에는 모델 파일만 들어갑니다. 추론 서버 편의 모델로 말하면 신경망 38MB 는 저장소에 들어가지만 임베딩 표 27.7GB 는 들어가지 않고 여전히 임베딩 서비스 한 곳에 남아 있습니다. 서비스는 요청이 올 때마다 그 요청에 필요한 행만 임베딩 서비스에서 가져옵니다. 임베딩 표를 서버마다 두지 않고 한 곳에 두는 까닭은 [추론 서버](post.html?id=inference-server) 편에 있습니다.

## 4. Bento 빌드와 도커 이미지 한 장

**`bentoml build` 명령은 서비스 코드, 모델 파일, 의존 라이브러리 목록을 Bento 라는 패키지 하나로 묶습니다. Bento 를 도커 이미지로 바꾸면 그 이미지를 손대지 않고 앞 편의 배포 파이프라인에 올릴 수 있습니다.**

BentoML 은 서비스 코드와 함께 모델 파일까지 패키지에 담아 도커 이미지로 만들기 때문에, 2절과 3절에서 말한 대로 버전 전환과 롤백이 이미지 배포의 일로 넘어갑니다. 이 절은 그 이미지가 만들어지는 과정을 봅니다.

Bento 에 무엇을 담을지는 `bentofile.yaml` 하나에 적습니다. 아래 파일에는 어느 파일의 어느 클래스가 서비스인지(`service`), 같이 담을 코드 파일(`include`), 라이브러리 목록 파일(`python`), 같이 담을 모델의 태그(`models`), 도커 이미지에 쓸 파이썬 버전(`docker`)이 적혀 있습니다.

```yaml
# bentofile.yaml — Bento 에 무엇을 담을지 적는다
service: "service.py:PcvrPreview"      # 어느 파일의 어느 클래스가 서비스인가
include:
  - "service.py"
  - "features.py"                      # 입력 변환 코드
python:
  requirements_txt: "./requirements.txt"
models:
  - "pcvr_preview:latest"              # 이 태그의 모델 파일을 같이 담는다
docker:
  python_version: "3.11"
```

`include` 의 `features.py` 는 1절과 2절에서 모델마다 직접 쓴다고 한 입력 변환 코드입니다. `models` 에는 3절의 태그 `pcvr_preview:latest` 를 적었으므로 그 태그의 모델 파일이 Bento 안에 같이 들어갑니다.

이 설정 파일을 두고 명령 두 줄을 돌리면 이미지가 나옵니다. 아래처럼 `bentoml build` 로 Bento 를 만든 다음 `bentoml containerize` 로 그 Bento 를 도커 이미지로 바꿉니다.

```text
$ bentoml build
Successfully built Bento(tag="pcvr_preview:h4d8rn2xc")

$ bentoml containerize pcvr_preview:h4d8rn2xc
Successfully built docker image "pcvr_preview:h4d8rn2xc"    1.4GB
```

첫 명령이 찍은 `pcvr_preview:h4d8rn2xc` 는 새로 만든 Bento 의 태그입니다. 둘째 명령은 이 Bento 로 같은 이름의 1.4GB 짜리 도커 이미지를 만들었습니다.

이 이미지는 [Docker 와 CI](post.html?id=container-ci-pipeline) 편에서 다룬 도커 이미지에 해당하지만 안에 든 것이 조금 다릅니다. 그 편의 직접 짠 추론 서버 이미지는 크기가 1.1GB 이며 모델 파일이 이미지 밖에 있었던 반면, BentoML 이 만든 이 이미지는 크기가 1.4GB 이며 모델 파일이 안에 들어 있습니다.

모델 파일이 이미지 안에 들어가면 2가지가 달라집니다. 첫째로 모델만 바꾸려 해도 이미지를 다시 빌드해야 해서 매일 새 모델이 나오는 pCTR 서버라면 매일 새 이미지가 하나씩 생깁니다. 버전 전환과 롤백도 서버 안에서 모델을 바꿔 끼우는 대신 이미지 태그를 바꿔 다시 배포하는 일이 됩니다. 둘째로 이미지 하나에 그때의 코드, 모델, 라이브러리가 그대로 들어 있어서 재현(예전과 같은 서버를 다시 만들어 내는 일)이 쉬워집니다.

카드 아래쪽에서는 직접 짠 서버의 이미지 1.1GB 와 BentoML 이미지 1.4GB 를 막대로 나란히 놓고 모델 파일이 어느 쪽 이미지 안에 들어 있는지 표시합니다.

## 5. 동적 배칭이 이득인 경우

**동적 배칭(dynamic batching)은 여러 요청을 잠깐 모았다가 한 번에 추론하는 기능입니다. `@bentoml.api` 에 옵션 몇 개만 주면 켜지지만 이득을 보는 경우는 좁습니다. 요청 하나가 이미 크면 요청 한 건에 드는 계산은 거의 줄지 않고 요청이 모이기를 기다리는 시간만 붙습니다.**

모아서 추론하면 계산이 줄어든다는 말만 들으면 동적 배칭은 켜 둘수록 좋아 보입니다. 하지만 요청을 모으려면 다음 요청이 들어오기를 기다려야 하므로, 계산이 줄어 얻는 몫과 기다리느라 드는 몫을 함께 따져야 합니다. 배치(batch)는 모델에 한 번에 넣는 요청 여러 개를 말합니다. BentoML 문서에서는 동적 배칭을 adaptive batching 이라고 부릅니다.

BentoML 에서는 `predict` 의 데코레이터에 배치 최대 크기와 최대 지연 시간을 같이 적어 동적 배칭을 켭니다. 아래 발췌에서는 2절 서비스 파일의 `@bentoml.api` 한 줄을 그렇게 바꿨습니다.

```python
# (발췌 — 그대로 실행되지 않습니다.)
# 하는 일: predict 의 데코레이터에 배치 최대 크기 32건과 최대 지연 2ms 를 적어 동적 배칭을 켠다.
    @bentoml.api(batchable=True, max_batch_size=32, max_latency_ms=2)
    def predict(self, feats: np.ndarray) -> np.ndarray:
        with torch.no_grad():
            return self.model(torch.from_numpy(feats)).numpy()
```

`batchable=True` 가 동적 배칭을 켜고 `max_batch_size=32` 와 `max_latency_ms=2` 가 배치 최대 크기 32건과 최대 지연 시간 2ms 를 정합니다.

켜 두었을 때 얻는 몫과 드는 몫이 요청의 크기와 빈도에 따라 어떻게 바뀌는지 보려고 가상 요청 세 경우를 흉내 내어 셉니다. 추론 한 번에 걸리는 시간은 [추론 서버](post.html?id=inference-server) 편의 값대로 고정 0.116ms 에 후보 한 건당 0.0036ms 를 더한 값으로 놓습니다. 여기서 0.116ms 는 후보 수와 상관없이 추론을 한 번 부를 때마다 드는 고정 오버헤드입니다. 이 값으로 요청 하나를 따로 추론하면 후보 1건짜리 요청은 0.116 + 0.0036 을 반올림한 0.120ms 가 걸리고 후보 800건짜리 요청은 0.116 + 0.0036 × 800 = 2.996ms 가 걸립니다.

요청 도착은 푸아송 과정을 따른다고 놓습니다. 푸아송 과정은 평균 빈도만 정해져 있고 요청 하나하나는 서로 상관없이 무작위 간격으로 들어오는 모형입니다. 배치는 첫 요청이 온 뒤 2ms 가 지나거나 32건이 모이면 모인 요청을 한 번에 보낸다고 놓습니다.

아래 코드는 세 경우마다 평균 배치 크기, 요청이 기다린 평균 시간(대기), 요청 하나를 따로 보낼 때와 배치로 보낼 때의 건당 계산(요청 한 건에 드는 계산 시간)을 찍습니다. 판정은 건당 계산이 줄어든 비율이 40% 를 넘으면 「이득이 크다」, 10% 보다 작으면 「거의 안 줄어든다」, 그 사이면 「반반이다」입니다.

```python
# 하는 일: 가상 요청 세 경우로, 동적 배칭(요청 여러 개를 모아 한 번에 추론)이 건당 계산을 얼마나 줄이는지 센다.
import random

# 1단계: 추론 시간과 배치 규칙을 둔다
# 추론 시간은 고정 0.116ms 에 후보 한 건당 0.0036ms 를 더하고(추론 서버 편의 값), 2ms 가 지나거나 32건이 모이면 보낸다. 전부 가상 값이다.
FIXED, PER = 0.116, 0.0036
WINDOW, MAXB, N = 2.0, 32, 60_000

# 2단계: 요청이 모였다가 나가는 모습을 흉내 낸다
# 요청은 푸아송 과정으로 들어온다. 배치마다 크기를, 요청마다 기다린 시간을 모은다.
def run(qps, cand):
    """cand 는 요청 하나에 담겨 오는 후보 수. 평균 배치 크기와 평균 대기를 돌려준다."""
    random.seed(4104)
    lam = qps / 1000.0
    waits, sizes, done = [], [], 0
    while done < N:
        t, n, arrivals = 0.0, 1, [0.0]
        while n < MAXB:
            gap = random.expovariate(lam)
            if t + gap > WINDOW:
                break
            t += gap; n += 1; arrivals.append(t)
        close = t if n == MAXB else WINDOW
        waits += [close - a for a in arrivals]
        sizes.append(n); done += n
    size = sum(sizes) / len(sizes)
    return size, sum(waits) / len(waits)

# 3단계: 세 경우를 비교한다
# 얻는 것은 건당 계산이 줄어드는 몫이고, 드는 것은 요청이 모이기를 기다리는 시간이다.
print('경우 / 배치 크기 / 대기 / 건당 계산 (하나씩 → 배치) / 판정')
for name, qps, cand in [('내부 화면 40 QPS, 요청에 후보 1건', 40, 1),
                        ('내부 화면 2,000 QPS, 후보 1건', 2000, 1),
                        ('광고 서빙 2,639 QPS, 후보 800건', 2639, 800)]:
    size, wait = run(qps, cand)
    alone = FIXED + PER * cand                      # 하나씩 보낼 때 건당
    batched = (FIXED + PER * cand * size) / size    # 배치로 보낼 때 건당
    cut = (1 - batched / alone) * 100
    verdict = '이득이 크다' if cut > 40 else '거의 안 줄어든다' if cut < 10 else '반반이다'
    print(f'  {name}')
    print(f'    배치 {size:.1f}건, 대기 {wait:.2f}ms, 건당 {alone:.3f} → {batched:.3f}ms '
          f'({cut:.0f}% 절감) — {verdict}')

print('\n요청 하나가 이미 크면 배치로 묶어도 건당 계산이 거의 안 줄어든다. 대기만 붙는다')
print('요청 하나가 작고 지연 예산이 넉넉할 때만 동적 배칭이 이득이다')

# 출력:
# 3단계 뜻: 후보 1건짜리 요청이 2,000 QPS 로 들어오면 배치가 5.0건으로 커져 건당 계산이 78% 준다. 40 QPS 는 배치가 1.1건뿐이고, 후보 800건짜리 요청은 이미 커서 3% 만 준다.
# 경우 / 배치 크기 / 대기 / 건당 계산 (하나씩 → 배치) / 판정
#   내부 화면 40 QPS, 요청에 후보 1건
#     배치 1.1건, 대기 1.93ms, 건당 0.120 → 0.111ms (7% 절감) — 거의 안 줄어든다
#   내부 화면 2,000 QPS, 후보 1건
#     배치 5.0건, 대기 1.20ms, 건당 0.120 → 0.027ms (78% 절감) — 이득이 크다
#   광고 서빙 2,639 QPS, 후보 800건
#     배치 6.3건, 대기 1.16ms, 건당 2.996 → 2.899ms (3% 절감) — 거의 안 줄어든다
#
# 요청 하나가 이미 크면 배치로 묶어도 건당 계산이 거의 안 줄어든다. 대기만 붙는다
# 요청 하나가 작고 지연 예산이 넉넉할 때만 동적 배칭이 이득이다
```

출력의 첫 경우인 「내부 화면 40 QPS」는 초당 요청 수(QPS)가 40건뿐이라 2ms 안에 다음 요청이 거의 오지 않으므로 배치가 평균 1.1건에 그칩니다. 모을 요청이 거의 없는데도 2ms 가 지나기를 기다리느라 대기가 1.93ms 붙습니다. 건당 계산은 0.120ms 에서 0.111ms 로 7% 만 줄어 「거의 안 줄어든다」로 판정됐습니다.

둘째 경우(초당 2,000건, 후보 1건)는 요청이 자주 와서 배치가 평균 5.0건으로 커지고 고정 오버헤드 0.116ms 를 그 5.0건이 나눠 내므로, 건당 계산이 0.120ms 에서 0.027ms 로 78% 줄어듭니다. 대기는 1.20ms 입니다. 요청이 이렇게 자주 오고 요청 하나가 작을 때 동적 배칭이 이득입니다.

셋째 경우인 광고 서빙(초당 2,639건, 후보 800건)은 요청 하나에 이미 후보 800건이 담겨 있습니다. 배치에 요청 6건이 모이면 후보 4,800건짜리 텐서 하나가 됩니다. 그런데 요청 하나를 따로 추론할 때 드는 2.996ms 가운데 여러 요청이 나눠 낼 수 있는 몫은 고정 오버헤드 0.116ms 뿐이고 후보 800건에 드는 나머지는 묶어도 줄지 않습니다. 그래서 건당 계산은 2.996ms 에서 2.899ms 로 3% 만 줄어드는데, 그 3% 를 얻으려고 대기 1.16ms 가 붙습니다. 메인 pCTR 서빙은 지연 예산이 8ms 라서 이 대기 1.16ms 만으로도 예산의 15% 를 씁니다.

카드 오른쪽의 건당 계산 절감 막대에서 후보 1건짜리 요청이 자주 올 때의 78% 와 후보 800건짜리 요청의 3% 를 비교합니다.

## 6. 파이썬 서빙 코드의 오버헤드와 지연 예산 8ms

**직접 짠 서버와 BentoML 서버는 추론 계산이 같고 HTTP 요청을 받아 모델에 넘기고 응답을 돌려주는 서빙 코드만 다릅니다. 이 서빙 코드를 파이썬이 처리하면 요청마다 오버헤드가 붙고 가끔 지연이 크게 늘어납니다.**

선배가 메인 pCTR 서버에는 BentoML 을 쓰지 않는다고 한 까닭이 이 절의 숫자에 있습니다. BentoML 이 만들어 주는 서빙 코드는 파이썬으로 짜여 있어서 요청이 올 때마다 그 파이썬 코드를 지나는 시간이 조금씩 더해지는데, 지연 예산이 넉넉하면 이 시간이 보이지 않지만 빠듯하면 곧바로 보입니다. 아래 코드 주석에 적힌 대로 직접 짠 서버는 같은 일을 컴파일된 코드(실행 전에 기계어로 바꿔 둔 코드)로 처리합니다.

두 서버의 차이가 지연 예산 8ms 와 200ms 에서 각각 얼마나 보이는지 알아보려고 같은 모델을 두 방식으로 서빙했다고 놓고 요청 20만 건의 처리 시간을 무작위로 뽑습니다. 추론 계산은 양쪽 모두 평균 2.80ms 에 표준편차(값이 평균에서 흩어진 정도) 0.45ms 로 같게 두고 서빙 코드의 오버헤드만 직접 짠 서버 0.12ms, BentoML 서버 1.80ms 로 다르게 놓습니다.

지연 스파이크는 처리 시간이 가끔 평소보다 크게 늘어나는 일입니다. 두 서버 모두 요청의 15% 에 평균 3.5ms 짜리 스파이크가 붙는다고 놓습니다. 여기에 더해 파이썬 서빙 코드를 쓰는 BentoML 서버에는 요청의 9% 에 평균 6.0ms 짜리 스파이크가 더 붙는다고 놓습니다. 가비지 컬렉션(GC, 쓰지 않는 메모리를 정리하는 일)이 요청 처리 도중에 끼어드는 경우가 그 예입니다.

출력을 읽으려면 p50 과 p99 를 먼저 알아야 합니다. p50 은 요청 20만 건의 시간을 짧은 순으로 늘어놓았을 때 가운데에 오는 값입니다. p99 는 그렇게 늘어놓았을 때 99% 지점에 오는 값이라 가장 느린 1% 의 요청이 p99 보다 오래 걸립니다. 아래 코드는 두 서버의 p50, p99 와 8ms, 200ms 를 넘는 요청의 비율을 찍습니다.

```python
# 하는 일: 같은 모델을 직접 짠 서버와 BentoML 서버로 서빙했다고 놓고, 요청 20만 건의 시간을 뽑아 지연 예산을 넘는 비율을 비교한다.
import random

# 1단계: 추론 시간과 지연 스파이크를 정한다
# 추론 계산은 두 서버가 같다. 수치는 전부 가상 값이고 시드를 고정해 누가 돌려도 같은 값이 나온다.
N = 200_000
INFER_MU, INFER_SD = 2.80, 0.45      # 추론 계산 자체 (후보 800건을 텐서 하나로)
JITTER_P, JITTER_MU = 0.15, 3.5      # 가끔 생기는 지연 스파이크 — GC, 다른 요청과 겹침

# 2단계: 요청 한 건의 시간을 뽑는 함수와 20만 건의 통계를 내는 함수를 만든다
# 다른 것은 추론 앞뒤에서 HTTP 요청을 처리하는 서빙 코드다. 직접 짠 서버는 컴파일된 코드가, BentoML 서버는 파이썬이 맡는다.
def draw(fixed, extra_p, extra_mu):
    """서빙 오버헤드 + 추론 + 지연 스파이크. extra 는 파이썬 서빙 코드에서 더 자주 생기는 스파이크다."""
    t = fixed + max(0.4, random.gauss(INFER_MU, INFER_SD))
    if random.random() < JITTER_P:
        t += random.expovariate(1 / JITTER_MU)
    if random.random() < extra_p:
        t += random.expovariate(1 / extra_mu)
    return t

def stats(name, fixed, extra_p, extra_mu):
    random.seed(4104)
    xs = sorted(draw(fixed, extra_p, extra_mu) for _ in range(N))
    p50, p99 = xs[N // 2], xs[int(N * 0.99)]
    return name, p50, p99, sum(1 for x in xs if x > 8) / N * 100, sum(1 for x in xs if x > 200) / N * 100

# 3단계: 두 서버의 지연을 찍는다
rows = [stats('직접 짠 서버', 0.12, 0.0, 1.0),
        stats('BentoML 서버', 1.80, 0.09, 6.0)]

print('서버 / p50 / p99 / 8ms 초과 / 200ms 초과')
for n, p50, p99, o8, o200 in rows:
    print(f'  {n}  {p50:.2f}ms  {p99:.2f}ms  {o8:.2f}%  {o200:.2f}%')

# 4단계: 지연 예산 둘로 읽는다
print(f'\n지연 예산 8ms: 초과율이 {rows[0][3]:.2f}% 에서 {rows[1][3]:.2f}% 로 {rows[1][3] / rows[0][3]:.1f}배')
print(f'지연 예산 200ms: 둘 다 {rows[1][4]:.2f}% 다. 예산이 넉넉하면 이 차이가 안 보인다')
print(f'파이썬 서빙 코드가 더하는 오버헤드 {1.80 - 0.12:.2f}ms 는 예산 8ms 의 {(1.80 - 0.12) / 8 * 100:.0f}% 다')

# 출력:
# 3단계 뜻: 추론은 같은데 BentoML 서버가 p50 4.75ms, p99 20.08ms 로 직접 짠 서버의 3.01ms, 12.64ms 보다 길다. 8ms 를 넘는 요청도 3.53% 에서 10.69% 로 는다.
# 서버 / p50 / p99 / 8ms 초과 / 200ms 초과
#   직접 짠 서버  3.01ms  12.64ms  3.53%  0.00%
#   BentoML 서버  4.75ms  20.08ms  10.69%  0.00%
# 4단계 뜻: 예산 8ms 에서는 초과율이 3.0배로 벌어지고 200ms 에서는 둘 다 0.00% 다. 어느 서버가 맞는지는 지연 예산이 정한다.
#
# 지연 예산 8ms: 초과율이 3.53% 에서 10.69% 로 3.0배
# 지연 예산 200ms: 둘 다 0.00% 다. 예산이 넉넉하면 이 차이가 안 보인다
# 파이썬 서빙 코드가 더하는 오버헤드 1.68ms 는 예산 8ms 의 21% 다
```

찍힌 값을 보면 추론 계산이 같은데도 BentoML 서버의 p50 은 4.75ms, p99 는 20.08ms 로 직접 짠 서버의 3.01ms, 12.64ms 보다 깁니다. 지연 예산 8ms 를 넘는 요청은 3.53% 에서 10.69% 로 10.69 ÷ 3.53 = 3.0배가 되지만 200ms 를 넘는 요청은 두 서버 모두 0.00% 입니다. 그래서 어느 서버가 맞는지는 지연 예산이 정합니다. 같은 BentoML 서버라도 지연 예산이 8ms 인 메인 pCTR 서빙에는 맞지 않고 200ms 인 내부 화면에서는 아무 문제가 없습니다.

8ms 초과율이 세 배가 되는 데는 까닭이 2가지 있습니다. 첫째로 파이썬 서빙 코드가 더하는 오버헤드 1.80 - 0.12 = 1.68ms 가 지연 예산 8ms 의 21% 를 먼저 씁니다. 둘째로 BentoML 서버는 지연 스파이크가 더 잦아서 느린 쪽 끝의 p99 가 12.64ms 에서 20.08ms 로 늘어납니다.

분포에서 가장 오래 걸리는 끝부분을 꼬리라고 부릅니다. 두 서버의 차이를 p50 과 p99 에서 따로 보면 p50 은 4.75 - 3.01 = 1.74ms 차이인데 p99 는 20.08 - 12.64 = 7.44ms 차이라서, 지연 예산을 넘기는 요청은 가운데 값 근처가 아니라 느린 쪽 꼬리에서 나옵니다. 꼬리가 예산을 넘기는 이 성질은 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편에서 본 성질과 같습니다.

지훈 씨 팀은 BentoML 을 쓸지 정하기 전에 지연 예산에서 서빙 오버헤드가 차지하는 비율부터 측정하고 그 비율이 20% 를 넘으면 BentoML 을 쓰지 않습니다. 메인 pCTR 서빙은 이 비율이 21% 라 이 기준을 넘습니다. 파이썬 프로세스를 여러 개 띄우면 이 문제가 해결되는지는 7절에서 봅니다.

## 7. 워커 수에 따른 처리량과 요청 한 건의 지연

**BentoML 에는 파이썬 프로세스를 여러 개 띄우는 방법이 3가지 있습니다. 3가지 모두 처리량(초당 처리 건수)을 늘리지만 요청 한 건의 지연은 줄이지 못합니다.**

6절 끝에 남긴 물음, 곧 파이썬 프로세스를 여러 개 띄우면 8ms 초과율이 내려가는지를 이 절에서 숫자로 봅니다. 프로세스는 실행 중인 프로그램 하나입니다. 스레드는 한 프로세스 안에서 코드를 실행하는 흐름으로 한 프로세스에 여러 개를 둘 수 있습니다. 그런데 파이썬에는 GIL(Global Interpreter Lock)이라는 제약이 있습니다. GIL 은 한 프로세스 안에서 한 번에 한 스레드만 파이썬 코드를 실행하게 합니다. 그래서 서버에 코어(CPU 안에서 계산을 맡는 단위)가 8개 있어도 파이썬 프로세스 하나는 코어 하나만 씁니다. BentoML 이 이 제약을 넘는 방법 3가지는 아래 표와 같습니다. 표의 워커(worker)는 서비스의 요청을 받아 처리하는 파이썬 프로세스 하나입니다.

| 방식 | 무엇을 하나 | 어디에 효과가 있나 |
|---|---|---|
| 워커 프로세스 여러 개 | 서비스 하나를 파이썬 프로세스 여러 개로 띄운다. 서비스에 워커 수를 적고, 코어 수에 맞추는 설정도 있다 | 코어를 다 쓴다. 처리량을 늘리는 가장 기본 방법이다 |
| 서비스를 여러 개로 나누기 | 입력 변환 서비스와 모델 서비스를 따로 정의하고 한쪽이 다른 쪽을 호출한다. 각각 자기 프로세스로 돈다 | 가벼운 쪽과 무거운 쪽의 워커 수를 따로 정한다 |
| 비동기 API 함수 | API 함수를 `async` 로 쓰면 워커 하나가 여러 요청을 번갈아 처리한다 | 외부 응답을 기다리는 시간에만 효과가 있다. 계산에는 효과가 없다 |

표의 첫째 방법인 워커 프로세스 여러 개가 가장 자주 쓰는 방법입니다. 아래 발췌에서는 2절의 서비스 데코레이터에 워커 수 4를 한 줄 적어 파이썬 프로세스 4개가 요청을 나눠 받게 했습니다.

```python
# (앞 블록에 이어서 돌린다.)
# 하는 일: 서비스 데코레이터에 워커 4개를 적어, 파이썬 프로세스 4개가 요청을 나눠 받게 한다.
@bentoml.service(
    workers=4,                         # 파이썬 프로세스를 4개 띄운다
    resources={"cpu": "4"},
)
class PcvrPreview:
    ...
```

`resources` 의 CPU 도 2절의 2개에서 4개로 늘려 적었습니다.

표의 둘째 방법은 서비스를 나누는 방식입니다. 요청을 텐서로 바꾸는 입력 변환은 가벼운 반면 모델 계산은 무거운데, 두 일을 한 서비스에 두면 워커를 같은 수로만 늘릴 수 있습니다. 입력 변환 서비스와 모델 서비스로 나눠 두면 입력 변환은 워커 2개, 모델은 6개처럼 수를 따로 정할 수 있습니다. BentoML 1.2 보다 이전 버전에서는 이 기능이 Runner 라는 이름으로 따로 있었는데, 1.2 버전부터 서비스를 여러 개 두는 방식으로 바뀌었습니다. 그래서 찾아본 예제가 Runner 를 쓰고 있다면 1.2 이전 버전의 문법입니다.

표의 셋째 방법인 비동기 API 함수는 API 함수를 `async` 로 써서 워커 하나가 한 요청의 외부 응답을 기다리는 동안 다른 요청을 처리하게 합니다. 그래서 피처 스토어(학습과 서빙에 쓰는 피처 값을 모아 둔 저장소)에서 값을 읽어 오는 것처럼 기다리는 시간이 있는 함수에는 효과가 있지만 계산만 하는 함수에는 효과가 없습니다.

워커 수를 늘리면 무엇이 바뀌고 무엇이 그대로인지 보려고 첫째 방법의 효과를 숫자로 계산합니다. 메인 pCTR 서빙의 요청 초당 2,639건을 서버 12대가 나눠 받으면 서버 한 대에는 2,639 를 12 로 나눈 초당 약 220건이 들어옵니다. 요청 한 건의 처리 시간은 6절에서 뽑은 BentoML 서버의 p50 4.75ms 로 둡니다.

부하율(utilization)은 워커가 요청을 처리하느라 바쁜 시간의 비율입니다. 부하율이 1 이상이면 요청이 처리되는 속도 이상으로 들어와서 대기열(처리를 기다리는 요청의 줄)이 계속 쌓입니다. 계산에는 대기행렬 이론의 간단한 모형인 M/M/c 를 씁니다. M/M/c 는 요청이 무작위 간격으로 들어오고 처리 시간도 무작위인 대기열을 워커 c 개가 처리한다고 놓는 모형입니다. 코드의 `erlang_c` 는 이 모형에서 요청이 대기열에 서게 될 확률을 구하는 식(Erlang C)입니다.

아래 코드는 워커를 1개에서 16개까지 바꿔 가며 서버 한 대의 최대 처리량, 부하율, 대기 시간, 한 건의 처리 시간을 찍습니다.

```python
# 하는 일: 워커(파이썬 프로세스) 수를 1개에서 16개까지 바꿔 가며, 서버 한 대의 최대 처리량과 대기 시간이 어떻게 바뀌는지 센다.
import math

# 1단계: 요청량과 처리 시간을 둔다
# 요청 한 건의 처리 시간은 앞 절에서 뽑은 값 그대로 둔다. 전부 가상 값이다.
QPS_PER_SERVER = 2639 / 12          # 서버 12대가 나눠 받는 요청 (건/초)
SERVICE_MS = 4.75                   # BentoML 서버의 요청 한 건 p50
OVERHEAD_MS = 1.68                  # 그중 파이썬 서빙 코드가 더하는 오버헤드

# 2단계: 요청이 대기열에 설 확률을 구하는 식을 만든다
# 대기행렬 이론의 간단한 모형(M/M/c)으로 근사한다.
def erlang_c(c, a):
    """워커 c 개에 부하 a 일 때 요청이 대기열에 서게 될 확률."""
    s = sum(a ** k / math.factorial(k) for k in range(c))
    last = a ** c / math.factorial(c) * (c / (c - a))
    return last / (s + last)

# 3단계: 워커 수마다 처리량과 대기를 찍는다
# 워커 수만 바꿔 가며 무엇이 바뀌고 무엇이 그대로인지 본다.
print('워커 / 최대 처리량 / 부하율 / 대기 시간 / 한 건의 처리 시간')
mu = 1000 / SERVICE_MS              # 워커 하나가 초당 처리하는 건수
for c in (1, 2, 4, 8, 16):
    cap = mu * c
    rho = QPS_PER_SERVER / cap
    if rho >= 1:
        print(f'  {c:>2}개  {cap:7.0f} 건/초  부하율 {rho:.2f}  대기열이 계속 쌓인다')
        continue
    a = QPS_PER_SERVER / mu
    wq = erlang_c(c, a) / (c * mu - QPS_PER_SERVER) * 1000 if c > a else float('inf')
    print(f'  {c:>2}개  {cap:7.0f} 건/초  부하율 {rho:.2f}  {wq:6.3f}ms 대기  '
          f'처리 시간은 그대로 {SERVICE_MS:.2f}ms')

# 4단계: 워커가 몇 개면 되는지 정리한다
need = math.ceil(QPS_PER_SERVER / mu / 0.77)
print(f'\n부하율을 0.77 아래로 두려면 워커 {need}개면 되는데, 그때 대기가 1.78ms 붙는다')
print('4개로 늘리면 대기가 0.04ms 로 거의 사라지고, 그 뒤로는 늘려도 얻을 것이 없다')
print(f'바뀌지 않는 것 둘 — 한 건의 처리 시간 {SERVICE_MS:.2f}ms 와 그 안의 오버헤드 {OVERHEAD_MS:.2f}ms')
print('그래서 8ms 초과율 10.69% 는 워커를 몇 개로 늘려도 그대로다')

# 출력:
# 3단계 뜻: 워커 1개는 부하율 1.04 라 대기열이 쌓이고, 2개면 1.782ms, 4개면 0.038ms 를 기다린다. 한 건의 처리 시간은 몇 개든 4.75ms 다.
# 워커 / 최대 처리량 / 부하율 / 대기 시간 / 한 건의 처리 시간
#    1개      211 건/초  부하율 1.04  대기열이 계속 쌓인다
#    2개      421 건/초  부하율 0.52   1.782ms 대기  처리 시간은 그대로 4.75ms
#    4개      842 건/초  부하율 0.26   0.038ms 대기  처리 시간은 그대로 4.75ms
#    8개     1684 건/초  부하율 0.13   0.000ms 대기  처리 시간은 그대로 4.75ms
#   16개     3368 건/초  부하율 0.07   0.000ms 대기  처리 시간은 그대로 4.75ms
# 4단계 뜻: 워커를 늘려 줄어드는 시간은 대기뿐이다. 처리 시간과 그 안의 오버헤드 1.68ms 가 그대로라 8ms 초과율 10.69% 도 그대로다.
#
# 부하율을 0.77 아래로 두려면 워커 2개면 되는데, 그때 대기가 1.78ms 붙는다
# 4개로 늘리면 대기가 0.04ms 로 거의 사라지고, 그 뒤로는 늘려도 얻을 것이 없다
# 바뀌지 않는 것 둘 — 한 건의 처리 시간 4.75ms 와 그 안의 오버헤드 1.68ms
# 그래서 8ms 초과율 10.69% 는 워커를 몇 개로 늘려도 그대로다
```

찍힌 값을 위에서부터 읽으면 워커 하나는 요청 한 건에 4.75ms 가 걸리므로 1초에 약 211건(1000 ÷ 4.75)을 처리합니다. 서버 한 대에 초당 약 220건이 들어오니 워커 1개의 부하율은 1.04 로 1 을 넘어서 출력대로 대기열이 계속 쌓입니다. 워커 2개면 최대 처리량이 421건으로 늘어 부하율이 0.52 로 내려가지만 평균 대기가 1.782ms 붙습니다. 워커 4개면 최대 처리량 842건, 부하율 0.26 에서 평균 대기가 0.038ms 로 거의 사라집니다. 그런데 워커를 몇 개로 늘려도 마지막 열의 한 건의 처리 시간은 4.75ms 그대로입니다.

워커를 어디까지 늘릴지도 이 출력에서 보입니다. 부하율만 보면 워커 2개의 0.52 로 충분해 보이고 출력의 4단계도 부하율을 0.77 아래로 두려면 워커 2개면 된다고 찍지만 그때 대기가 1.78ms 붙습니다. 4개로 늘리면 대기가 0.04ms 로 거의 사라지고 그 뒤로는 늘려도 얻을 것이 없습니다. 모델은 워커마다 한 번씩 메모리에 올라가서 워커를 늘린 만큼 메모리도 더 쓰므로, 대기가 이미 0.000ms 인 8개와 16개는 얻는 것 없이 메모리만 더 씁니다.

카드에서 왼쪽 칸의 대기 시간은 워커를 늘릴수록 줄어드는 반면 오른쪽 칸의 한 건의 처리 시간은 4.75ms 로 내내 같습니다.

워커를 늘려 줄어드는 시간은 대기뿐입니다. 요청 한 건의 처리 시간과 그 안의 오버헤드 1.68ms 가 그대로라서 8ms 초과율 10.69% 도 워커를 몇 개로 늘리든 10.69% 이므로 6절의 결론은 바뀌지 않습니다. 이 초과율은 요청 한 건이 파이썬 서빙 코드를 지나며 붙는 오버헤드에서 나오는데, 워커 수는 서버가 1초에 처리하는 건수를 바꿀 뿐 요청 한 건이 지연 예산 안에 끝나는지는 바꾸지 못합니다.

그래서 처리량이 모자랄 때는 워커를 늘리지만 요청 한 건이 지연 예산을 넘을 때는 서빙 방식을 바꿉니다.

## 8. BentoML 을 쓰는 곳과 쓰지 않는 곳

**BentoML 을 쓸지는 지연 예산, 요청량, 모델 개수 세 가지로 정합니다. 예산이 넉넉하고 모델이 여럿이면 BentoML 이 나은 반면 예산이 빠듯하고 모델이 하나면 직접 짠 서버가 낫습니다.**

BentoML 은 2절에서 본 것처럼 직접 쓰는 코드를 줄여 개발 시간을 아껴 주는 대신 6절에서 본 것처럼 요청마다 오버헤드를 더하는데, 둘 가운데 어느 쪽이 더 큰지는 서비스마다 다릅니다. 지훈 씨 팀의 모델이 쓰이는 곳 5군데를 늘어놓고 세 가지를 물어보면 아래 표처럼 나뉩니다. 표의 값은 모두 가상입니다.

| 어디에 쓰나 | 지연 예산 | 요청량 | 모델 개수 | 무엇을 쓰나 |
|---|---|---|---|---|
| 메인 pCTR 서빙 | 8ms | 초당 2,639건 | 하나 | 직접 짠 서버 |
| 운영자 내부 화면의 pCVR 실험용 모델 | 200ms | 초당 40건 | 실험용 모델 여럿 | BentoML |
| 분석가가 돌리는 배치 추론 | 없음 | 하루 한 번 | 그때마다 다름 | BentoML |
| 광고주 리포트의 예상 전환 | 2초 | 초당 30건 | 둘 | BentoML |
| two-tower retrieval 모델의 유저 타워 | 3ms | 초당 2,639건 | 하나 | 직접 짠 서버 |

배치 추론은 요청을 기다리지 않고 정해진 때에 예측값을 한꺼번에 계산해 두는 일입니다. two-tower retrieval 모델은 유저 쪽 신경망(유저 타워)과 광고 쪽 신경망이 각각 벡터를 만들어 후보 광고를 골라내는 모델입니다.

표의 가운데 세 줄인 운영자 내부 화면의 실험용 모델, 분석가가 돌리는 배치 추론, 광고주 리포트의 예상 전환에는 BentoML 이 낫습니다. 세 곳 모두 지연 예산이 밀리초가 아니라 초 단위이거나 아예 없습니다. 모델도 자주 바뀌거나 여럿이라 이런 곳에서 서버를 직접 짜면 1절의 1,800줄을 모델마다 다시 만들어야 합니다.

반대로 맨 위의 메인 pCTR 서빙과 맨 아래의 two-tower retrieval 모델의 유저 타워에는 직접 짠 서버가 낫습니다. 두 곳은 지연 예산이 8ms 와 3ms 로 한 자리 밀리초이고 요청량이 초당 2,639건으로 크며 모델이 하나입니다. 이런 곳에서는 1,800줄을 짜는 일이 한 번으로 끝나지만 1.68ms 의 오버헤드는 초당 2,639건의 요청 하나하나에 붙습니다.

두 방식 가운데 하나만 고를 필요는 없습니다. 새 모델을 BentoML 로 먼저 띄워 예측값을 확인한 다음 광고에 쓰기로 정해지면 그때 직접 짠 서버로 옮길 수 있습니다. 지훈 씨 팀도 실험용 pCVR 모델을 이 순서로 다루려고 합니다.

## 9. 두 무대의 지연 예산과 BentoML 선택 기준

**지연 예산을 누가 정하는지가 무대마다 다릅니다. 한 회사가 앱과 광고 서버를 다 가진 담장 안에서는 광고 플랫폼이 직접 정하는 반면 매체와 광고 서버가 서로 다른 회사인 열린 RTB 에서는 거래소가 정합니다. 그래서 BentoML 을 쓸 수 있는 범위도 무대마다 다릅니다.**

8절의 표는 지연 예산을 이미 정해진 값으로 놓고 읽었습니다. 그 예산을 정하는 곳이 무대마다 다르므로 같은 기준으로 판단해도 BentoML 을 쓸 수 있는 곳의 범위가 달라집니다.

### 담장 안: 플랫폼이 나눠 주는 지연 예산 [무대: 닫힌 생태계]

담장 안에서는 플랫폼이 응답 전체에 주어진 시간을 단계마다 나눠 줍니다. 메인 pCTR 서빙의 모델 호출이 받은 8ms 도 플랫폼이 그렇게 나눠 준 몫입니다. 이렇게 플랫폼이 예산을 정하므로 어떤 모델은 예산을 넉넉히 받을 수 있습니다.

예산을 넉넉히 받을 수 있는 모델은 광고를 고르는 경로에 들어가지 않는 모델입니다. 8절 표의 운영자 화면 실험용 모델, 광고주 리포트의 예상 전환, 하루 한 번 도는 배치 추론이 그 예입니다. 이 3가지는 요청이 광고 경매(보여 줄 광고를 입찰로 고르는 단계)를 지나지 않으므로 예산이 초 단위입니다. 담장 안에는 자사 데이터로 만드는 내부 도구가 많아서 이런 모델도 많습니다.

지훈 씨의 pCVR 실험용 모델도 이런 모델에 해당합니다. 이 모델은 BentoML 로 하루 만에 띄울 수 있고 예측값을 보다가 광고에 쓰기로 정해지면 그때 직접 짠 서버로 옮깁니다. 옮길 때는 서빙 코드를 다시 쓰고 모델과 입력 변환 코드는 그대로 가져갑니다.

### 열린 RTB: 거래소가 정하는 응답 시간 [무대: 열린 RTB]

열린 RTB 에서는 광고 서버가 입찰 요청에 답해야 하는 시간을 거래소가 정합니다. 거래소는 매체(광고를 실을 앱이나 웹사이트)의 광고 자리를 실시간 입찰에 부쳐 여러 광고 서버에 입찰 요청을 보내고 응답을 받는 곳입니다. 그 시간은 흔히 100ms 안쪽이고 요청과 응답이 네트워크를 오가는 왕복 시간도 그 안에 들어 있으므로, 우리 서버가 쓸 수 있는 시간은 그보다 더 짧습니다. 시간 안에 답하지 못하면 그 입찰은 버려집니다.

서버가 쓸 수 있는 시간이 짧을수록 BentoML 의 오버헤드 1.68ms 가 그 시간에서 차지하는 비율이 커지는 데다 거래소마다 정한 시간이 달라 가장 빠듯한 거래소에 맞춰야 하므로, 입찰 경로에 있는 모델은 BentoML 로 띄우기 어렵습니다.

그래도 열린 RTB 에도 입찰 경로 밖에서 도는 일이 있고 그런 일에는 BentoML 을 쓸 수 있습니다. 광고주에게 보내는 리포트, 소재(광고에 쓰는 이미지와 문구) 점수를 미리 계산해 두는 배치 추론, 세그먼트(비슷한 사용자를 모은 그룹)를 만드는 작업이 그렇습니다. 무대가 달라도 판단 기준은 같아서 어느 무대에서든 지연 예산이 밀리초 단위인지 초 단위인지를 먼저 봅니다.

## 한눈 정리

| 무엇 | 직접 짠 서버 | BentoML 서버 |
|---|---|---|
| 직접 쓰는 코드 | 일곱 기능 전부, 약 1,800줄 | 서비스 파일 21줄과 입력 변환, 웜업 몇 줄 |
| 요청당 서빙 오버헤드 | 0.12ms | 1.80ms |
| p50 과 p99 | 3.01ms, 12.64ms | 4.75ms, 20.08ms |
| 지연 예산 8ms 초과율 | 3.53% | 10.69% |
| 지연 예산 200ms 초과율 | 0.00% | 0.00% |
| 모델 파일이 있는 곳 | 이미지 밖 | 이미지 안 (1.4GB) |
| 버전 전환과 롤백 | 서버 안에서 모델을 바꿔 끼운다 | 이미지 태그를 바꿔 다시 배포한다 |
| 새 모델 하나를 띄우는 데 | 며칠 | 하루 |
| 맞는 경우 | 예산이 한 자리 밀리초, 모델 하나 | 예산이 초 단위, 모델 여럿 |

## 헷갈리기 쉬운 점

**BentoML 이 서버 기능 7가지를 전부 만들어 주지는 않습니다.** BentoML 이 만들어 주는 기능은 HTTP 엔드포인트, 모델 로딩, readiness probe, 메트릭 4가지입니다. 입력 변환과 웜업은 여전히 직접 씁니다. 두 버전 사이의 트래픽 전환은 BentoML 이 아니라 배포 환경이 맡습니다.

**BentoML 자체가 느린 것은 아닙니다.** 두 서버는 추론 계산에 똑같이 2.80ms 를 쓰고 HTTP 요청을 처리하는 서빙 코드만 다릅니다. 이 서빙 코드가 더하는 오버헤드 1.68ms 는 지연 예산이 200ms 면 그 0.8% 에 그쳐 차이가 보이지 않습니다.

**지연 예산을 넘기는 요청은 가운데 값 근처가 아니라 느린 쪽 꼬리에서 나옵니다.** 두 서버의 차이는 p50 에서 1.74ms 뿐이지만 p99 에서는 7.44ms 로 벌어집니다. 그래서 p50 만 보고 「2ms 차이면 괜찮다」고 판단하면 8ms 초과율이 세 배가 된 것을 놓칩니다.

**동적 배칭을 켠다고 늘 이득을 보지는 않습니다.** 요청 하나에 이미 후보 800건이 담겨 있으면 여러 요청을 묶어도 건당 계산이 3% 만 줄어드는데, 그 3% 를 얻으려고 대기 1.16ms 가 붙습니다. 그래서 동적 배칭은 요청 하나가 작을 때만 켭니다.

**BentoML 의 모델 저장소와 모델 레지스트리는 담는 것이 다릅니다.** 모델 저장소에는 모델 파일과 버전이 들어 있는 반면 레지스트리에는 그 모델을 만든 데이터와 코드, 운영 상태가 적혀 있습니다. 실무에서는 두 곳을 같이 씁니다.

**모델 파일을 이미지 안에 담으면 롤백하는 방법이 바뀝니다.** 모델만 바꾸려 해도 이미지를 다시 빌드해야 하므로 매일 새 모델이 나오는 서버라면 매일 새 이미지가 하나씩 생깁니다. 앞 편에서 본 롤백 한 줄도 이미지 태그를 바꾸는 일이 됩니다.
