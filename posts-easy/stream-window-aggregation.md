지훈 씨는 여섯째 주입니다. 모델 팀 사람이 채팅으로 한 줄을 보냈습니다. 「광고별 최근 1시간 클릭 수를 피처로 쓰고 싶은데 만들어 주실 수 있나요?」

부탁이 한 줄뿐이라 지훈 씨는 쉬운 일로 여겼습니다. 지금까지 만든 피처(모델이 광고 점수를 매길 때 입력으로 받는 값)는 모두 새벽에 하루치를 한 번에 계산했는데, 새벽에는 어제 로그가 이미 다 놓여 있어 세기만 하면 됐습니다. 그런데 이번 피처는 광고 서버가 요청을 받는 바로 그 순간에 값을 읽어 갑니다.

책상에서 종이에 적어 보던 지훈 씨는 손을 멈췄습니다. 15시 1분에 묻는 「최근 1시간」과 15시 7분에 묻는 「최근 1시간」은 같은 구간이 아니므로 값 하나를 만들어 두면 끝나는 일이 아니었습니다.

**「최근 1시간 클릭 수」는 누가, 언제까지 센 값일까요?**

이 값은 스트림 잡(stream job)이 셉니다. 스트림 잡은 클릭이 들어오는 대로 광고마다 개수를 더해 두었다가 정해진 구간이 끝나면 그 구간의 값을 하나 내놓는 프로그램입니다. 값을 내는 단위인 이 구간을 윈도우(window)라고 부르고 시간을 윈도우로 잘라 그 안에 든 클릭을 세는 일을 윈도우 집계라고 부릅니다. 스트림 잡이 내놓은 값은 그대로 광고 점수에 들어가 입찰가를 바꾸므로 숫자가 맞는지와 함께 그 숫자를 몇 분 전에 셌는지도 따져야 합니다.

> **한 줄 요약:** 「최근 1시간 클릭 수」는 광고 서버가 요청마다 세는 값이 아니라 스트림 잡이 시간을 윈도우로 잘라 미리 세어 Redis(값을 메모리에 두어 빠르게 읽고 쓰는 저장소)에 놓아 둔 값입니다. 윈도우를 자르는 방법은 정각마다 잘라 겹치지 않게 이어 붙이는 텀블링과 같은 길이를 1분씩 밀어 겹치게 두는 슬라이딩 두 가지입니다. 윈도우를 언제 닫을지는 워터마크(윈도우가 끝난 뒤 늦게 오는 클릭을 얼마나 더 기다릴지 적은 값)가 정하는데, 워터마크를 2분으로 두면 14:00~15:00 윈도우는 15:02 에 닫히고 하루 클릭 228만 건 가운데 2분보다 늦게 도착한 2,280건은 자기 윈도우가 닫힌 뒤에 와서 그 윈도우에 들어가지 못합니다. 그래서 광고 9931 의 14:00~15:00 을 스트림 잡은 1,203 으로 세고 늦게 온 클릭까지 모아 하루 뒤에 세는 배치(쌓인 데이터를 정해진 때에 한꺼번에 처리하는 작업)는 1,204 로 셉니다.

> **골라 읽는 법** — 절이 8개이고 절마다 카드 한 장이나 표 하나가 들어 있어 카드나 표만 보고 넘어가도 됩니다.
>
> - 묻는 시각마다 달라지는 「최근 1시간」의 구간 → 1절
> - 클릭이 값이 되기까지 지나는 세 곳, topic 과 스트림 잡과 Redis → 2절
> - 윈도우를 자르는 두 방법, 텀블링 윈도우와 슬라이딩 윈도우 → 3절
> - 클릭에 붙는 두 시각, 일어난 시각과 도착한 시각 → 4절
> - 윈도우가 닫히는 시각을 정하는 워터마크 → 5절
> - 윈도우가 닫힌 뒤 도착한 클릭을 다루는 세 가지 방법 → 6절
> - 스트림 잡이 센 값과 하루 뒤 배치가 센 값의 차이 → 7절
> - 담장 안(앱과 광고 서버를 한 회사가 다 가진 곳)과 열린 RTB(매체와 광고 서버가 서로 다른 회사인 실시간 경매 시장)에서 클릭이 오는 경로의 차이 → 8절

이 글에 나오는 시각, 건수, 광고 번호는 모두 설명을 위해 만든 가상 값입니다. 그 가운데 하루 클릭 228만 건, 클릭이 쌓이는 topic `ad.click` 을 나눈 partition 12 개, 줄마다 붙어 partition 을 정하는 key `req_id` 는 [Kafka 기초](post.html?id=kafka-log-pipeline) 편에서 쓴 값을 그대로 가져왔습니다. 실시간으로 계산하는 스트리밍 피처가 Redis 를 거쳐 서빙(학습한 모델이 실제 요청에 점수를 매기는 일)에 쓰이기까지의 경로도 [피처 스토어](post.html?id=feature-store-serving) 편과 같습니다. topic, partition, key 가 이 글의 잡에서 어떻게 쓰이는지는 2절에서 풉니다.

## 1. 묻는 시각마다 달라지는 「최근 1시간」의 구간

**「최근 1시간」은 묻는 시각에 따라 앞뒤가 함께 밀리는 구간이라 15:01 에 물으면 14:01~15:01 이고 15:07 에 물으면 14:07~15:07 입니다. 두 구간은 앞뒤가 6분씩 밀려 있어서 그 6분 사이에 클릭 120건이 오갑니다.**

지훈 씨가 종이에 적다 손을 멈춘 까닭도 이 차이에 있습니다. 「최근 1시간」이 고정된 구간이라면 값을 하나 세어 두면 되지만 실제로는 묻는 순간마다 구간의 앞뒤가 함께 밀리므로, 언제 센 값을 얼마나 오래 쓸지까지 정해야 합니다.

광고 9931 로 세어 보겠습니다. 광고 9931 은 14:00 부터 15:00 까지 한 시간 동안 클릭 1,204건을 받았으므로 1분에 평균 20.1건(1,204 ÷ 60)이 들어옵니다. 15:07 요청이 묻는 14:07~15:07 은 15:01 요청이 묻는 14:01~15:01 에서 앞쪽 14:01~14:07 의 6분이 빠지고 뒤쪽 15:01~15:07 의 6분이 붙은 구간인데, 1분에 20.1건이면 6분에는 120건 남짓이 들어오므로 두 요청 사이에서 빠지는 클릭과 새로 들어오는 클릭이 각각 120건 남짓입니다. 120건은 1,204건의 10% 라서 이름은 같은 「최근 1시간」이어도 두 요청이 세는 클릭은 10% 가 서로 다릅니다.

그러면 요청이 올 때마다 그 자리에서 세면 되지 않느냐고 물을 수 있는데, 요청 수와 요청 하나에 쓸 수 있는 시간을 보면 그렇게 할 수 없습니다. 요청은 하루 2억 2,800만 건으로 초당 2,639건이 들어옵니다. 요청 하나가 광고 점수를 매기는 데 쓸 수 있는 시간은 8밀리초이고 그 안에 후보 광고 800건의 점수를 모두 계산해야 하므로, 한 시간치 클릭 로그를 스캔(처음부터 끝까지 읽으며 세는 일)할 시간은 그 8밀리초 어디에도 없습니다.

그래서 순서를 뒤집습니다. 값을 미리 세어 어딘가에 놓아 두고 광고 서버는 그 값을 읽기만 하게 합니다. 광고 서버가 읽기만 하면 「이 값은 언제 센 값인가」라는 물음이 새로 생기는데, 아래 표는 스트림 잡이 1분에 한 번 값을 새로 내놓는다고 가정하고 요청이 뜻하는 구간과 미리 세어 둔 값의 구간을 나란히 놓았습니다. 표의 「값이 묵은 시간」은 값을 센 구간이 끝난 뒤 요청 시각까지 지난 시간이라 짧을수록 신선한 값입니다.

| 요청 시각 | 요청이 뜻하는 구간 | 미리 세어 둔 값의 구간 | 값이 묵은 시간 |
|---|---|---|---|
| 15:01 | 14:01~15:01 | 14:00~15:00 | 1분 |
| 15:07 | 14:07~15:07 | 14:06~15:06 | 1분 |
| 15:59 | 14:59~15:59 | 14:58~15:58 | 1분 |

세 요청 모두 미리 세어 둔 값은 요청이 뜻하는 구간보다 1분 앞에서 끝난 구간의 값입니다. 예를 들어 15:07 요청은 14:07~15:07 을 묻지만 받는 값은 15:06 에 끝난 14:06~15:06 의 값이라 1분 묵었습니다.

그래서 첫 결정은 「광고 서버는 세지 않고 읽기만 한다」입니다. 대신 읽는 값이 몇 분 묵었는지는 우리가 정합니다. 그 값을 누가 세어 어디에 놓아 두는지가 다음 절의 내용입니다.

## 2. 클릭 한 건이 값이 되기까지 지나는 세 곳

**클릭은 topic `ad.click` 에 쌓입니다. 스트림 잡 `ad_click_1h` 가 그 클릭을 읽어 광고마다 센 값을 Redis 키 `ad:9931:clk_1h` 에 써 두면 광고 서버는 그 키를 읽기만 합니다.**

1절에서 값을 미리 세어 놓아 두기로 했으니 이제 누가 세고 어디에 놓을지를 정해야 합니다. 클릭이 지나는 곳은 쌓이는 곳, 세는 곳, 놓아 두는 곳의 세 곳이고 곳마다 이름이 하나씩 붙어 있습니다. 실시간 피처에서 생기는 일은 거의 다 이 세 곳 사이에서 일어납니다.

첫째 곳은 Kafka 입니다. Kafka 는 들어온 메시지를 한 줄씩 쌓아 두고 여러 프로그램이 각자 읽어 가게 하는 시스템으로, 같은 종류의 메시지를 topic 이라는 단위로 모아 둡니다. 앞 트랙에서 지훈 씨가 만든 클릭 수집 API 가 받은 클릭은 topic `ad.click` 에 놓입니다. topic 안은 partition 12개로 나뉘어 있고 partition 마다 줄이 따로 쌓이고 따로 읽힙니다. 줄이 어느 partition 에 들어갈지는 줄마다 붙은 key 가 정하는데, 같은 key 를 가진 줄은 늘 같은 partition 에 놓입니다. `ad.click` 의 key 는 요청 번호인 `req_id` 입니다.

잡이 읽는 줄 하나는 아래처럼 생겼습니다. 광고 9931 의 클릭 한 건이 partition 5 에 key `r-8f21` 로 놓여 있고 value 에는 광고 번호 `ad_id` 와 클릭이 일어난 시각 `event_time` 이 들어 있습니다.

```text
topic     ad.click
partition 5
key       r-8f21
value     {"event":"click","ad_id":9931,"req_id":"r-8f21","event_time":"2026-09-30T14:59:31.204+09:00"}
```

이 줄의 key `r-8f21` 은 광고 번호가 아니라 요청 번호입니다. 그래서 광고 9931 의 다른 클릭은 다른 요청 번호를 달고 다른 partition 에 놓일 수 있습니다.

둘째 곳은 Flink(흘러오는 데이터를 실시간으로 처리하는 도구)로 만든 스트림 잡 `ad_click_1h`(광고별 최근 1시간 클릭 수를 세는 잡)입니다. 잡은 partition 12개를 나눠 읽는데 여기서 단계를 하나 더 거쳐야 합니다. key 가 `req_id` 라서 같은 광고의 클릭이 12개 partition 에 흩어져 있으므로 광고마다 세려면 잡 안에서 클릭을 `ad_id` 기준으로 다시 모아야 합니다. 이렇게 다시 모으는 단계를 셔플(shuffle)이라고 부르며 셔플 때 클릭이 네트워크를 한 번 더 오갑니다. topic 의 key 를 무엇으로 정했느냐가 이렇게 세는 단계의 네트워크 비용에까지 영향을 줍니다.

셋째 곳은 키마다 값을 메모리에 두어 빠르게 읽고 쓰는 저장소인 Redis 입니다. 잡은 1분에 한 번 광고마다 값을 쓰는데 광고 9931 의 최근 1시간 클릭 수가 들어가는 키는 `ad:9931:clk_1h` 이고 TTL 은 2분입니다. TTL(Time-To-Live)은 키가 쓰인 뒤 저절로 지워지기까지의 시간이라, 2분 안에 새 값이 써지지 않으면 키가 사라집니다.

아래 네 줄에서 `SET` 은 잡이 값 1,203 을 쓰는 명령이고 `GET` 은 광고 서버가 그 값을 읽는 명령입니다. `SET` 끝의 `EX 120` 은 이 키를 120초, 곧 2분 뒤에 지우라는 옵션이라 TTL 2분이 이 자리에서 붙습니다. 광고 서버가 하는 일은 `GET` 으로 키를 읽는 것뿐입니다.

```text
> SET ad:9931:clk_1h 1203 EX 120
OK
> GET ad:9931:clk_1h
"1203"
```

TTL 을 2분으로 둔 데는 까닭이 있습니다. 값은 1분마다 새로 써지므로 2분이 지나도록 새로 써지지 않았다면 잡이 멈췄거나 밀린 상태입니다. TTL 이 없으면 잡이 멈춰도 마지막 값이 Redis 에 그대로 남아 광고 서버는 몇 시간 전 값을 아무 의심 없이 계속 읽습니다. 그러면 광고 서버는 잡이 죽은 줄도 모른 채 그 옛 숫자로 입찰합니다. TTL 이 2분이면 새 값이 2분 동안 들어오지 않을 때 키가 지워지고 광고 서버는 값이 없을 때 쓰기로 정해 둔 기본값으로 넘어가므로 옛 숫자로 입찰하지 않습니다. [피처 스토어](post.html?id=feature-store-serving) 편의 「광고 최근 1시간 CTR」(클릭률)도 같은 곳에서 같은 방식으로 갱신됩니다.

결정은 세 가지로, 클릭은 topic 에 쌓고 세는 일은 잡이 맡으며 값은 Redis 에 놓아 광고 서버가 읽기만 하게 합니다. 남은 일은 잡이 무엇을 기준으로 시간을 자르느냐입니다. 자르는 방법은 두 가지가 있습니다.

## 3. 윈도우를 자르는 두 방법, 텀블링과 슬라이딩

**텀블링 윈도우는 시간을 정각마다 잘라 겹치지 않게 이어 붙이고 슬라이딩 윈도우는 같은 길이의 윈도우를 1분씩 밀어 겹치게 둡니다. 그래서 15:07 요청에 텀블링은 14:00~15:00 값을 주고 슬라이딩은 14:06~15:06 값을 줍니다.**

1절에서 「최근 1시간」은 묻는 시각마다 앞뒤가 밀린다고 했는데, 잡이 윈도우를 어떻게 자르느냐에 따라 광고 서버가 받는 값의 구간이 요청이 묻는 구간에 얼마나 가까운지가 정해집니다.

텀블링(tumbling) 1시간 윈도우는 만들기 쉽습니다. 잡은 광고마다 숫자 하나만 들고 있다가 정각이 되면 그 값을 내놓고 0 으로 되돌리면 됩니다. 대신 값이 정각에만 새로 나오므로 15:07 요청도 15:59 요청도 같은 14:00~15:00 값을 읽습니다. 15:59 요청이 읽는 값은 윈도우가 끝난 15:00 에서 59분이 지난 값입니다. 요청 시각이 정각에 가까우면 값이 신선하고 정각에서 멀어질수록 묵어서 값이 묵은 시간이 0분에서 59분까지 오르내리므로, 텀블링 1시간 윈도우의 값은 「최근 1시간」이라고 부르기 어렵습니다.

슬라이딩(sliding) 60분 윈도우를 1분마다 내면 값이 1분마다 새로 나오므로 어느 시각에 물어도 늘 1분 안의 값을 받습니다. 잡은 1분짜리 조각(그 1분 동안 들어온 클릭 수) 60개를 들고 있다가 60개를 더해 값을 냅니다. 1분이 지나면 가장 오래된 조각을 버리고 새 조각을 하나 붙인 뒤 다시 60개를 더하므로, 15:07 요청이 받는 14:06~15:06 값은 14:06 부터 15:06 까지의 조각 60개를 더한 값입니다.

카드 속 색은 4가지로, 파랑은 놓여 있는 데이터(topic, Redis 값, 아카이브), 벽돌색은 지금 오는 것(클릭), 먹색은 서버, 회색은 만드는 작업(윈도우 집계, 배치)입니다. 점선 상자는 윈도우 설정이나 워터마크처럼 적어 둔 값을 나타냅니다. 아카이브는 지난 클릭 로그를 쌓아 두는 저장소로 7절에서 다시 나옵니다. 첫 카드에서는 같은 15:07 요청에 텀블링 윈도우와 슬라이딩 윈도우가 각각 어느 구간의 값을 주는지 보면 됩니다.

값을 1분마다 새로 내는 대신 잡이 들고 있어야 할 숫자가 늘어나는데, 얼마나 늘어나는지 세어 보면 어느 윈도우를 고를지 정하기 쉬워집니다. 가정은 두 가지로, 이 자리에 뜨려는 광고가 12만 개이고 조각 하나가 4바이트 숫자 하나라고 둡니다. 필요한 메모리는 광고 수 × 광고 하나가 드는 숫자 × 4바이트이므로 텀블링은 12만 × 1 × 4바이트 = 480KB, 슬라이딩은 12만 × 60 × 4바이트 = 28.8MB 입니다.

| 윈도우 종류 | 광고 하나가 드는 숫자 | 광고 12만 개 | 값이 묵는 시간 |
|---|---|---|---|
| 텀블링 1시간 | 1개 | 480KB | 0분에서 59분 |
| 슬라이딩 60분, 1분마다 | 60개 | 28.8MB | 늘 1분 안 |

표의 마지막 열을 보면 텀블링은 값이 묵는 시간이 0분에서 59분까지 오르내리고 슬라이딩은 늘 1분 안입니다. 28.8MB 는 잡 하나가 들고 있기에 작은 크기라서 이만큼의 메모리를 들여 값을 늘 1분 안으로 받는 편이 이득입니다. 그래서 이 잡은 슬라이딩 60분 윈도우를 1분마다 내기로 정했습니다.

다만 지금까지는 윈도우가 끝나자마자 닫힌다고 보고 계산했는데 실제로는 그렇지 않습니다. 15:00 에 14:00~15:00 윈도우를 바로 닫으면 그 윈도우에 들어가야 할 클릭 가운데 아직 도착하지 않은 클릭이 남습니다. 클릭이 왜 늦게 도착하는지는 다음 절에서 봅니다.

## 4. 클릭에 붙는 두 시각, 일어난 시각과 도착한 시각

**클릭에는 일어난 시각과 잡에 도착한 시각이 따로 있고 두 시각 사이의 간격은 클릭마다 다릅니다. 하루 클릭의 95% 는 5초 안에 도착하지만 0.1% 는 2분 넘게 걸리고 그 0.1% 가운데 5분의 1인 0.02% 는 30분 넘게 걸립니다.**

3절 끝에서 본 대로 윈도우를 끝나자마자 닫으면 아직 도착하지 않은 클릭이 빠집니다. 클릭은 눌린 그 순간에 잡에 도착하지 않고 대부분은 몇 초 안에, 일부는 한참 뒤에 도착하므로 잡이 15:00 에 보고 있는 클릭은 15:00 까지 일어난 클릭 전부가 아닙니다.

클릭이 늦게 도착하는 첫 까닭은 거치는 단계가 여러 개라는 데 있습니다. 앞 트랙에서 클릭 한 건이 화면에서 눌린 뒤 Kafka 에 놓이기까지 1,112밀리초가 걸렸는데, 그 경로가 그대로 이 잡까지 이어집니다. 앱이 클릭을 모아 보내면 수집 서버가 받아 로그로 쓰고 그 로그가 Kafka 로 옮겨진 뒤 잡이 읽으므로 단계마다 시간이 조금씩 붙습니다.

늦는 까닭이 단계가 많아서만은 아닙니다. 폰이 지하철에서 신호를 잃으면 앱은 그동안 눌린 클릭을 기기에 쌓아 두었다가 신호가 돌아온 뒤에 보냅니다. 앱이 백그라운드로 내려가면 보내던 클릭이 그 자리에서 멈춥니다. 수집 서버를 배포하느라 서버가 몇 초 멈추면 그사이에 들어온 클릭이 뒤로 밀립니다. 세 경우 모두 드물지만 없어지지는 않습니다.

그래서 클릭 한 건에는 시각이 두 개 붙습니다. 일어난 시각(이벤트 시각, event time)은 클릭이 눌린 순간으로 폰이 찍어 `event_time` 에 담습니다. 도착한 시각(처리 시각, processing time)은 잡이 그 줄을 읽은 순간입니다. 「최근 1시간 클릭 수」는 일어난 시각을 기준으로 셉니다. 도착한 시각을 기준으로 삼으면 지하철에서 나온 사람이 30분 전에 누른 클릭이 방금 일어난 클릭처럼 세어집니다.

도착 지연(일어난 시각부터 도착한 시각까지 걸린 시간)을 하루치 모아 구간으로 나누면 아래 표와 같습니다. 하루 클릭 228만 건이 이 분포를 따른다고 가정했으므로 표의 건수는 228만에 구간의 비율을 곱한 값입니다.

| 도착까지 걸린 시간 | 비율 | 하루 클릭 228만 건 중 |
|---|---|---|
| 5초 안 | 95% | 216만 6,000건 |
| 5초에서 2분 | 4.9% | 11만 1,720건 |
| 2분에서 10분 | 0.06% | 1,368건 |
| 10분에서 30분 | 0.02% | 456건 |
| 30분 넘음 | 0.02% | 456건 |

예를 들어 5초 안에 도착하는 95% 는 228만 × 95% = 216만 6,000건입니다. 표에서 2분이 넘게 걸리는 아래 세 행을 더하면 1,368 + 456 + 456 = 2,280건으로 하루 클릭의 0.1% 입니다. 이 글의 나머지 절은 이 2,280건에서 생기는 문제를 다룹니다.

2분 넘게 걸린 클릭 한 건이 어떤 문제를 만드는지 보겠습니다. 14:59:31 에 일어난 클릭이 15:03:10 에 도착했다면 잡은 15:03 에야 그 줄을 보지만 일어난 시각으로는 14:00~15:00 윈도우에 들어가야 할 클릭입니다. 그 윈도우가 이미 닫혔다면 잡은 이 클릭을 넣을 곳이 없습니다.

그래서 이 잡은 일어난 시각을 기준으로 세기로 정합니다. 그러면 곧바로 다음 물음이 생깁니다. 일어난 시각으로 세려면 윈도우가 끝난 뒤 얼마나 기다렸다가 닫아야 할까요?

## 5. 윈도우를 닫는 시각을 정하는 워터마크

**워터마크는 윈도우가 끝난 뒤 얼마나 더 기다렸다가 닫을지를 정하는 값입니다. 워터마크가 2분이면 14:00~15:00 윈도우는 15:02 에 닫히고 그때까지 도착하지 않은 클릭은 그 윈도우에 들어가지 못합니다.**

일어난 시각으로 세기로 했으니 잡은 윈도우가 끝난 뒤에도 늦게 오는 클릭을 얼마간 기다려야 합니다. 짧게 기다리면 잃는 클릭이 늘고 길게 기다리면 값이 늦게 나와 그만큼 묵으므로, 얼마나 기다릴지를 숫자 하나로 정해야 합니다.

잡이 시간을 어떻게 아는지부터 보겠습니다. 잡은 벽시계 시간(서버의 시계)을 보지 않고 지금까지 읽은 클릭의 `event_time` 가운데 가장 늦은 시각에서 2분을 뺀 시각을 「여기까지 일어난 클릭은 다 봤다고 치자」는 기준으로 삼습니다. 이 기준 시각이 워터마크(watermark)입니다. 이 글에서 「워터마크 2분」이라고 하면 워터마크를 가장 늦은 `event_time` 보다 2분 이른 시각에 두는 설정을 가리킵니다.

예를 들어 15:02 에 도착한 클릭 가운데 `event_time` 이 15:02:00 인 클릭이 있으면 가장 늦은 `event_time` 이 15:02:00 이므로 워터마크는 15:02:00 에서 2분을 뺀 15:00 입니다. 워터마크가 15:00 을 넘는 순간 잡은 15:00 까지 일어난 클릭이 다 왔다고 보고 14:00~15:00 윈도우를 닫아 값을 내놓습니다. 그래서 워터마크가 2분이면 윈도우는 끝나고 2분 뒤인 15:02 에 닫힙니다. 두 번째 카드에서는 워터마크가 2분일 때 윈도우가 닫히는 시각과 하루에 빠지는 클릭 수를 보면 됩니다.

워터마크로 윈도우를 닫으면 잡이 밀려도 값이 틀리지 않습니다. 잡이 5분 밀리면 잡이 읽는 클릭의 `event_time` 도 5분 늦게 올라가므로 워터마크 역시 5분 늦게 올라갑니다. 그러면 윈도우가 그만큼 늦게 닫혀 값도 늦게 나오지만 윈도우에 들어가는 클릭은 밀리지 않았을 때와 같습니다. 벽시계 시간으로 닫았다면 잡이 밀려 있던 5분 동안 도착한 클릭은 모두 윈도우에서 빠집니다.

워터마크 2분은 4절의 표에서 정했습니다. 도착 지연이 2분 안인 클릭이 99.9% 라서 2분을 기다리면 나머지 0.1% 만 윈도우가 닫힌 뒤에 옵니다. 워터마크를 늘리면 잃는 클릭은 줄지만 값이 그만큼 늦게 나와 묵습니다.

워터마크를 몇 분으로 두느냐에 따라 하루에 몇 건을 잃는지 보려고 아래 코드를 돌립니다. 코드는 4절 표와 같은 분포에서 2분을 넘는 0.1% 가 2~10분, 10~30분, 30분~2시간에 6:2:2 로, 구간 안에서는 고르게 퍼져 있다고 두고 도착 지연을 하루 클릭 수인 228만 개만큼 뽑아 지연이 워터마크보다 긴 클릭을 셉니다. 뽑을 때는 시드를 고정하는데, 시드 고정은 난수를 만드는 시작값을 정해 두어 몇 번을 돌려도 같은 값이 나오게 하는 방법입니다. 같은 값을 분포의 식으로도 계산해 「뽑아서 센 것」과 「식으로 계산」 두 열에 나란히 찍습니다.

```python
# 하는 일: 워터마크 값마다 하루 클릭 가운데 몇 건이 윈도우에서 빠지는지, 도착 지연을 뽑아 센 값을 식으로 구한 값과 비교한다.
import random

# 1단계: 도착 지연 분포를 둔다
# 분포는 4절 표와 같은 가상 값이다. 5초 안 95%, 2분 안 99.9%, 2분 넘음 0.1% 다.
N_DAY = 2_280_000                 # 하루 클릭 (엔지니어링 트랙의 값)
P_LATE = 0.001                    # 2분 넘게 늦는 비율

base = (1 - P_LATE) / 0.999       # 2분 안에 오는 99.9% 를 두 구간에 나눈다

# 2분을 넘는 0.1% 는 2~10분, 10~30분, 30분~2시간에 6:2:2 로 퍼져 있다고 둔다.
GROUPS = [                        # (몫, 지연 시작 초, 지연 끝 초). 구간 안은 고르게 퍼져 있다고 본다
    (0.95 * base, 0, 5), (0.049 * base, 5, 120),
    (P_LATE * 0.6, 120, 600), (P_LATE * 0.2, 600, 1800), (P_LATE * 0.2, 1800, 7200),
]

# 2단계: 늦을 확률을 구하는 식과 지연을 뽑는 함수를 만든다
def p_later(sec):
    """도착 지연이 sec 를 넘을 확률 — 구간마다 넘는 쪽 몫을 더한다."""
    total = 0.0
    for share, lo, hi in GROUPS:
        if sec <= lo:
            total += share
        elif sec < hi:
            total += share * (hi - sec) / (hi - lo)
    return total

def sample_delay(rnd):
    """구간 하나를 몫대로 고르고 그 안에서 고르게 하나 뽑는다 (초)."""
    u = rnd.random()
    for share, lo, hi in GROUPS:
        if u < share:
            return lo + rnd.random() * (hi - lo)
        u -= share
    return 7200.0

# 3단계: 하루치 지연을 뽑아 워터마크마다 센다
# 시드를 고정해 도착 지연을 하루 클릭 수만큼 뽑는다.
rnd = random.Random(20260930)                        # 시드 고정 — 몇 번을 돌려도 같은 값
delays = [sample_delay(rnd) for _ in range(N_DAY)]

print("워터마크   뽑아서 센 것    식으로 계산     하루 클릭 중")
for minute in (0.5, 1, 2, 5, 10, 30):
    drawn = sum(1 for d in delays if d > minute * 60)
    calc = N_DAY * p_later(minute * 60)
    print(f"{minute:>5}분 {drawn:>12,} {round(calc):>13,} {p_later(minute * 60):>15.3%}")

# 4단계: 2분과 10분을 비교한다
gain = round(N_DAY * p_later(120)) - round(N_DAY * p_later(600))
print(f"\n2분에서 10분으로 늘리면 {gain:,}건을 더 건지고 값은 8분 더 묵는다")

# 출력:
# 3단계 뜻: 뽑아서 센 값과 식으로 구한 값이 가깝다. 센 값이 작은 줄일수록 비율로 더 벌어진다. 워터마크 2분이면 하루 2,280건(0.100%)이 빠지고, 1분으로 줄이면 60,569건으로 뛴다.
# 워터마크   뽑아서 센 것    식으로 계산     하루 클릭 중
#   0.5분       89,681        89,713          3.935%
#     1분       60,521        60,569          2.657%
#     2분        2,278         2,280          0.100%
#     5분        1,773         1,767          0.077%
#    10분          880           912          0.040%
#    30분          420           456          0.020%
# 4단계 뜻: 10분으로 늘리면 1,368건을 더 건지는 대신 모든 값이 8분씩 더 묵는다.
#
# 2분에서 10분으로 늘리면 1,368건을 더 건지고 값은 8분 더 묵는다
```

찍힌 표의 「뽑아서 센 것」과 「식으로 계산」은 가깝습니다. 워터마크 2분이면 뽑아서 센 값이 2,278건, 식으로 계산한 값이 2,280건으로 하루 클릭의 0.100% 입니다. 센 값이 작은 줄일수록 두 값의 차이가 비율로는 더 벌어져 30분 줄은 420건과 456건입니다.

표에서는 2분 앞뒤의 낙차가 가장 큽니다. 워터마크를 2분에서 1분으로 줄이면 4절 표에서 5초에서 2분 사이에 오는 4.9% 가운데 1분을 넘겨 오는 절반쯤이 더 잘리므로, 하루에 잃는 클릭(적을수록 좋습니다)이 2,280건에서 6만 569건(하루 클릭의 2.657%)으로 27배 가까이 뜁니다. 반대로 2분에서 10분으로 늘리면 잃는 클릭이 912건으로 줄어 1,368건을 더 건지지만 그 대가로 모든 값이 8분씩 더 늦게 나옵니다. 3절에서 값을 늘 1분 안으로 받으려고 슬라이딩 윈도우를 골랐는데 하루 1,368건을 건지려고 모든 값을 8분씩 늦추면 앞뒤가 맞지 않으므로 워터마크는 2분으로 정합니다.

워터마크의 대가는 텀블링 윈도우에서 더 크게 나타납니다. 15:01 요청이 오면 14:00~15:00 윈도우는 15:02 에야 닫히므로 아직 읽을 수 없고 읽을 수 있는 가장 최근 윈도우는 13:00~14:00 입니다. 그래서 15:01 요청은 윈도우가 끝난 14:00 에서 61분이 지난 값을 받습니다. 「최근 1시간」을 물었는데 두 시간 전 구간의 값이 옵니다. 아래 놀이터에서 윈도우 종류를 텀블링으로 바꾸고 요청 시각을 15:01 로 옮기면 그 장면을 그대로 볼 수 있습니다. 워터마크와 늦는 비율을 움직이면 하루에 빠지는 클릭 수가 어떻게 바뀌는지도 보입니다.

## 6. 늦게 온 클릭을 다루는 세 가지 방법

**윈도우가 닫힌 뒤 도착한 클릭은 버리거나, 따로 적어 두거나, 그 윈도우를 다시 세어 값을 고치는 세 가지 방법 가운데 하나로 다룹니다. 세 방법은 정확도와 비용을 맞바꿉니다.**

5절에서 워터마크를 2분으로 정했으므로 하루 2,280건은 자기 윈도우가 닫힌 뒤에 도착합니다. 잡이 이 클릭들을 어떻게 다루느냐에 따라 값이 얼마나 정확한지와 잡이 치르는 비용이 달라집니다.

늦게 온 클릭 한 건을 따라가 보겠습니다. 회원 A 가 14:59:31 에 광고 9931 을 눌렀고 그 줄은 15:03:10 에 잡에 닿았으므로 도착까지 219초가 걸렸습니다. 14:00~15:00 윈도우는 그보다 앞선 15:02 에 이미 닫혀 값 1,203 이 Redis 에 놓인 뒤였습니다. 그래서 이 줄이 도착한 순간 잡은 세 방법 가운데 하나를 골라야 합니다. 세 번째 카드에서는 윈도우가 닫힌 뒤 도착한 클릭이 세 방법에서 각각 어디로 가는지 보면 됩니다.

첫째 방법인 「버린다」는 잡의 기본 동작입니다. 값은 1,203 그대로이고 드는 비용도 없지만 버렸다는 사실이 어디에도 남지 않아 하루에 몇 건을 버렸는지, 어제보다 늘었는지 줄었는지를 아무도 모릅니다. 그래서 수집 서버가 느려져 도착 지연이 2분에서 5분으로 밀려도 알람이 울리지 않고 값만 조용히 작아집니다.

둘째 방법인 「따로 적어 둔다」는 윈도우가 닫힌 뒤 도착한 클릭을 `ad.click.late` 라는 topic 에 그대로 보냅니다. 늦게 온 클릭은 하루 2,280줄이라 저장 비용은 따질 만한 크기가 아닙니다. 이 topic 을 하루 한 번 세면 어제 몇 건이 늦었는지와 그중 몇 % 가 몇 분 늦게 몰려 왔는지 두 가지를 알 수 있으므로 워터마크 2분을 다시 정할 근거가 여기서 나옵니다. 값 자체는 버릴 때와 같은 1,203 입니다.

셋째 방법인 「다시 센다」는 윈도우를 닫은 뒤에도 30분 더 열어 두었다가 늦게 온 클릭이 오면 그 윈도우의 값을 1,203 에서 1,204 로 고쳐 씁니다. 세 방법 가운데 값이 가장 정확해지는 대신 드는 것이 두 가지로, 잡은 윈도우 상태(그 윈도우를 세려고 메모리에 들고 있는 값)를 30분 더 들고 있어야 하고 같은 윈도우에 값을 두 번 씁니다. 게다가 값을 고치기 전에 읽어 간 요청은 1,203 을 봤으므로 나중에 로그를 맞춰 볼 때 「그때 서버가 본 값」이 무엇이었는지가 흐려집니다.

| 갈래 | 이 윈도우의 값 | 드는 것 | 언제 고르나 |
|---|---|---|---|
| 버린다 | 1,203 | 없음 | 서빙 피처의 기본 |
| 따로 적어 둔다 | 1,203 | topic 하나, 하루 2,280줄 | 늘 함께 켠다 |
| 다시 센다 | 1,204 | 윈도우 상태 30분, 값 두 번 쓰기 | 숫자가 맞아야 하는 정산 |

표의 마지막 열에 적은 대로 「다시 센다」는 정산(광고비를 계산해 주고받는 일)처럼 숫자가 맞아야 하는 곳에서 고릅니다. 모델이 쓰는 피처에서 1,203 과 1,204 의 차이인 0.08% 를 더 맞히려고 값을 두 번 쓰기보다 얼마나 버렸는지를 매일 아는 편이 나으므로, 이 잡은 늦게 온 클릭을 버리고 따로 적어 두기로 합니다. 다만 학습 데이터는 하루 뒤에 늦게 온 클릭까지 다 모아 세므로 사정이 다릅니다.

## 7. 스트림 값과 배치 값의 차이

**광고 9931 의 같은 14:00~15:00 을 스트림 잡은 15:02 까지 도착한 클릭만 세어 1,203 으로 내고 하루 뒤 배치는 늦게 온 클릭까지 모두 세어 1,204 로 냅니다. 학습 데이터를 배치 값으로 다시 만들면 모델은 서빙 때 보지 못하는 값을 배웁니다.**

6절에서 서빙에 쓰는 값은 늦게 온 클릭을 버린 1,203 으로 정했지만 같은 피처를 학습에 쓰려면 학습 데이터를 만들 때 그 시각의 값을 다시 만들어야 합니다. Redis 의 값은 TTL 2분이 지나면 지워져 남아 있지 않으므로 학습 데이터를 만들 때는 아카이브에 쌓인 클릭 로그를 다시 읽어 같은 윈도우로 셉니다. 이 배치는 다음 날 새벽에 도는데 그때는 늦게 온 클릭까지 전부 아카이브에 들어와 있어서 배치는 1,204 를 셉니다. 네 번째 카드에서는 같은 14:00~15:00 을 스트림과 배치가 각각 몇으로 세는지, 서빙과 학습이 어느 값을 쓰는지 보면 됩니다.

다만 모든 시간에 스트림 값이 한 건씩 모자라지는 않습니다. 광고 9931 은 한 시간에 클릭이 1,204건이고 그 0.1% 인 평균 1.2건이 2분보다 늦게 옵니다. 그런데 윈도우 앞쪽에서 일어난 클릭은 한참 늦게 와도 윈도우가 닫히는 15:02 전에 도착하므로, 스트림 값이 하나 모자라는 시간은 늦게 온 클릭이 윈도우 끝 가까이에서 일어난 시간뿐입니다. 5절의 놀이터에서 「클릭 다시 뽑기」를 여러 번 눌러 보면 한 건도 빠지지 않는 뽑기가 빠지는 뽑기보다 많습니다.

스트림 1,203, 배치 1,204 의 한 건 차이는 1,204 의 0.08% 라 크기만 보면 무시할 만하지만 문제는 차이의 방향입니다. 배치는 스트림 잡이 센 클릭에 늦게 온 클릭까지 더해 세므로 배치 값은 스트림 값보다 늘 크거나 같고 절대 작지 않습니다. 이렇게 한쪽으로만 틀리는 차이는 모델이 그대로 배웁니다. 모델은 학습에서 이 피처가 1,204 일 때 클릭률이 얼마였는지를 배웠는데 서빙 때 같은 상황에서 받는 값은 1,203 입니다. 학습에 쓴 값과 서빙 때 본 값이 이렇게 다른 문제를 학습과 서빙의 불일치(training-serving skew)라고 부릅니다.

차이는 광고마다 고르게 나지도 않습니다. 늦게 오는 클릭은 신호가 나쁜 지면(광고가 나가는 화면 자리)과 앱이 오래 백그라운드에 있는 기기에 몰리므로 그런 지면의 광고일수록 스트림 값이 배치 값보다 더 많이 모자랍니다. 그리고 모델이 가장 많이 틀리는 광고가 하필 그런 지면의 광고들입니다. 한쪽으로만 틀리는 이 모양은 [피처 스토어](post.html?id=feature-store-serving) 편에서 본 것과 같은 종류로, 그 편에서는 배치 피처가 늘 과거 값이라 한쪽으로만 틀렸습니다.

| 무엇 | 세는 것 | 광고 9931 의 14:00~15:00 | 언제 정해지나 |
|---|---|---|---|
| 스트림 값 | 15:02 까지 도착한 클릭 | 1,203 | 15:02 |
| 배치 값 | 아카이브의 그 시간 클릭 전부 | 1,204 | 다음 날 새벽 |
| 서빙이 본 값 | 광고 서버가 그때 읽은 값 | 1,203 | 요청을 받은 그 순간 |

0.08% 는 견딜 수 있는 폭이고 아카이브를 다시 읽는 방식이 30일치 학습 데이터를 한 번에 만들기 편하므로, 지금 이 팀은 배치 값으로 학습하고 스트림 값으로 서빙합니다. 불일치를 0 으로 만드는 방법도 있습니다. 광고 서버가 그때 읽은 값을 요청 로그에 같이 적어 두었다가 학습 때 그 값을 그대로 쓰면 학습과 서빙이 같은 값을 봅니다. 대신 요청마다 숫자가 하나씩 더 붙는데 요청 로그는 하루 2억 2,800만 줄이라 그 숫자 하나가 곧 저장 비용으로 이어집니다.

그래서 지금은 배치 값으로 학습하면서 불일치를 매일 측정하기로 정합니다. 차이가 0.08% 를 넘어 커지면 그때 서빙이 본 값을 로그로 남기는 방식으로 옮깁니다. 이 결정은 클릭이 우리 서버로 바로 온다는 전제에서 성립하므로 클릭이 오는 경로가 다른 무대(광고가 나가는 시장의 형태)에서는 전제부터 흔들립니다.

## 8. 담장 안과 열린 RTB 에서 클릭이 오는 경로

**워터마크 2분은 클릭이 우리 수집 API 로 바로 온다는 전제로 정한 값이라, 클릭이 남의 서버를 거쳐 오는 무대에서는 2분을 기다려도 99.9% 를 받지 못합니다.**

도착 지연이 얼마나 되느냐는 클릭이 몇 회사의 서버를 거쳐 오느냐에 달려 있습니다. 거치는 회사가 늘수록 클릭이 늦게 도착하므로 워터마크도 그만큼 늘려야 합니다.

### 수집 API 로 바로 오는 담장 안의 클릭 [무대: 닫힌 생태계]

한 회사가 앱과 광고 서버를 다 가진 담장 안에서는 클릭이 그 회사의 수집 API 로 바로 옵니다. 사이에 끼는 다른 회사가 없으니 클릭이 늦는 까닭은 기기와 네트워크뿐이라 4절의 분포처럼 2분 안에 99.9% 가 도착합니다. 이 글의 시각표는 담장 안에서 성립합니다.

담장 안에서 할 수 있는 일이 하나 더 있습니다. 클릭에 회원 ID 가 붙어 오므로 광고별 윈도우만이 아니라 「이 회원이 최근 5분에 누른 광고 수」 같은 사람별 윈도우도 만들 수 있습니다. 이 값은 같은 사람에게 같은 광고를 거듭 보이지 않게 막는 빈도 제한(frequency capping)에 바로 쓰입니다.

### 남의 서버를 거쳐 오는 열린 RTB 의 클릭 [무대: 열린 RTB]

매체(광고가 나가는 앱이나 사이트)와 광고 서버가 서로 다른 회사인 열린 RTB(real-time bidding, 광고 자리를 실시간 경매로 사고파는 시장)에서는 클릭이 매체 서버와 중개 회사를 차례로 지나 옵니다. 회사마다 자기 배치 주기가 있어서 클릭을 몇 분씩 모아 보내는 곳도 있습니다. 이 무대에서는 도착 지연이 분 단위가 아니라 시간 단위가 되는 일도 흔하므로 워터마크를 2분으로 두면 윈도우가 닫히기 전에 도착하는 클릭이 99.9% 보다 훨씬 적습니다.

그래서 이 무대에서는 실시간 피처의 재료를 바꿔 남을 거쳐 오는 클릭 대신 우리 서버가 직접 보는 것으로 피처를 만듭니다. 우리가 받은 입찰 요청 수, 우리가 낸 응답, 우리가 경매에서 이긴 횟수 같은 값이며 이 값들은 우리 서버 안에서 생기므로 도착 지연이 밀리초 단위입니다. 낙찰가(경매에서 이긴 입찰자가 내는 가격)처럼 아예 알려 주지 않는 값도 있는데 그 이야기는 [Bid Shading](post.html?id=bid-shading-censored) 편에 있습니다.

전환(클릭 뒤 구매처럼 광고주가 바라는 행동)은 클릭보다 더 늦게 옵니다. 광고주 서버에서 며칠 뒤에 오는 일도 흔해서 실시간 전환 피처는 사실상 만들 수 없습니다. 전환을 얼마나 기다려야 하는지와 기다리는 동안 무엇을 하는지는 [Online Learning 과 지연 피드백](post.html?id=online-learning-delayed-feedback) 편에서 다룹니다.

지훈 씨는 요청서에 「슬라이딩 60분 윈도우를 1분마다」, 「워터마크 2분」, 「늦게 온 클릭은 버리고 따로 적어 둠」 세 줄을 적어 돌려보냈습니다. 다음 주에는 반대 방향의 일이 옵니다. 요청이 올 때마다 계산하지 않고 새벽에 미리 계산해 두는 값이 있는데, 무엇을 미리 계산하고 무엇을 요청이 올 때 계산할지 정하는 일이 [배치 추론과 실시간 추론](post.html?id=batch-vs-realtime-inference) 편의 이야기입니다.

|---|---|---|
| 쌓는 곳 | 클릭이 어디에 놓이나 | topic `ad.click`, partition 12, key `req_id` |
| 세는 곳 | 어느 잡이 세나 | Flink 잡 `ad_click_1h`, `ad_id` 로 다시 모음 |
| 놓는 곳 | 값이 어디에 놓이나 | Redis `ad:9931:clk_1h`, TTL 2분 |
| 윈도우 종류 | 어떻게 자르나 | 슬라이딩 60분, 1분마다. 광고 12만 개에 28.8MB |
| 워터마크 | 언제 닫나 | 2분. 14:00~15:00 윈도우는 15:02 에 닫힘 |
| 잃는 클릭 | 몇 건이 빠지나 | 하루 2,280건, 클릭의 0.1% |
| 늦게 온 클릭 | 어디로 보내나 | 버리고 `ad.click.late` 에 적어 둠 |
| 스트림과 배치 | 얼마나 다른가 | 1,203 대 1,204, 0.08%. 배치가 늘 크거나 같음 |

## 헷갈리기 쉬운 점

- **텀블링 1시간 윈도우의 값은 「최근 1시간」이 아닙니다.** 텀블링은 정각에만 값을 내므로 15:59 요청도 14:00~15:00 의 값을 받습니다. 워터마크 2분까지 생각하면 15:01 요청은 아직 닫히지 않은 14:00~15:00 대신 13:00~14:00 의 값을 받아 61분 묵은 값을 씁니다. 「최근」이라는 뜻을 지키려면 슬라이딩 윈도우처럼 윈도우를 1분마다 내야 합니다.
- **워터마크는 벽시계 시간이 아닙니다.** 잡은 서버 시계를 보고 윈도우를 닫지 않고 지금까지 읽은 클릭의 일어난 시각 가운데 가장 늦은 시각에서 2분을 뺀 워터마크로 닫으므로, 잡이 5분 밀려도 윈도우에 들어가는 클릭은 달라지지 않습니다.
- **하루 2,280건은 한 윈도우에서 빠지는 수가 아닙니다.** 늦게 온 클릭마다 놓치는 윈도우가 다르므로 광고 9931 의 14:00~15:00 윈도우에서 빠진 클릭은 2,280건 가운데 한 건이고 나머지는 다른 시간, 다른 광고의 윈도우에서 빠집니다.
- **윈도우 끝 가까이에서 일어난 클릭일수록 잘 빠집니다.** 14:00~15:00 윈도우는 15:02 에 닫히므로 14:05 에 일어난 클릭은 도착이 57분 늦어도 15:02 전에 들어오지만 14:59 에 일어난 클릭은 3분만 늦어도 윈도우를 놓칩니다. 같은 지연이라도 윈도우 안 어디에서 일어났느냐에 따라 결과가 다릅니다.
- **노출과 클릭 사이의 간격은 도착 지연과 다릅니다.** [Kafka 기초](post.html?id=kafka-log-pipeline) 편의 3시간 윈도우는 광고가 노출(화면에 보인 것)된 뒤 사용자가 언제 누르는지를 기다리는 시간입니다. 이 글의 2분은 클릭이 눌린 뒤 그 줄이 잡에 닿기까지 걸린 시간입니다.
