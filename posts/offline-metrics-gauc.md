지훈이 월요일 아침에 새 클릭 예측 모델의 배포 승인을 올렸다. 이 모델이 값을 매기는 광고 물량은 하루 ₩8억어치다. 배포 전 평가에서 점수가 0.7412 에서 0.7434 로 올랐고, 팀은 이 정도면 태워도 되겠다고 봤다.

A/B 를 7일 돌린 결과는 매출 +0.1% 였다. 참값이 들어 있을 만한 범위는 -0.4% 에서 +0.6% 였고, 그 범위가 0 을 품고 있었다. 아무 일도 일어나지 않았다는 뜻이다.

**점수는 분명히 올랐는데 돈은 왜 안 움직였을까?** 보통은 A/B 설계를 의심하거나, 모델이 실제로는 나빠졌다고 본다. 그런데 세 번째 답이 있다. 점수가 지훈이 바꾼 것을 재고 있지 않았던 것이다.

배포 전에 보는 이런 점수를 오프라인 지표라고 부른다. 이 글은 그 점수 넷이 각각 무엇에 반응하는지 손으로 세어 가르고, 어느 점수를 승인 기준에 걸지까지 간다. 잘못 고르면 매출을 못 올릴 모델에 몇 주를 붓고, 정작 돈이 되는 모델은 중단시킨다.

> **한 줄 요약:** 순위 점수는 순서만 재고, 그것도 요청을 다 섞어서 잰다. 경매가 실제로 쓰는 것은 한 요청 안의 순서와 확률의 크기 두 가지다.

**무대 표시** — `열린 RTB` 는 남의 거래소에 입찰만 넣는 자리, `닫힌 생태계` 는 우리가 경매를 직접 돌리는 자리, `공통` 은 둘 다라는 뜻이다. 숫자는 전부 지어낸 값이다.

## 1. 올라간 점수는 하나뿐이었다

**점수 하나만 보면 이긴 배포다. 점수를 다섯으로 늘리면 진 자리가 먼저 보인다.**

승인 자료에 적힌 점수 다섯 개를 다시 적으면 아래 표가 된다. 이름은 뒤에서 붙일 테니 지금은 각 줄이 무엇을 재는지만 보면 된다.

| 무엇을 재는 점수 | 기존 모델 | 새 모델 | 무엇이 달라졌나 |
|---|---|---|---|
| 순서 — 노출을 전부 한 통에 섞어서 | 0.7412 | 0.7434 | 올랐다 |
| 순서 — 같은 요청 안에서만 | 0.6180 | 0.6172 | 오히려 내렸다 |
| 확률의 크기 | 0.9031 | 0.9026 | 사실상 제자리 |
| 예측 총합 대 실제 | 1.012 | 1.043 | 벌어졌다 |
| 매출 (A/B 7일) | 기준 | +0.1% | 안 움직였다 |

올라간 건 첫 줄 하나뿐이다. 둘째 줄은 0.6180 에서 0.6172 로 오히려 내려갔고, 넷째 줄은 1.012 에서 1.043 으로 벌어졌다. 셋째 줄은 소수점 넷째 자리에서만 움직였으니 제자리로 봐야 한다.

승인 회의에서 첫 줄만 띄운 것이 사고의 시작이었다. 지표를 안 만들어서가 아니라 무엇을 먼저 볼지 정해 두지 않아서 생긴 일이다.

다섯 줄을 다 봤다면 결정이 달라졌을까. 달라진다. 둘째 줄이 안 오르고 넷째 줄만 벌어진 배포는 순서는 그대로인데 값만 커진 모델이라, 매출 대신 비용만 늘린다.

## 2. 순위 점수는 짝의 비율이다 — 노출 여덟 건을 손으로 센다

**클릭한 노출과 안 눌린 노출로 짝을 전부 만든다. 클릭한 쪽 예측이 더 높은 짝의 비율이 그 점수다. 확률의 크기는 세지 않는다.**

노출 여덟 건으로 직접 세어 보자. 손으로 셀 수 있게 클릭을 많이 넣은 가상 표본이라, 이 비율로 예산을 잡으면 안 된다.

| 노출 | 예측 클릭률 | 실제 | 이 노출이 지는 짝 |
|---|---|---|---|
| A | 0.082 | 클릭 | 없음 |
| B | 0.061 | 안 눌림 | |
| C | 0.055 | 클릭 | B |
| D | 0.040 | 안 눌림 | |
| E | 0.034 | 안 눌림 | |
| F | 0.028 | 클릭 | B, D, E |
| G | 0.019 | 안 눌림 | |
| H | 0.011 | 안 눌림 | |

클릭이 세 건이고 안 눌린 것이 다섯 건이니 짝은 모두 열다섯 개다. 클릭한 쪽 예측이 더 높은 짝만 세면 열한 개고, 표 오른쪽 칸의 네 개가 지는 짝이다. 열한을 열다섯으로 나눈 0.7333 이 이 점수의 값이다.

이 점수의 이름이 **순위 점수(AUC, Area Under the ROC Curve)** 다. 이름은 곡선 아래 넓이에서 왔지만 계산은 방금 손으로 한 짝 세기와 똑같다.

이제 축을 통째로 늘려 보자. 모든 예측에 3을 곱하면 0.082 는 0.246 이 되고 0.011 은 0.033 이 된다. 그런데 좌우 순서는 한 칸도 안 바뀌고 지는 짝도 그대로 네 개다.

순서를 지키는 변환이라면 이 점수는 아무 반응도 하지 않는다. 광고를 어느 자리에 올릴지는 순서만 있으면 되지만, 얼마를 입찰할지는 확률의 크기가 있어야 정해진다.

그래서 이 점수 하나로 승인을 내면, 예측을 통째로 3배 부풀린 모델도 통과한다. 그 모델은 입찰가를 3배로 올려 예산만 태우고 매출은 그대로 둔다. 승인 기준에 무엇을 더 걸어야 하는지가 다음 두 절이다.

## 3. 한 통에 섞느냐, 요청으로 쪼개느냐

**순위 점수는 서로 다른 요청에서 온 노출끼리도 짝을 짓는다. 경매는 한 요청 안에서만 줄을 세운다. 요청을 가로지른 짝은 잘 맞혀도 경매가 쓰지 않는다.**

그런데 그 점수를 만든 짝을 뜯어보면 사정이 다르다. 짝은 모두 144개인데 같은 요청 안의 짝은 20개뿐이다. 나머지 124개는 메인상단의 클릭과 검색상단의 안 눌린 노출처럼 만날 일이 없는 조합이다.

짝을 같은 요청 안으로 제한한 점수를 **요청 안 순위 점수(GAUC, Group AUC)** 라고 부른다. 요청마다 점수를 따로 잰 다음 하나로 합치고, 여기서 그룹은 요청이지 사용자나 지면이 아니다.

승인 기준에 걸려면 하나의 숫자여야 하니, 이 글은 **짝 수만큼 무게 주기**로 합친다. 요청별로 이긴 짝과 전체 짝을 각각 더한 다음 나누는 방법이고, 위 데이터에서 값은 0.6000 이다. 클릭이 없는 검색상단 두 건은 짝을 못 만들어 빠진다.

빠지는 요청은 생각보다 많다. 자리가 다섯이고 자리마다 눌릴 확률이 2.5% 라면, 한 자리도 안 눌릴 확률은 0.975 를 다섯 번 곱한 값이다. 계산하면 88.1% 이니, 요청 100건 중 88건을 버린 나머지로 배포 결정을 내리는 셈이다.

아래 코드는 앞 절의 여덟 건과 이 절의 여섯 요청을 한 함수로 잰다.

```python
# 규칙은 하나뿐이다 — 클릭한 것 하나와 안 눌린 것 하나를 붙여 비교한다.

def pairs(rows):                 # -> (이긴 짝 수, 전체 짝 수). 두 예측이 같으면 반 개
    pos = [p for p, y in rows if y == 1]
    neg = [p for p, y in rows if y == 0]
    win = sum(1.0 if a > b else 0.5 if a == b else 0.0 for a in pos for b in neg)
    return win, len(pos) * len(neg)

eight = [(0.082, 1), (0.061, 0), (0.055, 1), (0.040, 0),      # 노출 여덟 건
         (0.034, 0), (0.028, 1), (0.019, 0), (0.011, 0)]

win, total = pairs(eight)
print(f"이긴 짝 {win:.0f} / 전체 짝 {total} -> 순위 점수 {win / total:.4f}")

w3, t3 = pairs([(p * 3, y) for p, y in eight])   # 모든 예측에 3을 곱해도
print(f"3배 후 순위 점수 {w3 / t3:.4f} (소수점까지 같다)")

# 요청 여섯 건 x 자리 다섯 = 노출 서른 건. 요청 안에서 예측 내림차순이다.
requests = {
    "메인상단 A": [(3.52, 0), (3.04, 1), (2.60, 1), (2.20, 0), (1.84, 0)],
    "메인상단 B": [(2.88, 1), (2.44, 0), (2.08, 0), (1.76, 1), (1.48, 0)],
    "피드중간 A": [(2.32, 0), (2.00, 0), (1.52, 1), (1.40, 0), (1.16, 0)],
    "피드중간 B": [(1.92, 0), (1.64, 0), (1.44, 1), (1.16, 0), (0.96, 0)],
    "검색상단 A": [(1.56, 0), (1.32, 0), (1.12, 0), (0.92, 0), (0.76, 0)],
    "검색상단 B": [(1.24, 0), (1.04, 0), (0.88, 0), (0.72, 0), (0.60, 0)],
}

flat = [r for rows in requests.values() for r in rows]   # 요청 구분을 지운다
w, t = pairs(flat)
print(f"한 통에 섞어서 = {w:.0f}/{t} = {w / t:.4f}")

gw = gt = 0.0
for name, rows in requests.items():
    w, t = pairs(rows)
    if t == 0:                       # 클릭이 없으면 짝을 하나도 못 만든다
        print(f"  {name}: 클릭 0건 -> 잴 수 없다, 버린다")
        continue
    gw, gt = gw + w, gt + t
    print(f"  {name}: {w:.0f}/{t} = {w / t:.3f}")
print(f"요청 안 순위 점수 = {gw:.0f}/{gt:.0f} = {gw / gt:.4f}")

# 출력:
# 이긴 짝 11 / 전체 짝 15 -> 순위 점수 0.7333
# 3배 후 순위 점수 0.7333 (소수점까지 같다)
# 한 통에 섞어서 = 112/144 = 0.7778
#   메인상단 A: 4/6 = 0.667
#   메인상단 B: 4/6 = 0.667
#   피드중간 A: 2/4 = 0.500
#   피드중간 B: 2/4 = 0.500
#   검색상단 A: 클릭 0건 -> 잴 수 없다, 버린다
#   검색상단 B: 클릭 0건 -> 잴 수 없다, 버린다
# 요청 안 순위 점수 = 12/20 = 0.6000
```

0.7778 과 0.6000 의 간격 0.1778 이 이 절의 결론이다. 그 간격은 모델이 지면과 사용자를 구분할 줄 안다는 사실이 만든 값이지, 한 요청 안에서 광고를 줄 세울 줄 안다는 사실이 만든 값이 아니다.

간격이 크다고 나쁜 모델인 것은 아니다. 다만 섞어 잰 점수가 오른 이유를 모르면 승인 결정을 낼 근거가 없다. 지면 피처를 더 넣어 그 점수를 0.02 올리는 일은 쉽고, 그렇게 올린 점수가 매출을 한 푼도 안 바꾸는 일도 흔하다.

지훈의 배포가 정확히 이 경우였다. 섞어 잰 점수는 0.7412 에서 0.7434 로 올랐는데 요청 안 점수는 0.6180 에서 0.6172 로 내렸고, 매출은 움직이지 않았다.

그래서 승인 기준에는 요청 안 순위 점수를 걸고 섞어 잰 점수는 기록만 남긴다. 다만 순서를 아무리 잘 맞혀도 확률의 크기가 틀리면 입찰가가 통째로 밀리는데, 두 순위 점수 모두 그것을 못 잡는다. 다음 절에서 크기를 재는 자를 따로 만든다.

:::deep 더 깊이 — 합치는 두 방법과 그룹의 정의
합치는 방법은 둘이다. **짝 수만큼 무게 주기**는 요청별 이긴 짝과 전체 짝을 각각 더한 뒤 나누고, **요청마다 같은 무게 주기**는 요청별 점수를 평균한다. 같은 데이터에서 앞의 것은 0.6000, 뒤의 것은 0.5833 이다. 후보가 20개인 요청과 3개인 요청이 같은 무게를 갖는 것이 이상하니 앞의 것을 권한다. 어느 쪽이든 팀 안에서 고정해야 하고, 섞으면 배포 결정이 흔들린다.

그룹을 사용자로 잡는 정의도 쓰인다. 사용자별 리스트가 그룹인 추천 도메인에서 온 것이다. 광고 랭킹에서는 한 사용자가 요청을 수십 번 내고 그때마다 후보가 다르니, 요청으로 잡는 편이 맞는다.
:::

## 4. 확률의 크기를 재는 점수

**정답 쪽에 얼마나 큰 확률을 걸었는지 재는 벌점이 있다. 그 벌점을 지면끼리 그냥 비교하면 클릭률 낮은 지면이 늘 이긴다. 기준 모델의 벌점으로 나눠야 같은 자가 된다.**

노출 한 건마다 벌점을 매기고 평균하는 점수가 있다. 클릭이 일어났으면 예측 확률에, 안 일어났으면 1에서 예측을 뺀 값에 로그를 씌워 부호를 바꾼다. 이름은 **확률 벌점(LogLoss)** 이고 낮을수록 좋다.

| 실제 | 예측 | 벌점 | 읽는 법 |
|---|---|---|---|
| 클릭 | 0.90 | 0.105 | 맞혔고 자신도 있었다 |
| 클릭 | 0.50 | 0.693 | 맞혔지만 반신반의였다 |
| 클릭 | 0.02 | 3.912 | 거의 아니라고 했는데 눌렸다 |
| 안 눌림 | 0.02 | 0.020 | 거의 아니라고 했고 맞았다 |
| 안 눌림 | 0.50 | 0.693 | 반신반의했는데 안 눌렸다 |
| 안 눌림 | 0.90 | 2.303 | 누른다고 했는데 안 눌렸다 |

표의 넷째 줄이 문제의 씨앗이다. 클릭률이 1% 인 지면은 노출 100건 중 99건이 안 눌린 건이라, 그 99건에 0.01 만 답해도 건당 벌점이 0.010 에 그친다.

클릭률이 4% 인 지면은 사정이 다르다. 안 눌린 노출에 0.04 를 답하면 건당 0.041 이고, 큰 벌점을 무는 클릭 쪽 노출도 자주 등장한다. 모델 품질이 똑같아도 평균 벌점이 이렇게 갈린다.

그래서 "검색 모델은 벌점이 0.054 인데 피드 모델은 0.153 이니 피드 팀이 뭘 잘못하나" 같은 물음이 나온다. 두 값은 같은 자로 잰 것이 아니라서, 그 물음으로 예산을 옮기는 결정을 내리면 손해가 난다.

데이터가 갈리면 어디서든 이 일이 생긴다. 안 눌린 노출을 일부러 솎아 내 학습 데이터를 줄이는 것을 **다운샘플링**이라고 하는데, 학습 비용을 아끼려던 이 일이 평가의 자까지 바꾼다.

그러니 나눗셈이 필요하다. 나누는 자로 쓸 기준 모델은 누가 오든 그 데이터의 평균 클릭률을 답하고 피처는 하나도 안 본다. 늘 같은 값만 답하는 이 모델의 벌점을 **기저엔트로피**라고 부른다.

엔트로피는 "결과를 미리 맞히기가 얼마나 어려운가"를 재는 값에 붙는 이름이다. 클릭률이 50% 인 자리는 동전 던지기라 가장 어렵고, 1% 인 자리는 "안 눌린다"고만 답해도 거의 맞으니 훨씬 쉽다. 그러니 이 값은 모델의 실력이 아니라 그 데이터가 원래 갖고 있던 어려움의 크기다.

이 값은 데이터가 정해지면 결정되고 모델이 무엇을 하든 안 움직이니, 나누는 자로 쓸 수 있다. 평균 클릭률이 4.070% 면 0.17016 이고, 0.986% 면 0.05536 이다.

벌점을 기저엔트로피로 나눈 값이 **정규화 엔트로피(NE, Normalized Entropy)** 다. 원래 있던 어려움 가운데 모델이 얼마나 걷어 냈는지를 재고, 1보다 작으면 늘 같은 값만 답하는 모델보다 낫다. 지면 두 곳에서 20만 건씩 뽑으면 아래 값이 나온다.

| 지면 | 평균 클릭률 | 확률 벌점 | 기저엔트로피 | 정규화 엔트로피 |
|---|---|---|---|---|
| 뉴스피드 | 4.070% | 0.15296 | 0.17016 | 0.8989 |
| 검색 | 0.986% | 0.05418 | 0.05536 | 0.9788 |

벌점만 보면 검색이 뉴스피드보다 세 배 가까이 좋다. 나눈 뒤에는 순서가 뒤집힌다. 뉴스피드 모델은 기준보다 10.1% 잘하고 있고, 검색 모델은 2.1% 잘할 뿐이다. 예산을 어디에 더 줄지의 결정도 같이 뒤집힌다.

뒤집히는 이유는 앞에서 본 그대로다. 검색 지면은 클릭률이 낮아서 "거의 안 눌린다"고만 답해도 벌점이 낮게 나온다. 그 낮은 벌점의 상당 부분은 모델이 번 것이 아니라 지면이 원래 쉬웠기 때문에 공짜로 얻은 몫이다. 기저엔트로피로 나누는 순간 그 공짜 몫이 분모에도 똑같이 들어가서 서로 지워진다.

이 점수는 순위 점수와 달리 크기에 반응한다. 뉴스피드 예측에 3을 곱하면 순서는 한 칸도 안 바뀌는데, 정규화 엔트로피는 0.8989 에서 1.2093 이 된다. 이 모델을 쓸 바에는 모든 요청에 4.070% 를 그대로 답하는 편이 낫다는 뜻이다.

피처를 하나도 안 보는 모델에게 졌으니, 1을 넘으면 승인을 취소하고 배포를 중단해야 한다. 같은 3배에서 예측 총합 대 실제도 1.018 에서 0.342 로 떨어진다. 이 값이 비용 청구서에 가장 먼저 나타나는 숫자이고, 다음 절의 주제다.

분자는 확률 벌점 그대로이고, 분모는 라벨 평균 $\bar{y}$ 하나로 결정되는 상수다.

$$\mathrm{NE} = \frac{-\frac{1}{N}\sum_{i=1}^{N}\left[y_i \log p_i + (1-y_i)\log(1-p_i)\right]}{-\left[\bar{y}\log\bar{y} + (1-\bar{y})\log(1-\bar{y})\right]}$$

분모가 상수라 같은 데이터 안에서는 두 점수의 순서가 반드시 같다. 값을 더해 주는 자리는 데이터가 갈릴 때뿐이다. Facebook 의 2014년 광고 예측 논문이 표준으로 쓰면서 업계에 퍼졌다.

안 눌린 노출을 $r$ 배로 줄여 학습했다면 아래 식으로 예측을 원본 스케일에 되돌린 뒤 **원본 분포의 평가 데이터** 위에서 잰다. 순서를 뒤집으면 정규화 엔트로피는 멀쩡한데 예측 총합만 어긋난 채로 승인이 나간다.

$$p_{\mathrm{orig}} = \frac{p}{p + (1-p)/r}$$

```python
import math, random

# 지면 두 곳에서 20만 건씩 뽑았다고 하자. base 는 평균 클릭률,
# spread 가 클수록 예측이 넓게 퍼진다(순서를 잘 가른다). 전부 지어낸 값이다.
rnd = random.Random(20260814)

def sample(n, base, spread):
    out = []
    for _ in range(n):
        z = rnd.gauss(0, 1)
        p = base * math.exp(spread * z - spread * spread / 2)  # 평균이 base 로 남는다
        p = min(p, 0.9)
        out.append((p, 1 if rnd.random() < p else 0))
    return out

def logloss(rows):
    s = 0.0
    for p, y in rows:
        s += -(y * math.log(p) + (1 - y) * math.log(1 - p))
    return s / len(rows)

def entropy(p):                # 늘 같은 값만 답하는 모델의 벌점
    return -(p * math.log(p) + (1 - p) * math.log(1 - p))

feed = sample(200_000, 0.040, 0.9)     # 뉴스피드 — 평균 4%, 잘 가르는 모델
search = sample(200_000, 0.010, 0.5)   # 검색 — 평균 1%, 덜 가르는 모델

for name, rows in (("뉴스피드", feed), ("검색", search)):
    ctr = sum(y for _, y in rows) / len(rows)
    ll, h = logloss(rows), entropy(ctr)
    print(f"{name}: 평균클릭률 {ctr * 100:.3f}%  확률벌점 {ll:.5f}"
          f"  기저엔트로피 {h:.5f}  정규화엔트로피 {ll / h:.4f}")

tripled = [(min(p * 3, 0.999), y) for p, y in feed]   # 1에 닿지 않게 0.999 에서 자른다
ctr = sum(y for _, y in feed) / len(feed)
h = entropy(ctr)
print(f"뉴스피드 3배: 확률벌점 {logloss(tripled):.5f}"
      f"  정규화엔트로피 {logloss(tripled) / h:.4f}")
print(f"뉴스피드 예측총합대실제: {ctr / (sum(p for p, _ in feed) / len(feed)):.3f}"
      f" -> {ctr / (sum(p for p, _ in tripled) / len(tripled)):.3f}")

# 출력:
# 뉴스피드: 평균클릭률 4.070%  확률벌점 0.15296  기저엔트로피 0.17016  정규화엔트로피 0.8989
# 검색: 평균클릭률 0.986%  확률벌점 0.05418  기저엔트로피 0.05536  정규화엔트로피 0.9788
# 뉴스피드 3배: 확률벌점 0.20577  정규화엔트로피 1.2093
# 뉴스피드 예측총합대실제: 1.018 -> 0.342
```

## 5. 예측 총합이 실제와 맞나

**실제 클릭 수를 예측 클릭 수의 합으로 나눈 값이다. 1보다 크면 실제가 더 많았다는 뜻이고, 곧 모델이 낮게 봤다는 뜻이다.**

이 값의 이름은 **예측 대비 실제(COPC, Click Over Predicted Click)** 다. 방향을 반대로 외우기 쉬운데, 분자가 실제고 분모가 예측이니 1보다 크면 분자 쪽이 많았던 것이다. 지훈의 새 모델을 지면별로 쪼개면 아래 표가 된다.

| 지면 | 노출 | 예측 클릭 합 | 실제 클릭 | 예측 대비 실제 |
|---|---|---|---|---|
| 메인상단 | 400,000 | 12,800 | 14,080 | 1.100 |
| 피드중간 | 300,000 | 7,500 | 7,050 | 0.940 |
| 검색상단 | 200,000 | 2,400 | 2,760 | 1.150 |
| 영상앞 | 60,000 | 1,020 | 918 | 0.900 |
| 상세옆 | 40,000 | 480 | 432 | 0.900 |
| **합계** | **1,000,000** | **24,200** | **25,240** | **1.043** |

합계 줄의 1.043 부터 읽자. 실제 클릭이 예측보다 4.3% 많았다는 뜻이고, 뒤집어 보면 예측 총합이 실제보다 4.1% 적다.

지면별로 쪼개면 훨씬 넓게 흩어진다. 검색상단은 1.150 이라 실제가 예측보다 15% 많았고, 영상앞과 상세옆은 0.900 이라 10% 적었다. 전체 1.043 만 보고 승인을 내면 이 흩어짐이 안 보인다.

다만 조심할 것이 있다. **지면 단위로 값이 어긋나도 그것만으로는 요청 안 순서가 안 바뀐다.** 한 요청 안의 다섯 자리는 전부 같은 지면이라, 그 지면의 예측에 같은 수를 곱해도 순서가 그대로다.

매출이 움직이는 것은 광고 단위로 어긋날 때다. 같은 요청 안에서 광고마다 어긋난 정도가 다르면 보정하는 순간 줄이 뒤집힌다.

| 광고 | 예측 클릭률 | 광고별 예측 대비 실제 | 보정 후 | 보정 전 순위 | 보정 후 순위 |
|---|---|---|---|---|---|
| 운동화 | 3.52% | 0.85 | 2.99% | 1 | 2 |
| 노트북 | 3.04% | 1.30 | 3.95% | 2 | 1 |
| 여행 | 2.60% | 1.00 | 2.60% | 3 | 3 |

1등이 운동화에서 노트북으로 바뀐다. 보정 기법과 그때 나는 손해의 계산은 [Calibration](post.html?id=calibration)에 있다.

지킬 것은 셋이다. 전체와 쪼갠 묶음을 늘 같이 보고, 쪼개는 축을 지면뿐 아니라 광고·시간대·기기로도 잡고, 문턱을 미리 정해 두었다가 넘으면 배포를 중단한다.

### 그 오차가 어디를 아프게 하나 [무대: 공통]

**[무대: 열린 RTB]** 입찰가는 예측 확률에 값을 곱해 만든다. 예측이 평균 4.1% 낮으면 입찰가도 그만큼 낮으니 아슬아슬하게 이기던 노출을 진다. 진 건은 낙찰가도 안 보이니 왜 매출이 새는지조차 모른다. 그 구조는 [Bid Shading 과 Censored 데이터](post.html?id=bid-shading-censored)에 있다.

**[무대: 닫힌 생태계]** 경매를 우리가 돌리니 진 건도 다 보이지만, 대신 다른 곳이 아프다. 클릭당 과금 상품과 노출당 과금 상품을 한 줄에 세우려면 1,000회 노출당 기대 매출로 환산해야 한다. 예측이 낮으면 클릭당 과금 물량이 아래로 눌려 앉고, 예산을 하루에 고르게 나눠 쓰는 조절도 같이 어긋난다.

점수 넷을 다 봤으니 남은 일은 승인 기준, 곧 문턱과 결정의 짝을 짜는 것이다.

## 6. 배포 관문에 무엇을 걸까 — 그리고 무엇을 못 거나

**관문은 지표 목록이 아니라 문턱과 결정의 짝이다. 넘으면 무엇을 할지 미리 안 정해 두면 관문이 아니다.**

먼저 어떤 점수로도 못 잡는 것을 짚자. 노출 로그에는 보여 준 광고만 남는다. 요청 하나에 후보가 마흔 개 올라와도 자리는 다섯 개고, 그 다섯을 고른 것은 지금 서빙 중인 옛 모델이다.

하루 노출을 2.28억 건이라고 하자. 자리가 다섯이니 요청은 4,560만 건이고, 후보로 올라온 광고는 18.24억 건이다. 로그에 남는 것은 그중 12.5% 뿐이고, 나머지 87.5% 는 눌렸을지 아무도 모른다.

새 모델의 강점이 "옛 모델이 안 고르던 후보를 잘 고르는 것"이라면 그 강점은 평가에서 안 보인다. 그 후보들이 표본에 아예 없어서, 평가 표본은 중립이 아니라 옛 모델의 취향이 찍힌 표본이 된다.

없앨 방법은 없고 줄이는 방법만 있다. 트래픽 일부를 무작위 노출로 돌려 치우치지 않은 표본을 따로 모으는 것이다. 1% 만 떼어도 하루 228만 건이 쌓이는데, 그 1% 는 당장의 매출을 깎아 사는 비용이다.

그 한계를 알고 나면 관문은 이렇게 짠다. 아래 문턱은 지어낸 값이라 지면과 규모에 따라 다시 잡아야 한다.

| 무엇을 보나 | 문턱 | 넘으면 | 왜 이 자리인가 |
|---|---|---|---|
| 요청 안 순위 점수 | 기존 대비 -0.001 아래 | 배포 중단 | 요청 안 순서가 나빠졌다 |
| 정규화 엔트로피 (기존 대비) | 0.5% 이상 나빠짐 | 배포 중단 | 확률의 크기가 나빠졌다 |
| 정규화 엔트로피 (절댓값) | 1.0 이상 | 즉시 중단 | 늘 같은 값만 답하는 모델보다 못하다 |
| 예측 대비 실제 (전체) | 0.97~1.03 밖 | 배포 중단 | 입찰가와 과금이 밀린다 |
| 예측 대비 실제 (지면별 최악) | 0.90~1.10 밖 | 경고 후 검토 | 한 지면만 무너진다 |
| 예측 평균 | 실제 클릭률 대비 ±3% 밖 | 즉시 중단 | 보정 누락을 잡는다 |
| 섞어서 잰 순위 점수 | 문턱 없음 | 기록만 | 요청을 다 섞어서 잰다 |
| 가장 느린 응답 시간 | 12ms 예산 초과 | 배포 중단 | 늦은 응답은 없던 응답 |

섞어 잰 순위 점수를 목록에서 빼지 않은 이유가 있다. 0.74 에서 0.62 로 갑자기 떨어지면 피처 파이프라인이 깨진 것이라 값 자체는 쓸모가 있다. 다만 작은 개선을 승인하는 자리에는 못 쓰니 기록만 한다.

맨 아래 줄은 지표가 아니라 응답 시간이다. 요청 100건 중 가장 느린 한 건이 예산을 넘으면 그 요청은 광고 없이 나가고, 예측이 정확해도 매출은 0 이다. 정확도와 속도를 한 표에 놓아야 둘을 맞바꾸는 결정을 한자리에서 낸다.

관문을 통과해도 끝이 아니다. 오프라인 관문은 "온라인에 태울 자격"까지만 준다. 매출이 올랐는지는 [모델 A/B 테스트](post.html?id=model-ab-testing)만 답할 수 있고, 배포 뒤 조용히 나빠지는 것은 [모델 모니터링](post.html?id=model-monitoring)이 잡는다.

:::deep 더 깊이 — 문턱을 정하는 방법과 관문에 안 넣은 것
가장 흔한 실수는 소수점 넷째 자리 차이를 유의미하게 읽는 것이다. 위 표의 -0.001 도 그 자체로는 근거가 없다. 같은 모델을 시드만 바꿔 다섯 번 학습해 점수가 얼마나 흔들리는지 먼저 재고, 그 흔들림보다 큰 값을 문턱으로 잡는다.

Precision·Recall·F1 을 안 넣은 이유도 적어 둘 만하다. 이 셋은 임계값을 정해 클릭할지 안 할지를 이분법으로 갈라야 계산되는데, 우리는 그런 결정을 하지 않는다. 확률을 그대로 1,000회 노출당 기대 매출에 곱해 줄을 세울 뿐이다.
:::

## 한눈 정리

| 점수 | 무엇을 재나 | 반응하는 것 | 반응하지 않는 것 | 이 글의 값 |
|---|---|---|---|---|
| 순위 점수 (AUC) | 순서 — 노출을 다 섞어서 | 순서 뒤바뀜 | 예측의 크기 | 0.7333 · 0.7778 |
| 요청 안 순위 점수 (GAUC) | 순서 — 한 요청 안에서만 | 요청 안 순서 | 요청끼리의 차이 | 0.6000 |
| 확률 벌점 (LogLoss) | 확률의 크기 | 크기와 순서 둘 다 | — (데이터가 갈리면 비교 불가) | 0.15296 · 0.05418 |
| 정규화 엔트로피 (NE) | 벌점 ÷ 기저엔트로피 | 크기와 순서 둘 다 | 지면별 클릭률 차이 | 0.8989 · 0.9788 |
| 예측 대비 실제 (COPC) | 실제 ÷ 예측 총합 | 총합 어긋남 | 순서 | 1.043 |

**요청 안 순위 점수로 순서를 보고, 정규화 엔트로피로 크기를 보고, 예측 대비 실제로 총합을 본다.** 순서를 맨 앞에 두는 이유는, 순서가 틀리면 크기를 맞춰도 매출이 안 따라오기 때문이다. 반대로 순서만 맞으면 크기는 보정으로 뒤에서 고칠 수 있다. 셋 다 통과해야 온라인에 태우는 결정을 낸다.

## 헷갈리기 쉬운 점

- **예측 대비 실제가 1보다 크면 낮게 본 것이다.** 실제를 예측으로 나눈 값이니 분자인 실제가 더 컸다는 뜻이다. 역수인 P/O Ratio 와 헷갈리면 보정을 거꾸로 걸어 손해를 키운다.
- **순위 점수가 0.5 라고 모델이 쓸모없는 것은 아니다.** 요청 안 순위 점수가 0.5 면 쓸모없는 것이 맞다. 섞어 잰 값이 그렇게 낮으면 대개 라벨이나 피처 조인이 깨진 신호다.
- **정규화 엔트로피 1.0 은 "보통"이 아니라 "실패"다.** 평균 클릭률만 답하는 모델과 같다는 뜻이라, 넘으면 승인을 취소하고 중단해야 한다.
- **확률 벌점은 같은 데이터 안에서만 비교한다.** 지면·기간·솎아 낸 비율이 다르면 다른 자로 잰 값이라, 그 비교로 예산을 옮기면 손해가 난다.
- **오프라인 점수가 다 통과해도 매출은 안 오를 수 있다.** 평가 표본이 옛 모델 쪽으로 기운 문제는 지표를 늘려도 안 없어지니, 승인 뒤에도 A/B 로 확인하고 결정한다.
