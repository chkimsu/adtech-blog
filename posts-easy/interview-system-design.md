면접관은 화이트보드를 가리키며 지훈에게 이렇게 말했습니다. "광고 추천 시스템을 설계해 보세요."

지훈은 그 말이 끝나자마자 카프카(메시지 큐), 모델 서버, 레디스(메모리에 값을 두는 저장소), 데이터베이스를 상자로 그리기 시작했습니다. 15분이 지나 화이트보드가 상자로 빼곡해졌을 때 면접관이 물었습니다. "응답 시간 예산이 얼마인가요?" 지훈은 그제야 그 예산을 정하지 않고 그려 왔다는 것을 알았습니다. 응답 시간 예산은 요청 하나를 받아 응답을 돌려줄 때까지 쓸 수 있는 시간의 한도입니다.

**설계를 시작하기 전에 무엇을 정해야 할까요?**

숫자부터 정해야 합니다. 초당 요청이 몇 건 들어오는지, 응답을 몇 밀리초(ms, 1,000분의 1초) 안에 돌려줘야 하는지, 후보 광고가 몇 개인지를 모르면 어떤 상자를 그려도 그 상자가 맞는지 틀린지 말할 수 없습니다. 후보 광고는 요청 하나에 내보낼 수 있는 광고들로, 광고 추천 시스템은 이 가운데 내보낼 광고를 고릅니다. 이 글은 광고 ML 시스템 설계 면접에서 되풀이해 나오는 질문 16개를 다룹니다.

> **한 줄 요약:** 시스템 설계 면접은 상자를 많이 그리는 시합이 아닙니다. 초당 요청, 응답 시간 예산, 후보 광고 수 같은 **숫자를 정하고 그 숫자가 어디서 깨지는지 말한 뒤 깨졌을 때 무엇을 할지 답하면** 됩니다.

> **골라 읽는 법** — 절이 10개이고 절마다 면접 질문이 1~2개 있습니다.
>
> - 시작하는 법과 숫자 정하기 → 1~3절
> - 피처를 가져오는 곳, 학습과 서빙의 불일치 → 4절과 5절
> - 배포와 감시 → 6절과 7절
> - 장애와 규모 확장 → 8절과 9절
> - 화이트보드에서 그리는 순서 → 마지막 10절

## 1. 상자를 그리기 전에 정할 숫자 4가지

**설계 질문을 받으면 그리기 전에 초당 요청 수, 응답 시간 예산, 후보 광고 수, 결과를 요청 순간에 계산해야 하는지를 되묻습니다. 이 네 숫자가 정해지면 설계의 절반이 정해지는데, 예산이 100밀리초이고 후보가 100,000개라면 싼 방법으로 후보를 먼저 줄이는 단계와 모델로 점수를 매기는 단계를 나눠야 한다는 결론이 숫자에서 바로 나옵니다.**

지훈처럼 상자부터 그리지 않으려면 첫 질문에서 무엇을 되물을지 미리 알고 있어야 합니다.

**Q. 광고 추천 시스템을 설계해 보십시오.**

이 질문을 듣자마자 그리기 시작하면 안 됩니다. **그리기 전에 면접관에게 되물어야 할 것이 네 가지 있습니다.**

| 물어볼 것 | 왜 필요한가 |
|---|---|
| 초당 요청이 몇 건인가 | 서버 대수와 저장소 종류가 여기서 정해진다 |
| 응답 시간 예산이 얼마인가 | 모델 크기와 피처 개수의 상한이다 |
| 후보 광고가 몇 개인가 | 전부 점수 매길지 추려낼지가 정해진다 |
| 실시간이어야 하나 | 미리 계산해 둘 수 있으면 문제가 완전히 달라진다 |

표의 피처는 모델이 예측에 쓰는 입력 값으로, 기기, 사용자 관심사, 최근 클릭 같은 값입니다. 모델이 크고 피처가 많을수록 추론과 조회에 시간이 더 들기 때문에 응답 시간 예산이 모델 크기와 피처 개수의 상한이 됩니다. 마지막 줄의 실시간 여부는 결과를 요청이 온 순간에 계산해야 하는지 묻는 항목인데, 결과를 미리 계산해 둘 수 있으면 요청이 왔을 때는 읽기만 하면 되므로 문제가 완전히 달라집니다.

**네 숫자가 정해지면 설계의 절반이 정해지므로** 이렇게 되묻는 일은 시간 끌기가 아닙니다.

예를 들어 초당 요청이 1만 건이고 예산이 100밀리초이며 후보가 100,000개라고 해 봅니다. 후보 100,000개 전부에 모델을 돌리면 100밀리초 안에 절대 끝나지 않으므로, 싼 방법으로 후보를 먼저 줄이는 후보 생성과 남은 후보에만 모델을 돌리는 점수 매기기로 **두 단계를 나눠야 한다**는 결론이 숫자에서 바로 나옵니다.

**답의 뼈대는 다섯 단계로 잡습니다.** 요구사항 확인 → 대략의 용량 계산 → 큰 그림 → 병목 하나를 골라 파고들기 → 감시와 장애 대응 순서입니다. 대략의 용량 계산에서는 초당 요청과 데이터 크기로 서버가 몇 대, 저장 공간이 얼마나 필요한지 미리 계산해 봅니다. 병목은 시스템 가운데 가장 느리거나 늘리기 어려워 전체 성능의 한계를 정하는 부분입니다. 면접이 45분이라면 앞의 세 단계에 15분, 병목 파고들기에 20분, 감시와 장애 대응에 10분쯤 나눠 쓰는 것이 적당합니다.

## 2. 요청 하나가 지나가는 길과 후보 생성

**요청 하나가 요청 받기, 후보 생성, 피처 조회, 점수 매기기, 경매와 응답의 다섯 단계를 지나는 동안 후보 생성이 후보를 100,000개에서 1,000개로 줄이고 점수 매기기가 1,000개를 10개로 줄입니다. 후보 생성은 규칙으로 거르기, 미리 만든 목록 찾기, 비슷한 광고 찾기처럼 싼 방법을 섞어 쓰고 비싼 모델은 점수 매기기에만 씁니다.**

면접에서 요청의 흐름을 설명할 때 후보 생성과 점수 매기기를 나누지 않으면 대체로 이 부분부터 지적을 받습니다.

**Q. 후보 생성은 어떻게 합니까?**

**세 가지 방법을 섞어 씁니다.** 먼저 **규칙으로 거릅니다.** 광고주의 예산을 다 쓴 광고, 광고주가 정한 타겟팅 조건(광고를 보여 줄 대상)에 맞지 않는 광고, 소재(광고에 쓰는 이미지와 문구) 심사를 통과하지 않은 광고를 뺍니다. 다음으로 **색인으로 찾습니다.** 색인은 업종별, 지면(광고가 실리는 화면 속 자리)별로 미리 만들어 둔 광고 목록입니다. 그래도 남는 자리는 **임베딩으로 가까운 광고를 뽑아** 채웁니다. 임베딩은 사용자나 광고를 숫자 벡터로 바꾼 것으로, 벡터가 가까울수록 서로 비슷하다고 봅니다. 가까운 광고를 뽑을 때 쓰는 검색이 근사 최근접 검색(ANN)으로, 정확도를 조금 내주는 대신 가까운 벡터를 빠르게 찾습니다.

앞의 두 방법인 규칙과 색인은 빼면 안 됩니다. 예산이 떨어진 광고를 점수 매기기까지 보내면 내보내지도 못할 광고에 모델 계산을 낭비합니다. 심사를 통과하지 않은 소재가 나가면 그 자체로 사고입니다.

## 3. 응답 시간 예산의 배분과 꼬리 지연

**100밀리초 예산은 단계별 시간을 숫자로 적어 나눕니다. 이 글의 예에서는 네트워크를 오가는 시간과 처리 여섯 단계가 83밀리초를 쓰고 17밀리초가 남습니다. 예산은 평균이 아니라 드물게 느린 요청(꼬리)을 기준으로 잡아야 하는데, 서버 한 대가 느린 꼬리에 걸릴 확률이 1% 여도 요청이 서버 30대를 거치면 그 가운데 하나라도 걸릴 확률이 26% 가 됩니다.**

100밀리초를 어떻게 나눌지 물었을 때 "빠르게 하겠다"고만 답하면 어느 단계에서 무엇을 줄여야 하는지가 숫자로 나오지 않아 답이 되지 않습니다.

**Q. 100밀리초 안에 답해야 합니다. 어떻게 나누시겠습니까?**

**단계마다 몇 밀리초를 쓰는지 실제 숫자로 적어서 나눕니다.**

```python
    ("요청 파싱, 검증",        2),
    ("후보 광고 가져오기",     12),
    ("피처 조회",             25),
    ("모델 추론",             18),
    ("입찰가 계산, 경매",       8),
    ("응답 만들기",            3),
]
네트워크 = 15                                  # 앞뒤 왕복

# 2단계: 단계마다 누적 시간과 남은 예산을 찍는다
쓴것 = sum(t for _, t in 단계) + 네트워크
print(f"{'단계':<20}{'ms':>6}{'누적':>8}{'남은 예산':>10}")
누적 = 네트워크
print(f"{'네트워크 왕복':<19}{네트워크:>6}{누적:>8}{예산-누적:>10}")
for 이름, t in 단계:
    누적 += t
    print(f"{이름:<19}{t:>6}{누적:>8}{예산-누적:>10}")

# 3단계: 합계와 가장 큰 몫을 찍는다
print(f"\n합계 {쓴것}ms, 예산 {예산}ms, 여유 {예산-쓴것}ms")
print(f"가장 큰 몫은 피처 조회 {단계[2][1]}ms 로 전체의 {단계[2][1]/쓴것:.0%} 다.")

# 4단계: 모델을 두 배로 무겁게 했을 때 여유를 본다
print("\n같은 예산에서 모델을 두 배 무겁게 하려면(18 → 36ms)")
남는여유 = 예산 - (쓴것 + 18)
print(f"  여유가 {예산-쓴것}ms 에서 {남는여유}ms 가 된다 — {'가능' if 남는여유 >= 0 else '불가능, 다른 데서 줄여야 한다'}")

# 출력:
# 2단계 뜻: 네트워크 왕복 15ms 부터 응답 만들기까지 쌓으면 83ms 를 쓰고 17ms 가 남는다.
# 단계                      ms      누적     남은 예산
# 네트워크 왕복                15      15        85
# 요청 파싱, 검증               2      17        83
# 후보 광고 가져오기             12      29        71
# 피처 조회                  25      54        46
# 모델 추론                  18      72        28
# 입찰가 계산, 경매              8      80        20
# 응답 만들기                  3      83        17
# 3단계 뜻: 합계 83ms 가운데 피처 조회 25ms 가 30% 로 가장 크다.
#
# 합계 83ms, 예산 100ms, 여유 17ms
# 가장 큰 몫은 피처 조회 25ms 로 전체의 30% 다.
# 4단계 뜻: 모델 추론을 18ms 에서 36ms 로 늘리면 여유가 -1ms 가 되어, 다른 데서 줄여야 한다.
#
# 같은 예산에서 모델을 두 배 무겁게 하려면(18 → 36ms)
#   여유가 17ms 에서 -1ms 가 된다 — 불가능, 다른 데서 줄여야 한다
```

찍힌 표는 네트워크 왕복 15밀리초에서 시작해 단계마다 시간을 누적합니다. 응답 만들기까지 쌓으면 83밀리초를 쓰고 예산 100밀리초 가운데 17밀리초가 남습니다. 가장 큰 몫은 피처 조회 25밀리초로 합계 83밀리초의 30% 를 차지합니다. 모델 추론을 18밀리초에서 36밀리초로 두 배 무겁게 하면 18밀리초가 더 들어 남아 있던 17밀리초를 1밀리초 넘기므로, 여유가 −1밀리초가 되어 출력의 마지막 줄대로 다른 단계에서 줄여야 합니다.

이 표를 화이트보드에 그려 두면 면접관이 "모델을 더 크게 쓰면 되지 않나요"라고 물을 때 **"여유가 −1밀리초가 됩니다"라고 숫자로 답할 수 있어** 뒤의 대화가 쉬워집니다. 실무에서도 출력의 마지막 줄처럼 대화합니다. 모델을 키우려면 다른 단계에서 1밀리초 이상 줄여야 한다는 식으로 무엇을 하려면 무엇을 줄여야 하는지가 숫자로 나오므로, 의견이 달라도 논쟁이 취향 싸움이 되지 않습니다.

**Q. 이 예산은 평균 기준입니까?**

아닙니다. 예산을 평균에 맞춰 잡으면 요청 10건 가운데 4건꼴로 예산을 넘으므로 **예산은 느린 꼬리를 기준으로 잡아야 합니다.** 꼬리는 응답 시간 분포에서 드물게 오래 걸리는 느린 끝부분으로, 앞에서 본 p99 같은 높은 분위수로 나타냅니다. 분위수는 값을 작은 것부터 늘어놓았을 때 몇 % 지점에 오는 값이며 50% 지점이 중앙값입니다.

아래 코드는 요청 처리 시간 20만 건을 로그정규 분포에서 뽑아 중앙값, p90 부터 p99.9 까지의 분위수, 평균을 비교한 다음, 요청 하나가 서버를 여러 대 거칠 때 그 가운데 하나라도 p99 를 넘을 확률을 구합니다. 로그정규 분포는 코드 주석의 말대로 대부분 빠르고 가끔 느린 값이 나오는 분포입니다.

```python
# 하는 일: 로그정규 분포로 요청 처리 시간 20만 건을 뽑아 중앙값, p90 부터 p99.9 까지와 평균을 비교하고, 서버를 여러 대 거치면 하나라도 p99 를 넘을 확률을 구한다.
import random, statistics

random.seed(3)

# 1단계: 요청 처리 시간 20만 건을 뽑는다
# 서버 한 대가 요청 하나를 처리하는 데 걸리는 시간(ms). 대부분 빠르고 가끔 느리다.
def 한건():
    return random.lognormvariate(2.7, 0.55)

표본 = sorted(한건() for _ in range(200_000))
def 분위(p): return 표본[int(len(표본) * p)]

# 2단계: 분위수와 평균을 찍는다
평균 = statistics.mean(표본)
print(f"{'지표':<10}{'ms':>8}")
for 이름, p in (("중앙값", 0.50), ("p90", 0.90), ("p95", 0.95), ("p99", 0.99), ("p99.9", 0.999)):
    print(f"{이름:<10}{분위(p):>8.1f}")
print(f"{'평균':<10}{평균:>8.1f}")

print(f"\n중앙값은 {분위(0.5):.0f}ms 인데 p99 는 {분위(0.99):.0f}ms 로 {분위(0.99)/분위(0.5):.1f}배다.")
print("평균만 보면 느린 꼬리가 안 보인다.\n")

# 3단계: 거치는 서버 수마다 p99 를 만날 확률을 구한다
# 하나의 요청이 서버 여러 대를 거치면 꼬리가 커진다
print(f"{'거치는 서버 수':>14}{'하나라도 p99 를 넘을 확률':>26}")
for k in (1, 5, 10, 30):
    print(f"{k:>14}{1 - 0.99**k:>24.1%}")
print("\n서버 30대를 거치면 요청 넷 중 하나가 어딘가에서 p99 를 만난다.")

# 출력:
# 2단계 뜻: 중앙값은 14.9ms 인데 p99 는 53.2ms 로 3.6배이고, 평균 17.3ms 는 느린 꼬리를 보여 주지 못한다.
# 지표              ms
# 중앙값           14.9
# p90           30.2
# p95           36.8
# p99           53.2
# p99.9         81.4
# 평균            17.3
#
# 중앙값은 15ms 인데 p99 는 53ms 로 3.6배다.
# 평균만 보면 느린 꼬리가 안 보인다.
#
# 3단계 뜻: 서버 30대를 거치면 하나라도 p99 를 넘을 확률이 26.0% 로, 요청 넷 중 하나가 어딘가에서 p99 를 만난다.
#       거치는 서버 수          하나라도 p99 를 넘을 확률
#              1                    1.0%
#              5                    4.9%
#             10                    9.6%
#             30                   26.0%
#
# 서버 30대를 거치면 요청 넷 중 하나가 어딘가에서 p99 를 만난다.
```

찍힌 첫 표에서 중앙값은 14.9밀리초인데 p99 는 53.2밀리초로 중앙값의 3.6배입니다. 평균 17.3밀리초는 중앙값보다 조금 클 뿐이라 평균만 보면 53.2밀리초까지 늘어지는 느린 꼬리가 보이지 않습니다.

아래쪽 표는 서버마다 서로 상관없이 1% 확률로 p99 를 넘는다고 보고 계산했습니다. 서버 한 대가 p99 를 넘지 않을 확률이 0.99 라서 요청이 서버를 k 대 거치는 동안 한 번도 넘지 않을 확률은 0.99 를 k 번 곱한 값이므로, 1 에서 이 값을 빼면 그 가운데 하나라도 넘을 확률이 됩니다. 1대면 1.0%, 5대면 4.9%, 10대면 9.6% 입니다. **서버 한 대가 p99 보다 느릴 확률은 1% 뿐이어도 요청이 30대를 거치면 26% 가 되어 요청 4건 가운데 1건꼴로 어딘가에서 느린 꼬리를 만납니다.** 마이크로서비스(기능마다 작은 서버로 나눠 서로 호출하는 구조)로 잘게 나눌수록 요청이 거치는 서버가 늘어 이 문제가 커집니다.

**대응책은 세 가지입니다.** 첫째, 서로 기다릴 필요가 없는 호출은 하나씩 차례로 부르지 않고 병렬로 부릅니다. 둘째, 호출마다 타임아웃(정해 둔 시간 안에 답이 없으면 더 기다리지 않는 한도)을 걸어 늦으면 미리 정한 기본값으로 넘어갑니다. 셋째, 꼭 필요하지 않은 호출은 아예 빼서 요청이 거치는 서버 수를 줄입니다.

## 4. 피처를 가져오는 곳과 피처 스토어

**피처 조회 시간은 피처를 값이 바뀌는 빠르기에 따라 나눈 뒤 요청에 이미 들어 있거나 서버 메모리에 둘 수 있는 피처를 그쪽으로 옮기면 가장 크게 줄어듭니다. 옮길 수 없는 피처는 한 키에 묶어 왕복 한 번에 가져옵니다. 같은 피처를 학습과 서빙(배포한 모델이 실제 요청에 답하는 일)에서 따로 계산하기 시작하면 피처 스토어(학습과 서빙 양쪽에 같은 피처 값을 내주는 시스템)가 필요해집니다.**

두 곳에서 따로 계산한 값은 언젠가 반드시 달라집니다. 사용자의 최근 클릭 수를 예로 들면 학습 쪽은 하루치 로그를 다 모은 뒤 정확히 세지만 서빙 쪽은 이벤트가 올 때마다 숫자를 올리는 실시간 카운터라 몇 건이 빠집니다. 이 작은 차이가 5절에서 다룰 학습과 서빙의 불일치를 만듭니다.

## 5. 학습과 서빙의 불일치

**배포한 뒤 AUC(클릭할 노출에 더 높은 값을 주는 정도)가 배포 전 오프라인 평가보다 떨어지면, 데이터 누수(서비스 시점에는 알 수 없는 정보가 학습에 섞이는 문제)가 아닌 한 같은 이름의 피처가 학습과 서빙에서 다른 값일 가능성이 높습니다. 모델 코드는 그대로 두고 서빙 쪽 피처 값만 바꿔도 AUC 가 0.78 에서 0.74 로 떨어지므로, 서빙 시점의 피처 값을 로그에 남겨 그 값으로 학습합니다.**

4절 끝에서 본 작은 차이(학습은 정확히 세고 서빙은 몇 건을 빠뜨리는 차이)가 배포 뒤의 지표를 얼마나 바꾸는지를 아래 질문과 코드로 따라갑니다.

**Q. 오프라인 AUC는 0.78인데 배포하면 0.74가 나옵니다. 왜일까요?**

오프라인 AUC 는 배포하기 전에 모아 둔 데이터로 측정한 AUC 입니다. AUC 는 클릭한 노출과 클릭하지 않은 노출을 하나씩 짝지었을 때 모델이 클릭한 쪽에 더 높은 값을 준 짝의 비율입니다. 같은 값을 준 짝은 절반만 맞힌 것으로 칩니다. AUC 가 1 에 가까울수록 클릭할 노출을 위에 잘 놓는 모델입니다.

데이터 누수가 원인이 아니라면 **학습과 서빙에서 같은 이름의 피처가 서로 다른 값일 가능성이 높습니다.** 모델링 질문 편에서 다룬 데이터 누수는 서비스 시점에는 알 수 없는 정보가 학습이나 검증에 섞여 오프라인 성능이 서비스에서 나올 성능보다 좋게 나오는 문제입니다.

아래 코드는 사용자 최근 클릭 수라는 피처 하나를 학습 때는 정확히 세고 서빙 때는 늦거나 빠진 값으로 받을 때, 같은 모델의 AUC 와 COPC 가 얼마나 달라지는지를 노출 10만 건으로 비교합니다. 2단계를 보면 서빙 쪽 값은 10% 확률로 0 이 되고 나머지는 진짜 값보다 1 작게(0 아래로는 내려가지 않게) 들어옵니다. COPC 는 3단계의 copc 함수처럼 실제 클릭 수를 모델이 낸 예측 확률의 합으로 나눈 값입니다. COPC 가 1 이면 예측과 실제가 맞고 1 보다 크면 모델이 실제보다 작게 예측했다는 뜻입니다.

```python
# 하는 일: 사용자 최근 클릭 수 피처를 학습 때는 정확히 세고 서빙 때는 늦거나 빠진 값으로 받을 때, 같은 모델의 AUC 와 COPC 가 얼마나 달라지는지 노출 10만 건으로 비교한다.
import random, math, bisect

random.seed(42)
N = 100_000

# 1단계: 진짜 클릭 수와 클릭 라벨을 만든다
# 사용자 최근 클릭 수라는 피처가 있다.
# 학습 때는 하루치 로그를 다 모아 정확히 세지만,
# 서빙 때는 실시간 카운터라 늦게 반영되거나 일부가 빠진다.
진짜카운트 = [max(0, int(random.expovariate(1/3))) for _ in range(N)]
클릭확률 = [min(0.4, 0.005 + 0.02 * c) for c in 진짜카운트]
라벨 = [1 if random.random() < p else 0 for p in 클릭확률]

# 2단계: 학습 피처와 서빙 피처를 만든다
학습피처 = 진짜카운트                              # 정확한 값
서빙피처 = [0 if random.random() < 0.10 else max(0, c - 1) for c in 진짜카운트]

# 3단계: 모델, AUC, COPC 함수를 만든다
def 모델(c):                                   # 학습 데이터로 맞춘 아주 단순한 모델
    return min(0.4, 0.005 + 0.02 * c)

def auc(pred):
    양 = sorted(p for p, y in zip(pred, 라벨) if y == 1)
    음 = sorted(p for p, y in zip(pred, 라벨) if y == 0)
    합 = 0.0
    for p in 양:
        아래 = bisect.bisect_left(음, p); 같음 = bisect.bisect_right(음, p) - 아래
        합 += 아래 + 같음 / 2
    return 합 / (len(양) * len(음))

def copc(pred):
    return sum(라벨) / sum(pred)

# 4단계: 두 피처로 같은 모델을 채점한다
print(f"{'피처를 어디서 가져왔나':<24}{'AUC':>8}{'COPC':>9}")
for 이름, f in (("학습 때와 같은 값", 학습피처), ("서빙에서 실제로 오는 값", 서빙피처)):
    p = [모델(c) for c in f]
    print(f"{이름:<22}{auc(p):>8.4f}{copc(p):>9.3f}")

같은값 = sum(a == b for a, b in zip(학습피처, 서빙피처)) / N
print(f"\n두 피처가 같은 비율 {같은값:.1%}")
print("모델은 그대로인데 들어가는 값이 달라 오프라인 지표가 그대로 안 나온다.")

# 출력:
# 4단계 뜻: 학습 때와 같은 값을 넣으면 AUC 0.7828, COPC 1.006 인데, 서빙에서 실제로 오는 값을 넣으면 AUC 0.7404, COPC 1.482 로 어긋난다. 두 피처가 같은 비율은 28.4% 뿐이다.
# 피처를 어디서 가져왔나                 AUC     COPC
# 학습 때와 같은 값              0.7828    1.006
# 서빙에서 실제로 오는 값           0.7404    1.482
#
# 두 피처가 같은 비율 28.4%
# 모델은 그대로인데 들어가는 값이 달라 오프라인 지표가 그대로 안 나온다.
```

찍힌 표에서 학습 때와 같은 값을 넣으면 AUC 0.7828, COPC 1.006 이고 서빙에서 실제로 오는 값을 넣으면 AUC 0.7404, COPC 1.482 입니다. 3단계의 모델은 1단계에서 클릭 확률을 만든 식과 같은 식이라 학습 때와 같은 값을 넣은 첫 줄은 COPC 가 1 에 가깝습니다. 두 피처가 같은 비율은 28.4% 뿐인데, 2단계의 규칙대로라면 진짜 클릭 수가 0 인 노출만 두 값이 같기 때문입니다.

**모델 코드는 한 글자도 바꾸지 않고 모델에 들어가는 피처 값만 달라졌는데 AUC 가 0.78 에서 0.74 로 떨어졌습니다.** 서빙 쪽 값은 10% 가 0 으로 들어오고 나머지도 1 씩 작아서 클릭 수가 서로 다른 노출들이 같은 0 을 받는 경우가 생기는데, 모델은 같은 값을 받은 노출끼리는 구분하지 못하므로 클릭할 노출을 위에 놓는 정도가 낮아집니다.

COPC 도 1.006 에서 1.482 로 1 에서 크게 벗어났습니다. 1.482 는 실제 클릭 수가 예측 확률 합의 1.482배라는 뜻이라 실제 클릭이 예측보다 48% 많습니다. 서빙 값이 진짜 값보다 작게 들어오니 예측 확률도 작아진 탓인데, 예측이 이렇게 낮은 상태로는 그 예측으로 정하는 입찰가(경매에서 노출 하나에 내겠다고 부르는 값)도 계속 낮게 나와 물량(따낼 수 있었던 노출)을 잃습니다.

**모범 답안 — "같은 피처를 두 곳에서 각각 계산하고 있는지부터 확인합니다. 서빙 로그에 실제로 들어간 피처 값을 남겨서 학습 데이터와 맞춰 봅니다."**

모범 답안의 둘째 문장이 실무의 해법입니다. **서빙할 때 모델에 실제로 들어간 피처 값을 그대로 로그에 남기고 그 로그로 학습하면** 학습과 서빙이 같은 값을 쓰므로 불일치가 원천적으로 사라집니다. 로그를 저장하는 비용은 늘지만 원인을 모르는 성능 하락을 쫓는 데 드는 시간보다는 쌉니다.

## 6. 모델 배포와 되돌리기

**새 모델은 한 번에 다 바꾸지 않고 그림자 배포(결과를 쓰지 않고 돌려 보는 단계), 소량 트래픽, 점진 확대, 되돌릴 준비의 네 단계로 내보냅니다. 모델 배포와 코드 배포를 분리해 이전 모델을 서버에 올려 둔 채 모델 파일 경로만 설정으로 바꿔 되돌릴 수 있으면 되돌리기가 몇 초면 됩니다. 그 되돌리기도 평소에 실제로 해 본 적이 있어야 사고 때 작동합니다.**

배포 질문의 답에는 새 모델을 내보내는 순서와 문제가 났을 때 되돌리는 방법이 함께 들어가야 합니다.

**Q. 새 모델을 어떻게 배포하시겠습니까?**

먼저 모든 요청을 한 번에 새 모델로 바꾸지 않는다고 말한 뒤 **네 단계를 차례로 설명합니다.**

**첫째는 그림자 배포입니다.** 요청을 새 모델에도 돌리지만 사용자에게 나가는 응답에는 그 결과를 쓰지 않고 새 모델의 응답 시간과 예측값 분포만 봅니다. 예측값 분포는 모델이 내놓은 예측 확률들이 어느 값에 얼마나 몰려 있는지를 말하며 7절에서 다시 다룹니다. "너무 느리다"와 "값이 이상하다" 같은 문제는 대부분 이 단계에서 걸립니다.

**둘째는 소량 트래픽입니다.** 전체 요청의 1% 나 5% 에만 새 모델의 결과를 내보내는데, 새 모델을 받은 요청과 이전 모델을 받은 요청을 비교하는 실험이므로 앞 편에서 다룬 실험 설계가 여기에 그대로 적용됩니다.

**셋째는 점진 확대입니다.** 지표가 괜찮으면 새 모델에 보내는 비율을 5% 에서 20%, 50% 로 늘립니다. 늘릴 때마다 앞 편에서 본 가드레일을 확인합니다. 가드레일은 실험의 주요 지표가 좋아져도 나빠지면 안 되는 지표입니다.

**넷째는 되돌릴 준비입니다.** 되돌리는 데 30분이 걸리면 문제가 있는 새 모델이 그 30분 동안 계속 요청을 받아 사고가 이어지므로, 이전 모델을 즉시 되살릴 수 있어야 합니다.

**Q. 되돌리기를 어떻게 빠르게 합니까?**

**모델 배포와 코드 배포를 분리합니다.** 모델 배포는 학습한 모델 파일만 바꾸는 일이고 코드 배포는 서버 프로그램 자체를 새로 내보내는 일입니다. 두 배포가 분리되어 이전 모델을 서버에 올려 둔 채 설정에 적힌 모델 파일 경로만 바꿔 되돌릴 수 있으면 몇 초면 되지만 모델이 코드에 묶여 있으면 모델 하나를 되돌릴 때도 코드 배포 절차를 다시 밟아야 해서 느립니다.

답에 한 가지를 더 붙이면 좋은데, 평소에 써 보지 않은 되돌리기는 사고가 났을 때 작동하지 않으므로 **되돌리기를 실제로 해 본 적이 있어야 합니다.**

## 7. 배포 뒤 감시하는 세 층과 예측값 분포

**배포 뒤에 볼 지표는 시스템, 모델, 비즈니스의 세 층으로 나눕니다. 모델 층은 시스템이 멀쩡하고 비즈니스 지표가 아직 움직이지 않는 사이의 조용한 고장을 잡는 층인데도 자주 빠집니다. 예측값은 평균만 보지 않고 어제와 오늘의 분포를 겹쳐 봅니다.**

모델이 나빠지는데도 서버가 오류를 내지 않는 고장이 있어서 오류율만 보고 있으면 그런 고장을 알아채지 못합니다.

**Q. 배포 후에 무엇을 보시겠습니까?**

**보는 지표를 시스템, 모델, 비즈니스의 세 층으로 나눠 말하면 답이 정리됩니다.**

| 층 | 보는 것 | 이상하면 |
|---|---|---|
| 시스템 | p99 응답 시간, 오류율, 타임아웃 비율 | 즉시 되돌린다 |
| 모델 | 예측값 평균, 분포, COPC, 피처 결측률 | 조사하고 판단한다 |
| 비즈니스 | 매출, 클릭률, 전환율, 예산 소진 속도 | 실험 결과로 판단한다 |

표의 오류율, 타임아웃 비율, 피처 결측률은 각각 요청이 오류로 끝난 비율, 정해 둔 시간 안에 답하지 못한 요청의 비율, 피처 값이 비어서 들어온 요청의 비율입니다. 전환율은 광고를 클릭한 뒤 구매 같은 전환으로 이어진 비율이고 예산 소진 속도는 광고주의 예산이 쓰이는 빠르기입니다.

**이 가운데 모델 층이 자주 빠집니다.** 모델이 나빠져도 시스템 층의 지표는 멀쩡하고 비즈니스 지표는 며칠 뒤에야 움직이므로, 그 며칠 사이에 오류 없이 진행되는 조용한 고장은 모델 층이 잡습니다.

모델 층에는 특히 **피처 결측률**을 꼭 넣어야 합니다. 이 모델에 피처를 만들어 보내는 상류의 데이터 파이프라인이 조용히 멈추면 피처가 전부 기본값으로 들어오는데 시스템은 오류를 내지 않습니다. 모델은 기본값을 받은 채 계속 답하고 그 답은 점점 나빠집니다.

**Q. 예측값 분포를 본다는 게 무슨 뜻입니까?**

**어제와 오늘의 예측값 히스토그램을 겹쳐 보고 모양이 갑자기 바뀌었으면 무언가 잘못되었다고 본다는 뜻입니다.** 히스토그램은 값을 구간으로 나눠 구간마다 몇 건이 들어 있는지를 막대로 그린 그림입니다.

분포를 보면 평균만으로는 잡히지 않는 고장이 잡힙니다. 예를 들어 오늘 예측값의 절반이 0.001 에, 나머지 절반이 0.05 에 몰려도 평균은 어제와 같을 수 있는데, 히스토그램에서는 0.001 과 0.05 두 곳에 봉우리가 생긴 것이 보입니다.

## 8. 장애 대응과 출력 상한

**광고는 대체로 안 내보내는 것이 나쁜 광고를 내보내는 것보다 더 나빠서, 피처 스토어가 응답하지 않으면 성능을 낮춰서라도 응답하고 모델까지 돌릴 수 없으면 미리 만들어 둔 인기 광고 목록을 내보냅니다. 반대로 이상한 값을 내보내는 것이 더 나쁜 경우에 대비해 예측 확률과 입찰가에 상한을 걸어 모델을 믿지 않는 층을 하나 둡니다.**

피처 스토어가 응답하지 않으면 모델에 넣을 피처를 가져올 수 없어 평소처럼 점수를 매길 수 없습니다.

**Q. 피처 스토어가 응답을 안 합니다. 어떻게 하시겠습니까?**

**대응을 말하기 전에 광고를 아예 안 내보내는 것과 나쁜 광고를 내보내는 것 가운데 무엇이 더 나쁜지부터 정해 둬야 합니다.**

광고에서는 대체로 안 내보내는 것이 더 나쁩니다. 광고 자리인 지면이 비면 그 자리에서 나올 수익이 0 이고 사용자에게도 빈자리가 이상하게 보이므로 **예측 성능을 낮춰서라도 응답하는 쪽**을 고릅니다.

응답하는 방법을 단계별로 말하면 이렇습니다. 먼저 피처 스토어 호출에 타임아웃을 짧게 걸어 응답이 늦으면 빨리 포기합니다. 다음으로 캐시(자주 쓰는 값을 가까운 곳에 복사해 둔 저장 공간)에 남은 값을 쓰는데, 캐시에도 없으면 미리 정한 기본값을 넣어 모델을 돌립니다. 모델까지 돌릴 수 없으면 **미리 만들어 둔 인기 광고 목록**을 내보냅니다.

이 마지막 단계까지 말해야 답이 완성되는데, **어떤 상황에서도 응답할 수 있는 가장 단순한 경로를 하나 준비해 두는 일**도 설계의 일부이기 때문입니다.

**Q. 반대로, 이상한 값을 내보내는 게 더 나쁜 경우도 있지 않습니까?**

있습니다. 그런 경우에 대비해 **모델의 출력에 상한을 겁니다.** 예측 확률이 정해 둔 값을 넘으면 잘라 냅니다. 입찰가가 하루 예산의 일정 비율을 넘으면 그 입찰을 막습니다.

모델이 아무리 좋아도 데이터 사고가 한 번 나면 이상한 값을 내므로, 출력 상한으로 **모델을 믿지 않는 층을 하나 둡니다.**

:::deep 캐시를 두는 세 층과 각각의 함정

응답 시간을 줄이는 방법으로 가장 흔히 나오는 답이 캐시인데, 캐시를 어디에 두느냐에 따라 빠르기와 약점이 완전히 달라집니다.

**서버 메모리 캐시**는 각 서버가 자기 메모리에 값을 두는 캐시라 가장 빠르고 조회 비용이 사실상 들지 않습니다. 대신 서버마다 들고 있는 내용이 다르고 배포할 때마다 캐시가 비워집니다. 배포 직후 잠깐 느려지는 현상이 이렇게 비워진 캐시에서 생기므로, 거의 바뀌지 않는 값만 넣습니다.

**공용 인메모리 저장소**는 여러 서버가 네트워크로 함께 읽는 메모리 저장소라 모든 서버가 같은 값을 보는 대신 읽을 때마다 네트워크 왕복이 한 번 듭니다. 사용자 피처처럼 어느 서버가 요청을 받든 같아야 하는 값은 여기에 넣습니다.

**미리 계산해 둔 결과**는 캐시라기보다 설계가 다른 방식입니다. 사용자별 추천 목록을 밤에 만들어 두면 요청이 왔을 때는 읽기만 하면 되므로, 결과를 요청 순간에 계산하지 않아도 되는 자리에서는 세 층 가운데 가장 쌉니다.

약점도 층마다 다릅니다. 서버 메모리 캐시는 서버마다 내용이 달라 **일관성이 없으므로** 같은 사용자가 요청이 어느 서버로 가느냐에 따라 다른 답을 받습니다. 공용 저장소는 모든 서버가 그 하나만 보므로 **공용 저장소가 죽으면 전부 죽습니다.** 미리 계산한 결과는 계산해 둔 뒤에 들어온 **새 광고나 새 사용자를 다루지 못합니다.**

면접에서 "캐시를 쓰겠습니다"라고만 말하면 부족합니다. **"어느 층에, 무엇을, 얼마나 오래 두고, 안 맞을 때 어떻게 되나"까지 말해야 답이 됩니다.** 네 가지 가운데 특히 마지막은 캐시가 오래된 값을 주는 상황을 허용할지 말지를 정하는 물음이라 그 답이 곧 설계 결정입니다.
:::

## 9. 규모 확장과 병목

**트래픽이 열 배가 되면 먼저 요청에 비례해 늘릴 수 있는 부분과 그렇지 않은 부분을 나누는데, 늘어나지 않는 부분이 병목입니다. 상태가 없는(따로 기억해 둘 데이터가 없는) 서버를 먼저 늘리고 읽기와 쓰기는 그 뒤에 차례로 나눕니다. 모델 서버가 병목이면 계산 줄이기, 한 번에 여러 개 처리하기, 미리 계산하기의 세 갈래로 답합니다.**

트래픽이 열 배가 되면 1절에서 정한 초당 요청도 열 배가 되어 그 숫자에 맞춰 그린 상자 가운데 어느 것이 먼저 버티지 못하는지를 답해야 합니다.

**Q. 트래픽이 열 배가 됐습니다. 무엇부터 깨질까요?**

**먼저 요청에 비례해(선형으로) 늘릴 수 있는 부분과 그렇지 않은 부분을 나눕니다.**

서버 대수는 대체로 선형으로 늘릴 수 있어 요청이 열 배면 서버도 열 배로 늘리면 되므로, 이렇게 늘릴 수 있는 부분은 애초에 병목이 아닙니다.

**병목은 늘어나지 않는 부분입니다.** 모든 것이 데이터베이스 한 대에 몰려 있으면 서버를 늘려도 그 한 대가 늘어난 요청을 버티지 못합니다. 3절 아래쪽 표에서 본 꼬리 문제(요청이 거치는 서버가 많을수록 어딘가에서 p99 를 만날 확률이 커지는 문제)도 여기서 심해집니다.

답은 순서를 정해 말하면 정리되어 들립니다. **먼저 상태가 없는 서버를 늘리고 그다음 읽기를 나눈 뒤 마지막으로 쓰기를 나눕니다.** 상태가 없는 서버는 요청마다 받은 것만으로 처리할 뿐 따로 기억해 두는 데이터가 없어 대수를 늘리기만 하면 됩니다. 읽기는 같은 데이터를 담은 복제본을 늘려 나눠 받으면 되므로 쉽지만 쓰기를 나누는 일은 어렵습니다.

**Q. 모델 서버가 병목이면 어떻게 합니까?**

**계산을 줄이는 방법, 한 번에 여러 개를 처리하는 방법, 미리 계산하는 방법의 세 갈래로 나눠 답합니다.**

첫째 갈래인 **계산을 줄이는 방법**을 먼저 봅니다. 모델을 작게 만들거나, 양자화(모델의 숫자를 더 적은 비트로 나타내 계산을 가볍게 하는 기법)하거나, 후보를 더 일찍 줄입니다. **점수를 매길 후보를 1,000개에서 500개로 줄이면 모델이 하는 계산이 그 자체로 절반이 됩니다.**

둘째 갈래는 **한 번에 여러 개를 처리하는 방법**으로, 3절 카드에서 본 배치가 여기에 해당합니다. 처리량은 같은 시간에 처리하는 요청 수이고 지연은 요청 하나가 응답을 받기까지 걸리는 시간입니다. 요청을 조금 모았다가 한 번에 추론하면 처리량이 크게 늘지만 요청이 모이기를 기다리는 동안 지연도 늘어납니다. 이 방법은 **처리량과 지연을 맞바꾸므로** 응답 시간 예산에 여유가 있을 때만 씁니다.

셋째 갈래는 **미리 계산하는 방법**입니다. 자주 나오는 조합을 미리 계산해 두면 요청이 왔을 때 드는 비용이 0 이 되지만 조합의 수가 폭발적으로 늘어나 다 계산해 둘 수 없는 자리에서는 통하지 않습니다.

## 10. 화이트보드에서 그리는 순서

**상자를 너무 빨리 그리는 것이 설계 면접에서 지는 가장 흔한 방식이므로, 요구사항, 가장 단순한 그림, 병목 하나, 감시와 장애의 순서를 미리 정해 두고 그립니다.**

도입의 지훈이 그랬습니다. 지훈은 15분 동안 화이트보드를 상자로 채웠지만 그 상자들이 어떤 숫자를 만족시키는지는 지훈도 면접관도 몰랐습니다. 그리는 순서를 미리 정해 두면 숫자 없이 상자만 늘어나는 일이 생기지 않습니다.

**첫째로 요구사항을 적습니다.** 화이트보드 왼쪽 위 구석에 초당 요청, 응답 예산, 후보 개수, 데이터 크기를 적어 두고 설명하는 내내 이 숫자를 가리키며 말하면 논리가 이어집니다.

**둘째로 가장 단순한 그림을 그립니다.** 요청 → 모델 → 응답의 상자 3개면 충분합니다. 여기서 시작해 "이러면 뭐가 안 되죠?"를 스스로 물으며 하나씩 고쳐 나갑니다. **처음부터 완성된 그림을 그리면 그림이 왜 그런 모양이 되었는지 설명할 기회가 없습니다.**

**셋째로 병목 하나를 골라 깊이 파고듭니다.** 모든 부분을 얕게 다루면 어느 것도 인상에 남지 않으므로, 피처 조회를 골랐다면 저장소 선택, 자료 구조, 캐시 층, 장애 대응까지 끝까지 갑니다.

**마지막으로 감시와 장애를 말합니다.** 여기까지 오는 지원자가 많지 않아 오히려 눈에 띄므로, 시간이 부족해도 감시와 장애는 한 문장씩이라도 말해야 합니다.

반대로 하지 말아야 할 것도 분명한데, 들어 본 기술 이름 늘어놓기, 요구사항을 묻지 않고 그리기, "이건 나중에 최적화하면 됩니다"라는 말로 넘기기의 세 가지입니다. 이 가운데 마지막은 **무엇을 나중으로 미룰지 그 판단 자체가 질문의 내용**인 경우가 많으므로 특히 조심해야 합니다.

## 한눈 정리

| 질문 | 답 한 줄 |
|---|---|
| 추천 시스템을 설계하라 | 초당 요청, 응답 예산, 후보 개수, 실시간 여부부터 되묻습니다 |
| 요청이 어떻게 흐르나 | 후보 생성과 점수 매기기를 나눕니다. 후보 100,000개 전부에 모델을 돌릴 수는 없습니다 |
| 100ms를 어떻게 나누나 | 숫자로 적어서 나눕니다. 이 예에서는 피처 조회가 30%로 가장 큽니다 |
| 평균 기준인가 | 아닙니다. 서버 30대를 거치면 26%가 p99를 만납니다 |
| 피처 조회를 어떻게 줄이나 | 조회가 필요 없는 층으로 옮기고 남은 것은 묶어서 한 번에 가져옵니다 |
| 피처 스토어가 필요한가 | 같은 피처를 두 곳에서 계산하기 시작하면 필요합니다 |
| 오프라인과 온라인이 다르다 | 서빙 시점 피처를 로그에 남겨 그 값으로 학습합니다 |
| 새 모델을 어떻게 배포하나 | 그림자 → 소량 → 확대 → 되돌리기. 네 단계를 다 말합니다 |
| 되돌리기를 빠르게 하려면 | 모델 배포와 코드 배포를 분리합니다 |
| 배포 후 뭘 보나 | 시스템, 모델, 비즈니스 세 층. 가운데 모델 층이 자주 빠집니다 |
| 피처 스토어가 죽었다 | 성능을 낮춰서라도 응답합니다. 최후의 단순 경로를 준비해 둡니다 |
| 트래픽이 열 배가 됐다 | 선형으로 늘지 않는 것을 찾습니다. 상태 없는 것부터 늘립니다 |
| 모델 서버가 병목이다 | 계산 줄이기, 묶어서 처리하기, 미리 계산하기의 세 갈래 |

## 헷갈리기 쉬운 점

- **숫자를 정하기 전에 그리면 안 됩니다.** 초당 요청과 응답 예산이 없으면 어떤 설계도 평가할 수 없습니다.
- **후보 생성과 점수 매기기는 반드시 나눕니다.** 후보 100,000개에 무거운 모델을 돌리는 설계는 그 자리에서 탈락합니다.
- **예산은 평균 응답 시간으로 잡지 않습니다.** 3절의 예에서 p99 는 중앙값의 3.6배입니다. 요청이 서버를 많이 거칠수록 어딘가에서 그 꼬리를 만날 확률이 커집니다.
- **같은 피처를 두 곳에서 따로 계산하면 안 됩니다.** 모델을 바꾸지 않아도 AUC 가 0.78 에서 0.74 로 떨어집니다.
- **되돌리기를 설계에서 빼지 않습니다.** 되돌리는 데 30분이 걸리면 사고가 30분 동안 이어집니다.
- **모델 층 감시를 빼먹지 않습니다.** 시스템은 멀쩡하고 비즈니스 지표는 늦게 움직이므로 그 사이의 고장은 모델 층이 잡습니다.
- **"캐시를 쓰겠습니다"로 끝내면 안 됩니다.** 어느 층에 얼마나 오래 두고 안 맞을 때 어떻게 되는지까지 말합니다.
- **"나중에 최적화하면 됩니다"로 넘기지 않습니다.** 무엇을 미루는지가 질문의 내용일 때가 많습니다.
