지훈이 어제 새 랭킹 모델을 오프라인 평가에 통과시켰다. 이 모델을 전면에 올릴지 결정하려면 트래픽 절반을 일주일 걸어야 하는데, 그 일주일에 이 지면이 태우는 광고비가 ₩420,000,000이다. 모델이 기대만큼 못 하면 그 예산의 일부는 손해로 남는다.

그래서 지훈은 돈이 안 드는 길을 먼저 간다. 지난주에 쌓인 로그로 새 모델의 클릭률을 오늘 오후 안에 추정해 보는 것이다. 계산에 드는 비용은 몇 분이다.

로그 한 줄에는 그때 실제로 띄운 광고 하나의 결과만 있다. 새 모델이 대신 골랐을 광고가 클릭됐을지는 어디에도 없다. 그런데 배포 결정은 그 빈칸에 달려 있다. **로그에 없는 결과를 어떻게 메울까?**

이 질문에 붙은 이름이 **오프폴리시 평가**(off-policy evaluation)다. 로그를 남긴 규칙과 다른 규칙을 그 로그만으로 채점하는 일이다. 채점이 되면 후보 마흔 개를 하루에 대여섯 개로 줄이고, 매출을 걸고 재는 A/B는 그 대여섯 개에만 쓴다.

> **한 줄 요약:** 옛 규칙이 그 광고를 고를 확률 `p`를 로그에 같이 남겨 둬야 한다. 그러면 두 규칙이 같은 광고를 고른 건을 `1/p`배로 세어 새 규칙의 성적을 추정할 수 있다. 대신 `p`가 아주 작았던 건 하나가 추정치를 흔들어, 배포 결정을 뒤집을 만큼 값이 튄다.

> 절 제목 옆의 무대 표시는 이런 뜻이다. **열린 RTB**는 남의 거래소에 입찰만 넣는 자리, **닫힌 생태계**는 우리가 경매를 직접 돌리는 자리, **공통**은 두 자리 모두라는 표시다.

## 1. 안 띄운 광고는 결과가 없다

**로그 한 줄에는 결과가 하나뿐이다. 옛 규칙이 고른 광고의 결과이고, 배포를 결정해야 할 새 규칙 쪽 결과는 없다.**

요청이 들어올 때마다 후보 광고 여덟 개 중 무엇을 띄울지 결정해야 한다. 점수를 매기고 그중 하나를 고르는 절차 전체를 **정책**(policy)이라 부른다. 모델 하나가 아니다. 점수 1등만 고르느냐 가끔 다른 것도 섞느냐까지 포함한 절차다.

로그를 남긴 쪽을 **옛 정책**, 배포를 결정할 채점 대상을 **새 정책**이라 부르기로 한다. 논문에서는 각각 behavior policy와 target policy다.

이 글의 숫자는 전부 지어낸 값이고 규모도 작게 잡았다. 하루 노출 로그가 2억 2,800만 줄인 서비스에서, 예산 하나짜리 캠페인의 요청 10,000건만 떼어 온 셈이다. 지면 이름은 로그에 `main_top`처럼 적히지만 이 글에서는 메인 상단·검색 상단·피드 중간·피드 하단·상세 사이드로 부른다.

메인 상단의 요청 한 건을 펼쳐 보자.

| 후보 | 옛 정책 확률 `p` | 옛 정책이 골랐나 | 새 정책이 고르나 | 로그에 남은 결과 |
|---|---|---|---|---|
| 0 | 0.0125 | 아니오 | 아니오 | 없음 |
| 1 | 0.0128 | 아니오 | **고른다** | **없음** |
| 2 | 0.0125 | 아니오 | 아니오 | 없음 |
| 3 | 0.0125 | 아니오 | 아니오 | 없음 |
| 4 | 0.9109 | **골랐다** | 아니오 | **클릭 0** |
| 5 | 0.0137 | 아니오 | 아니오 | 없음 |
| 6 | 0.0125 | 아니오 | 아니오 | 없음 |
| 7 | 0.0125 | 아니오 | 아니오 | 없음 |

확률 여덟 개를 더하면 1이 된다. 결과가 적힌 줄은 여덟 중 하나뿐이다. 나머지 일곱은 뜨지도 않아 비용도 성과도 없다.

새 모델이 후보 1번의 클릭률을 예측할 수는 있지만, 맞는지 확인할 정답 라벨이 없다. 그러니 이것은 모델이 정확한가가 아니라 빈칸을 무엇으로 메울까의 문제다. 메우는 방법에 따라 성적이 두 배까지 갈리고, 그 숫자로 배포 승인이 결정된다.

## 2. 겹친 건만 세면 새 정책이 새롭지 않은 자리만 남는다

**두 정책이 같은 광고를 고른 건만 세면 계산은 한 줄로 끝난다. 대신 표본이 달라져서 성적이 두 배 넘게 좋아 보이고, 그 숫자로 예산을 늘리게 된다.**

가장 단순한 방법부터 본다. 두 정책이 같은 광고를 고른 건만 남기고, 그 건들의 클릭률을 새 정책의 성적으로 삼는다. 계산 비용이 거의 안 든다. 이 방법을 **겹치는 건만 쓰기**(Replay, 매칭)라 부른다.

아래 코드가 지난주 로그를 지어낸다. 예산 하나짜리 캠페인의 요청 10,000건, 지면 다섯 개, 요청마다 후보 여덟 개다. 옛 정책은 열 번에 한 번 균등 무작위로 고르고, 새 모델은 옛 모델이 못 보는 피처를 하나 더 본다.

```python
# 이 글의 공용 준비 코드다. 지난주 로그 10,000건을 지어내고,
# 겹치는 건만 쓰기로 새 정책을 채점한다.
# 진짜 CTR을 우리가 정해 놓았으므로 '정답'을 알 수 있다. 실제 로그에는 정답이 없다.
# 3절·4절 코드는 여기서 만든 build_log()를 그대로 이어서 쓴다.

import math, random

K, EPS, TAU = 8, 0.10, 0.0014      # 후보 8개 · 옛 정책 = softmax + 균등 10% 섞기
# (지면, 요청 수, 기저 CTR 하한, 상한, 숨은 피처 z의 값어치)
# z는 옛 모델이 못 보는 피처다. 새 모델만 본다. 지면마다 z의 값어치가 다르다.
SLOTS = [("main_top", 2600, 0.024, 0.044, 0.000), ("search_top", 1400, 0.016, 0.032, 0.003),
         ("feed_mid", 3100, 0.007, 0.018, 0.010), ("feed_low", 2000, 0.004, 0.012, 0.014),
         ("detail_side", 900, 0.003, 0.009, 0.018)]

def build_log(seed=7):
    random.seed(seed); log = []
    for name, n, lo, hi, bonus in SLOTS:
        for _ in range(n):
            base = [random.uniform(lo, hi) for _ in range(K)]
            ctr = [b + bonus * (1 if random.random() < 0.2 else 0) for b in base]
            old_s = [b + random.gauss(0, 0.004) for b in base]     # 옛 모델은 z를 못 본다
            new_s = [c + random.gauss(0, 0.002) for c in ctr]      # 새 모델은 z를 본다
            m = max(old_s); ex = [math.exp((s - m) / TAU) for s in old_s]; Z = sum(ex)
            p = [(1 - EPS) * (x / Z) + EPS / K for x in ex]        # 옛 정책의 선택 확률
            u, acc, a = random.random(), 0.0, K - 1
            for i, pi in enumerate(p):
                acc += pi
                if u <= acc: a = i; break                          # 옛 정책이 실제로 고른 것
            log.append((name, ctr, p, a, 1 if random.random() < ctr[a] else 0,
                        max(range(K), key=lambda i: new_s[i])))    # 새 정책이라면 골랐을 것
    return log

log = build_log()
N = len(log)
print(f"{'지면':<12}{'요청':>7}{'겹친 건':>9}{'겹침률':>8}{'겹친 건 클릭':>12}{'Replay CTR':>12}")
tm = tc = 0
for name, n, lo, hi, bonus in SLOTS:
    sub = [x for x in log if x[0] == name]
    mt = [x for x in sub if x[3] == x[5]]
    ck = sum(x[4] for x in mt); tm += len(mt); tc += ck
    print(f"{name:<12}{len(sub):>7,}{len(mt):>9,}{len(mt)/len(sub):>8.1%}{ck:>12}{ck/len(mt):>12.2%}")
print(f"{'합계':<12}{N:>7,}{tm:>9,}{tm/N:>8.1%}{tc:>12}{tc/tm:>12.2%}")

obs = sum(x[4] for x in log) / N                    # 옛 정책이 실제로 낸 성적
v_new = sum(x[1][x[5]] for x in log) / N            # 새 정책의 진짜 값
v_old = sum(sum(pi * ci for pi, ci in zip(x[2], x[1])) for x in log) / N
print()
print(f"로그 전체 CTR (옛 정책 실측)   : {obs:.3%}  (클릭 {sum(x[4] for x in log)}건)")
print(f"Replay 추정 (겹친 {tm:,}건만)  : {tc/tm:.3%}  → 옛 정책 대비 {(tc/tm)/obs-1:+.1%}")
print(f"새 정책의 진짜 값             : {v_new:.3%}  → 옛 정책 진짜 값 {v_old:.3%} 대비 {v_new/v_old-1:+.1%}")

nm, ctr, p, a, r, e = log[9]           # 1절 그림에 쓴 요청 한 건
print(f"\n1절 표의 요청({nm}) — 옛 정책은 후보 {a}번을 확률 {p[a]:.1%}로 골랐고 클릭은 {r}이다.")
print(f"  새 정책이라면 후보 {e}번을 고른다. 그 후보가 겹칠 확률은 {p[e]:.2%}, 가중치로는 {1/p[e]:.0f}배다.")
print(f"  후보 8개를 균등 무작위로 골랐다면 CTR은 {sum(sum(x[1])/K for x in log)/N:.3%}였다.")

# 출력:
# 지면               요청     겹친 건     겹침률     겹친 건 클릭  Replay CTR
# main_top      2,600    1,021   39.3%          42       4.11%
# search_top    1,400      485   34.6%          15       3.09%
# feed_mid      3,100      628   20.3%          13       2.07%
# feed_low      2,000      316   15.8%          12       3.80%
# detail_side     900      145   16.1%           4       2.76%
# 합계           10,000    2,595   25.9%          86       3.31%
#
# 로그 전체 CTR (옛 정책 실측)   : 2.120%  (클릭 212건)
# Replay 추정 (겹친 2,595건만)  : 3.314%  → 옛 정책 대비 +56.3%
# 새 정책의 진짜 값             : 2.807%  → 옛 정책 진짜 값 2.291% 대비 +22.5%
#
# 1절 표의 요청(main_top) — 옛 정책은 후보 4번을 확률 91.1%로 골랐고 클릭은 0이다.
#   새 정책이라면 후보 1번을 고른다. 그 후보가 겹칠 확률은 1.28%, 가중치로는 78배다.
#   후보 8개를 균등 무작위로 골랐다면 CTR은 1.983%였다.
```

요청 10,000건 중 2,595건이 겹쳤고, 그 건들의 클릭률은 3.31%다. 로그 전체 2.12%보다 한참 높으니, 이 숫자만 보고서에 옮기면 배포 승인을 받기가 아주 쉽다.

진짜 값은 2.807%다. 옛 정책의 2.291%와 견주면 나아진 폭은 22.5%이고, 겹치는 건만 쓰기가 말한 56.3%는 그 두 배를 넘는다. 이 차이를 믿고 예산을 늘렸다면 늘린 만큼이 손해다.

원인은 겹침률 열에 있다. 메인 상단은 39.3%가 살아남는데 피드 하단은 15.8%만 남는다. 메인 상단은 원래 클릭률이 높은 지면이라 표본이 그쪽으로 기운다.

더 나쁜 것이 있다. **새 정책이 가장 크게 달라지는 지면이 가장 많이 버려진다.** 새 모델의 강점인 숨은 피처가 피드 하단과 상세 사이드에서 값어치가 가장 크기 때문이다. 예산이 가장 크게 움직일 자리가 통째로 빠지는 셈이다.

남는 것은 두 정책이 이미 같은 답을 내던 자리다. 로그를 열 배로 늘려도 그대로라, 이 숫자로는 배포를 결정할 수 없다.

## 3. 확률의 역수로 몇 배 세나

**겹칠 확률이 `p`였던 건을 `1/p`건 몫으로 세면 버려진 건까지 대신 세어진다. 대신 그 `p`가 로그에 있어야 한다.**

2절의 문제는 겹친 건을 전부 한 건으로 센 것이다. 겹칠 확률이 42%인 요청과 1.3%인 요청을 같은 무게로 세면 겹치기 쉬운 쪽이 과하게 대표된다. 그 왜곡이 그대로 예산 결정에 실린다.

무게를 바로잡는 길은 이렇다. 겹칠 확률이 `p`였던 건을 `1/p`건 몫으로 센다. 확률 1.28%로 겹친 건이라면 78건 몫이니, 같은 상황을 78번 중 한 번 봤다고 치는 것이다.

이 방법을 **확률의 역수로 세기**(IPS, inverse propensity scoring)라 부른다. 분모에 들어가는 확률에도 이름이 있다. **성향점수**(propensity score, 그때 옛 정책이 그 광고를 고를 확률)다.

아래 코드는 요청 하나에서 이 계산이 왜 맞는지를 여덟 줄로 펼쳐 본다.

```python
# ── 2절 코드에 이어서 돌린다 (K, EPS, TAU, SLOTS, build_log 그대로) ──
# 확률의 역수로 세기가 왜 치우침이 없나 — 한 요청에서 기대값을 직접 더해 본다.
# 그 다음 로그 10,000건 전체에 같은 식을 적용한다.

log = build_log()
name, ctr, p, a, r, e = log[3100]        # 로그에서 요청 한 건을 꺼내 펼쳐 본다
print(f"요청 하나({name}) — 새 정책은 후보 {e}번을 고른다\n")
print(f"{'후보':>4}{'옛 정책 확률 p':>15}{'진짜 CTR':>10}{'새 정책이 고르나':>17}{'IPS 기여 = p x (1/p) x CTR':>28}")
tot = 0.0
for i in range(K):
    hit = (i == e)
    contrib = p[i] * (1 / p[e]) * ctr[i] if hit else 0.0
    tot += contrib
    print(f"{i:>4}{p[i]:>15.4f}{ctr[i]:>10.4f}{'예' if hit else '아니오':>17}{contrib:>28.5f}")
print(f"{'합계':>4}{sum(p):>15.4f}{'':>10}{'':>17}{tot:>28.5f}")
print(f"\n합계 {tot:.5f} = 후보 {e}번의 진짜 CTR {ctr[e]:.5f}  →  한 건 기준으로 정확히 맞는다")
print("옛 정책이 그 후보를 안 고른 경우는 0을 더하고, 고른 경우는 1/p 배로 부풀린다.")
print("고를 확률이 p이니 'p번 중 1/p배'가 상쇄돼 딱 한 번 센 것이 된다.\n")

N = len(log)
w = [(1 / x[2][x[5]]) if x[3] == x[5] else 0.0 for x in log]
ips = sum(wi * x[4] for wi, x in zip(w, log)) / N
v_new = sum(x[1][x[5]] for x in log) / N
v_old = sum(sum(pi * ci for pi, ci in zip(x[2], x[1])) for x in log) / N
matched = sum(1 for x in log if x[3] == x[5])
print(f"로그 {N:,}건 전체")
print(f"  겹친 건            : {matched:,}건 ({matched/N:.1%})")
print(f"  가중치 합계        : {sum(w):,.0f}  (요청 수 {N:,}건과 비슷해야 한다)")
print(f"  IPS 추정           : {ips:.3%}")
print(f"  Replay 추정        : {sum(x[4] for x in log if x[3] == x[5])/matched:.3%}")
print(f"  새 정책 진짜 값    : {v_new:.3%}   (옛 정책 진짜 값 {v_old:.3%})")

# 출력:
# 요청 하나(search_top) — 새 정책은 후보 4번을 고른다
#
#   후보      옛 정책 확률 p    진짜 CTR        새 정책이 고르나    IPS 기여 = p x (1/p) x CTR
#    0         0.0125    0.0185              아니오                     0.00000
#    1         0.1841    0.0276              아니오                     0.00000
#    2         0.0125    0.0199              아니오                     0.00000
#    3         0.3181    0.0304              아니오                     0.00000
#    4         0.4235    0.0284                예                     0.02839
#    5         0.0237    0.0258              아니오                     0.00000
#    6         0.0126    0.0182              아니오                     0.00000
#    7         0.0130    0.0258              아니오                     0.00000
#   합계         1.0000                                                0.02839
#
# 합계 0.02839 = 후보 4번의 진짜 CTR 0.02839  →  한 건 기준으로 정확히 맞는다
# 옛 정책이 그 후보를 안 고른 경우는 0을 더하고, 고른 경우는 1/p 배로 부풀린다.
# 고를 확률이 p이니 'p번 중 1/p배'가 상쇄돼 딱 한 번 센 것이 된다.
#
# 로그 10,000건 전체
#   겹친 건            : 2,595건 (25.9%)
#   가중치 합계        : 9,681  (요청 수 10,000건과 비슷해야 한다)
#   IPS 추정           : 1.669%
#   Replay 추정        : 3.314%
#   새 정책 진짜 값    : 2.807%   (옛 정책 진짜 값 2.291%)
```

여덟 줄 중 일곱 줄은 0을 더하고, 남은 한 줄이 `0.4235 × (1/0.4235) × 0.0284`를 더한다. 확률과 가중치가 서로를 지워 합계가 진짜 클릭률 0.02839와 같아지고, 여러 번 평균 내면 진짜 값에 맞는다.

논문은 이 성질을 불편추정이라 부르는데, '불편'은 치우침이 없다는 뜻이다. 가중치 합계 9,681도 신호라서, 요청 수 10,000과 크게 어긋나면 로깅을 먼저 의심한다.

그런데 이번 주의 추정치는 1.669%로 진짜 값 2.807%의 60% 수준이다. 이대로 올리면 멀쩡한 모델을 중단시킨다. **방법이 틀린 것이 아니라 이 한 주가 그렇게 나온 것이다.**

조건이 하나 붙는다. 옛 정책이 그 광고를 고를 확률이 0이면 `1/p`를 만들 수 없고, 그런 요청은 예산을 아무리 써도 못 메운다. 이 조건을 **공통 지지 조건**(support)이라 부른다.

평균이 맞는다는 성질은 이번 추정치를 보장하지 않는다. 이대로는 승인이든 중단이든 결정에 못 쓴다.

:::deep 더 깊이 — 식과 평균이 맞는 이유

$a_i$는 옛 정책이 고른 광고, $\pi_e(x_i)$는 새 정책이 골랐을 광고다. $p_i$는 그 확률이고 $r_i$는 클릭 여부다.

$$\hat{V}_{\mathrm{IPS}} = \frac{1}{n}\sum_{i=1}^{n} \frac{\mathbf{1}[a_i = \pi_e(x_i)]}{p_i}\, r_i$$

요청 $x$를 두고 한 건이 더하는 값의 기대값을 펼쳐 보자. 합 안에서 $p(a \mid x)$가 약분되고, 지시함수 때문에 $a = \pi_e(x)$인 항만 남는다.

$$E\!\left[\frac{\mathbf{1}[a = \pi_e(x)]}{p(a \mid x)}\, r \;\middle|\; x\right] = E[r \mid x, \pi_e(x)]$$

남은 것이 새 정책의 기대 보상이다. 약분이 성립하려면 보상이 문맥과 고른 광고에만 달려 있어야 하는데, 한 화면에 광고가 여럿 뜨는 랭킹에서는 위태롭다([위치 편향과 ULTR](post.html?id=position-bias-ultr)).
:::

## 4. 흔들림 — 어디서 오고 어떻게 줄이나

**가중치의 3분의 1을 52건이 들고 있는데 그 안에는 클릭이 없다. 그래서 10,000건짜리 로그가 실제로는 339건 몫이고, 흔들림을 줄이려면 값이 내려가는 비용을 치른다.**

3절의 추정치는 왜 1.669%까지 내려갔나. 아래 코드는 겹친 건을 가중치 구간으로 나눠 세고, 이어서 같은 조건의 '지난주'를 400번 다시 뽑아 방법마다 성적을 비교한다.

```python
# ── 2절 코드에 이어서 돌린다 (K, EPS, TAU, SLOTS, build_log 그대로) ──
# 앞부분: 가중치가 어디에 몰려 있나 — 그리고 유효표본크기(ESS)로 다시 재 본다.
# 뒷부분: 같은 조건의 '지난주'를 400번 다시 뽑아, 방법마다 평균과 흔들림을 잰다.

log = build_log(); N = len(log)
rows = [(1 / x[2][x[5]], x[4]) for x in log if x[3] == x[5]]     # (가중치, 클릭) — 겹친 건만
sw = sum(w for w, r in rows); sw2 = sum(w * w for w, r in rows)
ess = sw * sw / sw2
ips = sum(w * r for w, r in rows) / N
v_new = sum(x[1][x[5]] for x in log) / N        # 새 정책의 진짜 값

print(f"{'가중치 1/p':>12}{'건수':>7}{'가중치 합':>11}{'제곱 합':>11}{'클릭':>6}{'IPS 기여':>11}")
BINS = [("1 ~ 2", 1, 2), ("2 ~ 5", 2, 5), ("5 ~ 10", 5, 10),
        ("10 ~ 20", 10, 20), ("20 ~ 40", 20, 40), ("40 ~ 80", 40, 81)]
for label, lo, hi in BINS:
    g = [(w, r) for w, r in rows if lo <= w < hi]
    s = sum(w for w, r in g); s2 = sum(w * w for w, r in g); c = sum(r for w, r in g)
    print(f"{label:>12}{len(g):>7,}{s:>11,.0f}{s2:>11,.0f}{c:>6}{sum(w*r for w,r in g)/N:>11.4%}")
print(f"{'합계':>12}{len(rows):>7,}{sw:>11,.0f}{sw2:>11,.0f}{sum(r for w,r in rows):>6}{ips:>11.4%}")

print(f"\n유효표본크기 ESS = (가중치 합)^2 / (제곱 합) = {sw:,.0f}^2 / {sw2:,.0f} = {ess:,.0f}")
print(f"  겹친 건 {len(rows):,}건 · 로그 {N:,}건 → 실제로 값을 지탱하는 건 {ess:,.0f}건")
print(f"  ESS {ess:,.0f}건에 진짜 CTR {v_new:.3%}를 곱하면 클릭 {ess*v_new:.1f}건 — 그만큼이 이 숫자를 받친다")

# 겹치지 않은 건은 어떤 추정기에도 0을 더한다. 그래서 겹칠 확률과 그때의 CTR만 있으면 된다.
pool = [(x[2][x[5]], x[1][x[5]]) for x in build_log()]
N = len(pool)
V = sum(c for p, c in pool) / N                 # 새 정책의 진짜 값

def one_week(rng):
    return [(1 / pe, 1 if rng.random() < ce else 0) for pe, ce in pool if rng.random() < pe]

EST = ["Replay", "IPS", "SNIPS", "절단 M=20", "절단 M=5", "절단 M=20 + 자기정규화"]
acc = {k: [] for k in EST}
for wk in range(400):
    rows = one_week(random.Random(1000 + wk))
    sw = sum(w for w, r in rows); swr = sum(w * r for w, r in rows)
    acc["Replay"].append(sum(r for w, r in rows) / len(rows))
    acc["IPS"].append(swr / N)
    acc["SNIPS"].append(swr / sw)
    for M, key in ((20, "절단 M=20"), (5, "절단 M=5")):
        cw = [min(w, M) for w, r in rows]
        acc[key].append(sum(c * r for c, (w, r) in zip(cw, rows)) / N)
        if M == 20:
            acc["절단 M=20 + 자기정규화"].append(sum(c * r for c, (w, r) in zip(cw, rows)) / sum(cw))

print(f"새 정책의 진짜 값 = {V:.3%}   ('지난주'를 400번 다시 뽑았다)\n")
print(f"{'추정기':<22}{'평균':>9}{'편향':>9}{'표준편차':>10}{'RMSE':>9}{'20% 넘게 빗나간 주':>20}")
for k in EST:
    v = acc[k]; mu = sum(v) / len(v)
    sd = (sum((x - mu) ** 2 for x in v) / (len(v) - 1)) ** 0.5
    rmse = (sum((x - V) ** 2 for x in v) / len(v)) ** 0.5
    off = sum(1 for x in v if abs(x - V) > 0.2 * V) / len(v)
    print(f"{k:<22}{mu:>9.3%}{mu-V:>+9.3%}{sd:>10.3%}{rmse:>9.3%}{off:>20.0%}")

# 400주를 10주씩 40묶음으로 합치면 요청 100,000건짜리 추정 40개가 된다.
print(f"\n{'로그를 10배(100,000건)로 늘리면':<28}{'평균':>9}{'편향':>9}{'표준편차':>10}")
for k in ("Replay", "IPS"):
    g = [sum(acc[k][i*10:(i+1)*10]) / 10 for i in range(40)]
    mu = sum(g) / 40; sd = (sum((x - mu) ** 2 for x in g) / 39) ** 0.5
    print(f"{k:<28}{mu:>9.3%}{mu-V:>+9.3%}{sd:>10.3%}")

# 출력:
#      가중치 1/p     건수      가중치 합       제곱 합    클릭     IPS 기여
#        1 ~ 2  1,883      2,437      3,254    68    0.8776%
#        2 ~ 5    442      1,304      4,101    14    0.4322%
#       5 ~ 10    135        935      6,784     4    0.3587%
#      10 ~ 20     50        715     10,545     0    0.0000%
#      20 ~ 40     33        947     28,370     0    0.0000%
#      40 ~ 80     52      3,343    223,039     0    0.0000%
#           합계  2,595      9,681    276,093    86    1.6685%
#
# 유효표본크기 ESS = (가중치 합)^2 / (제곱 합) = 9,681^2 / 276,093 = 339
#   겹친 건 2,595건 · 로그 10,000건 → 실제로 값을 지탱하는 건 339건
#   ESS 339건에 진짜 CTR 2.807%를 곱하면 클릭 9.5건 — 그만큼이 이 숫자를 받친다
# 새 정책의 진짜 값 = 2.807%   ('지난주'를 400번 다시 뽑았다)
#
# 추정기                          평균       편향      표준편차     RMSE        20% 넘게 빗나간 주
# Replay                   3.183%  +0.376%    0.355%   0.517%                 31%
# IPS                      2.776%  -0.031%    0.809%   0.808%                 48%
# SNIPS                    2.781%  -0.026%    0.812%   0.811%                 50%
# 절단 M=20                  2.124%  -0.683%    0.407%   0.795%                 64%
# 절단 M=5                   1.582%  -1.225%    0.210%   1.243%                100%
# 절단 M=20 + 자기정규화          2.917%  +0.110%    0.553%   0.563%                 30%
#
# 로그를 10배(100,000건)로 늘리면             평균       편향      표준편차
# Replay                         3.183%  +0.376%    0.117%
# IPS                            2.776%  -0.031%    0.224%
```

### 흔들림이 어디서 오나

첫 표의 마지막 줄을 보자. 가중치가 40에서 80 사이인 건이 52개로 겹친 건의 2.0%다. **그런데 이 52건에는 클릭이 하나도 없다.**

무게로 보면 다르다. 가중치 합 9,681 중 3,343을 이 건들이 들고 있어 3분의 1이 넘는다. 클릭이 없으니 그 무게는 0을 더하고, 결정에 쓰는 값이 그만큼 눌린다.

만약 이 중 하나에 클릭이 붙었다면 추정치가 1.669%에서 2.469%로 뛴다. 클릭 한 번이 배포 결정을 뒤집을 만큼 값을 밀어 올리는 것이다.

이 상태를 한 수로 요약한 것이 **유효표본크기**(ESS, effective sample size)다. 가중치가 전부 같으면 표본 수와 같아지고 몇 건에 몰릴수록 작아진다. 이 로그에서는 339이고, 보고할지 말지를 이 값으로 결정한다.

### 흔들림을 줄이는 두 손질

한 주만 보고는 그 주가 운이 나빴는지 알 수 없다. 그래서 코드가 같은 조건의 지난주를 400번 다시 뽑았다. 아래 표가 손질을 고르는 근거이자 비용표다.

평균이 진짜 값 2.807%에서 벗어난 만큼이 치우침이고, 표준편차가 주마다 흔들리는 폭이다. RMSE는 그 둘을 합친 값이라 작을수록 좋다.

| 추정 방법 | 400주 평균 | 표준편차 | RMSE | 20% 넘게 빗나간 주 | 언제 쓰나 |
|---|---|---|---|---|---|
| 겹치는 건만 쓰기 (Replay) | 3.183% | 0.355% | 0.517% | 31% | 확률이 없을 때뿐 |
| 확률의 역수로 세기 (IPS) | 2.776% | 0.809% | 0.808% | 48% | 치우침 없는 기준선 |
| 가중치 합으로 나누기 (SNIPS) | 2.781% | 0.812% | 0.811% | 50% | 가중치 합이 어긋날 때 |
| 잘라내기 상한 20 | 2.124% | 0.407% | 0.795% | 64% | 단독으로는 권하지 않는다 |
| 잘라내기 상한 5 | 1.582% | 0.210% | 1.243% | 100% | 너무 조인 예 |
| 잘라내기 상한 20 + 합으로 나누기 | 2.917% | 0.553% | 0.563% | 30% | **실무 기본값** |

첫째, 확률의 역수로 세기는 정말로 치우침이 없다. 400주 평균 2.776%가 진짜 값 2.807%와 거의 같다. 겹치는 건만 쓰기는 400주를 평균 내도 3.183%에 머문다.

코드 마지막 두 줄이 그 차이를 못박는다. 로그를 열 배로 늘리면 표준편차는 0.809%에서 0.224%로 줄지만 3.183%는 그대로다. **흔들림은 데이터로 사고, 치우침은 데이터로 못 산다.**

둘째, **가중치 합으로 나누기**(SNIPS, 자기정규화)는 여기서 도움이 안 된다. 요청 수 10,000 대신 가중치 합 9,681로 나누는 손질인데, 표준편차가 0.809%에서 0.812%로 그대로다.

**흔들림의 주범이 분모가 아니기 때문이다.** 클릭이 드물어 분자가 훨씬 크게 흔들린다. 어떤 주에는 가중치 큰 건에 클릭이 붙고 어떤 주에는 안 붙는데, 그 차이는 분모를 다듬어도 남는다.

셋째, **가중치 잘라내기**(clipping, 절단)는 흔들림을 줄이는 대신 값이 내려가는 비용을 치른다. 상한 20이면 표준편차가 절반인 0.407%가 되지만, 400주 평균이 2.124%로 내려앉는다.

잘라 낸 몫이 아무 데도 안 돌아가기 때문이다. 가중치 80을 20으로 자르면 그 건이 대표하던 60건 몫이 사라진다. 상한 5로 조이면 평균이 1.582%까지 내려가 결정에 못 쓴다.

**넷째, 둘을 같이 걸면 잘라 낸 몫이 대부분 돌아온다.** 분자에서 깎인 만큼 분모도 줄기 때문이다. 400주 평균 2.917%에 RMSE 0.563%로 표에서 가장 낫다. 상한은 유효표본크기가 목표선을 넘는 값 중 가장 큰 것으로 결정한다.

:::deep 더 깊이 — 유효표본크기와 가중치 합으로 나누기의 식

가중치 $w_i$의 합을 제곱한 뒤 제곱의 합으로 나눈 것이 유효표본크기다. 위 코드 출력의 두 합을 넣으면 `9,681² ÷ 276,093 = 339`다.

$$\mathrm{ESS} = \frac{\left(\sum_i w_i\right)^2}{\sum_i w_i^2}, \qquad w_i = \frac{\mathbf{1}[a_i = \pi_e(x_i)]}{p_i}$$

가중치 합으로 나누기는 같은 가중치를 쓰되 분모만 바꾼다. 3절은 요청 수 $n$으로 나눴고 여기서는 가중치 합으로 나눈다. 이쪽은 표본이 커져야 치우침이 사라지는 종류다.

$$\hat{V}_{\mathrm{SNIPS}} = \frac{\sum_i w_i r_i}{\sum_i w_i}$$
:::

재료를 하나 더 쓰는 길도 있다. 클릭 확률을 예측하는 pCTR 모델로 답을 먼저 깔고, 확률의 역수 가중은 예측이 빗나간 몫에만 거는 방식이다. 그러면 둘 중 하나만 맞아도 값이 진짜에 붙어 결정을 받친다. 이 방법이 이중 강건이고, 절차와 실험은 [추정 방법 둘을 겹치면 왜 더 튼튼한가](post.html?id=doubly-robust)에 있다.

손질을 무엇으로 하든 출발점은 하나다. 로그에 성향점수가 적혀 있어야 한다.

## 5. 로그에 확률이 없으면 아무것도 못 한다

**성향점수는 나중에 되살릴 수 없다. 서빙하는 순간에 안 남겼다면 겹치는 건만 쓰기의 치우침을 안고 결정해야 한다.**

성향점수는 지난주 로그를 다시 훑어서 계산할 수 없다. 그 순간 옛 모델이 낸 점수와 그때의 탐색 설정이 있어야 나온다. 모델은 매일 배포되고 피처도 갱신되니, 첫 관문은 통계가 아니라 로깅이다.

| 남길 필드 | 무엇이 들어가나 | 없으면 무엇이 막히나 |
|---|---|---|
| 지면 | 메인 상단·피드 하단 같은 자리 이름 | 지면별 진단이 안 된다 |
| 후보 목록 | 그때 겨루던 광고 여덟 개 | 새 정책을 못 돌린다 |
| 고른 광고 | 실제로 띄운 광고 하나 | 무엇을 골랐는지 모른다 |
| **고른 광고의 확률** | 성향점수 (예: 0.9109) | 이 글의 계산이 전부 막힌다 |
| 정책 이름과 판 번호 | 어느 정책이 남긴 줄인지 | 다른 정책 로그와 섞인다 |
| 탐색으로 고른 건인지 | 참 또는 거짓 | 탐색 건을 못 가른다 |
| 클릭 여부 | 0 또는 1 | 라벨이 없다 |

**고른 것의 확률 하나면 충분하다.** 분모에 들어가는 것은 실제로 고른 광고의 확률뿐이다. 후보 여덟 개의 확률을 전부 남길 필요는 없다.

저장 비용도 걱정만큼 크지 않다. 필드 하나가 부동소수 8바이트면 하루 2억 2,800만 줄에 1.8GB다. 대신 후보 목록과 [피처 값](post.html?id=feature-store-serving)도 남겨야 새 정책을 다시 돌릴 수 있다. 필드 하나 넣는 결정이 다음 분기의 평가를 살린다.

### 점수 1등만 고르는 것이 문제가 되는 쪽은 반대다

새 정책이 점수 1등만 고르니 확률의 역수로 셀 수 없다는 말이 있다. **반은 틀렸다.** 새 정책이 그렇게 고르는 것은 문제가 없고, 3절의 계산이 바로 그 경우였다.

막히는 것은 반대쪽이다. **로그를 남긴 옛 정책이 점수 1등만 골랐을 때** 고른 것의 확률이 1이고 나머지가 0이 되어, 공통 지지 조건이 깨진다.

그러니 오늘 무엇을 고르느냐가 아니라 지난주에 어떻게 남겼느냐의 문제다. 확률을 안 심었다면 겹치는 건만 쓰기밖에 안 남고, 거기서 본 치우침을 안은 채 결정해야 한다.

확률을 심는 방법은 둘이 흔하다. ε-greedy는 정한 비율만큼만 균등 무작위로 고르고, softmax는 점수를 확률로 바꿔 전부 확률적으로 고른다.

| 로깅 방식 | 가장 작은 선택 확률 | 가장 큰 가중치 | 확률의 역수로 셀 수 있나 |
|---|---|---|---|
| 점수 1등만 고르기 | 0 | 무한 | 못 쓴다 |
| softmax만 | 하한이 없다 | 제한이 없다 | 위태롭다 |
| ε-greedy, 무작위 2% | 0.0025 | 400 | 되지만 흔들린다 |
| ε-greedy, 무작위 10% | 0.0125 | 80 | 쓸 만하다 |
| ε-greedy, 무작위 20% | 0.025 | 40 | 넉넉하다 |
| 전부 균등 무작위 | 0.125 | 8 | 가장 깨끗하다 |

가장 큰 가중치는 후보 수를 탐색 비율로 나눈 값이라 여기서는 `8 ÷ 0.10 = 80`이다. softmax만 쓰면 확률이 얼마든지 작아지니 하한을 같이 건다.

탐색은 오늘의 매출로 치르는 비용이다. 무작위로 고르는 구간에서는 클릭률이 1.983%로 떨어진다. 탐색을 끄면 옛 정책의 진짜 값이 2.325%였을 텐데, 열 번에 한 번을 무작위로 돌린 탓에 2.291%가 됐다.

**여기가 맞바꿈이 생기는 자리다.** 탐색을 늘리면 추정이 튼튼해지고 오늘의 매출이 내려간다. 탐색 비율은 통계 문제가 아니라 예산 결정이고, 불확실한 곳에 탐색을 몰아 주는 [밴딧](post.html?id=exploration-exploitation)이 그 비용을 줄인다.

결국 로깅 설계가 곧 평가 예산이다. 확률 필드 하나와 탐색 비율 하나가 다음 분기에 A/B로 태울 비용을 결정한다.

## 6. 이 숫자로 배포를 결정할 수는 없다 [무대: 공통]

**로그 추정은 후보를 걸러 내는 단계다. 통과한 한둘만 온라인 A/B로 보낸다. 순서를 바꾸면 둘 다 망가진다.**

로그로 이만큼 잴 수 있는데 트래픽 절반과 일주일을 들여 A/B를 또 해야 하나. 비용이 큰데도 세 가지 이유로 그렇다.

**첫째, 구간이 너무 넓다.** 4절에서 유효표본크기가 339였고 클릭으로 치면 9.5건이었다. 그 숫자로는 예산을 못 옮긴다.

주간 표준편차 0.809%는 진짜 값 2.807%의 29%다. 이 폭으로는 5% 차이를 가르지 못하니, 배포 결정을 이 숫자로 내릴 수 없다.

**둘째, 정책을 바꾸면 세상이 반응한다.** 새 정책이 입찰가를 높이면 낙찰이 늘고, 예산이 빨리 말라 광고가 나가는 시간대가 달라진다. 이 되먹임은 지난주 로그에 없다.

**셋째, 로그에 없는 행동은 영원히 못 잰다.** 지난주에 한 번도 안 뜬 신규 광고는 어떤 방법으로도 성적이 안 나온다. 신규 광고에 예산을 얼마나 줄지는 로그로 결정할 수 없다([콜드 스타트 pCTR](post.html?id=cold-start-pctr)).

| 묻는 것 | 지난주 로그로 추정 | 온라인 A/B |
|---|---|---|
| 후보 마흔 개 중 어느 것이 나은가 | 하루면 대여섯 개로 줄인다 | 마흔 주가 걸린다 |
| 진짜 클릭률이 정확히 얼마인가 | 폭이 너무 넓다 | 이 자리의 답 |
| 정책을 바꾼 뒤 예산과 낙찰 | 못 잰다 | 이 자리의 답 |
| 광고주 보고와 정산 숫자 | 쓰면 안 된다 | 여기서 나온 것만 |
| 드는 비용 | 계산 몇 분 | 트래픽 절반과 일주일 |

**거르는 데 쓰는 값은 정확할 필요가 없다.** 순위만 맞으면 되고, 그 순위가 곧 예산 배분 결정이다. 4절에서 두 손질을 같이 걸어 RMSE를 줄인 이유가 그것이다.

반대로 광고주 보고와 정산에 들어갈 숫자는 로그 추정치로 채우지 않는다. 그 숫자로 정산 금액이 결정되니 [무작위 통제 실험](post.html?id=rct-randomized-experiment)에서 받는다.

### 담장 안에서는 로깅 정책을 우리가 정한다 [무대: 닫힌 생태계]

담장 안 DSP는 경매를 직접 돌리니 5절의 맞바꿈을 우리가 결정한다. 트래픽이 많고 클릭률이 낮은 지면에서 탐색을 더 하고, 매출이 큰 지면에서는 덜 한다. 확률 필드를 [로그 스키마](post.html?id=kafka-log-pipeline)에 넣는 것도 우리 결정이다.

대신 지면과 광고주가 둘 다 우리 고객이라, 탐색이 만드는 매출 하락을 양쪽에 설명하고 승인을 받아야 한다.

### 열린 RTB에서는 성향점수가 남의 손에 있다 [무대: 열린 RTB]

외부 DSP가 결정하는 것은 입찰가와 크리에이티브까지다. 그 입찰이 노출로 이어질지는 거래소의 경매가 정하니, 우리 정책이 그 광고를 고를 확률과 실제로 노출될 확률이 갈린다.

뒤의 것은 경쟁 입찰가에 달려 있는데 우리는 그 값을 못 본다([Bid Shading과 검열된 데이터](post.html?id=bid-shading-censored)). 두 확률을 따로 모델링해 곱하면 뒤 항에 오차가 실리고, 이런 자리에서 [이중 강건](post.html?id=doubly-robust)이 값을 한다.

전환이 늦게 도착하는 것도 이 무대에서 더 아프다. 포스트백(전환을 알려 주는 서버 호출)을 거쳐 오는 사이 일부는 안 들어온다. 그러면 값이 낮게 나와 멀쩡한 캠페인을 중단하게 된다([지연 피드백](post.html?id=online-learning-delayed-feedback)).

어느 무대든 결론은 같다. 로그 추정은 A/B 예산을 아끼는 도구이고, 배포 승인은 A/B가 낸 숫자로 결정한다.

## 한눈 정리와 헷갈리기 쉬운 점

추정치를 보고서에 올리기 전에 다섯 줄만 확인하면 된다. 하나라도 기준을 못 넘으면 그 숫자로는 배포를 결정하지 않는다.

| 점검 항목 | 이 로그의 값 | 기준 |
|---|---|---|
| 두 정책이 같은 광고를 고른 비율 | 25.9% | 10% 아래면 겹치는 건만 쓰기는 못 쓴다 |
| 가중치 합 대 요청 수 | 9,681 대 10,000 | 10% 넘게 어긋나면 로깅을 의심한다 |
| 가장 큰 가중치 | 80 | 후보 수를 탐색 비율로 나눈 값과 맞아야 한다 |
| 유효표본크기 | 339 (요청의 3.4%) | 1% 아래면 보고하지 않는다 |
| 유효표본크기로 환산한 클릭 | 9.5건 | 두 자리 아래면 순위 비교에만 쓴다 |

### 헷갈리기 쉬운 점

- **새 정책이 점수 1등만 고르는 것은 문제가 아니다.** 문제는 로그를 남긴 옛 정책이 그랬을 때다. 그러면 분모가 0 아니면 1이 되어 결정에 쓸 값이 안 나온다.
- **성향점수는 나중에 계산할 수 없다.** 그 순간의 모델과 탐색 설정이 있어야 나오는 값인데 모델은 매일 바뀐다. 로깅 결정이 평가 가능 여부를 가른다.
- **치우침이 없다는 말은 이번 추정치가 맞는다는 뜻이 아니다.** 이 글에서 한 주의 추정치는 진짜 값의 60% 수준이었다. 그 한 번으로 중단을 결정하면 안 된다.
- **겹친 건 수와 유효표본크기는 다르다.** 겹친 건 수만 보고 판단하면 클릭 열 번짜리 숫자로 배포를 결정하게 된다.
- **가중치 잘라내기는 공짜가 아니다.** 잘라 낸 몫이 어디에도 안 더해져 값이 내려가니, 그 비용을 알고 상한을 결정한다.
- **로그로 낸 추정치는 절대값으로 보고하지 않는다.** 광고주 보고와 정산 숫자는 온라인 실험에서 받는다.
