면접관이 화이트보드를 가리키며 말했다. "광고 추천 시스템을 설계해 보세요."

지훈은 곧장 그리기 시작했다. 카프카, 모델 서버, 레디스, 데이터베이스. 15분 뒤 화이트보드가 상자로 가득 찼을 때 면접관이 물었다. "응답 시간 예산이 얼마인가요?" 지훈은 정하지 않았다는 걸 그제야 알았다.

**설계를 시작하기 전에 무엇을 정해야 할까?**

숫자다. 초당 요청 몇 건, 응답 시간 몇 밀리초, 후보 광고 몇 개. 이 숫자가 없으면 어떤 상자를 그려도 맞는지 틀린지 말할 수 없다. 이 글은 광고 ML 시스템 설계 면접에서 반복되는 질문 스물두 개를 다룬다.

> **한 줄 요약:** 시스템 설계 면접은 상자를 많이 그리는 시합이 아니다. **숫자를 정하고, 그 숫자가 어디서 깨지는지 말하고, 깨졌을 때 뭘 할지 답하는** 것이 전부다.

> **골라 읽는 법** — 절이 열 개이고 절마다 질문 두세 개가 있습니다.
>
> - 시작하는 법과 숫자 잡기 → 첫째~셋째 절
> - 피처와 학습·서빙 불일치 → 넷째·다섯째 절
> - 배포와 감시 → 여섯째·일곱째 절
> - 장애와 규모 확장 → 여덟째·아홉째 절
> - 화이트보드에서 그리는 순서 → 마지막 절

## 1. 상자를 그리기 전에 숫자를 정한다

**Q. 광고 추천 시스템을 설계해 보세요.**

바로 그리면 안 된다. **먼저 되물어야 할 것이 네 가지 있다.**

| 물어볼 것 | 왜 필요한가 |
|---|---|
| 초당 요청이 몇 건인가 | 서버 대수와 저장소 종류가 여기서 갈린다 |
| 응답 시간 예산이 얼마인가 | 모델 크기와 피처 개수의 상한이다 |
| 후보 광고가 몇 개인가 | 전부 점수 매길지 추려낼지가 정해진다 |
| 실시간이어야 하나 | 미리 계산해 둘 수 있으면 문제가 완전히 달라진다 |

이 되묻기는 시간 끌기가 아니다. **네 숫자가 정해지면 설계의 절반이 정해진다.**

초당 만 건이고 예산이 100밀리초이며 후보가 십만 개라 하자. 십만 개에 전부 모델을 돌리면 100밀리초 안에 절대 안 끝난다. 그러니 **추려내기와 점수 매기기를 나눠야 한다**는 결론이 숫자에서 바로 나온다.

**답의 뼈대는 이렇게 잡는다.** 요구사항 확인 → 대략의 용량 계산 → 큰 그림 → 병목 하나를 골라 파고들기 → 감시와 장애 대응. 시간이 45분이면 앞의 셋에 15분, 파고들기에 20분, 나머지에 10분쯤이 적당하다.

**Q. 추려내기는 어떻게 하나요?**

세 가지를 섞어 쓴다. **규칙으로 거르고**(예산 소진, 타겟팅 조건, 소재 심사 상태) **색인으로 찾는다**(업종·지면별 미리 만든 목록). 남은 자리는 **임베딩으로 가까운 것을 뽑아** 채우는데, 근사 최근접 검색이 그것이다.

앞의 둘은 없으면 안 된다. 예산이 떨어진 광고를 점수 매기기까지 보내면 계산을 버리는 것이고, 심사 안 난 소재가 나가면 사고다.

## 3. 응답 시간 예산을 나눈다

**Q. 100밀리초 안에 답해야 합니다. 어떻게 나누시겠어요?**

**숫자를 실제로 적어서 나눈다.** 말로 "빠르게 하겠다"고 하면 답이 안 된다.

```python
예산 = 100                                    # 광고 응답 전체에 주어진 시간(ms)

단계 = [
    ("요청 파싱·검증",        2),
    ("후보 광고 가져오기",     12),
    ("피처 조회",             25),
    ("모델 추론",             18),
    ("입찰가 계산·경매",       8),
    ("응답 만들기",            3),
]
네트워크 = 15                                  # 앞뒤 왕복

쓴것 = sum(t for _, t in 단계) + 네트워크
print(f"{'단계':<20}{'ms':>6}{'누적':>8}{'남은 예산':>10}")
누적 = 네트워크
print(f"{'네트워크 왕복':<19}{네트워크:>6}{누적:>8}{예산-누적:>10}")
for 이름, t in 단계:
    누적 += t
    print(f"{이름:<19}{t:>6}{누적:>8}{예산-누적:>10}")

print(f"\n합계 {쓴것}ms · 예산 {예산}ms · 여유 {예산-쓴것}ms")
print(f"가장 큰 몫은 피처 조회 {단계[2][1]}ms 로 전체의 {단계[2][1]/쓴것:.0%} 다.")
print("\n같은 예산에서 모델을 두 배 무겁게 하려면(18 → 36ms)")
남는여유 = 예산 - (쓴것 + 18)
print(f"  여유가 {예산-쓴것}ms 에서 {남는여유}ms 가 된다 — {'가능' if 남는여유 >= 0 else '불가능, 다른 데서 줄여야 한다'}")
```

이 표를 그려 두면 뒤의 대화가 쉬워진다. **"모델을 더 크게 쓰면 되지 않나요"에 "예산이 −1밀리초가 됩니다"로 답할 수 있다.**

마지막 줄이 실무의 대화 방식이다. 무엇을 하려면 무엇을 줄여야 하는지가 숫자로 나오니, 논쟁이 취향 싸움이 안 된다.

**Q. 이 예산은 평균 기준인가요?**

아니다. **꼬리 기준이어야 한다.** 평균으로 잡으면 절반의 요청이 예산을 넘는다.

```python
import random, statistics

random.seed(3)

# 서버 한 대가 요청 하나를 처리하는 데 걸리는 시간(ms). 대부분 빠르고 가끔 느리다.
def 한건():
    return random.lognormvariate(2.7, 0.55)

표본 = sorted(한건() for _ in range(200_000))
def 분위(p): return 표본[int(len(표본) * p)]

평균 = statistics.mean(표본)
print(f"{'지표':<10}{'ms':>8}")
for 이름, p in (("중앙값", 0.50), ("p90", 0.90), ("p95", 0.95), ("p99", 0.99), ("p99.9", 0.999)):
    print(f"{이름:<10}{분위(p):>8.1f}")
print(f"{'평균':<10}{평균:>8.1f}")

print(f"\n중앙값은 {분위(0.5):.0f}ms 인데 p99 는 {분위(0.99):.0f}ms 로 {분위(0.99)/분위(0.5):.1f}배다.")
print("평균만 보면 느린 꼬리가 안 보인다.\n")

# 하나의 요청이 서버 여러 대를 거치면 꼬리가 커진다
print(f"{'거치는 서버 수':>14}{'하나라도 p99 를 넘을 확률':>26}")
for k in (1, 5, 10, 30):
    print(f"{k:>14}{1 - 0.99**k:>24.1%}")
print("\n서버 30대를 거치면 요청 넷 중 하나가 어딘가에서 p99 를 만난다.")
```

```

p90           30.2
p95           36.8
p99           53.2
p99.9         81.4
평균            17.3

중앙값은 15ms 인데 p99 는 53ms 로 3.6배다.
평균만 보면 느린 꼬리가 안 보인다.

      거치는 서버 수          하나라도 p99 를 넘을 확률
             1                    1.0%
             5                    4.9%
            10                    9.6%
            30                   26.0%

서버 30대를 거치면 요청 넷 중 하나가 어딘가에서 p99 를 만난다.
```

아래쪽 표가 이 질문의 핵심을 보여 준다. **서버 하나가 p99에서 느린 확률이 1%여도, 30대를 거치면 26%가 된다.** 마이크로서비스로 잘게 쪼갤수록 이 문제가 커진다.

**대응책은 세 가지다.** 병렬로 부를 수 있는 것은 병렬로 부르고, 각 호출에 타임아웃을 걸어 늦으면 기본값으로 넘어가고, 꼭 필요하지 않은 호출은 아예 뺀다.

## 4. 피처를 어디서 가져오나

**Q. 피처 조회가 25밀리초입니다. 어떻게 줄이시겠어요?**

먼저 **피처를 성격별로 나눠야** 답이 나온다.

| 종류 | 예 | 어디에 두나 | 갱신 |
|---|---|---|---|
| 요청에 들어 있는 것 | 지면, 기기, 시간 | 조회 없음 | 즉시 |
| 거의 안 바뀌는 것 | 광고 업종, 소재 크기 | 서버 메모리 | 하루 한 번 |
| 천천히 바뀌는 것 | 사용자 관심사, 통계 | 인메모리 저장소 | 시간 단위 |
| 빨리 바뀌는 것 | 최근 클릭, 노출 횟수 | 스트림 처리 결과 | 초 단위 |

**첫 두 줄로 옮길 수 있는 피처를 옮기는 것이 가장 큰 절감이다.** 조회를 아예 안 하는 것보다 빠른 방법은 없다.

옮길 수 없는 것은 묶어서 한 번에 가져온다. 사용자 피처 열 개를 열 번 조회하면 열 번의 왕복이지만, 한 열쇠에 묶어 두면 한 번이다. **왕복 횟수가 곧 시간이다.**

**Q. 피처 스토어가 꼭 필요한가요?**

작게 시작하면 필요 없다. 필요해지는 시점이 있는데, **같은 피처를 학습과 서빙에서 각각 계산하기 시작할 때**다.

두 곳에서 따로 계산하면 언젠가 반드시 어긋난다. 학습 쪽은 하루치 로그를 다 모아 정확히 세고, 서빙 쪽은 실시간 카운터라 몇 건이 빠진다. 그 작은 차이가 다음 절에서 다룰 문제를 만든다.

## 5. 학습·서빙 불일치

**Q. 오프라인 AUC는 0.78인데 배포하면 0.74가 나옵니다. 왜일까요?**

앞 편에서 다룬 데이터 누수가 아니라면, **같은 이름의 피처가 학습과 서빙에서 다른 값일 가능성이 높다.**

```python
import random, math, bisect

random.seed(42)
N = 100_000

# 사용자 최근 클릭 수라는 피처가 있다.
# 학습 때는 하루치 로그를 다 모아 정확히 세지만,
# 서빙 때는 실시간 카운터라 늦게 반영되거나 일부가 빠진다.
진짜카운트 = [max(0, int(random.expovariate(1/3))) for _ in range(N)]
클릭확률 = [min(0.4, 0.005 + 0.02 * c) for c in 진짜카운트]
라벨 = [1 if random.random() < p else 0 for p in 클릭확률]

학습피처 = 진짜카운트                              # 정확한 값
서빙피처 = [0 if random.random() < 0.10 else max(0, c - 1) for c in 진짜카운트]

def 모델(c):                                   # 학습 데이터로 맞춘 아주 단순한 모델
    return min(0.4, 0.005 + 0.02 * c)

def auc(pred):
    양 = sorted(p for p, y in zip(pred, 라벨) if y == 1)
    음 = sorted(p for p, y in zip(pred, 라벨) if y == 0)
    합 = 0.0
    for p in 양:
        아래 = bisect.bisect_left(음, p); 같음 = bisect.bisect_right(음, p) - 아래
        합 += 아래 + 같음 / 2
    return 합 / (len(양) * len(음))

def copc(pred):
    return sum(라벨) / sum(pred)
```

이 마지막 문장이 실무의 해법이다. **서빙 시점의 피처를 그대로 로그에 남겨 그것으로 학습하면** 불일치가 원천적으로 사라진다. 저장 비용이 늘지만, 원인 모를 성능 하락을 쫓는 시간보다 싸다.

## 6. 모델 배포

**Q. 새 모델을 어떻게 배포하시겠어요?**

한 번에 다 바꾸지 않는다는 것부터 말한다. **단계는 넷이다.**

**첫째, 그림자 배포다.** 새 모델을 돌리되 결과를 쓰지 않는다. 응답 시간과 예측값 분포만 보는데, 이 단계에서 "너무 느리다"와 "값이 이상하다"의 대부분이 걸린다.

**둘째, 소량 트래픽이다.** 1%나 5%에만 새 모델을 쓴다. 앞 편의 실험 설계가 여기 그대로 적용된다.

**셋째, 점진 확대다.** 지표가 괜찮으면 5%에서 20%, 50%로 늘린다. 늘릴 때마다 앞 편에서 본 가드레일을 확인한다.

**넷째, 되돌릴 준비다.** 이전 모델을 즉시 되살릴 수 있어야 한다. 되돌리는 데 30분이 걸리면 그 30분 동안 사고가 계속된다.

**Q. 되돌리기를 어떻게 빠르게 하나요?**

**모델 배포와 코드 배포를 분리한다.** 모델 파일 경로만 설정으로 바꿔 되돌릴 수 있으면 몇 초면 된다. 모델이 코드에 묶여 있으면 코드 배포 절차를 다시 밟아야 해서 느리다.

한 가지 더 붙이면 좋은 말이 있다. **되돌리기를 실제로 해 본 적이 있어야 한다.** 평소에 안 써 본 되돌리기는 사고 때 안 된다.

## 7. 무엇을 감시하나

**Q. 배포 후에 뭘 보시겠어요?**

세 층으로 나눠 말하면 정리된다.

| 층 | 보는 것 | 이상하면 |
|---|---|---|
| 시스템 | p99 응답 시간, 오류율, 타임아웃 비율 | 즉시 되돌린다 |
| 모델 | 예측값 평균·분포, COPC, 피처 결측률 | 조사하고 판단한다 |
| 비즈니스 | 매출, 클릭률, 전환율, 예산 소진 속도 | 실험 결과로 판단한다 |

**가운데 층이 자주 빠진다.** 시스템은 멀쩡하고 비즈니스 지표는 며칠 뒤에야 움직이니, 그 사이의 조용한 고장을 잡는 것이 모델 층이다.

특히 **피처 결측률**을 꼭 넣어야 한다. 상류의 데이터 파이프라인이 조용히 멈추면 피처가 전부 기본값이 되는데, 시스템은 오류를 안 낸다. 모델은 계속 답을 하고, 그 답이 점점 나빠진다.

**Q. 예측값 분포를 본다는 게 무슨 뜻인가요?**

어제와 오늘의 예측값 히스토그램을 겹쳐 보는 것이다. **모양이 갑자기 바뀌면 무언가 잘못된 것이다.**

평균만 보면 안 잡히는 것이 잡힌다. 절반이 0.001로, 나머지 절반이 0.05로 몰려도 평균은 어제와 같을 수 있다. 분포를 보면 두 봉우리가 생긴 것이 보인다.

## 8. 장애가 났을 때

**Q. 피처 저장소가 응답을 안 합니다. 어떻게 하시겠어요?**

**답하기 전에 정해 둬야 할 것이 있다 — 광고를 안 내보내는 것과 나쁜 광고를 내보내는 것 중 무엇이 더 나쁜가.**

광고는 대체로 "안 내보내는 것"이 더 나쁘다. 지면이 비면 수익이 0이고 사용자 경험도 이상하다. 그래서 **성능을 낮춰서라도 응답하는 쪽**을 택한다.

단계별로 말하면 이렇다. 먼저 타임아웃을 짧게 걸어 빨리 포기하는 것이 시작이다. 그다음 캐시에 남은 값을 쓰고, 그것도 없으면 기본값으로 모델을 돌린다. 모델까지 안 되면 **미리 만들어 둔 인기 광고 목록**을 내보낸다.

이 마지막 단계까지 말해야 답이 완성된다. **어떤 상황에서도 응답할 수 있는 가장 단순한 경로를 하나 준비해 두는 것**이 설계의 일부다.

**Q. 반대로, 이상한 값을 내보내는 게 더 나쁜 경우도 있지 않나요?**

있다. 그래서 **출력에 상한을 건다.** 예측 확률이 어떤 값을 넘으면 잘라 내고, 입찰가가 하루 예산의 일정 비율을 넘으면 막는다.

이런 장치를 서킷 브레이커라 부르는데, 요점은 **모델을 믿지 않는 층을 하나 두는 것**이다. 모델이 아무리 좋아도 데이터 사고 한 번이면 이상한 값을 낸다.

:::deep 캐시를 어디에 둘 것인가 — 세 층과 각각의 함정

응답 시간을 줄이는 가장 흔한 답이 캐시인데, 어디에 두느냐로 성격이 완전히 달라진다.

**서버 메모리 캐시**가 가장 빠르고 조회가 사실상 공짜다. 대신 서버마다 내용이 다르고, 배포할 때마다 비워진다. 배포 직후 잠깐 느려지는 현상이 여기서 오니, 거의 안 바뀌는 것만 넣는다.

**공용 인메모리 저장소**는 모든 서버가 같은 값을 보는 대신 네트워크 왕복이 한 번 든다. 사용자 피처처럼 서버마다 같아야 하는 것을 넣는다.

**미리 계산해 둔 결과**는 캐시라기보다 다른 설계다. 사용자별 추천 목록을 밤에 만들어 두면 요청 시점에는 읽기만 하면 된다. 실시간성이 필요 없는 자리에서는 가장 싸다.

발목을 잡는 지점도 층마다 다르다. 서버 메모리 캐시는 **일관성이 없다** — 같은 사용자가 서버마다 다른 답을 받는다. 공용 저장소는 **그것이 죽으면 전부 죽는다.** 미리 계산은 **새 광고나 새 사용자를 못 다룬다.**

면접에서 "캐시를 쓰겠습니다"만 말하면 부족하다. **"어느 층에, 무엇을, 얼마나 오래 두고, 안 맞을 때 어떻게 되나"까지 말해야 답이 된다.** 특히 마지막이 중요한데, 캐시가 오래된 값을 주는 상황을 허용할지 말지가 곧 설계 결정이기 때문이다.
:::

## 9. 규모가 열 배가 되면

**Q. 트래픽이 열 배가 됐습니다. 무엇부터 깨질까요?**

**먼저 무엇이 선형으로 늘고 무엇이 안 그런지를 나눈다.**

서버 대수는 대체로 선형이다. 요청이 열 배면 서버도 열 배 늘리면 된다. 이렇게 늘릴 수 있는 부분은 애초에 병목이 아니다.

**안 늘어나는 것이 병목이다.** 데이터베이스 한 대에 다 몰려 있으면 서버를 늘려도 그 한 대가 못 버틴다. 3절 아래쪽 표에서 본 꼬리 문제도 여기서 심해진다.

순서를 정해 답하면 정리돼 들린다. **먼저 상태 없는 것을 늘리고, 그다음 읽기를 나누고, 그다음 쓰기를 나눈다.** 읽기는 복제본을 늘리면 되니 쉽고, 쓰기를 나누는 것은 어렵다.

**Q. 모델 서버가 병목이면요?**

세 갈래로 나눠 말한다.

**계산을 줄이는 방법**을 먼저 본다. 모델을 작게 만들거나, 양자화하거나, 후보를 더 일찍 추려낸다. 앞 편들에서 본 것처럼 **점수 매길 후보를 천 개에서 오백 개로 줄이면 그 자체로 절반**이다.

**한 번에 여러 개를 처리하는 방법**이 그다음이다. 요청을 조금 모아서 한 번에 추론하면 처리량이 크게 는다. 대신 모으는 동안 기다려야 하니 지연이 는다. **처리량과 지연의 맞바꿈**이고, 예산에 여유가 있을 때만 쓴다.

**미리 계산하는 방법**이 마지막 갈래다. 자주 나오는 조합을 미리 계산해 두면 요청 시점 비용이 0이 된다. 다만 조합이 폭발하지 않는 자리에서만 통한다.

## 10. 화이트보드에서 그리는 순서

**설계 면접에서 지는 가장 흔한 방식은 상자를 너무 빨리 그리는 것이다.**

지훈이 그랬다. 15분 동안 상자를 채웠는데 그 상자들이 어떤 숫자를 만족시키는지 아무도 몰랐다. 그리는 순서를 정해 두면 이런 일이 안 생긴다.

**먼저 요구사항을 적는다.** 왼쪽 위 구석에 초당 요청, 응답 예산, 후보 개수, 데이터 크기를 적어 둔다. 이 숫자를 계속 가리키면서 설명하면 논리가 이어진다.

**그다음 가장 단순한 것을 그린다.** 요청 → 모델 → 응답 세 상자면 충분하다. 여기서 시작해 "이러면 뭐가 안 되죠?"를 스스로 묻고 하나씩 고쳐 나간다. **처음부터 완성된 그림을 그리면 왜 그렇게 됐는지를 설명할 기회가 없다.**

**그다음 병목 하나를 골라 파고든다.** 전부 얕게 다루면 어느 것도 인상에 안 남는다. 피처 조회를 골랐다면 저장소 선택, 자료 구조, 캐시 층, 장애 대응까지 끝까지 간다.

**마지막으로 감시와 장애를 말한다.** 시간이 부족해도 이건 한 문장씩이라도 말해야 한다. 여기까지 오는 지원자가 많지 않아서 오히려 눈에 띈다.

반대로 하지 말아야 할 것도 분명하다. 들어 본 기술 이름을 나열하는 것, 요구사항을 안 묻고 그리는 것, "이건 나중에 최적화하면 됩니다"로 넘기는 것이다. 마지막은 특히 조심해야 하는데, **무엇을 나중으로 미루는지 그 판단 자체가 질문의 내용**인 경우가 많다.

## 헷갈리기 쉬운 점

- **숫자를 안 정하고 그리지 마라.** 초당 요청과 응답 예산이 없으면 어떤 설계도 평가할 수 없다.
- **추려내기와 점수 매기기를 안 나누지 마라.** 후보 십만 개에 무거운 모델을 돌리는 설계는 그 자리에서 탈락한다.
- **평균 응답 시간으로 예산을 잡지 마라.** 꼬리가 3.6배이고, 서버를 거칠수록 그 꼬리를 만날 확률이 는다.
- **같은 피처를 두 곳에서 계산하지 마라.** 모델을 안 바꿔도 AUC가 0.78에서 0.74로 떨어진다.
- **되돌리기를 설계에 안 넣지 마라.** 되돌리는 데 30분 걸리면 사고가 30분 계속된다.
- **모델 층 감시를 빼먹지 마라.** 시스템은 멀쩡하고 비즈니스 지표는 늦게 움직인다.
- **"캐시를 쓰겠습니다"로 끝내지 마라.** 어느 층에 얼마나 오래 두고 안 맞을 때 어떻게 되는지까지 말한다.
- **"나중에 최적화하면 됩니다"로 넘기지 마라.** 무엇을 미루는지가 질문의 내용일 때가 많다.
