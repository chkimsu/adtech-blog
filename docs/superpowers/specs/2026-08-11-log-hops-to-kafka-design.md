## 왜 이 글인가 — 지금 블로그에 있는 것

`kafka-log-pipeline`(2026-08-07)이 시작하는 자리는 **이미 JSON 한 줄이 `bidder` 안에 만들어져 있는 상태**다. 그 줄이 화면에서 어떻게 생겨나 여기까지 왔는지는 도입부 한 문장으로 지나간다.

| 글 | 로그 수집 계층을 어디까지 다루나 |
|---|---|
| `kafka-log-pipeline` | `producer.send()` 이후만. 그 앞은 "매체가 `log-collector` 로 보낸다" 한 문장 |
| `ad-log-system` 7절 | 수집 계층을 5문단. 재전송·멱등키·저장소 3단. **데이터를 한 번도 안 보여 준다** |
| `ad-log-pipeline` | 로그 10종이 각각 왜 남는지. 볼륨과 통과율. 홉은 안 다룸 |

세 편 어디에도 **"수집기 안의 데이터가 실제로 어떻게 생겼나"** 가 없다. 이 글이 그 빈칸을 채운다.

## 기존 Kafka 글과의 접합 — 수정 0

`kafka-log-pipeline` 7절에 이미 이렇게 박혀 있다.

> `ad.impression` 은 `bidder` 가 넣고 `ad.click` 은 매체를 거쳐 `log-collector` 가 넣는다(도입).

새 글은 뒤쪽 문장 하나를 펼치는 글이다. **주인공을 클릭으로 잡으면 기존 글을 한 글자도 안 고쳐도 된다.**

노출을 주인공으로 잡았으면 문제가 생겼다. 기존 글 2절은 `pctr`·`bid` 가 든 노출 줄을 `bidder` 가 `ad.impression` 에 넣는다고 쓴다. 클라이언트에서 오는 노출 확인은 그 줄에 없는 정보라서, 노출을 따라가면 topic 을 새로 만들거나 기존 글 3절("topic 을 셋으로 나눈다")을 고쳐야 했다. 클릭은 그 충돌이 없다.

### 이어받는 값 (전부 기존 글에서 가져온다)

| 값 | 기존 글 출처 |
|---|---|
| `req_id` `r-8f21`, `ad_id` 9931, `slot` `main_top`, `media` `A앱` | 도입·2절 |
| 노출 시각 `ts=1786000101` = 2026-08-06 16:08:21 KST | 도입 |
| 클릭 시각 `click_ts=1786002501` = 2026-08-06 16:48:21 KST (40분 뒤) | 7절 |
| `ad.click` 하루 228만 줄 (초당 26.4건) | 7절 표 |
| `ad.impression` 하루 2억 2,800만 줄 (초당 2,639건) | 1절 |
| partition 12개, key `req_id` | 3절 |
| 보존 7일 | 6절 |
| 조인 창 3시간 | 7절 |
| `bid` 182.4 | 도입 |
| 끝나는 줄 `{"req_id":"r-8f21","ad_id":9931,"slot":"main_top","media":"A앱","bid":182.4,"y":1}` | 7절 |

수집 서버가 받는 총량은 두 종류를 합친다. 노출 확인 2억 2,800만 + 클릭 228만 = 하루 2억 3,028만, **초당 2,665건**.

글의 마지막 문장은 "이 글이 따라온 한 건이 저 `y:1` 이다"가 된다.

## 홉별 실물 데이터

아래 값은 전부 가상이다. 본문에도 그렇게 밝힌다. **바이트 수는 파이썬 예제 2를 실제로 실행한 출력에서 가져온다.** 이 스펙의 바이트 수는 설계 의도이고, 실행값과 다르면 실행값을 따른다.

### 1절 — 앱 SDK 메모리 큐

```
ClickEvent(t="clk", rid="r-8f21", ad=9931, s="main_top",
           ts=1786002501234, seq=47, tz=540, sdk="3.2.1")
```

- `seq` 는 앱 실행 후 몇 번째 이벤트인지. `rid` 와 합쳐 멱등키가 된다
- 머무는 시간: **노출은 0~5초, 클릭은 0초**
- 클릭만 즉시 보내는 이유: 탭하면 랜딩 페이지로 넘어가고 앱이 백그라운드로 간다. 묶어 두면 못 보낸다. 노출은 10건 차거나 5초 지나면 보낸다
- 오프라인이면 디스크 큐에 넣고 다음 실행 때 보낸다 → 며칠 늦게 도착하는 로그의 첫 원인

여기가 "저장이냐 즉시냐"의 첫 답이다. **이벤트 종류마다 다르다.**

### 2절 — HTTP 요청 한 번

```
POST /v1/e HTTP/1.1
Host: log.adsvc.example
Content-Type: application/json
User-Agent: MyApp/3.2.1 (iPhone; iOS 19.2)

{"t":"clk","rid":"r-8f21","ad":9931,"s":"main_top","ts":1786002501234,"seq":47}
```

응답은 `HTTP/1.1 204 No Content`. 본문이 없어야 모바일 데이터와 지연이 준다.

GET 픽셀 방식과 POST 배치 방식을 표로 대비한다.

| | GET 픽셀 (`<img src="…/imp?rid=…">`) | POST 배치 |
|---|---|---|
| 어디서 쓰나 | 웹, 서드파티 지면, 앱 종료 직전 | 앱 SDK |
| 한 번에 | 1건 | 여러 건 |
| 길이 제한 | URL 길이(실무상 2KB 안팎) | 없다시피 |
| 앱이 죽어도 | 브라우저가 마저 보낸다 | 안 간다 |

재시도 규칙: 2초 안에 204 를 못 받으면 다시 보낸다. **재전송이 있는 곳에는 중복이 있다.** 멱등키 `rid`+`seq` 는 보내는 쪽이 만든다. 받는 쪽이 붙이면 재전송마다 새 키가 생겨 중복 제거가 불가능하다. (`ad-log-system` 7절과 이어짐)

왕복 168ms → `collect_ts` = 16:48:21.402.

### 3절 — 수집 서버가 받는 것

nginx `log_format` 설정을 그대로 보인다.

```
log_format collect '$remote_addr $time_iso8601 $request_method $uri $status '
                   '$request_time "$http_user_agent" $request_body';
```

찍히는 한 줄:

```
10.2.31.7 2026-08-06T16:48:21+09:00 POST /v1/e 204 0.002 "MyApp/3.2.1 (iPhone; iOS 19.2)" {"t":"clk","rid":"r-8f21","ad":9931,"s":"main_top","ts":1786002501234,"seq":47}
```

**이 절의 핵심 문장:** 이 시점의 데이터에는 타입이 없다. `9931` 은 숫자가 아니라 글자 넷이고 `204` 도 글자 셋이다. 숫자로 쓰려면 누군가 바꿔야 하는데, 그 자리가 6절이다.

유실 지점 하나를 짚는다. `access_log … buffer=32k` 를 주면 32KB 씩 묶어 쓴다. 디스크 쓰기는 줄지만 프로세스가 죽으면 그 버퍼가 사라진다. 버퍼 32KB ÷ 한 줄 190 B ≈ 172줄이다.

### 4절 — 파일이냐 직행이냐

이 글의 하이라이트 절. `kafka-log-pipeline` 1절 ②가 "파일에 쓰고 나중에 옮긴다"를 유실 사례로 깠으므로, **왜 그럼에도 현장이 파일을 거치는지**에 정면으로 답해야 한다. 기존 글은 5분 배치 이동을 깠고, 같은 절에서 "파일을 계속 따라 읽는 에이전트를 붙이면 5분이 몇 초로 줄어든다. 맞다"고 이미 인정했다. 이 글은 그 지점에서 이어받는다.

| | 파일 경유 | 프로세스 안 producer 직행 |
|---|---|---|
| 홉 수 | 3 (파일 → 에이전트 → Kafka) | 1 |
| Kafka 도달까지 | 0.2~1초 | 5~50ms |
| Kafka 가 멈추면 버티는 시간 | 디스크 100GB → **약 55시간** | 메모리 512MB → **약 17분** |
| 수집 서버가 죽으면 | 파일은 남는다. 안 읽은 끝부분만 늦어진다 | 버퍼가 사라진다 |
| 인스턴스가 사라지면 | 파일도 같이 사라진다 | 같음 |
| 디스크가 차면 | 쓰기 실패가 요청 처리까지 흔든다 | 영향 없다 |
| 배포 | 수집 서버와 전송 로직을 따로 배포 | 같이 배포 |
| 언어 | 무관 | Kafka 클라이언트가 있는 언어여야 |

버티는 시간 계산: 초당 2,665건 × 190 B ≈ 506 KB/s. 100GB ÷ 506 KB/s ≈ 55시간. 512MB ÷ 506 KB/s ≈ 17분.

이 절의 네 값은 하나에 물려 있다 — **한 줄 바이트 수 → 초당 KB → 버티는 시간 두 개.** 예제 2가 한 줄 바이트를 실제로 세면 나머지 셋을 함께 갱신한다. 스펙에 적힌 190 B · 506 KB/s · 55시간 · 17분은 설계 의도이고 실행값이 이긴다.

**우리 답은 파일 경유다.** 근거는 버티는 시간 하나다. 대신 홉이 둘 늘고 Kafka 도달이 0.2~1초로 늘어난다는 것을 받는다. 대시보드가 몇 초 안에 숫자를 올려야 하는데(기존 글 1절) 1초를 여기서 쓴다.

정직하게 적을 것: **직행이 틀린 것이 아니다.** 지연이 밀리초 단위로 중요한 곳, 디스크가 없는 컨테이너 환경, 언어가 이미 맞는 곳은 직행이 낫다. 판정 기준은 "Kafka 가 30분 멈춰도 되나"다.

### 5절 — 수집 에이전트

Fluent Bit 설정을 그대로 보인다.

```
[INPUT]
    Name              tail
    Path              /var/log/collect/e-*.log
    DB                /var/lib/fluent-bit/pos.db
    Refresh_Interval  1
    Parser            collect_v1
[OUTPUT]
    Name              kafka
    Match             *
    Brokers           kafka-01:9092,kafka-02:9092
    Topics            ad.click
```

파싱 결과(에이전트 안의 레코드) — **여전히 전부 문자열이다.**

```json
{"remote":"10.2.31.7","ts":"2026-08-06T16:48:21+09:00","method":"POST",
 "uri":"/v1/e","status":"204","rt":"0.002",
 "agent":"MyApp/3.2.1 (iPhone; iOS 19.2)",
 "body":"{\"t\":\"clk\",\"rid\":\"r-8f21\",\"ad\":9931,\"s\":\"main_top\",\"ts\":1786002501234,\"seq\":47}"}
```

`"204"` 가 따옴표 안이라는 것을 짚는다. `body` 는 아직 통째로 문자열 하나다.

위치 파일 `pos.db` 의 내용:

```
/var/log/collect/e-2026080616.log   inode=8391204   offset=48,271,104
```

**offset 의 예고편이 여기다.** "어디까지 읽었나"를 적어 두는 물건이 Kafka 이전에도 있다. 다른 점은 있는 자리다 — Kafka offset 은 브로커에 있고 이건 에이전트 로컬 디스크에 있다. 인스턴스가 사라지면 이 파일도 사라진다.

로테이션 함정을 한 문단. 파일이 `e-2026080616.log` → `e-2026080617.log` 로 바뀔 때 inode 가 바뀐다. 에이전트가 옛 파일의 끝을 다 읽기 전에 파일이 지워지면 그만큼이 안 간다.

머무는 시간: `Refresh_Interval 1` 이면 0.2~1초.

### 6절 — 변환

다섯 가지 작업이 일어난다.

| 작업 | 이 줄에서 무슨 일이 | 결과 |
|---|---|---|
| 쪼개기 | `body` 문자열을 JSON 으로 파싱 | 필드 1개 → 6개 |
| 타입 붙이기 | 문자열을 숫자로 | `"9931"` → `9931` |
| 보강 | 밖에서 값을 가져와 붙임 | UA → `os`·`os_ver`·`device`·`app_ver` / IP → `region` / `ad_id` → `campaign_id`·`advertiser_id` |
| 지우기 | 남기면 안 되는 것 | `remote_ip` 삭제, 광고 식별자는 해시 |
| 검증 | 스키마에 안 맞으면 따로 뺌 | `event_ts` 가 미래면 dead-letter topic 으로 |

변환 뒤 (17필드):

```json
{"req_id":"r-8f21","event":"click","ad_id":9931,"slot":"main_top","media":"A앱",
 "campaign_id":5502,"advertiser_id":311,
 "os":"iOS","os_ver":"19.2","device":"iPhone","app_ver":"3.2.1",
 "region":"KR-11","seq":47,
 "event_ts":1786002501234,"collect_ts":1786002501402,"process_ts":1786002502310,
 "schema":"click.v3"}
```

**시각이 하나에서 셋이 되는 것을 별도 표로 다룬다.**

| 이름 | 값 | 누가 찍나 | 믿을 수 있나 |
|---|---|---|---|
| `event_ts` | 16:48:21.234 | 기기 | 기기 시계가 틀리면 틀린다 |
| `collect_ts` | 16:48:21.402 | 수집 서버 | 서버 시계라 믿을 수 있다 |
| `process_ts` | 16:48:22.310 | 변환기 | 재처리하면 값이 바뀐다 |

셋을 어디에 쓰는지가 실무의 갈림길이다. 저장소 파티션(`dt=`·`hour=`)은 `collect_ts` 로 자르고, 조인 창 3시간(기존 글 7절)은 `event_ts` 로 잰다. 섞으면 하루치가 새거나 겹친다. 9절 지뢰로도 다시 나온다.

보강이 밖을 부른다는 것도 짚는다. `ad_id` → `campaign_id` 조회는 다른 저장소를 읽는 일이다. 그 저장소가 느려지면 변환이 밀리고, 그 밀림이 5절 파일에 쌓인다.

### 7절 — Kafka 안을 바이트로 본다

producer 에 넘기는 것:

```
topic      ad.click
key        b'r-8f21'                              6 B
value      b'{"req_id":"r-8f21","ad_id":9931,…}'  약 300 B
headers    [('schema', b'click.v3'), ('src', b'collector-07')]
```

브로커에 붙은 뒤 생기는 것:

```
partition 5      ← hash(b'r-8f21') % 12   (기존 글 3절)
offset    8412
timestamp 1786002502310   type=CREATE_TIME
```

console consumer 로 꺼내 보기 (JSON):

```
$ kafka-console-consumer --topic ad.click --partition 5 --offset 8412 \
    --max-messages 1 --property print.key=true --property print.offset=true
Offset:8412	r-8f21	{"req_id":"r-8f21","ad_id":9931,"slot":"main_top",…}
```

같은 줄을 Avro 로 바꾸면:

```
Offset:8412	r-8f21	\x00\x00\x00\x00\x11\x0cr-8f21\xa6\x9b\x01\x10main_top…
```

바이트 해부:

| 위치 | 바이트 | 무엇 |
|---|---|---|
| 0 | `\x00` | 매직 — 이 뒤가 스키마 번호라는 표시 |
| 1~4 | `\x00\x00\x00\x11` | 스키마 번호 17 (big-endian) |
| 5~ | `\x0c` `r-8f21` … | 길이 6 + 값. 필드 이름이 없다 |

**필드 이름이 통째로 빠지는 것이 크기 차이의 대부분이다.** 그래서 안 읽힌다. 스키마 레지스트리에 번호 17로 등록된 정의를 붙여야 이름이 돌아온다.

크기·볼륨 비교는 파이썬 예제 2의 출력을 그대로 싣는다.

**"바로바로 consuming 해가나"에 답하는 표** — 절 끝에 놓는다.

| group | 읽는 방식 | 이 클릭을 보는 시각 | 탭한 때(16:48:21)부터 |
|---|---|---|---|
| 대시보드 | poll 루프가 계속 돈다 | 16:48:23 | 약 2초 |
| 정산 | 계속 | 16:48:25 | 약 4초 |
| 학습 | 하루 한 번, 다음 날 03:00 | 8월 7일 03:00 | 약 10시간 |

같은 줄을 누구는 2초 뒤에, 누구는 10시간 뒤에 읽는다. **그래서 보존 7일이 필요하다.** 기존 글 6절과 여기서 이어진다.

데모 iframe 을 이 절에 넣는다.

### 8절 — consume 한 쪽이 받는 것

`poll()` 이 돌려주는 것은 값이 아니라 봉투째다.

```python
ConsumerRecord(
    topic='ad.click', partition=5, offset=8412,
    timestamp=1786002502310, timestamp_type=0,
    key=b'r-8f21',
    value=b'{"req_id":"r-8f21","ad_id":9931,…}',
    headers=[('schema', b'click.v3'), ('src', b'collector-07')],
    serialized_key_size=6, serialized_value_size=300,
)
```

값은 `value` 하나뿐이고 나머지는 브로커가 붙인 꼬리표다. `offset` 은 보내는 쪽이 만든 적 없는 값이라는 것을 짚는다.

이 뒤의 두 갈래:

| 갈래 | 하는 일 | 결과 모양 |
|---|---|---|
| 그대로 쌓기 | 시간 파티션으로 S3 에 쓴다 | `s3://adlog/ad.click/dt=2026-08-06/hour=16/part-00005-….parquet` |
| 조인해서 라벨 만들기 | 노출 LEFT JOIN 클릭, 창 3시간 | 학습 한 줄 |

Parquet 은 줄이 아니라 열로 눕는다. 같은 필드의 값이 모여서 압축이 잘 되고, 한 건당 크기가 JSON 300 B 에서 41 B 로 준다. 그리고 학습이 `req_id` 열만 읽을 때 나머지 열을 안 읽는다.

마지막 줄:

```json
{"req_id":"r-8f21","ad_id":9931,"slot":"main_top","media":"A앱","bid":182.4,"y":1}
```

**"이 글이 따라온 한 건이 저 `y:1` 이다."** 기존 글 7절이 시작하는 자리다.

### 9절 — 전체 지도 + 자주 밟는 것

9홉을 한 표로 쌓는다. 열은 `# / 어디 / 무슨 모양 / 크기 / 머무는 시간 / 여기서 죽으면 사라지는 것`.

총합 두 줄:
- 탭 → Kafka 도달: **약 1.1초** (16:48:21.234 → 22.310)
- 탭 → 학습 데이터: **약 10시간** (다음 날 03:00)

지뢰 5개:

1. **"수집기가 로그를 만든다"** — 아니다. 만드는 것은 SDK고 수집기는 받아 적는다. 수집기에 안 보이면 애초에 안 왔을 수 있다. 그 구간은 수집기 그래프에 안 잡힌다
2. **수집기 단계에서 숫자로 보이는 것은 전부 문자열이다** — 타입은 6절에서 처음 생긴다. 여기서 집계하면 문자열 비교가 된다
3. **시각 셋을 섞지 마라** — 파티션은 `collect_ts`, 조인 창은 `event_ts`. 섞으면 하루치가 새거나 겹친다
4. **재전송이 있으면 중복이 있다** — 멱등키는 보내는 쪽이 만든다. 받는 쪽이 붙이면 재전송마다 새 키가 생긴다
5. **파일 경유 홉의 유실은 그래프에 안 잡힌다** — `pos.db` 가 남아 있으면 늦게라도 온다. 인스턴스가 사라지면 안 온다. 평균값 그래프로는 안 보이고 축소 시각에 맞춰 봐야 보인다
