이벤트 한 건 따라가기 기록

노트북 한 대에 Kafka, 처리기, Redis, API 를 띄우고 이벤트를 보내며 응답을 기록해 두었습니다. 이 페이지는 그 기록을 시간 순서대로 다시 그립니다. 숫자는 지어낸 값이 아니라 그때 받은 응답 그대로입니다. 운영 서버가 아니라 노트북에서 잰 값이므로 ms 의 크기보다 어느 자리가 큰지를 봅니다.

파랑 = 지나간 자리, 읽고 커밋한 메시지 벽돌색 = 기다리는 중 (hold, 아직 안 읽은 메시지) 회색 = 아직 오지 않은 자리

1이벤트 한 건이 다섯 자리를 지나는 2초

사용자 u42 가 영상 v7 을 START, PLAY, PAUSE, PLAY, END 순서로 봤습니다. 다섯 건을 하나씩 보냈고, 건마다 Kafka 의 자리, 처리기의 적용 기록, Redis 의 값, API 응답을 따라가 기록했습니다.

+0ms

    1번과 2번 자리는 몇 ms 안에 끝납니다. 걸리는 시간은 거의 다 3번 자리의 hold 2초입니다. 처리기는 받은 이벤트를 2초 들고 있다가 이벤트 시각 순서로 정렬해 적용합니다. 4번의 시각은 0.25초마다 Redis 를 읽다가 바뀐 값을 본 때라 적용 시각보다 조금 늦습니다. 기록할 때는 보내기 전 값을 같이 받으려고 POST /events 와 같은 길로 보내는 /trace/send 를 썼습니다.

    2처리기를 12초 멈추면 이벤트는 Kafka 에 쌓였다가 한꺼번에 적용됩니다

    초당 40건을 28초 동안 보냈습니다. 6초에 처리기를 멈추고 18초에 다시 켰습니다. 0.5초마다 파티션 넷의 끝 자리와 커밋 자리, lag, 영상 v11 의 누적 재생 초를 읽었습니다.

    처리기 도는 중 0.0초 / 28초
    lag, 아직 안 읽은 메시지 수영상 v11 의 누적 재생 초

    평소에도 lag 이 80 인 것은 처리기가 2초씩 들고 있어서입니다. 초당 40건 × 2초입니다. 멈춘 직후 2초는 처리기가 이미 읽어 둔 80건을 마저 적용해 lag 이 그대로입니다. 그 뒤로 lag 은 1초에 40씩 늘어 552 까지 갔고, 영상 v11 의 누적 재생 초는 25 에서 멈췄습니다. 다시 켜고 2초 뒤 쌓인 것이 한꺼번에 적용돼 lag 은 80 으로 돌아왔고, 누적 재생 초는 75 로 따라잡았습니다. 보낸 이벤트는 사라지지 않았고 늦게 적용됐을 뿐입니다.

    3읽는 길은 ms 단위입니다. 추천 요청 한 건의 5.2ms

    같은 실습 환경에서 추천 요청 한 건이 지나는 구간 열 곳을 50번 재고, 구간마다 가운데 값을 냈습니다. Redis 를 다섯 구간에서 읽고, 피처 행렬을 만들고, 모델 서버를 한 번 부르고, 응답을 만듭니다.

    CPU 가 일한 구간다른 서버의 답을 기다린 구간

    열 구간의 합은 5.2ms 이고 그중 CPU 가 일한 시간은 1ms 도 안 됩니다. 나머지는 Redis 와 모델 서버의 답을 기다린 시간입니다. 모델 서버 한 번이 거의 4분의 3 입니다. 그 안에는 네트워크 왕복, 모델 서버가 요청을 모아 한 번에 계산하려고 기다리는 시간, 그쪽 계산이 다 들어 있습니다. 막대나 표의 줄을 누르면 위 해설 칸에 그 구간 이야기가 나옵니다.

    현업에서는 이렇게 씁니다

    • 「피처가 늦다」는 문의가 오면 lag 부터 봅니다. 처리기가 멈췄거나 느려졌으면 lag 이 자랍니다. lag 이 평소 값이면 늦은 자리는 처리기 뒤쪽입니다.
    • 평소 lag 은 0 이 아닙니다. 초당 건수 × 들고 있는 시간만큼은 늘 남아 있습니다. 경보의 문턱을 그 값 위에 둡니다.
    • 처리기가 죽어도 이벤트는 Kafka 에 남습니다. 다시 켜면 커밋 자리부터 이어 읽습니다. 보관 기간 안이면 커밋 자리를 되돌려 처음부터 다시 셀 수도 있습니다.
    • 읽는 길과 쓰는 길은 단위가 다릅니다. 피처가 써지기까지는 초, 그 피처를 읽어 점수를 내기까지는 ms 입니다. 둘을 같은 예산으로 보지 않습니다.
    • 글로 이어 읽으려면 실시간 피처 파이프라인에 이 그림 셋이 절마다 들어 있습니다.
