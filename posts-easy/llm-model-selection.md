모델 팀 20주째 월요일, 지훈 씨는 선배에게서 모델 이름이 길게 적힌 목록을 받았습니다. 지난주 [LLM 호출 한 번](post.html?id=llm-first-call) 편에서 노트북의 모델에 요청 하나를 보내 본 다음입니다. 이름마다 만든 회사와 숫자 몇 개, 영어 낱말이 붙어 있었습니다.

선배는 광고주가 캠페인 화면에서 묻는 숫자 질문, 예를 들어 「하루 예산을 이 단가로 다 쓰면 전환이 몇 건인가」 같은 질문에 답할 모델을 고르라고 했습니다. 지훈 씨는 그런 문제 20개를 적어 노트북의 모델에 하나씩 물었고 그중 어려운 10개는 풀이를 먼저 쓰게 해서 한 번 더 물었습니다.

**모델은 이름 말고 무엇으로 비교하고 풀이를 먼저 쓰게 하면 무엇이 달라질까요?**

이름 옆에 붙은 회사와 숫자, 영어 낱말은 모델의 네 가지 특징을 말해 줍니다. 모델이 어디서 도는지, 얼마나 큰지, 한 번에 얼마나 긴 글을 읽는지, 답 앞에 풀이를 먼저 쓰는지입니다. 이 네 가지는 모두 요청 한 건에 드는 값과 답을 기다리는 시간을 바꿉니다. 다만 같은 모델도 어떤 문제를 받느냐에 따라 맞히는 수가 달라서 네 가지 옆에는 서비스가 답할 문제로 측정한 숫자를 함께 놓고 봅니다.

> **한 줄 요약:** 모델은 이름보다 네 가지로 고릅니다. 첫째는 어디서 도는지인데, 만든 회사의 서버로만 부르는 상용 API 인지 가중치(모델이 학습으로 얻은 숫자들)를 내려받아 직접 운영하는 서버에서 돌리는 공개 가중치인지를 봅니다. API 는 프로그램이 다른 프로그램의 기능을 부를 때 쓰는 정해진 요청의 꼴입니다. 나머지 세 가지는 크기, 한 번에 읽는 글의 상한인 컨텍스트 길이, 답 앞의 풀이입니다. 토큰은 모델이 글을 읽고 쓰는 조각입니다. 답 앞에 쓰는 풀이 토큰은 thinking 이라고 부르고 reasoning 도 같은 풀이를 가리킵니다. 풀이 토큰도 모델이 쓰는 출력 토큰이라 값을 냅니다. 광고 운영 숫자 문제 20개를 노트북의 qwen3.5:27b 에 물어 보니 두세 단계로 푸는 문제 10개는 thinking 을 끄면 4개만 맞혔고 켜면 10개를 모두 맞혔습니다. 다만 켰을 때는 출력 토큰이 92.9배로 늘었습니다. 가상 단가로 하루 100만 요청의 값을 세면 큰 모델은 780만 원으로 작은 모델 72만 원의 열 배가 넘습니다. 요청마다 같이 보내는 할 일 설명인 시스템 메시지를 캐시(앞 요청에서 계산해 둔 결과)에서 읽으면 큰 모델도 하루 420만 원으로 줄어듭니다.

> **골라 읽는 법** — 절이 7개입니다. 절마다 표나 코드나 카드가 있어서 그 부분만 보고 넘어가도 됩니다.
>
> - 모델 7개 계열을 네 가지 기준으로 나란히 놓은 표 → 1절
> - 메모리를 정하는 크기, 계산량을 정하는 활성 파라미터, 컨텍스트 길이 → 2절
> - thinking 을 켜고 끄는 API 별 필드와 풀이 토큰에 붙는 값 → 3절
> - 문제 20개를 thinking 을 끄고 켜서 물은 기록 → 4절
> - 요청 한 건과 하루 100만 건의 값, 캐시를 쓸 때의 값 → 5절
> - 지훈 씨가 고른 것과 그 근거가 된 숫자 → 6절
> - 담장 안과 열린 RTB 에서 모델을 부르는 자리 → 7절

이 글의 문제 20개와 5절의 단가, 요청 크기는 설명을 위해 만든 가상 데이터입니다. 모델 표에 적은 값은 각 회사의 공개 문서와 모델 카드에서 옮겼습니다. 모델 카드는 모델을 낸 곳이 크기와 쓰는 법을 적어 둔 문서입니다. 옮겨 온 값의 출처는 모두 참고문헌에 모았습니다. 반면 모델의 답과 토큰 수, 걸린 시간은 지어낸 값이 아니라 2026-11-05 에 이 블로그를 쓰는 맥에서 Ollama 0.40.11 로 qwen3.5:27b 를 띄워 기록한 값입니다. Ollama 는 공개된 모델을 개인 컴퓨터에서 돌리는 도구입니다. 기록은 `data/llm-records/llm-model-selection.json` 파일에 있습니다. 4절 블록의 두 상수 RECORD 와 USAGE 는 그 기록을 `--export-constant --with-usage` 로 찍은 줄 그대로입니다.

## 1. 모델 이름보다 먼저 보는 네 가지

**상용 API 3개 계열(Claude, GPT, Gemini)은 만든 회사의 서버로만 부르는 반면 공개 가중치 4개 계열(Qwen3.5, Llama 4, Gemma 4, DeepSeek-V4)은 직접 운영하는 서버에서도 돌립니다. 크기는 상용 3개 계열이 문서에 적지 않았고 공개 4개 계열은 모델 카드에 적었습니다. 컨텍스트 길이와 thinking 지원은 같은 계열 안에서도 모델마다 다릅니다.**

선배의 목록에는 이름마다 회사가 붙어 있었지만 같은 회사가 두 갈래(상용 API 와 공개 가중치)의 모델을 다 내기도 하므로, 회사 이름만으로는 모델이 어디서 도는지조차 알 수 없습니다. Google 만 해도 Gemini 는 API 로 열고 Gemma 는 가중치를 공개했습니다. 그래서 아래 표는 모델 7개 계열을 회사 대신 네 가지 기준으로 나란히 놓았습니다.

표의 7개 계열은 모두 LLM 입니다. LLM 은 글을 읽고 이어 쓰도록 학습한 큰 언어 모델을 말합니다. 상용 API 로 LLM 을 부르면 요청은 모델을 만든 회사의 서버에서 처리되고 요청에 담은 글도 그 서버로 가므로, 광고주의 자료를 요청에 담을 때는 이 점부터 확인합니다. Claude 는 Anthropic 이, GPT 는 OpenAI 가, Gemini 는 Google 이 이런 상용 API 로 엽니다.

공개 가중치 모델은 가중치 파일을 내려받아 직접 운영하는 서버나 노트북에서 돌리는 모델입니다. 지난 편에서 쓴 qwen3.5:27b 도 Ollama 로 가중치를 받아 이 블로그를 쓰는 맥에서 돌렸습니다. 이렇게 돌리면 요청이 그 컴퓨터 밖으로 나가지 않고 요청마다 내는 값도 없는 대신 모델을 올릴 메모리와 계산할 기계를 직접 마련합니다. Qwen 과 DeepSeek 은 가중치를 공개하는 한편 만든 회사의 API 로도 모델을 부를 수 있게 했습니다.

받은 가중치를 어디까지 써도 되는지는 라이선스가 정하는데, 라이선스는 모델을 낸 곳이 적어 둔 사용 조건입니다. 표의 「가중치를 받나」 칸에 라이선스 이름을 함께 적었습니다. Qwen3.5 와 Gemma 4 는 Apache 2.0, DeepSeek-V4 는 MIT 라이선스이고 Llama 4 는 Meta 가 따로 쓴 Llama 4 Community License 를 따릅니다. 서비스에 붙이기 전에는 그 라이선스의 원문을 읽습니다.

표의 크기 칸에는 파라미터 수를 적었습니다. 파라미터는 가중치를 이루는 숫자 하나하나입니다. 크기 칸의 B 는 10억을 뜻합니다. Qwen3.5 칸의 「35B 중 3B」는 파라미터 35B 를 모두 갖고 있지만 토큰 하나를 쓸 때는 그중 3B 만 계산한다는 뜻입니다. 이렇게 토큰 하나를 쓸 때 실제로 계산하는 파라미터를 활성 파라미터라고 부릅니다. 활성 파라미터가 어떻게 전체보다 작을 수 있는지는 2절에서 봅니다. 마지막 thinking 칸에는 답 앞의 풀이를 켜고 끌 수 있는지와 풀이의 양을 정하는 방법을 적었습니다.

컨텍스트 길이 칸의 숫자는 토큰 수로 적었습니다. 토큰은 모델이 글을 읽고 쓰는 조각입니다. 컨텍스트 길이는 모델이 한 번에 둘 수 있는 토큰 수의 상한을 말합니다. 표의 K 는 약 1,000, M 은 약 100만을 뜻합니다.

표를 위아래로 비교하면 두 갈래의 차이가 보입니다. 상용 3개 계열은 크기를 문서에 적지 않아서 크기 칸이 모두 「문서에 없음」입니다. 컨텍스트 길이는 세 계열 모두 100만 토큰 안팎으로 적었습니다. 공개 4개 계열은 크기와 활성 파라미터를 모델 카드에 적었습니다. 이 4개 계열의 컨텍스트 길이는 128K 에서 10M 까지 퍼져 있습니다. thinking 을 켜는 방법도 계열마다 다릅니다. 시스템 메시지는 요청마다 같이 보내는 할 일 설명인데, Gemma 4 는 이 시스템 메시지의 맨 앞에 `<|think|>` 표시를 넣어 thinking 을 켭니다. Llama 4 의 모델 카드에는 thinking 이야기가 아예 없습니다.

한 줄을 예로 들어 Gemma 4 를 왼쪽부터 읽으면 이렇습니다. Gemma 4 는 직접 운영하는 서버뿐 아니라 노트북과 휴대폰에서도 돌고 Apache 2.0 라이선스로 가중치를 받습니다. 크기는 다섯 가지인데 그 가운데 26B A4B 는 파라미터 25.2B 를 갖고도 토큰 하나에는 3.8B 만 계산합니다. 컨텍스트 길이는 E2B 와 E4B 가 128K 토큰이고 나머지 3개가 256K 토큰입니다.

모델을 고를 때도 회사 이름이 아니라 이 표의 칸을 하나씩 정합니다. 첫째 칸은 요청에 담을 글이 회사 밖으로 나가도 되는지로 정하고 나머지 칸은 2~4절의 숫자로 정합니다.

| 계열 | 어디서 도나 | 가중치를 받나 | 크기와 활성 파라미터 | 컨텍스트 길이 | thinking 지원 |
|---|---|---|---|---|---|
| Claude | Claude API, 클라우드 플랫폼 | 받지 않음 | 문서에 없음 | 지금 모델 4개 모두 1M 토큰 | 기본으로 켬, 끌 수 있는 것은 Claude Haiku 5.5, Sonnet 5.5 는 풀이 양이 high 단계 이하일 때 답 앞의 풀이만 끔 |
| GPT | OpenAI API | 받지 않음 | 문서에 없음 | 대표 모델 4개 모두 1.05M 토큰 | 풀이 양을 단계로 정함, 끄는 단계는 GPT-6.1 Terra, GPT-6 Luna 만 |
| Gemini | Gemini API | 받지 않음 | 문서에 없음 | Gemini 4 Argon 1,048,576 토큰 | 기본으로 켬, 양을 low 에서 high 로 정함 |
| Qwen3.5 | 직접 운영하는 서버, Alibaba Cloud API | 받음, Apache 2.0 | 27B, 35B 중 3B, 397B 중 17B | 262,144 토큰, 늘리면 1,010,000 | 기본으로 켬, 끌 수 있음 |
| Llama 4 | 직접 운영 | 받음, Llama 4 Community License | Scout 109B 중 17B, Maverick 400B 중 17B | Scout 10M, Maverick 1M 토큰 | 문서에 없음 |
| Gemma 4 | 직접 운영, 노트북, 휴대폰 | 받음, Apache 2.0 | E2B, E4B, 12B, 31B, 26B A4B 5개, 26B A4B 는 25.2B 중 3.8B | E2B, E4B 는 128K, 나머지 3개 256K 토큰 | 시스템 메시지 첫머리의 표시로 켬 |
| DeepSeek-V4 | 직접 운영, DeepSeek API | 받음, MIT | Flash 284B 중 13B, Pro 1.6T 중 49B | 1M 토큰 | Non-think, Think High, Think Max 3가지 |

카드에서는 상용 API 3개 계열과 공개 가중치 4개 계열이 어디서 돌고 문서에 무엇을 적었는지 나란히 보면 됩니다. 이 글의 카드 네 장에서 파랑은 thinking 을 끈 답, 벽돌색은 켠 답과 출력 토큰, 먹색은 모델과 서버, 회색은 문서에 없는 값이고 점선 상자는 가상 값입니다.

## 2. 크기, 활성 파라미터, 컨텍스트 길이

**모델의 크기(파라미터 수)는 가중치를 올릴 메모리를 정하고 활성 파라미터는 토큰 하나를 쓸 때의 계산량을 정합니다. 그래서 Gemma 4 의 26B A4B 는 파라미터 25.2B 가운데 3.8B 만 계산하는데도 메모리는 31B 모델과 비슷하게 듭니다. 이 글의 요청은 qwen3.5:27b 가 한 번에 둘 수 있는 262,144 토큰에 한참 못 미칩니다.**

1절 표의 크기 칸만 보고는 모델을 올리는 데 메모리가 얼마나 드는지 바로 알 수 없습니다. 같은 27B 도 숫자 하나를 몇 비트로 적느냐에 따라 파일 크기가 다르기 때문입니다. 활성 파라미터가 전체보다 작은 모델은 크기 숫자가 두 개라 어느 숫자가 메모리를 정하는지도 헷갈리기 쉽습니다.

먼저 이 블로그가 기록에 쓰는 qwen3.5:27b 부터 봅니다. 맥에서 `ollama show qwen3.5:27b` 를 돌리면 파라미터 27.4B, 컨텍스트 길이 262144, 양자화 nvfp4 가 찍힙니다. 27.4B 는 모델 카드의 27B 를 소수 한 자리까지 적은 값입니다. 양자화는 가중치 숫자 하나를 더 적은 비트로 줄여 적는 일입니다. nvfp4 방식으로 양자화한 이 파일은 맥에 받았을 때 19GB 였습니다.

모델이 토큰을 쓰려면 가중치를 메모리에 올려 두어야 하므로 가중치가 차지하는 메모리는 파라미터 수와 숫자 하나에 쓰는 비트 수가 정합니다. Ollama 라이브러리에 올라 있는 qwen3.5:27b 만 해도 16비트 bf16 판이 56GB, 8비트 int8 판이 30GB, 4비트 int4 판이 16GB 입니다. 16비트는 2바이트라서 27.4B 에 2바이트를 곱하면 약 55GB 인데, bf16 판의 56GB 와 가깝습니다. Gemma 문서는 파라미터와 비트가 많을수록 대개 더 잘하지만 계산과 메모리와 전력이 더 든다고 적었습니다. 이 글의 기록은 모두 nvfp4 판 하나로 했습니다.

1절의 표에서 활성 파라미터가 전체보다 작은 모델은 MoE(Mixture of Experts) 구조입니다. MoE 는 층마다 전문가(expert)라고 부르는 작은 신경망을 여럿 두고 토큰마다 그중 몇 개만 골라 계산합니다. Gemma 4 의 26B A4B 는 전문가 128개 가운데 8개와 늘 쓰는 1개를 골라 25.2B 중 3.8B 를 계산합니다. 모델 이름의 A4B 는 활성 파라미터가 약 4B 라는 표시입니다. 토큰 하나에 전체의 일부만 계산하므로 Gemma 문서는 이 모델이 26B 라는 전체 크기보다 훨씬 빨리 돈다고 적었습니다.

모든 파라미터를 계산에 쓰는 보통의 모델은 dense 모델이라고 부릅니다. 활성 파라미터가 작은 MoE 모델은 토큰을 빨리 쓰지만 메모리는 전체 크기만큼 듭니다. Gemma 문서에 따르면 토큰마다 전문가를 빠르게 고르려면 26B 전부를 메모리에 올려 두어야 하므로, 26B A4B 의 메모리는 4B 모델보다 dense 26B 모델에 훨씬 가깝습니다. 같은 문서가 4비트로 어림한 메모리도 26B A4B 가 14.4GB, dense 31B 가 17.5GB 로 비슷합니다.

프롬프트는 모델에 보내는 글 전체입니다. 컨텍스트 길이의 상한에는 프롬프트의 토큰과 모델이 쓴 답의 토큰이 함께 듭니다. 4절에서 thinking 을 끄고 받은 답(끈 답) 20개는 입력이 68~111 토큰이라 qwen3.5:27b 의 상한 262,144 토큰에 한참 못 미칩니다. 이 상한은 긴 문서나 대화 기록을 그대로 넣는 요청에서 걸립니다. Gemma 문서는 프롬프트와 답의 토큰이 늘수록 가중치 말고도 메모리가 더 든다고 적었습니다.

그래서 직접 운영하는 서버에 올릴 모델은 활성 파라미터가 아니라 메모리에 들어가는 전체 크기로 먼저 고릅니다. 상용 API 는 크기가 문서에 없으므로 크기 대신 4절처럼 같은 문제의 맞힘과 걸린 시간을 측정해서 비교합니다.

## 3. 답 앞의 풀이, reasoning 과 thinking

**thinking 을 켜면 모델은 답 앞에 풀이 토큰을 먼저 쓰는데, 이 풀이 토큰도 출력 토큰으로 값을 냅니다. OpenAI 는 같은 풀이를 reasoning 토큰이라고 부릅니다. 풀이를 켜고 끄는 필드(요청에 적는 이름과 값의 짝)는 Ollama 가 think, Claude 가 thinking 이며 OpenAI 는 reasoning.effort, Gemini 는 thinking_level 로 풀이의 양을 정합니다.**

어려운 문제에 thinking 을 켜 보려면 요청의 어느 필드를 바꾸고 그 대가로 무엇에 값을 내는지부터 알아야 하는데, 같은 풀이를 회사마다 다른 이름과 필드로 부릅니다.

thinking 을 켜면 모델은 문제를 나눠 따지는 글을 먼저 쓰고 그 뒤에 답을 씁니다. Qwen3.5 의 모델 카드는 이 풀이가 `<think>` 와 `</think>` 사이에 먼저 나온다고 적었습니다. 필드는 요청이나 응답에 담는 이름과 값의 짝입니다. Ollama 는 풀이와 답을 나눠서 응답의 message 필드 안에 풀이는 thinking 에, 답은 content 에 담습니다. 이런 응답의 필드는 [LLM 호출 한 번](post.html?id=llm-first-call) 편에서 하나씩 읽었습니다. 이 블로그의 기록 도구는 풀이 글 자체는 남기지 않고 글자 수만 적습니다.

reasoning 도 같은 풀이를 부르는 이름입니다. OpenAI 문서는 reasoning 모델이 답을 내기 전에 안에서 reasoning 토큰을 쓴다고 적었습니다. 강화 학습은 모델이 낸 결과에 따라 보상을 주어 모델을 고쳐 나가는 학습 방법입니다. DeepSeek-R1 보고서는 강화 학습만으로 모델이 풀이 안에서 스스로 다시 살펴보고 검증하게 되었다고 적었습니다. 같은 보고서에 따르면 성적은 수학과 코딩처럼 답을 맞춰 볼 수 있는 과제에서 올랐습니다.

1절의 표를 보면 한 모델이 풀이를 쓰는 모드와 쓰지 않는 모드를 모두 갖는 계열이 여럿입니다. Qwen3 기술 보고서는 thinking 모드와 non-thinking 모드를 한 틀에 넣어 모델을 바꾸지 않고 두 모드를 오가게 했으며 풀이에 쓸 양을 정하는 thinking budget 도 두었다고 적었습니다. 모델 하나가 두 모드와 풀이의 양을 다 받으므로 요청마다 켜고 끄거나 양을 정하는 필드가 따로 있는데, 그 필드의 이름이 API 마다 다릅니다.

아래 표에 이 글이 살펴본 네 곳의 필드를 모았습니다. Ollama 의 think 필드는 true(켬)와 false(끔)를 받는데, gpt-oss 처럼 low, medium, high 같은 이름을 받는 모델도 있습니다. Claude 의 지금 모델 4개는 thinking.type 의 기본값이 adaptive 라서 따로 적지 않으면 풀이의 양을 모델이 정합니다. effort 는 풀이를 포함해 응답에 들이는 양을 정하는 단계로, 요청의 output_config 안에 적습니다. thinking 을 끄는 값 disabled 는 Haiku 5.5 만 받으며 그마저 effort 가 high 이하일 때로 한정됩니다. Sonnet 5.5 는 disabled 대신 between_tools 를 받아 답 앞의 풀이만 끄는데, 이 값도 effort 가 high 이하일 때만 받을 수 있습니다. OpenAI 와 Gemini 도 켜고 끄기보다 풀이의 양을 단계로 정합니다.

켜고 끄는 방식이든 양을 정하는 방식이든 풀이 토큰은 출력 토큰으로 값을 냅니다. Claude 문서는 풀이 글을 돌려주지 않아도 풀이에 쓴 토큰은 출력 토큰으로 값을 낸다고 적었고 OpenAI 문서도 reasoning 토큰이 API 에 보이지 않지만 출력 토큰으로 값을 낸다고 적었습니다. Gemini 문서는 thinking 을 켜면 출력 토큰과 thinking 토큰을 더해 값을 매긴다고 적었습니다. 풀이 토큰에도 값이 붙으니 세 API 의 응답에는 풀이 토큰 수를 따로 적은 필드가 있습니다.

Ollama 의 응답에는 그런 필드가 따로 없습니다. 이 기록에서는 풀이 토큰이 출력 토큰 수인 eval_count 에 함께 들어 있습니다. 4절에서 물을 p11(「하루 예산 300만 원을 클릭당 250원으로 모두 쓰고 전환율이 2%이면 하루 전환은 몇 건인가?」)을 보면, thinking 을 끈 답은 `{"answer": 240}` 한 줄에 출력 토큰 8개를 썼고 켠 답은 같은 240 을 내기 전에 풀이를 먼저 써서 출력 토큰이 583개였습니다.

풀이가 맞힘을 늘리는지는 문제에 따라 다릅니다. 지난 편의 캠페인 한 줄은 thinking 을 켜도 답이 같았지만 [컨텍스추얼 타겟팅](post.html?id=contextual-targeting) 편에서는 제목과 첫 문단이 서로 다른 이야기인 지면(광고가 실리는 페이지)에 thinking 을 켜자 붙는 라벨이 제목 쪽으로 바뀌었습니다. 4절은 광고 운영 숫자 문제 20개로 같은 물음을 측정합니다.

표의 마지막 칸은 응답에서 풀이 토큰 수를 확인하는 자리입니다. usage 는 응답에서 토큰 수를 담는 필드입니다.

| 어디서 | 켜고 끄는 필드 | 받는 값 | 풀이 토큰 수를 보는 곳 |
|---|---|---|---|
| Ollama `/api/chat` | think | true, false, 모델이 정한 이름 | 따로 없음, 이 기록에서는 eval_count 에 같이 듦 |
| Claude Messages API | thinking.type, output_config.effort | adaptive, disabled 와 effort 단계 | usage 의 output_tokens_details.thinking_tokens |
| OpenAI Responses API | reasoning.effort | none 에서 max 까지, 모델마다 다름 | usage 의 output_tokens_details.reasoning_tokens |
| Gemini API | thinking_level | minimal 에서 high 까지, 모델마다 다름 | usage 의 total_thought_tokens |

## 4. 같은 문제 20개에서 thinking 을 끈 답과 켠 답

**thinking 을 끈 답은 문제 20개 가운데 14개를 맞혔습니다. 한 단계로 푸는 easy 10개는 모두 맞았지만 두세 단계로 푸는 hard 10개는 4개만 맞았습니다. hard 10개에 thinking 을 켜자 10개가 모두 맞은 대신 출력 토큰은 83개에서 7,713개로 92.9배, 걸린 시간은 11.3초에서 493.4초로 43.6배가 되었습니다.**

3절에서 보았듯 thinking 은 문제에 따라 답을 바꾸기도 하고 그대로 두기도 하는데, 어느 쪽이든 켜면 풀이만큼 출력 토큰이 늘어납니다. 그래서 광고주의 숫자 질문에서 thinking 이 맞힘을 얼마나 늘리고 토큰과 시간이 얼마나 더 드는지를 지훈 씨의 문제 20개로 측정합니다.

문제 20개는 광고 운영에서 자주 하는 계산으로 만들었습니다. 클릭률은 노출 가운데 클릭이 나온 비율이고 전환율은 클릭 가운데 구매 같은 전환이 일어난 비율입니다. easy 10개는 p01(「노출 120,000건에서 클릭이 3,600건이면 클릭률은 몇 %인가?」)처럼 3,600 을 120,000 으로 나눠 3% 를 얻는 한 단계 문제입니다. hard 10개는 예산을 클릭당 비용으로 나눈 뒤 전환율을 곱하는 식으로 두세 단계를 거치는 문제인데, 3절의 p11 은 300만 원을 250원으로 나누면 클릭이 12,000건이고 여기에 전환율 2% 를 곱하면 정답 240건이 나옵니다. 답은 모두 단위 없는 정수입니다. 블록의 PROBLEMS 에 문제와 정답이 함께 들어 있습니다.

모델에는 메시지 두 개를 보냈습니다. 시스템 메시지는 「문제를 읽고 정수 답 하나를 JSON {"answer": 정수} 로만 답한다. 설명을 쓰지 않는다.」 두 문장입니다. JSON 은 이름과 값의 짝을 중괄호로 묶어 적는 꼴입니다. 이 지시대로라면 답은 `{"answer": 240}` 같은 한 줄이 됩니다. 사용자 메시지는 이번에 물을 내용을 담는 메시지로, 「문제: 」 뒤에 문제 한 줄을 붙인 글입니다.

20개 모두 thinking 을 끄고 temperature 0 과 seed 7 로 한 번씩 물었습니다. temperature 는 다음 토큰을 얼마나 흔들리게 뽑을지 정하는 값이고 seed 는 뽑을 때 쓰는 난수의 시작값입니다. [자연어 오디언스](post.html?id=natural-language-audience) 편과 [컨텍스추얼 타겟팅](post.html?id=contextual-targeting) 편에서는 temperature 0 으로 다시 기록해도 같은 답이 나왔습니다. 여기서 같은 답은 답이 같았다는 뜻이지 글자까지 같았다는 뜻은 아닙니다. 두 가지의 차이는 [비용, 캐시, 비결정성](post.html?id=llm-cost-cache-nondeterminism) 편에서 봅니다. hard 10개는 다른 것은 그대로 두고 thinking 만 켜서 한 번 더 물었습니다.

아래 블록은 기록한 답 30개(끈 답 20개와 hard 10개의 켠 답 10개)를 정답과 비교해, thinking 을 끄고 켰을 때 맞힘과 출력 토큰과 시간이 어떻게 달라지는지 보려고 돌립니다. 답은 JSON 으로 읽어 키가 answer 하나이고 값이 정수일 때만 답으로 칩니다. 3.0 같은 실수나 "240" 같은 글자처럼 꼴이 틀린 답은 읽지 못한 답으로 세고 틀린 답으로 칩니다. 틀린 답은 정답과 자릿수만 다른지, 다시 말해 정답의 10배, 100배, 1,000배이거나 1/10, 1/100, 1/1,000 인지도 함께 찍습니다. 기록의 키 p11 은 thinking 을 끄고 받은 답이고 p11|on|1 은 같은 문제를 thinking 을 켜고 받은 답입니다.

**가상 단가로 입력 1,200 토큰, 출력 150 토큰짜리 요청 한 건의 값을 세면 작은 모델은 0.72원, 큰 모델은 7.80원이고 하루 100만 요청이면 72만 원과 780만 원입니다. 요청마다 같은 시스템 메시지 1,000 토큰을 캐시에서 읽으면 큰 모델도 하루 420만 원으로 줄어듭니다.**

지훈 씨가 서비스에 붙일 모델을 고르려면 4절의 맞힘 옆에 하루에 드는 값을 놓아야 하는데, 상용 API 의 값은 요청마다 쓴 토큰 수로 매겨집니다.

입력 토큰은 모델이 읽는 프롬프트의 토큰이고 출력 토큰은 모델이 쓰는 토큰입니다. 상용 API 는 토큰 100만 개에 얼마인지를 정한 단가로 값을 매기고 입력 토큰과 출력 토큰의 단가를 따로 둡니다. 그래서 요청 한 건의 값은 입력 토큰 수와 입력 단가의 곱에 출력 토큰 수와 출력 단가의 곱을 더한 뒤 100만으로 나누어 셉니다. 실제 단가는 [Anthropic](https://platform.claude.com/docs/en/about-claude/pricing), [OpenAI](https://developers.openai.com/api/docs/pricing), [Google](https://aistudio.google.com/docs/pricing) 의 가격 문서에 있습니다. 이 절은 설명을 위해 정한 가상 단가로 작은 모델과 큰 모델 두 가지를 둡니다.

요청 한 건은 시스템 메시지 1,000 토큰과 사용자 메시지 200 토큰을 읽고 출력 150 토큰을 쓴다고 둡니다. 요청마다 시스템 메시지는 글이 같으므로 앞 요청에서 계산한 결과를 캐시에 남겨 두었다가 다음 요청이 그대로 읽어 쓸 수 있습니다. 이 절은 캐시에서 읽은 토큰을 입력 단가의 0.1배로 세는데, 실제 비율과 캐시에 처음 쓰는 토큰의 값은 API 마다 가격 문서에 따로 있습니다.

아래 블록은 같은 요청을 작은 모델, 큰 모델, 시스템 메시지를 캐시에서 읽는 큰 모델의 세 경우로 세어 모델을 바꿀 때와 캐시를 쓸 때 하루 값이 얼마나 달라지는지 보려고 돌립니다.

```python
# 하는 일: 100만 토큰당 단가로 요청 한 건의 값을 세고, 하루 100만 요청의 값을 작은 모델, 큰 모델, 시스템 메시지를 캐시에서 읽는 큰 모델로 비교한다.

# 1단계: 요청 한 건의 값을 세는 함수를 둔다
# 단가 price_in, price_out 은 100만 토큰당 원이다. in_tokens 는 캐시에서 읽은 토큰까지 센 입력 토큰 전부다.
# 그 가운데 cached_tokens 만큼은 입력 단가의 0.1배로 센다. 나머지 입력과 출력은 단가 그대로다.
def cost_won(in_tokens, out_tokens, price_in, price_out, cached_tokens=0):
    fresh = in_tokens - cached_tokens
    return (fresh * price_in + cached_tokens * price_in * 0.1 + out_tokens * price_out) / 1_000_000


# 2단계: 가상 단가와 요청 한 건의 토큰을 둔다
# 단가는 설명을 위해 정한 가상 값이다. 실제 단가는 회사마다 가격 문서에 있고, 모델마다 다르다.
# 요청 한 건은 시스템 메시지 1,000 토큰과 사용자 메시지 200 토큰을 읽고 150 토큰을 쓴다.
PRICES = {'작은 모델': (400, 1_600), '큰 모델': (4_000, 20_000)}
SYSTEM, USER, OUT = 1_000, 200, 150
DAILY = 1_000_000
for model, (price_in, price_out) in PRICES.items():
    print(f'{model} 단가: 100만 토큰당 입력 {price_in:,}원, 출력 {price_out:,}원')
print(f'요청 한 건: 입력 {SYSTEM + USER:,} 토큰 (시스템 {SYSTEM:,} + 사용자 {USER}), 출력 {OUT} 토큰, 하루 {DAILY:,}건')

# 3단계: 세 경우의 요청 한 건과 하루 값을 센다
# 셋째 경우는 요청마다 같은 시스템 메시지 1,000 토큰을 캐시에서 읽는다. 사용자 메시지와 출력은 그대로다.
cases = [('작은 모델', '작은 모델', 0), ('큰 모델', '큰 모델', 0), ('큰 모델 + 시스템 캐시', '큰 모델', SYSTEM)]
daily = {}
for name, model, cached_tokens in cases:
    price_in, price_out = PRICES[model]
    one = cost_won(SYSTEM + USER, OUT, price_in, price_out, cached_tokens)
    part_in = cost_won(SYSTEM + USER, 0, price_in, price_out, cached_tokens)
    daily[name] = round(cost_won((SYSTEM + USER) * DAILY, OUT * DAILY, price_in, price_out, cached_tokens * DAILY))
    print(f'{name}: 한 건 {one:.2f}원 (입력 {part_in:.2f}원, 출력 {one - part_in:.2f}원), 하루 {daily[name]:,}원')

# 4단계: 세 값을 비교한다
# 출력은 토큰 수로는 작지만 단가가 입력의 4~5배라 값에서 차지하는 몫이 크다.
small, large, cached = daily['작은 모델'], daily['큰 모델'], daily['큰 모델 + 시스템 캐시']
print(f'큰 모델은 작은 모델의 {large / small:.1f}배')
print(f'캐시를 쓰면 큰 모델의 하루 값이 {large - cached:,}원 줄어 {cached / large:.0%} 가 된다')
out_share = cost_won(0, OUT, *PRICES['큰 모델']) / cost_won(SYSTEM + USER, OUT, *PRICES['큰 모델'])
print(f'큰 모델에서 출력은 토큰 수의 {OUT / (SYSTEM + USER + OUT):.0%} 인데 값의 {out_share:.0%} 다')

# 출력:
# 2단계 뜻: 가상 단가 둘과 요청 한 건의 토큰이다.
# 작은 모델 단가: 100만 토큰당 입력 400원, 출력 1,600원
# 큰 모델 단가: 100만 토큰당 입력 4,000원, 출력 20,000원
# 요청 한 건: 입력 1,200 토큰 (시스템 1,000 + 사용자 200), 출력 150 토큰, 하루 1,000,000건
# 3단계 뜻: 하루 100만 요청이면 작은 모델 720,000원, 큰 모델 7,800,000원, 캐시를 쓴 큰 모델 4,200,000원이다.
# 작은 모델: 한 건 0.72원 (입력 0.48원, 출력 0.24원), 하루 720,000원
# 큰 모델: 한 건 7.80원 (입력 4.80원, 출력 3.00원), 하루 7,800,000원
# 큰 모델 + 시스템 캐시: 한 건 4.20원 (입력 1.20원, 출력 3.00원), 하루 4,200,000원
# 4단계 뜻: 큰 모델은 작은 모델의 10.8배이고, 캐시는 큰 모델을 54% 로 줄인다. 출력은 토큰 수의 11% 인데 값의 38% 다.
# 큰 모델은 작은 모델의 10.8배
# 캐시를 쓰면 큰 모델의 하루 값이 3,600,000원 줄어 54% 가 된다
# 큰 모델에서 출력은 토큰 수의 11% 인데 값의 38% 다
```

3단계가 찍은 값을 큰 모델로 따라가 보면, 입력 1,200 토큰에 입력 단가 4,000원을 곱해 100만으로 나눈 4.80원과 출력 150 토큰에 출력 단가 20,000원을 곱해 100만으로 나눈 3.00원을 더해 한 건이 7.80원이고 하루 100만 건이면 7,800,000원(780만 원)입니다. 작은 모델은 같은 계산으로 입력 0.48원과 출력 0.24원을 더한 0.72원이고 하루 720,000원(72만 원)입니다. 큰 모델의 입력 단가는 작은 모델의 10배, 출력 단가는 12.5배라서 하루 값은 그 사이인 10.8배입니다. 같은 요청이라도 모델 하나를 바꾸면 하루 값이 열 배 넘게 달라집니다.

4단계의 마지막 줄은 출력이 값에서 차지하는 몫을 셉니다. 출력 단가 20,000원이 입력 단가 4,000원의 5배라서 큰 모델에서 출력 150 토큰은 요청 한 건의 토큰 수로는 11% 뿐인데도 값으로는 7.80원 가운데 3.00원(38%)을 차지합니다. thinking 을 켜면 풀이 토큰이 바로 이 출력 쪽에 붙으므로, 4절의 hard 10개처럼 출력 토큰이 92.9배가 되면 값에서 출력이 차지하는 몫은 더 커집니다.

셋째 경우는 요청마다 같은 시스템 메시지 1,000 토큰을 입력 단가의 0.1배로 읽어서 한 건의 입력 값이 4.80원에서 1.20원으로 줄고 출력 3.00원은 그대로라 한 건이 4.20원, 하루 4,200,000원(420만 원)입니다. 큰 모델의 하루 값이 360만 원 줄어 원래의 54% 가 됩니다. Anthropic 의 문서는 프롬프트의 앞부분이 같을 때 캐시가 맞는다고 적었는데, 캐시가 맞으면 앞 요청의 계산을 다시 씁니다. 그래서 요청마다 같은 시스템 메시지를 프롬프트 앞에 두고 바뀌는 사용자 메시지를 그 뒤에 둡니다.

단가표만 보아서는 하루 값이 나오지 않습니다. 요청 한 건의 입력과 출력 토큰, thinking 이 붙이는 풀이 토큰, 캐시에서 읽는 몫을 함께 세어야 하루 값이 나옵니다. 지훈 씨가 서비스 모델을 고를 때 맞힘 옆에 놓는 숫자가 이렇게 센 하루 값입니다.

## 6. 지훈 씨의 선택: 기록은 공개 모델, 서비스 모델은 측정한 숫자로

**지훈 씨는 요청이 맥 밖으로 나가지 않고 같은 설정으로 다시 물어 숫자를 맞춰 볼 수 있으므로 글과 실험의 기록은 노트북의 공개 모델로 계속하기로 했습니다. 서비스에 붙일 모델은 후보마다 같은 문제 20개로 측정한 맞힘과 토큰, 시간, 하루 값을 나란히 놓고 고릅니다.**

지훈 씨는 선배의 목록으로 돌아가 첫째 칸(어디서 도나)부터 정했습니다. 광고주의 질문에는 예산과 단가 같은 광고주의 자료가 들어 있는데, 공개 가중치 모델을 회사 안 서버에 띄우면 그 글이 회사 밖으로 나가지 않지만 상용 API 로 보내면 글은 API 를 연 회사의 서버로 갑니다.

같은 모델을 같은 설정으로 다시 부를 수 있어 글에 적은 숫자를 다시 맞춰 볼 수 있으므로, 글과 실험의 기록은 노트북의 qwen3.5:27b 로 계속합니다. 다만 컨텍스추얼 타겟팅 편에서 같은 설정으로 다시 기록해 보니 thinking 을 켠 답은 풀이의 길이가 달라지기도 했으므로 이 글도 켠 답의 토큰과 시간은 한 번 기록한 값으로 읽습니다. 공개 모델은 요청마다 내는 값은 없지만 시간과 기계가 드는데, hard 10개에 thinking 을 켠 답이 493.4초를 쓴 것이 그 예입니다.

서비스에 붙일 모델은 같은 문제 20개를 후보마다 보내 측정한 숫자로 고릅니다. 4절에서 같은 모델이 같은 설정으로 easy 는 10개, hard 는 4개를 맞혔듯 맞히는 수는 어떤 문제 세트로 측정하느냐에 따라 다르므로, 남이 측정한 점수보다 서비스가 답할 문제에서 맞힌 수를 먼저 봅니다. 상용 API 는 크기가 문서에 없어 크기로 비교할 수도 없으므로 후보끼리는 이렇게 측정한 숫자로 비교합니다.

thinking 은 어려운 문제에만 켜기로 했습니다. 이 기록에서 hard 10개는 thinking 을 켜면 6개를 더 맞혔지만 문제 하나에 32.9초에서 69.6초가 걸렸으므로, 광고주를 화면에서 그만큼 기다리게 할지는 화면을 만드는 사람들과 함께 정합니다. 다만 어느 질문이 어려운지 미리 나누는 규칙은 이 기록으로 측정하지 않았습니다.

값은 5절에서 센 하루 값으로 봅니다. 작은 모델로 이 문제들을 충분히 맞힐 수 있다면 하루 값은 72만 원입니다. 큰 모델이 꼭 필요하다면 시스템 메시지를 캐시에서 읽어 하루 780만 원을 420만 원으로 줄입니다.

아래 표에 고를 것마다 이 글에서 본 값과 지훈 씨의 선택을 모았습니다.

| 고를 것 | 이 글에서 본 값 | 지훈 씨의 선택 |
|---|---|---|
| 어디서 도나 | 공개 가중치는 회사 안 서버, 상용 API 는 회사 밖 서버 | 기록은 노트북의 qwen3.5:27b |
| 크기와 메모리 | qwen3.5:27b 27.4B, 파일 19GB | 노트북 메모리에 들어가는 크기 |
| 컨텍스트 길이 | 끈 답의 입력 68~111 토큰, 상한 262,144 | 이 문제들에는 걸리지 않음 |
| 맞힘 | 끈 답 easy 10개, hard 4개 | 후보마다 같은 문제 20개로 측정 |
| thinking | hard 맞힘 4개에서 10개, 시간 43.6배 | 어려운 문제에만 켬 |
| 값 | 하루 72만, 780만, 캐시로 420만 원 | 맞힘이 같으면 작은 모델 |

## 7. 두 무대에서 모델을 부르는 자리

**모델을 고르는 네 가지 기준은 두 무대(한 회사가 서비스와 광고 서버를 다 가진 곳과 여러 회사가 실시간 경매로 광고를 사고파는 곳)에서 같습니다. 다만 답을 기다릴 수 있는 시간과 요청에 담는 글이 누구의 자료인지가 무대마다 다릅니다.**

### 캠페인 화면에서 답을 기다릴 수 있는 담장 안 [무대: 닫힌 생태계]

담장 안은 한 회사가 서비스와 광고 서버를 모두 가진 곳입니다. 여기서 광고주가 캠페인 화면에 숫자를 물으면 답이 사람에게 가므로 thinking 을 끈 답이 걸린 1초 안팎은 기다릴 수 있습니다. 하지만 켠 답이 걸린 32.9초에서 69.6초는 화면에서 기다리기에 길므로 계산은 코드에 맡기고 모델에게는 질문을 식으로 옮기게 하는 방법도 있습니다. 광고주의 예산과 단가는 회사 안의 자료이므로 회사 안 서버에 띄운 공개 모델로 부르면 그 자료가 회사 밖으로 나가지 않습니다.

### 입찰 요청마다 모델을 부를 수 없는 열린 RTB [무대: 열린 RTB]

열린 RTB 는 여러 회사가 실시간 경매로 남의 지면에 광고를 사고파는 곳입니다. 여기서 광고를 사는 시스템인 DSP 는 입찰 요청에 100ms 안팎으로 답해야 하는데, 이 글의 모델은 thinking 을 끈 답도 1초 안팎이 걸려 입찰 요청을 받아 답하는 경로(입찰 경로)에 둘 수 없습니다. 그래서 LLM 은 캠페인 설정이나 지면 분류처럼 입찰 전에 미리 해 둘 수 있는 일에 씁니다. 그런 일도 하루 100만 건이 되면 작은 모델의 72만 원과 큰 모델의 780만 원의 차이가 날마다 쌓입니다.

| 컨텍스트 길이 | 한 번에 둘 수 있는 토큰의 상한 | qwen3.5 262,144, 상용 3개 계열 100만 토큰 안팎 |

## 헷갈리기 쉬운 점

- **파라미터 수와 활성 파라미터는 서로 다른 숫자입니다.** Gemma 4 26B A4B 의 26B 는 메모리에 올리는 전체 크기이고 4B 는 토큰 하나를 쓸 때 계산하는 크기입니다. 그래서 활성 파라미터가 작은 MoE 모델도 메모리는 전체 크기만큼 듭니다. Gemma 문서가 4비트로 어림한 값으로도 26B A4B 는 14.4GB 로 dense 31B 의 17.5GB 와 비슷합니다. 모델 이름에서는 Gemma 와 Qwen 이 A 뒤에 활성 파라미터를 적습니다.
- **thinking 토큰은 출력 토큰으로 값을 냅니다.** 풀이 글이 응답에 보이지 않아도 값은 붙습니다. Claude 의 지금 모델은 풀이 글을 기본으로 돌려주지 않고 OpenAI 의 reasoning 토큰도 API 에 보이지 않습니다. 그래도 두 회사의 문서는 모두 그 토큰을 출력 토큰으로 값을 매긴다고 적었습니다. 이 글의 hard 10개에서도 thinking 을 켜자 출력 토큰이 83개에서 7,713개로 늘었습니다.
- **정답률은 어떤 문제 세트로 측정했는지에 달려 있습니다.** 같은 모델이 같은 설정으로 easy 10개는 모두 맞히고 hard 10개는 4개만 맞혔으므로 20개를 한꺼번에 세면 70% 이지만 easy 와 hard 로 나누어 세면 100% 와 40% 입니다. 남이 측정한 점수표의 정답률도 그 점수표가 쓴 문제 세트에서 나온 값이므로, 모델은 실제로 풀 문제로 다시 측정합니다.

## 더 깊이 보기

:::deep MoE 는 토큰마다 전문가 몇 개만 계산합니다
MoE 층에는 전문가가 여럿 있고, 토큰마다 그중 몇 개를 골라 계산합니다. 전문가 하나하나는 피드포워드 층, 곧 토큰 하나의 벡터에 가중치를 곱하고 더해 다음 층으로 넘기는 층입니다. Qwen3.5-35B-A3B 의 모델 카드는 전문가 256개 가운데 8개와 늘 쓰는 공유 전문가 1개를 쓴다고 적었습니다. 그래서 35B 를 갖고도 토큰 하나에는 3B 를 계산합니다. 같은 계열의 Qwen3.5-27B 는 층마다 MoE 대신 보통 피드포워드 층을 두어 27B 를 모두 계산합니다. Gemma 4 26B A4B 는 전문가 128개 가운데 8개와 공유 1개를 씁니다. DeepSeek-V4-Pro 는 1.6T 중 49B 를 계산합니다. Gemma 문서는 26B A4B 의 전문가 전부를 메모리에 올려야 한다고 적었습니다.
:::

:::deep 요청 한 건의 값을 세는 식
5절의 `cost_won` 은 아래 식을 그대로 옮긴 것입니다. $p_{in}$ 과 $p_{out}$ 은 100만 토큰당 단가입니다. $N_{in}$ 은 캐시에서 읽은 토큰 $N_{cache}$ 까지 센 입력 토큰 전부입니다.

$$\mathrm{cost} = \frac{(N_{in} - N_{cache})\,p_{in} + 0.1\,N_{cache}\,p_{in} + N_{out}\,p_{out}}{10^6}$$

셋째 경우를 넣으면 한 건이 4.2원이고, 하루 100만 요청이면 420만 원입니다.

$$\frac{200 \times 4000 + 0.1 \times 1000 \times 4000 + 150 \times 20000}{10^6} = 4.2$$

thinking 을 켜면 풀이 토큰이 $N_{out}$ 에 더해집니다. 실제 API 는 캐시에 처음 쓰는 토큰의 단가와 캐시가 남는 시간을 따로 정합니다. Anthropic 의 prompt caching 문서는 캐시가 5분이나 1시간 동안 남는다고 적었습니다.
:::
