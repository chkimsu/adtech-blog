지훈이 어제 티켓을 하나 올렸다. 광고 노출 로그를 운영자 검색 창에도 넣어 달라는 요청이다. 이게 밀리면 하루 ₩3,200,000짜리 캠페인의 이상 신고를 사람이 눈으로 찾는다.

같은 티켓인데 팀마다 답이 갈린다. 한쪽은 설정 파일에 블록 하나를 더하고 그날 오후에 승인을 받는다. 다른 한쪽은 돌고 있는 처리 잡 다섯 개를 전부 열어야 해서, 배포가 다 끝날 때까지 다른 일이 중단된다.

**무엇이 반나절과 두 주의 차이를 만들었을까?**

갈리는 자리는 티켓이 온 날이 아니라 파이프라인을 처음 그린 날이다. 그날 무엇을 먼저 적었느냐가 이 차이를 만들고, 그 순서를 정하는 일을 **파이프라인 설계**라고 부른다. 수집기를 고르는 일이 아니라 누가 이 데이터를 언제까지 봐야 하는지를 먼저 적는 일이다.

> **한 줄 요약:** 파이프라인 설계는 부품 고르기가 아니라 소비자의 마감을 적는 데서 시작한다. 여섯 층 중 어디에 무엇을 세울지는 그 마감과 거기 붙는 비용이 정한다.

> **무대 표시** — 배지의 **열린 RTB** 는 남의 거래소에 입찰만 넣는 자리, **닫힌 생태계** 는 우리가 경매를 직접 돌리는 자리, **공통** 은 둘 다입니다.
> 이 글은 **무관** 입니다. 경매를 누가 돌리든 로그는 같은 여섯 층을 지납니다. 볼륨과 비용 숫자는 설명을 위해 지어낸 값입니다.

## 1. 설계는 저장부터 거꾸로 한다

**부품을 먼저 고르면 반드시 다시 뜯는다. 먼저 적을 것은 "누가 무엇을 언제까지 조회하나" 넷이다.**

처음 그리는 사람은 대개 수집기부터 고른다. 그런데 요구가 없으면 판정할 기준이 없어서, 비교에 쓴 며칠이 그대로 손해다. 결정의 순서가 뒤집혀 있다. 그래서 실무에서 먼저 적는 것은 소비자 넷이다.

| 소비자 | 언제까지 봐야 하나 | 못 틀리는 정도 | 조회 모양 |
|---|---|---|---|
| 실시간 대시보드 | 2초 | 1% 오차 허용 | 최근 5분을 지면별로 |
| 광고주 리포트 | 5분 | 0.1% | 광고별 기간 합계 |
| 학습 데이터 | 하루 1회 (06시) | 라벨이 정확할 것 | 하루치를 통째로 |
| 정산 확정 | 다음 날 09시 마감 | 0건 | 매체별 하루 합계 |

넷의 요구가 다르다는 것이 표의 전부가 아니다. **얼마나 다른지가 부품을 정하고, 그 부품이 매달 낼 비용을 정한다.** 2초와 33시간은 4만 배 넘게 벌어져 있어서, 한 부품으로 둘을 맞추면 어느 한쪽이 반드시 손해를 본다.

마감은 **가장 오래된 이벤트**로 잰다. 하루치를 06시에 학습하면 전날 00시 이벤트가 30시간을 기다리고, 그 최악값이 예산이다. 그 예산도 다 못 쓴다. 앱에서 Kafka 브로커에 닿기까지 이미 1,112 ms 를 썼기 때문이다.

아래 **비용지수**는 그 경로로 하루치를 처리할 때 드는 돈을 스트림 100 기준으로 적은 값이다.

```python
# 부품을 고르기 전에 "언제까지"를 먼저 적는다.
#
# 소비자마다 마감이 있다. 그 마감에서 Kafka 도달까지 쓰는 1,112 ms 를 빼면
# 처리·유통·저장에 쓸 수 있는 시간이 남는다. 그 안에 드는 경로만 후보이고,
# 후보가 둘 이상이면 가장 싼 것을 고른다. 볼륨·비용지수는 지어낸 값이다.
from unicodedata import east_asian_width

TO_KAFKA = 1_112                      # 탭에서 브로커 도달까지 (ms)

# 경로 후보 — (이름, 창 크기 + 처리 시간 ms, 상대 비용지수)
PATHS = [
    ("스트림 집계",       800,          100),
    ("1분 마이크로배치",  90_000,        40),
    ("1시간 배치",        4_200_000,     12),
    ("하루 배치",         88_200_000,     4),
]

# 소비자 — (이름, 마감 ms, 마감을 사람 말로)
CONSUMERS = [
    ("실시간 대시보드", 2_000,       "2초"),
    ("광고주 리포트",   300_000,     "5분"),
    ("학습 데이터",     108_000_000, "30시간"),
    ("정산 확정",       118_800_000, "33시간"),
]

def w(s):                             # 한글은 모노스페이스에서 두 칸을 먹는다
    return sum(2 if east_asian_width(c) in "WF" else 1 for c in s)

def row(*cells):                      # (글자, 칸수) 쌍을 오른쪽 맞춤으로 찍는다
    print("".join(" " * (n - w(c)) + c for c, n in cells))

print("소비자마다 남는 예산과 그 안에 드는 경로")
row(("소비자", 18), ("마감", 8), ("남는 예산(ms)", 15), ("드는 경로", 11), ("고른 경로", 20), ("비용", 6))
total, all_stream = 0, 0
for name, deadline, human in CONSUMERS:
    left = deadline - TO_KAFKA
    fit = [p for p in PATHS if p[1] <= left]
    pick = min(fit, key=lambda p: p[2])          # 드는 것 중 가장 싼 것
    total += pick[2]
    all_stream += PATHS[0][2]
    row((name, 18), (human, 8), (f"{left:,}", 15), (f"{len(fit)}개", 11), (pick[0], 20), (str(pick[2]), 6))

print()
print(f"고른 대로 붙이면 비용 합계 {total}")
print(f"넷 다 스트림으로 붙이면 {all_stream}  →  {all_stream / total:.1f}배")

# 출력:
# 소비자마다 남는 예산과 그 안에 드는 경로
#             소비자    마감  남는 예산(ms)  드는 경로           고른 경로  비용
#    실시간 대시보드     2초            888        1개         스트림 집계   100
#      광고주 리포트     5분        298,888        2개    1분 마이크로배치    40
#        학습 데이터  30시간    107,998,888        4개           하루 배치     4
#          정산 확정  33시간    118,798,888        4개           하루 배치     4
#
# 고른 대로 붙이면 비용 합계 148
# 넷 다 스트림으로 붙이면 400  →  2.7배
```

**대시보드는 후보가 하나뿐이다.** 마감 2초에서 브로커까지 쓴 시간을 빼면 888 ms 가 남고, 그 안에 드는 경로가 스트림 집계밖에 없다. 취향이 아니라 888 ms 가 그 결정을 대신했다.

정산과 학습은 반대다. 후보가 넷 다 드니 가장 싼 것을 고르면 되는데, 여기서 스트림을 고르면 비용을 25배 더 내고 똑같은 결과를 얻는다.

그래서 결정은 하나다. 남는 예산이 888 ms 면 스트림에 100을 낸다. 33시간이면 배치에 4를 낸다. 넷을 다 스트림에 붙이면 400, 마감에 맞추면 148 이다. 그렇게 고른 경로를 어느 자리에 놓을지가 다음 절이다.

## 2. 여섯 층 지도 — 무엇이 어디에 서나

**수집 → 버퍼 → 처리 → 유통 → 저장 → 조회. 여섯 층이고, 층마다 정할 질문이 하나씩 붙는다.**

1절이 경로를 정했으니 그 위에 부품을 놓는다. 자리는 여섯이고, 자리마다 결정할 질문이 하나씩 달려 있다.

| 층 | 하는 일 | 이 층이 정하는 질문 | 흔한 부품 |
|---|---|---|---|
| 수집 | 파일·SDK에서 긁어 보낸다 | 어디서 긁나 | Fluent Bit · Vector |
| 버퍼 | 한 번 쓰고 여럿이 읽는다 | 며칠 남기나 | Kafka · Pulsar |
| 처리 | 정제·검증·조인·집계 | 언제 세나 | Flink · Spark |
| 유통 | 목적지마다 갈라 보낸다 | 어디로 보내나 | Kafka Connect |
| 저장 | 오래 담는다 | 어떤 포맷으로 | Iceberg · ClickHouse |
| 조회 | SQL 로 꺼낸다 | 누가 읽나 | Trino · Hive Metastore |

낯선 이름 둘만 풀어 둔다. Iceberg 는 흩어진 파일 묶음을 한 테이블처럼 보이게 하는 장부다. Hive Metastore 는 그 테이블의 이름과 위치를 적어 두는 **카탈로그**, 곧 목록 서버다. 목록이 없으면 SQL 을 던질 대상 자체가 없다.

**층이 여섯이라는 말은 서버가 여섯 종이라는 뜻이 아니다.** Flink 잡 하나가 처리와 유통을 같이 하기도 한다. 층은 물건이 아니라 책임의 이름이고, 값어치는 **바꿀 때 흔들리는 범위가 그 층 안에서 끝난다**는 데 있다. 층을 안 나누면 하나 바꿀 때마다 전부 확인해야 해서, 그 시간이 배포 승인이 늦어지는 비용이 된다.

### 수집기는 어디에 무엇을 두나

갈림길은 넷이다. 상주 메모리, 파싱 능력, 막혔을 때 하는 행동, 어느 자리에 두느냐다. **상주 메모리**는 아무 일 안 해도 계속 차지하는 메모리라, 대수를 곱하면 그대로 서버 비용이 된다.

Fluent Bit·Filebeat·Vector 는 가볍고 Fluentd·Logstash 는 무거운데, 무거운 쪽이 파싱을 잘한다. 우연이 아니다. **파싱을 잘하려면 런타임과 플러그인을 들어야 하고, 그게 곧 메모리다.**

:::deep 더 깊이 — 제품 다섯의 언어·파싱·버퍼
아래 세 열은 각 제품 문서에 있는 사실이고, 버퍼 열은 받는 쪽이 막혔을 때의 동작이다.

| 제품 | 언어 | 파싱 | 버퍼·막혔을 때 | 주로 두는 자리 |
|---|---|---|---|---|
| Fluent Bit | C | 정규식 · Lua | 메모리 한도 + 파일 버퍼 | 앱 서버 |
| Filebeat | Go | 얕다 | 막히면 읽기를 멈춘다 | 앱 서버 |
| Vector | Rust | VRL 변환 언어 | 넘칠 때 동작을 고른다 | 양쪽 다 |
| Fluentd | Ruby | 플러그인이 많다 | 파일 버퍼 + 재시도 | 모아 받는 서버 |
| Logstash | JVM | grok 등 가장 강하다 | 디스크 큐 | 모아 받는 서버 |

:::

자리가 갈리는 이유는 대수다. 이 글의 규모에서 앱 인스턴스는 300대이고 모아 받는 대수는 20대라, 같은 메모리라도 매달 낼 비용이 다르다. 이 결정은 성능이 아니라 돈이 정한다.

| 어디에 무엇을 | 대당 상주 메모리 | 대수 | 합계 |
|---|---|---|---|
| 앱 서버에 가벼운 것 (Fluent Bit) | 25 MB | 300 | 7,500 MB = 7.5 GB |
| 앱 서버에 무거운 것 (Logstash) | 1,024 MB | 300 | 307,200 MB = 307.2 GB |
| 모아 받는 서버에 무거운 것 | 1,024 MB | 20 | 20,480 MB = 20.5 GB |

300대에 무거운 것을 깔면 가벼운 것의 41배를 쓰고, 같은 것을 20대에만 두면 20.5 GB 로 끝난다. **그래서 흔한 결정이 "앱 서버는 가볍게, 파싱은 모아 받는 자리에서"** 가 된다.

막혔을 때 하는 행동은 다른 축이고 답은 셋뿐이다. 버리거나, 디스크에 쌓거나, 아예 읽기를 멈춘다. 버리면 그 구간이 사라져 정산에서 손해가 나고, 멈추면 원본 파일이 지워질 때 같이 잃는다. 이 결정은 **그 로그가 정산에 쓰이느냐**가 정한다. 정산은 0건이 조건이라 디스크에 쌓는 쪽이다.

### 유통 층은 글 하나로 떼어 놨다

넷째 층은 처리 결과를 목적지마다 갈라 보내는 자리다. 처리 잡이 다섯이고 목적지가 여섯인데, 이 층이 없으면 연결이 30개이고 두면 11개다.

도입의 티켓이 값을 내는 자리가 여기다. 목적지를 하나 더 붙일 때 손대는 처리 잡이 다섯 개와 0개로 갈려 배포 승인 횟수부터 달라진다. 그 셈은 [목적지가 여럿일 때 — 연결을 30에서 11로](post.html?id=data-distribution-layer)가 끝까지 센다.

## 3. 원본 · 정제 · 마트 — 왜 세 벌을 두나

**원본을 그대로 남기는 값은 하루 21.9 GB 다. 그 비용을 안 내면 5절의 백필이 통째로 불가능해진다.**

저장 층 안이 다시 셋으로 갈린다. 받은 그대로인 원본, 타입과 중복을 정리한 정제, 소비자별로 미리 합쳐 둔 마트다. 셋의 보존 기간과 비용이 다르다.

| 층 | 무엇이 들어 있나 | 포맷 | 보존 | 하루 크기 | 읽는 곳 |
|---|---|---|---|---|---|
| 원본 (raw) | 들어온 그대로 | JSON + gzip | 90일 | 21.9 GB | 재처리 · 감사 |
| 정제 | 타입·시각·중복 정리 | Parquet + Iceberg | 400일 | 9.12 GB | 학습 · 정산 |
| 마트 | 미리 집계한 것 | 열로 눕힌 저장 | 720일 | 0.09 GB | 대시보드 · 리포트 |

가운데 줄의 Parquet 은 같은 열의 값끼리 붙여 두는 포맷이라 조회 비용이 싸다. 보존 기간까지 곱하면 세 층 합이 5.69 TB 이고, 그중 원본이 1.98 TB 로 34.7% 를 먹는다. 저장 비용을 줄이자는 회의에서 "원본을 지우자"는 말이 나오는 자리가 여기다.

지우면 셋을 잃고, 그 셋이 다 돈으로 돌아온다. 첫째는 재처리다. 노출과 클릭을 붙이는 범위를 3시간에서 6시간으로 늘리려면 원본이 있어야 한다.

둘째는 감사다. 정산 금액이 틀렸다는 문의가 오면 우리가 받은 것을 그대로 보여야 하는데, 정제 층에 있는 것은 우리가 해석한 결과다. 광고주와 매출을 두고 다투는 자리에서 이 구분이 승패를 가른다. 셋째는 스키마 사고다. 필드가 지워져 잡이 죽었을 때 원본이 없으면 그 며칠은 영원히 비어 있다.

**되돌릴 수 없는 변환을 원본에 섞으면 이 셋이 한꺼번에 사라진다.**

| 원본에 섞기 쉬운 변환 | 왜 되돌릴 수 없나 | 대신 어디서 |
|---|---|---|
| 개인 식별자 해시 | 원래 값을 못 되살린다 | 정제 층에서 열을 하나 더 |
| 시각을 날짜로 자르기 | 시·분·초가 사라진다 | 정제 층의 기준 열로 |
| 소수 반올림 | 잘린 자릿수가 사라진다 | 마트에서 표시용으로 |
| 필요 없는 필드 삭제 | 나중에 필요해져도 없다 | 정제 층에서 안 읽으면 그만 |
| 조인해서 합치기 | 어느 쪽이 원본인지 흐려진다 | 정제 층에서 새 테이블로 |

원칙은 하나다. **원본에는 더하기만 하고 빼기·바꾸기는 안 한다.** 결정도 둘로 끝난다. 원본 1.98 TB 는 비용을 아끼자는 말이 나와도 안 지우고, 마트는 소비자별로 늘려도 66.4 GB 라 싸다. 다음 절은 그 마트에 값이 두 벌로 들어와 안 맞는 상황이다.

## 4. 배치와 스트림 — 값이 어긋날 때

**같은 클릭 수를 스트림은 2,202,480건, 배치는 2,273,160건으로 센다. 틀린 쪽은 없고, 매출은 한쪽으로만 청구된다.**

두 말부터 푼다. **스트림**은 들어오는 대로 계속 세는 방식이고, **배치**는 하루치를 다 모은 뒤 한 번에 세는 방식이다. 둘 다 있어야 하는데 여기서 돈이 걸린 골칫거리가 생긴다. **같은 지표를 두 경로로 계산하면 값이 다르게 나온다.**

이유는 늦게 도착하는 이벤트다. 스트림은 5분짜리 **창**으로 세는데, 창은 몇 분치를 묶어 셀지 정해 둔 시간 토막이다. 창이 닫히면 값이 확정돼 그 뒤에 온 건은 못 들어간다.

```python
# 같은 클릭 수를 스트림과 배치가 다르게 세는 이유.
#
# 스트림은 5분 창이 닫히면 그 창을 확정한다. 늦게 온 건은 그 창에 못 들어간다.
# 배치는 event_ts 로 다시 묶으니 늦게 온 건도 원래 시각 자리에 넣는다.
# 아래 분포는 지어낸 값이다. 노출 2.28억 · 기저 CTR 1.0% 는 형제 글과 같다.
from unicodedata import east_asian_width

IMPRESSIONS = 228_000_000
CLICKS = 2_280_000                      # 기저 CTR 1.0%

# 도착 지연 분포 — (구간 이름, 비중)
BUCKETS = [
    ("1분 이내",       0.920),
    ("1분~5분",        0.046),
    ("5분~3시간",      0.022),
    ("3시간~24시간",   0.009),
    ("하루 넘김",      0.003),
]

# 경로 — (이름, 이 경로가 세는 구간 수)
ROUTES = [
    ("스트림 5분 창",   2),
    ("배치 D+1",        4),
    ("배치 D+2 재집계", 5),
]

def w(s):
    return sum(2 if east_asian_width(c) in "WF" else 1 for c in s)

def row(*cells):
    print("".join(" " * (n - w(c)) + c for c, n in cells))

print(f"클릭 {CLICKS:,}건이 언제 도착하나 (합계 {sum(b[1] for b in BUCKETS):.3f})")
row(("구간", 16), ("비중", 9), ("건수", 12))
for name, share in BUCKETS:
    row((name, 16), (f"{share:.1%}", 9), (f"{round(CLICKS * share):,}", 12))
print()

print("경로마다 몇 건을 세나")
row(("경로", 20), ("세는 건수", 12), ("전체 대비", 11), ("CTR", 9), ("확정과 차이", 13))
final = round(CLICKS * sum(b[1] for b in BUCKETS[:ROUTES[-1][1]]))
for name, upto in ROUTES:
    got = round(CLICKS * sum(b[1] for b in BUCKETS[:upto]))
    row((name, 20), (f"{got:,}", 12), (f"{got / CLICKS:.1%}", 11),
        (f"{got / IMPRESSIONS:.3%}", 9), (f"{got - final:+,}", 13))
print()
print(f"스트림과 D+1 의 차이: {round(CLICKS * sum(b[1] for b in BUCKETS[:4])) - round(CLICKS * sum(b[1] for b in BUCKETS[:2])):,}건")
print(f"D+1 과 확정의 차이: {final - round(CLICKS * sum(b[1] for b in BUCKETS[:4])):,}건")
print()
print("→ 대시보드의 0.966% 는 틀린 값이 아니라 5분 창이 세는 값이다.")
print("→ 두 값을 나란히 두면 싸움이 난다. 어느 쪽이 확정인지 한 곳에만 적어 둔다.")

# 출력:
# 클릭 2,280,000건이 언제 도착하나 (합계 1.000)
#             구간     비중        건수
#         1분 이내    92.0%   2,097,600
#          1분~5분     4.6%     104,880
#        5분~3시간     2.2%      50,160
#     3시간~24시간     0.9%      20,520
#        하루 넘김     0.3%       6,840
#
# 경로마다 몇 건을 세나
#                 경로   세는 건수  전체 대비      CTR  확정과 차이
#        스트림 5분 창   2,202,480      96.6%   0.966%      -77,520
#             배치 D+1   2,273,160      99.7%   0.997%       -6,840
#      배치 D+2 재집계   2,280,000     100.0%   1.000%           +0
#
# 스트림과 D+1 의 차이: 70,680건
# D+1 과 확정의 차이: 6,840건
#
# → 대시보드의 0.966% 는 틀린 값이 아니라 5분 창이 세는 값이다.
# → 두 값을 나란히 두면 싸움이 난다. 어느 쪽이 확정인지 한 곳에만 적어 둔다.
```

돈이 걸린 사고가 나는 지점은 값이 다르다는 것 자체가 아니다. **어느 쪽이 확정인지를 아무도 안 적어 둔 것이다.** 광고주가 대시보드의 0.966% 와 청구서의 0.997% 를 나란히 보면 그 자리에서 환불 요구가 나오고, 매출이 그만큼 깎인다.

푸는 방법은 셋이고 셋 다 실무에서 쓴다.

| 방법 | 무엇을 하나 | 대가 |
|---|---|---|
| 확정을 한 곳으로 | 배치 값만 공식으로, 스트림은 "잠정" | 대시보드 숫자를 못 인용한다 |

### 중복은 어디서 거르나

덮어쓰기가 되려면 두 번 써도 결과가 같아야 한다. 그 성질에 붙은 이름이 셋이고, 셋의 비용이 다르다.

| 보장 | 무슨 뜻인가 | 유실 | 중복 | 비용 |
|---|---|---|---|---|
| 많아도 한 번 | 한 번만 보내고 만다 | 있다 | 없다 | 가장 싸다 |
| 적어도 한 번 | 확인 못 받으면 또 보낸다 | 없다 | 있다 | 보통 |
| 정확히 한 번 | 보내는 쪽과 받는 쪽을 한 묶음으로 | 없다 | 없다 | 비싸다 |

셋째 이름이 오해를 부른다. **한 번만 배달된다는 뜻이 아니라 결과가 한 번만 반영된다는 뜻이다.** 그 한 묶음 처리를 **트랜잭션**이라 부르는데, 대개 한 시스템 안에서만 성립해 목적지가 ClickHouse 면 경계에서 보장이 끊긴다.

그래서 흔한 결정이 **확인 못 받으면 또 보내기 + 멱등 쓰기**다. 재전송률 0.4% 면 하루 중복 후보가 912,000건이라, 그냥 두면 정산이 부풀어 손해가 난다.

거를 수 있는 자리는 넷이다. 수집 서버, producer, 처리 잡, 그리고 목적지에 실제로 쓰는 자리다. **뒤로 갈수록 앞의 중복까지 받아 내고 맨 뒤가 가장 확실하다.** 앞의 셋은 창이 있어 그 밖을 못 보지만, 목적지의 기본 키에는 창이 없다. 키는 보내는 쪽이 만든다. 받는 쪽이 도착 시각으로 붙이면 멱등이 깨진다.

정산의 결정은 두 단계다. 스트림 값은 잠정으로 두고 배치가 확정하며, 두 값의 차이가 갑자기 커지면 청구를 중단하는 편이 손해가 가장 적다.

## 5. 스키마가 깨질 때, 그리고 지난 30일을 다시 돌릴 때

**스키마 레지스트리의 기본 설정은 필드 삭제를 막지 않는다. 그래서 배포는 승인되고 사흘 뒤에 학습이 나빠진다.**

topic 하나를 여러 팀이 읽으면 그 모양이 팀 사이의 계약이 된다. **스키마 레지스트리**는 그 계약을 적어 두고, 새 스키마가 옛 것과 맞는지 검사해 주는 서버다. 아래는 그 계약을 Avro 로 적은 것이다.

```json
{"type":"record","name":"Impression","namespace":"ad",
 "fields":[
   {"name":"req_id","type":"string"},
   {"name":"seq","type":"int"},
   {"name":"ad_id","type":"long"},
   {"name":"slot","type":"string"},
   {"name":"media","type":"string"},
   {"name":"pctr","type":"double"},
   {"name":"event_ts","type":{"type":"long","logicalType":"timestamp-millis"}},
   {"name":"exp_id","type":["null","string"],"default":null}
 ]}
```

맨 아랫줄의 실험 번호만 기본값이 있고 나머지 일곱은 기본값이 없는 필수 필드다. 무엇을 맞다고 볼지는 **호환 모드**가 정하고, 셋만 알면 된다.

| 모드 | 무엇을 보장하나 | 허용되는 변경 |
|---|---|---|
| BACKWARD (기본값) | 새 스키마로 옛 데이터를 읽는다 | 필드 삭제 · 기본값 있는 추가 |
| FORWARD | 옛 스키마로 새 데이터를 읽는다 | 필드 추가 · 기본값 있는 삭제 |
| FULL | 양쪽 다 | 기본값 있는 필드만 추가·삭제 |

**기본값은 BACKWARD 이고, BACKWARD 는 필드 삭제를 허용한다.** 생산자가 지면 필드를 지운 스키마를 올려도 검사는 맞다고 답하고, 배포가 그대로 승인된다.

왜 통과하는지가 이 절에서 가장 어려운 대목인데, 기준이 한쪽 방향만 보기 때문이다. BACKWARD 가 검사하는 것은 새 스키마로 옛 데이터를 읽을 수 있나뿐이고, 옛 데이터에는 지면 필드가 있으니 문제가 없다. 정작 사고가 나는 방향은 반대다. **옛 스키마를 든 소비자가 지면 없는 새 데이터를 만나는 경우**를 BACKWARD 는 아예 안 본다.

:::deep 더 깊이 — 등록 전에 맞는지만 물어보는 요청
응답에 `{"is_compatible":true}` 가 오면 등록해도 된다는 뜻이고, 그 판정은 위 호환 모드가 정한다. 배포 스크립트에서 이 요청을 먼저 던지면 승인 전에 사고를 막는다.

```http
POST /compatibility/subjects/ad.impression.clean-value/versions/latest HTTP/1.1
Host: schema-registry:8081
Content-Type: application/vnd.schemaregistry.v1+json

{"schemaType":"AVRO","schema":"{\"type\":\"record\",\"name\":\"Impression\",\"fields\":[...]}"}
```
:::

승인이 난 뒤 무슨 일이 벌어지는지를 날짜로 적으면 이렇다.

| 시각 | 무슨 일 | 에러가 나나 |
|---|---|---|
| D+0 10:14 | 생산자 배포. 지면 필드 삭제. 등록 통과 | 안 난다 |
| D+0 10:14 | 스트림 잡이 지면을 빈 값으로 읽는다 | 안 난다 |
| D+0 10:19 | 대시보드 지면별 막대가 한 칸으로 뭉침 | 안 난다 |
| D+1 01:00 | 배치가 지면을 빈 값으로 씀 | 안 난다 |
| D+1 06:00 | 학습이 지면 피처를 상수로 받음 | 안 난다 |
| D+3 | pCTR 오프라인 지표가 내려간 것을 발견 | — |
| D+7 | 광고주가 지면별 항목이 없다고 문의 | — |

**일곱 줄 중 다섯 줄에서 에러가 안 난다.** 파이프라인은 끝까지 멀쩡히 돌고 처음 발견되는 자리가 D+3 의 사람이다. 그 사흘치로 학습한 모델이 매출을 얼마나 깎았는지는 나중에도 못 센다.

막는 결정은 셋이다. 여러 팀이 읽는 topic 은 FULL 로 두면 기본값 없는 필드의 삭제가 등록 단계에서 거절된다. 새 필드는 기본값을 달아서 넣고, 정말 지워야 하면 소비자를 먼저 다 바꾼 뒤에 생산자가 지운다.

### 지난 30일을 다시 돌리기

조인 조건이 잘못돼 클릭 일부가 라벨에 안 붙었다고 하자. 고친 코드로 지난 30일을 다시 돌리는 일을 **백필**, 곧 지난 기간 다시 돌리기라고 부른다.

30일이면 6,840,000,000줄이고, 워커 40개가 각각 초당 5,000줄을 처리하면 합쳐서 초당 200,000줄이다. 다 도는 데 9.5시간이 걸린다.

정상 유입이 초당 2,639건이니 백필은 그 75.8배 속도로 돈다. **이 배수가 백필의 진짜 문제다.** 그동안 클러스터를 정상 파이프라인과 나눠 쓰니 대시보드의 888 ms 예산이 흔들린다. 그래서 백필은 별도 클러스터나 한산한 시간대로 민다.

돌리기 전에 확인할 것은 넷이다. 원본이 30일 이상 남아 있어야 한다. 큰 테이블을 조회 조건에 맞춰 미리 잘라 둔 조각을 **파티션**이라 하는데, 하루 단위여야 그 기간만 골라 지운다. 같은 파티션을 덮어써도 돼야 하고, 안 그러면 두 번 돌린 값이 두 배가 되어 정산이 틀어진다.

넷째가 가장 어렵고, 여기서 틀리면 9.5시간을 쓰고도 결정을 못 내린다. **처리 코드가 바깥 값을 읽으면 재처리 결과가 달라진다.**

| 코드 안의 것 | 다시 돌리면 | 어떻게 하나 |
|---|---|---|
| 지금 시각을 찍는 함수 | 오늘 날짜가 박힌다 | 이벤트 시각에서 계산한다 |
| 조회 저장소에서 붙인 광고 카테고리 | 오늘 카테고리가 붙는다 | 붙인 값을 원본에 같이 남긴다 |
| 무작위 샘플링 | 다른 줄이 뽑힌다 | 키를 해시해 뽑는다 |
| 실행 순서에 기대는 집계 | 순서가 달라진다 | 키로 정렬한 뒤 집계한다 |

둘째 줄이 가장 자주 밟힌다. 광고 카테고리를 조회 저장소에서 가져와 붙이면 그 값은 오늘 것이라, 30일 전 줄에 붙는 순간 학습 데이터가 오염된다. 답은 3절의 원칙 그대로다. 카테고리 열을 하나 더 만들어 그때 값을 적어 둔다.

전체를 돌리기 전에 하루를 골라 고치기 전 코드로 다시 돌려 보고, 줄 수와 합계와 해시가 같으면 30일을 돌려도 된다는 승인이 선 것이다.

## 6. 매일 보는 것 다섯

**읽기 밀림, 건수 대조, 지연 분위수, 실패 큐, 그리고 파일 크기. 각자 다른 종류의 사고와 비용을 잡는다.**

파이프라인이 돌기 시작하면 매일 보는 것이 정해진다. 다섯인데, 하나가 놓치는 사고를 다른 하나가 잡는다.

| 무엇 | 무엇을 잡나 | 이 글 규모의 임계값 | 안 보면 |
|---|---|---|---|
| 읽기 밀림 | 읽는 쪽이 밀리는 것 | 30초치 = 79,170건 | 마감을 넘기고 안다 |
| 단계별 건수 대조 | 중간에서 새는 것 | 유실률 0.1% | 줄어든 것을 모른다 |
| 처음부터 끝까지 걸린 시간 | 한 구간만 느려지는 것 | 느린 쪽 1% 가 10초 | 평균만 보면 안 보인다 |
| 실패 큐 유입 | 못 처리한 건이 쌓이는 것 | 하루 2,000건 | 버려진 줄을 모른다 |
| 파일 크기·개수 | 저장 비용과 조회 속도 | 파일당 30 MB 아래 | 조회가 느려진다 |

셋째 줄만 풀어 둔다. 평균 지연이 좋아 보여도 느린 쪽 1% 가 10초를 넘으면 그 안에 정산 로그가 있을 수 있어서, 평균이 아니라 느린 쪽 끝을 본다.

**둘째가 가장 안 만들어져 있고 가장 값어치가 크다.** 단계마다 건수를 세어 나란히 놓기만 하면 되는데, 이 표가 없으면 정산 문의에 답할 근거가 없다.

| 지점 | 하루 건수 | 앞 단계 대비 |
|---|---|---|
| SDK 발신 | 228,000,000 | — |
| 수집 서버 수신 | 227,880,000 | −120,000 |
| Kafka 적재 | 227,862,000 | −18,000 |
| 정제 층 | 227,862,000 | 0 |
| 마트 | 227,862,000 | 0 |

전체 유실이 138,000건, 비율로는 0.061% 다. **어디서 샜는지가 이 표에 그대로 나온다.** 새는 자리를 모르면 정산 담당자에게 그 비율의 출처를 설명할 수 없고, 설명이 안 되면 매체 지급이 중단된다.

실패 큐는 처리하다 끝내 실패한 건이 가는 자리다. 하루 1,800건 중 스키마 불일치가 940건으로 절반을 넘는다. **쌓인 건은 버린 것이 아니라 다시 돌릴 것이다.** 사유를 고쳐 다시 흘려 넣어야 그 건들이 매출로 살아난다. 실패 큐를 만들고 안 보는 것이 가장 흔한 손해다.

마지막이 파일 크기다. 3절의 정제 층 하루 9.12 GB 를 시간 단위로 자르면 파일이 288개, 파일당 31.7 MB 다. 분 단위면 17,280개가 되고 파일당 0.53 MB 다.

작은 파일이 왜 손해인지는 여는 비용에 있다. 파일 하나를 여는 비용은 크기와 거의 상관없이 일정하다. 개수가 60배면 여는 비용도 카탈로그 메타데이터도 60배다.

마지막 결정은 이렇다. **파티션은 조회 조건에 맞춰 자르되, 파일이 너무 작아지면 뒤에서 합친다.** 조회 비용은 그렇게 잡는다. 이 다섯이 다 정상인데 모델만 나빠지는 경우는 [모델 모니터링](post.html?id=model-monitoring)이 따로 다룬다.

## 헷갈리기 쉬운 점

**"Kafka 를 쓰면 파이프라인이 있는 것이다"** — 버퍼 층 하나가 생긴 것이다. 처리 잡이 목적지마다 직접 쓰고 있으면 연결 30개 상태 그대로다.

**"실시간이 좋은 것이다"** — 마감이 33시간인 정산을 스트림으로 붙이면 비용을 25배 더 내고 같은 결과를 얻는다.

**"스키마 레지스트리가 있으니 안 깨진다"** — 기본 모드는 필드 삭제를 통과시킨다. 배포가 승인돼도 사흘치 학습 데이터가 매출을 깎을 수 있다.

**"대시보드 숫자가 틀렸다"** — 0.966% 는 5분 창이 세는 값이다. 고칠 것은 숫자가 아니라 어느 쪽이 확정인지 안 적어 둔 결정이다.
