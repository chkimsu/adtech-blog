요청 경로 시뮬레이터

LB · Ingress · API Gateway · 서비스 메시는 한꺼번에 설계된 것이 아닙니다. 부품을 하나씩 꺼 보면 각자 어떤 문제 때문에 생겼는지가 드러납니다 — 없으면 무엇이 터지나.

이 데모가 보여주는 것매체가 보낸 입찰 요청 한 건이 bidder 까지 가는 길에 네 부품이 서 있습니다. 하나를 끄고 요청을 보내면 어느 칸에서 멈추는지, 그리고 그 부품이 하던 일이 사람 쪽으로 몇 개 옮겨오는지 확인합니다.
왜 알아야 하나넷 다 "요청을 어디로 보낼지 정하는" 일을 해서 경계가 헷갈립니다. 끄고 켜 보면 각자 답하는 문제가 다르다는 게 드러납니다. 도입 순서를 정할 때 쓰는 판단이 이것입니다.
    이렇게 해보세요 — 4분
  1. 기본값에서 요청 한 건 보내기 — 칸이 하나씩 켜지며 bidder 까지 도착합니다.
  2. Ingress 를 끄면 서비스 4개에서 멈춥니다. 서비스 수를 1로 내리면 다시 통과합니다.
  3. API Gateway 를 끄면 매체 3곳에서 멈춥니다. 매체 수를 1로 내리면 다시 통과합니다.
  4. 서비스 메시 를 켜면 요청은 그대로 도착하지만 12ms 예산이 사이드카만큼 깎입니다.
설정 — 매체와 이 DSP는 같은 데이터센터 안에서 전용 회선으로 붙어 있습니다. 주소는 사설 10.0.x.x, 평문 http, 응답 예산은 12ms. 그래서 여기서 세는 것에 공인 IP도 TLS 인증서도 없습니다. 세는 것은 관리할 대표 주소, 대상 그룹 설정, 정책을 구현한 벌수, 그리고 사이드카가 먹는 시간입니다.

이 데모에서 알게 된 3가지

  1. 없어도 되는 구간이 있다 — 서비스가 1개, 매체가 1곳이면 Ingress도 API Gateway도 없이 요청이 통과한다. 부품이 처음부터 필요했던 게 아니다.
  2. 숫자가 늘 때 터진다 — 서비스가 2개가 되는 순간 경로로 나눌 수단이, 매체가 2곳이 되는 순간 인증·쿼터를 한곳에서 볼 자리가 필요해진다. 부품은 그 자리에 들어온다.
  3. 부품을 빼도 일은 안 사라진다 — 사람이 관리하는 주소·설정·정책 벌수로 옮겨갈 뿐이다. 서비스 4개면 1벌이 4벌이 된다.

현업에서는 이렇게 씁니다

"우리도 API Gateway 넣어야 하나" 같은 질문은 부품 이름으로는 답이 안 나옵니다. 지금 서비스가 몇 개인지, 매체가 몇 곳인지를 넣어 보고 어디서 먼저 터지는지를 보는 쪽이 빠릅니다.

  • 도입 순서 정하기: 서비스를 쪼개기 전에 Ingress를 먼저 넣을 필요는 없습니다. 반대로 매체를 한 곳 더 붙이기로 했다면 인증·쿼터를 서비스마다 복사하기 전에 게이트웨이 자리를 먼저 잡는 게 쌉니다.
  • 배포 손실 점검: LB만 붙였다고 배포 손실이 0이 되지는 않습니다. LB는 새 연결만 돌리므로, 앱이 종료할 때 남은 연결을 스스로 닫아 줘야(graceful shutdown) 마지막 몇백 건이 안 샙니다.
  • 메시는 저울로 봅니다: 재시도·타임아웃·mTLS를 앱 밖으로 빼는 대신 홉마다 사이드카 왕복이 붙습니다. 12ms 예산의 입찰 경로에서는 이 숫자를 먼저 재고 결정합니다.
