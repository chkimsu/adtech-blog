지훈 씨는 모델 팀으로 옮긴 지 다섯째 주입니다. 지난주에 등록한 새 pCTR 모델(광고가 클릭될 확률을 예측하는 모델) v418 을 오늘 아침 처음으로 실제 서버에 올립니다. 배포 화면을 열자 첫 칸이 「새 버전에 보낼 트래픽 비율」이었고 기본값은 1 이었습니다.

옆자리 선배가 한마디 덧붙였습니다. 「올리는 건 몇 초면 되는데, 되돌리는 순서를 먼저 알고 눌러요.」 지훈 씨는 이 말이 이상했습니다. 오프라인 평가에서 v418 은 어제 모델보다 좋았고 게이트도 통과했는데, 왜 전부가 아니라 1 로 시작하는지, 왜 되돌릴 준비부터 하라고 하는지 알 수 없었습니다.

**새 모델을 왜 1% 에게만 먼저 보여 주고 무엇을 보고 나머지 99% 로 넓힐까요?**

배포 화면의 기본값 1 은 트래픽의 1%, 요청 100건 가운데 1건만 새 버전으로 보낸다는 뜻입니다. 이렇게 트래픽의 일부에만 새 버전을 보내 지표를 확인한 뒤 비율을 넓혀 가는 방식을 카나리(canary) 배포라고 부릅니다. 비율을 넓혀도 되는지 정하는 조건은 게이트입니다. 게이트에 걸렸을 때 옛 버전으로 돌아가는 일은 롤백(rollback)이라고 부르며 이 글에서는 되돌리기라고도 씁니다. 지훈 씨가 통과한 게이트는 어제 로그로 채점한 오프라인 평가의 게이트였는데, 이 글이 다루는 게이트는 실제 요청을 받는 동안 판정하는 온라인 게이트입니다. 카나리 배포, 게이트, 롤백 세 가지를 지훈 씨의 첫 배포 하루를 따라 차례로 보고 나면 「배포했다」는 말이 어느 단계까지 갔다는 뜻인지, 사고가 났을 때 몇 분 안에 무엇을 눌러야 하는지 알 수 있습니다.

> **한 줄 요약:** 새 모델은 트래픽 1% 에서 시작해 게이트 4개를 모두 통과할 때마다 10%, 50%, 100% 로 넓힙니다. 게이트가 하나라도 걸리면 요청을 버전별로 나눠 보내는 게이트웨이에서 새 모델 몫의 가중치를 0 으로 바꾸는데, 옛 모델이 아직 떠 있으므로 이 되돌리기는 몇 초면 끝납니다. 지훈 씨의 첫 배포는 10% 단계에서 COPC(실제 클릭 수 ÷ 예측 클릭 수, 1 에 가까울수록 예측이 맞음)가 1.09 로 나와 게이트에 걸렸고 알람이 울린 지 14분 만에 옛 모델로 돌아와 확인까지 마쳤습니다.

> **골라 읽는 법** — 절이 8개이고 절마다 카드 한 장이나 표 하나가 있어 카드나 표만 보고 넘어가도 됩니다.
>
> - 한 번에 다 바꾸지 않는 까닭 → 1절
> - 응답에는 쓰지 않고 계산만 하는 섀도 배포 → 2절
> - 1%, 10%, 50%, 100% 로 넓히는 순서 → 3절
> - 넓혀도 되는지 정하는 게이트 4개와 놀이터 → 4절
> - 그날 아침 07:04 부터 07:18 까지의 시간선 → 5절
> - 새 서버가 처음 30초 동안 느린 까닭 → 6절
> - 되돌리기가 초 단위로 끝나는 구조 → 7절
> - 광고가 나가는 앱이 우리 회사 것일 때(담장 안)와 남의 것일 때(열린 RTB)의 차이 → 8절

이 글의 모델 이름, 시각, 숫자는 모두 설명을 위해 만든 가상 값입니다. 그 가운데 요청량 초당 2,639건, 모델 서버 12대, 8ms 예산, 초과율 4.62% 는 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편에서 쓴 값을 그대로 가져왔습니다. 8ms 예산은 모델 호출 한 번에 허용한 시간입니다. 초과율은 모델 호출이 그 8ms 를 넘긴 비율이라 낮을수록 좋은데, 평소에도 모델 호출의 4.62% 는 8ms 를 넘깁니다.

## 1. 한 번에 전부 바꿀 때의 손해, 1분에 15만 건

**모델 서버 12대가 답하는 요청은 초당 2,639건이라 새 모델에 문제가 있다면 100% 로 올린 순간부터 1분에 요청 158,340건이 틀린 점수를 받습니다. 그래서 새 모델로 보내는 트래픽의 비율을 나눠 일부에만 먼저 보냅니다.**

지훈 씨처럼 오프라인 평가를 통과했는데 왜 실제 요청으로 또 확인하느냐고 물을 수 있습니다. 오프라인 평가는 어제 로그로 새 모델을 채점하는데, 어제 로그에는 어제 모델이 골라 실제로 내보낸 광고의 결과만 남아 있습니다. 새 모델이 어제 모델과 다른 광고를 고르면 그 광고의 결과는 로그에 없으므로, 오프라인에서 좋았던 모델이 실제 요청에서는 다른 답을 내는 일이 생깁니다. 오프라인 평가와 실제 결과가 이렇게 달라지는 문제는 [피드백 루프 편향](post.html?id=feedback-loop-bias) 편의 주제입니다. 이 글은 새 모델이 좋은지 나쁜지는 실제 요청을 받아 봐야 안다는 결론만 가져옵니다.

다만 실제 요청으로 확인하는 동안 새 모델에 문제가 있으면 그 요청들은 틀린 점수를 받으므로, 확인을 전체 요청으로 하면 확인하는 동안의 손해가 너무 큽니다. 손해의 크기는 문제를 발견하기까지 새 모델이 답한 요청 수로 셉니다. 요청이 초당 2,639건 오고 새 모델의 문제를 발견하는 데 40분이 걸린다고 가정합니다. 새 모델이 답한 요청 수는 초당 요청 × 새 모델에 보낸 비율 × 초입니다. 100% 로 보내면 1분(60초)에 2,639 × 60 = 158,340건이 새 모델을 지나므로, 40분 동안에는 그 40배인 6,333,600건이 새 모델의 점수를 받습니다. 비율을 10% 와 1% 로 낮추면 같은 40분 동안 새 모델이 답하는 요청이 아래 표처럼 10분의 1, 100분의 1 로 줄어듭니다.

| 새 모델에 보낸 비율 | 40분 동안 새 모델이 답한 요청 | 문제였다면 |
|---|---|---|
| 100% | 6,333,600건 | 전부 틀린 점수 |
| 10% | 633,360건 | 10분의 1 |
| 1% | 63,336건 | 100분의 1 |

1% 로 시작하면 새 모델에 문제가 있더라도 같은 40분 동안 틀린 점수를 받는 요청이 63,336건으로 100% 일 때의 100분의 1 에 그칩니다. 대신 새 모델을 지나는 요청도 100분의 1 로 줄어 1% 로는 알 수 있는 것이 적습니다. 4절에서 계산하겠지만 1% 로 5분을 보내면 클릭이 79건밖에 모이지 않아 새 모델의 보정 상태(예측한 클릭 확률이 실제 클릭 비율과 맞는지)를 판정할 수 없습니다. 그래서 1% 에서 10% 로, 10% 에서 50% 로 넓혀 가며 단계마다 다른 것을 확인합니다. 비율을 나누는 결정은 확인하는 동안의 손해를 줄이고 비율을 넓히는 결정은 확인할 수 있는 것을 늘립니다. 이 두 결정보다 먼저 거치는 단계는 다음 절의 섀도 배포입니다.

## 2. 계산만 하고 응답에는 쓰지 않는 섀도 배포

**섀도(shadow) 배포는 요청을 복사해 새 모델에도 보내되 사람에게 나가는 응답에는 옛 모델의 점수만 씁니다. 그래서 같은 요청에 대한 두 모델의 예측값이 로그에 나란히 남고 새 모델이 틀려도 손해는 0 입니다.**

카나리 배포는 1% 로 시작해도 그 1% 의 요청에는 새 모델의 점수를 실제로 쓰므로, 새 모델에 문제가 있으면 1% 만큼의 손해는 생깁니다. 섀도 배포에서는 새 모델이 실제 요청을 계산해도 내보내는 답은 옛 모델 것뿐이라, 그 1% 의 손해도 없이 새 모델이 얼마나 틀리는지를 알 수 있습니다.

이 글의 카드 다섯 장은 색을 같은 뜻으로 씁니다. 파랑은 놓여 있는 것(로그, 가중치 규칙), 벽돌색은 지금 들어오는 것(요청, 알람), 먹색은 모델과 서버, 회색은 무언가를 만드는 작업(복사, 가중치 바꾸기, 웜업)이고 점선 상자는 미리 적어 둔 것(게이트 조건)입니다. 가중치 규칙(요청을 버전별로 몇 대 몇으로 나눌지 적은 규칙)은 3절에서, 웜업(warm-up, 진짜 요청을 받기 전에 더미 요청을 먼저 보내는 작업)은 6절에서 자세히 봅니다. 첫 카드에서는 요청 한 건이 복사되어 옛 모델 v417 의 점수만 응답이 되고 새 모델 v418 의 점수는 로그에만 남는 길을 보면 됩니다.

요청 한 건이 API 서버(요청을 받아 모델에 점수를 물어보는 서버)에 오면 API 서버는 그 요청을 복사해 v417 과 v418 두 곳으로 보냅니다. 지금 운영 중인 v417 이 낸 점수는 그대로 응답이 되지만 v418 이 낸 점수는 응답에 쓰지 않고 로그에만 적으므로, 로그 한 줄에는 같은 요청에 대한 두 모델의 점수가 나란히 남습니다. 예를 들어 v417 이 클릭 확률을 0.0412 로 예측한 광고를 v418 은 0.0455 로 예측했다는 식입니다.

섀도 배포로는 세 가지를 알 수 있습니다. 첫째로 새 모델이 8ms 예산 안에 답하는지가 보이는데, 실제 요청의 크기와 모양 그대로 측정하므로 미리 만든 요청을 보내 서버의 처리 한계를 확인하는 부하 시험보다 정확합니다. 둘째로 두 모델이 낸 예측값의 분포를 평균과 분위수(값을 크기순으로 늘어놓았을 때 아래에서 몇 % 자리에 오는 값)로 겹쳐 보면, 한쪽 모델의 예측값이 크게 올라갔거나 양 끝으로 쏠렸는지가 보입니다. 셋째로 두 모델이 1위로 고른 광고가 얼마나 다른지를 봅니다. 요청의 절반에서 1위 광고가 바뀐다면 카나리 배포로 넘어갔을 때 지표가 크게 움직이리라는 것을 섀도 단계에서 미리 알 수 있습니다.

반면 클릭은 섀도 배포로 알 수 없습니다. 사람에게 나간 광고는 v417 이 고른 광고라서 v418 이 골랐을 광고를 사람들이 클릭했을지는 로그에 남지 않으므로, 새 모델이 돈이 되는지는 섀도 배포가 아니라 v418 의 점수를 실제 응답에 쓰는 카나리 배포에서 확인합니다.

섀도 배포는 모델 서버 비용이 두 배로 듭니다. 요청을 전부 복사하면 v418 도 v417 과 같은 양의 요청을 계산해야 하므로, 운영 중인 12대 말고도 모델 서버가 12대 더 필요합니다. 그래서 섀도 배포는 하루 종일 돌리지 않고 두세 시간만 돌리거나 요청의 절반만 복사해 돌립니다. 지훈 씨의 v418 은 전날 오후에 세 시간 동안 섀도 배포를 거쳤고 그동안 지연과 예측값 분포가 v417 과 거의 같았습니다. 다음 절에서는 v418 의 점수를 실제 응답에 쓰기 시작합니다.

## 3. 1, 10, 50, 100 으로 넓히는 카나리 배포

**카나리 배포에서 새 버전에 보내는 비율은 게이트웨이의 가중치 한 줄로 정합니다. 1% 에서 5분, 10% 에서 30분, 50% 에서 30분을 지켜본 뒤 100% 로 가는데, 단계마다 확인하는 것이 다릅니다.**

섀도 배포를 마친 v418 의 점수를 실제 응답에 쓰려면 운영 중인 v417 을 멈추지 않고 요청의 일부만 v418 로 보낼 수 있어야 합니다. 그래서 새 모델 서버 몇 대를 옆에 더 띄운 다음 요청을 나눠 주는 장치에 「100건 중 1건만 저쪽으로」라고 적어 두었다가 괜찮으면 그 숫자를 「10건」, 「50건」으로 바꿉니다. 두 번째 카드는 요청 100건 가운데 99건이 v417 로, 1건이 v418 로 나뉘는 모습과 가중치를 올리는 순서를 보여 줍니다.

요청을 나누는 장치는 API 서버 앞의 게이트웨이입니다. 게이트웨이의 구조는 [로드밸런서, Ingress, API Gateway](post.html?id=gateway-ingress-router) 편에 있습니다. 이 글에서는 요청을 어느 서버 그룹으로 보낼지 정하는 장치라는 뜻으로만 씁니다. 파드(pod)는 서버 프로그램을 컨테이너로 띄운 실행 단위입니다. 이 글에서 지금 운영 중인 모델 서버 12대는 v417 을 띄운 파드 12대입니다.

카나리 배포를 시작할 때는 v417 파드 12대를 그대로 두고 v418 파드 2대를 더 띄운 뒤, 게이트웨이 규칙에 v417 파드 99, v418 파드 1 의 가중치를 적습니다. 가중치는 두 파드 그룹에 요청을 나눠 줄 몫이라 99 대 1 이면 요청 100건 가운데 1건이 새 버전으로 갑니다. 가중치를 올리는 순서와 단계마다 머무는 시간은 배포 전에 미리 정해 두는데, 이 글은 아래 표처럼 가정합니다.

| 단계 | 비율 | 머무는 시간 | 이 단계에서 확인하는 것 |
|---|---|---|---|
| 1 | 1% | 5분 | 죽지 않나, 느리지 않나 (초과율, 오류율) |
| 2 | 10% | 30분 | 보정이 맞나 (COPC), 클릭률이 빠지지 않나 |
| 3 | 50% | 30분 | 절반 부하에서도 같은가 |
| 4 | 100% | 계속 | 옛 파드를 30분 더 두었다가 내립니다 |

1% 단계에서는 오류율(응답이 아예 오지 않은 비율)과 초과율로 서버가 죽거나 느려지지 않는지를 봅니다. 5분(300초) 동안 초당 2,639건의 1% 를 받으면 2,639 × 0.01 × 300 = 7,917건이 새 모델을 지나는데, 그 정도면 서버가 죽거나 8ms 를 크게 넘기는지는 보이므로 1% 단계는 5분으로 짧게 둡니다. 하지만 클릭률을 1% 로 가정하면 그 7,917건에서 나오는 클릭은 79건이라 보정이 맞는지 판정하기에는 턱없이 적습니다. 4절에서 계산하듯 보정 지표인 COPC 로 게이트를 판정하려면 클릭이 1,600건은 모여야 합니다. 그래서 10% 로 올려 30분을 지켜보는데, 그동안 요청 475,020건과 클릭 4,750건이 모여 COPC 를 읽을 수 있습니다. 50% 단계에서는 새 버전이 부하의 절반을 받으므로 부하가 오를 때 지연이 크게 늘지 않는지를 봅니다.

새 파드 수도 단계마다 함께 늘립니다. 10% 단계의 요청은 초당 264건(2,639건의 10%)이고 파드 한 대가 초당 287건까지 받으므로, 1% 와 10% 단계는 새 파드 2대로 여유가 있습니다. 50% 로 올리기 전에는 새 파드를 6대로 늘리고 100% 에서는 12대로 맞춥니다. 7절에서 보듯 가장 빠른 되돌리기는 옛 파드가 떠 있어야 쓸 수 있으므로, 옛 파드는 100% 가 된 뒤에도 30분을 더 두어 되돌릴 자리를 남긴 다음 내립니다. 다음 단계로 넘어가도 되는지는 다음 절의 게이트가 정합니다.

## 4. 넓혀도 되는지 정하는 게이트 4개

**게이트는 8ms 초과율 6% 이하, 오류율 0.1% 이하, COPC 0.95~1.05, 클릭률 차이 -2% 이상의 4개이고 하나라도 걸리면 넓히지 않고 되돌립니다.**

3절의 표가 단계마다 무엇을 확인할지를 정했다면 게이트는 확인한 값이 어디까지일 때 넓혀도 되는지를 정합니다. 다음 단계로 가려면 게이트 4개가 모두 열려야 하는데, 앞의 2개는 서버가 멀쩡한지를 보고 뒤의 2개는 모델이 돈을 잘 버는지를 봅니다. 세 번째 카드에는 게이트 4개의 한계값과 1% 단계, 10% 단계의 판정 결과가 함께 나옵니다.

게이트 4개를 표로 적으면 아래와 같습니다. 게이트가 보는 값은 새 모델 파드에서 측정해 같은 시간에 옛 모델 파드에서 측정한 값과 비교합니다.

| 게이트 | 무엇을 측정하나 | 한계 | 왜 이 값인가 |
|---|---|---|---|
| 8ms 초과율 | 모델 호출이 예산을 넘긴 비율 | 6% 이하 | 평소 4.62% 에 여유를 조금 둔 값 |
| 오류율 | 응답이 아예 안 온 비율 | 0.1% 이하 | 오류는 폴백으로 빠져 순위가 나빠집니다 |
| COPC | 실제 클릭 수 ÷ 예측 클릭 수 | 0.95~1.05 | 1 에서 멀수록 입찰가 전체가 틀립니다 |
| 클릭률 차이 | 새 버전 클릭률 - 옛 버전 클릭률 | -2% 이상 | 조금 빠지는 것은 잡음, 2% 는 신호 |

폴백(fallback)은 모델 점수를 받지 못했을 때 대신 쓰는 예비 경로입니다. 응답이 아예 오지 않은 요청은 폴백으로 빠져 광고 순위가 나빠지므로 오류율 한계를 0.1% 이하로 둡니다. 클릭률 차이는 새 버전의 클릭률에서 옛 버전의 클릭률을 뺀 값으로, 조금 빠지면 잡음(우연으로 생기는 흔들림)으로 보지만 2% 빠지면 신호(모델에 문제가 있다는 표시)로 봅니다.

COPC 는 [Calibration](post.html?id=calibration) 편에서 다룬 보정 지표로, 실제 클릭 수를 모델이 예측한 클릭 수로 나눈 값입니다. COPC 가 1 보다 크면 실제 클릭이 예측보다 많았다는 뜻이므로, 모델이 클릭 확률을 실제보다 낮게 본 이 상태를 과소예측이라고 부릅니다. 입찰가(광고 자리를 사려고 경매에 내는 값)는 예측한 클릭 확률을 따라 움직이므로 예측이 낮으면 입찰가도 낮아져 이길 수 있던 경매를 놓치고 예측이 높으면 광고 자리를 비싸게 삽니다. COPC 가 1 에서 멀수록 입찰가 전체가 틀리므로 COPC 게이트는 서버 상태를 보는 앞의 두 게이트보다 돈에 가깝습니다.

그런데 게이트 4개는 같은 시간을 지켜봐도 같은 확신으로 읽히지 않습니다. 초과율과 오류율은 요청이 수천 건만 모여도 충분히 읽힙니다. 반면 COPC 는 클릭 수로 계산하는데 클릭률이 1% 면 요청 100건에 클릭이 1건뿐이라, 클릭이 적은 동안에는 모델이 멀쩡해도 COPC 가 우연 때문에 크게 흔들립니다.

아래 코드는 COPC 가 얼마나 흔들리는지를 배포 단계마다 계산해 어느 단계부터 COPC 로 게이트를 판정할 수 있는지 보여 줍니다. 단계마다 판정 윈도우(지표를 모아 판정하는 시간 구간)에 모이는 요청과 클릭을 센 다음 흔들림 폭을 게이트 ±0.05 와 비교합니다. 표준오차(standard error)는 우연만으로 값이 흔들리는 정도입니다. 모델의 예측이 정확해도 클릭은 확률로 오므로 클릭 n 건에서 COPC 의 표준오차는 대략 1/√n 입니다. 코드는 그 2배인 2/√n 을 흔들림 폭으로 봅니다. 게이트 0.95~1.05 는 1 에서 위아래로 0.05 씩의 폭이라, 흔들림 폭이 0.05 보다 크면 COPC 가 게이트 밖에 나와도 우연인지 신호인지 구분할 수 없습니다.

```python
# 하는 일: 배포 단계마다 판정 윈도우에 모이는 요청과 클릭을 세고, COPC 가 우연으로 흔들리는 폭을 게이트 ±0.05 와 비교한다.
import math

# 1단계: 요청량과 배포 단계를 둔다
# 요청 초당 2,639건, 클릭률 1% 로 가정한다. 전부 가상 값이다.
QPS, CTR, GATE = 2639, 0.01, 0.05          # 게이트는 1 에서 ±0.05
stages = [("1%  5분", 0.01, 300), ("10%  5분", 0.10, 300),
          ("10% 30분", 0.10, 1800), ("50% 30분", 0.50, 1800)]

# 2단계: 단계마다 클릭 수와 COPC 흔들림 폭을 찍는다
# COPC 는 실제 클릭 ÷ 예측 클릭이다. 모델이 완벽해도 클릭은 확률로 오므로, 클릭 n 건에서 표준오차가 대략 1/sqrt(n) 이고 그 2배를 흔들림 폭으로 본다.
print("단계          요청        클릭   COPC 흔들림   판정")
for name, share, sec in stages:
    req = QPS * share * sec
    clicks = req * CTR
    band = 2 / math.sqrt(clicks)             # 2 × 표준오차
    ok = "읽을 수 있음" if band <= GATE else "못 읽음 (잡음이 게이트보다 큼)"
    print(f"{name}  {req:>10,.0f}  {clicks:>8,.0f}   ±{band:.3f}       {ok}")

# 3단계: 게이트 안에 넣는 데 필요한 클릭 수를 구한다
need = math.ceil((2 / GATE) ** 2)            # 흔들림이 게이트 안에 들어오는 최소 클릭
print(f"\n흔들림을 ±{GATE} 안에 넣으려면 클릭 {need:,}건이 필요하다")

# 출력:
# 2단계 뜻: 1% 단계 5분에는 클릭이 79건뿐이라 COPC 흔들림 ±0.225 가 게이트보다 크다. 10% 로 30분을 모으면 클릭 4,750건에 흔들림이 ±0.029 로 줄어 읽을 수 있다.
# 단계          요청        클릭   COPC 흔들림   판정
# 1%  5분       7,917        79   ±0.225       못 읽음 (잡음이 게이트보다 큼)
# 10%  5분      79,170       792   ±0.071       못 읽음 (잡음이 게이트보다 큼)
# 10% 30분     475,020     4,750   ±0.029       읽을 수 있음
# 50% 30분   2,375,100    23,751   ±0.013       읽을 수 있음
# 3단계 뜻: 흔들림이 ±0.05 안에 들려면 클릭이 1,600건은 모여야 한다.
#
# 흔들림을 ±0.05 안에 넣으려면 클릭 1,600건이 필요하다
```

출력에서 1% 5분 줄을 보면 요청 7,917건에 클릭이 79건뿐이라 흔들림 폭(2 를 79 의 제곱근으로 나눈 값)이 ±0.225 입니다. 그래서 예측이 정확히 맞는 모델이라도 이 단계의 COPC 는 우연만으로 0.78 에서 1.22 사이를 오갑니다. 이 흔들림 폭은 게이트 폭 ±0.05 보다 네 배 넘게 큽니다. 1% 단계에서 COPC 1.09 가 나와도 1.09 는 0.78~1.22 의 잡음 안에 있으므로 신호가 아닙니다.

10% 단계도 5분만 보면 요청 79,170건에 클릭이 792건이고 흔들림이 ±0.071 이라 아직 게이트보다 큽니다. 10% 에서 30분을 기다리면 클릭이 4,750건으로 늘고 흔들림이 ±0.029 로 줄어 게이트 ±0.05 안에 들어오므로, 이때부터 COPC 로 게이트를 판정할 수 있습니다. 50% 에서 30분을 보면 요청 2,375,100건과 클릭 23,751건이 모여 흔들림이 ±0.013 까지 줄어듭니다.

코드의 3단계가 찍은 1,600건은 흔들림을 게이트 안에 넣는 데 필요한 최소 클릭 수입니다. 흔들림 폭 2/√n 이 0.05 와 같아지는 n 은 2 ÷ 0.05 = 40 의 제곱인 1,600 이라, 10% 에서 5분의 792건은 1,600건에 못 미치고 30분의 4,750건은 1,600건을 넘습니다. 그래서 3절 표의 「이 단계에서 확인하는 것」이 단계마다 다릅니다. 1% 에서는 서버 게이트 2개(초과율, 오류율)만 보고 COPC 와 클릭률은 10% 에서 30분이 지난 뒤에 봅니다.

놀이터에서는 이 계산을 직접 해 볼 수 있습니다. 배포 단계를 고르고 새 모델의 값 4가지(초과율, 오류율, COPC, 클릭률 차이)를 움직이면 게이트 4개의 판정과 되돌림 여부가 바뀝니다.

| 07:18 | v418 파드 2대 내림. 초과율과 COPC 가 평소 값으로 돌아온 것 확인 | 지훈 씨 |

07:01 에 나온 COPC 1.09 는 실제 클릭이 예측보다 9% 많았다는 뜻이라, v418 이 클릭 확률을 낮게 봤고 그만큼 입찰가를 낮게 냈습니다. 오프라인 평가에서 v418 의 COPC 는 1.06 이었는데 실제 요청에서는 1.09 로 1 에서 더 멀어졌습니다. 지훈 씨 팀은 그날 오후에 v418 이 클릭 확률을 낮게 본 원인을 찾았습니다. 학습 데이터의 마지막 사흘에 새 지면(광고가 노출되는 화면 자리)의 로그가 빠져 있었는데, 그 지면은 클릭률이 평균보다 높은 곳이었습니다. 로그가 어디서 빠졌는지는 [학습 파이프라인](post.html?id=training-pipeline-dag) 편에서 다룹니다.

알람부터 확인 끝까지 14분이 어디에 쓰였는지 나눠 보면, 기계가 한 일은 07:10 에 가중치를 바꾼 뒤 07:11 에 새 요청이 모두 v417 로 가기까지 1분입니다. 나머지 13분 가운데 5분(07:04~07:09)은 지훈 씨와 선배가 대시보드를 보고 되돌릴지 판단한 시간이고 7분(07:11~07:18)은 v418 파드를 내리고 초과율과 COPC 가 평소 값으로 돌아왔는지 확인한 시간입니다. 남은 1분(07:09~07:10)은 되돌리기로 정한 뒤 명령 한 줄을 내리기까지 걸린 시간입니다.

되돌리기를 빠르게 하려면 기계를 더 빠르게 하기보다 게이트를 미리 적어 두어 사람이 정하는 시간을 줄여야 합니다. 「COPC 가 게이트 밖이면 되돌린다」가 미리 적혀 있으면 07:09 까지 판단하던 5분이 없어집니다. 이 팀은 그 뒤로 COPC 게이트에서 탈락하면 사람의 판단을 기다리지 않고 자동으로 되돌리도록 바꿨습니다.

06:31 부터 07:11 까지 40분 동안 v418 이 답한 요청은 1절에서 가정으로 계산한 표의 10% 줄과 같은 633,360건이었습니다. 100% 로 한 번에 올렸다면 그 수는 같은 40분 동안 표의 100% 줄인 6,333,600건이었습니다. 그리고 그 40분 동안 서버는 한 번도 느려지지 않았습니다. 서버가 느려지는 배포는 다음 절에서 봅니다.

## 6. 웜업 없이 올린 새 파드의 느린 첫 30초

**웜업 없이 뜬 새 파드는 처음 30초 동안 평소보다 2.5배 느려 8ms 초과율이 4.62% 에서 11.74% 로 오릅니다. readiness probe(요청을 받을 준비가 됐는지 확인하는 검사)를 통과하기 전에 더미 요청 200건으로 웜업하면 이 느린 구간이 사라집니다.**

카나리 배포는 단계마다 새 파드를 띄우는데, 갓 켠 서버는 캐시(자주 쓰는 값을 빠른 메모리에 두는 곳)가 비어 있어 첫 요청들을 느리게 받습니다. 그래서 진짜 요청을 받기 전에 더미 요청(응답을 어디에도 쓰지 않는 요청)을 먼저 보내 두는 웜업을 합니다. 다섯 번째 카드는 파드가 뜨는 순서를 초 단위로 늘어놓은 그림이라 웜업이 있을 때와 없을 때 요청을 받기 시작하는 시점과 초과율을 나란히 비교할 수 있습니다.

[추론 서버](post.html?id=inference-server) 편에서 다룬 대로 파드가 뜰 때는 컨테이너 이미지(서버 프로그램과 실행 환경을 담은 파일)를 시작하는 데 12초, 모델 파일을 내려받는 데 6초, 모델을 메모리에 적재하는 데 3초가 걸리고 마지막으로 웜업에 20초가 걸립니다. 웜업을 빼면 12 + 6 + 3 = 21초 만에 readiness probe 를 통과해 Ready(요청을 받을 수 있는 상태)가 되는데, 게이트웨이는 그 순간부터 새 파드에 요청을 보냅니다.

문제는 Ready 가 된 뒤의 30초입니다. 갓 뜬 새 파드는 모델의 가중치(게이트웨이의 가중치가 아니라 모델이 학습한 값)가 아직 캐시에 올라와 있지 않습니다. 임베딩(피처를 숫자 벡터로 바꾼 값)도 처음 조회할 때는 전부 캐시 미스(찾는 값이 캐시에 없어 느린 저장소에서 읽어 오는 일)가 납니다. 그래서 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편 8절이 측정한 대로 그 30초 동안 지연이 2.5배가 되고 초과율이 11.74% 까지 오릅니다. 웜업이 있을 때와 없을 때를 나란히 놓으면 아래와 같습니다.

| | Ready 까지 | 첫 30초 초과율 | 그 뒤 초과율 |
|---|---|---|---|
| 웜업 없이 | 21초 | 11.74% | 4.62% |
| 웜업 200건 | 41초 | 4.62% | 4.62% |

표의 값은 서빙 지연 편의 값을 그대로 가져온 가정이라 이 절에서 따로 돌린 계산은 없습니다. 웜업을 빼면 파드가 21초에 요청을 받기 시작하는 대신 처음 30초 동안 초과율 11.74% 로 느리게 받습니다. 웜업 200건을 넣으면 20초 늦은 41초(21초 + 웜업 20초)에 요청을 받기 시작하지만 처음부터 평소와 같은 초과율 4.62% 로 받습니다.

카나리 1% 단계라면 그 느린 30초 동안 들어오는 요청은 초당 2,639건의 1% 를 30초 받은 792건이라 적어 보입니다. 하지만 게이트가 그 30초를 포함한 5분 윈도우로 초과율을 측정하면 모델에는 문제가 없는데도 1% 단계의 첫 게이트에서 걸릴 수 있습니다. 이 느린 30초는 모델이 아니라 배포 절차에서 생기는 문제라서 readiness probe 가 웜업이 끝난 뒤에야 통과하도록 절차를 바꾸면 해결됩니다.

지훈 씨 팀의 파드 정의(파드를 어떻게 띄울지 적은 설정)에는 이미 웜업이 들어 있었으므로, 06:26 에 시작한 1% 단계에서도 초과율이 4.71% 로 평소와 같았습니다. 되돌릴 때도 같은 규칙이 적용되는데, 옛 파드를 미리 내리지 않았으므로 07:10 에 가중치를 돌렸을 때 요청을 모두 넘겨받은 v417 파드는 이미 웜업이 끝난 상태였습니다. 옛 파드를 남겨 두는 이 구조는 다음 절에서 자세히 봅니다.

## 7. 되돌리기가 초 단위로 끝나는 구조

**되돌리는 방법은 3가지이고 방법마다 몇 초, 1~2분, 10분 넘게 걸립니다. 그 가운데 게이트웨이 가중치를 돌리는 방법이 가장 빠른데, 이 방법을 쓰려면 옛 버전이 아직 떠 있어야 합니다.**

5절의 지훈 씨는 07:10 에 명령 한 줄을 내렸고 1분 뒤인 07:11 에 새 요청이 모두 v417 로 갔습니다. 이렇게 빨리 되돌리는 팀은 옛 버전을 미리 지우지 않는 팀으로, 새 버전이 완전히 자리 잡을 때까지 두 버전을 모두 켜 두고 요청이 가는 길만 바꿉니다. 되돌리는 방법 3가지를 바꾸는 대상, 걸리는 시간, 쓸 수 있는 조건으로 나란히 놓으면 아래와 같습니다.

| 되돌리는 방법 | 무엇을 바꾸나 | 걸리는 시간 | 조건 |
|---|---|---|---|
| 게이트웨이 가중치 | 규칙 한 줄. 새 버전 0, 옛 버전 100 | 몇 초 | 옛 파드가 떠 있어야 합니다 |
| 모델 파일 경로 | 서버 설정의 모델 버전 이름 | 1~2분 | 서버가 두 버전을 같이 들고 있거나 다시 읽어야 합니다 |
| 이미지 재배포 | 옛 이미지로 파드 12대를 다시 띄움 | 10분 넘게 | 웜업 포함. 배포 중 지연이 다시 생깁니다 |

지훈 씨가 07:10 에 쓴 방법은 첫 줄의 게이트웨이 가중치입니다. 게이트웨이 규칙 한 줄에서 새 버전을 0, 옛 버전을 100 으로 바꾸면 몇 초 안에 요청이 옛 파드로 가는데, 요청을 받을 옛 파드가 떠 있어야 한다는 조건이 붙습니다. 그래서 3절에서 100% 가 된 뒤에도 옛 파드를 30분 더 두었습니다.

셋째 줄의 이미지 재배포는 옛 파드를 이미 내린 뒤에 문제를 발견했을 때 쓰는 방법으로, 옛 이미지로 파드 12대를 다시 띄워야 합니다. 롤링 업데이트(rolling update)는 파드를 몇 대씩 차례로 새로 띄워 바꾸는 방식입니다. 파드 하나가 Ready 가 되기까지 41초가 걸리고 12대를 두 대씩 롤링 업데이트로 바꾼다고 가정하면, 바꾸는 횟수는 12 ÷ 2 = 6번이고 한 번마다 41초에 여유 60초를 더한 시간이 드므로 6번이면 10분이 넘습니다. 게다가 파드 12대를 롤링 업데이트로 바꾸는 동안에는 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편 8절이 측정한 배포 지연이 다시 생겨 초과율이 20.87% 까지 오르므로 사고를 수습하면서 사고를 하나 더 만듭니다.

둘째 줄의 모델 파일 경로는 서버 설정에 적힌 모델 버전 이름을 바꾸는 방법이고 1~2분이 걸립니다. 이 방법을 쓰려면 서버가 두 버전을 함께 적재해 두었거나 모델 파일을 다시 읽어야 하며 모델 배포와 코드 배포도 나뉘어 있어야 합니다. 모델 파일이 이미지 안에 들어 있으면 모델을 바꾸는 일이 이미지를 다시 배포하는 일과 같아지지만 모델 파일을 이미지 밖에 두고 서버가 시작할 때 내려받는 구조라면 설정의 버전 이름 한 줄로 모델을 바꿀 수 있습니다. 그래서 [Docker 와 CI](post.html?id=container-ci-pipeline) 편은 모델 파일을 이미지 밖에 두는 구조를 씁니다.

마지막으로, 평소에 눌러 보지 않은 명령은 사고가 났을 때 손이 가지 않으므로 되돌리기는 미리 해 본 적이 있어야 합니다. 이 팀은 배포할 때마다 100% 로 가기 전에 가중치를 한 번 0 으로 내렸다가 다시 올려 보는 절차를 넣었으므로, 되돌리기가 배포마다 한 번은 실제로 실행됩니다.

## 8. 담장 안과 열린 RTB 에서 트래픽을 나누는 자리

지금까지 본 배포는 지훈 씨처럼 앱과 광고 서버가 한 회사 안에 있는 경우였습니다. 광고가 노출되는 매체(앱이나 사이트)가 남의 것인 열린 RTB(real-time bidding, 광고 자리를 실시간 경매로 사고파는 시장)에서는 트래픽을 나누는 자리와 게이트를 읽는 속도가 달라집니다.

### 우리가 요청을 나누는 담장 안 [무대: 닫힌 생태계]

**앱과 광고 서버가 한 회사 안에 있는 담장 안에서는 게이트웨이도 우리 것이라, 1% 를 어느 요청으로 할지와 두 버전을 어떻게 비교할지를 우리가 정합니다.**

이 글의 지훈 씨가 이 경우입니다. 게이트웨이는 요청을 하나하나 무작위로 골라 1% 를 새 버전에 보내므로 두 버전에는 같은 지면, 같은 시간의 요청이 섞여 들어갑니다. 그래서 두 버전의 COPC 와 클릭률을 서로 바로 비교할 수 있습니다. 요청 대신 회원 ID 로 나누면 같은 사람이 늘 같은 모델을 보게 할 수도 있습니다. 나누는 단위를 이렇게 바꾸면 지표에 무엇이 달라지는지는 [모델 온라인 A/B 설계](post.html?id=model-ab-testing) 편에서 설명합니다.

클릭도 우리 로그로 바로 들어옵니다. 노출(광고가 화면에 보인 것) 뒤 2분 안에 클릭의 99.9% 가 도착하므로 30분 윈도우의 COPC 는 윈도우가 닫힐 때 거의 확정됩니다. 그래서 담장 안에서는 게이트를 30분 만에 읽을 수 있습니다.

### 입찰 요청의 일부로 나누는 열린 RTB [무대: 열린 RTB]

**매체가 남의 것이면 우리가 나눌 수 있는 대상은 거래소(ad exchange, 매체의 광고 자리를 경매로 파는 곳)에서 오는 입찰 요청뿐입니다. 경매에서 이겼는지는 우리가 응답을 보낸 뒤에 오고 클릭은 그보다 더 뒤에 옵니다.**

열린 RTB 에서 광고주 쪽 입찰을 맡는 DSP(demand-side platform)는 거래소가 보낸 입찰 요청을 받아 입찰가를 냅니다. 여기서 카나리 배포는 그 입찰 요청의 1% 에 새 모델이 계산한 입찰가를 씁니다. 이때 담장 안과 달라지는 점이 두 가지 있습니다.

첫째, 새 모델이 입찰가를 낮게 내면 경매에서 져 노출 자체가 줄어드는데, 담장 안에서라면 광고 순위가 바뀌는 데 그쳤을 일이 열린 RTB 에서는 노출이 사라지는 일이 됩니다. 그래서 열린 RTB 의 게이트에는 낙찰률(낸 입찰 가운데 경매에서 이긴 비율)이 하나 더 들어갑니다.

둘째, 클릭과 전환(클릭 뒤 구매처럼 광고주가 바라는 행동)이 매체와 광고주 쪽에서 늦게 넘어옵니다. 그래서 30분 윈도우로는 COPC 를 읽을 수 없어 몇 시간을 기다려야 합니다. 기다리는 만큼 한 단계에 머무는 시간이 길어지므로 그 시간 동안의 손해도 커집니다.

두 가지 차이 때문에 열린 RTB 의 카나리 배포는 담장 안보다 오래, 더 조심스럽게 진행합니다. 1% 단계를 하루 동안 두는 팀도 있습니다. 낙찰 여부가 왜 늦게 오고 왜 보지 못한 값이 생기는지는 [Bid Shading](post.html?id=bid-shading-censored) 편에 있습니다.

| 섀도는 무엇인가 | 요청을 복사해 계산만 하고 응답에는 안 쓰는 것. 손해 0, 클릭은 못 봄 |
| 카나리 단계는 | 1% 5분, 10% 30분, 50% 30분, 100% |
| 게이트 4개는 | 8ms 초과율 6% 이하, 오류율 0.1% 이하, COPC 0.95~1.05, 클릭률 차이 -2% 이상 |
| 왜 COPC 는 10% 부터 보나 | 클릭 1,600건은 모여야 흔들림이 게이트 안에 들어와서 |
| 되돌리기는 어떻게 | 게이트웨이 가중치를 0 으로. 몇 초. 옛 파드가 떠 있어야 |
| 그날 14분은 어디에 쓰였나 | 기계 1분, 사람 판단 5분, 확인 7분 |
| 웜업은 왜 하나 | 새 파드의 첫 30초가 2.5배 느려서. Ready 를 웜업 뒤로 |

## 헷갈리기 쉬운 점

- **카나리는 A/B 테스트가 아닙니다.** 카나리 배포는 새 버전이 「망가지지 않았나」를 빨리 확인하며 비율을 넓혀 가는 절차입니다. A/B 테스트는 두 버전 가운데 「어느 쪽이 나은가」를 충분한 기간 동안 측정하는 실험입니다. 카나리 배포를 마친 뒤에 A/B 테스트를 따로 돌리는 팀이 많습니다.
- **게이트를 통과했다고 좋은 모델인 것은 아닙니다.** 게이트는 나쁜 모델을 걸러 낼 뿐 좋은 모델임을 증명하지는 않습니다.
- **1% 단계에서 COPC 가 이상해 보여도 신호가 아닙니다.** 클릭이 79건뿐이면 모델에 문제가 없어도 COPC 가 우연만으로 ±0.22 만큼 흔들리므로 이 폭 안의 값은 잡음입니다.
- **되돌리기는 새 파드를 끄는 일이 아닙니다.** 되돌리기는 게이트웨이 가중치를 바꿔 요청이 가는 길을 옛 파드 쪽으로 돌리는 일입니다. 새 파드는 길을 돌린 뒤에 내립니다.
- **오프라인 게이트와 온라인 게이트는 다른 문입니다.** v418 은 어제 로그로 채점한 오프라인 게이트를 통과하고도 실제 요청으로 판정한 온라인 게이트에서 걸렸습니다. 두 게이트가 모두 있어야 합니다.
- **COPC 1.09 는 「9% 더 좋다」는 뜻이 아닙니다.** COPC 1.09 는 실제 클릭이 예측보다 많았다는 뜻이므로 모델이 클릭 확률을 낮게 봤고 그만큼 입찰가가 9% 낮게 나갔습니다.
