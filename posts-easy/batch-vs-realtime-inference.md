지훈 씨는 일곱째 주에 후보 생성(retrieval) 코드를 읽었습니다. 후보 생성은 광고 수십만 개 가운데 요청한 회원에게 보여 줄 만한 광고를 후보로 고르는 단계입니다. 코드는 요청이 들어오면 그 회원의 최근 행동을 읽어 유저 벡터(그 회원을 숫자 64개로 나타낸 값) 하나를 만들고 그 벡터로 광고를 고르는 순서로 짜여 있었는데, 최근 행동을 읽고 유저 벡터를 만드는 두 단계에 요청 한 건마다 2.0ms 가 들어가고 있었습니다.

요청 로그를 하루치 열어 보니 같은 회원 번호가 아침에 한 번, 점심에 한 번, 저녁에 여러 번 찍혀 있었고 코드는 그때마다 같은 계산을 처음부터 다시 하고 있었습니다. 어제 밤에 만든 값과 오늘 아침에 만든 값도 크게 다르지 않았습니다. 옆자리 선배에게 물어보니 처음부터 그렇게 만들어져 있었다는 답이 돌아왔습니다.

**어제까지의 행동으로 만드는 값이라면, 새벽에 미리 만들어 두면 안 될까요?**

추론(inference)은 학습을 마친 모델에 입력을 넣어 값을 계산하는 일입니다. 요청이 오기 전에 미리 계산해 두는 방식을 배치 추론(batch inference), 요청이 들어온 그때 요청 안에서 계산하는 방식을 실시간 추론(real-time inference)이라고 부릅니다. 어떤 값을 어느 방식으로 만드느냐가 요청 한 건에 걸리는 시간과 한 달 서버 값을 정하므로 이 결정을 잘못 내리면 필요 없는 서버를 몇 대씩 더 삽니다. CPU 서버는 한 대에 시간당 480원이라 한 달 720시간이면 345,600원이 들고 일곱 대면 240만 원이 넘습니다.

> **한 줄 요약:** 유저 벡터는 어제까지의 행동으로 만드는 값이라 요청이 올 때마다 만들지 않고 새벽에 회원 전체의 벡터를 한 번에 만들어 둘 수 있습니다. 그러면 요청 때 하던 계산이 미리 만든 벡터를 꺼내는 0.20ms 짜리 조회 한 번으로 바뀝니다. 요청마다 만들면 하루 126.7시간이 드는 계산이 새벽 배치로는 3.3시간으로 줄어듭니다. 다만 새벽에 만든 값에는 오늘 오후의 행동이 들어 있지 않으므로 자주 바뀌는 사람만 한 시간마다 다시 만듭니다.

> **골라 읽는 법** — 절이 9개인 글입니다. 1~6절마다 카드 한 장이나 표 하나가 들어 있어서 카드나 표만 보고 넘어가도 됩니다.
>
> - 요청 때 만드는 유저 벡터와 미리 만들어 둔 광고 벡터 → 1절
> - 새벽 배치가 만드는 유저 벡터 표와 그 크기 → 2절
> - 새벽에 만든 값이 낡는 문제와 활성 유저(오늘 로그인한 회원)만 다시 만드는 주기 → 3절
> - 미리 만든 벡터를 저장소에서 찾는 비율과 요청당 평균 시간 → 4절
> - CPU 서버와 GPU 서버의 대수와 한 달 값 → 5절
> - 담장 안(한 회사가 앱과 광고 서버를 다 가진 곳)과 열린 RTB(남의 앱이나 웹페이지에 나갈 광고를 실시간 입찰로 사는 곳)의 차이 → 6절

이 글의 시간, 크기, 값은 모두 설명을 위해 정한 가상 값이며 그 가운데 몇 가지는 다른 편과 같은 값을 씁니다. 유저 벡터의 64차원(숫자 64개)과 유저 타워(회원의 입력을 받아 유저 벡터를 만드는 모델) 한 번에 드는 0.8ms 는 [Two-Tower Retrieval](post.html?id=two-tower-retrieval) 편의 값입니다. 회원 1,400만 명은 타겟팅 트랙과 같은 회원 수입니다. 평시 요청량 2,639 QPS(초당 요청 수)와 부하율(실제로 받는 요청량을 서버가 받아 낼 수 있는 한계로 나눈 값) 0.77 은 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편에서 나온 값입니다.

## 1. 요청 때 만드는 유저 벡터와 미리 만들어 둔 광고 벡터

**후보 생성은 유저 벡터 하나를 광고 벡터 수십만 개와 맞춰 보는 일인데, 광고 벡터는 미리 만들어져 있고 유저 벡터만 요청 안에서 만듭니다. 요청 한 건에서 회원의 최근 행동을 읽어 유저 벡터를 만드는 데 2.0ms 가 듭니다.**

광고를 고르려면 유저와 광고를 같은 길이의 벡터로 바꿔야 하는데, 지훈 씨가 읽은 코드는 광고 벡터를 미리 만들어 두고 유저 벡터만 요청이 올 때 만들어 한 요청 안에서 미리 만든 벡터와 그때 만든 벡터를 함께 쓰고 있었습니다. 벡터는 숫자를 정해진 개수만큼 늘어놓은 것으로, 이 서비스는 유저와 광고를 각각 숫자 64개짜리 벡터(64차원)로 바꿉니다. 벡터를 만드는 모델을 타워라고 부르며 유저 벡터를 만드는 유저 타워와 광고 벡터를 만드는 광고 타워가 따로 있습니다. 두 타워가 만든 벡터를 맞춰 보면 이 회원이 이 광고를 누를 만한지가 점수 하나로 나옵니다. 두 타워를 나란히 두는 이 구조는 [Two-Tower Retrieval](post.html?id=two-tower-retrieval) 편에서 다룹니다.

광고는 수십만 개로 회원 1,400만 명보다 수가 적고 잘 바뀌지 않아서 광고 벡터를 미리 만들어 둡니다. 새 캠페인(광고주가 예산과 기간을 정해 내보내는 광고 단위)이 들어와도 한 시간에 한 번 다시 만들면 충분한 반면, 요청마다 광고 벡터를 만들면 요청 한 건에서 수십만 번을 계산해야 하므로 광고 벡터는 처음부터 미리 만드는 방식에 두었습니다.

유저 벡터는 요청 한 건에 한 번만 만들면 되니 비용이 작아 보입니다. 아래 표에 요청 한 건이 후보 생성에서 거치는 일과 일마다 드는 시간을 적었습니다. 유저 타워 0.8ms 와 후보 고르기(유저 벡터를 광고 벡터와 맞춰 보며 후보를 고르는 일) 12.8ms 는 Two-Tower 편에서 가져온 값입니다. 유저 피처(최근 클릭, 관심사처럼 유저 타워에 넣는 입력 값)를 읽어 오는 1.2ms 는 이 글에서 새로 정한 가상 값입니다. 유저 벡터 하나에는 피처 읽기 1.2ms 와 유저 타워 0.8ms 를 더한 2.0ms 가 듭니다.

| 하는 일 | 언제 만드나 | 요청당 시간 |
|---|---|---|
| 유저 피처 읽기 (최근 클릭, 관심사) | 요청 때 | 1.2ms |
| 유저 벡터 만들기 (유저 타워 한 번) | 요청 때 | 0.8ms |
| 광고 벡터 | 한 시간마다 미리 | 읽기만 |
| 후보 고르기 (벡터끼리 맞춰 보기) | 요청 때 | 12.8ms |

요청 한 건만 보면 2.0ms 는 전체 14.8ms(1.2 + 0.8 + 12.8) 가운데 작은 부분이라 지금까지 아무도 이 부분을 건드리지 않았습니다. 그런데 이 서비스가 하루에 받는 요청은 2억 2,800만 번입니다. 2.0ms 에 2억 2,800만을 곱하면 하루 126.7시간인데 서버 한 대가 하루에 돌 수 있는 시간은 24시간이므로, 126.7시간은 서버가 하루 내내 이 계산만 해도 다섯 대가 넘게 필요한 분량입니다. 요청 한 건에서는 작은 시간도 하루 요청 수만큼 쌓이면 서버 대수가 됩니다.

지훈 씨가 본 코드에는 광고 벡터는 미리, 유저 벡터는 요청 때 만든다는 결정이 이미 들어 있었습니다. 그런데 유저 벡터도 어제까지의 행동으로 만드는 값이므로 광고 벡터처럼 미리 만들지 못할 까닭이 없습니다. 유저 벡터를 새벽에 미리 만드는 방법은 다음 절에서 봅니다.

## 2. 회원 전체의 벡터를 한 번에 만드는 새벽 배치

**새벽 04:30 에 배치 작업이 돌아 회원 1,400만 명의 유저 벡터를 한꺼번에 만들어 두면 요청 때는 회원 번호로 꺼내 쓰기만 하면 됩니다. 한 명에 숫자 64개인 벡터 표는 전체가 3.58GB 입니다. 이 표를 만드는 배치는 작업을 나눠 맡는 워커 8개로 25분이면 끝납니다.**

지훈 씨가 요청 로그에서 본 대로 지금 코드는 같은 회원의 유저 벡터를 요청이 올 때마다 처음부터 다시 만듭니다. 배치(batch)는 데이터를 모아 두었다가 정해진 시각에 한꺼번에 처리하는 작업입니다. 새벽에 배치로 회원 전체의 벡터를 한 번에 만들어 표로 저장해 두면 요청이 왔을 때 그 표에서 회원 번호로 벡터를 꺼내기만 하면 되므로 요청 안에서 하던 계산이 조회 한 번으로 바뀝니다.

먼저 이 표가 얼마나 큰지 계산합니다. 벡터의 값 하나가 4바이트이고 한 명의 벡터에 값이 64개이니 한 명에 4 × 64 = 256바이트가 들며 여기에 회원 1,400만 명을 곱하면 3,584,000,000바이트(3.58GB)입니다. 3.58GB 는 서버 한 대의 메모리에 들어가는 크기입니다. 임베딩 표(ID 마다 벡터 한 줄씩을 적은 표) 27.7GB 를 다루는 [임베딩 테이블 운영](post.html?id=embedding-table-ops) 편과 비교하면 작은 편입니다.

새벽 배치는 어제까지의 로그로 만든 유저 피처를 읽어 유저 타워를 회원 수만큼 1,400만 번 돌린 뒤 그 결과를 온라인 저장소에 쓰는 세 가지 일을 합니다. 온라인 저장소는 요청을 처리하는 도중에 바로 읽을 수 있게 값을 메모리에 올려 두는 저장소입니다. 이 저장소에는 회원 번호 하나에 벡터 하나가 놓입니다. 워커(worker)는 배치 작업을 나눠 받아 실행하는 계산 단위입니다. 워커 8개가 회원 1,400만 명을 나눠 맡아 25분 만에 일을 끝냅니다. 작업에 든 계산량은 워커 수와 걸린 시간을 곱한 워커 시간으로 세는데 8 × 25분 = 200분(3.3시간)입니다.

카드는 색으로 역할을 구분합니다. 파랑은 놓여 있는 데이터(회원 표, 벡터 표, 저장소), 벽돌색은 지금 오는 것(요청), 먹색은 모델과 서버, 회색은 만드는 작업(새벽 배치)이며 점선 상자는 적어 둔 내용을 나타냅니다. 첫 번째 카드에서는 새벽 04:30 에 한 번 도는 배치가 회원 1,400만 명의 벡터를 만들어 온라인 저장소에 올린 뒤 회원 A 의 요청이 오면 광고 서버가 그 저장소에서 벡터를 조회만 하는 흐름을 보면 됩니다.

같은 유저 타워를 돌리는데도 회원 한 명의 벡터에 드는 시간은 새벽 배치가 더 짧습니다. 워커 시간 200분을 회원 1,400만 명으로 나누면 한 명에 0.86ms 로 요청 때의 2.0ms 보다 작은데, 까닭은 두 가지입니다. 첫째, 요청 때는 회원마다 피처를 따로 읽어 오느라 1.2ms 가 들었지만 배치는 피처 표 전체를 처음부터 순서대로 읽어 쓰므로 요청마다 하던 피처 읽기가 사라집니다. 둘째, 배치는 회원을 한 명씩 돌리지 않고 수천 명을 텐서(모델에 한 번에 넣는 숫자 배열) 하나로 묶어 한 번에 계산합니다. 묶어서 한 번에 계산하면 왜 빨라지는지는 [추론 서버](post.html?id=inference-server) 편에서 다룹니다.

하루 단위로 보면 차이가 더 벌어집니다. 하루 요청 2억 2,800만 건을 회원 1,400만 명으로 나누면 같은 사람이 하루 평균 16.3번 요청하는데, 요청마다 만들면 한 사람의 벡터를 하루 16.3번 계산하지만 새벽에 만들면 한 번만 계산합니다. 그 한 번에 드는 시간도 요청 때의 2.0ms 보다 작은 0.86ms 라서 하루 계산 시간은 요청마다 만들 때의 126.7시간에서 새벽에 한 번 만들 때의 3.3시간으로 38배 줄어듭니다. 그래서 어제까지의 데이터로 만드는 값은 새벽에 미리 만들어 둡니다. 다만 새벽에 만든 값에는 오늘 낮의 행동이 들어 있지 않습니다. 이 값이 낡는 문제는 다음 절에서 봅니다.

## 3. 값이 낡는 문제와 다시 만드는 주기

**새벽에 만든 벡터에는 오늘 낮의 행동이 들어 있지 않은데 회원 전원을 자주 다시 만들면 계산이 그만큼 늘어납니다. 오늘 로그인한 활성 유저는 회원의 12% 인 168만 명이지만 하루 요청의 80% 를 만들기 때문에 이 사람들만 한 시간마다 다시 만듭니다.**

값이 낡는다는 말은 벡터를 만든 뒤에 생긴 행동이 벡터에 들어 있지 않다는 뜻입니다. 회원 A 가 오후 2시에 러닝화를 여러 번 봤다고 하면 이 행동은 새벽 04:30 에 만든 벡터에 없으므로, 오후 3시에 광고 요청이 와도 회원 A 의 벡터는 아침의 취향 그대로라 러닝화 광고가 후보에 덜 오릅니다. 이때 오류는 어디에도 나지 않고 광고만 덜 맞습니다.

회원 전원을 한 시간마다 다시 만드는 방법이 먼저 떠오르지만 1,400만 명을 한 시간마다 만들면 하루 24번이 되고 한 번에 워커 시간 200분(3.3시간)이 드니 하루 80시간입니다. 80시간은 새벽에 한 번 만드는 3.3시간의 24배이고 요청마다 만드는 126.7시간에 가까워서 미리 만들어 두는 이득이 사라집니다.

그래서 다시 만드는 대상을 좁힙니다. 활성 유저 168만 명은 전체 회원 1,400만 명의 12% 이지만 이 사람들이 하루 요청 2억 2,800만 건 가운데 80% 를 만들므로, 12% 만 한 시간마다 다시 만들어도 요청의 80% 는 최대 1시간 전에 만든 벡터를 받습니다. 활성 유저가 회원의 12% 이니 한 번 다시 만드는 데 드는 워커 시간도 3.3시간의 12% 인 0.4시간이며 하루 24번이면 9.6시간입니다.

아래 표에 미리 만드는 세 가지 방법과 요청마다 만드는 경우를 나란히 놓았습니다. 값이 얼마나 낡았는지는 요청이 오는 순간 그 값이 만들어진 지 얼마나 지났는지로 보며 하루 계산 시간은 워커 시간으로 셉니다.

| 방법 | 값이 얼마나 낡나 (요청이 오는 순간까지 지난 시간) | 하루 계산 시간 (워커 시간) |
|---|---|---|
| 새벽에 한 번, 전원 | 최대 24시간 | 3.3시간 |
| 한 시간마다, 활성 유저만 | 활성은 최대 1시간, 나머지는 최대 24시간 | 9.6시간 (새벽 배치 3.3시간 별도) |
| 한 시간마다, 전원 | 최대 1시간 | 80시간 |
| 요청마다, 그 자리에서 | 없음 | 126.7시간 |

값이 낡는 문제를 더 줄이는 방법도 하나 있습니다. 벡터를 만드는 입력을 두 가지로 나눠 오래 바뀌지 않는 취향은 새벽 배치에서 넣고 최근 클릭 몇 개처럼 자주 바뀌는 입력만 요청 때 넣으면, 유저 타워 전체를 다시 돌리지 않고도 방금 전 행동을 반영합니다. 이 방법은 [Two-Tower Retrieval](post.html?id=two-tower-retrieval) 편의 여덟째 절에 있습니다.

이 글은 활성 유저만 한 시간마다 다시 만드는 방법을 고릅니다. 저장소에 활성 유저의 벡터만 올려 두면 요청 때 벡터를 못 찾는 사람이 생기는데, 못 찾았을 때 무슨 일이 일어나는지와 저장소에 누구의 벡터를 올려 둘지는 다음 절에서 봅니다.

## 4. 저장소에서 찾는 비율과 요청당 시간

**미리 만든 벡터를 온라인 저장소에서 못 찾으면 그 자리에서 다시 만들므로 저장소에 누구의 벡터를 올려 두느냐가 요청당 평균 시간을 정합니다. 회원 전원을 올리면 메모리 3,584MB 에 요청당 0.20ms 이고 활성 유저만 올리면 430MB 에 0.56ms 입니다.**

저장소에 올려 두는 벡터를 줄이면 메모리는 아끼지만 저장소에 없는 회원의 요청은 시간이 더 걸립니다. 저장소를 쓰려면 벡터를 못 찾았을 때 무엇을 할지부터 정해 둬야 하는데, 이 서비스는 오류를 내지 않고 그 자리에서 유저 타워를 돌려 벡터를 만듭니다. 응답은 그대로 나가고 값도 맞지만 그 요청에는 1절의 2.0ms 가 붙어 그 요청만 느려집니다. 저장소에 올려 둔 회원이 적을수록 이렇게 느린 요청이 늘어납니다.

찾는 비율은 요청 가운데 저장소에서 벡터를 찾은 요청의 비율로, 높을수록 요청당 평균 시간이 짧아집니다. 온라인 저장소처럼 빨리 읽으려고 값을 미리 올려 두는 곳을 캐시라고 부르므로 찾는 비율은 캐시 적중률(cache hit rate)이라고도 합니다. 아래 코드 출력에는 「적중」으로 찍힙니다. 요청당 평균 시간은 찾은 요청이 쓰는 조회 시간 0.20ms 와 못 찾은 요청이 쓰는 2.0ms 를 두 비율대로 평균 낸 값이라, 찾는 비율에 0.20ms 를 곱한 값과 못 찾는 비율에 2.0ms 를 곱한 값을 더해 구합니다. 회원 전원을 올리면 찾는 비율이 100% 라 요청당 평균이 조회 시간 그대로 0.20ms 입니다. 활성 유저만 올리면 활성 유저가 요청의 80% 를 만드므로 찾는 비율도 80% 가 되어 0.8 × 0.20ms 와 0.2 × 2.0ms 를 더한 0.56ms 입니다. 아무 벡터도 올리지 않으면 모든 요청이 그 자리에서 벡터를 만들어야 하므로 요청당 평균이 2.00ms 로 가장 깁니다.

두 번째 카드에서는 저장소에 전원을 올릴 때와 활성 유저만 올릴 때, 아무것도 올리지 않을 때의 메모리와 요청당 평균 시간을 막대로 나란히 보면 됩니다.

활성 유저만 올리는 선택지는 메모리를 아끼려고 둡니다. 회원 한 명의 벡터가 256바이트이므로 전원 1,400만 명은 3,584MB, 활성 유저 168만 명은 430MB 라 메모리가 여덟 배 차이 납니다. 이 서비스의 벡터 표는 3.58GB 로 서버 한 대의 메모리에 전원이 들어가므로 전원을 올립니다. 벡터 표가 열 배 컸다면 판단이 달라집니다. 임베딩 표처럼 27.7GB 짜리라면 활성 유저만 올리고 나머지 회원은 못 찾는 경우로 둡니다.

아래 코드는 1절부터 이 절까지 쓴 숫자를 한 번에 계산해 보려고 돌립니다. 2단계에서 유저 벡터 표의 크기와 새벽 배치의 한 명당 시간, 하루 계산 시간을 세고 3단계에서 저장소에 누구의 벡터를 올릴 때 요청당 평균이 얼마인지를 셉니다.

```python
# 하는 일: 유저 벡터를 요청마다 계산할 때와 새벽에 미리 만들어 둘 때를 하루 계산 시간, 온라인 저장소 메모리, 캐시 적중률로 비교한다.
# 1단계: 요청량과 걸리는 시간을 둔다
# 전부 설명용 가상 값이다.
REQ_PER_DAY = 228_000_000      # 하루 광고 요청 (노출 수와 같다고 둔다)
USERS = 14_000_000             # 전체 회원
DIM, NBYTES = 64, 4            # 유저 벡터 64차원, 값 하나 4바이트
TOWER_MS = 0.8                 # 요청 때 유저 타워 한 번 (Two-Tower 글의 값)
FEAT_MS = 1.2                  # 그 입력 피처를 읽어 오는 시간
LOOKUP_MS = 0.2                # 미리 만든 벡터를 온라인 저장소에서 읽는 시간
WORKERS, BATCH_MIN = 8, 25     # 새벽 배치의 워커 수와 걸리는 시간
ACTIVE, ACTIVE_SHARE = 0.12, 0.80   # 활성 유저 비율, 그들이 만드는 요청 비율

# 2단계: 표 크기와 하루 계산 시간을 센다
make_ms = TOWER_MS + FEAT_MS                       # 그 자리에서 만들면 드는 시간
table_gb = USERS * DIM * NBYTES / 1e9
print(f"유저 벡터 표: {USERS:,}명 x {DIM}차원 x {NBYTES}B = {table_gb:.2f} GB")
print(f"새벽 배치: 워커 {WORKERS}개가 {BATCH_MIN}분 "
      f"= 한 명에 {WORKERS * BATCH_MIN * 60_000 / USERS:.2f} ms")

online_h = REQ_PER_DAY * make_ms / 1000 / 3600     # 요청마다 만들 때의 하루 계산 시간
batch_h = WORKERS * BATCH_MIN / 60                 # 새벽 배치가 쓴 워커 시간
print(f"하루 계산: 요청마다 {online_h:,.1f}시간, 새벽에 한 번 {batch_h:.1f}시간"
      f" -> {online_h / batch_h:.0f}배")
print(f"같은 사람이 하루 평균 {REQ_PER_DAY / USERS:.1f}번 요청한다\n")

# 3단계: 온라인 저장소에 누구의 벡터를 올릴지 비교한다
# 올리지 않은 사람의 벡터는 요청 때 그 자리에서 만든다.
print("온라인 저장소에 누구의 벡터를 올리나")
for label, share, hit in (("전원 ", 1.0, 1.0), ("활성만", ACTIVE, ACTIVE_SHARE)):
    n = round(USERS * share)
    mem = n * DIM * NBYTES / 1e6
    avg = hit * LOOKUP_MS + (1 - hit) * make_ms    # 못 찾으면 그 자리에서 만든다
    print(f"  {label} {n:>10,}명  {mem:>5,.0f}MB  적중 {hit:>4.0%}  요청당 {avg:.2f}ms")
print(f"  안 올림 {0:>10}명  {0:>5}MB  적중   0%  요청당 {make_ms:.2f}ms")

# 출력:
# 2단계 뜻: 요청마다 만들면 하루 126.7시간, 새벽에 한 번 만들면 3.3시간으로 38배 차이다. 같은 사람이 하루 16.3번 요청해 같은 계산을 되풀이하고, 새벽 배치는 한 명에 0.86 ms 로 요청 때보다 싸기 때문이다.
# 유저 벡터 표: 14,000,000명 x 64차원 x 4B = 3.58 GB
# 새벽 배치: 워커 8개가 25분 = 한 명에 0.86 ms
# 하루 계산: 요청마다 126.7시간, 새벽에 한 번 3.3시간 -> 38배
# 같은 사람이 하루 평균 16.3번 요청한다
#
# 3단계 뜻: 전원을 올리면 3,584MB 로 요청당 0.20ms 다. 활성만 올리면 메모리는 430MB 로 줄지만, 못 찾은 요청은 그 자리에서 만들어 요청당 0.56ms 가 된다.
# 온라인 저장소에 누구의 벡터를 올리나
#   전원  14,000,000명  3,584MB  적중 100%  요청당 0.20ms
#   활성만  1,680,000명    430MB  적중  80%  요청당 0.56ms
#   안 올림          0명      0MB  적중   0%  요청당 2.00ms
```

2단계 출력에서 유저 벡터 표는 14,000,000명 × 64차원 × 4B 로 3.58GB 입니다. 같은 사람이 하루 평균 16.3번 요청해 같은 계산을 되풀이하는 데다 새벽 배치는 한 명에 0.86ms 로 요청 때의 2.0ms 보다 싸서 요청마다 만드는 하루 126.7시간과 새벽에 한 번 만드는 3.3시간이 38배 차이 납니다. 3단계 출력에서는 저장소에 올리는 사람 수에 따라 메모리와 요청당 시간이 반대로 움직이는데, 활성만 올리면 메모리가 3,584MB 에서 430MB 로 줄지만 적중이 100% 에서 80% 로 내려가 요청당 시간이 0.20ms 에서 0.56ms 로 늘어납니다. 아무것도 올리지 않는 「안 올림」은 메모리를 쓰지 않는 대신 적중이 0% 라 요청당 2.00ms 입니다.

그래서 이 서비스는 3.58GB 를 전부 저장소에 올려 찾는 비율을 100% 로 둡니다. 값이 낡는 문제는 3절에서 고른 대로 활성 유저만 한 시간마다 다시 만들어 따로 막습니다. 그러면 요청마다 만들 때의 2.00ms 와 저장소에서 꺼낼 때의 0.20ms 사이의 차이가 남는데, 이 차이가 서버 몇 대이고 한 달에 얼마인지는 다음 절에서 계산합니다.

## 5. 서버 대수와 한 달 값 계산

**요청마다 유저 벡터를 만들면 그 계산만으로 CPU 서버가 7대 더 들어 한 달 2,419,200원이지만 같은 계산을 새벽 배치로 옮기면 한 달 100시간, 48,000원이면 됩니다.**

4절까지는 시간을 ms 와 워커 시간으로 셌지만 서버 값은 서버 대수에 시간당 값을 곱해 치르므로, 요청당 몇 ms 가 드는지를 서버 몇 대가 필요한지로 바꿔야 한 달 값을 비교할 수 있습니다. 대수가 정해지면 한 달 값은 대수 × 720시간 × 시간당 값의 곱셈 한 번으로 나옵니다. 미리 만들어 두면 이 곱셈의 앞자리인 대수가 줄어듭니다.

먼저 요청마다 유저 벡터를 만드는 2.0ms 를 서버 대수로 바꿉니다. 요청이 초당 2,639건 오고 한 건에 2.0ms 가 들면 1초마다 2,639 × 2.0ms = 5,278ms 의 계산이 생기므로, 서버 한 대가 1초에 1초어치 계산을 한다고 두면 5.28대 분량입니다. 이 가정은 이 글의 CPU 서버와 맞는데, 한 대가 287 QPS 를 받고 요청 하나에 3.49ms 가 들어 두 값을 곱하면 1초가 됩니다. 평시에 서버 한 대를 부하율 0.77 까지만 채운다는 규칙을 지키면 5.28대 분량을 0.77 로 나눈 6.86대가 필요한데 서버는 한 대 단위로 사므로 올려서 7대입니다. 7대의 한 달 값은 7대 × 720시간 × 시간당 480원 = 2,419,200원입니다. 같은 계산을 새벽 배치로 옮기면 하루 200분(3.3시간)이라 한 달(30일)이면 100시간이고 100시간 × 480원 = 48,000원입니다.

이번에는 모델 서버 전체가 몇 대 필요한지 셉니다. 대수는 평시 조건과 고장 조건 가운데 큰 쪽으로 정합니다. 평시 조건은 요청량을 한 대 처리량(서버 한 대가 1초에 받아 내는 요청 수)과 부하율 상한(평시에 한 대를 채우는 한계)의 곱으로 나눠 올린 값입니다. 고장 조건은 요청량을 한 대 처리량으로 나눠 올린 값에 예비 대수(서버가 빠져도 요청을 받아 내려고 더 두는 대수)를 더한 값입니다. 평시 조건은 평소에 요청이 기다리는 줄이 길어지지 않게 하고 고장 조건은 서버 한 대가 빠져도 요청을 받아 내게 하므로, 두 조건을 다 지키려면 둘 가운데 큰 대수가 필요합니다.

이 서비스는 지금 부하율 0.77 로 돌고 있어서 부하율 상한도 0.77 로 둡니다. [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편은 부하율이 0.87 을 넘으면 서버를 늘리라고 했으므로 0.77 은 그 기준에서 한 걸음 앞선 값입니다. 부하율이 1 에 가까워질 때 지연이 왜 급하게 나빠지는지는 같은 편에서 다룹니다.

CPU 서버는 한 대가 287 QPS 를 받고 시간당 480원이 듭니다. 평시 조건은 2,639 를 287 × 0.77 로 나눈 11.94 를 올린 12대입니다. 고장 조건은 2,639 를 287 로 나눈 9.20 을 올린 10대에 예비 1대를 더한 11대라서 둘 가운데 큰 12대가 CPU 서버 대수입니다. 한 달 값은 12대 × 720시간 × 480원 = 4,147,200원입니다.

GPU 서버는 한 대가 2,300 QPS 를 받고 시간당 3,800원이 듭니다. 평시 조건으로는 2대면 되지만 2대 가운데 한 대가 빠지면 남은 한 대가 2,639 QPS 를 혼자 받아 부하율이 2,639 ÷ 2,300 = 1.15 가 되는데, 부하율이 1 을 넘으면 들어오는 요청이 서버가 처리할 수 있는 양보다 많아 요청을 다 받아 내지 못합니다. 그래서 GPU 는 고장 조건이 정하는 3대(2,639 ÷ 2,300 을 올린 2대에 예비 1대)가 필요합니다. 한 달 값은 3대 × 720시간 × 3,800원 = 8,208,000원입니다.

세 번째 카드는 요청 2,639 QPS 를 받아 내는 CPU 서버 12대와 GPU 서버 2대에 예비 1대의 한 달 값을 나란히 보여 줍니다.

CPU 와 GPU 가운데 어느 쪽이 싼지가 뒤집히는 자리는 서버 한 대의 값이 아니라 요청량 단위의 값으로 봅니다. 초당 요청 1건(1 QPS)을 한 시간 동안 받아 내는 값을 세면 CPU 는 시간당 480원을 287 QPS 로 나눈 1.67원이고 GPU 는 3,800원을 2,300 QPS 로 나눈 1.65원이라 거의 같으므로, 두 서버의 한 달 값 차이는 대수를 올림하는 데서 생기는 몫과 예비 대수에서만 나옵니다. GPU 는 3대 가운데 1대가 예비라 한 달 값의 3분의 1 이 예비 몫인데, 요청량이 커져 대수가 늘면 예비 1대가 차지하는 몫이 작아져 6,851 QPS 에서 GPU 가 처음으로 CPU 보다 싸집니다. 다만 그보다 큰 요청량에서도 대수를 올림하는 자리마다 싼 쪽이 다시 바뀝니다.

아래 코드는 요청량에 맞춰 서버가 몇 대 필요하고 한 달에 얼마인지를 CPU 와 GPU 로 센 뒤 요청량을 바꿔 가며 어느 쪽이 싼지 확인하려고 돌립니다.

```python
# 하는 일: 요청량에 맞춰 서버가 몇 대 필요한지, 한 달에 얼마인지 CPU 와 GPU 로 센다.
import math

# 1단계: 요청량과 서버 값을 둔다
# 가상 값이다.
QPS = 2_639           # 평시 요청량 (서빙 지연 글의 값)
LOAD_CAP = 0.77       # 부하율 상한. 평시에 이 선을 넘지 않게 대수를 잡는다 (같은 글)
SPARE = 1             # 예비 대수. 이만큼 빠져도 요청을 받아 낸다
HOURS = 720           # 한 달 (30일 x 24시간)
KINDS = {"CPU": (287, 480), "GPU": (2_300, 3_800)}   # (한 대 처리량 QPS, 시간당 원)

# 2단계: 대수와 한 달 값을 구하는 식을 만든다
# 평시에 부하율 상한을 지키는 대수와, 예비가 빠져도 요청을 받아 내는 대수를 비교한다.
def machines(qps, cap):
    """평시 조건과 고장 조건 중 큰 쪽이 대수다."""
    normal = math.ceil(qps / (cap * LOAD_CAP))       # 평시에 부하율 상한을 지키는 대수
    failover = math.ceil(qps / cap) + SPARE          # 예비가 빠져도 요청을 받아 내는 대수
    return max(normal, failover), normal, failover

def cost(qps, cap, won):
    return machines(qps, cap)[0] * HOURS * won

# 3단계: 지금 요청량에서 CPU 와 GPU 를 비교한다
print(f"요청 {QPS:,} QPS, 부하율 상한 {LOAD_CAP}, 예비 {SPARE}대")
for name, (cap, won) in KINDS.items():
    n, normal, failover = machines(QPS, cap)
    print(f"  {name}: 평시 {normal}대, 고장 {failover}대 -> {n}대"
          f" = 한 달 {cost(QPS, cap, won):,}원  (한 대 {cap:,} QPS, 시간당 {won:,}원)")
print(f"  차액 {cost(QPS, *KINDS['GPU']) - cost(QPS, *KINDS['CPU']):,}원\n")

# 4단계: 요청량을 바꿔 가며 싼 쪽을 찾는다
print(f"{'QPS':>7}{'CPU 대수':>8}{'CPU 한 달':>13}{'GPU 대수':>8}{'GPU 한 달':>13}  싼 쪽")
for q in (500, 2_639, 5_000, 10_000, 20_000):
    c, g = cost(q, *KINDS["CPU"]), cost(q, *KINDS["GPU"])
    print(f"{q:>7,}{machines(q, 287)[0]:>8}{c:>13,}{machines(q, 2_300)[0]:>8}{g:>13,}"
          f"  {'GPU' if g < c else 'CPU'}")

flip = next((q for q in range(500, 20_001)
             if cost(q, *KINDS["GPU"]) < cost(q, *KINDS["CPU"])), None)
print(f"\nGPU 가 처음 싸지는 요청량: {flip:,} QPS" if flip
      else "\n20,000 QPS 까지 GPU 가 싸지는 자리가 없다")
for k, (cap, won) in KINDS.items():
    print(f"  {k} 는 QPS 하나를 한 시간 받는 데 {won / cap:.2f}원")

# 출력:
# 3단계 뜻: 2,639 QPS 에서는 CPU 12대가 한 달 4,147,200원으로, GPU 3대의 8,208,000원보다 4,060,800원 싸다.
# 요청 2,639 QPS, 부하율 상한 0.77, 예비 1대
#   CPU: 평시 12대, 고장 11대 -> 12대 = 한 달 4,147,200원  (한 대 287 QPS, 시간당 480원)
#   GPU: 평시 2대, 고장 3대 -> 3대 = 한 달 8,208,000원  (한 대 2,300 QPS, 시간당 3,800원)
#   차액 4,060,800원
#
# 4단계 뜻: 표의 다섯 요청량에서는 모두 CPU 가 싸지만 6,851 QPS 에서는 GPU 가 싸진다. QPS 하나를 한 시간 받는 값이 1.67원과 1.65원으로 거의 같아서, 대수를 올림하는 데서 싼 쪽이 오간다.
#     QPS  CPU 대수      CPU 한 달  GPU 대수      GPU 한 달  싼 쪽
#     500       3    1,036,800       2    5,472,000  CPU
#   2,639      12    4,147,200       3    8,208,000  CPU
#   5,000      23    7,948,800       4   10,944,000  CPU
#  10,000      46   15,897,600       6   16,416,000  CPU
#  20,000      91   31,449,600      12   32,832,000  CPU
#
# GPU 가 처음 싸지는 요청량: 6,851 QPS
#   CPU 는 QPS 하나를 한 시간 받는 데 1.67원
#   GPU 는 QPS 하나를 한 시간 받는 데 1.65원
```

3단계 출력을 보면 지금 요청량 2,639 QPS 에서 CPU 는 평시 12대와 고장 11대 가운데 큰 12대로 한 달 4,147,200원이 들고 GPU 는 평시 2대와 고장 3대 가운데 큰 3대로 한 달 8,208,000원이 들어 CPU 가 4,060,800원 쌉니다. 4단계 표에 찍힌 500 QPS 부터 20,000 QPS 까지의 다섯 요청량에서도 모두 CPU 가 쌉니다. 10,000 QPS 에서도 CPU 46대는 한 달 15,897,600원, GPU 6대는 16,416,000원입니다. QPS 하나를 한 시간 받는 값이 1.67원과 1.65원으로 거의 같아서 싼 쪽은 대수를 올림하는 자리에 따라 오갑니다. 그래서 요청량을 1 QPS 씩 늘려 가며 세어 보면 표에 없는 6,851 QPS 에서 GPU 가 처음 싸집니다.

아래 서빙 비용 계산기는 위 코드와 같은 식으로 대수와 한 달 값을 그립니다. 요청량을 두 배로 올리거나 예비 대수를 0 으로 내리면 CPU 와 GPU 의 두 곡선이 어떻게 움직이는지 보입니다.

이 규모에서는 CPU 12대를 씁니다. GPU 는 대수가 3대로 적어 예비 1대가 한 달 값에서 차지하는 몫이 크므로 CPU 의 두 배가 됩니다. 지금까지의 계산은 모두 새벽에 만든 표를 요청 때 찾을 수 있다는 전제에서 나왔는데, 이 전제는 무대에 따라 달라집니다.

## 6. 미리 만들어 둘 수 있는 범위의 무대별 차이

**미리 만든 벡터를 쓰려면 표에서 그 벡터를 찾을 키(표의 한 줄을 찾는 데 쓰는 값)가 있어야 합니다. 담장 안에서는 회원 번호가 어제도 오늘도 같아서 새벽에 만든 표를 그대로 쓰지만 열린 RTB 에서는 쿠키(브라우저에 저장해 두는 식별 값)가 바뀌어 찾을 키가 없습니다.**

미리 만든 벡터를 꺼내려면 오늘 온 사람이 어제의 누구인지 알아야 하므로, 미리 만들어 둘 수 있는지는 계산이 아니라 그 사람을 알아볼 키가 있는지에 달려 있습니다. 광고가 거래되는 두 무대(담장 안과 열린 RTB)에서는 이 키가 다릅니다.

### 담장 안: 회원 번호로 찾는 벡터 [무대: 닫힌 생태계]

담장 안은 한 회사가 앱과 광고 서버를 다 가진 곳이라 요청에 회원 번호가 담겨 오는데, 이 번호는 어제도 오늘도 같습니다. 그래서 새벽 04:30 에 만든 표에서 오후 3시 요청의 벡터를 회원 번호로 그대로 찾습니다. 폰에서 온 요청과 PC 에서 온 요청도 같은 회원 번호라 같은 벡터를 쓰므로 이 글의 3.58GB 표는 회원 1,400만 명 거의 전부에게 쓸모가 있습니다.

담장 안에 남는 문제는 3절의 값이 낡는 문제 하나뿐입니다. 이 문제는 3절에서 본 대로 활성 유저만 한 시간마다 다시 만들거나 자주 바뀌는 입력만 요청 때 넣어 막습니다. 어느 방법이든 계산을 어디에 둘지 정하는 문제이지 벡터를 찾지 못하는 문제가 아닙니다.

### 열린 RTB: 바뀌는 쿠키와 요청마다 돌리는 유저 타워 [무대: 열린 RTB]

열린 RTB(Real-Time Bidding, 실시간 입찰)에서 광고를 사는 쪽은 남의 지면(광고가 실리는 앱이나 웹페이지의 자리)에서 남의 쿠키를 봅니다. 쿠키는 브라우저마다 다르고 수명도 짧아서 어제 만든 벡터를 찾아올 키 자체가 없는 경우가 많습니다. 그래서 열린 RTB 에서는 요청마다 유저 타워를 돌리고 그때마다 1절의 유저 타워 0.8ms 가 입찰 한 건에 주어진 응답 시간 예산에 그대로 더해집니다. 두 무대의 이 차이는 [Two-Tower Retrieval](post.html?id=two-tower-retrieval) 편의 여덟째 절과 아홉째 절에 나란히 정리되어 있습니다.

처음 보는 쿠키는 더 다루기 어렵습니다. 행동 이력이 없어 유저 타워에 넣을 입력이 거의 비어 있으므로 지면, 시간, 기기처럼 요청 안에 담겨 오는 정보가 입력의 큰 부분을 차지합니다. 그래서 열린 RTB 에서 미리 만들어 둘 수 있는 벡터는 유저 쪽이 아니라 캠페인 쪽입니다. 아래 표에는 가상 데이터가 아니라 두 무대의 설계 차이를 적었습니다.

| 결정 | 담장 안 | 열린 RTB |
|---|---|---|
| 벡터를 찾는 키 | 회원 번호, 어제와 오늘이 같다 | 쿠키, 자주 바뀐다 |
| 유저 벡터 | 새벽에 미리, 요청 때 조회 0.20ms | 요청마다 계산 2.0ms |
| 미리 만든 표의 쓸모 | 회원 1,400만 명 거의 전부 | 다시 온 쿠키만 |
| 남는 문제 | 값이 낡는 것 | 처음 보는 쿠키에 입력이 없는 것 |

유저 타워와 광고 타워는 둘 다 학습을 거쳐야 생기므로 다음 편은 모델을 만드는 학습으로 다시 갑니다. 임베딩이 큰 광고 모델을 GPU 여러 장에 나눠 학습하는 방법은 [분산 학습](post.html?id=distributed-training) 편에서 다룹니다.

|---|---|---|
| 요청 안에서 만들기 | 유저 피처를 읽고 유저 타워를 한 번 돌린다 | 요청당 2.0ms, 하루 126.7시간 |
| 새벽 배치 | 04:30 에 회원 전체의 벡터를 한 번에 만든다 | 워커 8개 25분, 워커 시간 3.3시간 |
| 유저 벡터 표 | 한 명이 64개의 숫자, 값 하나가 4바이트 | 3.58GB, 한 명에 256바이트 |
| 다시 만드는 주기 | 활성 유저만 한 시간마다 | 168만 명, 하루 9.6시간 |
| 온라인 저장소 | 전원을 올리면 찾는 비율이 100% | 3,584MB, 요청당 0.20ms |
| 못 찾은 요청 | 그 자리에서 유저 타워를 돌린다 | 그 요청만 2.0ms |
| 모델 서버 대수 | 평시 조건과 고장 조건 중 큰 쪽 | CPU 12대, GPU 3대 |
| 한 달 값 | 대수 곱하기 720시간 곱하기 시간당 값 | CPU 4,147,200원, GPU 8,208,000원 |

## 헷갈리기 쉬운 점

- **배치 추론과 학습은 다른 일입니다.** 학습은 모델을 만드는 일이고 배치 추론은 이미 만든 모델로 값을 미리 계산해 두는 일인데, 새벽에 도는 작업이 둘 다 있어서 이름이 섞이기 쉽습니다.
- **저장소에서 벡터를 못 찾아도 오류가 나지 않습니다.** 그 자리에서 유저 벡터를 다시 만들어 응답하므로 값은 맞고 그 요청만 느려집니다. 그래서 찾는 비율이 낮아도 대시보드에는 아무 문제가 보이지 않습니다.
- **광고 벡터와 유저 벡터는 다시 만드는 주기가 다릅니다.** 두 벡터는 수가 다르고 바뀌는 속도도 달라서 광고 벡터는 한 시간마다 다시 만들지만 유저 벡터는 새벽에 한 번 만들고 활성 유저의 벡터만 한 시간마다 다시 만듭니다.
- **빠른 서버가 싼 서버는 아닙니다.** 초당 요청 1건(1 QPS)을 한 시간 동안 받아 내는 값이 CPU 1.67원, GPU 1.65원으로 거의 같습니다. 대수가 적을수록 예비 1대가 한 달 값에서 차지하는 몫이 커집니다.
- **미리 만들어 두는 것이 늘 이득은 아닙니다.** 이 글에서는 같은 사람이 하루 평균 16.3번 요청해서 이득이었지만 사람마다 하루에 한 번 올까 말까 하면 미리 만든 벡터의 대부분은 한 번도 쓰이지 않습니다.
