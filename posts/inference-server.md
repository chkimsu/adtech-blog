지훈 씨는 모델 팀으로 옮긴 지 넷째 주입니다. 다음 주에 첫 배포를 맡게 됐습니다. 그래서 그 전에 지금 서버가 모델을 어떻게 싣고 있는지 보기로 했습니다. 학습 폴더를 열어 보니 파일이 둘 있었습니다. 하나는 작고 하나는 컸습니다.

선배에게 물었습니다. 「학습이 끝나면 이 파일이 나오는데, 이게 어떻게 요청에 답하는 서버가 되나요?」 선배의 답은 이랬습니다. 「작은 쪽은 서빙 포맷으로 바꿔서 서버가 뜰 때 내려받아요. 큰 쪽은 따로 있는 서비스에 올려요. 서버가 뜨고 41초 뒤부터 요청을 받아요.」

지훈 씨는 그 41초 동안 무슨 일이 일어나는지 몰랐습니다. 서버가 켜지자마자 답하지 않는 이유도 몰랐습니다. 그리고 요청 하나에 후보가 수백 건 실려 오는데 그것을 하나씩 계산하는지 한꺼번에 계산하는지도 몰랐습니다.

**학습이 남긴 파일은 어디로 가고, 서버는 그것을 어떻게 싣고, 첫 요청은 언제부터 받나요?**

파일이 서버가 되는 자리를 추론 서버(inference server)라고 부릅니다. 학습이 남긴 파일을 열어 메모리에 올리고, 요청에 실려 온 후보에 점수를 매겨 돌려주는 서버입니다. 이 글은 그 서버가 파일을 싣고 첫 요청을 받기까지를 카드 그림으로 봅니다. 이것을 알면 배포 때 왜 서버가 30초 동안 느려지는지, 두 버전을 왜 같이 실어 두는지가 보입니다.

> **한 줄 요약:** 학습이 남긴 파일은 둘입니다. 신경망 38MB 는 ONNX 로 바꿔 서버에 싣고, 임베딩 27.7GB 는 임베딩 서비스에 따로 둡니다. 새 서버는 이미지 시작 12초, 내려받기 6초, 적재 3초, 웜업 20초를 지나 41초에 준비 신호를 켭니다. 후보 800건은 한 텐서로 한 번에 넣어 3.0ms 이고 하나씩이면 96ms 입니다. 두 버전을 같이 실으면 전환이 설정 한 줄이고, 값은 임베딩 27.7GB 입니다.

> **골라 읽는 법** — 절이 열 개인 글입니다. 절마다 카드 한 장이나 표 하나가 들어 있어 그것만 보고 넘어가도 됩니다.
>
> - 학습이 남긴 파일 둘과 그것이 가는 곳 → 1~2절
> - 서버가 뜨는 41초와 준비 신호 → 3절
> - 후보 800건을 한 번에 넣는 이유 → 4절
> - 두 버전을 같이 싣는 값 → 5절
> - 준비 신호가 없으면 생기는 일 → 6절
> - 담장 안과 열린 RTB 의 차이 → 7절

이 글의 파일 크기와 시간은 전부 설명을 위한 가상 값입니다. 임베딩 표 27.7GB 는 [대규모 임베딩 테이블 운영](post.html?id=embedding-table-ops) 편과 같은 값입니다. 모델 서버 12대, 모델 호출 예산 8ms, 새 서버의 첫 30초가 2.5배 느린 것은 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편과 같은 값입니다. 후보 800건은 [Ad Serving Flow](post.html?id=ad-serving-flow) 편의 값입니다. 카드 속 색은 넷입니다. 파랑은 놓여 있는 것(모델 파일, 임베딩 표, 설정), 벽돌색은 지금 오는 것(요청, 후보)입니다. 먹색은 모델과 서버이고 회색은 만드는 작업(변환, 웜업, 추론)입니다. 점선 상자는 적어 둔 것(설정, 준비 조건)입니다.

## 1. 학습이 남긴 파일은 둘입니다

**학습이 끝나면 신경망 가중치 38MB 와 임베딩 표 27.7GB 가 남습니다. 둘은 크기가 700배 다르고 가는 곳도 다릅니다.**

쉽게 말하면 모델은 한 덩어리가 아닙니다. 「어떤 ID 가 어떤 숫자 묶음인가」를 적은 큰 표와, 그 숫자 묶음을 받아 확률을 내는 작은 계산기로 나뉩니다. 큰 표는 서버 한 대에 실을 크기가 아니라 따로 둡니다.

지훈 씨가 본 학습 폴더의 파일 둘이 그것입니다. 가정은 아래 표의 크기이고, 임베딩 표의 크기는 임베딩 편에서 계산한 값 그대로입니다. 2억 줄 곱하기 32차원 곱하기 4바이트에 다른 표를 더한 27.7GB 입니다.

| 파일 | 무엇 | 크기 | 어디로 가나 | 얼마나 자주 바뀌나 |
|---|---|---|---|---|
| 신경망 가중치 | 숫자 묶음을 받아 클릭 확률을 내는 계산 | 38MB | 서버 12대 각각 | 매일 새벽 |
| 임베딩 표 | 회원 ID, 광고 ID 마다 숫자 묶음 | 27.7GB | 임베딩 서비스 한 곳 | 매일 새벽, 줄 일부만 |

서버 12대가 각각 27.7GB 를 들면 332GB 입니다. 그래서 임베딩 표는 한 곳에 두고 서버가 요청마다 필요한 줄만 가져옵니다. 요청 하나에 회원 한 줄과 광고 800줄입니다. 그 서비스가 무엇이고 어떻게 쪼개 담는지는 [대규모 임베딩 테이블 운영](post.html?id=embedding-table-ops) 편에 있습니다. 이 글은 서버 12대에 각각 실리는 38MB 쪽을 따라갑니다.

두 파일은 바뀌는 방식도 다릅니다. 신경망은 매일 새벽 통째로 새 파일이 됩니다. 임베딩 표는 새로 생긴 ID 의 줄만 더해지고 죽은 ID 의 줄만 빠집니다. 통째로 바뀌는 쪽은 서버가 뜰 때 내려받으면 되고, 줄 단위로 바뀌는 쪽은 켜 둔 채로 고칩니다. 38MB 를 서버에 싣는 첫걸음은 파일의 모양을 바꾸는 것입니다.

## 2. 학습 파일을 서빙 포맷으로 바꿉니다

**학습이 남긴 파일은 학습 프레임워크와 파이썬 코드가 있어야 열립니다. ONNX 로 바꾸면 그래프와 가중치만 남아 작은 런타임 하나로 열립니다.**

쉽게 말하면 학습 파일은 「이 클래스의 객체를 이렇게 복원하라」는 지시라서, 그 클래스 코드와 프레임워크가 서버에 같이 있어야 합니다. ONNX 는 계산 순서와 숫자만 적은 파일이라 코드 없이 파일만 있으면 됩니다.

바꾸고 나면 서버에 같이 있어야 하는 것이 달라집니다. 학습 형식 그대로 실으면 학습 프레임워크 1.2GB 와 모델 클래스의 파이썬 코드가 서버 이미지에 들어가야 합니다. ONNX 면 추론 런타임 0.8GB 만 있으면 됩니다. 앞 편 [Docker 와 CI](post.html?id=container-ci-pipeline) 의 추론 이미지가 1.1GB 로 작았던 이유가 이것입니다. 적재 시간도 줄어듭니다. 이 팀에서는 학습 형식이 9초, ONNX 가 3초입니다.

바꾼 파일을 서버가 열면 이런 서명이 나옵니다. 입력 셋과 출력 하나이고, 800 은 요청 하나에 실린 후보 수입니다.

```text
model: pctr-v418.onnx (38MB)
inputs
  ids     int64   [800, 6]     # 후보마다 해시된 ID 칸 여섯 (광고, 지면, 카테고리 등)
  emb     float32 [800, 32]    # 임베딩 서비스에서 가져온 광고 줄 800개
  dense   float32 [800, 12]    # 집계 피처 열두 개 (7일 클릭률 등)
outputs
  pctr    float32 [800]        # 후보마다 클릭 확률 하나
```

이 서명이 앞 편의 계약 테스트가 보던 「모양」입니다. 입력 세 개의 이름과 자료형과 칸 수가 서버 코드와 맞아야 합니다. 지훈 씨가 더한 7일 클릭률은 `dense` 의 열두 칸 중 하나로 들어갑니다. 파일이 준비됐으니 이제 서버가 그것을 싣는 41초를 봅니다.

## 3. 서버가 뜨는 41초

**새 서버는 켜지자마자 답하지 않습니다. 이미지 시작 12초, 모델 내려받기 6초, 적재 3초, 웜업 20초를 지나 41초에 준비 신호를 켭니다. 게이트웨이는 그 신호가 켜진 서버에만 요청을 보냅니다.**

쉽게 말하면 서버가 「나 준비됐다」고 말하기 전에는 요청을 안 보내는 것입니다. 준비됐다는 말의 조건이 정해져 있고, 그 조건에 웜업이 들어 있습니다.

41초는 넷으로 나뉩니다. 처음 12초는 이미지가 켜지는 시간입니다. 앞 편의 1.1GB 이미지에서 파이썬과 런타임이 올라옵니다. 다음 6초는 모델 파일 38MB 를 저장소에서 가져오는 시간입니다. 이미지에 모델을 안 넣었으니 여기서 내려받습니다. 다음 3초는 그 파일을 메모리에 올리는 적재입니다. 여기까지 21초이고 모델은 답할 수 있는 상태입니다. 그런데 바로 열지 않습니다.

마지막 20초가 웜업입니다. 가짜 요청 200건을 서버 자신에게 보내 답하게 합니다. 처음 몇 번의 계산은 느립니다. 런타임이 계산 순서를 최적화하고 메모리를 잡는 일을 첫 요청에서 하기 때문입니다. 실제 요청이 그 몫을 치르게 두면 첫 30초가 2.5배 느립니다. 200건을 먼저 먹여 그 몫을 미리 치릅니다. 200건이 끝나면 준비 신호를 켭니다.

준비 신호는 서버가 도는 자리에 설정으로 적어 둡니다. [쿠버네티스 네트워킹](post.html?id=kubernetes-networking) 편의 Pod 설정에 이렇게 들어갑니다.

```yaml
readinessProbe:
  httpGet:
    path: /ready            # 모델이 올라오고 웜업 200건이 끝나면 200 을 돌려주는 주소
    port: 8080
  initialDelaySeconds: 20   # 켜지고 20초는 묻지 않습니다
  periodSeconds: 3          # 그 뒤 3초마다 묻습니다
  failureThreshold: 10      # 열 번 연속 실패면 이 서버에는 안 보냅니다
```

`/ready` 가 200 을 돌려주는 조건이 셋입니다. 파일을 내려받았다, 메모리에 올렸다, 웜업 200건이 끝났다. 이 셋이 다 참이어야 게이트웨이의 목록에 들어갑니다. 신호를 안 켜고 열면 무슨 일이 생기는지는 6절에서 셉니다. 그 전에 준비된 서버가 요청 하나를 어떻게 처리하는지 봅니다.

## 4. 후보 800건을 한 번에 넣습니다

**요청 하나에 후보 800건이 실려 옵니다. 하나씩 800번 모델을 부르면 96ms 이고, 800줄을 한 텐서로 한 번에 넣으면 3.0ms 입니다. 예산 8ms 안에 드는 것은 한 번에 넣는 쪽뿐입니다.**

쉽게 말하면 모델을 한 번 부를 때마다 계산과 상관없는 고정 비용이 붙습니다. 입력을 받아 넘기고 결과를 꺼내는 일입니다. 800번 부르면 그 비용이 800번 붙고, 한 번 부르면 한 번만 붙습니다.

<iframe class="demo-embed" src="demo-inference-cards.html?embed=1&card=batch" height="480" loading="lazy" title="후보 800건을 한 번에"></iframe>

고정 비용과 건당 비용은 측정 둘로 풀립니다. 이 팀의 서버는 후보 800건을 한 텐서로 넣으면 3.0ms 이고, 후보 한 건만 넣으면 0.12ms 입니다. 두 값에서 호출 한 번의 고정 비용과 후보 한 건의 계산 비용이 나옵니다. 아래는 그 계산이고, 후보 수를 바꾸면 두 방식의 시간이 어떻게 달라지는지도 같이 냅니다.

```python
# 후보를 한 텐서로 넣을 때와 하나씩 부를 때의 시간 — 측정 둘에서 고정 비용과 건당 비용을 푼다.
# 측정값(가상): 한 텐서 800건 3.0ms, 후보 1건 한 번 0.12ms. 모델 호출 예산은 8ms.
# 시간 = 고정 비용 + 후보 수 × 건당 비용 이라고 두면, 두 측정값으로 미지수 둘이 풀린다.

BUDGET = 8.0
T_800, T_1 = 3.0, 0.12
per_row = (T_800 - T_1) / 799          # 후보 한 건의 계산 비용
fixed = T_1 - per_row                   # 호출 한 번의 고정 비용
print(f"호출 고정 비용 {fixed:.4f}ms, 건당 계산 {per_row:.4f}ms")
print(f"{'후보 수':>7}  {'한 텐서':>8}  {'하나씩':>9}   판정 (예산 {BUDGET:.0f}ms)")
for n in (1, 100, 800, 2000):
    one = fixed + n * per_row           # 한 번 부르고 n 줄 계산
    each = n * (fixed + per_row)        # n 번 부르고 매번 1줄 계산
    v1 = "통과" if one <= BUDGET else "초과"
    v2 = "통과" if each <= BUDGET else "초과"
    print(f"{n:>7,}  {one:>7.2f}ms  {each:>8.2f}ms   한 텐서 {v1}, 하나씩 {v2}")

# 출력:
# 호출 고정 비용 0.1164ms, 건당 계산 0.0036ms
#    후보 수      한 텐서        하나씩   판정 (예산 8ms)
#       1     0.12ms      0.12ms   한 텐서 통과, 하나씩 통과
#     100     0.48ms     12.00ms   한 텐서 통과, 하나씩 초과
#     800     3.00ms     96.00ms   한 텐서 통과, 하나씩 초과
#   2,000     7.33ms    240.00ms   한 텐서 통과, 하나씩 초과
```

호출 한 번의 고정 비용이 0.1164ms 이고 후보 한 건의 계산은 0.0036ms 입니다. 고정 비용이 계산의 32배입니다. 그래서 하나씩 부르면 후보 100건에서 이미 12ms 로 예산을 넘깁니다. 한 텐서로 넣으면 2,000건도 7.33ms 로 예산 안입니다. 후보를 800건에서 2,000건으로 늘려도 되는 여유가 이 계산에서 나옵니다.

여기서 나오는 결정은 하나입니다. 서버 코드는 요청에 실린 후보를 모아 한 텐서로 만든 뒤 모델을 한 번만 부릅니다. 2절의 서명에서 입력이 `[800, …]` 모양이었던 이유입니다. 요청 여럿을 모아 더 큰 텐서로 만드는 방법도 있는데, 그러면 모이기를 기다리는 시간이 붙습니다. 그 저울질은 [광고 모델 서빙 아키텍처](post.html?id=model-serving-architecture) 편의 배치 카드에 있습니다.

## 5. 두 버전을 동시에 싣습니다

**운영 중인 v417 과 새 v418 을 한 서버에 같이 올려 두고, 어느 쪽이 답할지는 설정 한 줄로 정합니다. 바꾸는 것도 되돌리는 것도 그 한 줄이라 몇 초면 됩니다.**

쉽게 말하면 새 모델로 바꾸는 순간에 서버를 껐다 켜지 않는 것입니다. 두 파일을 다 올려 두고 가리키는 곳만 바꿉니다. 문제가 생기면 가리키는 곳을 도로 돌립니다.

<div class="demo-embed-wrap">
<iframe class="demo-embed" src="demo-inference-cards.html?embed=1&card=twoversions" height="480" loading="lazy" title="두 버전을 동시에 싣는다"></iframe>
<a class="demo-embed-open" href="demo-inference-cards.html" target="_blank" rel="noopener">↗ 카드 네 장 전체로 열기</a>
</div>

서버 안의 설정은 이 한 줄입니다.

```yaml
active: v417        # 지금 답하는 버전. v418 로 바꾸면 다음 요청부터 v418 이 답합니다
loaded: [v417, v418]
```

바꾸는 데 걸리는 시간이 왜 몇 초인지가 중요합니다. 새 서버를 띄우면 3절의 41초가 12대 전부에 듭니다. 설정 한 줄이면 서버는 그대로이고 메모리에 이미 올라온 파일을 가리키기만 합니다. 되돌리기도 같습니다. 새 모델이 이상하면 `active` 를 v417 로 돌립니다. [시스템 설계 면접](post.html?id=interview-system-design) 편이 「되돌리는 데 30분이 걸리면 그 30분 동안 사고가 계속된다」고 한 것이 이 자리입니다.

값은 메모리입니다. 가정은 버전마다 신경망 38MB 와 임베딩 표 27.7GB 가 든다는 것이고, 둘 다 실으면 각각 두 배입니다.

| 무엇 | v417 만 | v417 과 v418 | 두 배가 되는 값 |
|---|---|---|---|
| 서버 12대의 신경망 | 38MB 씩 | 76MB 씩 | 거의 안 듭니다 |
| 임베딩 서비스의 표 | 27.7GB | 55.4GB | 27.7GB 를 더 듭니다 |
| 전환에 걸리는 시간 | 없음 | 설정 한 줄, 몇 초 | |
| 되돌리기 | 없음 | 같은 한 줄 | |

신경망은 둘을 실어도 76MB 라 값이 거의 없습니다. 값은 임베딩에서 듭니다. v418 은 v417 과 다른 숫자 묶음을 배웠으니 임베딩 표도 v418 것이 따로 있어야 합니다. 27.7GB 가 55.4GB 가 됩니다. 두 버전을 같이 두는 값이 여기서 듭니다. 그래서 두 버전을 같이 두는 기간을 정해 놓고, 새 버전이 자리를 잡으면 옛 표를 내립니다. 그 기간을 정하는 절차가 다음 편 [모델 배포와 롤백](post.html?id=model-deployment-rollback) 입니다.

## 6. 준비 신호가 없으면 생기는 일

**웜업 없이 서버를 열면 첫 30초 동안 요청이 2.5배 느립니다. 서버 2대를 바꿀 때마다 폴백이 939건 더 나가고, 12대를 다 바꾸면 5,637건입니다.**

쉽게 말하면 3절의 웜업 20초를 아끼면 그 값을 실제 요청이 치릅니다. 예산을 넘긴 요청은 모델 답 대신 기본값으로 나갑니다. 그 수를 세어 봅니다.

[서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편 8절에 그 장면이 있습니다. 서버 12대 중 2대를 새로 올리면 그 2대가 첫 30초 동안 2.5배 느립니다. 그동안 8ms 초과율이 4.62% 에서 11.74% 로 오릅니다. 아래는 그 값으로 폴백이 몇 건 더 나가는지 센 것입니다.

```python
# 준비 신호 없이 새 서버 2대를 열면 첫 30초 동안 폴백이 몇 건 더 나가나.
# 서버 12대가 초당 2,639건을 나눠 받는다. 새 서버는 첫 30초 동안 2.5배 느려
# 8ms 초과율이 4.62% 에서 11.74% 가 된다 (서빙 지연과 처리량 편 8절 값). 배포는 2대씩 여섯 번.

QPS, SERVERS, COLD_SEC = 2639, 12, 30
NORMAL, COLD = 0.0462, 0.1174
per_server = QPS / SERVERS                      # 서버 한 대가 받는 초당 요청
cold_reqs = per_server * 2 * COLD_SEC           # 새 2대가 느린 30초 동안 받는 요청
extra = cold_reqs * (COLD - NORMAL)             # 평소보다 더 넘긴 요청
print(f"서버 한 대 초당 {per_server:.0f}건. 새 2대가 첫 30초 동안 받는 요청 {cold_reqs:,.0f}건")
print(f"그중 예산을 넘겨 폴백으로 나간 요청이 평소보다 {extra:,.0f}건 더 (2대 한 번 바꿀 때)")
print(f"12대를 2대씩 여섯 번 바꾸면 {extra * 6:,.0f}건. 웜업 200건을 먼저 먹이면 0건")

# 출력:
# 서버 한 대 초당 220건. 새 2대가 첫 30초 동안 받는 요청 13,195건
# 그중 예산을 넘겨 폴백으로 나간 요청이 평소보다 939건 더 (2대 한 번 바꿀 때)
# 12대를 2대씩 여섯 번 바꾸면 5,637건. 웜업 200건을 먼저 먹이면 0건
```

한 번 배포에 5,637건입니다. 하루 2억 2,800만 건에 견주면 작아 보입니다. 그런데 이 5,637건은 전부 배포 직후 몇 분에 몰려 있습니다. 그 시각에 광고를 본 사람들은 순위가 틀린 광고를 봅니다. 그리고 배포는 모델이 바뀌는 매일 일어납니다.

웜업 200건은 20초입니다. 서버 한 대가 초당 220건을 받으니 200건은 실제 요청으로 치면 1초 분량입니다. 그 1초 분량을 가짜 요청으로 먼저 치르는 것이 준비 신호의 조건에 웜업이 들어 있는 이유입니다. 다음 편에서 카나리 배포가 새 서버 2대를 띄울 때 이 41초를 그대로 기다립니다.

| 열 때 | 첫 30초 초과율 | 2대 한 번에 폴백 | 12대 전부 |
|---|---|---|---|
| 준비 신호 없이 바로 | 11.74% | 939건 더 | 5,637건 더 |
| 웜업 200건 뒤 준비 신호 | 4.62% (평소와 같음) | 0건 | 0건 |

## 7. 무엇을 미리 구워 둘 수 있나가 다릅니다

**담장 안에서는 요청량과 회원을 알아 웜업 요청을 실제 분포로 만들고 유저 임베딩을 미리 구워 둡니다. 열린 RTB 에서는 트래픽이 튀고 쿠키가 매번 달라 웜업 표본을 로그에서 뽑고 유저 쪽은 그때그때 계산합니다.**

쉽게 말하면 서버가 뜨는 41초와 한 텐서로 넣는 계산은 두 무대가 같습니다. 다른 것은 「미리 해 둘 수 있는 것」의 범위입니다.

### 담장 안에서는 웜업이 실제 요청과 같습니다 [무대: 닫힌 생태계]

한 회사가 앱과 서버를 다 가진 담장 안에서는 요청이 얼마나 오고 어떤 회원이 오는지 압니다. 웜업 200건을 어제 로그에서 뽑으면 실제 요청과 같은 모양입니다. 회원 ID 로 임베딩 줄을 미리 만들어 두니 서버는 요청마다 조회만 합니다. [Two-Tower Retrieval](post.html?id=two-tower-retrieval) 편이 「유저 벡터를 미리 구워 둘 수 있다」고 한 것이 이 자리입니다. 이 블로그의 저자가 일하는 자리이고, 이 글의 카드들은 이 상태를 그린 것입니다.

### 열린 RTB 에서는 유저 쪽을 그때 계산합니다 [무대: 열린 RTB]

열린 RTB 의 입찰 서버는 남의 거래소가 보내는 요청을 받습니다. 요청량은 거래소 사정에 따라 튀고, 요청에 실린 것은 회원 ID 가 아니라 쿠키입니다. 쿠키는 매번 달라서 그 사람의 임베딩 줄을 미리 만들어 둘 수 없습니다. 유저 쪽 숫자 묶음을 요청이 온 그때 계산해야 하니 한 텐서 계산에 그 몫이 더 붙습니다. 웜업 표본도 어느 거래소 요청이 올지 몰라 거래소별 로그에서 섞어 뽑습니다. [광고 모델 서빙 아키텍처](post.html?id=model-serving-architecture) 편 9절이 이 차이를 「남의 트래픽은 튀고 캐시는 안 맞는다」로 적었습니다.

| 무엇 | 담장 안 | 열린 RTB |
|---|---|---|
| 웜업 요청 200건의 출처 | 어제 우리 로그 | 거래소별 로그를 섞어서 |
| 유저 쪽 임베딩 | 회원 ID 로 미리 구워 둠 | 쿠키라 요청 때 계산 |
| 요청량 | 우리가 압니다 | 거래소 사정에 따라 튑니다 |
| 한 텐서 계산에 붙는 것 | 조회뿐 | 유저 쪽 계산이 더 붙습니다 |

## 한눈 정리

| 질문 | 한 줄 답 |
|---|---|
| 학습이 남기는 파일은 | 둘입니다. 신경망 38MB 와 임베딩 표 27.7GB 입니다 |
| 둘은 어디로 가나 | 신경망은 서버 12대 각각, 임베딩은 임베딩 서비스 한 곳입니다 |
| 왜 포맷을 바꾸나 | ONNX 면 프레임워크와 코드 없이 런타임 0.8GB 로 열립니다 |
| 서버가 뜨는 데 얼마나 걸리나 | 41초입니다. 이미지 12초, 내려받기 6초, 적재 3초, 웜업 20초 |
| 준비 신호가 무엇인가 | 셋이 다 됐을 때 켜는 신호입니다. 게이트웨이는 켜진 서버에만 보냅니다 |
| 후보 800건은 어떻게 넣나 | 한 텐서로 한 번에 3.0ms 입니다. 하나씩이면 96ms 입니다 |
| 두 버전을 왜 같이 싣나 | 전환과 되돌리기가 설정 한 줄, 몇 초가 됩니다 |
| 그 값은 | 임베딩 표 27.7GB 가 하나 더 듭니다 |
| 웜업을 빼면 | 2대 바꿀 때 폴백 939건, 12대면 5,637건이 더 나갑니다 |

## 헷갈리기 쉬운 점

- **모델 파일은 하나가 아닙니다.** 신경망 38MB 와 임베딩 27.7GB 이고, 서버에 실리는 것은 38MB 쪽입니다.
- **ONNX 로 바꿔도 가중치는 그대로 38MB 입니다.** 줄어드는 것은 서버가 같이 실어야 하는 프레임워크와 코드입니다.
- **적재가 끝났다고 준비된 것이 아닙니다.** 웜업 200건까지 끝나야 준비 신호가 켜집니다.
- **한 텐서는 요청 하나 안의 후보를 묶는 것입니다.** 요청 여럿을 묶는 배치와는 다른 이야기입니다.
- **두 버전을 같이 싣는 값은 신경망이 아니라 임베딩입니다.** 76MB 는 값이 아니고 55.4GB 가 값입니다.
