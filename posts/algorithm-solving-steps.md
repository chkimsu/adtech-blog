코딩테스트 문제를 받으면 지문을 다 읽기도 전에 손이 먼저 반복문을 쓰기 시작하는 경우가 많습니다. 예제가 맞아서 제출했는데 입력이 10만 개인 채점 데이터에서 시간 초과가 나고, 그때서야 n 의 범위를 다시 읽게 됩니다.

문제를 푸는 사람 대부분은 머릿속에서 두 단계를 거칩니다. 데이터를 어떤 자료구조에 담을지 정하고, 그 위에서 투 포인터, 슬라이딩 윈도우, 그리디 같은 접근 방법을 고릅니다. 그런데 이 두 단계 앞에는 「무엇을 묻는가」와 「얼마나 빨라야 하는가」를 확인하는 단계가 있고, 뒤에는 「정말 맞는가」를 확인하는 단계가 있습니다.

**자료구조와 접근 방법을 고르기 전과 후에 무엇을 해야 할까요?**

이 글은 그 전체 순서를 다섯 단계(이해, 제약 보기, 자료구조, 접근 방법, 구현과 확인)로 정리한 풀이 템플릿입니다. 면접 준비 자료는 비슷한 순서를 UMPIRE 라고 부르는데, 순서를 정해 두면 시간 초과나 빈 입력 같은 실수를 제출 전에 잡을 수 있어서 같은 실력으로도 통과하는 문제가 늘어납니다.

> **한 줄 요약:** 지문에서 입력 범위와 예외 입력을 먼저 묻고, n 으로 허용 시간 복잡도를 거꾸로 계산한 뒤, 자료구조와 접근 방법을 고르고, 예제와 경계 입력으로 확인하고 복잡도를 말합니다. 이 글의 예제에서 n 이 10만이면 모든 구간을 보는 풀이는 50억 번이 넘고, 슬라이딩 윈도우는 20만 번 안쪽입니다.

> **골라 읽는 법** — 절이 여덟 개인 글입니다.
>
> - 전체 순서와 UMPIRE → 1절
> - 이해와 제약 보기 → 2~3절
> - 자료구조와 접근 방법 고르기 → 4~5절
> - 예제 하나를 처음부터 끝까지 → 2~6절
> - 입력 방식 두 가지와 30분 라이브 코딩 → 7~8절

## 1. 풀이 다섯 단계

**순서는 이해, 제약 보기, 자료구조, 접근 방법, 구현과 확인입니다. 흔히 말하는 「데이터를 자료구조로 만들고 접근 방법을 고른다」는 가운데 두 단계입니다.**

가운데 두 단계만으로 풀면 양쪽 끝이 빠집니다. 앞쪽에서는 「이 문제가 얼마나 빠른 풀이를 요구하는가」가 빠져서 맞지만 느린 풀이를 다 쓴 뒤에야 시간 초과를 보고, 뒤쪽에서는 「빈 배열이나 답이 없는 입력에서도 맞는가」가 빠져서 예제는 통과하고 채점 데이터에서 틀립니다.

| 단계 | 하는 일 | 끝나면 손에 있는 것 | UMPIRE 의 이름 |
|---|---|---|---|
| 1. 이해 | 입력 범위, 빈 입력, 중복을 묻고 작은 예제를 손으로 푼다 | 손으로 구한 답과 경계 입력 목록 | Understand |
| 2. 제약 보기 | n 의 최댓값으로 허용 시간 복잡도를 계산한다 | 「O(n log n) 이하」 같은 목표 | (이 글이 따로 뗀 단계) |
| 3. 자료구조 | 배열, 해시, 힙, 덱, 그래프 가운데 고른다 | 데이터를 담을 자료구조 | Match |
| 4. 접근 방법 | 투 포인터, 슬라이딩 윈도우, 이진 탐색, 그리디, BFS/DFS, DP 가운데 고른다 | 의사코드 몇 줄 | Match, Plan |
| 5. 구현과 확인 | 코드를 쓰고 예제와 경계 입력을 돌리고 복잡도를 말한다 | 통과한 코드와 「시간 O(n), 공간 O(1)」 한 줄 | Implement, Review, Evaluate |

UMPIRE 는 Understand, Match, Plan, Implement, Review, Evaluate 의 머리글자입니다. CodePath 의 면접 안내서는 Understand 에서 면접관에게 묻고 테스트 케이스를 만들며, Match 에서 문제 유형을 맞추고, Plan 에서 의사코드를 쓰고, Implement 에서 코드를 쓰고, Review 에서 코드를 한 줄씩 따라가고, Evaluate 에서 시간과 공간 복잡도를 말하라고 합니다.

그 안내서는 입력 크기 제한을 따로 다루지 않습니다. 코딩테스트 사이트는 지문에 n 의 범위를 적어 주고 그 범위가 고를 수 있는 풀이를 줄여 주므로, 이 글은 그것을 2단계로 따로 뗐습니다.

이 글은 지어낸 문제 하나를 이 순서로 처음부터 끝까지 풉니다. 2절에서 지문을 읽고 손으로 풀고, 3절에서 n 으로 목표 복잡도를 정하고, 4~5절에서 배열과 슬라이딩 윈도우를 고르고, 6절에서 코드를 돌려 확인합니다.

## 2. 이해: 입력 범위, 빈 입력, 중복

**코드를 쓰기 전에 「입력이 얼마나 크고, 비어 있을 수 있고, 같은 값이 있는가」를 확인하고, 작은 예제를 손으로 풀어 답 하나를 구해 둡니다.**

이 단계를 건너뛰면 지문의 한 낱말을 잘못 읽은 채 20분을 씁니다. 「연속한」을 놓치면 아무 날이나 골라도 되는 문제로 풀게 되고, 「없으면 0」을 놓치면 답이 없는 입력에서 무한대 값이나 오류를 돌려줍니다. 면접이라면 이 질문을 소리 내어 물으면 되고, 시험이라면 지문의 제한 칸에서 찾아 적어 둡니다.

설명을 위해 문제 하나를 지어냈습니다. 같은 모양의 문제가 여러 연습 사이트에 있지만, 아래 지문과 숫자는 이 글이 만든 가상 데이터입니다.

> **지문(가상):** 광고 하나의 하루 클릭 수가 날짜 순서대로 배열 `clicks` 에 담겨 있습니다. 클릭 합이 `S` 이상인 연속한 기간 가운데 가장 짧은 기간의 날 수를 구합니다. 그런 기간이 없으면 0 을 답합니다. 제한: 1 ≤ n ≤ 100,000, 1 ≤ `clicks[i]` ≤ 10,000, 1 ≤ `S` ≤ 10^9.

지문에서 확인한 것은 셋입니다. 첫째, n 은 1 이상이라 빈 배열은 들어오지 않지만 함수로 받는 문제라면 빈 배열에도 0 을 돌려주게 짜 두는 편이 안전합니다. 둘째, 클릭 수가 모두 1 이상이라 음수와 0 이 없는데, 이 조건 덕분에 6절에서 슬라이딩 윈도우를 쓸 수 있습니다. 셋째, 같은 값이 여러 번 나와도 답은 기간의 길이라 중복은 결과를 바꾸지 않습니다.

이제 작은 예제를 손으로 풉니다. 8일치 가상 클릭 수이고, `S` 는 7 입니다.

| 날 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| 클릭 | 2 | 3 | 1 | 2 | 4 | 3 | 1 | 5 |

하루짜리 기간은 가장 큰 값이 5 라서 7 에 닿지 않습니다. 이틀짜리를 앞에서부터 더하면 5, 4, 3, 6, 7 이 나오는데, 5일째와 6일째를 더한 4 + 3 = 7 에서 처음 7 이 되므로 답은 2 입니다. 이 손 풀이가 6절에서 코드가 내야 할 정답이 되고, 「합이 S 에 못 미치는 입력」과 「하루로 끝나는 입력」은 경계 입력 목록에 적어 둡니다.

## 3. 제약 보기: n 에서 구하는 허용 복잡도

**n 의 최댓값을 후보 복잡도에 넣어 연산 횟수를 구하고 1초 안에 들어가는지 봅니다. 어림 기준은 컴파일 언어에서 단순 연산 약 1억 회가 1초입니다.**

이 단계가 없으면 풀이를 다 쓴 뒤에야 느리다는 것을 압니다. 반대로 n 을 먼저 보면 「이 문제는 O(n^2) 으로는 안 된다」를 코드 한 줄 쓰기 전에 알 수 있어서, 4~5절에서 고를 후보가 줄어듭니다. 시간 복잡도는 입력 크기 n 이 커질 때 연산 횟수가 어떤 꼴로 늘어나는지를 나타낸 것이고, O(n^2) 은 n 이 두 배가 되면 연산이 네 배가 된다는 뜻입니다.

1억 회라는 기준은 C++ 같은 컴파일 언어에서 덧셈과 비교 같은 단순 연산을 셀 때 쓰는 어림값입니다. 채점 서버와 연산 종류에 따라 몇 배씩 달라지므로 보장값이 아니고, Python 은 같은 반복문이 여러 배 느리므로 계산 결과가 1초 근처라면 통과를 기대하지 말고 한 단계 빠른 방법을 찾습니다.

```python
# 하는 일: n 이 20, 1,000, 10만, 100만일 때 2^n, n^2, n log n, n 번의 연산이 초당 1억 회 기준으로 몇 초인지 계산한다.
import math

# 1단계: 어림 기준을 둔다
# 컴파일 언어에서 단순 연산 1억 회를 대략 1초로 잡는 어림값이다. 보장값이 아니다.
OPS_PER_SEC = 10**8

def sec(ops):
    s = ops / OPS_PER_SEC
    if s < 0.01:
        return '0.01초 미만'
    if s > 10**6:
        return '너무 큼'
    return f'{s:,.2f}초'

# 2단계: n 마다 네 가지 복잡도의 예상 시간을 찍는다
# 2^n 은 n 이 30 을 넘으면 너무 커서 계산하지 않는다.
for n in [20, 1_000, 100_000, 1_000_000]:
    two_n = sec(2**n) if n <= 30 else '너무 큼'
    print(f'n={n:>9,}  2^n {two_n:>8}  n^2 {sec(n*n):>11}  '
          f'n log n {sec(n*math.log2(n)):>8}  n {sec(n):>8}')

# 3단계: 이 글의 예제에서 두 풀이의 연산 횟수를 비교한다
# 모든 연속 구간을 보면 구간이 n(n+1)/2 개다. 슬라이딩 윈도우는 양 끝이 각각 최대 n 번 움직인다.
n = 100_000
print(f'모든 구간       {n*(n+1)//2:>13,}번  {sec(n*(n+1)//2)}')
print(f'슬라이딩 윈도우 {2*n:>13,}번  {sec(2*n)}')

# 출력:
# 2단계 뜻: n 이 10만이면 n^2 은 100초, n log n 은 0.02초라 O(n log n) 이하가 목표가 된다.
# n=       20  2^n    0.01초  n^2    0.01초 미만  n log n 0.01초 미만  n 0.01초 미만
# n=    1,000  2^n     너무 큼  n^2       0.01초  n log n 0.01초 미만  n 0.01초 미만
# n=  100,000  2^n     너무 큼  n^2     100.00초  n log n    0.02초  n 0.01초 미만
# n=1,000,000  2^n     너무 큼  n^2  10,000.00초  n log n    0.20초  n    0.01초
# 3단계 뜻: 모든 구간을 보면 50억 번이 넘어 50초이고, 슬라이딩 윈도우는 20만 번이라 0.01초도 안 걸린다.
# 모든 구간       5,000,050,000번  50.00초
# 슬라이딩 윈도우       200,000번  0.01초 미만
```

표로 정리하면 아래와 같습니다. 왼쪽 칸의 n 을 보고 오른쪽 칸 이하의 복잡도를 목표로 잡는다는 어림 기준이고, 경계 근처에서는 상수와 언어에 따라 결과가 달라집니다.

| n 의 최댓값 | 목표 복잡도 | 자주 쓰는 풀이 |
|---|---|---|
| 20 안팎 | O(2^n), O(n 2^n) | 완전 탐색, 비트마스크, 백트래킹 |
| 1,000 안팎 | O(n^2) | 이중 반복문, 2차원 DP |
| 10만 안팎 | O(n log n) | 정렬, 이진 탐색, 힙 |
| 100만 이상 | O(n) | 한 번 순회, 투 포인터, 슬라이딩 윈도우, 해시 |

이 글의 예제는 n 이 10만이라 표의 셋째 줄이고, 모든 구간을 보는 풀이는 3단계 출력처럼 구간이 50억 개가 넘어 1억 회 기준으로도 50초입니다. 그래서 목표를 O(n log n) 이하로 잡고, 실제로는 O(n) 인 슬라이딩 윈도우가 20만 번 안쪽으로 끝나므로 Python 으로도 여유가 있습니다.

## 4. 자료구조: 데이터를 담는 다섯 가지

**목표 복잡도가 정해지면 「자주 하는 연산이 무엇인가」로 자료구조를 고릅니다. 같은 데이터라도 찾기가 많으면 해시, 최솟값 꺼내기가 많으면 힙입니다.**

자료구조를 잘못 고르면 풀이 방법이 맞아도 느려집니다. 리스트에서 `x in list` 는 원소를 하나씩 보므로 O(n) 이고, 이것을 반복문 안에서 n 번 부르면 3절 표의 O(n^2) 이 됩니다. 같은 일을 `set` 으로 하면 한 번에 평균 O(1) 이라 전체가 O(n) 으로 내려갑니다.

| 자료구조 | Python | 빠른 연산 | 느린 연산 |
|---|---|---|---|
| 배열 | `list` | 인덱스로 읽기 O(1), 끝에 넣기 O(1) | 값으로 찾기 O(n), 앞에 넣고 빼기 O(n) |
| 해시 | `dict`, `set`, `Counter` | 키로 찾기, 넣기, 지우기 평균 O(1) | 순서가 필요한 일(정렬된 순회) |
| 힙 | `heapq` | 최솟값 보기 O(1), 넣기와 꺼내기 O(log n) | 임의의 값 찾기 O(n) |
| 덱 | `collections.deque` | 양 끝에 넣고 빼기 O(1) | 가운데 인덱스로 읽기 O(n) |
| 그래프 | `defaultdict(list)` 인접 리스트 | 한 노드의 이웃 나열 | 두 노드가 이어졌는지 확인(이웃 수만큼) |

인접 리스트는 노드마다 이웃 목록을 들고 있는 그래프 표현이고, 지문이 `(A, B)` 쌍으로 관계를 주면 이것을 먼저 만듭니다. 이 글의 예제는 날짜 순서대로 들어온 숫자를 인덱스로 읽기만 하므로 배열(`list`) 하나면 되고, 따로 만들 자료구조가 없습니다.

자료구조마다 직접 시간을 재 본 비교는 [복잡도와 배열 순회](post.html?id=algorithm-complexity-array) 편과 [해시와 정렬](post.html?id=algorithm-hash-sort) 편에 있고, 힙은 [트리와 힙](post.html?id=algorithm-tree-heap) 편에 있습니다.

## 5. 접근 방법: 지문 신호와 풀이

**지문에 나오는 말이 접근 방법을 알려 줍니다. 「연속한 구간」과 「양수만」이 같이 보이면 슬라이딩 윈도우, 「정렬된 배열에서 두 수」면 투 포인터입니다.**

접근 방법을 늦게 고르면 반복문 두 개를 먼저 쓰고 나서 줄이는 방법을 찾게 됩니다. 신호를 먼저 보면 2절에서 적은 조건(연속, 양수)이 곧바로 후보를 정해 줍니다. 슬라이딩 윈도우는 연속한 구간의 양 끝을 오른쪽으로만 움직이며 구간 합 같은 값을 고쳐 가는 방법이고, 투 포인터는 배열의 두 위치를 조건에 따라 좁혀 가는 방법입니다.

| 지문 신호 | 자료구조 | 접근 방법 | 자세한 글 |
|---|---|---|---|
| 연속한 구간, 길이 k 인 구간, 값이 모두 양수 | 배열 | 슬라이딩 윈도우 | [복잡도와 배열 순회](post.html?id=algorithm-complexity-array) |
| 정렬된 배열에서 합이 x 인 두 수 | 배열 | 투 포인터 | [복잡도와 배열 순회](post.html?id=algorithm-complexity-array) |
| 정렬된 배열에서 개수, 조건을 만족하는 최솟값 | 배열 | 이진 탐색 | [이분 탐색과 스택](post.html?id=algorithm-binary-search-stack) |
| 등장 횟수, 이미 본 값인가, 짝 찾기 | 해시 | 한 번 순회 + 해시 | [해시와 정렬](post.html?id=algorithm-hash-sort) |
| 매 순간 가장 작은 것, 상위 K개 | 힙 | 그리디 + 힙 | [트리와 힙](post.html?id=algorithm-tree-heap) |
| 최소 이동 횟수, 가중치 없는 최단 거리 | 덱, 그래프 | BFS | [그래프 탐색](post.html?id=algorithm-graph-search) |
| 연결된 덩어리 수, 모든 경로 | 그래프 | DFS | [그래프 탐색](post.html?id=algorithm-graph-search) |
| 최대 이익, 경우의 수, 앞의 답으로 다음 답 | 배열(DP 표) | DP | [DP와 그리디](post.html?id=algorithm-dp-greedy) |
| 끝나는 시각이 이른 것부터, 가장 큰 것부터 고르면 최적 | 배열(정렬) | 그리디 | [DP와 그리디](post.html?id=algorithm-dp-greedy) |

이 글의 예제는 첫째 줄에 들어맞습니다. 클릭 수가 모두 1 이상이라 오른쪽 끝을 늘리면 합이 커지고 왼쪽 끝을 줄이면 합이 작아지는데, 이 한 방향 성질이 있어야 「합이 S 이상이면 왼쪽을 줄여 본다」는 규칙이 답을 놓치지 않습니다. 값에 음수가 섞이면 왼쪽을 줄였을 때 합이 커질 수도 있어서 이 규칙이 깨지고, 그때는 누적합과 덱을 쓰는 다른 방법이 필요합니다.

신호표는 후보를 좁히는 데까지만 씁니다. 한 지문에 신호가 둘 이상 보이면 3절의 목표 복잡도에 맞는 쪽을 고르고, 도구별 표준 라이브러리 사용법은 [코딩테스트 핵심 도구](post.html?id=algorithm-coding-test-toolkit) 편에 있습니다.

## 6. 구현과 확인: 예제, 경계 입력, 복잡도

**코드를 쓴 뒤 세 가지를 돌립니다. 손으로 푼 예제, 2절에서 적어 둔 경계 입력, 그리고 느리지만 확실한 풀이와의 비교입니다.**

예제 하나만 돌리고 제출하면 답이 없는 입력이나 하루로 끝나는 입력에서 틀린 것을 모릅니다. 느리지만 확실한 풀이(브루트 포스, 모든 경우를 다 보는 풀이)를 같이 짜 두면 작은 무작위 입력 수백 개에서 두 답이 같은지 기계로 볼 수 있어서, 경계 입력을 사람이 다 떠올리지 못해도 틀린 자리를 찾습니다.

```python
# 하는 일: 8일치 가상 클릭 수에서 합이 7 이상인 가장 짧은 연속 기간을 슬라이딩 윈도우로 구하고, 경계 입력과 무작위 입력 500개로 브루트 포스와 비교한다.
import random

# 1단계: 느리지만 확실한 풀이를 만든다
# 모든 시작 날에서 오른쪽으로 더해 가며 처음 S 이상이 되는 길이를 본다. O(n^2) 이다.
def brute(clicks, s):
    best = 0
    for i in range(len(clicks)):
        total = 0
        for j in range(i, len(clicks)):
            total += clicks[j]
            if total >= s:
                if best == 0 or j - i + 1 < best:
                    best = j - i + 1
                break
    return best

# 2단계: 슬라이딩 윈도우 풀이를 만든다
# 오른쪽 끝을 하나씩 늘리고, 합이 S 이상인 동안 길이를 기록하며 왼쪽 끝을 줄인다. trace 가 참이면 찾은 기간을 찍는다.
def shortest(clicks, s, trace=False):
    best = 0
    total = 0
    left = 0
    for right in range(len(clicks)):
        total += clicks[right]
        while total >= s:
            length = right - left + 1
            if trace:
                print(f'{left+1}~{right+1}일  합 {total:2d}  길이 {length}')
            if best == 0 or length < best:
                best = length
            total -= clicks[left]
            left += 1
    return best

# 3단계: 손으로 푼 예제를 돌린다
clicks = [2, 3, 1, 2, 4, 3, 1, 5]   # 가상 데이터
print(f'답 {shortest(clicks, 7, trace=True)}')

# 4단계: 경계 입력을 돌린다
# 빈 배열, 합이 S 에 못 미치는 입력, 하루로 끝나는 입력 둘이다.
cases = [([], 7), ([1, 1, 1], 10), ([7], 7), ([2, 10, 1], 7)]
for arr, s in cases:
    print(f'{str(arr):12} S={s:2d}  윈도우 {shortest(arr, s)}  브루트 {brute(arr, s)}')

# 5단계: 무작위 입력 500개로 두 풀이를 비교한다
# 길이 0~12, 값 1~9 인 배열을 만든다. 시드를 고정해 돌릴 때마다 같은 입력이 나온다.
random.seed(0)
diff = 0
for _ in range(500):
    arr = [random.randint(1, 9) for _ in range(random.randint(0, 12))]
    s = random.randint(1, 40)
    if shortest(arr, s) != brute(arr, s):
        diff += 1
print(f'무작위 500개 중 다른 답 {diff}개')

# 출력:
# 3단계 뜻: 합이 7 이상인 기간을 6번 찾았고, 가장 짧은 것은 5~6일의 2일로 손 풀이와 같다.
# 1~4일  합  8  길이 4
# 2~5일  합 10  길이 4
# 3~5일  합  7  길이 3
# 4~6일  합  9  길이 3
# 5~6일  합  7  길이 2
# 6~8일  합  9  길이 3
# 답 2
# 4단계 뜻: 경계 입력 4개에서 두 풀이의 답이 모두 같다.
# []           S= 7  윈도우 0  브루트 0
# [1, 1, 1]    S=10  윈도우 0  브루트 0
# [7]          S= 7  윈도우 1  브루트 1
# [2, 10, 1]   S= 7  윈도우 1  브루트 1
# 5단계 뜻: 무작위 입력 500개에서도 두 풀이의 답이 하나도 다르지 않다.
# 무작위 500개 중 다른 답 0개
```

마지막으로 복잡도를 한 줄로 말합니다. 오른쪽 끝 `right` 는 n 번 움직이고 왼쪽 끝 `left` 도 전체를 통틀어 n 번을 넘지 못하므로, 안쪽에 `while` 이 있어도 시간은 O(n) 이고, 입력 말고는 변수 몇 개만 쓰므로 추가 공간은 O(1) 입니다. 면접에서는 「시간 O(n), 공간 O(1), 값이 양수라는 조건 덕분에 왼쪽 끝을 되돌릴 일이 없습니다」까지 말하면 Evaluate 단계가 끝납니다.

## 7. 입력 방식 두 가지

**프로그래머스와 LeetCode 는 함수 하나를 채우고, 백준은 표준 입력을 직접 읽고 답을 출력합니다. 풀이 함수는 같게 두고 바깥만 바꿉니다.**

입력 방식을 헷갈리면 맞는 풀이도 0점이 됩니다. 함수형 사이트에서 `print` 만 하고 `return` 을 빼면 채점기는 `None` 을 받고, 백준에서 `input()` 을 10만 번 부르면 읽기만으로 느려질 수 있습니다. 그래서 백준에서는 `sys.stdin.readline` 을 `input` 대신 씁니다. 이 함수는 한 줄을 끝의 줄바꿈까지 읽어 돌려주는 표준 라이브러리 함수입니다.

```python
# 하는 일: 6절의 풀이를 함수형(프로그래머스, LeetCode)과 표준 입력형(백준) 두 템플릿으로 감싸 같은 답이 나오는지 본다.
import io
import sys

# 1단계: 함수형 템플릿을 만든다
# 프로그래머스는 solution 함수를, LeetCode 는 Solution 클래스의 메서드를 채운다. 답은 return 으로 돌려준다.
def solution(clicks, s):
    best, total, left = 0, 0, 0
    for right in range(len(clicks)):
        total += clicks[right]
        while total >= s:
            if best == 0 or right - left + 1 < best:
                best = right - left + 1
            total -= clicks[left]
            left += 1
    return best

class Solution:
    def minDays(self, clicks, s):
        return solution(clicks, s)

print(f'함수형      {solution([2, 3, 1, 2, 4, 3, 1, 5], 7)}')
print(f'클래스형    {Solution().minDays([2, 3, 1, 2, 4, 3, 1, 5], 7)}')

# 2단계: 표준 입력형 템플릿을 만든다
# 첫 줄에 n 과 S, 둘째 줄에 클릭 수가 온다고 가정한다. 백준에 낼 때는 io.StringIO 줄을 지운다.
sys.stdin = io.StringIO('8 7\n2 3 1 2 4 3 1 5\n')
input = sys.stdin.readline

n, s = map(int, input().split())
clicks = list(map(int, input().split()))
print(f'표준 입력형 {solution(clicks, s)}')

# 출력:
# 1단계 뜻: 함수형과 클래스형 모두 2 를 돌려준다.
# 함수형      2
# 클래스형    2
# 2단계 뜻: 표준 입력으로 읽어도 같은 2 가 나온다.
# 표준 입력형 2
```

세 줄 모두 2 가 찍히면 풀이 함수는 그대로이고 바깥만 바뀐 것입니다. 시험 전에 두 템플릿을 손에 익혀 두면 문제를 받았을 때 입력 처리에 시간을 쓰지 않고, 그 시간을 2~3절의 이해와 제약 보기에 쓸 수 있습니다.

## 8. 30분 라이브 코딩

**라이브 코딩에서는 표준 라이브러리를 쓰고, 편집기에 무엇이 미리 들어 있는지와 무엇을 써도 되는지를 시작할 때 면접관에게 묻습니다.**

라이브 코딩은 면접관이 보는 앞에서 정해진 시간 안에 문제를 푸는 형식이고, 회사마다 쓰는 편집기와 규칙이 다릅니다. LeetCode 형식의 편집기는 트리나 연결 리스트 문제에서 `TreeNode`, `ListNode` 정의를 주석으로 미리 넣어 두고 채점 환경이 그 클래스를 제공하므로, 대개 직접 만들 일이 없습니다. 반대로 아무것도 없는 빈 편집기에서는 아래처럼 세 줄짜리 노드 클래스를 직접 써야 할 수 있습니다.

```python
# 하는 일: 빈 편집기에서 이진 트리 노드를 세 줄로 정의하고, 노드 셋으로 트리를 만들어 값의 합을 찍는다.
# 1단계: 노드 클래스를 정의한다
# LeetCode 의 TreeNode 와 같은 필드 이름(val, left, right)을 쓴다.
class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val, self.left, self.right = val, left, right

# 2단계: 노드 셋으로 트리를 만들고 합을 찍는다
def total(node):
    return 0 if node is None else node.val + total(node.left) + total(node.right)

root = TreeNode(1, TreeNode(2), TreeNode(3))
print(f'트리 값의 합 {total(root)}')

# 출력:
# 2단계 뜻: 노드 셋의 값 1, 2, 3 을 더해 6 이다.
# 트리 값의 합 6
```

힙이나 균형 이진 탐색 트리를 직접 구현하는 경우는 드문 편이고, 대개 `heapq`, `collections.deque`, `Counter`, `bisect` 로 대신합니다. 쓸 수 있는 라이브러리와 언어도 회사마다 다르므로, 시작할 때 「표준 라이브러리를 써도 됩니까?」, 「입력을 함수 인자로 받습니까?」를 먼저 묻는 것이 가장 확실합니다.

시간 배분은 정해진 규칙이 없고, 아래는 30분 한 문제를 기준으로 한 이 글의 제안입니다. 구현에 가장 많은 시간을 주되, 이해와 확인을 합친 시간이 구현의 절반을 넘게 잡았습니다.

| 단계 | 제안 시간 | 이 시간에 말로 하는 것 |
|---|---|---|
| 이해, 제약 보기 | 5분 | 입력 범위, 빈 입력, 중복 질문과 손 풀이 |
| 자료구조, 접근 방법 | 5분 | 「n 이 10만이라 O(n log n) 이하가 필요합니다」와 의사코드 |
| 구현 | 12분 | 지금 쓰는 줄이 계획의 어느 부분인지 |
| 확인 | 5분 | 예제와 경계 입력을 한 줄씩 따라가기 |
| 복잡도와 개선 | 3분 | 시간과 공간 복잡도, 더 빠른 방법이 있는지 |

구현이 12분을 넘기면 남은 시간에 확인을 줄이지 말고 면접관에게 지금 막힌 자리를 말합니다. 말로 계획을 공유해 두면 코드가 끝나지 않아도 1~4단계는 평가받을 여지가 남기 때문입니다.

## 한눈 정리

| 단계 | 확인할 것 | 이 글의 예제에서 |
|---|---|---|
| 1. 이해 | 입력 범위, 빈 입력, 중복, 손 풀이 | 값이 모두 1 이상, 답이 없으면 0, 손 풀이 답 2 |
| 2. 제약 보기 | n 으로 목표 복잡도 | n 10만 → O(n log n) 이하, 모든 구간은 50억 개 넘음 |
| 3. 자료구조 | 자주 하는 연산 | 인덱스로 읽기만 하므로 배열 |
| 4. 접근 방법 | 지문 신호 | 「연속한 구간」 + 「양수」 → 슬라이딩 윈도우 |
| 5. 구현과 확인 | 예제, 경계 입력, 브루트 포스 비교, 복잡도 | 답 2, 경계 입력 4개 일치, 무작위 500개 중 다른 답 0개, 시간 O(n) 공간 O(1) |

## 헷갈리기 쉬운 점

- **1억 회는 보장이 아니라 어림 기준입니다.** 채점 서버, 언어, 연산 종류에 따라 몇 배씩 달라지고 Python 은 더 느리므로, 계산 결과가 1초 근처면 한 단계 빠른 풀이를 찾습니다.
- **안쪽에 while 이 있다고 O(n^2) 은 아닙니다.** 슬라이딩 윈도우의 왼쪽 끝은 전체를 통틀어 n 번까지만 움직이므로 두 반복문을 합쳐 O(n) 입니다. 반복문 개수가 아니라 각 변수가 몇 번 움직이는지를 셉니다.
- **슬라이딩 윈도우는 값이 양수일 때의 방법입니다.** 음수가 섞이면 왼쪽 끝을 줄였을 때 합이 커질 수 있어서 「합이 S 이상이면 줄인다」는 규칙이 답을 놓칩니다.
- **자료구조와 접근 방법은 순서가 바뀌기도 합니다.** BFS 를 고르면 덱이 따라오고, 그리디는 힙과 함께 쓰는 일이 많습니다. 두 단계는 함께 정해지는 경우가 많고, 어느 순서로 정하든 둘 다 3절의 목표 복잡도에 맞아야 합니다.
- **함수형 사이트는 return, 백준은 print 입니다.** 풀이 함수는 같게 두고 바깥 템플릿만 바꿉니다.

- 요구가 하나씩 늘어나는 로그 집계 문제와 LRU 캐시 같은 작은 클래스를 직접 짜 보는 글은 [실무형 라이브 코딩](post.html?id=algorithm-practical-live-coding) 편입니다.
- 이 다섯 단계를 면접관에게 소리 내어 말하는 순서와 영어 표현은 [말하며 풀기](post.html?id=algorithm-think-aloud) 편에 있습니다.
- 이 글의 신호표에 없는 연결 리스트, 문자열, Union-Find, Trie, 구간 다섯 가지는 [시리즈에서 빠진 다섯 가지](post.html?id=algorithm-more-structures) 편에 있습니다.
