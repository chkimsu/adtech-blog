지훈 씨는 모델 팀으로 옮긴 지 셋째 주입니다. 처음 맡은 일은 피처 하나를 더하는 것이었습니다. 광고별 최근 7일 클릭률입니다. 노트북에서 피처를 만들고 모델에 넣어 돌려 보니 잘 됐습니다. 예측값도 그럴듯했습니다.

그래서 선배에게 물었습니다. 「이제 이걸 서버에 올리려면 어떻게 하나요?」 선배는 「커밋해서 올리면 CI 가 검문 세 곳을 통과시킨 뒤 이미지를 만들어요. 그 이미지가 서버 12대에 올라가요」라고 했습니다. 지훈 씨는 검문이 무엇이고 이미지가 무엇인지 몰랐습니다.

더 마음에 걸리는 것이 있었습니다. 노트북에서 돌아간 코드가 서버에서도 똑같이 돌아간다고 누가 보장하는가였습니다. 서버는 12대이고 노트북은 한 대입니다. 서버마다 조금씩 다르면 같은 요청에 다른 예측값이 나옵니다.

**내 노트북에서 돌아가는 코드가 서버에서도 똑같이 돌아간다고 누가 보장하나요?**

그 보장을 만드는 것이 컨테이너 이미지(container image)와 CI 입니다. 이미지는 코드와 그 아래 깔린 것을 한 장으로 굳힌 것이고, CI 는 커밋마다 그 이미지를 만들어 검문 셋을 통과시키는 자동 절차입니다. 이 글은 커밋 하나가 검문 셋을 지나 이미지 저장소에 오르기까지를 카드 그림으로 봅니다. 이것을 알면 「내 노트북에서는 되는데」라는 말이 왜 나오고 어디를 봐야 하는지가 보입니다.

> **한 줄 요약:** 이미지는 기본 리눅스부터 코드까지 층을 쌓아 굳힌 한 장이고, 서버 12대가 같은 장을 씁니다. 커밋 하나는 CI 에서 6분 20초 동안 이미지가 되고 검문 셋을 지납니다. 유닛 테스트 214개, 계약 테스트 스키마 12개와 부하 1,000건, 이미지 검사입니다. 하나라도 걸리면 이미지는 저장소에 오르지 않습니다.

> **골라 읽는 법** — 절이 열 개인 글입니다. 절마다 카드 한 장이나 표 하나가 들어 있어 그것만 보고 넘어가도 됩니다.
>
> - 노트북과 서버가 다른 값을 내는 이유 → 1절
> - 이미지 한 장에 무엇이 들었나 → 2절
> - 커밋이 이미지 저장소에 오르기까지 → 3절
> - 검문 셋 (유닛, 계약, 이미지) → 4~6절
> - 담장 안과 열린 RTB 의 차이 → 7절

이 글의 이름, 파일 크기, 시간은 전부 설명을 위한 가상 값입니다. 요청 원문의 예측값 0.0412 와 모델 서버 12대, 모델 호출 예산 8ms 는 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편과 같은 값입니다. 피처 이름 `ad_ctr_7d` 는 [CTR 피처 엔지니어링](post.html?id=ctr-feature-engineering) 편의 표에 있는 것입니다. 카드 속 색은 넷입니다. 파랑은 놓여 있는 것(파일, 이미지, 저장소), 벽돌색은 지금 오는 것(커밋, 요청)입니다. 먹색은 모델과 서버이고 회색은 만드는 작업(빌드, 테스트, 검사)입니다. 점선 상자는 적어 둔 것(설정, 통과 조건)입니다.

## 1. 내 노트북에서는 되는데

**같은 코드와 같은 모델 파일인데 노트북과 서버가 다른 예측값을 냅니다. 다른 것은 코드 아래에 깔린 라이브러리 판 하나입니다.**

쉽게 말하면 코드는 혼자 돌지 않습니다. 파이썬이 있어야 하고, 수를 곱하고 더하는 라이브러리가 있어야 하고, 그 아래 리눅스가 있어야 합니다. 코드가 같아도 그 아래 층 하나가 다르면 값이 달라질 수 있습니다.

지훈 씨가 겪은 일이 그것이었습니다. 새 피처를 넣기 전에 먼저 지금 모델 v418 로 요청 하나를 노트북에서 돌려 봤습니다. 회원 u-3f9c 에게 광고 9931 을 보였을 때의 클릭 확률입니다. 노트북은 0.0412 라고 했습니다. 같은 요청을 서버에 보내니 0.0397 이 왔습니다. 3.6% 낮은 값입니다. 코드는 같은 커밋이고 모델 파일도 같은 38MB 였습니다.

## 2. 이미지 한 장에 든 것

**이미지는 기본 리눅스, 파이썬, 라이브러리, 코드를 아래부터 차례로 쌓은 한 장입니다. 코드는 맨 위 한 층이고, 모델 파일은 이미지에 넣지 않습니다.**

쉽게 말하면 이미지는 「이 코드가 돌아가는 데 필요한 모든 것」을 층층이 쌓아 굳힌 파일입니다. 서버 12대가 같은 이미지를 받으면 12대의 층이 모두 같습니다. 1절의 라이브러리 판 차이는 여기서 사라집니다.

층은 아래부터 쌓입니다. 이 팀의 추론 이미지는 네 층입니다. 기본 리눅스, 파이썬 3.11, 추론 런타임, 그리고 코드입니다. 학습 이미지는 다섯 층입니다. 학습에는 GPU 라이브러리와 학습 프레임워크가 더 필요하기 때문입니다. 층마다 크기가 다릅니다. 가정은 층별 크기가 아래 표와 같다는 것이고, 이미지 크기는 층을 더한 값입니다.

| 층 | 학습 이미지 | 추론 이미지 |
|---|---|---|
| 코드 (커밋 a3f9c21) | 12MB | 12MB |
| 학습 프레임워크 | 1.2GB | 없음 |
| GPU 라이브러리 | 3.1GB | 없음 |
| 추론 런타임 | 없음 | 0.8GB |
| 파이썬 3.11 | 0.2GB | 0.2GB |
| 기본 리눅스 | 0.1GB | 0.1GB |
| 합계 | 4.6GB | 1.1GB |

표에서 두 가지가 보입니다. 첫째, 코드는 12MB 로 가장 작은 층입니다. 이미지 크기는 코드가 아니라 라이브러리가 정합니다. 학습 이미지와 추론 이미지의 차이 3.5GB 는 전부 라이브러리 층입니다. 둘째, 코드를 고치면 맨 위 한 층만 다시 만듭니다. 아래 네 층은 그대로 다시 씁니다. 그래서 커밋마다 4.6GB 를 새로 만드는 것이 아니라 12MB 층 하나만 새로 만듭니다.

이미지를 적는 파일이 Dockerfile 입니다. 추론 이미지의 것을 줄여 옮기면 이렇습니다. 위에서 아래로 읽으면 층이 쌓이는 순서 그대로입니다.

```dockerfile
FROM python:3.11-slim                      # 기본 리눅스 + 파이썬 3.11 (0.3GB)
RUN pip install onnxruntime==1.18.0        # 추론 런타임 (0.8GB). 판을 박아 둡니다
COPY src/ /app/src/                        # 코드 (12MB). 커밋마다 이 층만 새로
WORKDIR /app
CMD ["python", "-m", "src.server"]         # 서버를 켜는 명령
```

둘째 줄이 1절의 답입니다. 런타임 판을 `1.18.0` 으로 박아 두면 노트북에서 이 이미지를 켜도 서버에서 켜도 같은 판입니다. 모델 파일 38MB 는 이 파일에 없습니다. 모델은 매일 새벽 새로 만들어지는데 이미지는 코드가 바뀔 때만 만들기 때문입니다. 모델은 서버가 뜰 때 저장소에서 내려받습니다. 그 순서는 [추론 서버](post.html?id=inference-server) 편에 있습니다.

## 3. 커밋에서 이미지 저장소까지

**커밋을 올리면 CI 가 이미지를 만들고 검문 셋을 통과시킨 뒤 이미지 저장소에 올립니다. 6분 20초가 걸리고, 이미지 이름에 커밋 해시가 붙습니다.**

쉽게 말하면 CI 는 「커밋이 올라오면 정해진 순서로 만들고 검사하는 기계」입니다. 사람이 노트북에서 이미지를 만들어 올리면 1절의 문제가 다시 생깁니다. 그래서 만드는 자리도 한 곳으로 정합니다.

지훈 씨가 커밋 `a3f9c21` 을 올리자 CI 가 돌기 시작했습니다. 순서는 넷입니다. 이미지 만들기, 유닛 테스트, 계약 테스트, 이미지 검사입니다. 가정은 단계마다 아래 표의 시간이 든다는 것이고, 끝나는 시각은 앞 단계까지 더한 값입니다.

| 단계 | 무엇을 하나 | 걸린 시간 | 끝나는 시각 |
|---|---|---|---|
| 이미지 만들기 | 코드 층을 새로 쌓습니다 | 2분 10초 | 2:10 |
| 검문 첫째, 유닛 테스트 | 함수 214개가 맞나 | 48초 | 2:58 |
| 검문 둘째, 계약 테스트 | 요청과 응답의 모양과 속도 | 2분 30초 | 5:28 |
| 검문 셋째, 이미지 검사 | 위험한 것이 없나, 크기 | 52초 | 6:20 |

6분 20초 뒤 이미지 저장소에 한 장이 올라갔습니다. 이름은 `pctr-serve:2026.09.17-a3f9c21` 입니다. 날짜와 커밋 해시가 이름에 들어 있습니다. 그래서 서버에 오른 이미지가 어느 코드로 만든 것인지 이름만 보고 압니다. 사고가 났을 때 「지금 서버에 있는 코드가 무엇인가」를 찾는 데 1초면 됩니다.

이 순서를 적어 둔 파일이 CI 설정입니다. 저장소에 놓여 있고 커밋이 올라올 때마다 읽힙니다. 줄여 옮기면 이렇습니다.

```yaml
on:
  push:
    branches: [main]
jobs:
  build-and-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t pctr-serve:${DATE}-${SHA} .     # 이미지 만들기
      - run: python -m unittest discover tests/unit          # 검문 첫째
      - run: python -m unittest discover tests/contract      # 검문 둘째
      - run: image-scan pctr-serve:${DATE}-${SHA}            # 검문 셋째
      - run: docker push registry.example.com/pctr-serve:${DATE}-${SHA}
```

마지막 줄이 저장소에 올리는 명령입니다. 그 앞 세 줄 중 하나라도 실패하면 마지막 줄은 실행되지 않습니다. 검문에 걸린 커밋은 서버 근처에도 못 갑니다. 세 검문이 각각 무엇을 보는지가 다음 세 절입니다.

## 4. 검문 첫째, 유닛 테스트 214개

**유닛 테스트는 함수 하나에 입력 하나를 넣고 답이 정해진 값과 같은지 봅니다. 214개가 48초에 끝나고, 하나라도 다르면 이미지는 여기서 멈춥니다.**

쉽게 말하면 「이 함수에 이것을 넣으면 저것이 나와야 한다」를 적어 둔 것입니다. 사람이 매번 확인하는 대신 기계가 커밋마다 확인합니다.

지훈 씨의 피처 함수를 예로 보겠습니다. 광고별 최근 7일 클릭률입니다. 7일 창 안의 로그만 세고, 창 밖의 로그는 뺍니다. 노출이 없으면 나눗셈을 못 하니 0 을 돌려줍니다. 이 세 가지가 테스트 셋이 됩니다. 아래는 표준 라이브러리만으로 그 테스트를 돌린 것입니다.

```python
# 광고별 최근 7일 클릭률 피처와 그 유닛 테스트 셋.
# CI 는 이런 테스트 214개를 커밋마다 돌린다. 하나라도 틀리면 이미지가 만들어지지 않는다.
# 로그 값은 전부 가상이다.

import unittest

def ad_ctr_7d(logs, ad_id, today):
    """today 를 뺀 앞 7일(D-7 ~ D-1) 로그로 광고 하나의 클릭률을 낸다. 노출이 없으면 0."""
    imp = clk = 0
    for day, aid, is_click in logs:
        if aid != ad_id or not (today - 7 <= day <= today - 1):
            continue                       # 다른 광고이거나 창 밖이면 세지 않는다
        imp += 1
        clk += is_click
    return clk / imp if imp else 0.0

LOGS = [(day, 9931, 0) for day in range(1, 11)]   # 광고 9931: 1~10일 노출 10건
LOGS += [(3, 9931, 1), (9, 9931, 1)]             # 그중 3일과 9일에 클릭 (노출 12건, 클릭 2)
LOGS += [(5, 7720, 1)]                            # 다른 광고 7720 의 클릭 하나

class TestAdCtr7d(unittest.TestCase):
    def test_window_only(self):
        # today=10 이면 창은 3~9일. 그 안의 9931 노출 9건, 클릭 2건 → 2/9
        self.assertAlmostEqual(ad_ctr_7d(LOGS, 9931, today=10), 2 / 9)
    def test_other_ad_excluded(self):
        # 7720 의 클릭은 9931 의 분자에 들어가면 안 된다
        self.assertAlmostEqual(ad_ctr_7d(LOGS, 7720, today=10), 1.0)
    def test_no_impression(self):
        # 창 안에 노출이 없으면 나누지 않고 0
        self.assertEqual(ad_ctr_7d(LOGS, 9931, today=30), 0.0)

unittest.main(argv=["x"], verbosity=2, exit=False)

# 출력:
# test_no_impression (__main__.TestAdCtr7d) ... ok
# test_other_ad_excluded (__main__.TestAdCtr7d) ... ok
# test_window_only (__main__.TestAdCtr7d) ... ok
#
# ----------------------------------------------------------------------
# Ran 3 tests in 0.000s
#
# OK
```

첫 테스트가 이 피처의 핵심입니다. 오늘이 10일이면 창은 3일부터 9일까지입니다. 10일 노출은 오늘 것이라 빼고, 1일과 2일 노출은 창 밖이라 뺍니다. 그러면 노출 9건에 클릭 2건이라 2/9 입니다. 창을 잘못 잡아 10일을 넣으면 값이 달라지고 테스트가 걸립니다. 창을 잘못 잡은 피처가 무슨 일을 내는지는 [CTR 피처 엔지니어링](post.html?id=ctr-feature-engineering) 편 6절에 있습니다. 오프라인 AUC 0.89 가 실서빙에서 0.78 이 됩니다.

지훈 씨의 커밋은 214개 중 214개를 통과했습니다. 48초였습니다. 그런데 유닛 테스트는 함수 하나씩만 봅니다. 서버 전체가 요청을 받아 응답을 돌려주는 모양은 보지 않습니다. 그것이 둘째 검문입니다.

## 5. 검문 둘째, 계약 테스트

**계약 테스트는 서버를 실제로 켜고 요청을 보내 응답의 모양과 속도가 약속대로인지 봅니다. 필드 12개가 맞아야 하고, 1,000건 부하에서 8ms 초과율이 6% 이하여야 합니다.**

쉽게 말하면 API 서버와 모델 서버 사이의 약속을 검사하는 것입니다. 「이 필드를 보내면 이 필드가 돌아온다, 그리고 8ms 안에 온다」가 약속이고, 그 약속을 [API 연동 실무](post.html?id=api-kinds-and-contracts) 편에서는 계약이라고 불렀습니다.

계약 테스트는 두 부분입니다. 첫째는 모양입니다. 새 이미지로 서버를 켜고 요청 하나를 보내 응답의 필드 12개가 이름과 자료형까지 맞는지 봅니다. 지훈 씨가 피처를 하나 더했어도 응답 모양은 그대로여야 합니다. API 서버는 응답에 `pctr` 이 있다고 믿고 순위를 매기기 때문입니다. 둘째는 속도입니다. 요청 1,000건을 보내 8ms 를 넘긴 비율을 셉니다. 새 피처는 조회를 하나 더 하니 요청마다 시간이 조금 더 듭니다. 그 조금이 얼마인지가 문제입니다.

아래는 그 부하 시험을 흉내 낸 것입니다. 추론 시간의 분포는 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편과 같은 값을 썼습니다. 중앙값 3.0ms 에 흩어진 정도 0.55 입니다. 새 피처의 조회가 요청마다 더하는 시간을 바꿔 가며 초과율을 봅니다.

```python
# 계약 테스트의 부하 부분 — 요청 1,000건에서 8ms 초과율을 센다.
# 추론 시간은 로그정규(중앙값 3.0ms, 흩어짐 0.55)로 잡았고, 새 피처의 조회가
# 요청마다 더하는 시간을 0 부터 1.0ms 까지 바꿔 본다. 통과 기준은 6% 이하. 전부 가상 값이다.

import random, math

BUDGET_MS = 8.0
LIMIT_PCT = 6.0
N = 1000

def exceed_rate(extra_ms, seed=20260917):
    """요청 N 건 중 예산 8ms 를 넘긴 비율(%). extra_ms 는 새 피처가 더하는 시간."""
    rnd = random.Random(seed)
    mu = math.log(3.0)
    over = 0
    for _ in range(N):
        t = rnd.lognormvariate(mu, 0.55) + extra_ms
        over += t > BUDGET_MS
    return 100 * over / N

print(f"{'새 피처가 더하는 시간':>14}  {'8ms 초과율':>8}  판정 (기준 {LIMIT_PCT}% 이하)")
for extra in (0.0, 0.2, 0.5, 1.0):
    rate = exceed_rate(extra)
    verdict = "통과" if rate <= LIMIT_PCT else "탈락"
    print(f"{extra:>12.1f}ms  {rate:>7.1f}%  {verdict}")

# 출력:
#   새 피처가 더하는 시간   8ms 초과율  판정 (기준 6.0% 이하)
#          0.0ms      3.2%  통과
#          0.2ms      3.6%  통과
#          0.5ms      4.8%  통과
#          1.0ms      6.3%  탈락
```

지훈 씨의 피처는 조회 한 번에 0.5ms 를 더했습니다. 초과율은 3.2% 에서 4.8% 로 올랐고 기준 6% 아래라 통과했습니다. 그런데 표의 마지막 줄을 보면 1.0ms 를 더했다면 6.3% 로 탈락입니다. 조회를 두 번 하는 피처였다면 이미지는 여기서 멈췄을 것입니다.

이 검문이 잡는 것은 「코드는 맞는데 서비스가 느려지는 커밋」입니다. 유닛 테스트 214개가 전부 통과해도 여기서 걸립니다. 실제 서버에서 12대가 요청을 나눠 받을 때 초과율이 어떻게 달라지는지는 서빙 지연 편의 5절이 다룹니다. 여기서는 서버 한 대에 1,000건을 보낸 값만 봅니다.

여기서 나오는 결정은 피처를 더할 때 조회 시간을 같이 재는 것입니다. 정확도를 0.001 올리는 피처가 초과율을 2% 올리면 그 피처는 서버에 오를 수 없습니다. 이미지가 서버에 오르기 전 마지막 검문이 다음 절입니다.

## 6. 검문 셋째, 이미지 검사

**이미지 검사는 코드가 아니라 이미지 자체를 봅니다. 층 안에 알려진 위험이 있는 라이브러리가 없나, 크기가 1.5GB 를 넘지 않나입니다.**

쉽게 말하면 앞 두 검문은 「이 코드가 일을 제대로 하나」를 보고, 이 검문은 「이 한 장을 서버 12대에 올려도 되나」를 봅니다. 코드가 맞아도 그 아래 층에 문제가 있을 수 있기 때문입니다.

보는 것은 둘입니다. 첫째는 취약점입니다. 이미지 안의 라이브러리 목록을 뽑아 알려진 문제가 있는 판이 섞여 있는지 봅니다. 심각한 것이 하나라도 있으면 탈락입니다. 둘째는 크기입니다. 이 팀의 상한은 1.5GB 입니다. 지훈 씨의 이미지는 1.1GB 라 통과했습니다. 크기를 보는 이유가 있습니다. 서버가 뜰 때 이미지를 내려받는데, 이미지가 커지면 그 시간이 늘어납니다. 배포 때 서버 2대씩 바꾸는 동안 나머지 10대가 요청을 다 받으니 그 시간이 길수록 위험합니다. 그 장면은 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편 8절에 있습니다.

검문 셋을 한 표로 모으면 이렇습니다.

| 검문 | 무엇을 보나 | 통과 조건 | 걸리는 시간 | 여기서 걸리는 커밋 |
|---|---|---|---|---|
| 첫째, 유닛 테스트 | 함수 하나하나의 답 | 214개 전부 통과 | 48초 | 계산이 틀린 코드 |
| 둘째, 계약 테스트 | 요청 응답의 모양과 속도 | 필드 12개 일치, 8ms 초과율 6% 이하 | 2분 30초 | 모양을 바꾸거나 느려진 코드 |
| 셋째, 이미지 검사 | 이미지 층의 위험과 크기 | 심각 취약점 0, 1.5GB 이하 | 52초 | 위험한 라이브러리, 커진 이미지 |

세 검문은 순서가 있습니다. 싼 것부터 돕니다. 유닛 테스트가 48초로 가장 싸고 계약 테스트가 서버를 켜야 해서 가장 비쌉니다. 유닛에서 걸린 커밋은 계약 테스트까지 가지 않으니 CI 시간이 줄어듭니다. 후보 광고를 싼 필터부터 거르는 것과 같은 순서입니다.

지훈 씨의 커밋은 셋을 다 지났습니다. 이미지 `pctr-serve:2026.09.17-a3f9c21` 이 저장소에 올라갔습니다. 서버 12대에 그것을 올리는 일은 다른 절차이고 [모델 배포와 롤백](post.html?id=model-deployment-rollback) 편이 다룹니다. 그 전에 이 검문이 두 무대에서 어떻게 다른지 봅니다.

## 7. 배포 창구가 다르면 검문도 다릅니다

**담장 안에서는 이미지 하나가 우리 게이트웨이 뒤의 서버 12대로 갑니다. 열린 RTB 에서는 입찰 서버가 거래소 여럿의 형식에 맞춰야 해서 계약 테스트가 거래소 수만큼 늘어납니다.**

쉽게 말하면 검문 셋은 두 무대에 다 있습니다. 다른 것은 둘째 검문의 「약속」을 누가 정하느냐입니다.

### 담장 안에서는 약속을 우리가 정합니다 [무대: 닫힌 생태계]

한 회사가 앱과 API 서버와 모델 서버를 다 가진 담장 안에서는, 요청과 응답의 모양을 우리 팀이 정합니다. 필드 12개가 무엇인지, 예산이 8ms 인지도 우리가 정한 값입니다. 계약 테스트는 한 벌이고 상대는 우리 API 팀뿐입니다. 이 블로그의 저자가 일하는 자리이고, 이 글의 카드들은 이 상태를 그린 것입니다. 배포 창구도 하나입니다. 이미지 하나가 게이트웨이 뒤의 서버 12대로 갑니다.

### 열린 RTB 에서는 약속을 거래소가 정합니다 [무대: 열린 RTB]

열린 RTB 의 입찰 서버는 남의 거래소가 보내는 요청에 답합니다. 요청 형식은 거래소가 정한 OpenRTB 판을 따르고, 응답 시간도 거래소가 정합니다. 보통 100ms 안쪽이고 거래소마다 조금씩 다릅니다. 거래소 다섯 곳에 연결돼 있으면 둘째 검문이 다섯 벌입니다. 거래소 한 곳이 형식을 바꾸면 그 벌만 걸립니다. 그래서 열린 RTB 의 CI 는 계약 테스트가 가장 크고 가장 자주 바뀝니다. 거래소가 무엇이고 요청이 어떻게 오는지는 [DSP, SSP, 광고 거래소](post.html?id=dsp-ssp-exchange) 편에 있습니다.

| 무엇 | 담장 안 | 열린 RTB |
|---|---|---|
| 요청 응답의 모양을 정하는 쪽 | 우리 팀 | 거래소마다 |
| 계약 테스트 벌 수 | 하나 | 연결된 거래소 수만큼 |
| 응답 예산을 정하는 쪽 | 우리 (모델 호출 8ms) | 거래소 (보통 100ms 안쪽) |
| 배포 창구 | 우리 게이트웨이 하나 | 거래소마다 연결 하나 |

## 한눈 정리

| 질문 | 한 줄 답 |
|---|---|
| 노트북과 서버가 왜 다른 값을 내나 | 코드 아래 층(라이브러리 판)이 다르기 때문입니다 |
| 이미지가 무엇인가 | 기본 리눅스부터 코드까지 층을 쌓아 굳힌 한 장입니다 |
| 이미지에 무엇이 안 들어가나 | 모델 파일입니다. 매일 바뀌니 서버가 뜰 때 내려받습니다 |
| 이미지 크기는 무엇이 정하나 | 라이브러리 층입니다. 코드는 12MB 로 가장 작습니다 |
| CI 가 무엇인가 | 커밋마다 이미지를 만들고 검문 셋을 통과시키는 기계입니다 |
| 검문 셋은 무엇인가 | 유닛 테스트, 계약 테스트, 이미지 검사입니다 |
| 하나라도 걸리면 | 이미지가 저장소에 오르지 않습니다. 6분 20초가 다 돌지도 않습니다 |
| 이미지 이름은 왜 그렇게 긴가 | 날짜와 커밋 해시가 들어 있어 어느 코드인지 이름으로 압니다 |

## 헷갈리기 쉬운 점

- **이미지는 코드가 아닙니다.** 코드는 이미지의 맨 위 한 층입니다. 나머지 층이 「내 노트북에서는 되는데」를 만듭니다.
- **모델 파일은 이미지에 없습니다.** 이미지는 코드가 바뀔 때, 모델은 매일 바뀝니다. 바뀌는 주기가 다른 것은 따로 둡니다.
- **유닛 테스트를 다 통과해도 서비스는 느려질 수 있습니다.** 그것을 잡는 것이 계약 테스트의 부하 부분입니다.
- **계약 테스트의 초과율은 서버 한 대의 값입니다.** 12대가 요청을 나눠 받는 실제 초과율과 다릅니다.
- **CI 가 통과했다고 서버에 올라간 것이 아닙니다.** 저장소에 오른 것까지입니다. 서버에 올리는 것은 배포이고 다음 편입니다.
