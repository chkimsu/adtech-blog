지난주에 지훈 씨는 새벽 알람을 받고 학습 파이프라인에서 멈춘 태스크(파이프라인을 이루는 작업 하나)부터 다시 돌렸습니다. 둘째 주 월요일 회의에서는 팀장이 날짜별 모델의 COPC 를 그린 대시보드 한 장을 띄웠습니다. COPC 는 실제 클릭 수를 모델이 노출마다 예측한 클릭 확률의 합으로 나눈 값입니다. COPC 가 1 이면 예측 확률의 합이 실제 클릭 수와 같다는 뜻이고 1 보다 크면 모델이 클릭을 실제보다 적게 예측했다는 뜻(과소예측)입니다. 그래프에서는 9월 3일 모델이 0.98 로 1 에 가장 가까웠습니다.

팀장이 물었습니다. 「9월 3일 모델이 제일 좋았는데, 그거 다시 만들어 볼 수 있어요? 무엇이 달랐는지 알고 싶어요.」 지훈 씨는 코드 저장소에서 9월 3일의 커밋을 찾아 그 코드로 학습을 다시 돌렸습니다. 커밋(commit)은 코드 저장소에 코드를 저장해 둔 한 시점입니다. 9월 3일 커밋을 받으면 그날의 코드를 그대로 얻을 수 있습니다. 그런데 다시 학습해 나온 모델의 COPC 는 0.98 이 아니었습니다.

코드는 같았는데 결과는 달랐습니다. 그날 학습이 어떤 데이터를 읽었는지, 설정값이 무엇이었는지, 학습 이미지가 어느 버전이었는지 적어 둔 곳이 없어서 지훈 씨는 무엇이 달라졌는지 알아낼 수 없었습니다. 학습 이미지는 학습이 도는 환경을 담아 버전 번호를 붙인 컨테이너 이미지입니다. 이미지 안에는 학습에 쓰는 라이브러리의 버전이 고정돼 있습니다.

**같은 코드로 다시 만들었는데 왜 다른 모델이 나올까요? 다시 만들려면 무엇을 적어 뒀어야 할까요?**

모델은 코드 하나로 정해지지 않고 코드, 데이터, 설정, 환경의 재료 네 가지가 학습을 한 번 거쳐 나온 결과입니다. 이 재료 네 가지를 모델 버전마다 적어 두는 표가 모델 레지스트리(model registry)입니다. 적어 둔 재료대로 다시 학습해 같은 값을 얻는 일을 재현(reproducibility)이라고 부릅니다. 버전마다 재료 네 가지를 알면 「그 모델 왜 좋았어요」에 답할 수 있고 배포한(서비스에 내보낸) 모델이 이상할 때 어느 재료가 바뀌었는지도 찾을 수 있습니다. 반대로 재료를 적어 두지 않은 모델은 결과가 좋았어도 다시 만들 수 없고 나빴어도 원인을 찾을 수 없습니다.

> **한 줄 요약:** 9월 3일 모델 v412 는 코드 a3f9c21 만으로 정해지지 않고 데이터 파티션(날짜별로 나눠 저장한 데이터) 30개, 설정 네 줄, 학습 이미지 1.14 까지 재료 네 가지가 학습을 한 번 거쳐 나온 결과입니다. 네 가지 가운데 하나라도 다르면 다른 모델이 나옵니다. 같은 코드로 오늘 다시 학습하면 8월 20일 파티션이 그 사이 백필(지난 날짜의 데이터를 다시 만드는 일)로 다시 써졌고 학습 이미지 안의 라이브러리 버전이 올라갔고 데이터를 섞는 순서를 정하는 시드를 적어 두지 않아서 다른 값이 나옵니다. 레지스트리에 버전마다 재료 네 가지와 지표와 상태를 적어 두면 「9월 3일 모델은 어느 데이터로 만들었나」에 30초 안에 답합니다. 적어 둔 대로 재료를 맞춰 다시 학습하면 같은 값이 나옵니다.

> **골라 읽는 법** — 절이 10개인 글입니다. 절마다 카드 한 장이나 표 하나가 있어서 그 카드나 표만 보고 넘어가도 됩니다.
>
> - 모델 하나를 만드는 재료 네 가지 → 1절
> - 「최근 30일」이라고 적으면 다른 데이터가 되는 까닭 → 2절
> - 레지스트리 표 한 장에 적는 것 → 3절
> - 배포된 모델에서 데이터까지 거꾸로 따라가는 방법 → 4절
> - 재현본(다시 만든 모델)이 9월 3일 모델과 다른 세 자리와 파이썬 실험 → 5절
> - 서버가 「최신」 대신 정한 버전 하나를 로드하는(메모리에 올려 요청에 쓰는) 까닭 → 6절
> - 담장 안(앱과 광고 서버를 한 회사가 다 가진 곳)과 열린 RTB(매체와 광고 서버가 다른 회사인 곳)에서 데이터 버전을 남기는 방식 → 7절

이 글에 나오는 버전 번호, 해시(hash, 커밋마다 붙는 a3f9c21 같은 고유한 문자열), 날짜, 지표는 모두 설명을 위해 정한 가상 값입니다. 학습 파이프라인의 태스크 일곱 개와 그 시각은 앞 편 [학습 파이프라인](post.html?id=training-pipeline-dag)의 값을 그대로 씁니다. 하루 학습 행 2,485만 행도 앞 편에서 계산해 둔 값을 가져왔습니다. 카드에 쓴 색은 네 가지입니다. 파랑은 놓여 있는 것(데이터 버전, 레지스트리 표), 벽돌색은 달라진 자리와 배포, 먹색은 모델과 서버, 회색은 만드는 작업(학습 실행)을 나타냅니다. 점선 상자는 적어 둔 재료입니다.

## 1. 모델 하나를 만드는 재료 네 가지

**모델 v412 는 파일 하나가 아니라 코드, 데이터, 설정, 환경의 재료 네 가지가 학습을 한 번 거쳐 나온 결과입니다. 네 가지가 모두 같아야 같은 모델이 나오고 하나라도 다르면 다른 모델이 나옵니다.**

지훈 씨가 9월 3일 모델을 다시 만들면서 맞춘 재료는 네 가지 가운데 코드 하나뿐이었습니다. 해시가 a3f9c21 인 9월 3일 커밋을 받아 그 코드로 학습을 돌렸을 뿐 데이터, 설정, 환경의 나머지 세 가지는 찾지 않았습니다. 그날 학습이 어느 파티션들을 읽었는지, 학습률과 임베딩 차원 같은 설정이 무엇이었는지, 학습이 어느 버전의 이미지에서 돌았는지가 그 세 가지입니다. 파티션(partition)은 테이블을 날짜 같은 값으로 나눠 저장한 단위입니다. 이 글의 데이터는 dt=2026-08-04 처럼 날짜 하나가 파티션 하나입니다.

이 세 가지는 원래 학습 실행 기록에 적혀 있어야 합니다. 학습 실행 기록은 학습을 한 번 돌릴 때마다 그 실행에 번호를 붙여 남기는 기록입니다. 9월 3일 모델의 재료 네 가지와 각 재료가 적혀 있어야 하는 곳을 표로 적으면 아래와 같습니다. 표의 설정 칸에서 lr 은 학습률(가중치를 한 번 고칠 때 얼마나 크게 고치는지 정하는 값), dim 은 임베딩 차원(입력을 나타내는 임베딩 벡터의 길이), epochs 는 학습 데이터를 처음부터 끝까지 몇 번 읽는지(에폭 수)입니다. 마지막 seed 는 표 아래 문단에서 설명하는 시드입니다.

| 재료 | 9월 3일 v412 의 값 | 적혀 있어야 하는 곳과 적혀 있었는지 |
|---|---|---|
| 코드 | 커밋 a3f9c21 | 코드 저장소. 있었습니다 |
| 데이터 | 파티션 30개, dt=2026-08-04 부터 09-02 까지, 9월 3일 버전 | 학습 실행 기록. 없었습니다 |
| 설정 | lr=0.002, dim=32, epochs=1, seed=417 | 학습 실행 기록. 없었습니다 |
| 환경 | 학습 이미지 pctr-train:1.14 | 학습 실행 기록. 없었습니다 |

표의 오른쪽 열을 보면 네 가지 가운데 적혀 있던 재료는 코드 하나뿐이고 나머지 세 가지는 어디에도 적혀 있지 않았으므로 지훈 씨는 처음부터 9월 3일 모델을 다시 만들 수 없었습니다. 코드가 같아야 같은 모델이 나오지만 코드만 같다고 같은 모델이 나오지는 않으므로 코드가 같다는 조건은 필요조건일 뿐 충분조건이 아닙니다.

설정 칸에는 시드(seed)도 들어 있습니다. 학습은 데이터를 섞은 뒤 그 순서대로 읽는데, 섞는 순서를 정하는 수가 시드입니다. 그래서 시드를 적어 두지 않으면 같은 코드와 같은 데이터로 학습해도 값이 달라집니다. 5절에서 이 차이를 파이썬 실험으로 확인합니다.

재료 네 가지가 모두 같아야 같은 모델이 나오므로 학습이 돌 때마다 네 가지를 빠짐없이 학습 실행 기록에 남기기로 합니다. 앞 편 파이프라인에서 학습은 네 번째 태스크이므로 그 태스크가 시작할 때 재료 네 가지를 적으면 됩니다. 다만 데이터 칸을 적는 방법에는 함정이 있습니다. 「최근 30일」이라고 적으면 안 되는데, 그 까닭은 다음 절에서 봅니다.

## 2. 「최근 30일」로 적어 두면 달라지는 데이터

**데이터 재료는 고르는 규칙이 아니라 읽은 파티션의 목록으로 적습니다. 「최근 30일」이라는 규칙은 오늘 적용하면 다른 30일을 고릅니다. 같은 날짜를 골라도 그 사이 백필로 다시 써진 파티션이 있습니다.**

9월 3일 커밋의 코드에는 학습 데이터를 고르는 규칙이 「최근 30일」로 적혀 있었습니다. 「최근 30일」은 데이터의 이름이 아니라 데이터를 고르는 규칙이라 같은 규칙도 적용하는 날에 따라 다른 날짜를 고릅니다. 같은 날짜를 고르더라도 그 사이 파티션 안의 내용이 바뀌어 있을 수 있습니다.

9월 3일 04:00 의 학습이 읽은 데이터는 8월 4일부터 9월 2일까지의 파티션 30개였습니다. 지훈 씨가 학습을 다시 돌린 9월 15일에는 같은 규칙이 그날을 기준으로 8월 16일부터 9월 14일까지의 30개를 골랐습니다. 두 범위에서 겹치는 날은 8월 16일부터 9월 2일까지 18개뿐입니다. 9월 15일 학습이 읽은 나머지 12개는 9월 3일부터 9월 14일까지라 9월 3일 학습이 읽지 않은 날입니다. 거꾸로 9월 3일 학습이 읽은 8월 4일부터 8월 15일까지의 12개는 9월 15일 학습에서 빠졌습니다. 첫 번째 차이는 이렇게 30개 가운데 12개의 날짜가 서로 다르다는 점입니다.

날짜를 8월 4일부터 9월 2일까지로 고정해 다시 돌려도 차이가 하나 더 남습니다. 세 경우를 표로 나란히 놓으면 아래와 같습니다.

| 무엇 | 9월 3일에 실제로 읽은 것 | 「최근 30일」을 9월 15일에 적용한 결과 | 날짜를 고정해도 남는 차이 |
|---|---|---|---|
| 날짜 범위 | 08-04 부터 09-02 | 08-16 부터 09-14 | 없음 |
| 겹치는 파티션 | 30개 | 18개 | 30개 |
| 08-20 파티션의 내용 | 9월 3일 버전 | 9월 5일 백필 버전 | 9월 5일 백필 버전 |

날짜를 고정해도 남는 차이는 표의 마지막 줄에 있는 8월 20일 파티션의 내용입니다. 백필(backfill)은 이미 만들어 둔 지난 날짜의 파티션을 다시 만드는 일입니다. 앞 편 4절에서 지훈 씨는 조인 조건(두 테이블의 행을 어떤 값으로 맞춰 붙일지 정하는 조건)을 고친 뒤 지난 30일을 백필했습니다. 9월 5일에 돌린 그 백필이 8월 20일 파티션도 다시 썼습니다. 그러니 지금 저장소에 있는 8월 20일 파티션은 9월 3일 학습이 읽은 8월 20일 파티션과 내용이 다릅니다. 다시 써진 파티션은 라벨(노출마다 클릭이 있었는지를 붙인 값)이 더 맞게 붙어 있지만 9월 3일 모델을 재현하려는 목적에서는 다른 데이터입니다.

앞 편 5절은 파티션 전체를 새 결과로 바꿔 쓰는 덮어쓰기가 옳다고 했는데 덮어쓰기는 바꾸기 전의 내용을 지웁니다. 9월 3일 모델을 재현하려면 덮어쓰기 전의 이전 버전이 따로 남아 있어야 합니다.

그래서 데이터 재료에는 읽은 파티션의 목록과 각 파티션의 버전을 함께 적습니다. 버전으로는 그 파티션이 마지막으로 써진 시각이나 스냅샷 번호를 씁니다. 스냅샷(snapshot)은 저장소가 어느 시점의 내용을 나중에 그대로 다시 읽을 수 있도록 보존해 둔 상태로, 스냅샷마다 번호가 붙습니다. 저장소가 스냅샷을 지원하면 9월 3일 학습이 읽은 시점의 스냅샷 번호 하나로 30개 파티션의 그때 내용을 다시 읽을 수 있습니다. 스냅샷을 지원하지 않는 저장소라면 학습에 쓴 데이터를 그대로 복사해 둡니다. 하루 2,485만 행씩 30일이면 복사본이 2,485만 × 30 = 7억 4,550만 행이라 싸지 않지만 재현이 필요한 모델에는 그 비용을 들입니다.

데이터 재료는 이렇게 고르는 규칙 대신 읽은 파티션의 목록과 버전으로 적습니다. 재료 네 가지를 적을 자리는 다음 절의 레지스트리 표입니다.

## 3. 레지스트리 표 한 장이 답하는 두 가지 질문

**레지스트리는 모델 파일을 넣어 두는 저장소가 아니라 모델 버전마다 재료 네 가지와 지표와 상태를 적은 표입니다. 서버는 이 표에서 상태가 「운영」인 버전을 로드합니다.**

앞 편 파이프라인에서 여섯 번째 태스크가 「등록」이었는데, 등록은 이 표에 새 버전의 줄을 하나 적는 일입니다. 팀장이 물은 9월 3일 모델 v412 도 이 표의 한 줄이고 지금은 상태가 폐기입니다. 폐기된 버전을 표와 저장소에 어떻게 남겨 두느냐에 따라 팀장의 질문에 답할 수 있는지가 정해집니다. 이 팀의 레지스트리 표는 아래와 같습니다.

| v412 | 09-03 04:00 | #4127 | 0.8119 | 0.98 | 폐기 | a3f9c21 |
| v417 | 09-08 04:00 | #4162 | 0.8123 | 0.99 | 운영 | b71e0d4 |
| v418 | 09-15 04:00 | #4211 | 0.8131 | 1.06 | 후보 | c02aa19 |

학습 실행 열의 #4127 같은 번호는 그 학습이 돌 때 남긴 학습 실행 기록의 번호입니다. 1절의 재료 네 가지는 이 기록 안에 있습니다. 레지스트리 표에는 그 번호만 적고 재료는 번호로 찾아간 기록에서 봅니다.

AUC 와 COPC 는 앞 편의 게이트가 측정한 값입니다. 게이트는 새 모델을 배포하기 전에 지표가 기준 안에 드는지 보고 기준 밖이면 배포를 막는 단계입니다. AUC 는 클릭이 난 노출과 나지 않은 노출을 모델이 얼마나 잘 구분하는지 나타내는 지표입니다. AUC 가 1 에 가까울수록 모델이 두 노출을 잘 구분합니다.

상태는 후보, 운영, 폐기 세 가지 가운데 하나입니다. 후보는 게이트를 지났거나 사람이 볼 차례인 버전, 운영은 지금 서버가 서빙하고 있는 버전, 폐기는 더는 쓰지 않는 버전입니다. 서빙(serving)은 서버가 들어오는 요청마다 모델로 예측값을 계산해 돌려주는 일입니다. 로드(load)는 서버가 모델 파일을 메모리에 올려 요청에 쓸 수 있게 하는 일입니다.

v418 은 AUC 가 0.8131 로 운영 중인 v417 의 0.8123 보다 높은데도 COPC 가 1.06 으로 게이트 기준 밖이라 배포되지 않고 후보로 남았습니다. 표의 한 줄만 봐도 v418 이 배포되지 않은 까닭이 보입니다.

폐기는 삭제와 다릅니다. v412 는 폐기됐어도 모델 파일과 학습 실행 기록이 남아 있습니다. 팀장이 다시 만들 수 있는지 물은 모델이 바로 폐기된 v412 입니다. 폐기하면서 파일과 기록까지 지웠다면 「다시 만들어 볼 수 있어요」에 「없습니다」로 답해야 합니다. 이 팀은 보존 기간을 90일로 정해 두고 그 기간 안에는 폐기된 버전의 파일과 재료를 지우지 않습니다.

레지스트리 표가 답하는 질문은 두 가지입니다. 「지금 서버에 무엇이 돌고 있나」는 상태 열에서 「운영」인 줄을 찾으면 답이 나옵니다. 「그 모델은 무엇으로 만들었나」는 그 줄의 학습 실행 열에 적힌 번호로 기록을 열면 알 수 있습니다. 그래서 등록은 모델 파일을 올리는 일이 아니라 이 표에 한 줄을 적는 일로 정합니다. 다만 표는 데이터로 모델을 만드는 순서대로 적히는데 팀장의 질문은 모델에서 데이터로 거꾸로 갑니다. 그 거꾸로 가는 순서는 다음 절에서 따라갑니다.

## 4. 배포된 모델에서 데이터까지 거꾸로 따라가는 계보

**데이터 파티션 30개가 학습 실행 하나를 거쳐 모델이 되고 그 모델이 배포됩니다. 질문은 이 연결을 배포 쪽에서 데이터 쪽으로 거꾸로 따라갑니다. 중간의 고리 하나가 끊기면 그 뒤로는 따라갈 수 없습니다.**

모델을 만들 때는 데이터에서 배포 쪽으로 가지만 팀장처럼 모델을 두고 물을 때는 배포에서 데이터 쪽으로 갑니다. 「9월 3일에 돌던 모델은 어느 데이터로 만들었나」라는 질문은 배포 기록, 모델 버전, 학습 실행, 파티션 목록의 네 고리를 이 순서로 지나야 답이 나옵니다.

만드는 순서로 먼저 따라가 보겠습니다. 학습 실행 #4127 이 8월 4일부터 9월 2일까지의 파티션 30개를 읽어 모델 v412 를 만들었습니다. v412 는 9월 3일 06:31 에 카나리 배포가 시작돼 그날 운영 상태가 됐습니다. 카나리 배포(canary deployment)는 새 버전을 트래픽의 일부에만 먼저 내보내 문제가 없는지 본 뒤 전체로 넓히는 배포 방식입니다. 배포 기록에는 서버가 어느 시각에 어느 버전으로 바뀌었는지가 적힙니다. 이렇게 데이터에서 학습 실행과 모델을 거쳐 배포까지 이어지는 연결을 계보(lineage)라고 부릅니다.

카드의 윗줄은 데이터 30일에서 배포까지 앞으로 가는 계보이고 그 아래 점선 화살표는 팀장의 질문이 거꾸로 가는 순서입니다.

반대로 고리 하나가 비어 있으면 그 고리에서 멈춥니다. 지훈 씨는 두 번째 고리에서 멈췄습니다. 레지스트리의 v412 줄이 학습 실행을 가리키지 않아 지훈 씨 손에는 코드 해시 a3f9c21 하나만 남았습니다.

계보는 「좋았던 모델」을 다시 만들 때보다 배포한 모델이 이상할 때 더 자주 필요합니다. 어제 내보낸 모델의 COPC 가 갑자기 1.09 가 됐다고 하겠습니다. 계보가 있으면 그 모델의 학습 실행으로 가서 데이터 버전을 열고 어느 파티션이 이상한지 볼 수 있지만 계보가 없으면 「모델이 이상하다」에서 더 나아가지 못합니다.

계보가 끊기지 않게 하려면 고리마다 다음 고리의 번호를 적어 둡니다. 배포 기록에는 버전을, 레지스트리에는 학습 실행 번호를, 학습 실행 기록에는 파티션 목록을 적습니다. 다음 절에서는 이렇게 찾은 재료를 맞춰 다시 만들면 정말 같은 값이 나오는지 확인합니다.

## 5. 재현본이 9월 3일 모델과 다른 세 자리

**같은 코드로 오늘 다시 만든 모델은 그 사이 8월 20일 파티션이 백필로 다시 써졌고 학습 이미지 안의 라이브러리 버전이 올라갔고 시드가 없었기 때문에 9월 3일 모델과 다른 값을 냅니다.**

지훈 씨의 재현본(9월 3일 모델을 다시 만들려고 9월 15일에 같은 코드로 학습한 모델)을 9월 3일 모델과 재료 네 가지로 하나씩 비교하면 세 자리가 달랐습니다. 첫째 자리는 데이터로, 2절에서 본 8월 20일 파티션이 9월 5일 백필 버전으로 바뀌어 있었습니다. 둘째 자리는 환경입니다. 학습 이미지가 1.14 에서 1.15 로 올라가면서 그 안의 라이브러리도 2.3 에서 2.4 가 됐는데, 라이브러리가 다르면 같은 코드라도 계산 순서와 초기값(학습을 시작할 때 가중치에 넣는 값)이 달라질 수 있습니다. 셋째 자리는 설정 안의 시드입니다. 9월 3일 학습에는 시드가 없었습니다. 그날의 난수(무작위로 뽑은 수)는 그날 것이고 오늘의 난수는 오늘 것이라 두 학습은 데이터를 서로 다른 순서로 섞어 읽습니다.

세 자리 가운데 시드와 데이터 버전은 작은 실험으로 확인할 수 있습니다. 아래 코드는 같은 재료로 두 번 학습하면 값이 같은지, 시드만 바꾸면 값이 얼마나 흔들리는지, 8월 20일에 해당하는 하루 파티션만 다른 버전으로 바꾸면 얼마나 달라지는지를 봅니다.

코드는 하루 600행씩 30일치의 가상 로그로 작은 로지스틱 회귀를 학습합니다. 로지스틱 회귀(logistic regression)는 피처(모델에 넣는 입력 값)에 가중치를 곱해 더한 값을 시그모이드 함수로 0 과 1 사이의 확률로 바꾸는 모델입니다. 이 코드의 모델은 피처 x1, x2 의 가중치 두 개와 피처와 상관없이 더하는 절편 하나까지 가중치 세 개를 학습합니다. make_data 의 seed 는 데이터 버전(스냅샷)을 정합니다. seed=2016 으로 만든 데이터를 9월 3일에 쓴 데이터 버전으로 두고 9월 5일 백필로 다시 써진 8월 20일 파티션은 seed=2017 로 만든 그 날의 행으로 바꿉니다. 8월 4일을 d=0 으로 세면 8월 20일은 16일 뒤라 코드에서는 d=16 입니다.

train 은 SGD 로 3에폭을 학습합니다. SGD(확률적 경사 하강법)는 학습 데이터를 한 행씩 읽을 때마다 가중치를 조금씩 고치는 학습 방법입니다. train 은 에폭마다 데이터를 섞은 뒤 한 행씩 읽으며 가중치를 고칩니다. 섞는 순서는 train 의 seed 가 정하므로 seed 가 바뀌면 같은 데이터를 다른 순서로 읽고 가중치를 고치는 차례도 달라집니다. copc 는 실제 클릭 수를 예측 확률의 합으로 나눠 COPC 를 계산합니다.

이 실험은 데이터가 작아서 COPC 가 레지스트리의 0.98 과 다른 값으로 나오고 시드에 따라 흔들리는 폭도 실제 크기의 학습 데이터로 학습할 때보다 큽니다. 이 실험에서는 값의 크기보다 무엇을 바꿨을 때 값이 그대로이고 무엇을 바꿨을 때 달라지는지를 봅니다.

```python
# 하는 일: 같은 코드로 모델을 다시 만들면 같은 값이 나오는지, 시드와 데이터 버전을 하나씩 바꿔 가며 본다.
import random, math

# 1단계: 데이터 버전을 만드는 함수를 둔다
# 데이터는 전부 가상이고 크기는 설명용으로 작게 잡았다.
def make_data(seed, days=30, per_day=600):
    """30일치 가상 로그. seed 가 데이터 버전(스냅샷)을 정한다. 날마다 바탕 클릭률이 조금 다르다."""
    rng = random.Random(seed)
    rows = []
    for d in range(days):
        base = 0.02 + 0.004 * math.sin(d / 5)
        for _ in range(per_day):
            x1, x2 = rng.random(), rng.random()          # 피처 둘
            p = base * (1 + 2 * x1) * (1 + x2)
            rows.append((d, x1, x2, 1 if rng.random() < p else 0))
    return rows

# 2단계: 학습과 눈금 확인 함수를 만든다
# 로지스틱 회귀를 SGD 로 3에폭 학습한다.
def train(rows, seed, lr=0.02, epochs=3):
    """SGD 3에폭. seed 가 섞는 순서를 정한다. 시드를 안 적으면 매번 다른 값이 걸리는 것과 같다."""
    rng = random.Random(seed)
    w = [0.0, 0.0, -3.0]
    for _ in range(epochs):
        order = rows[:]
        rng.shuffle(order)
        for _, x1, x2, y in order:
            p = 1 / (1 + math.exp(-(w[0] * x1 + w[1] * x2 + w[2])))
            g = p - y
            w = [w[0] - lr * g * x1, w[1] - lr * g * x2, w[2] - lr * g]
    return w

def copc(w, rows):
    """실제 클릭 ÷ 예측 합. 1 이면 눈금이 맞고, 1 보다 크면 과소예측이다."""
    pred = sum(1 / (1 + math.exp(-(w[0] * x1 + w[1] * x2 + w[2]))) for _, x1, x2, _ in rows)
    return sum(r[3] for r in rows) / pred

def show(label, w, rows):
    print(f"{label}  w = {[round(v, 4) for v in w]}  COPC {copc(w, rows):.4f}")

# 3단계: 같은 재료로 두 번 학습한다
data = make_data(seed=2016)                       # 9월 3일에 쓴 데이터 버전
show("9월 3일 v412 (시드 417)     ", train(data, 417), data)
show("재료 넷 같고 시드도 417     ", train(data, 417), data)

# 4단계: 시드만 바꿔 본다
for s in (1, 2, 3):
    show(f"시드만 다름 ({s})            ", train(data, s), data)

# 5단계: 하루 파티션만 다른 데이터 버전으로 학습한다
# 08-20 파티션(d=16)만 9월 5일 백필로 다시 써진 버전이다. 그 날 행만 다른 난수로 다시 만든다.
data2 = [r for r in data if r[0] != 16] + [r for r in make_data(seed=2017) if r[0] == 16]
show("08-20 한 날만 다른 버전 (417)", train(data2, 417), data2)

# 출력:
# 3단계 뜻: 재료 넷과 시드가 같으면 가중치 세 개와 COPC 0.9647 이 그대로 다시 나온다.
# 9월 3일 v412 (시드 417)       w = [1.0103, 0.8028, -3.7022]  COPC 0.9647
# 재료 넷 같고 시드도 417       w = [1.0103, 0.8028, -3.7022]  COPC 0.9647
# 4단계 뜻: 데이터와 코드가 같아도 시드만 바꾸면 COPC 가 흔들린다. 시드만 바꾼 세 줄의 COPC 는 0.9490 에서 0.9530 사이다.
# 시드만 다름 (1)              w = [0.9241, 0.8324, -3.652]  COPC 0.9490
# 시드만 다름 (2)              w = [1.0022, 0.7662, -3.6611]  COPC 0.9505
# 시드만 다름 (3)              w = [0.932, 0.8628, -3.6781]  COPC 0.9530
# 5단계 뜻: 08-20 하루 파티션만 다른 버전으로 바꾸면 COPC 가 1.0206 으로 가장 크게 달라진다.
# 08-20 한 날만 다른 버전 (417)  w = [0.9766, 0.8329, -3.7592]  COPC 1.0206
```

첫 두 줄은 재현에 성공한 경우입니다. 재료 네 가지와 시드 417 이 모두 같아서 가중치 세 개가 [1.0103, 0.8028, -3.7022] 로 소수점 넷째 자리까지 같고 COPC 도 둘 다 0.9647 입니다.

다음 세 줄은 데이터와 코드는 그대로 두고 시드만 1, 2, 3 으로 바꾼 학습입니다. 데이터와 코드가 같은데도 COPC 가 0.9490, 0.9505, 0.9530 으로 시드 417 의 0.9647 과 다르고 세 줄끼리도 0.949 와 0.953 사이에서 흔들립니다.

마지막 줄은 시드를 417 로 두고 30일 가운데 8월 20일 하루 파티션만 다른 버전으로 바꾼 학습입니다. COPC 가 0.9647 에서 1.0206 으로 바뀌어 이 실험에서 가장 크게 달라졌습니다. 지훈 씨의 재현본에서는 이 실험이 하나씩 바꿔 본 시드와 데이터 버전에 라이브러리 버전까지 세 가지가 한꺼번에 달라서 9월 3일 모델과 다른 값이 나왔습니다.

라이브러리 버전도 이 실험으로는 보여 줄 수 없을 뿐 재현본이 9월 3일 모델과 다른 세 자리 가운데 하나입니다. 학습 이미지 안에는 라이브러리 버전이 고정돼 있어 이미지 버전 번호 하나가 라이브러리 버전 전부를 대신하므로 환경 재료는 pctr-train:1.14 같은 이미지 버전 번호로 적습니다. 이미지가 무엇이고 어떻게 만드는지는 다음 편 [Docker 와 CI](post.html?id=container-ci-pipeline) 에서 봅니다.

재현을 위해 시드는 설정에 넣고 데이터는 파티션 목록과 버전까지 적고 환경은 이미지 버전 번호로 남깁니다. 이제 서버 쪽을 봅니다. 서버가 무엇을 로드하느냐에 따라 롤백(문제가 생긴 새 버전을 이전 버전으로 되돌리는 일)과 재현이 달라집니다.

## 6. 「최신」 대신 정한 버전 하나를 로드하는 서버

**모델 서버는 「가장 최신 모델」이 아니라 레지스트리에서 상태가 운영인 버전 하나를 로드합니다. 그래야 지금 무엇이 돌고 있는지가 확정되고 롤백이 표의 상태를 바꾸는 일이 됩니다.**

서버가 「최신」을 가리키면 새 모델이 등록되는 순간 로드하는 모델도 바뀌지만 버전 번호를 가리키면 사람이 표의 상태를 바꿀 때만 바뀝니다. 「지금 서버에 무엇이 돌고 있나」에 답하려면 서버가 버전 번호를 가리켜야 합니다. 두 방식을 표로 비교하면 아래와 같습니다.

| 서버가 가리키는 것 | 새 모델이 등록되면 | 「지금 무엇이 도나」를 아는 법 | 롤백하는 법 |
|---|---|---|---|
| 「최신」 | 바로 바뀝니다 | 등록 시각을 뒤져야 압니다 | 옛 파일을 다시 「최신」으로 덮어야 합니다 |
| 버전 v417 | 안 바뀝니다 | 표의 운영 줄이 답입니다 | 표의 운영 상태를 v417 로 되돌립니다 |

앞 편에서 게이트에 걸린 v418 은 레지스트리에 등록은 됐지만 상태가 후보였습니다. 서버는 상태가 운영인 v417 만 보므로 그날도 v417 을 계속 서빙했습니다. 「최신」을 가리키는 서버였다면 게이트 결과와 상관없이 v418 이 등록되는 순간 서빙에 나갔을 텐데, 서버가 버전 하나를 가리키는 규칙 덕분에 v418 은 나가지 않았습니다.

롤백도 같은 방식입니다. 배포한 v418 이 이상하다면 표에서 v417 을 다시 운영으로 바꿉니다. 서버는 바뀐 운영 줄을 다시 읽어 v417 을 로드합니다. 모델 파일을 옮기지 않고 표의 상태만 바꾸므로 롤백은 몇 초면 끝납니다. 배포와 롤백의 전체 순서는 [모델 배포와 롤백](post.html?id=model-deployment-rollback) 편에서 봅니다.

버전 하나를 가리키는 방식에는 규칙이 하나 더 따라옵니다. 버전 번호를 한 번 붙인 뒤에는 그 번호 안의 내용을 바꾸지 않습니다. v417 이 어제와 오늘 다른 파일이라면 「v417 이 돌고 있다」는 말로는 서버에서 어떤 모델이 도는지 알 수 없습니다. 그래서 내용을 고치면 새 번호를 붙입니다. 마지막 7절에서는 데이터 버전을 남기는 방식이 무대에 따라 어떻게 다른지 봅니다.

## 7. 무대에 따라 다른 데이터 버전 보존 방식

**담장 안에서는 로그가 자기 회사의 것이라 학습에 쓴 데이터 버전을 그대로 남길 수 있습니다. 열린 RTB 에서는 전환(광고를 본 뒤의 구매 같은 행동)이 며칠 뒤에야 들어와 파티션이 계속 다시 써지므로 버전을 남기지 않으면 재현이 처음부터 불가능합니다.**

재현의 첫 재료인 데이터는 무대마다 얼마나 자주 다시 써지는지가 다릅니다. 이 글의 두 무대 가운데 담장 안은 한 회사가 앱과 광고 서버를 다 가진 곳입니다. 열린 RTB 는 매체(광고가 실리는 앱이나 사이트)와 광고 서버가 서로 다른 회사인 곳입니다. 데이터가 자주 다시 써지는 무대일수록 학습이 읽은 「그날 버전」을 따로 남겨야 합니다.

### 그날 버전 전체를 남기는 담장 안 [무대: 닫힌 생태계]

담장 안에서는 노출과 클릭이 모두 자기 회사의 로그로 남습니다. 앞 편에서 본 대로 클릭은 노출 뒤 2분 안에 99.9% 가 들어옵니다. 04:00 이면 어제 파티션이 닫힙니다. 파티션이 닫힌다는 말은 그 날짜의 로그가 다 들어와 더는 새 행이 추가되지 않는다는 뜻입니다. 닫힌 파티션은 백필을 돌리지 않는 한 다시 써지지 않으므로 스냅샷 번호 하나로 30개 파티션의 그때 내용을 다시 읽을 수 있습니다. 스냅샷을 지원하지 않는 저장소라도 학습 데이터 30일치 7억 4,550만 행을 복사해 두면 됩니다. 이 블로그의 저자가 일하는 곳도 이 무대입니다. 이 글의 표와 카드는 이 무대의 상태를 그렸습니다.

### 버전을 남기지 않으면 재현이 불가능한 열린 RTB [무대: 열린 RTB]

열린 RTB 에서는 전환이 광고주 서버에서 며칠에 걸쳐 넘어오므로 어제 파티션이 오늘도 내일도 다시 써집니다. 9월 3일 학습이 읽은 8월 20일 파티션도 9월 4일이면 이미 다른 내용이 됩니다. 재료 네 가지 가운데 데이터가 저절로 없어지는 무대라서 학습 실행이 읽은 데이터를 그 자리에서 복사해 두지 않으면 재현이 처음부터 불가능합니다. 그래서 학습 실행 기록에는 파티션 목록만 적어서는 모자라고 읽은 행을 그대로 담은 복사본의 위치까지 적습니다.

## 한눈 정리

| 자리 | 무엇 | 숫자 |
|---|---|---|
| 재료 네 가지 | 코드, 데이터, 설정, 환경. 네 가지가 같아야 같은 모델 | v412 는 a3f9c21, 파티션 30개, 설정 네 줄, 이미지 1.14 |
| 데이터 재료 | 규칙이 아니라 목록과 버전으로 적는다 | 「최근 30일」은 9월 15일에 18개만 겹침 |
| 레지스트리 | 버전마다 학습 실행, 지표, 상태를 적은 표 | v417 운영, v418 후보(COPC 1.06), v412 폐기 |
| 계보 | 배포 → 버전 → 학습 실행 → 파티션 목록 | 고리 사이를 세 번 건너 30초 |
| 재현본이 다른 자리 | 데이터 버전, 라이브러리, 시드 | 실험에서 시드만 달라도 0.949 와 0.953, 한 날 버전이 다르면 1.0206 |
| 서버가 로드하는 것 | 「최신」이 아니라 운영 상태인 버전 하나 | 롤백은 표의 상태를 바꾸는 몇 초 |
| 보존 | 폐기해도 파일과 재료는 남긴다 | 90일 |

## 헷갈리기 쉬운 점

- **모델 파일이 곧 모델이 아닙니다.** 모델 파일은 결과이고 그 원인은 재료 네 가지입니다. 그래서 파일만 남기면 「왜 이 값이 나왔나」에 답할 수도 없고 같은 모델을 다시 만들 수도 없습니다.
- **「최근 30일」은 데이터 이름이 아니라 규칙입니다.** 이 규칙은 적용하는 날에 따라 다른 30일을 고릅니다. 날짜를 고정해 같은 30일을 골라도 그 사이 백필로 다시 써진 파티션은 학습이 읽었던 파티션과 다른 데이터입니다.
- **레지스트리는 파일 저장소가 아닙니다.** 모델 파일은 저장소에 따로 둡니다. 레지스트리 표에는 그 파일이 무엇으로 만들어졌는지와 지금 어떤 상태인지를 적습니다. 서버는 표에서 상태가 운영인 줄을 찾아 그 버전을 로드합니다.
- **폐기는 삭제가 아닙니다.** 폐기된 v412 도 보존 기간 안에는 모델 파일과 학습 실행 기록이 남아 있습니다. 지웠다면 팀장의 질문에 내놓을 답이 없습니다.
- **같은 코드가 같은 모델을 보장하지 않습니다.** 코드는 재료 네 가지 가운데 하나입니다. 코드와 데이터가 같아도 시드 하나만 없으면 값이 흔들립니다.
