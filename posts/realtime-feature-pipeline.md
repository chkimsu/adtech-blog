# 실시간 피처 파이프라인: 이벤트 한 건이 Redis 값이 되는 2초

지훈 씨가 모델 팀에 온 지 11주째입니다. 동영상 광고의 완주율을 피처로 쓰는 모델이 있는데, 그 피처가 언제 적힌 값인지 아는 사람이 없었습니다. 재생 이벤트가 나간 뒤 모델이 그 값을 읽기까지 몇 초냐고 물으면 다들 「거의 바로」라고만 했습니다.

선배는 노트북에 같은 구조를 띄우고 이벤트를 직접 보내 보라고 했습니다. 지훈 씨는 사용자 u42 가 영상 v7 을 보는 이벤트 다섯 건을 하나씩 보내며, 지나가는 자리마다 응답을 기록했습니다.

**앱에서 나간 이벤트 한 건이 모델이 읽는 피처 값이 되기까지, 어디를 지나며 얼마나 걸릴까요?**

이 길을 실시간 피처 파이프라인이라고 부릅니다. 이벤트를 받는 API, 차례로 쌓아 두는 Kafka, 읽어서 값을 더하는 처리기, 더한 값을 두는 Redis 로 이어집니다. 피처가 늦으면 방금 광고를 끝까지 본 사용자에게 같은 광고가 또 나갑니다. 몇 초 늦는지, 처리기가 멈추면 값이 사라지는지를 알아야 장애 때 다시 돌릴지 버릴지를 정합니다.

> **한 줄 요약:** 이벤트 한 건은 API 와 Kafka 를 몇 ms 안에 지납니다. 처리기가 2초 들고 있다가 적용해서, 보낸 지 2,035ms 뒤에 Redis 값이 바뀝니다. 처리기를 12초 멈추면 lag 이 80 에서 552 로 자라지만, 다시 켜고 2초 뒤 한꺼번에 적용돼 잃는 이벤트는 없습니다. 같은 피처를 읽어 추천 점수를 내는 요청은 5.2ms 이고 그중 4.0ms 가 모델 서버 한 번입니다.

> **골라 읽는 법** — 절이 일곱인 글입니다. 절마다 표나 코드나 기록 재생 그림이 하나 있어서 그것만 보고 넘어가도 됩니다.
>
> - 이벤트 한 건이 지나는 다섯 자리와 걸린 시간 → 1절
> - Kafka 가 돌려준 partition 과 offset → 2절
> - 처리기가 2초 들고 있는 이유와 파이썬 → 3절
> - Redis 에 남는 값 → 4절
> - 처리기가 멈췄을 때의 lag → 5절
> - 읽는 길의 5.2ms → 6절
> - 담장 안과 열린 RTB → 7절

이 글의 숫자는 지어낸 값이 아닙니다. 노트북 한 대에 띄운 Kafka 브로커 하나, Redis, 처리기, API, 모델 서버에서 직접 재 본 값입니다. 운영 서버라면 ms 의 크기가 다르지만 어느 자리가 큰지는 같습니다. 글 속의 그림 셋은 그때 기록한 응답을 시간 순서대로 다시 그립니다.

---

## 1. 이벤트 한 건은 다섯 자리를 지납니다

**PAUSE 한 건은 API, Kafka, 처리기, Redis 를 지나 다시 API 로 읽힙니다. 다섯 자리 가운데 시간을 쓰는 곳은 처리기 하나입니다.**

앱은 사용자가 재생을 멈춘 순간 이벤트 하나를 만듭니다. 누가(user_id), 무엇을(video_id), 무엇을 했나(action), 언제(ts)입니다. 이 JSON 을 HTTP 요청 하나에 담아 API 로 보냅니다. API 는 그것을 들고 있지 않고 바로 Kafka 에 넘깁니다. 넘기는 데 걸린 시간은 Kafka 브로커가 「받았다」고 답하기까지 1.2ms 였습니다.

Kafka 는 이벤트를 받은 순서대로 쌓아 두는 서버입니다. 처리기는 Kafka 에서 이벤트를 읽어 피처 값을 더하는 프로그램입니다. 이 실습 환경의 처리기는 읽은 이벤트를 2초 들고 있다가 적용하므로, 다섯 자리의 시간이 고르지 않습니다. 앞의 두 자리는 1ms 남짓에 끝나고, 셋째 자리에서 2초를 씁니다.

아래 표는 사용자 u42 가 영상 v7 을 12초 보고 멈춘 PAUSE 한 건의 기록입니다. 시간은 API 에 보낸 순간을 0 으로 잰 값입니다.

| 자리 | 하는 일 | 보낸 뒤 걸린 시간 |
|---|---|---|
| 1. API | 이벤트를 받아 Kafka 에 넘긴다 | 0ms |
| 2. Kafka | topic play_events 의 partition 3, offset 710 에 둔다 | 1.2ms |
| 3. 처리기 | 2초 들고 있다가 이벤트 시각 순서로 정렬해 적용한다. 12초를 더한다 | 2,035ms |
| 4. Redis | Hash 의 playtime_sec 이 0 에서 12 로 바뀐다 | 2,123ms 에 확인 |
| 5. API | 그 Hash 를 읽어 돌려준다 | 2,127ms |

4번의 시간은 0.25초마다 Redis 를 읽다가 바뀐 값을 본 때라 실제로 바뀐 때보다 조금 늦습니다. 값이 바뀐 것은 3번에서 처리기가 적용한 그 순간입니다. 다섯 건 모두 적용까지 2,029ms 에서 2,042ms 사이였습니다. 아래 그림에서 다섯 건을 하나씩 골라 기록을 다시 볼 수 있습니다.

그래서 이 피처의 신선도는 「2초 남짓 늦다」로 적습니다. 「거의 바로」가 아니라 hold 2초가 거의 전부라는 것이 이 표의 결론입니다. 그 2초가 무엇을 사는지는 3절에서 보고, 먼저 2번 자리가 이벤트를 어디에 두었는지를 봅니다.

## 2. Kafka 는 topic, partition, offset 으로 자리를 줍니다

**Kafka 가 돌려준 답은 「partition 3 의 710번 자리」입니다. key 가 같은 이벤트는 늘 같은 partition 에 차례로 앉습니다.**

topic 은 이벤트 종류마다 붙인 이름입니다. 이 실습 환경에는 재생 이벤트를 받는 topic play_events 가 있습니다. topic 은 partition 이라는 줄 여러 개로 나뉩니다. play_events 는 partition 이 넷입니다. partition 안에서 메시지마다 붙는 자리 번호가 offset 이고, 0 부터 하나씩 늘어납니다.

어느 partition 에 앉을지는 key 가 정합니다. API 는 user_id 를 key 로 붙여 보냅니다. Kafka 는 key 를 해시해 partition 수로 나눈 나머지를 씁니다. 그래서 u42 의 이벤트 다섯 건은 모두 partition 3 에 708, 709, 710, 711, 712번으로 차례로 앉았습니다. 다음은 그중 PAUSE 한 건을 Kafka 에서 다시 읽어 온 원문입니다.

```json
{
  "partition": 3,
  "offset": 710,
  "timestamp_ms": 1793436831018,
  "key": "u42",
  "value": {
    "event_id": "u42-v7-1793436831-PAUSE-5afe",
    "user_id": "u42",
    "video_id": "v7",
    "action": "PAUSE",
    "ts": 1793436831,
    "sent_at": 1793436831.018
  }
}
```

같은 partition 에 앉는 것이 중요한 이유는 순서입니다. Kafka 는 partition 하나 안의 순서를 지켜 줍니다. partition 이 다르면 순서를 지켜 주지 않습니다. 한 사용자의 START, PLAY, PAUSE 가 서로 다른 partition 에 흩어졌다고 해 봅니다. 그러면 처리기가 PAUSE 를 PLAY 보다 먼저 읽을 수 있습니다.

처리기는 consumer group playtime-agg 의 이름으로 읽습니다. 그룹마다 partition 별로 「어디까지 읽었나」를 Kafka 에 적어 두는데, 이것을 커밋한 offset 이라고 부릅니다. 처리기가 다시 켜지면 그 자리부터 이어 읽습니다. 읽어 간 메시지는 지워지지 않고 보관 기간 동안 그대로 남습니다. 5절의 「멈췄다 다시 켜기」가 되는 것이 이 두 성질 덕분입니다.

partition 수는 처리기를 몇 개까지 늘릴 수 있나를 정합니다. 한 그룹 안에서 partition 하나는 처리기 하나만 읽습니다. 그래서 partition 이 넷이면 다섯째 처리기는 받을 partition 이 없습니다. 다음 절은 그 처리기가 읽은 이벤트를 왜 바로 적용하지 않는지입니다.

## 3. 처리기가 2초 들고 있는 이유는 순서입니다

**처리기는 읽은 이벤트를 2초 들고 있다가 이벤트 시각 순서로 정렬해 적용합니다. 그러면 PAUSE 가 PLAY 보다 먼저 도착해도 12초를 맞게 셉니다.**

처리기의 규칙에서 PLAY 는 재생 구간을 열고 그 시각을 적어 둡니다. PAUSE 와 END 는 열린 구간을 닫고, 지금 시각에서 열린 시각을 뺀 초를 더합니다. 열린 구간이 없을 때 온 PAUSE 는 더할 것이 없어 무시합니다. 문제는 이 뺄셈이 순서에 기대고 있다는 것입니다.

같은 partition 이 지켜 주는 것은 사용자가 누른 순서가 아니라 「Kafka 에 도착한 순서」입니다. 휴대폰이 지하철에서 PLAY 를 늦게 보내거나, 첫 요청이 실패해 다시 보내면 PAUSE 가 먼저 도착합니다. 그래서 처리기는 읽은 이벤트를 2초 동안 들고 있다가, 그 사이에 모인 것을 이벤트가 찍힌 시각(ts) 순서로 정렬한 뒤 적용합니다. 이렇게 들고 있는 시간을 hold 라고 부릅니다.

아래 코드는 이 규칙을 그대로 옮겨, 순서가 뒤바뀐 두 이벤트를 두 번 셉니다. 숫자는 1절의 기록과 같은 3초의 PLAY 와 15초의 PAUSE 이고, PAUSE 가 먼저 도착했다고 가정합니다.

```python
# 하는 일: 순서가 뒤바뀌어 도착한 PLAY 와 PAUSE 로 누적 재생 초를 도착 순서와 시각 순서로 한 번씩 센다.
# 1단계: 도착한 이벤트를 둔다
# 3초에 누른 PLAY 와 15초에 누른 PAUSE 가 있다. PAUSE 가 먼저 도착했다고 가정한다.
arrived = [('PAUSE', 15), ('PLAY', 3)]

# 2단계: 처리기의 규칙을 함수로 둔다
# PLAY 는 구간을 연다. PAUSE 는 열린 구간이 있으면 닫고 시각의 차이를 더한다. 없으면 무시한다.
def count(events):
    open_ts, total, notes = None, 0, []
    for action, ts in events:
        if action == 'PLAY':
            open_ts = ts
            notes.append(f'{action}@{ts} 구간 열림')
        elif open_ts is not None:
            total += ts - open_ts
            notes.append(f'{action}@{ts} {ts - open_ts}초 더함')
            open_ts = None
        else:
            notes.append(f'{action}@{ts} 열린 구간이 없어 무시')
    return total, notes

# 3단계: 도착 순서 그대로 센다
# hold 가 0 초인 처리기다.
total, notes = count(arrived)
print(f'도착 순서: 누적 {total}초 | ' + ', '.join(notes))

# 4단계: 시각 순서로 정렬해 센다
# hold 동안 모인 것을 ts 로 정렬한 뒤 적용하는 처리기다.
total, notes = count(sorted(arrived, key=lambda e: e[1]))
print(f'시각 순서: 누적 {total}초 | ' + ', '.join(notes))

# 출력:
# 3단계 뜻: 도착한 대로 적용하면 PAUSE 가 버려지고 PLAY 는 열린 채 남아 12초를 잃는다.
# 도착 순서: 누적 0초 | PAUSE@15 열린 구간이 없어 무시, PLAY@3 구간 열림
# 4단계 뜻: 시각 순서로 정렬하면 1절 기록과 같은 12초가 나온다.
# 시각 순서: 누적 12초 | PLAY@3 구간 열림, PAUSE@15 12초 더함
```

hold 는 늦는 대신 맞게 세는 자리입니다. 2초 안에 도착한 뒤바뀜은 바로잡지만, 그보다 늦게 온 이벤트는 바로잡지 못합니다. 이 처리기는 그런 이벤트가 그 사용자와 영상의 마지막 적용 시각보다 과거이면 버리고, 버린 수를 셉니다. 늦게 온 것까지 다 받으려면 hold 를 늘려야 하고, 그만큼 모든 피처가 늦어집니다.

그래서 hold 는 피처마다 다르게 둡니다. 재생 초나 완주율처럼 두 이벤트의 시각을 빼서 세는 피처는 hold 를 둡니다. 클릭 수처럼 더하기만 하는 피처는 순서가 바뀌어도 합이 같아서 hold 없이 바로 셉니다. 다음은 그렇게 센 값이 Redis 에 어떤 모양으로 남는지입니다.

## 4. Redis 에는 다시 만들 수 있는 값만 둡니다

**처리기는 Redis 의 Hash 필드 몇 개만 고칩니다. PAUSE 한 건으로 playtime_sec 은 0 에서 12 로, events 는 2 에서 3 으로 바뀌었습니다.**

Redis 는 값을 메모리에 두는 키-값 저장소입니다. 이 실습 환경은 사용자와 영상 한 쌍마다 키 하나를 둡니다. u42 와 v7 의 키는 feat:user:u42:video:v7 이고, 자료형은 Hash 입니다. Hash 는 키 하나 안에 필드 여러 개를 두고, 필드 하나만 따로 고칠 수 있는 자료형입니다.

아래 표는 PAUSE 한 건을 보내기 직전과 적용한 뒤에 같은 키를 읽은 값입니다. Redis 는 값을 글자로 들고 있어서 숫자도 글자입니다.

| 필드 | 뜻 | 보내기 전 | 적용한 뒤 |
|---|---|---|---|
| playtime_sec | 누적 재생 초 | 0 | 12 |
| completed | 완주. 1 이면 END 까지 봄 | 0 | 0 |
| open_play_ts | 열린 PLAY 의 시각 | 1793436819 | (빈 값) |
| last_ts | 마지막으로 적용한 이벤트 시각 | 1793436819 | 1793436831 |
| events | 적용한 이벤트 수 | 2 | 3 |

같은 이벤트로 바뀌는 키가 셋 더 있습니다. viewers:v7 은 이 영상을 본 사용자 집합(Set)이고, rank:videos 는 영상별 누적 재생 초 순위(ZSet)입니다. dedupe: 로 시작하는 키는 TTL 300초짜리 중복 표시(String)입니다. 앱이 같은 event_id 를 다시 보내면 처리기가 이 표시를 보고 버립니다. 마지막 END 까지 적용한 뒤 u42 의 누적 재생 초는 30, completed 는 1 이었습니다.

API 가 이 Hash 를 읽는 데 걸린 시간은 0.2ms 였고, 이것이 Redis 를 쓰는 이유입니다. 모델 서버 앞의 API 는 요청마다 피처 수십 개를 읽어야 하고, 한 번에 1ms 를 넘기면 예산이 모자랍니다. 대신 메모리라서 Redis 가 꺼지면 값이 사라질 수 있습니다.

그래서 Redis 에는 Kafka 의 이벤트로 다시 만들 수 있는 값만 둡니다. 커밋한 offset 을 처음으로 되돌리고 보관 기간 안의 이벤트를 다시 읽으면 같은 값이 다시 찹니다. 보관 기간을 넘긴 이벤트는 데이터 레이크에서 가져와야 하므로, 다시 만드는 데 걸리는 시간이 Redis 를 잃었을 때의 복구 시간입니다. 다음 절은 Redis 대신 처리기가 멈췄을 때입니다.

## 5. 처리기가 멈추면 lag 이 자라고, 다시 켜면 따라잡습니다

**lag 은 Kafka 의 끝 offset 에서 처리기가 커밋한 offset 을 뺀 수입니다. 처리기를 12초 멈추자 80 에서 552 로 자랐고, 다시 켜고 2초 뒤 80 으로 돌아왔습니다.**

lag 은 원어로 consumer lag 이라고 부르고, 「아직 처리하지 않은 메시지 수」입니다. partition 마다 끝 offset 에서 커밋한 offset 을 빼고 넷을 더합니다. 이 실습에서는 사용자 40명이 영상 다섯 편을 보는 이벤트를 초당 40건씩 28초 동안 보냈습니다. 6초에 처리기를 멈추고 18초에 다시 켰습니다. 그동안 0.5초마다 lag 과 영상 v11 의 누적 재생 초를 읽었습니다.

| 기록 시각 | 처리기 | lag | v11 누적 재생 초 |
|---|---|---|---|
| 5초 | 도는 중 | 80 | 9 |
| 8초 | 멈춤 | 80 | 25 |
| 14초 | 멈춤 | 312 | 25 |
| 20초 | 다시 켠 직후 | 552 | 25 |
| 21초 | 도는 중 | 80 | 75 |
| 27.6초 | 도는 중 | 80 | 103 |

평소의 lag 이 0 이 아니라 80 인 것은 hold 때문입니다. 처리기는 적용한 뒤에 커밋하므로, 초당 40건 × 2초만큼은 늘 커밋 전입니다. 멈춘 직후 2초는 처리기가 이미 읽어 들고 있던 80건을 마저 적용해 lag 이 그대로입니다. 그 뒤로는 lag 이 1초에 40씩 늘었고, 그동안 v11 의 누적 재생 초는 25 에서 멈춰 있었습니다.

다시 켠 처리기는 커밋한 offset 부터 쌓인 메시지를 한꺼번에 읽었습니다. 읽은 것을 2초 들고 있다가 적용하자 lag 은 80 으로 돌아왔고, v11 은 75 로 따라잡았습니다. 마지막 장면인 27.6초까지 보낸 이벤트는 1,096건이고 적용한 이벤트는 1,016건입니다. 차이 80건은 그 순간 처리기가 들고 있던 몫이라 잃은 이벤트는 없습니다. 아래 그림에서 재생을 누르면 partition 넷의 막대와 두 선이 같이 움직입니다.

## 6. 읽는 길은 ms 단위입니다

**같은 실습 환경에서 피처를 읽어 추천 점수를 내는 요청 한 건은 5.2ms 였습니다. CPU 가 일한 시간은 0.85ms 이고 나머지는 Redis 와 모델 서버를 기다린 시간입니다.**

응답 시간은 줄에서 기다린 시간, CPU 가 계산한 시간, 차례로 기다린 I/O 를 더한 것입니다. I/O 는 다른 서버나 디스크에 묻고 답을 기다리는 일입니다. 동시에 보낸 I/O 라면 더하지 않고 가장 긴 하나만 셉니다. 이 요청은 줄이 없는 상태에서 50번 재서 구간마다 가운데 값을 냈습니다.

| 구간 | 걸린 시간 | CPU | 기다림 |
|---|---|---|---|
| Redis 를 읽는 다섯 구간 (캐시, 후보 순위, 후보마다 피처, 내 통계, 영상 통계) | 0.89ms | 0.56ms | 0.33ms |
| 피처 행렬과 모델 입력 JSON 만들기 | 0.26ms | 0.25ms | 0.01ms |
| 모델 서버 왕복 | 3.99ms | 0ms | 3.99ms |
| 답을 풀고 정렬해 응답 만들기 | 0.04ms | 0.03ms | 0ms |

모델 서버 왕복 한 번이 전체의 77% 입니다. 그 안에는 네트워크 왕복, 모델 서버가 요청을 모아 한 번에 계산하려고 기다리는 시간, 그쪽의 계산이 다 들어 있습니다. 같은 컴퓨터 안의 Redis 왕복은 0.1ms 남짓이고, 그것도 절반 넘게 파이썬 쪽 CPU 입니다. 서버가 다른 기계에 있으면 왕복마다 네트워크 시간이 더해집니다. 같은 데이터센터 안의 왕복이 보통 0.5ms 안팎이라, 다섯 구간의 왕복 여섯 번이면 3ms 쯤 늘어납니다.

쓰는 길과 읽는 길은 서로를 기다리지 않습니다. 추천 요청은 Redis 에 지금 있는 값을 읽고 끝나며, 처리기가 2초 뒤에 그 값을 고칩니다. 그래서 두 길의 예산은 따로 세워, 쓰는 길은 「몇 초 늦어도 되나」로, 읽는 길은 「몇 ms 안에 답하나」로 적습니다.

이 요청을 줄이려면 Redis 왕복보다 모델 서버를 먼저 봅니다. 기다리는 시간의 대부분이 거기 있고, 그중 배칭 대기는 설정 하나로 줄어듭니다. 같은 환경에서 모델 서버 구간이 2ms 아래로 내려가기도 하고 9ms 를 넘기도 했습니다. 모델 서버가 최근 요청을 보고 배칭 대기를 스스로 바꾸기 때문입니다.

## 7. 담장 안과 열린 RTB 는 key 와 늦게 오는 이벤트가 다릅니다

**다섯 자리의 구조는 두 무대가 같습니다. 다른 것은 Kafka 의 key 로 쓸 식별자가 얼마나 안정적인가와, 이벤트가 얼마나 늦게 오는가입니다.**

### 담장 안에서는 로그인 ID 가 key 입니다 [무대: 닫힌 생태계]

담장 안 플랫폼은 앱과 광고 서버와 로그를 다 가집니다. 재생 이벤트는 우리 앱이 우리 API 로 보내고, key 는 로그인한 회원 번호입니다. 회원 번호는 기기를 바꿔도 같아서 한 사람의 이벤트가 늘 한 partition 에 모입니다. 이벤트도 대부분 몇 초 안에 도착해서, 2초 hold 로 뒤바뀜 대부분을 바로잡습니다.

Kafka 의 보관 기간 안이면 처리기를 고친 뒤 커밋 offset 을 되돌려 지난 이벤트를 다시 셀 수 있습니다. 피처 정의를 바꿨을 때 지난 일주일 치를 새 정의로 다시 세는 일이 여기서 가능합니다.

### 열린 RTB 에서는 이벤트가 남의 서버를 거쳐 늦게 옵니다 [무대: 열린 RTB]

DSP 의 노출과 클릭과 재생 이벤트는 매체의 페이지나 앱에서 추적 요청으로 오거나, 거래소를 거쳐 들어옵니다. 여러 서버를 거치는 만큼 늦게 오거나 순서가 바뀌는 이벤트가 많고, 같은 사용자의 이벤트도 쿠키나 기기 ID 가 바뀌면 다른 key 가 됩니다. 2초 hold 로는 바로잡을 수 없는 뒤바뀜이 많습니다.

그래서 열린 RTB 의 실시간 피처는 순서에 덜 기대는 꼴로 만듭니다. 구간을 빼서 세는 재생 초 대신 진행 추적 이벤트를 세는 식입니다. 동영상 광고 표준 VAST 는 25%, 50%, 75%, 완료 지점에 닿을 때마다 이벤트를 하나씩 보냅니다. 늦게 온 이벤트는 버리지 않고 다음 배치에서 고칩니다. 실시간 값은 빠른 어림이고, 정확한 값은 배치가 맞춥니다.

## 한눈 정리

| 자리 | 하는 일 | 이 실습에서 잰 값 | 결정할 것 |
|---|---|---|---|
| API | 이벤트를 받아 Kafka 에 넘긴다 | Kafka 응답 1.2ms | key 로 무엇을 쓸지 |
| Kafka | partition 과 offset 을 주고 보관한다 | partition 넷, u42 는 모두 3번 | partition 수, 보관 기간 |
| 처리기 | hold 동안 모아 시각 순서로 적용한다 | 적용까지 2,029~2,042ms | 피처마다 hold 길이 |
| Redis | Hash 필드를 고친다 | 읽기 0.2ms | 다시 만들 수 있는 값만 둔다 |
| lag | 끝 offset 에서 커밋 offset 을 뺀 수 | 평소 80, 12초 멈춤에 552 | 알람 문턱 |
| 읽는 길 | 피처를 읽어 점수를 낸다 | 5.2ms, 모델 서버 77% | 모델 서버의 배칭 대기 |

## 헷갈리기 쉬운 점

- **Kafka 가 지켜 주는 순서는 도착 순서입니다.** 사용자가 누른 순서가 아닙니다. 누른 순서는 이벤트 안의 시각(ts)으로 처리기가 정렬해 되찾습니다.
- **평소의 lag 은 0 이 아닙니다.** 초당 건수 × hold 만큼은 늘 커밋 전입니다. 이 실습에서는 40 × 2 = 80 이었습니다.
- **처리기가 멈춰도 이벤트는 사라지지 않습니다.** Kafka 에 남아 있다가 다시 켜면 커밋한 offset 부터 읽힙니다. 사라지는 것은 보관 기간을 넘긴 경우입니다.
- **hold 는 모든 피처에 같지 않습니다.** 시각을 빼서 세는 피처에만 필요합니다. 더하기만 하는 피처는 순서가 바뀌어도 합이 같습니다.
- **피처의 신선도와 요청의 지연은 다른 숫자입니다.** 이 실습에서 앞은 2초, 뒤는 5.2ms 였습니다. 둘을 한 예산에 넣지 않습니다.
- **Redis 왕복이 느린 것이 아니라 횟수가 문제입니다.** 한 번은 0.1ms 남짓이지만 후보마다 따로 물으면 후보 수만큼 늘어납니다. 그래서 명령을 묶어 한 번에 보냅니다.
