지훈 씨의 아홉째 주입니다. 분석 팀이 새 pCVR 모델을 실험용으로 만들어 왔습니다. 아직 광고에 쓰지는 않고, 운영자가 쓰는 내부 화면에서 예측값을 먼저 확인하려고 합니다. 요청은 초당 40건 정도라고 했습니다.

지훈 씨는 지난주에 팀의 추론 서버 코드를 읽었습니다. 모델 파일을 메모리에 올리는 코드가 있었고, 더미 요청으로 웜업하는 코드가 있었습니다. readiness probe 에 답하는 코드, 후보를 텐서 하나로 만드는 코드, 두 모델 버전 사이에서 트래픽을 옮기는 코드도 있었습니다. 이 작은 실험용 모델에도 그것을 다 새로 만들어야 하는지 궁금했습니다.

선배는 이렇게 답했습니다. 「그건 BentoML 로 띄우면 하루면 됩니다. 다만 메인 pCTR 서버는 BentoML 을 쓰지 않습니다.」

**같은 팀에서 왜 어떤 모델은 BentoML 로 띄우고, 어떤 모델은 서버를 직접 짤까요?**

BentoML 은 학습한 모델 파일을 HTTP API 서버로 만들어 주는 파이썬 라이브러리입니다. 이런 도구를 모델 서빙 프레임워크라고 부릅니다. 같은 종류로 TorchServe, Triton Inference Server, Ray Serve 가 있습니다. 이 글은 BentoML 이 서버 코드의 어느 부분을 대신 만들어 주는지 봅니다. 그리고 응답 시간이 빠듯한 자리에서는 왜 쓰지 않는지를 숫자로 봅니다.

> **한 줄 요약:** 직접 짠 추론 서버의 기능 일곱 가지 가운데 넷은 BentoML 이 만들어 줍니다. HTTP 엔드포인트, 모델 로딩, readiness probe, 메트릭입니다. 웜업은 몇 줄을 직접 넣고, 버전 전환은 도커 이미지를 바꿔 배포하는 일이 됩니다. 입력 변환은 계속 직접 씁니다. 대신 HTTP 요청을 파이썬이 처리해서 요청마다 약 1.7ms 의 오버헤드가 붙습니다. 모델 호출에 8ms 까지 쓸 수 있는 메인 pCTR 서빙에서는 8ms 를 넘는 요청이 약 3.5% 에서 약 11% 로 세 배가 됩니다. 200ms 까지 쓸 수 있는 내부 화면에서는 둘 다 0% 라 차이가 보이지 않습니다.

> **골라 읽는 법** — 절이 9개인 글입니다. 절마다 카드 한 장이나 표 하나가 있어서 그것만 보고 넘어가도 됩니다.
>
> - 직접 짠 추론 서버의 기능 일곱 가지 → 1절
> - BentoML 서비스 파일 하나 → 2절
> - 모델 저장소와 태그 → 3절
> - Bento 빌드와 도커 이미지 → 4절
> - 동적 배칭이 이득인 경우 → 5절
> - 지연 예산 8ms 에서 파이썬 오버헤드 → 6절
> - 워커 수를 늘리면 바뀌는 것 → 7절
> - 어디에 쓰고 어디에 쓰지 않나 → 8절
> - 담장 안과 열린 RTB → 9절

이 글의 코드 줄 수, 시간, 크기는 전부 설명을 위한 가상 값입니다. 모델 호출에 쓸 수 있는 시간을 지연 예산이라고 부릅니다. 모델 서버 12대, 지연 예산 8ms, 요청 하나에 실린 후보 800건은 [추론 서버](post.html?id=inference-server) 편과 같은 값입니다. 신경망 38MB, 임베딩 표 27.7GB, 서버가 요청을 받을 준비가 되기까지 걸리는 41초도 그 편의 값입니다.

코드는 BentoML 1.2 이후의 API 를 따랐습니다. 버전이 올라가면서 이름과 옵션이 바뀐 적이 있으니, 옮겨 쓰기 전에 쓰는 버전의 문서를 확인합니다. 도커 이미지와 CI 검사는 [Docker 와 CI](post.html?id=container-ci-pipeline) 편에서 이어집니다.

카드 속 색은 넷입니다. 파랑은 저장된 것(모델 파일, 모델 저장소, 이미지)이고, 벽돌색은 들어오는 요청과 비용이 드는 곳입니다. 먹색은 서비스와 서버이고, 회색은 빌드와 배칭 같은 작업입니다.

## 1. 직접 짠 추론 서버에는 기능이 일곱 가지 있습니다

**기능 일곱 가지 가운데 모델마다 달라지는 것은 입력 변환 하나입니다. 나머지 여섯 가지는 어떤 모델을 띄워도 거의 같은 코드입니다.**

지훈 씨가 지난주에 읽은 추론 서버 코드를 기능별로 나누면 일곱 가지입니다. 줄 수는 설명을 위한 가상 값입니다.

| 기능 | 하는 일 | 왜 필요한가 | 줄 수 |
|---|---|---|---|
| HTTP 엔드포인트 | 요청을 받아 예측값을 돌려준다 | 앱과 API 서버가 이 URL 로 모델을 호출한다 | 220 |
| 모델 로딩 | 모델 파일을 열어 메모리에 올린다 | 매일 새벽 새 모델 파일이 나온다 | 180 |
| 입력 변환 | 요청에 실린 후보 800건을 텐서 하나로 만든다 | 800건을 하나씩 호출하면 96ms 가 걸린다 | 260 |
| 웜업(warm-up) | 서버를 띄운 직후 더미 요청을 몇 번 보낸다 | 안 하면 처음 30초 동안 2.5배 느리다 | 90 |
| readiness probe | 「요청 받을 준비 됨」을 알린다 | 게이트웨이는 준비된 서버에만 요청을 보낸다 | 70 |
| 버전 전환 | 두 모델 버전을 함께 띄우고 트래픽을 옮긴다 | 문제가 생기면 몇 초 안에 롤백해야 한다 | 310 |
| 메트릭 | 지연 시간과 오류 수를 내보낸다 | 대시보드와 알람이 이 값을 쓴다 | 240 |

일곱을 더하면 1,370줄입니다. 설정 파일과 테스트까지 합치면 약 1,800줄입니다.

이 가운데 모델마다 달라지는 것은 입력 변환입니다. 요청이 어떤 모양으로 오고 그것을 어떤 텐서로 바꿀지가 모델마다 다르기 때문입니다. 나머지 여섯 가지 1,110줄은 pCTR 모델이든 pCVR 모델이든 거의 같은 모양입니다. 모델을 새로 띄울 때마다 이 여섯 가지를 다시 짜지 않으려고 모델 서빙 프레임워크를 씁니다.

## 2. BentoML 을 쓰면 일곱 가지 가운데 넷은 짜지 않습니다

**BentoML 에서 직접 쓰는 것은 클래스 하나입니다. HTTP 엔드포인트, 모델 로딩, readiness probe, 메트릭은 BentoML 이 만들어 줍니다. 웜업은 몇 줄을 직접 넣고, 버전 전환은 4절의 이미지 배포로 옮겨 갑니다.**

파이썬 파일 하나에 클래스 하나를 두고 데코레이터를 붙입니다. 데코레이터는 함수나 클래스 바로 위에 붙이는 `@...` 줄입니다. 클래스에 `@bentoml.service` 를 붙이면 그 클래스가 서비스 하나가 됩니다. 메서드에 `@bentoml.api` 를 붙이면 그 메서드가 API 엔드포인트, 곧 호출할 수 있는 URL 하나가 됩니다.

```python
# service.py — 이 파일 하나가 BentoML 서비스 하나가 된다.
# 클래스에 붙인 @bentoml.service 가 서비스를 만들고,
# 메서드에 붙인 @bentoml.api 가 API 엔드포인트 하나를 만든다.
import bentoml
import numpy as np
import torch

@bentoml.service(
    resources={"cpu": "2"},            # 이 서비스가 쓰는 CPU
    traffic={"timeout": 30},           # 30초를 넘기는 요청은 끊는다
)
class PcvrPreview:
    def __init__(self) -> None:
        # 모델 저장소에서 태그로 불러온다. 코드에 파일 경로를 적지 않는다.
        self.model = bentoml.pytorch.load_model("pcvr_preview:latest")

    @bentoml.api
    def predict(self, feats: np.ndarray) -> np.ndarray:
        """입력 변환을 거친 피처 배열을 모델에 넣고 확률을 돌려준다."""
        with torch.no_grad():
            return self.model(torch.from_numpy(feats)).numpy()
```

주석까지 21줄입니다. 이 파일에 없는 것을 보면 BentoML 이 하는 일이 보입니다. HTTP 요청을 받는 코드와 지연 시간을 재는 코드가 없습니다. BentoML 이 서비스를 띄우면서 `predict` 를 호출하는 엔드포인트를 만듭니다.

엔드포인트가 몇 개 더 같이 생깁니다. 준비 상태를 알리는 `/readyz`, 프로세스가 살아 있는지 알리는 `/livez`, 메트릭을 내보내는 `/metrics` 입니다. readiness probe 는 `/readyz` 가 맡습니다. 준비 조건을 바꾸고 싶으면 서비스에 `__is_ready__` 메서드를 씁니다. 모델 로딩은 `__init__` 의 한 줄로 줄어듭니다.

나머지 셋은 사정이 다릅니다. 웜업은 BentoML 이 자동으로 하지 않습니다. 모델을 불러온 뒤 더미 입력으로 몇 번 호출하는 코드를 `__init__` 이나 시작 훅(`@bentoml.on_startup`)에 직접 넣습니다. 두 모델 버전 사이에서 트래픽을 옮기는 버전 전환은 BentoML 라이브러리에 없습니다. 모델이 이미지 안에 들어가므로, 버전을 바꾸는 일은 새 이미지를 배포하는 일이 됩니다. 이것은 4절에서 봅니다.

입력 변환은 그대로 직접 씁니다. 요청이 어떤 모양으로 오고 어떤 텐서로 바꿀지는 모델마다 다르기 때문입니다. BentoML 은 그 코드를 부를 자리만 만들어 줍니다.

## 3. 모델은 모델 저장소에 넣고 태그로 불러옵니다

**코드에 파일 경로를 적지 않습니다. 모델을 BentoML 의 모델 저장소(Model Store)에 넣으면 이름과 버전이 붙고, 코드는 그 이름으로 모델을 불러옵니다.**

파일 경로를 코드에 적으면 파일이 옮겨질 때마다 코드를 고쳐야 합니다. 태그로 부르면 파일이 어디 있든 코드는 그대로입니다.

학습이 끝나면 모델을 저장소에 넣습니다. 이름을 주면 버전이 자동으로 하나 붙습니다. 이름과 버전을 합친 `이름:버전` 을 태그라고 부릅니다.

```text
$ python save_model.py
Model(tag="pcvr_preview:g7k2mqx4a")            저장 완료

$ bentoml models list
 Tag                          Module           Size      Creation Time
 pcvr_preview:g7k2mqx4a       bentoml.pytorch  41.2 MiB  2026-10-04 04:12:31
 pcvr_preview:f3n9pqw1b       bentoml.pytorch  41.2 MiB  2026-10-03 04:11:58
```

코드에 `pcvr_preview:latest` 라고 적으면 가장 최근 버전을 불러옵니다. 특정 버전으로 고정하려면 `pcvr_preview:f3n9pqw1b` 처럼 적습니다. 모델만 이전 버전으로 되돌리려면 이 한 줄을 바꿔 다시 빌드합니다. 모델이 이미지 안에 들어가기 때문이고, 이것은 4절에서 봅니다.

모델 저장소는 [모델 버전과 재현](post.html?id=model-versioning-reproducibility) 편의 모델 레지스트리와 비슷해 보이지만 담는 것이 다릅니다. BentoML 의 모델 저장소는 모델 파일과 그 버전을 담습니다. 레지스트리는 그 모델을 어떤 데이터와 코드로 만들었고 지금 어떤 상태인지를 담습니다.

실무에서는 둘을 같이 씁니다. 레지스트리가 「v417 이 운영 중이다」라고 기록하고, 모델 저장소가 그 v417 의 파일을 갖고 있습니다.

주의할 것이 하나 있습니다. 모델 저장소에 들어가는 것은 모델 파일뿐입니다. 신경망 38MB 는 들어가지만 임베딩 표 27.7GB 는 들어가지 않습니다. 그 표는 여전히 임베딩 서비스 한 곳에 있고, 서비스가 요청마다 필요한 행만 가져옵니다. 그 이유는 [추론 서버](post.html?id=inference-server) 편에 있습니다.

## 4. Bento 로 빌드하면 도커 이미지 한 장이 됩니다

**`bentoml build` 는 서비스 코드, 모델 파일, 의존 라이브러리 목록을 하나로 패키징합니다. 이 패키지를 Bento 라고 부릅니다. Bento 를 도커 이미지로 바꾸면 앞 편의 배포 파이프라인에 그대로 올릴 수 있습니다.**

무엇을 담을지는 `bentofile.yaml` 파일 하나에 적습니다.

```yaml
# bentofile.yaml — Bento 에 무엇을 담을지 적는다
service: "service.py:PcvrPreview"      # 어느 파일의 어느 클래스가 서비스인가
include:
  - "service.py"
  - "features.py"                      # 입력 변환 코드
python:
  requirements_txt: "./requirements.txt"
models:
  - "pcvr_preview:latest"              # 이 태그의 모델 파일을 같이 담는다
docker:
  python_version: "3.11"
```

명령 두 줄이면 이미지가 나옵니다. `bentoml build` 가 Bento 를 만들고, `bentoml containerize` 가 그것을 도커 이미지로 바꿉니다.

```text
$ bentoml build
Successfully built Bento(tag="pcvr_preview:h4d8rn2xc")

$ bentoml containerize pcvr_preview:h4d8rn2xc
Successfully built docker image "pcvr_preview:h4d8rn2xc"    1.4GB
```

[Docker 와 CI](post.html?id=container-ci-pipeline) 편에서 본 이미지가 바로 이것입니다. 다만 이미지 구성이 조금 다릅니다. 직접 짠 추론 서버의 이미지는 1.1GB 이고, 모델 파일이 이미지 밖에 있었습니다. BentoML 이 만든 이미지는 1.4GB 이고, 모델 파일이 안에 들어 있습니다.

이 차이로 두 가지가 달라집니다. 첫째, 모델만 바꾸려 해도 이미지를 다시 빌드해야 합니다. 매일 새 모델이 나오는 pCTR 서버라면 매일 새 이미지가 생깁니다. 버전 전환과 롤백도 서버 안에서 모델을 바꿔 끼우는 대신, 이미지 태그를 바꿔 다시 배포하는 일이 됩니다.

둘째, 재현이 쉽습니다. 이미지 하나에 그때의 코드, 모델, 라이브러리가 그대로 들어 있습니다.

모델이 자주 바뀌는 서비스라면 모델을 이미지 밖에 두는 쪽이 낫습니다. 드물게 바뀌는 서비스라면 이미지 안에 담는 쪽이 재현에 유리합니다.

## 5. 동적 배칭은 요청이 작을 때만 이득입니다

**여러 요청을 잠깐 모아 한 번에 추론하는 기능을 동적 배칭(dynamic batching)이라고 부릅니다. BentoML 문서의 이름은 adaptive batching 입니다. `@bentoml.api` 에 옵션 몇 개를 주면 켜지지만, 이득을 보는 경우는 좁습니다.**

배치로 묶으면 건당 계산이 줄어듭니다. 대신 요청이 모이기를 기다리는 시간이 붙습니다. 요청 하나가 이미 크면 줄어드는 계산은 거의 없고 기다리는 시간만 남습니다.

켜는 것은 데코레이터 한 줄입니다. 배치 최대 크기와 최대 지연 시간을 같이 적습니다.

```python
    @bentoml.api(batchable=True, max_batch_size=32, max_latency_ms=2)
    def predict(self, feats: np.ndarray) -> np.ndarray:
        with torch.no_grad():
            return self.model(torch.from_numpy(feats)).numpy()
```

세 경우를 놓고 세어 봅니다. 추론 시간은 고정 0.116ms 에 후보 한 건당 0.0036ms 가 더해진다고 놓습니다. 이것은 [추론 서버](post.html?id=inference-server) 편의 값입니다. 요청은 푸아송 과정으로 들어오고, 2ms 가 지나거나 32건이 모이면 한 번에 보낸다고 놓습니다.

```python
# 동적 배칭(요청 여러 개를 모아 한 번에 추론)이 언제 이득인지 센다.
# 얻는 것은 건당 계산이 줄어드는 몫이고, 드는 것은 요청이 모이기를 기다리는 시간이다.
# 추론 시간 = 고정 0.116ms + 후보 한 건당 0.0036ms (추론 서버 편의 값).
# 요청은 푸아송 과정으로 들어오고, 2ms 가 지나거나 32건이 모이면 보낸다. 전부 가상 값이다.
import random

FIXED, PER = 0.116, 0.0036
WINDOW, MAXB, N = 2.0, 32, 60_000

def run(qps, cand):
    """cand 는 요청 하나에 실려 오는 후보 수. 평균 배치 크기와 평균 대기를 돌려준다."""
    random.seed(4104)
    lam = qps / 1000.0
    waits, sizes, done = [], [], 0
    while done < N:
        t, n, arrivals = 0.0, 1, [0.0]
        while n < MAXB:
            gap = random.expovariate(lam)
            if t + gap > WINDOW:
                break
            t += gap; n += 1; arrivals.append(t)
        close = t if n == MAXB else WINDOW
        waits += [close - a for a in arrivals]
        sizes.append(n); done += n
    size = sum(sizes) / len(sizes)
    return size, sum(waits) / len(waits)

print('경우 / 배치 크기 / 대기 / 건당 계산 (하나씩 → 배치) / 판정')
for name, qps, cand in [('내부 화면 40 QPS, 요청에 후보 1건', 40, 1),
                        ('내부 화면 2,000 QPS, 후보 1건', 2000, 1),
                        ('광고 서빙 2,639 QPS, 후보 800건', 2639, 800)]:
    size, wait = run(qps, cand)
    alone = FIXED + PER * cand                      # 하나씩 보낼 때 건당
    batched = (FIXED + PER * cand * size) / size    # 배치로 보낼 때 건당
    cut = (1 - batched / alone) * 100
    verdict = '이득이 크다' if cut > 40 else '거의 안 줄어든다' if cut < 10 else '반반이다'
    print(f'  {name}')
    print(f'    배치 {size:.1f}건, 대기 {wait:.2f}ms, 건당 {alone:.3f} → {batched:.3f}ms '
          f'({cut:.0f}% 절감) — {verdict}')

print('\n요청 하나가 이미 크면 배치로 묶어도 건당 계산이 거의 안 줄어든다. 대기만 붙는다')
print('요청 하나가 작고 지연 예산이 넉넉할 때만 동적 배칭이 이득이다')

# 출력:
# 경우 / 배치 크기 / 대기 / 건당 계산 (하나씩 → 배치) / 판정
#   내부 화면 40 QPS, 요청에 후보 1건
#     배치 1.1건, 대기 1.93ms, 건당 0.120 → 0.111ms (7% 절감) — 거의 안 줄어든다
#   내부 화면 2,000 QPS, 후보 1건
#     배치 5.0건, 대기 1.20ms, 건당 0.120 → 0.027ms (78% 절감) — 이득이 크다
#   광고 서빙 2,639 QPS, 후보 800건
#     배치 6.3건, 대기 1.16ms, 건당 2.996 → 2.899ms (3% 절감) — 거의 안 줄어든다
#
# 요청 하나가 이미 크면 배치로 묶어도 건당 계산이 거의 안 줄어든다. 대기만 붙는다
# 요청 하나가 작고 지연 예산이 넉넉할 때만 동적 배칭이 이득이다
```

첫 경우는 요청이 드물어서 배치가 평균 1.1건입니다. 모을 요청이 거의 없는데 2ms 를 기다리느라 대기만 1.93ms 붙습니다.

둘째 경우는 요청이 자주 오고 요청 하나가 작습니다. 배치로 묶으면 건당 계산이 78% 줄어듭니다. 동적 배칭이 이득인 것은 이런 경우입니다.

셋째 경우가 광고 서빙입니다. 요청 하나에 이미 후보 800건이 실려 있습니다. 6건을 묶으면 후보 4,800건짜리 텐서 하나가 됩니다. 줄어드는 것은 고정 오버헤드 0.116ms 를 여러 요청이 나눠 갖는 몫뿐이라, 건당 계산은 3% 만 줄어듭니다. 그 3% 를 위해 대기 1.16ms 가 붙습니다.

메인 pCTR 서빙의 지연 예산은 8ms 이고, 대기 1.16ms 는 그 15% 입니다.

## 6. 지연 예산 8ms 에서는 파이썬 오버헤드가 큽니다

**추론 계산은 두 서버가 같습니다. 다른 것은 HTTP 요청을 받아 모델에 넘기고 응답을 돌려주는 서빙 코드입니다. 이 코드를 파이썬이 처리하면 요청마다 오버헤드가 붙고, 가끔 지연이 크게 늘어납니다.**

BentoML 이 만들어 주는 서빙 코드는 파이썬으로 짜여 있습니다. 그래서 요청마다 파이썬 코드를 지나는 시간이 조금씩 더해집니다. 지연 예산이 넉넉하면 이 시간이 보이지 않고, 빠듯하면 바로 보입니다.

같은 모델을 두 방식으로 서빙했다고 놓고 요청 20만 건의 시간을 뽑습니다. 추론 계산은 양쪽 모두 평균 2.80ms 로 같게 두고, 서빙 코드의 오버헤드만 다르게 놓습니다. 파이썬 쪽은 지연 스파이크도 더 자주 생긴다고 놓습니다. 가비지 컬렉션(GC, 쓰지 않는 메모리를 정리하는 일)이 요청 처리 중에 끼어드는 경우입니다.

```python
# 같은 모델을 두 방식으로 서빙했을 때 요청 한 건에 드는 시간을 뽑는다.
# 추론 계산은 둘이 같다. 다른 것은 그 앞뒤에서 HTTP 요청을 처리하는 서빙 코드다.
# 직접 짠 서버는 컴파일된 코드가, BentoML 서버는 파이썬이 서빙 코드를 맡는다.
# 수치는 전부 가상 값이고 시드를 고정해 누가 돌려도 같은 값이 나온다.
import random

N = 200_000
INFER_MU, INFER_SD = 2.80, 0.45      # 추론 계산 자체 (후보 800건을 텐서 하나로)
JITTER_P, JITTER_MU = 0.15, 3.5      # 가끔 생기는 지연 스파이크 — GC, 다른 요청과 겹침

def draw(fixed, extra_p, extra_mu):
    """서빙 오버헤드 + 추론 + 지연 스파이크. extra 는 파이썬 서빙 코드에서 더 자주 생기는 스파이크다."""
    t = fixed + max(0.4, random.gauss(INFER_MU, INFER_SD))
    if random.random() < JITTER_P:
        t += random.expovariate(1 / JITTER_MU)
    if random.random() < extra_p:
        t += random.expovariate(1 / extra_mu)
    return t

def stats(name, fixed, extra_p, extra_mu):
    random.seed(4104)
    xs = sorted(draw(fixed, extra_p, extra_mu) for _ in range(N))
    p50, p99 = xs[N // 2], xs[int(N * 0.99)]
    return name, p50, p99, sum(1 for x in xs if x > 8) / N * 100, sum(1 for x in xs if x > 200) / N * 100

rows = [stats('직접 짠 서버', 0.12, 0.0, 1.0),
        stats('BentoML 서버', 1.80, 0.09, 6.0)]

print('서버 / p50 / p99 / 8ms 초과 / 200ms 초과')
for n, p50, p99, o8, o200 in rows:
    print(f'  {n}  {p50:.2f}ms  {p99:.2f}ms  {o8:.2f}%  {o200:.2f}%')

print(f'\n지연 예산 8ms: 초과율이 {rows[0][3]:.2f}% 에서 {rows[1][3]:.2f}% 로 {rows[1][3] / rows[0][3]:.1f}배')
print(f'지연 예산 200ms: 둘 다 {rows[1][4]:.2f}% 다. 예산이 넉넉하면 이 차이가 안 보인다')
print(f'파이썬 서빙 코드가 더하는 오버헤드 {1.80 - 0.12:.2f}ms 는 예산 8ms 의 {(1.80 - 0.12) / 8 * 100:.0f}% 다')

# 출력:
# 서버 / p50 / p99 / 8ms 초과 / 200ms 초과
#   직접 짠 서버  3.01ms  12.64ms  3.53%  0.00%
#   BentoML 서버  4.75ms  20.08ms  10.69%  0.00%
#
# 지연 예산 8ms: 초과율이 3.53% 에서 10.69% 로 3.0배
# 지연 예산 200ms: 둘 다 0.00% 다. 예산이 넉넉하면 이 차이가 안 보인다
# 파이썬 서빙 코드가 더하는 오버헤드 1.68ms 는 예산 8ms 의 21% 다
```

8ms 를 넘는 요청은 3.53% 에서 10.69% 로 세 배가 됩니다. 200ms 를 넘는 요청은 둘 다 0.00% 입니다. 같은 BentoML 서버가 메인 pCTR 서빙에는 맞지 않고, 내부 화면에서는 아무 문제가 없습니다.

세 배가 되는 이유는 둘입니다. 첫째, 오버헤드 1.68ms 가 지연 예산 8ms 의 21% 를 먼저 씁니다. 둘째, 파이썬 쪽은 지연 스파이크가 더 잦아서 p99 가 12.64ms 에서 20.08ms 로 늘어납니다.

p99 는 요청 시간을 짧은 순으로 늘어놓았을 때 99% 지점의 값이고, p50 은 가운데 값입니다. 두 서버는 p50 이 1.74ms 차이인데 p99 는 7.44ms 차이입니다. 예산을 넘기는 것은 가운데가 아니라 느린 쪽 꼬리입니다. 이 성질은 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편에서 본 것과 같습니다.

지훈 씨 팀은 지연 예산에서 오버헤드가 차지하는 비율을 먼저 잽니다. 그 비율이 20% 를 넘으면 BentoML 을 쓰지 않습니다. 파이썬 프로세스를 여러 개 띄우면 해결되는지는 7절에서 봅니다.

## 7. 워커를 늘리면 처리량이 늘고 한 건의 지연은 그대로입니다

**BentoML 에는 파이썬 프로세스를 여러 개 띄우는 방법이 셋 있습니다. 셋 다 처리량(초당 처리 건수)을 늘립니다. 요청 한 건의 지연은 줄이지 못합니다.**

파이썬은 한 프로세스 안에서 한 번에 한 스레드만 파이썬 코드를 실행합니다. 이 제약을 GIL(Global Interpreter Lock)이라고 부릅니다. 그래서 코어가 8개여도 프로세스 하나로는 코어 하나만 씁니다. BentoML 에는 이 제약을 넘는 방법이 셋 있습니다.

| 방식 | 무엇을 하나 | 어디에 효과가 있나 |
|---|---|---|
| 워커 프로세스 여러 개 | 서비스 하나를 파이썬 프로세스 여러 개로 띄운다. 서비스에 워커 수를 적고, 코어 수에 맞추는 설정도 있다 | 코어를 다 쓴다. 처리량을 늘리는 가장 기본 방법이다 |
| 서비스를 여러 개로 나누기 | 입력 변환 서비스와 모델 서비스를 따로 정의하고 한쪽이 다른 쪽을 호출한다. 각각 자기 프로세스로 돈다 | 가벼운 쪽과 무거운 쪽의 워커 수를 따로 정한다 |
| 비동기 API 함수 | API 함수를 `async` 로 쓰면 워커 하나가 여러 요청을 번갈아 처리한다 | 외부 응답을 기다리는 시간에만 효과가 있다. 계산에는 효과가 없다 |

첫째가 가장 자주 쓰는 방법입니다. 서비스 데코레이터에 워커 수를 한 줄 적습니다.

```python
@bentoml.service(
    workers=4,                         # 파이썬 프로세스를 4개 띄운다
    resources={"cpu": "4"},
)
class PcvrPreview:
    ...
```

둘째는 서비스를 나누는 것입니다. 요청을 텐서로 바꾸는 입력 변환은 가볍고 모델 계산은 무겁습니다. 둘을 한 서비스에 두면 같은 수로만 늘릴 수 있습니다. 나눠 두면 입력 변환은 2개, 모델은 6개처럼 따로 정할 수 있습니다.

이전 버전에는 이 기능이 Runner 라는 이름으로 따로 있었습니다. 1.2 버전부터 서비스를 여러 개 두는 방식으로 바뀌었습니다. 찾아본 예제가 Runner 를 쓰고 있으면 이전 버전의 문법입니다.

셋째는 기다리는 시간에만 효과가 있습니다. 피처 스토어에서 값을 읽어 오는 것처럼 외부 응답을 기다리는 동안 다른 요청을 처리합니다. 계산만 하는 함수에는 효과가 없습니다.

첫째를 숫자로 재 봅니다. 서버 한 대에 들어오는 요청은 초당 220건입니다. 요청 한 건의 처리 시간은 6절에서 뽑은 BentoML 서버의 p50 4.75ms 입니다.

```python
# 워커(파이썬 프로세스) 수를 늘리면 무엇이 바뀌고 무엇이 그대로인가.
# 요청 한 건의 처리 시간은 앞 절에서 뽑은 값 그대로 두고, 워커 수만 바꿔 가며
# 서버 한 대의 최대 처리량과 대기 시간을 센다.
# 대기행렬 이론의 간단한 모형(M/M/c)으로 근사한다. 전부 가상 값이다.
import math

QPS_PER_SERVER = 2639 / 12          # 서버 12대가 나눠 받는 요청 (건/초)
SERVICE_MS = 4.75                   # BentoML 서버의 요청 한 건 p50
OVERHEAD_MS = 1.68                  # 그중 파이썬 서빙 코드가 더하는 오버헤드

def erlang_c(c, a):
    """워커 c 개에 부하 a 일 때 요청이 대기열에 서게 될 확률."""
    s = sum(a ** k / math.factorial(k) for k in range(c))
    last = a ** c / math.factorial(c) * (c / (c - a))
    return last / (s + last)

print('워커 / 최대 처리량 / 부하율 / 대기 시간 / 한 건의 처리 시간')
mu = 1000 / SERVICE_MS              # 워커 하나가 초당 처리하는 건수
for c in (1, 2, 4, 8, 16):
    cap = mu * c
    rho = QPS_PER_SERVER / cap
    if rho >= 1:
        print(f'  {c:>2}개  {cap:7.0f} 건/초  부하율 {rho:.2f}  대기열이 계속 쌓인다')
        continue
    a = QPS_PER_SERVER / mu
    wq = erlang_c(c, a) / (c * mu - QPS_PER_SERVER) * 1000 if c > a else float('inf')
    print(f'  {c:>2}개  {cap:7.0f} 건/초  부하율 {rho:.2f}  {wq:6.3f}ms 대기  '
          f'처리 시간은 그대로 {SERVICE_MS:.2f}ms')

need = math.ceil(QPS_PER_SERVER / mu / 0.77)
print(f'\n부하율을 0.77 아래로 두려면 워커 {need}개면 되는데, 그때 대기가 1.78ms 붙는다')
print('4개로 늘리면 대기가 0.04ms 로 거의 사라지고, 그 뒤로는 늘려도 얻을 것이 없다')
print(f'바뀌지 않는 것 둘 — 한 건의 처리 시간 {SERVICE_MS:.2f}ms 와 그 안의 오버헤드 {OVERHEAD_MS:.2f}ms')
print('그래서 8ms 초과율 10.69% 는 워커를 몇 개로 늘려도 그대로다')

# 출력:
# 워커 / 최대 처리량 / 부하율 / 대기 시간 / 한 건의 처리 시간
#    1개      211 건/초  부하율 1.04  대기열이 계속 쌓인다
#    2개      421 건/초  부하율 0.52   1.782ms 대기  처리 시간은 그대로 4.75ms
#    4개      842 건/초  부하율 0.26   0.038ms 대기  처리 시간은 그대로 4.75ms
#    8개     1684 건/초  부하율 0.13   0.000ms 대기  처리 시간은 그대로 4.75ms
#   16개     3368 건/초  부하율 0.07   0.000ms 대기  처리 시간은 그대로 4.75ms
#
# 부하율을 0.77 아래로 두려면 워커 2개면 되는데, 그때 대기가 1.78ms 붙는다
# 4개로 늘리면 대기가 0.04ms 로 거의 사라지고, 그 뒤로는 늘려도 얻을 것이 없다
# 바뀌지 않는 것 둘 — 한 건의 처리 시간 4.75ms 와 그 안의 오버헤드 1.68ms
# 그래서 8ms 초과율 10.69% 는 워커를 몇 개로 늘려도 그대로다
```

부하율(utilization)은 워커가 요청을 처리하느라 바쁜 시간의 비율입니다. 워커 1개면 부하율이 1.04 라 대기열이 계속 쌓입니다. 4개면 대기가 0.04ms 로 거의 사라집니다. 한 건의 처리 시간은 워커 수와 상관없이 4.75ms 입니다.

어디서 멈출지도 이 출력에서 보입니다. 부하율만 보면 워커 2개로 0.52 가 되어 충분해 보입니다. 그런데 그때 대기가 1.78ms 붙습니다. 4개로 늘리면 대기가 0.04ms 가 됩니다.

8개와 16개는 대기가 이미 0 이라 더 얻을 것이 없고 메모리만 더 씁니다. 모델은 워커마다 한 번씩 메모리에 올라가므로, 워커 수만큼 메모리를 씁니다.

그래서 6절의 결론은 그대로입니다. 8ms 초과율 10.69% 는 워커를 몇 개로 늘려도 10.69% 입니다. 그 값은 요청 한 건이 파이썬 서빙 코드를 지나며 붙는 오버헤드에서 나옵니다. 워커 수는 처리량을 바꾸고, 한 건이 예산 안에 끝나는지는 바꾸지 못합니다.

처리량이 모자라면 워커를 늘립니다. 요청 한 건이 지연 예산을 넘으면 서빙 방식을 바꿉니다.

## 8. 어디에 쓰고 어디에 쓰지 않나

**지연 예산, 요청량, 모델 개수 세 가지가 답을 정합니다. 예산이 넉넉하고 모델이 여럿이면 BentoML 이 낫습니다. 예산이 빠듯하고 모델이 하나면 직접 짠 서버가 낫습니다.**

BentoML 은 개발 시간을 줄여 주는 대신 요청마다 오버헤드를 더합니다. 어느 쪽이 더 큰지는 서비스마다 다릅니다.

지훈 씨 팀의 모델을 늘어놓고 세 가지를 물어보면 이렇게 나뉩니다. 아래 값은 전부 가상입니다.

| 어디에 쓰나 | 지연 예산 | 요청량 | 모델 개수 | 무엇을 쓰나 |
|---|---|---|---|---|
| 메인 pCTR 서빙 | 8ms | 초당 2,639건 | 하나 | 직접 짠 서버 |
| 운영자 내부 화면의 pCVR 실험용 모델 | 200ms | 초당 40건 | 실험용 모델 여럿 | BentoML |
| 분석가가 돌리는 배치 추론 | 없음 | 하루 한 번 | 그때마다 다름 | BentoML |
| 광고주 리포트의 예상 전환 | 2초 | 초당 30건 | 둘 | BentoML |
| two-tower retrieval 모델의 유저 타워 | 3ms | 초당 2,639건 | 하나 | 직접 짠 서버 |

가운데 세 줄이 BentoML 이 나은 경우입니다. 셋 다 예산이 밀리초가 아니라 초 단위이거나 아예 없습니다. 모델도 자주 바뀌거나 여럿입니다. 이런 경우에 서버를 직접 짜면 1,800줄을 모델마다 다시 만들게 됩니다.

맨 위와 맨 아래 두 줄이 직접 짠 서버가 나은 경우입니다. 예산이 한 자리 밀리초이고, 요청량이 크고, 모델이 하나입니다. 1,800줄을 짜는 일은 한 번이지만, 1.68ms 의 오버헤드는 초당 2,639건의 요청마다 붙습니다.

둘 중 하나만 고를 필요는 없습니다. 새 모델을 BentoML 로 먼저 띄워 예측값을 확인하고, 광고에 쓰기로 정해지면 그때 직접 짠 서버로 옮길 수 있습니다. 지훈 씨 팀이 하려는 것도 이것입니다.

## 9. 무대가 바뀌면 고르는 기준도 바뀝니다

**지연 예산을 누가 정하는지가 무대마다 다릅니다. 담장 안에서는 광고 플랫폼이 직접 정하고, 열린 RTB 에서는 거래소가 정합니다. 그래서 BentoML 을 쓸 수 있는 범위도 다릅니다.**

### 담장 안에서는 플랫폼이 예산을 나눠 줍니다 [무대: 닫힌 생태계]

한 회사가 앱과 광고 서버를 다 가진 담장 안에서는, 응답 전체에 주어진 시간을 플랫폼이 단계마다 나눠 줍니다. 모델 호출에 8ms 를 준 것도 그 결정입니다. 그래서 어떤 모델은 예산을 넉넉히 받을 수 있습니다.

광고를 고르는 경로에 들어가지 않는 모델이 그렇습니다. 운영자 화면의 실험용 모델, 광고주 리포트의 예상 전환, 하루 한 번 도는 배치 추론이 그 예입니다. 이 셋은 요청이 광고 경매를 지나지 않으므로 예산이 초 단위입니다. 담장 안에는 이런 모델이 많습니다. 자사 데이터로 만드는 내부 도구가 많기 때문입니다.

지훈 씨의 pCVR 실험용 모델도 여기에 해당합니다. BentoML 로 하루면 띄울 수 있고, 예측값을 보다가 광고에 쓰기로 정해지면 그때 옮깁니다. 옮길 때 다시 쓰는 것은 서빙 코드이고, 모델과 입력 변환 코드는 그대로 가져갑니다.

### 열린 RTB 에서는 거래소가 정한 시간 안에 답해야 합니다 [무대: 열린 RTB]

매체와 광고 서버가 다른 회사인 열린 RTB 에서는 입찰 요청에 답하는 시간을 거래소가 정합니다. 흔히 100ms 안쪽이고, 그 안에 네트워크 왕복 시간이 들어 있습니다. 그래서 우리 서버가 쓸 수 있는 시간은 더 짧습니다. 늦으면 그 입찰은 버려집니다.

그래서 입찰 경로에 있는 모델은 BentoML 로 띄우기 어렵습니다. 서버가 쓸 수 있는 시간이 짧을수록 오버헤드 1.68ms 가 차지하는 비율이 커집니다. 게다가 거래소마다 시간이 달라 가장 빠듯한 곳에 맞춰야 합니다.

대신 이 무대에도 BentoML 을 쓸 곳이 있습니다. 입찰 경로 밖에서 도는 것들입니다. 광고주에게 보내는 리포트, 소재 점수를 미리 계산해 두는 배치 추론, 세그먼트를 만드는 작업이 그렇습니다. 무대가 달라도 기준은 같습니다. 지연 예산이 밀리초 단위인지 초 단위인지를 먼저 봅니다.

## 한눈 정리

| 무엇 | 직접 짠 서버 | BentoML 서버 |
|---|---|---|
| 직접 쓰는 코드 | 일곱 기능 전부, 약 1,800줄 | 서비스 파일 21줄과 입력 변환, 웜업 몇 줄 |
| 요청당 서빙 오버헤드 | 0.12ms | 1.80ms |
| p50 과 p99 | 3.01ms, 12.64ms | 4.75ms, 20.08ms |
| 지연 예산 8ms 초과율 | 3.53% | 10.69% |
| 지연 예산 200ms 초과율 | 0.00% | 0.00% |
| 모델 파일이 있는 곳 | 이미지 밖 | 이미지 안 (1.4GB) |
| 버전 전환과 롤백 | 서버 안에서 모델을 바꿔 끼운다 | 이미지 태그를 바꿔 다시 배포한다 |
| 새 모델 하나를 띄우는 데 | 며칠 | 하루 |
| 맞는 경우 | 예산이 한 자리 밀리초, 모델 하나 | 예산이 초 단위, 모델 여럿 |

## 헷갈리기 쉬운 점

**BentoML 이 서버 기능을 전부 만들어 주지는 않습니다.** HTTP 엔드포인트, 모델 로딩, readiness probe, 메트릭은 만들어 줍니다. 입력 변환과 웜업은 직접 쓰고, 두 버전 사이의 트래픽 전환은 배포 환경이 맡습니다.

**BentoML 이 느린 것이 아닙니다.** 추론 계산은 양쪽 모두 2.80ms 로 같습니다. 다른 것은 HTTP 요청을 처리하는 서빙 코드이고, 그 오버헤드가 1.68ms 입니다. 예산이 200ms 면 1.68ms 는 0.8% 라 차이가 드러나지 않습니다.

**가운데 값이 아니라 꼬리가 예산을 넘깁니다.** 두 서버의 p50 차이는 1.74ms 인데 p99 차이는 7.44ms 입니다. p50 만 보고 「2ms 차이면 괜찮다」고 하면 초과율이 세 배가 된 것을 놓칩니다.

**동적 배칭이 늘 이득은 아닙니다.** 요청 하나에 이미 후보 800건이 실려 있으면 묶어도 건당 계산이 3% 만 줄어듭니다. 그 3% 를 위해 대기 1.16ms 가 붙습니다. 요청 하나가 작을 때만 켭니다.

**모델 저장소와 모델 레지스트리는 다릅니다.** BentoML 의 모델 저장소는 모델 파일과 버전을 담습니다. 레지스트리는 모델을 만든 데이터와 코드, 운영 상태를 담습니다. 실무에서는 둘을 같이 씁니다.

**이미지 안에 모델을 담으면 롤백 방법이 바뀝니다.** 모델만 바꾸려 해도 이미지를 다시 빌드해야 합니다. 매일 새 모델이 나오는 서버라면 매일 새 이미지가 생기고, 앞 편에서 본 롤백 한 줄이 이미지 태그 바꾸기가 됩니다.
