파이프라인 조립기

수집 · 버퍼 · 처리 · 유통 · 저장 · 조회. 여섯 층에 부품을 하나씩 놓아 보면 무엇이 취향이고 무엇이 마감에 밀려 어쩔 수 없는지가 갈립니다. 유통 층을 끄면 관리할 연결이 11개에서 30개가 되고, 버퍼를 빼면 버티는 시간이 168시간에서 10.4분이 됩니다.

먼저 보면 좋아요 로그 여섯 층 내려가기 Kafka Partition 놀이터
이 데모가 보여주는 것층마다 부품을 놓거나 비워 둘 수 있습니다. 고르는 대로 계기 넷이 같이 움직입니다 — 대시보드가 보는 지연, 학습 데이터가 준비되는 시각, 한 층이 멈췄을 때 버티는 시간, 사람이 관리할 연결 수입니다. 아래 판정 칸은 그 조합에서 무엇이 먼저 터지는지를 순서대로 적습니다.
왜 알아야 하나부품 이름부터 고르면 반드시 다시 뜯습니다. 먼저 적을 것은 소비자의 마감입니다. 대시보드 마감 2초 하나가 스트림 처리를 강제하고, 목적지 수 하나가 유통 계층을 강제합니다. 취향이 정한 자리는 생각보다 적습니다.
    이렇게 해보세요 — 4분
  1. 기본값(에이전트 tail · Kafka · 스트림+배치 · 유통 켬 · 저장소 셋 · 목적지 6)에서 계기 넷을 봅니다. 대시보드는 1,112 + 800 + 200 = 2,112 ms로 마감 2,000 ms 를 112 ms 넘깁니다.
  2. 수집을 SDK 직행으로 바꿉니다. 도달이 1,112 ms 에서 426 ms 로 줄어 지연이 1,426 ms가 되고 마감 안에 듭니다. 버퍼가 있으니 버티는 시간은 168시간 그대로입니다.
  3. 유통 계층을 끕니다. 연결이 11개에서 30개로, 설정 자리가 44개에서 120개로 뜁니다. 아래 그림의 선이 덧셈에서 곱셈으로 바뀝니다.
  4. 버퍼(Kafka)를 끕니다. 유통 층이 같이 잠기고, 버티는 시간이 168시간에서 61.7시간(에이전트 tail) 또는 10.4분(SDK 직행)으로 떨어집니다. 10.4분은 사람이 붙는 30분보다 짧아 알아채기 전에 샙니다.

규모 — 노출 로그가 하루 2억 2,800만 줄, 초당 2,639건입니다. 그중 클릭은 하루 2,280,000건(기저 CTR 1.0%)입니다.

소비자 넷과 마감 — 실시간 대시보드 2초 · 광고주 리포트 5분 · 학습 데이터 30시간 · 정산 확정 33시간. 마감은 가장 오래된 이벤트로 잽니다. 하루치를 06시에 학습하면 전날 00시 이벤트가 30시간을 기다립니다.

도달 시간 — 탭에서 버퍼까지 에이전트 tail 은 1,112 ms, SDK 직행은 426 ms입니다. 처리는 스트림이 창+처리 800 ms, 1시간 배치가 4,200,000 ms입니다. 유통 층을 거치면 topic 왕복 200 ms가 붙습니다.

연결 세는 법 — 처리 잡이 목적지마다 쓰기 코드를 들면 연결은 잡 × 목적지입니다. 잡이 topic 한 곳에만 쓰고 목적지마다 커넥터를 두면 잡 + 목적지입니다. 연결마다 포맷 · 스키마 · 권한 · 재시도 넷을 정하니 설정 자리는 연결의 4배입니다.

숫자는 전부 설명을 위해 지어낸 값입니다.

수집 층 — 어디서 긁나

파일을 거치면 느리지만 그 파일이 버텁니다. 직행은 빠르지만 버틸 것이 메모리뿐입니다.

버퍼 층 — 며칠 남기나

한 번 쓰고 여럿이 읽는 자리입니다. 유통 층은 이 자리 위에만 설 수 있습니다.

처리 층 — 언제 세나

스트림은 잡 4개, 배치는 3개, 둘 다면 정제·조인을 한 번만 세어 5개입니다.

유통 층 — 어디로 보내나

버퍼가 없으면 이 층을 세울 자리가 없습니다. 읽어 갈 topic 이 없으니 처리 잡이 목적지마다 직접 씁니다.

잡은 ad.*.clean 한 곳에만 쓰고, 목적지별 포맷·재시도는 커넥터가 답니다.

저장 층 — 어떤 포맷으로

켜고 끄면 목적지 수도 같이 움직입니다. 새로 세운 저장소가 목적지 하나입니다.

목적지 수 — 결과가 가야 하는 곳
6

고른 저장소가 앞에 서고, 남는 자리는 리포트용 관계형 DB · 다른 팀 Kafka · 피처 스토어 · 광고주 API · 실험 분석 DB 순으로 채워집니다.

여섯 층 — 지금 세운 것

점선 칸은 비어 둔 층입니다. 굵게 두른 칸은 지금 켜 둔 유통 층입니다. 아래 왼쪽은 대시보드 지연 계산식, 오른쪽은 버티는 시간과 연결 수입니다.

대시보드 지연 마감 2,000 ms
학습 데이터 마감 30시간
버티는 시간 사람이 붙는 데 30분
관리할 연결 연결마다 설정 4개
처리 잡과 목적지를 잇는 선

왼쪽이 처리 잡, 오른쪽이 목적지입니다. 유통 층을 켜면 선이 가운데 한 칸을 거쳐 덧셈이 되고, 끄면 잡마다 목적지 전부로 선이 뻗어 곱셈이 됩니다.

이 조합에서 무엇이 먼저 터지나

이 데모에서 알게 된 3가지

  1. 대시보드 하나가 스트림을 강제한다 — 마감 2,000 ms 에서 도달 1,112 ms 를 빼면 남는 예산이 888 ms 입니다. 그 안에 드는 경로는 스트림 집계 하나뿐입니다. 1시간 배치로는 어떤 설정으로도 못 맞춥니다. 반대로 마감 30시간인 학습은 후보가 넷 다 들어서 가장 싼 하루 배치를 고릅니다.
  2. 유통 층은 곱셈을 덧셈으로 바꾼다 — 잡 5개 × 목적지 6개 = 30개가 5 + 6 = 11개가 됩니다. 설정 자리는 120개에서 44개입니다. 더 중요한 것은 목적지를 하나 더 붙일 때 손대는 처리 잡이 5개에서 0개가 된다는 쪽입니다.
  3. 버퍼는 지연이 아니라 버티는 시간을 산다 — 유통 층을 거치면 200 ms 를 더 씁니다. 대신 처리 잡이 멈춰도 168시간을 버티고 되감아 읽습니다. 버퍼를 빼면 로컬 파일이 61.7시간, SDK 직행이면 메모리 큐가 10.4분입니다.

현업에서는 이렇게 씁니다

"우리도 Flink 를 써야 하나" 같은 질문은 부품 이름으로는 답이 안 나옵니다. 소비자의 마감을 먼저 적고, 그 마감에서 도달 시간을 뺀 예산 안에 드는 경로만 후보로 남깁니다. 후보가 둘 이상이면 가장 싼 것을 고릅니다.

  • 마감표를 먼저 만듭니다: 소비자 이름 · 마감 · 허용 오차 · 조회 패턴 넷을 한 줄씩 적습니다. 이 표가 없으면 어떤 부품도 "왜 그것인가"에 답할 수 없습니다. 마감은 최근 이벤트가 아니라 가장 오래된 이벤트로 잽니다.
  • 유통 층은 미리 셈해 둡니다: 목적지가 셋을 넘고 처리 잡이 둘을 넘으면 이득이 확실합니다. 그 아래면 직접 쓰고, 늘어날 때 옮깁니다. 다만 옮기는 일 자체가 잡 전부를 고치는 일이라 시점을 미리 정해 둡니다.
  • 버티는 시간은 재 둡니다: 처리 잡이 멈춘 것을 사람이 알아채고 붙는 데 30분으로 잡고, 그 앞 층이 몇 시간을 들고 있는지 실제로 재 둡니다. 이 값이 분 단위면 알람보다 먼저 데이터가 사라집니다.

다음 배우기

관련 포스트 데이터 파이프라인 설계 설계는 수집기 고르기가 아니라 소비자의 마감을 적는 데서 시작한다. 여섯 층 중 어디에 무엇을 세울지는 그 마감이 정한다 관련 포스트 Kafka는 왜 있나 버퍼 층 안쪽 — 한 번 쓰고 여럿이 읽는 자리가 무엇을 해결하는지 관련 데모 로그 여섯 층 내려가기 탭에서 버퍼까지 1,112 ms 가 어느 홉에서 얼마씩 쓰이는지 따라갑니다
