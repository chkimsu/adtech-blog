데이터 건네기 카드 여덟 장

팀에서 팀으로 데이터를 옮기는 방법 하나가 카드 한 장입니다. 점이 흐르는 방향이 데이터가 가는 방향이고, 점이 몰려서 지나가면 하루 한 번 배치입니다. 이름과 숫자는 설명용 예시입니다.

파랑 = 놓여 있는 것 (테이블, 파일, DB) 벽돌색 = 흐르는 것 (토픽, 변경 로그) 먹색 = 부르는 것 (서비스, API) 회색 = 옮기는 도구 (배치 작업, 수집기) 점 = 지금 가고 있는 데이터

TABLE GRANT

같은 창고면 권한만 준다

쉽게 말하면 표는 그대로 두고 「이 표를 봐도 됩니다」 하고 허락만 하는 것입니다. 옆 팀이 자기 자리에서 같은 표를 열어 봅니다.

데이터는 그 자리에 있고 권한 한 줄만 갑니다. 두 팀이 같은 창고를 쓸 때 가장 싸고 빠릅니다.

BATCH PULL

남의 DB 를 하루 한 번 끌어온다

쉽게 말하면 남의 DB 에 있는 표를 매일 새벽 한 번 우리 창고에 복사해 두는 것입니다. 낮에는 그 복사본을 봅니다.

점이 몰려서 한 번 지나가는 것이 배치입니다. 어제까지의 값이면 충분할 때 씁니다. Sqoop 이 하던 일을 지금은 Spark JDBC 나 Airbyte 가 합니다.

CDC

바뀐 행만 흘려보낸다

쉽게 말하면 남의 DB 에서 행이 바뀔 때마다 「이 행이 이렇게 바뀌었다」는 알림을 받아 우리 표를 따라 고치는 것입니다.

DB 가 남기는 변경 로그를 읽어 토픽으로 보냅니다. 운영 DB 의 지금 상태를 몇 초 뒤에 창고에서 볼 수 있습니다.

FILE DROP

파일을 놓고 경로를 알려 준다

쉽게 말하면 하루치 데이터를 파일로 저장해 두고 「이 폴더에 있어요」 하고 경로만 알려 주는 것입니다. 받는 팀이 편할 때 가져갑니다.

하루 한 번, 대량이면 이것입니다. 받는 팀은 자기 시간에 읽고, 어제 파일은 그대로 남아 다시 읽을 수 있습니다.

TOPIC

토픽에 넣어 두고 여러 팀이 구독한다

쉽게 말하면 데이터가 생길 때마다 한 줄씩 공용 줄에 넣어 두고, 원하는 팀이 각자 그 줄을 구독해 받는 것입니다. 받는 팀이 늘어도 넣는 쪽은 안 바뀝니다.

같은 메시지를 세 팀이 각자 속도로 받습니다. 실시간이고 받는 쪽이 여럿일 때 씁니다.

API

건별로 지금 값을 물어본다

쉽게 말하면 필요한 것 하나를 그때그때 「이 광고 지금 상태 알려 줘」 하고 물어서 답을 받는 것입니다. 한 건에 한 번씩 묻습니다.

건 하나가 요청 하나입니다. 228만 건이면 요청 228만 번이라 대량 전달에는 안 맞고 조회에 맞습니다.

LOG PIPELINE

행동 기록을 수집기에 태운다

쉽게 말하면 서비스가 무슨 일이 있을 때마다 한 줄씩 기록을 남기면, 그 기록이 자동으로 창고까지 실려 가는 길입니다. 서비스 팀은 한 줄 남기는 것만 합니다.

서비스 팀에 오는 요청은 「이 로그 한 줄 남겨 주세요」 모양입니다. 한 번 남기면 뒤 자리들은 이미 깔려 있습니다.

REVERSE ETL

창고 결과를 서비스로 되돌린다

쉽게 말하면 창고에서 계산한 결과(이 사용자는 어느 그룹인가)를 서비스가 빨리 읽을 수 있는 DB 에 매일 옮겨 두는 것입니다. 서비스는 그 DB 만 봅니다.

창고는 느리고 서비스는 1ms 안에 답해야 합니다. 그래서 결과를 서비스 옆 DB 에 옮겨 두고 건별로 읽게 합니다.

현업에서는 이렇게 씁니다

  • 데이터 엔지니어에게 세 가지만 물으면 카드 하나로 좁혀집니다. 지금 어디에 어떤 모양으로 있나, 얼마나 자주 새로 와야 하나, 누가 옮기나(우리가 당겨 가나, 그쪽이 밀어 주나).
  • 카드를 누르면 위 해설 칸에 그 방법의 함정 하나가 더 나옵니다.
  • 글로 이어 읽으려면 데이터 건네기 글에 이 카드들이 절마다 한 장씩 들어 있습니다.
