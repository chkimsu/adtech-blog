여섯째 주에 지훈 씨는 옆 팀인 광고주 리포트 팀에서 메시지를 한 통 받았습니다. "클릭 로그를 우리도 쓰고 싶은데, 어떻게 받을 수 있을까요." 지훈 씨는 클릭 로그를 csv 파일(칸을 쉼표로 나눈 텍스트 파일)로 뽑아 주겠다는 답장을 쓰기 시작했습니다. "csv 로 뽑아 드릴까요?"

보내기 전에 선배가 그 답장을 보고 물었습니다. "그거 다음 주에도 뽑아 드릴 거예요?" 지훈 씨는 쓰던 손을 멈췄습니다. 클릭은 하루치만 해도 228만 줄인데, 그만한 데이터를 매주 뽑아 슬랙으로 보내는 일은 답이 될 수 없었습니다. 그렇다고 다른 답을 아는 것도 아니었습니다. 데이터 팀 사람들은 Sqoop, CDC, 토픽 같은 말을 자기들끼리만 주고받았는데, 지훈 씨는 그 이름들이 무엇을 가리키는지 몰랐습니다.

**팀에서 팀으로 데이터를 건네는 방법은 몇 가지이고 어느 것을 골라야 할까요?**

데이터를 건네는 방법은 여덟 가지이지만 팀 사이를 오가는 데이터의 모양은 테이블, 파일, 토픽(데이터가 생기는 대로 시간 순서로 흘러가는 곳), API(서비스가 요청을 받아 그때그때 답해 주는 방식) 네 가지뿐입니다. 데이터 팀이 말하는 도구 이름도 전부 「이 넷 중 무엇을, 누가, 얼마나 자주 옮기나」의 조합마다 붙은 이름입니다. 이 조합을 알면 데이터 팀과 같은 말로 이야기할 수 있고 매주 csv 를 뽑는 일도 하지 않게 됩니다.

> **한 줄 요약:** 팀 사이를 오가는 데이터의 모양은 테이블, 파일, 토픽, API 네 가지입니다. 데이터가 지금 어디에 어떤 모양으로 있나, 얼마나 자주 새로 와야 하나, 누가 옮기나 세 가지 질문에 답하면 건네는 방법 여덟 가지 가운데 하나로 좁혀집니다.

> **골라 읽는 법** — 이 글은 절 10개로 되어 있습니다. 절마다 카드가 한 장씩 들어 있으니 카드만 보고 다음 절로 넘어가도 됩니다.
>
> - 네 가지 모양과 먼저 물을 세 가지 질문 → 1절
> - 웨어하우스나 DB 에 놓여 있는 데이터를 옮기는 법 (테이블 권한, DB 배치, CDC, 파일) → 2~5절
> - 흐르는 데이터를 받는 토픽과 필요할 때 부르는 API → 6~7절
> - 서비스에 로그를 남기게 하는 법과 웨어하우스 결과를 서비스로 되돌리는 법 → 8~9절
> - 세 질문의 답으로 방법 하나를 고르는 과정 → 10절

이 글에 나오는 팀 이름, 테이블 이름, 시각은 설명하려고 정한 가상 값입니다. 하루 클릭 228만 건과 로그 한 줄의 크기 309 바이트는 이 트랙의 앞 글들에서 쓴 값과 같습니다.

## 1. 오가는 모양 네 가지와 먼저 물을 질문 세 가지

**팀 사이를 오가는 데이터는 테이블, 파일, 토픽, API 네 가지 모양 가운데 하나입니다. 건네는 방법 여덟 가지는 이 네 모양 사이에서 데이터를 옮기는 조합입니다.**

지훈 씨가 리포트 팀에 무엇을 물어야 할지 알려면 데이터가 팀 사이를 오갈 때 어떤 모양으로 있는지부터 알아야 합니다. 테이블은 데이터 웨어하우스나 DB 안에 줄과 칸으로 놓인 데이터입니다. 데이터 웨어하우스는 분석용 데이터를 모아 두는 저장소이고 이 글에서는 줄여서 웨어하우스라고 부릅니다. 파일로 건네는 데이터는 저장소의 경로(폴더 위치) 아래에 놓입니다. 토픽은 Kafka 같은 곳에서 시간 순서로 흐르는 데이터입니다. Kafka 는 들어오는 메시지를 시간 순서대로 쌓아 두고 여러 팀이 각자 읽어 가게 하는 시스템이고 6절에 다시 나옵니다. API 는 서비스가 요청을 받아 그때그때 답해 주는 방식이라, API 로 받는 데이터는 부를 때마다 답으로 옵니다. 네 모양 가운데 테이블과 파일은 놓여 있고 토픽은 흐르며 API 는 부르면 옵니다.

지훈 씨의 클릭 로그는 지금 웨어하우스의 테이블 `adlog.ad_click` 에 놓여 있습니다. 리포트 팀이 원하는 것도 결국 네 모양 가운데 하나입니다. 자기 웨어하우스의 테이블로 받고 싶은지, 파일로 받고 싶은지, 실시간으로 흘러오기를 원하는지, 화면에서 건별로 묻고 싶은지에 따라 고를 방법이 달라지므로, 리포트 팀에 원하는 모양을 먼저 묻지 않고는 방법을 고를 수 없습니다.

리포트 팀에 물을 질문은 아래 표의 세 가지입니다. 표에 처음 나오는 말부터 풀겠습니다. 배치는 정해진 시각에 데이터를 모아 한 번에 옮기는 방식입니다. 반면 흐름에서는 데이터가 생기는 대로 이어서 옮깁니다. 표에서 흐름에 넣은 CDC 는 DB 에서 바뀐 행을 몇 초 안에 보내는 방법이고 4절에 자세히 나옵니다. 토픽의 구독은 새 메시지가 들어오는 대로 받겠다고 토픽에 등록해 두는 것을 말합니다. API 의 호출은 요청을 보내고 답을 받는 동작입니다. 「우리가 당겨 가나, 그쪽이 밀어 주나」는 받는 팀이 직접 가져가는지(pull), 주는 팀이 보내 주는지(push)를 묻는 말입니다.

| 물을 것 | 답이 정해 주는 것 |
|---|---|
| 지금 어디에 어떤 모양으로 있나 | 테이블이면 권한이나 복사, 파일이면 경로, 토픽이면 구독, API 면 호출 |
| 얼마나 자주 새로 와야 하나 | 하루 한 번이면 배치(권한, 복사, 파일). 분 단위 아래면 흐름(토픽, CDC) |
| 누가 옮기나 | 우리가 당겨 가나, 그쪽이 밀어 주나. 실패했을 때 누가 다시 하나가 여기서 정해집니다 |

지훈 씨의 클릭 로그로 표의 첫째 줄을 따라가면, 로그가 웨어하우스 테이블에 놓여 있으므로 표는 권한을 주거나 복사하는 방법을 가리킵니다. 리포트 팀이 둘째와 셋째 질문에 어떻게 답했는지는 10절에서 맞춰 봅니다. 세 질문에 모두 답하면 2절부터 9절까지 한 장씩 나오는 카드 여덟 장 가운데 하나만 남습니다. 도구는 카드를 정한 뒤에 고르면 됩니다. 데이터 팀이 말하는 Sqoop 과 Airbyte 는 3절의 카드에, Debezium 은 4절의 카드에 붙은 도구 이름일 뿐입니다.

## 2. 같은 웨어하우스 안에서 주는 읽기 권한

**두 팀이 같은 웨어하우스를 쓰면 데이터는 옮기지 않고 받는 팀에 읽기 권한(테이블을 조회만 할 수 있는 권한) 한 줄만 줍니다.**

1절의 첫 질문에 「테이블」이라고 답했다면 리포트 팀이 지훈 씨 팀과 같은 Hive 웨어하우스를 쓸 때 가장 손이 덜 가는 답이 있습니다. Hive 는 여러 서버에 나뉘어 놓인 파일을 테이블처럼 SQL 로 읽게 해 주는 프로그램입니다. 이때는 `adlog.ad_click` 테이블에 리포트 팀 계정의 읽기 권한을 주기만 하면 됩니다. 테이블은 지훈 씨 팀의 웨어하우스에 그대로 있고 리포트 팀이 자기 자리에서 같은 테이블을 열어 보므로, 두 팀 사이에는 권한 설정 한 줄만 오갑니다. 복사본이 생기지 않으니 두 팀은 같은 값을 보고 웨어하우스에 새로 쌓이는 줄도 바로 봅니다.

카드 색은 네 가지입니다. 파랑은 놓여 있는 것(테이블, 파일, DB), 벽돌색은 흐르는 것(토픽, 변경 로그), 먹색은 부르는 것(서비스, API), 회색은 옮기는 도구입니다. 변경 로그는 DB 가 행이 바뀔 때마다 남기는 기록으로 4절에서 다룹니다. 첫 카드에서는 테이블은 제자리에 있고 권한 한 줄만 받는 팀에게 가는 모습을 보면 됩니다.

## 3. 남의 운영 DB 를 하루 한 번 복사해 오는 배치

**DB 배치는 운영 DB(서비스가 지금 읽고 쓰는 DB)의 표를 매일 정해진 시각에 전부 또는 바뀐 행만 웨어하우스로 복사해 두는 방법으로, 어제까지의 값이면 충분할 때 씁니다.**

2절과 방향이 반대인 경우도 있습니다. 이번에는 지훈 씨 팀이 리포트 팀의 주문 DB 를 받아 와야 합니다. 주문 데이터는 MySQL(많이 쓰는 DB 제품)에 있는데, 이 DB 는 서비스가 지금 쓰고 있는 운영 DB 라서 지훈 씨 팀이 직접 붙어 무거운 쿼리를 돌릴 수는 없습니다. 그래서 매일 03시에 배치 작업이 그 DB 의 주문 표를 한 번 읽어 지훈 씨 팀 웨어하우스의 `dw.orders` 테이블에 씁니다. 배치 작업은 정해진 시각에 한 번 돌아 그동안 쌓인 데이터를 한꺼번에 처리하는 작업입니다. 지훈 씨 팀은 새벽에 만든 이 복사본을 낮 동안 봅니다.

카드에서는 점이 한 번에 몰려 지나간 뒤 다음 주기까지 아무것도 지나가지 않는데, 이렇게 정해진 때에 몰아서 옮기는 움직임이 배치입니다.

매일 하는 복사에는 두 가지 방식이 있습니다. 전체 복사는 매일 표 전체를 처음부터 다시 읽어 오는 방식이고 표가 작으면 이 방식이 가장 단순합니다. 증분 복사는 행이 마지막으로 바뀐 시각을 적는 컬럼 `updated_at` 을 보고 그 값이 어제 03시 이후인 행만 읽어 옵니다. 그래서 오늘 03시에 도는 작업은 어제 03시부터 지금까지 하루 동안 바뀐 행만 가져옵니다. 표가 크면 매일 전체를 다시 읽는 대신 증분 복사를 써야 하는데, 증분 복사를 쓰려면 운영 DB 의 표에 `updated_at` 같은 갱신 시각 컬럼이 있어야 합니다. 그리고 지워진 행은 표에서 사라져 갱신 시각으로 고를 수 없으므로 증분 복사로는 어떤 행이 지워졌는지 알 수 없습니다.

이렇게 DB 를 배치로 복사해 오는 일을 오래 맡아 온 도구가 Sqoop 입니다. 다만 Sqoop 은 2021 년에 Apache(오픈소스 프로젝트를 관리하는 재단)에서 은퇴해 더 이상 개발되지 않는 프로젝트입니다. 지금은 Spark(여러 서버에서 대량 데이터를 나눠 처리하는 엔진)가 JDBC(자바 프로그램이 DB 에 접속하는 표준 방식)로 운영 DB 를 직접 읽거나, Airbyte 나 Fivetran 같은 도구가 같은 일을 합니다. 데이터 팀이 Sqoop 이라고 말하면 「DB 를 배치로 끌어오는 것」을 가리킨다고 들으면 됩니다.

## 4. 바뀐 행만 흘려보내는 CDC

**CDC 는 DB 가 남기는 변경 로그를 읽어 토픽으로 보내는 방법입니다. CDC 를 쓰면 운영 DB 의 지금 상태를 몇 초 뒤에 웨어하우스에서 볼 수 있습니다.**

하루 한 번 도는 3절의 배치로는 모자랄 때가 있습니다. 광고주가 예산을 바꾸면 그 값이 몇 초 안에 웨어하우스에도 반영돼야 하는 경우입니다. 배치 주기를 하루에서 1분으로 줄이면 운영 DB 가 1분마다 전체를 읽히느라 느려지지만 DB 가 이미 남기고 있는 기록을 쓰는 다른 길이 있습니다. DB 는 행에 생긴 모든 변경을 변경 로그에 남깁니다. MySQL 에서는 이 변경 로그를 binlog 라고 부릅니다. CDC 는 이 변경 로그를 읽어 토픽으로 보내는 방법이고 Change Data Capture(바뀐 데이터를 잡아낸다는 뜻)의 머리글자입니다. 이 일에 흔히 쓰는 도구는 Debezium 입니다. CDC 를 쓰면 받는 팀은 남의 DB 에서 행이 바뀔 때마다 「이 행이 이렇게 바뀌었다」는 메시지를 받아 자기 표를 그대로 따라 고칩니다.

카드에는 Debezium 이 읽어 토픽으로 보낸 변경을 웨어하우스의 표가 몇 초 뒤에 따라가는 모습이 그려져 있습니다.

메시지는 행을 넣는 INSERT, 고치는 UPDATE, 지우는 DELETE 한 건마다 한 개씩 가므로, 3절의 배치와 달리 지워진 행도 DELETE 메시지로 받습니다. 대신 받는 팀의 일이 늘어나는데, 같은 행이 두 번 바뀌면 메시지도 두 개가 와서 받는 팀은 그중 마지막 메시지만 남겨야 합니다. 이런 수고가 들기 때문에 CDC 는 「몇 초 안에」가 정말 필요한 테이블에만 씁니다. 그 밖의 테이블은 3절의 배치로 충분합니다.

## 5. 하루 한 번 대량으로 건네는 파일

**주는 팀이 파일을 저장소에 놓고 경로만 알려 주면 받는 팀이 자기 시간에 읽어 갑니다. 팀 사이에 데이터를 건넬 때 가장 흔히 쓰는 방법입니다.**

리포트 팀이 지훈 씨 팀과 다른 클러스터를 쓴다면 2절의 읽기 권한은 쓸 수 없는데, 이럴 때 가장 흔한 답이 파일입니다. 지훈 씨 팀의 배치 작업이 매일 04시에 어제 하루치 클릭 로그를 parquet 파일로 저장소에 씁니다. parquet 은 데이터를 열(컬럼) 단위로 모아 압축해 두는 파일 형식입니다. 파일이 놓이는 경로는 `s3://adlog/ad_click/dt=2026-09-17/` 처럼 날짜가 폴더 이름이라 날마다 날짜 이름이 붙은 폴더가 새로 생깁니다. 리포트 팀에는 이 경로 하나만 알려 주면 됩니다. 리포트 팀은 편할 때 그 폴더에서 파일을 가져갑니다.

가상 데이터로 하루치 파일의 크기를 계산해 보면 하루 클릭 228만 건에 로그 한 줄 309 바이트를 곱해 약 705 MB 가 나옵니다. 이 정도면 파일 하나로 두어도 부담이 없는 크기입니다. 게다가 parquet 은 열 단위로 압축하므로 실제로 저장소에 놓이는 파일은 705 MB 보다 작습니다.

카드에서는 파일이 폴더에 남고 받는 팀에게는 경로만 전달되는 모습을 보면 됩니다.

다만 파일에도 함정이 하나 있습니다. 주는 팀이 파일을 다 쓰기 전에 받는 팀이 읽으면 반쪽만 읽습니다. 그래서 주는 팀이 파일을 다 쓴 뒤 마지막에 「다 썼다」는 표시 파일을 따로 놓거나, 폴더 이름이 생긴 뒤에만 읽기로 두 팀이 미리 정해 둡니다.

## 6. 실시간으로 여러 팀이 구독하는 토픽

**데이터를 토픽에 넣어 두면 여러 팀이 같은 메시지를 각자 자기 속도로 받아 갑니다. 주는 팀은 토픽 한 곳에만 넣으면 되므로 받는 팀이 몇인지 몰라도 됩니다.**

클릭을 원한 팀은 리포트 팀만이 아니었습니다. 대시보드 팀은 같은 클릭을 2초 안에, 예산 소진 확인 팀(광고 예산이 얼마나 쓰였는지 확인하는 팀)은 5초 안에 받아야 했습니다. 5절의 파일은 매일 04시에 하루치를 한 번 놓는 방식이라 몇 초 안에 받아야 하는 두 팀에게는 맞지 않습니다.

이럴 때 답은 Kafka 토픽입니다. 1절에서 본 대로 토픽은 데이터가 시간 순서로 흐르는 곳이라, 데이터가 생길 때마다 한 줄씩 토픽에 넣어 두면 원하는 팀이 각자 토픽을 구독해서 가져갑니다. 지훈 씨 팀의 서비스가 클릭 한 건을 토픽 `ad.click` 에 넣으면 이 토픽을 구독한 세 팀이 같은 메시지를 각자 받습니다. 하루 클릭 228만 건을 하루의 초 수로 나누면 초당 26.4 건이 되는데, 이 26.4 건이 세 갈래로 나가 세 팀이 똑같이 받아 갑니다.

카드에는 토픽 하나에 들어간 같은 메시지를 세 팀이 각자 속도로 받아 가는 모습이 그려져 있습니다.

다만 조심할 점이 있는데, 토픽에는 보존 기간(토픽이 메시지를 지우지 않고 들고 있는 기간)이 있어 보통 7일치만 들고 있습니다. 토픽을 구독해 메시지를 읽어 가는 프로그램을 소비자라고 부릅니다. 소비자가 8일 동안 멈춰 있다가 다시 읽기 시작하면 멈춘 첫날 들어온 메시지는 이미 7일이 지나 지워진 뒤라, 그 소비자는 앞 하루치를 영영 받지 못합니다. 그래서 실시간은 토픽으로 주고 같은 데이터를 5절의 파일로도 놓아 두는 팀이 많습니다.

## 7. 건별로 지금 값을 묻는 API

**API 는 건 하나를 요청 하나로 묻는 방식이라 지금 값을 소량으로 볼 때 맞고 대량으로 건네는 데는 맞지 않습니다.**

리포트 팀의 화면에서는 광고 하나를 누르면 그 광고가 지금 켜져 있는지, 예산이 얼마 남았는지 같은 지금 상태가 보여야 합니다. 5절의 파일에는 어제까지의 데이터만 있으므로 지금 상태는 파일에서 찾을 수 없습니다. 그래서 지훈 씨 팀이 API 를 열어 둡니다. 리포트 화면이 `GET /v1/ads/9931` 을 부르면 광고 9931 의 지금 상태가 JSON 으로 돌아옵니다. GET 은 서버에서 정보를 가져올 때 쓰는 요청 방식입니다. JSON 은 이름과 값을 짝지어 글자로 적는 형식입니다. 요청 하나에 답이 하나 오므로 광고 하나를 볼 때마다 요청을 한 번씩 보냅니다.

카드에서는 리포트 화면이 요청을 보낼 때마다 API 가 답을 하나씩 돌려주는 모습을 보면 됩니다.

## 8. 서비스 로그를 웨어하우스까지 옮기는 로그 파이프라인

**서비스에서 나오는 행동 기록은 수집기(로그 파일을 읽어 다른 곳으로 보내는 프로그램)가 토픽으로, 토픽이 웨어하우스로 옮겨 주므로 서비스 팀은 로그 한 줄만 남기면 됩니다.**

여덟 방법 가운데 이 방법은 방향이 조금 다릅니다. 데이터를 가진 팀이 건네는 대신 데이터 팀이 서비스 팀에 「이 로그를 남겨 주세요」라고 요청합니다. 서비스 팀이 로그를 남기면 그 로그는 이미 깔린 길을 따라 웨어하우스까지 옮겨집니다. 지훈 씨의 클릭 로그도 이 길을 지나 웨어하우스에 들어왔습니다. 웹서버가 남긴 로그 한 줄을 수집기 Filebeat 가 읽어 토픽에 넣으면, 토픽에 들어간 줄이 웨어하우스 테이블로 옮겨져 쌓입니다.

카드에는 웹서버의 로그 한 줄이 수집기와 토픽을 지나 웨어하우스 테이블에 쌓이는 길이 그려져 있습니다.

## 9. 웨어하우스 결과를 서비스로 되돌리는 reverse ETL

**웨어하우스는 느리고 서비스는 1ms 안에 답해야 하므로, 분석 결과를 서비스 옆 DB(서비스가 빨리 읽을 수 있는 DB)에 옮겨 두고 서비스가 거기서 건별로 읽게 합니다.**

마지막 방법은 방향이 반대입니다. 데이터 팀이 웨어하우스에서 계산한 결과를 서비스 팀이 가져다 써야 할 때로, 사용자 세그먼트가 그 예입니다. 웨어하우스는 「이 사용자는 어느 그룹인가」를 매일 계산해 `dw.user_segment` 에 두는데, 광고 서버는 광고 요청이 올 때마다 이 결과를 읽어야 합니다. 그런데 웨어하우스에 직접 물으면 답이 오기까지 수 초가 걸리고 광고 서버는 1ms 안에 답해야 하므로 요청마다 웨어하우스에 물을 수는 없습니다.

카드에서는 결과 표가 배치로 서비스 옆 DB 에 옮겨진 뒤 광고 서버가 그 DB 를 건별로 읽는 차례를 보면 됩니다.

그래서 배치 작업이 매일 결과를 Redis 나 MySQL 같은 서비스 옆 DB 로 옮겨 놓습니다. 광고 서버는 웨어하우스가 아니라 그 DB 를 건별로 읽습니다. 이렇게 웨어하우스의 결과를 서비스 쪽으로 내보내는 방법을 reverse ETL 이라고 부릅니다. ETL 은 Extract, Transform, Load(추출, 변환, 적재)의 머리글자로 데이터를 웨어하우스로 들여오는 방향의 작업을 가리키는데, reverse ETL 은 그 반대 방향이라는 뜻입니다.

reverse ETL 에는 서비스가 낡은 값을 보는 함정이 있습니다. 결과를 하루에 한 번 계산해 옮기므로 서비스가 보는 값은 최대 하루 전 값입니다. 그래서 reverse ETL 은 세그먼트처럼 하루 늦어도 괜찮은 데이터에만 씁니다.

## 10. 세 질문의 답에 따른 방법 선택

**1절의 세 질문에 답한 뒤 여덟 카드에 맞춰 보면 카드 하나가 남습니다. 같은 하루 228만 건도 어떤 방법으로 옮기느냐에 따라 전혀 다른 모양이 됩니다.**

지훈 씨의 일로 돌아가 보면 리포트 팀이 준 답은 세 가지였습니다. 리포트 팀은 지훈 씨 팀과 다른 클러스터를 쓰므로 2절의 읽기 권한은 쓸 수 없습니다. 어제까지의 클릭이면 충분하다고 했으니 하루 한 번 새로 오면 됩니다. 자기들이 읽어 가겠다고 했으니 데이터를 당겨 가는 팀은 리포트 팀입니다. 세 답이 모두 5절의 파일을 가리키므로 매일 04시에 파일을 놓고 경로를 알려 주면 일이 끝납니다. 매주 csv 를 뽑아 보낼 일도 없어집니다.

아래 표에 같은 하루 228만 건을 방법마다 옮겼을 때 데이터가 어떤 모양이 되는지 적었습니다. 값은 가상이고 로그 한 줄을 309 바이트로 잡아 계산했습니다. DB 배치와 파일 줄의 약 705 MB 는 5절에서, 토픽 줄의 초당 26.4 건은 6절에서 계산한 값입니다.

| 방법 | 하루 228만 건이 이 모양이 됩니다 | 새로 오는 간격 | 누가 옮기나 |
|---|---|---|---|
| 테이블 권한 | 옮기지 않음. 권한 한 줄 | 쌓이는 즉시 | 아무도 |
| DB 배치 | 표 한 번 복사, 약 705 MB | 하루 한 번 | 받는 팀의 배치 |
| CDC | 메시지 228만 개가 종일 흐름 | 몇 초 | 도구(Debezium)가 계속 |
| 파일 | 파일 하나 약 705 MB | 하루 한 번 | 주는 팀이 놓고, 받는 팀이 읽음 |
| 토픽 | 초당 26.4 건이 흐름 | 즉시 | 주는 팀이 넣고, 받는 팀이 구독 |
| API | 요청 228만 번 | 부를 때마다 | 받는 팀이 매번 |
| 로그 파이프라인 | 로그 228만 줄 → 토픽 → 테이블 | 초 단위 | 수집기가 계속 |
| reverse ETL | 결과 표 한 번 복사 | 하루 한 번 | 데이터 팀의 배치 |

표를 보면 놓여 있는 것(권한, 배치, 파일, reverse ETL)은 하루 한 번 새로 오고 흐르는 것(CDC, 토픽, 로그)은 초 단위로 옵니다. 「누가 옮기나」 열에서 받는 팀이 매번 옮기는 방법은 API 하나뿐이므로, API 는 데이터를 건네는 전달이 아니라 필요할 때마다 값을 묻는 조회입니다.

도입에서 지훈 씨가 하려던 대로 슬랙으로 csv 를 보내는 방법도 이 표에 한 줄로 넣을 수 있습니다. 그 줄의 「누가 옮기나」 칸에는 사람이, 「새로 오는 간격」 칸에는 「부탁할 때마다」가 들어갑니다. 한 번은 그렇게 보내도 괜찮지만 같은 부탁이 두 번째로 오면 그때는 표에 있는 방법 하나로 바꿀 때입니다.

## 한눈 정리

| 질문 | 한 줄 답 |
|---|---|
| 데이터를 건네는 방법이 몇 가지인가 | 여덟 가지. 오가는 모양은 테이블, 파일, 토픽, API 네 가지 |
| 무엇을 먼저 물어야 하나 | 어디에 어떤 모양으로 있나, 얼마나 자주 새로 와야 하나, 누가 옮기나 |
| 같은 웨어하우스를 쓰면 | 권한만 줍니다. 데이터는 안 움직입니다 |
| 하루 한 번 대량이면 | 파일을 놓고 경로를 알려 줍니다 |
| 실시간이고 받는 팀이 여럿이면 | 토픽에 넣어 두고 각자 구독합니다 |
| 운영 DB 의 변경을 몇 초 안에 | CDC. 변경 로그를 토픽으로 |
| Sqoop 이 무엇인가 | DB 를 배치로 끌어오던 도구. 2021 년 은퇴. 지금은 Spark JDBC, Airbyte |
| API 로 대량을 받아도 되나 | 안 맞습니다. 228만 건이면 요청 228만 번입니다 |
| 분석 결과를 서비스가 써야 하면 | reverse ETL. 서비스 옆 DB 에 옮겨 두고 건별로 읽게 합니다 |

## 헷갈리기 쉬운 점

- **도구 이름보다 모양, 주기, 옮기는 팀을 먼저 정합니다.** 데이터가 어떤 모양으로 있는지, 얼마나 자주 새로 와야 하는지, 누가 옮기는지 세 가지가 정해지면 쓸 만한 도구는 한두 개로 줄어듭니다.
- **받는 팀에는 읽기 권한만 줍니다.** 지우거나 고치는 권한까지 주면 팀 A 의 테이블을 팀 B 가 지우거나 바꿀 수 있습니다.
- **증분 복사로는 지워진 행을 알 수 없습니다.** 갱신 시각으로 행을 고르는 방식이라 표에서 사라진 행은 고를 수 없습니다. 삭제까지 받아야 하면 CDC 를 씁니다.
- **파일에는 다 썼다는 표시가 있어야 합니다.** 주는 팀이 쓰고 있는 동안 받는 팀이 읽으면 반쪽만 읽습니다.
- **토픽은 7일치만 들고 있습니다.** 늦게 읽으러 온 소비자는 보존 기간이 지난 앞쪽 메시지를 받지 못합니다. 그래서 같은 데이터를 파일로도 함께 놓아 둡니다.
- **API 는 조회 방법입니다.** 화면의 줄마다 API 를 한 번씩 부르면 화면 하나를 띄우는 데 요청이 수백 번 나갑니다.
- **reverse ETL 로 옮긴 값은 최대 하루 전 값입니다.** 하루 늦은 값이어도 괜찮은 용도에만 씁니다.
- **csv 를 두 번째로 부탁받으면** 그때 여덟 방법 가운데 하나로 바꿉니다.
