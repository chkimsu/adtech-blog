지훈 씨가 올린 그 티켓 — 클릭 로그를 운영자 검색 창에도 넣어 달라는 요청 — 을 받은 데이터 팀은 설정 파일에 블록 열두 줄을 더했습니다. 처리 잡은 한 줄도 안 고쳤고 배포 승인은 반나절 만에 났습니다.

앞 글 도입에 나온 다른 팀은 같은 요청을 두 주째 붙들고 있습니다. 그쪽은 처리 잡 다섯 개가 각자 목적지에 직접 쓰고 있어서, 잡을 전부 열어 고치고 승인을 다섯 번 받아야 합니다. 배포마다 그 잡이 중단되니 그동안 뒤가 밀립니다.

**왜 한쪽은 설정 한 블록이고 다른 쪽은 처리 잡 다섯 개일까요?**

차이는 하나입니다. **처리와 목적지 사이에 층이 있느냐**입니다. 결과를 목적지마다 갈라 보내는 그 자리를 **유통 층**이라고 부릅니다. 처리 잡은 한 곳에만 쓰고, 어디로 보낼지는 그 층의 설정 파일이 결정합니다.

> **한 줄 요약:** 나눠 보내는 층을 두면 연결이 곱셈에서 덧셈으로 바뀝니다. 처리 잡 다섯과 목적지 여섯이면 연결 30개가 11개가 되고, 목적지를 하나 더 붙일 때 손대는 잡이 5개에서 0개가 됩니다.

이 층은 앞 글이 세운 여섯 층 중 **넷째 층**입니다. 숫자는 설명을 위해 지어낸 값입니다.

## 1. 목적지가 여섯입니다

**같은 로그가 여섯 곳으로 갑니다. 포맷도 쓰기 방식도 재시도도 다르고, 그 다름이 그대로 유지 비용이 됩니다.**

앞 글 1절이 읽는 쪽 넷의 마감을 적었습니다. **그 넷이 실제 저장소 이름을 갖는 자리가 여기이고, 실제로는 여섯입니다.**

| 목적지 | 무엇을 위해 | 포맷 | 쓰기 방식 | 재시도 |
|---|---|---|---|---|
| 스토리지 + Iceberg | 학습·정산 원천 | Parquet | 파티션 덮어쓰기 | 5회 · 2초 |
| ClickHouse | 실시간 대시보드 | RowBinary | 같은 키면 덮어쓰기 | 3회 · 0.2초 |
| OpenSearch | 운영자 검색 | JSON | 문서 id 색인 | 3회 · 1초 |
| 리포트용 DB | 광고주 리포트 | 행 | 배치 insert | 5회 · 2초 |
| 다른 팀 Kafka | 이상 탐지 팀 | Avro | topic 에 붙이기 | 무한 |
| 피처 스토어 | 서빙 피처 | 키-값 | 키 덮어쓰기 | 3회 · 0.5초 |

**셋째 열부터가 요점입니다. 포맷이 여섯 다 다르고 쓰기 방식도 재시도도 다릅니다.** 이 다름을 처리 잡이 떠안으면 잡마다 여섯 벌의 쓰기 코드가 생기고, 그만큼 배포 승인이 늘어납니다.

낯선 말 둘만 풀어 두겠습니다. **파티션**은 큰 테이블을 날짜 같은 기준으로 미리 잘라 둔 조각이고, 그 조각째 다시 쓰는 것이 파티션 덮어쓰기입니다. **Avro** 는 필드 이름과 타입을 따로 적어 두는 포맷입니다.

재시도 열도 마감이 결정한 값입니다. **대시보드는 2초 안에 못 쓰면 포기하고, 다른 팀 Kafka 는 마감이 없어 될 때까지 재시도합니다.**

여기까지가 목적지 쪽 절반입니다. 나머지 절반은 **처리 잡이 하나가 아니라는 것**입니다. 정제, 노출과 클릭 붙이기, 5분 집계, 시간 집계, 이상 탐지로 다섯입니다. 다음 절이 그 곱셈의 비용을 셉니다.

## 2. 곱셈이 덧셈이 됩니다

**연결이 30개에서 11개로 줍니다. 그리고 목적지를 하나 더 붙일 때 손대는 처리 잡이 5개와 0개로 갈립니다.**

층이 없으면 잡마다 목적지마다 쓰기 코드를 듭니다. 층을 두면 잡은 topic 한 곳에만 씁니다.

| | 층 없음 | 층 있음 |
|---|---|---|
| 연결 수 | 5 × 6 = **30개** | 5 + 6 = **11개** |
| 설정 자리 (연결마다 넷) | 120개 | 44개 |
| 목적지 하나 더 붙일 때 손대는 잡 | **5개** | **0개** |

30과 11의 차이는 19입니다. 숫자만 보면 크지 않아 보이는데, **비용이 나오는 자리는 셋째 줄입니다.** 잡 다섯을 손대면 코드 리뷰 다섯 번과 배포 승인 다섯 번이고, 배포마다 그 잡이 중단돼 뒤가 밀립니다. **도입의 두 팀이 갈린 자리가 여기입니다.**

설정 자리 120개와 44개도 같은 이야기입니다. 재시도 횟수 하나를 바꾸려면 층이 없는 쪽은 30곳을 찾아야 하고, **다섯 잡이 각자 다른 언어를 쓰면 그 30곳이 다 다르게 생겼습니다.**

**한 축만 늘어도 곱셈은 전체 비용을 끌어올립니다.** 목적지를 늘려 가며 세어 보면 이렇습니다.

없는 쪽은 목적지가 하나 늘 때마다 **다섯씩** 뛰고, 있는 쪽은 **하나씩** 늡니다. 그래서 결정은 하나입니다. **목적지가 늘 것 같으면 층을 먼저 세웁니다.**

## 3. 설정 파일 한 장이 하는 일

**목적지마다 블록 하나입니다. 처리 잡은 이 파일을 아예 모르고, 배포 승인도 이 파일 하나로 납니다.**

나눠 보내는 층의 설정은 대개 한 파일에 모입니다. 두 목적지만 적으면 이렇게 생겼습니다.

```yaml
# 나눠 보내는 층의 라우팅 규칙 — 목적지마다 한 블록
routes:
  - name: warehouse-click
    source: ad.click.clean
    sink: iceberg
    table: ad.click_v3
    format: parquet
    partition_by: [ingest_date, ingest_hour]
    write_mode: overwrite_partition
    retry: { max_attempts: 5, backoff_ms: 2000 }
    dlq: ad.click.dlq
  - name: realtime-click
    source: ad.click.clean
    sink: clickhouse
    table: click_5m
    format: rowbinary
    write_mode: idempotent_upsert
    dedup_key: [req_id]
    retry: { max_attempts: 3, backoff_ms: 200 }
    dlq: ad.click.dlq
```

**두 블록의 `source` 가 같습니다.** 같은 topic 을 읽어서 서로 다른 곳에 서로 다른 모양으로 넣습니다. 지훈 씨의 검색 인덱스 티켓은 **여기 블록 하나를 더하는 일**이 되고, 배포 승인도 이 파일 하나만 보면 납니다.

1절 표의 열들이 그대로 아래 다섯 줄로 내려옵니다.

| 키 | 무엇을 정하나 | 잘못 잡으면 |
|---|---|---|
| `source` | 어느 topic 을 읽나 | 엉뚱한 데이터가 실립니다 |
| `sink` · `table` | 어느 테이블에 쓰나 | 다른 테이블을 덮어씁니다 |
| `write_mode` | 덮어쓰나 새로 넣나 | 두 번 돌면 정산이 두 배가 됩니다 |
| `retry` | 몇 번 · 얼마 간격으로 | 마감을 넘기거나 버립니다 |
| `dlq` | 실패한 건이 어디로 | 버려진 줄을 모릅니다 |

맨 아랫줄의 `dlq` 는 쓰기가 끝까지 실패한 건이 가는 자리이고, 이것을 **실패 큐**라고 부릅니다. **여기 쌓인 건은 버린 것이 아니라, 사유를 고쳐 다시 흘려 넣어 매출로 살려야 하는 건입니다.**

회사마다 이 층에 자기 이름을 붙여 부릅니다. 이름은 낯설어도 하는 일은 대개 위 표와 위 파일이고, 공개된 것 중에서는 Kafka Connect 가 가장 흔합니다.

:::deep 더 깊이 — 수집기로 쓰던 도구로 유통까지 하는 설정
**Logstash 도 이 자리에 섭니다.** 앞 글들에서는 변환기로 나왔는데 같은 도구가 유통도 합니다. **받는 곳이 하나이고 내보내는 곳이 여럿이기 때문입니다.** 위 라우팅 규칙을 Logstash 설정으로 옮기면 이렇게 생겼습니다.

```ruby
# logstash.conf — 하나로 받아 여럿으로 나눠 씁니다
input {
  kafka {
    bootstrap_servers => "kafka:9092"
    topics => ["ad.click.clean"]
    group_id => "dist-click"
  }
}

filter {
  # 목적지마다 모양이 다르면 여기서 표시만 붙여 둡니다
  if [event] == "click" {
    mutate { add_tag => ["warehouse", "realtime"] }
  } else {
    mutate { add_tag => ["dlq"] }
  }
}

output {
  if "warehouse" in [tags] {
    s3 { bucket => "ad-log"
         prefix => "click/dt=%{+YYYY-MM-dd}"
         retry_count => 5 }
  }
  if "realtime" in [tags] {
    http { url => "http://clickhouse:8123/?query=INSERT+INTO+click_5m"
           http_method => "post"
           retry_failed => true }
  }
  if "dlq" in [tags] {
    kafka { bootstrap_servers => "kafka:9092"
            topic_id => "ad.click.dlq" }
  }
}
```

`output` 안에 블록이 셋이고 앞의 `input` 은 하나입니다. 다만 Logstash 를 이 자리에 두면 비용이 붙습니다. JVM 이라 한 대가 1 GB 를 먹고, **한 목적지의 설정 실수가 같은 프로세스의 다른 목적지를 중단시킬 수 있습니다.** 그래서 목적지가 열을 넘어가면 커넥터를 따로 띄우는 쪽으로 옮겨 갑니다.
:::

**이 파일 한 장이 도입의 반나절과 두 주를 갈랐습니다.** 그런데 이 층이 늘 이기는 것은 아니고, 다음 절이 손해가 나는 자리입니다.

## 4. 언제는 두지 않는 편이 싼가

**홉이 하나 늘고, 잡과 목적지가 둘 다 적으면 순손해입니다.**

연결이 30에서 11로 준다고 늘 이득인 것은 아닙니다. 비용을 치르는 자리가 두 곳 있습니다.

**첫째는 홉이 하나 더 생기는 것입니다.** 잡이 목적지에 바로 쓰면 쓰기가 한 번인데, 이 층을 거치면 topic 에 쓰고 커넥터가 다시 읽습니다. 앞 글의 대시보드는 남는 예산이 888 밀리초뿐이라, **topic 왕복 200 밀리초를 더하면 예산의 22% 를 먹습니다.**

**둘째는 잡이 하나뿐일 때입니다.** 잡 하나에 목적지 둘이면 없는 쪽이 2이고 있는 쪽이 3이라, **층이 연결을 오히려 하나 늘립니다.** 목적지와 잡이 둘 다 하나둘일 때는 이 층이 순손해입니다.

| 규모 | 어떻게 하나 | 왜 |
|---|---|---|
| 목적지 셋 이하 · 잡 둘 이하 | 잡이 직접 씁니다 | 층이 연결을 오히려 늘립니다 |
| 목적지 넷 이상 · 잡 셋 이상 | 층을 둡니다 | 곱셈이 덧셈으로 바뀝니다 |
| 마감이 1초 아래 | 잡이 직접 씁니다 | topic 왕복이 예산을 먹습니다 |
| 목적지가 늘 예정 | 미리 층을 둡니다 | 나중엔 잡 전부를 고칩니다 |

기준은 이렇습니다. **목적지가 셋을 넘고 처리 잡이 둘을 넘으면 이득이 확실하고, 그 아래면 직접 쓰다가 늘어날 때 옮깁니다.** 옮기는 일 자체가 잡 전부를 고치는 일이니, 그 비용을 미리 셈해 두고 언제 옮길지를 결정해 둡니다.

| 층이 있으면 | 연결 11개 · 설정 자리 44개 | 잡 5 더하기 목적지 6 |
| 목적지 하나 추가 | 손대는 잡 5개 → 0개 | 설정 블록 하나로 끝납니다 |
| 언제 두지 않나 | 목적지 셋 이하 · 잡 둘 이하 | 연결이 2에서 3으로 늘어납니다 |

## 헷갈리기 쉬운 점

**"유통 층은 새 제품을 사는 일이다"** — 자리의 이름이지 제품 이름이 아닙니다. 처리 잡이 결과를 쓰는 부분을 공용으로 뽑아 쓰는 구성도 같은 층이라, 비용을 새로 쓰지 않고도 세울 수 있습니다.

**"연결이 19개 줄어든 것이 값어치다"** — 값어치는 개수가 아니라 **배포 승인 횟수**입니다. 목적지 하나에 손대는 잡이 5개와 0개로 갈리는 것이 도입의 반나절과 두 주를 만들었습니다.

**"실패 큐를 만들어 뒀으니 안심이다"** — **만들어 놓고 안 보는 것이 가장 흔한 손해입니다.** 사유를 고쳐 다시 흘려 넣어야 그 건들이 매출로 살아납니다.

**"층을 두면 늘 빨라진다"** — 반대입니다. 홉이 하나 늘어 늦어지고, 대신 고치는 비용이 줍니다. 마감이 1초 아래면 이 거래가 안 맞습니다.
