## 1. 왜 만드나

사용자(ML 엔지니어)가 최근 커밋을 읽고 던진 질문 열몇 개가 출발점입니다. 조각은 이미 블로그에 거의 다 있는데 **한 줄기로 이어 보는 자리가 없고**, 있는 것도 어렵다는 진단이었습니다.

원문: *"kafka의 어려운 개념들은 필요없고 topic에 저장을 해서 그다음 어떻게 사용하는지"*, *"데이터 엔지니어가 아닌 ML ENGINEER 관점에서 이해를 쉽게 하기 위한 과정"*, *"지금까지 쓴 내용도 좋지만 아무래도 어렵기도 해"*.

### 1.1 질문을 4묶음 14개로 정리한 것

| # | 묶음 | 질문 | 지금 상태 |
|---|---|---|---|
| 1 | API | API 한 건이 실제로 어떻게 생겼나 | 글 `api-basics` 있음. 누르는 데모 없음 |
| 2 | | 누가 받고 뭘 돌려주나 | 글 있음. 데모 없음 |
| 3 | | **액세스 로그와 이벤트 로그를 누가 남기나** | `api-basics` 8·9절에 도식. **데모 없음** |
| 4 | | server→server 와 client→server 차이 | `api-kinds` 1절에 조금 |
| 5 | | 그 둘은 주소 이름을 다르게 짓나 | **거의 없음** |
| 6 | 수집 | 왜 곧장 Kafka 로 안 보내고 파일에 떨구나 | 글·데모 있음 |
| 7 | | Filebeat 와 Logstash 는 각각 뭘 하나 | 글에 흩어져 있음 |
| 8 | Kafka | Kafka 로 모으는 이유 | 글 `kafka-log-pipeline` 있음 |
| 9 | | topic 에 놓인 뒤 어떻게 쓰나 | **약함.** 기존 데모는 partition·key 라 어려운 쪽 |
| 10 | | 기다렸다 가져가도 되나 | 글에 있음 |
| 11 | | 바로 가져가야 하는 쪽은 어떻게 하나 | 글·데모 있음 |
| 12 | 전체 | 각 자리가 데이터를 어떻게 바꾸나 | 데모 `cart-pipeline` 이 거의 이것 |
| 13 | | 실제 서비스는 각 자리에 뭘 쓰나 | **없음** |
| 14 | | ML 엔지니어인 나는 어디에 서 있나 | **없음** (설계 중 추가, 사용자 승인) |

빈 곳은 3, 5, 9, 13, 14 다섯입니다. 나머지는 있지만 흩어져 있습니다.

## 2. 확정된 결정 (2026-08-17 사용자)

1. **두 장으로 나눈다** — API 한 장, 데이터 파이프라인 한 장. 서로 링크로 잇는다
2. **움직임을 페이지마다 다르게 섞는다** — API 는 「직접 조립해 보내기」, 파이프라인은 「흘려보내고 자리를 눌러 멈춰 보기」
3. **실제 서비스 예시는 둘 다** — 자리마다 「누가 쓰나」와 「흔히 쓰는 제품」 두 줄
4. **v2 토큰** — 스킬은 새 문서에 v3 를 권하지만, 이 저장소는 CI 게이트 `scripts/check-design.js` 가 v2 팔레트 17색만 알고 형제 페이지 40여 장이 전부 v2 다. 스킬 1번의 「형제와 나란히 놓일 새 문서는 형제 버전을 따른다」에 해당

### 4.1 공통 상태와 가짜 서버

1~3절이 **한 상태를 같이 봅니다.** 4절 스위치가 그 상태를 통째로 바꿉니다.

```js
state = {
  caller: 'app' | 'server',                 // 4절
  method: 'GET' | 'POST',
  path: '/v1/events',
  ctype: true,                              // Content-Type 헤더
  auth: 'none' | 'token' | 'apikey',
  body: { req_id, ad_id, slot, event, ts }, // 각각 채움/비움
  server: 'ok' | 'down' | 'slow'            // 2절
}
```

**판정 순서** — 위에서부터, 먼저 걸리는 것이 이깁니다.

| 순서 | 조건 | 응답 |
|---|---|---|
| 1 | `server === 'down'` | 응답 없음 (연결 실패) |
| 2 | 요구 인증과 다름 | `401 Unauthorized` |
| 3 | `method !== 'POST'` | `405 Method Not Allowed` |
| 4 | `ctype === false` | `415 Unsupported Media Type` |
| 5 | `req_id`·`ad_id`·`event` 중 빈 것 | `400 Bad Request` |
| 6 | `server === 'slow'` | 서버는 `204`, **앱은 타임아웃** |
| 7 | 통과 | `204 No Content` |

`204` 를 고른 이유는 글에 이미 있습니다 — 본문 `{"ok":true}` 11바이트 × 하루 5,928만 = 652MB 이고 그 요금은 사용자가 냅니다.

### 4.2 절별 설계

**1절 — 요청 한 건은 이렇게 생겼습니다** (질문 1)

- 왼쪽에 고르는 칸, 오른쪽에 **HTTP 원문이 실시간으로 조립**됩니다.
- 고를 수 있는 것: 메서드, 주소, `Content-Type` 켜기·끄기, 인증 3택, 바디 필드 5개 각각 채움·비움.
- 원문 예 (전부 통과 상태):

```http
POST /v1/events HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"req_id":"r-8f21","event":"click","ad_id":9931,"slot":"main_top","event_ts":1786002501234}
```

- 바이트 수를 실시간으로 셉니다. 다 채우면 85 B 입니다.
- 설명은 네 조각만 — 메서드는 하려는 일, 주소는 대상, 헤더는 부가 정보, 바디는 내용.

**2절 — 받는 쪽은 뭘 보고 뭘 돌려줍니까** (질문 2)

- `[보내기]` 버튼. 4.1 판정 순서를 그대로 돌리고 응답 원문을 보여 줍니다.
- 서버 상태 3택(`정상` · `안 떠 있음` · `느림`)을 눌러 `500` 계열과 타임아웃도 만들어 봅니다.
- 응답마다 한 줄 — **"부르는 쪽은 이때 뭘 해야 하나"**. `api-kinds` 2절 표를 씁니다.

| 코드 | 누가 고쳐야 하나 | 다시 보내도 되나 |
|---|---|---|
| 204 | — | — |
| 400 | 부르는 쪽 | 아니요 · 그대로 또 틀립니다 |
| 401 | 부르는 쪽 | 갱신한 뒤 한 번만 |
| 405 · 415 | 부르는 쪽 | 아니요 |
| 500 계열 | 받는 쪽 | 됩니다 · 간격을 늘려 가며 |

- **함정 하나를 켜 볼 수 있게 합니다** — `[200 안에 에러 담기]` 스위치. 켜면 응답이 `200 OK` + `{"result":"fail"}` 로 바뀌고, 재시도·실패율 그래프·로드밸런서 세 곳이 동시에 눈이 머는 것을 표시합니다.

**3절 — 이 줄은 누가 남깁니까** (질문 3 · 이 페이지의 핵심)

🔴 **축이 바뀌었습니다 (2026-08-17 사용자 확인).** 초안은 「요청 때냐 응답 때냐」로 짰는데, 사용자가 궁금했던 것은 *"액세스, 이벤트 로그를 누가 남기는지"* 였습니다. **「누가 남기나」를 1축으로 놓고 「언제 찍히나」는 그 아래 딸린 항목으로 내립니다.**

- 화면 위쪽: 요청 한 건을 보내면 **층마다 한 줄씩** 채워지고, 줄마다 왼쪽에 **남긴 주체 이름표**가 붙습니다. 클릭 한 건이 한 곳에 남는 것이 아니라 층마다 흩어져 남는다는 것이 첫 그림입니다.

```
[ 앱 SDK        ]  폰 안의 SDK 코드가 남김 — 사용자 기기라 우리가 못 봄
[ 로드밸런서    ]  LB 프로세스가 남김
[ nginx         ]  nginx 워커 프로세스가 남김
[ 우리 앱       ]  우리가 짠 핸들러 함수가 남김
```

- 화면 아래쪽: **방식 3택 스위치.** 같은 요청인데 누가 무엇을 남기는지가 통째로 바뀝니다. 셋 다 넣습니다(사용자 확정).

| 방식 | 파일에 실제로 쓰는 것 | 우리가 짜는 것 | 그 줄에 본문이 있나 | 근거 |
|---|---|---|---|---|
| A. nginx 가 접속만 | nginx 워커 프로세스 | 0줄 (설정에 형식 한 줄) | 없음 | `api-basics` 8절 ① |
| B. 앱 코드가 본문을 | 앱 프로세스 안의 로거 | 핸들러 함수 안 한 줄 | 있음 | `api-basics` 8절 ② |
| C. nginx 가 본문까지 한 줄에 | **nginx 혼자** | 설정 한 줄 (`$request_body`) | 있음 | `log-hops` 3절 — **이 블로그 수집 서버가 이것** |

- 방식마다 실물 줄을 그대로 보여 줍니다.

A — 표준 형식. 본문이 없어 어느 광고였는지 모릅니다.
```
10.2.31.7 - - [16/Aug/2026:16:48:21 +0900] "POST /v1/events HTTP/1.1" 204 0 "-" "AdSDK/3.2.1" 0.002
```

B — 우리 코드가 본문을 꺼내 적은 줄.
```json
{"req_id":"r-8f21","event":"click","ad_id":9931,"slot":"main_top","event_ts":1786002501234,"app_ver":"3.2.1"}
```

C — nginx 설정에 `$request_body` 를 넣어 둘을 한 줄로. 183 B 이고 2페이지가 이 줄을 받습니다.
```text
log_format collect '$remote_addr $time_iso8601 $request_method $uri $status '
                   '$request_time "$http_user_agent" $request_body';
```
```
121.130.8.24 2026-08-16T16:48:21+09:00 POST /v1/events 204 0.002 "AdSDK/3.2.1 (iPhone; iOS 19.2)" {"event":"click","ad_id":9931,"slot":"main_top","req_id":"r-8f21","ts":1786002501234}
```

- **nginx 가 남기는 것과 우리 코드가 남기는 것이 갈리는 축 넷.** 이 표가 절의 답입니다.

| 축 | nginx (A · C) | 우리 코드 (B) |
|---|---|---|
| 파일에 실제로 쓰는 것 | nginx 워커 프로세스 | 앱 프로세스 안의 로거 |
| 끄려면 | 설정 고치고 reload | 코드 지우고 배포 |
| 앱이 죽어 있으면 | **남습니다.** 502 라고 적힙니다 | 안 남습니다 |
| 붙일 수 있는 값 | nginx 가 아는 것만 — IP, 시각, 경로, 상태, 걸린 시간 | **DB를 뒤져 붙일 수 있습니다** — 캠페인 id, 광고주 id, 비용 |

마지막 줄이 우리가 코드를 짜서까지 남기는 이유입니다. **요청에 없는 값은 앱만 붙일 수 있습니다.**

- **C 방식의 한계를 여기서 짚고 2페이지로 넘깁니다.** C 는 본문을 담지만 캠페인 id·광고주 id·비용은 못 담습니다. nginx 가 모르는 값입니다. 그것은 2페이지 5번 자리(Logstash)가 붙이고, 그 자리가 필드를 5개에서 15개로 늘립니다.

- **경우별로 어느 줄이 남고 어느 줄이 안 남나** (C 방식 기준).

| 경우 | 앱 SDK 로그 | nginx 줄 | 앱이 남긴 줄 (B 를 같이 쓸 때) |
|---|---|---|---|
| 정상 204 | `ok` | 남음 (204) | 남음 |
| 400 | `got 400` | 남음 (400) | **없음** |
| 401 | `got 401` | 남음 (401) | **없음** |
| 앱 프로세스가 죽음 | `got 502` | **남음 (502)** | **없음** |
| 서버 장비가 안 뜸 | `connect failed` | **없음** | **없음** |
| 앱이 포기(타임아웃) | `timeout` | 남음 (204) | 있음 |

- 여기서 나오는 문장 넷:
  - **누가 남기느냐가 「무엇을 적을 수 있느냐」를 정합니다.** nginx 는 자기가 아는 것만 적습니다.
  - 액세스 로그는 응답을 보낸 뒤에 찍힙니다. 그래서 상태코드와 걸린 시간이 그 줄에 있습니다. 요청 받자마자 찍으면 둘 다 못 적습니다.
  - **학습 데이터로 쓸 클릭 로그를 A 방식에서 찾으면 안 됩니다.** 주소가 전부 `/v1/events` 라 어느 광고였는지 모릅니다.
  - 넷째·다섯째 줄이 「앱은 1,000건, 서버는 985건」의 정체입니다.

**4절 — 부르는 쪽이 앱이냐 다른 서버냐** (질문 4)

- 스위치 하나(`앱이 부른다` ↔ `광고주 서버가 부른다`)로 1~3절이 통째로 바뀝니다. 같은 목적(전환 1건 기록)인데 요청·인증·검증·로그가 어떻게 달라지는지.

| 축 | 클라이언트 → 서버 | 서버 → 서버 |
|---|---|---|
| 누가 부르나 | 앱·브라우저 | 광고주 서버·매체 서버 |
| 인증 | 사용자 토큰 (사람 단위) | API 키·서명 (회사 단위) |
| 비밀키를 실을 수 있나 | 못 싣습니다 | 실을 수 있습니다 |
| 보낸 값을 믿나 | 안 믿고 다시 검사합니다 | 상대적으로 믿습니다 |
| 못 닿으면 | 그냥 사라집니다 | 재시도합니다 |
| 건수와 두께 | 많고 얇습니다 (초당 686) | 적고 두껍습니다 (하루 1,000) |
| 오는 시각 | 사람이 누른 그때 | 몇 분 뒤 몰아서 올 수 있습니다 |
| 남는 IP | 사용자 IP | 서버 IP (고정) |

- S2S 쪽 원문은 실물 그대로:

```http
POST /v1/conversions HTTP/1.1
Host: api.example.com
Content-Type: application/json
Idempotency-Key: O-00042

{"click_id":"ck-8f21","order_id":"O-00042","value":39000,"ts":1786002501}
```

- 재시도가 만드는 것도 한 번 눌러 봅니다 — 응답이 오는 길에서 유실돼 3번까지 다시 보내면 실제 전환 1,000건이 리포트에 **1,180건**이 되고, CPA 가 ₩5,000 → ₩4,237 로 싸 보입니다. `Idempotency-Key` 를 켜면 1,000건으로 돌아옵니다. **이름은 안 부르고 "요청 번호"로 씁니다.**

**5절 — 그래서 주소 이름을 나눕니까** (질문 5)

🔴 **묻는 것이 둘입니다 (2026-08-17 사용자 확인).** *"둘 다 궁금했어"* — (가) 왜 나뉘나, (나) 이름을 실제로 어떻게 짓나. 절을 5-1, 5-2 로 가릅니다.

**5-1. 왜 나뉩니까**

- 3.6 표의 주소 다섯을 눌러 보면 문 앞 규칙(인증·한도·마감·누가 부르나)이 바뀝니다. 마감이 글에 없는 주소는 칸을 비웁니다.
- 나누는 이유 셋:
  1. 인증 방식이 다릅니다 — 한 주소에 두 인증을 받으려면 코드가 갈라집니다
  2. 유량과 마감이 다릅니다 — 12 ms 와 100 ms 를 한 줄에 놓을 수 없습니다
  3. 문 앞(Ingress·Gateway)에서 다른 규칙을 걸어야 합니다
- `[한 주소로 합치기]` 스위치 — 켜면 `/v1/bid` 와 `/v1/track` 이 한 주소가 되고, 트래킹이 100 ms 를 쓰는 동안 입찰이 슬롯을 못 잡아 12 ms 를 넘기는 것을 표시합니다 (`gateway-ingress-router` 2절 실물).

**5-2. 이름은 실제로 어떻게 짓습니까**

- 답: **주소에 `s2s` 를 박는 일은 드뭅니다.** 자원 이름이 어차피 다르기 때문입니다.

| 가르는 방법 | 예 | 흔한가 | 왜 |
|---|---|---|---|
| **자원 이름이 어차피 다르다** | `/v1/events` 대 `/v1/conversions` | **가장 흔합니다** | 앱은 클릭을, 광고주 서버는 전환을 보냅니다. 보내는 것이 다르니 주소가 다릅니다 |
| **호스트로** | `api.example.com` 대 `partner.example.com` | 흔합니다 | 인증·한도·방화벽을 호스트 단위로 겁니다. 문 앞에서 제일 먼저 갈립니다 |
| **`/internal` 접두사** | `/internal/v1/scores` | 흔합니다 | 주소만 보고 "밖에 안 열려 있다"를 압니다 |
| **`/s2s` 접두사** | `/v1/s2s/conversions` | **드뭅니다** | `s2s` 는 우리 사정입니다. 광고주는 그냥 전환 보내는 주소를 원합니다 |
| 헤더로 | `x-api-version: 1` | 버전 가를 때만 | 주소를 안 바꿔도 됩니다 (`gateway` 4절) |

- **첫 줄이 답의 핵심입니다.** 대부분은 「부르는 쪽이 달라서 나눈 것」이 아니라 **애초에 다른 것을 보내서 이름이 다른 것**입니다.
- 같은 자원인데 부르는 쪽만 다르면 한 주소에 인증 두 가지를 받는 것도 흔합니다. 나누는 게 나은 신호 셋:
  - 응답에 담을 필드가 달라야 할 때 — 앱에는 개인정보를 못 줍니다
  - 초당 한도가 달라야 할 때
  - 마감이 달라야 할 때
- 마지막으로 되돌리기 비용 한 줄 — **주소를 나누면 되돌리기 어렵습니다.** 매체와 광고주에게 알려 준 뒤에는 고쳐 달라고 부탁해야 합니다 (`gateway` 3절의 "그 부탁은 이번이 마지막"). **그래서 나눌지는 처음에 정합니다.**
- 위젯: 이름 짓기 5택을 눌러 보면 같은 전환 수집 API 의 주소가 다섯 가지로 바뀌고, 각각 문 앞에서 무엇으로 갈리는지(호스트냐 경로냐 헤더냐)가 표시됩니다.

**6절 — 이 한 건이 남긴 줄** (이어짐)

- 지금까지 만든 요청이 남긴 두 줄을 실물로 굳혀 보여 줍니다 (액세스 로그 183 B, 이벤트 로그).

### 5.2 절별 설계

**1절 — 왜 곧장 안 보내고 파일에 떨굽니까** (질문 6)

- 두 경로를 나란히 두고 `[Kafka 멈추기]` 를 누릅니다.

| | 앱 → Kafka 직행 | 앱 → 파일 → Filebeat → Kafka |
|---|---|---|
| Kafka 가 멈추면 | 메모리에 쌓입니다. 512MB 가 **10.9분**에 참 | 파일만 찹니다. 100GB 로 **237시간** |
| 그 다음 | 서버가 같이 위험해집니다 | 앞단은 아무 영향 없습니다 |
| 대가 | 없음 | 640 ms 를 더 기다립니다 |

- 이유가 셋인 것을 밝힙니다.
  1. 버티는 시간을 삽니다 — 640 ms 를 주고 237시간을 얻습니다
  2. **광고 서버가 Kafka 클라이언트를 안 들고 있어도 됩니다.** 서버는 파일에만 씁니다. Kafka 주소가 바뀌어도 서버 배포가 필요 없습니다
  3. nginx 가 이미 파일에 쓰고 있습니다. 새로 만드는 것이 아니라 있는 것을 줍는 것입니다

**2절 — Filebeat 와 Logstash 는 뭐가 다릅니까** (질문 7)

- 한 줄: **Filebeat 는 옮기기만 하고, Logstash 는 바꿉니다.**

| | Filebeat | Logstash |
|---|---|---|
| 하는 일 | 파일을 읽어 그대로 보냅니다 | 한 줄을 필드로 쪼개고 붙입니다 |
| 원문 | 안 건드립니다 — `message` 칸에 통째로 | 파싱해서 15개 필드로 |
| 무겁나 | 가볍습니다 (Go · 메모리 수십 MB) | 무겁습니다 (JVM · 수백 MB~GB) |
| 어디에 두나 | 로그가 있는 서버마다 | 따로 몇 대 |
| 없으면 | 아무도 파일을 안 줍습니다 | Kafka 에 원문 문자열만 쌓입니다 |

- Filebeat 봉투 실물(346 B)과 Logstash 출력 실물(309 B)을 나란히 보여 줍니다.
- `[Logstash 끄기]` — Kafka 값이 `message` 한 칸짜리 원문으로 바뀌고, **읽는 쪽 넷 중 누가 곤란해지는지** 표시합니다. 대시보드는 못 그립니다. 모델 학습은 어차피 자기가 파싱하니 덜 곤란합니다. 이 차이가 요점입니다.
- 한 문단으로 덧붙임 — Logstash 를 안 두고 Kafka 에 원문을 넣은 뒤 Flink·Spark 가 파싱하는 방식도 흔합니다.

**3절 — Kafka 로 모으는 이유** (질문 8)

- 핵심 하나: **한 번 쓰고 여럿이 읽습니다.**
- `[Kafka 빼기]` — 선이 1개에서 4개로 늘고, 한 곳을 죽이면 어디까지 번지는지 표시합니다.
- Kafka 없이 할 때 생기는 것 셋:
  1. 보내는 쪽이 받는 쪽 넷을 다 알아야 합니다. 새 소비자가 생기면 보내는 쪽 코드를 고칩니다
  2. 한 곳이 죽으면 보내는 쪽이 멈추거나 메모리에 쌓입니다. 20초 배포에 52,780줄이 쌓입니다
  3. **버릴지 말지의 답이 받는 쪽마다 다릅니다.** 광고주 리포트는 한 건도 버리면 안 되고 대시보드는 버려도 됩니다. 그래서 코드가 네 벌 필요합니다
- 두 번째 이유: **읽는 속도가 서로 달라도 됩니다.** 대시보드 2초와 모델 학습 다음 날 새벽이 한 topic 위에 같이 있습니다.

**4절 — topic 에 놓인 뒤 누가 언제 읽어 갑니까** (질문 9 · 이 페이지의 핵심)

🔴 **축이 하나 더 붙었습니다 (2026-08-17 사용자 확인).** 사용자 원문 — *"어떤 주기로 보통 읽어가고 어떤 시스템은 언제 빠르게 읽어가고. 이 필요성이 궁금한거야. 사용성."* 초안은 주기를 적어만 두고 도구는 6절로 미뤄 뒀는데, **정작 궁금한 것은 「왜 그 주기라야 하나」였습니다.** 필요성을 4절 안으로 당깁니다. 6절은 그 주기를 지키는 수단만 맡습니다.

- 남기는 개념은 넷뿐입니다. 나머지는 안 부릅니다.
  - topic 은 이름 붙은 줄입니다 — `ad.click`
  - 줄마다 번호가 붙습니다 — 0번부터 계속 늘어납니다
  - 읽는 쪽은 **"내가 몇 번까지 읽었다"만 기억합니다.** 그게 전부입니다
  - **읽어 가도 안 지워집니다**
- 위젯: 가로 줄에 레코드 20칸(offset 8,405~8,424). `r-8f21` 은 8,412 에 굵게. 아래에 커서 4개.

| 커서 | 시작 자리 | 시간이 흐르면 |
|---|---|---|
| 실시간 대시보드 | 맨 끝 | 새 레코드마다 바로 따라붙습니다 |
| 예산 소진 확인 | 끝에서 한두 칸 | 거의 따라붙습니다 |
| 광고주 리포트 | 5분 뒤처짐 | 5분마다 확 당깁니다 |
| 모델 학습 | 어제 자리 | 멈춰 있다가 새벽에 확 달립니다 |

- `[시간 흐르기]` 를 누르면 오른쪽에 새 레코드가 붙고 커서가 각자 속도로 움직입니다. 커서 옆에 「밀린 정도 N건」. 이름(lag)은 안 붙입니다.
- 여기서 나오는 문장: 네 명이 서로를 모릅니다. 모델 학습이 어디까지 읽었든 대시보드 자리는 그대로입니다.

**4-1. 왜 그 주기라야 합니까** (이 절의 답)

커서를 누르면 그 소비자의 사정이 펼쳐집니다. **주기 숫자가 아니라 그 숫자를 만든 이유를 먼저 보입니다.**

| 읽는 쪽 | 주기 | 왜 그 주기라야 하나 | 늦으면 | 더 빨리 하면 |
|---|---|---|---|---|
| 예산 소진 확인 | 5초 | **돈이 샙니다.** 예산을 다 쓴 캠페인이 계속 나가면 그 광고비는 우리가 뭅니다 | 5초 늦으면 노출 13,195건이 더 나갑니다 (초당 2,639 × 5) | 이득이 큽니다. 넷 중 여기가 제일 급합니다 |
| 실시간 대시보드 | 2초 | 운영자가 화면을 보며 지금 잘 나가는지 판단합니다 | 멈춘 화면으로 보입니다 | 이득 없습니다. 사람 눈이 2초 아래를 못 가립니다 |
| 광고주 리포트 | 5분 | 그대로 청구서가 됩니다. 빠른 것보다 정확한 것이 먼저입니다 | 광고주 문의가 옵니다 | 필요 없습니다 |
| 모델 학습 | 다음 날 새벽 | 하루치가 다 모여야 라벨이 확정됩니다 | 어제 데이터로 오늘 모델을 못 만듭니다 | **불가능합니다.** 라벨이 아직 안 왔습니다 |

- 원칙 한 줄로 닫습니다 — **주기는 "얼마나 빨리 볼 수 있나"가 아니라 "늦으면 무엇을 잃나"가 정합니다.**
- 마지막 줄이 ML 엔지니어에게 중요합니다. **빨리 읽어도 소용없는 자리가 있습니다.** 전환은 며칠 뒤에도 들어옵니다.

**4-2. 읽는 방식은 셋입니다**

| 방식 | 어떻게 | 누가 | 잡이 도는 시간 |
|---|---|---|---|
| 계속 붙어 있기 | 새 줄이 생기면 바로 받습니다 | 대시보드, 예산 소진 | **24시간** |
| 주기로 몰아 읽기 | 5분마다 그동안 쌓인 것을 | 광고주 리포트 | 5분마다 몇 초 |
| 하루 한 번 | 새벽에 하루치를 파일로 | 모델 학습 | 새벽 20분 |

- 네 번째가 하나 더 있는데 주기가 아닙니다 — **되감기.** 피처를 바꿔 3일치를 다시 읽는 일회성입니다. 5절이 이어받습니다.
- 방식을 눌러 바꾸면 4-1 표의 「늦으면」 칸이 같이 바뀝니다. 리포트를 「하루 한 번」으로 돌리면 광고주가 오늘 숫자를 못 봅니다.

**4-3. 같은 클릭이 두 경로로 갑니다** (ML 엔지니어 자리)

- 내 **학습 데이터**는 「하루 한 번」에서 나옵니다.
- 그런데 내 모델이 서빙될 때 쓰는 **피처**는 「계속 붙어 있기」에서 나올 수 있습니다 (피처 스토어).
- 같은 클릭 한 건이 두 갈래로 갈라져 서로 다른 주기로 흐릅니다. **둘이 어긋나면 학습 때 본 값과 서빙 때 보는 값이 달라집니다.**
- 여기서 기존 글 [피처 스토어와 서빙](post.html?id=feature-store-serving) 으로 링크를 답니다. 이 페이지에서는 더 파지 않습니다.

**5절 — 기다렸다 가져가도 됩니까** (질문 10)

- 답: **보존 기간 안에서는 됩니다.** 우리 답은 7일입니다.
- 슬라이더(보존 1~30일) + `[학습을 N일 멈췄다]` 버튼. 보존 7일이면 3일 멈춰도 살고, 2일이면 하루치가 사라집니다.
- 디스크 표를 그대로 씁니다 — 3일 14% · **7일 32%** · 14일 64% · 30일 138%(안 들어감).
- 초심자가 제일 헷갈리는 자리 두 개를 콕 집습니다.
  - **읽어 가도 안 지워집니다.** 시간이 지나서 지워지는 것입니다
  - 커서 위치도 저장돼 있어서, 소비자를 새로 띄우면 "처음부터"인지 "이어서"인지 골라야 합니다
- 되감아도 저절로 복구되지 않는 것도 한 줄 — 밀린 것을 읽는 동안에도 새 줄은 초당 2,665건씩 들어옵니다. 4명이면 3일치에 14.1일, 12명이면 1.1일입니다. **되감는 속도의 상한도 partition 수입니다.**

**6절 — 그 주기를 지키려면 무엇이 필요합니까** (질문 11 · 13)

4절이 「왜 그 주기인가」를 답했습니다. **6절은 수단만 맡습니다** — 그 주기를 지키려면 무엇을 세우고 얼마를 내야 하는지.

- 먼저 한 줄: **같은 topic 을 넷이 각자 읽습니다.** 실시간 쪽과 배치 쪽이 서로 방해하지 않습니다. 이것이 3절에서 Kafka 를 세운 값이 실제로 회수되는 자리입니다.

| 읽는 쪽 | 주기 | 어떻게 읽나 | 흔히 쓰는 제품 | 어디에 쌓나 |
|---|---|---|---|---|
| 실시간 대시보드 | 2초 | 붙어서 한 건씩 | Flink · Kafka Streams | ClickHouse |
| 예산 소진 확인 | 5초 | 붙어서 합계만 | Flink | 집계 결과 |
| 광고주 리포트 | 5분 | 5분마다 모아서 | Spark 마이크로배치 | 리포트용 DB |
| 모델 학습 | 다음 날 새벽 | 하루치를 파일로 | Spark · Airflow | Iceberg + 스토리지 |

- **비용이 갈리는 축은 「잡이 몇 시간 떠 있나」입니다.** 2초를 고르면 24시간 도는 잡과 그것을 받칠 서버가 항상 필요합니다. 다음 날이면 새벽에 20분만 돌면 됩니다.
- 목적지가 여섯이고 포맷·쓰기 방식·재시도가 다 다르다는 것도 여기서 한 표로 보입니다 (`data-distribution-layer` 1절). 재시도 횟수도 마감이 정한 값입니다 — 대시보드는 2초 안에 못 쓰면 포기하고, 다른 팀 Kafka 는 마감이 없어 될 때까지 재시도합니다.
- ML 엔지니어에게 중요한 함정 하나: **실시간 쪽 숫자와 배치 쪽 숫자가 안 맞는 것이 정상입니다.** 늦게 온 로그 때문입니다. 대시보드 CTR 과 학습 데이터 CTR 이 다른 이유가 이것입니다.

**7절 — 내 학습 데이터는 여기서 나옵니다** (질문 14)

- 클릭 한 건이 학습 행 한 줄이 되기까지. 노출과 클릭을 `req_id` 로 붙여야 라벨이 생깁니다.

```json
{"req_id":"r-8f21","ad_id":9931,"slot":"main_top","media":"A앱","pctr":0.0213,"bid":182.4,"ts":1786000101}
```
```json
{"req_id":"r-8f21","ad_id":9931,"slot":"main_top","media":"A앱","bid":182.4,"y":1}
```

- 붙이기 위젯 — 노출 6줄과 클릭 1줄을 놓고 `req_id` 로 이어 붙이면 `y=1` 하나, `y=0` 다섯이 나옵니다. **위젯은 붙이는 방법만 보입니다.** 실제 비율은 하루치로 재야 나오고 그 값이 1.00%(228만 ÷ 2.28억)입니다. 표본 일곱 줄로 1% 를 만들 수는 없으니 둘을 같은 문장에 두지 않습니다.
- 붙이는 창을 3시간과 24시간으로 바꿔 봅니다. 24시간이면 11,400건을 더 건지는데 228만의 0.5% 이고, 그 0.5% 를 사려고 학습 데이터 확정이 21시간 늦어집니다.
- ML 엔지니어가 실제로 만나는 것 셋으로 닫습니다.
  1. 라벨이 늦게 옵니다 — 전환은 며칠 뒤입니다
  2. 붙이는 열쇠가 `req_id` 입니다 — **1페이지에서 그 필드를 빼먹으면 여기서 라벨이 안 붙습니다**
  3. 대시보드 숫자와 내 학습 데이터 숫자가 다릅니다
- 1페이지 5절로 되돌아가는 링크를 답니다.

## 8. 형식 규칙과 검증

| 규칙 | 값 |
|---|---|
| 모서리 | `border-radius: 0` — 예외 없음 |
| 그림자 | `box-shadow: none` (inset 밑줄만) |
| 색 | hex 를 박지 않습니다. `var(--text-primary)` 같은 저장소 토큰만. 계열이 넷 이상 필요하면 `--series-1..6`, 그 전에 채움/테두리로 가를 수 있는지 먼저 봅니다 |
| 이모지·장식 글자 | 안 씁니다. 상태는 글자 라벨로. `→ ▸ ▲ ▾ ×` 는 허용 |
| 한 줄 | 표 셀·카드 120자 아래 |
| 나열 구분자 | 쉼표. 가운뎃점 안 씁니다 |
| 넓은 것 | 스크롤 상자에 담습니다. 375px 에서 `document.scrollWidth == clientWidth` 확인 |
| SVG `marker` id | 페이지 안에서 유일하게. 접두사 + 절 번호 (`apc3-arr`) |

**검증 절차**

1. `node scripts/check-design.js demo-api-course.html demo-pipeline-course.html`
2. `python3 -m http.server` 로 띄우고 라이트·다크 둘 다 눈으로 봅니다
3. 375px 폭에서 가로 스크롤이 없는지 확인
4. 배지·칩이 맨 글자로 나온 것이 없는지 확인 (없는 색 이름을 준 것입니다)

⚠ `check-design.js` 는 `<style>` 과 `style=""` 만 봅니다. **JS 안의 색은 검사 밖입니다.** JS 에서도 `var(--...)` 만 쓰고, canvas 를 쓰면 `var()` 가 조용히 실패하므로 `cssVar()` 헬퍼 + 폴백 상수를 씁니다.
