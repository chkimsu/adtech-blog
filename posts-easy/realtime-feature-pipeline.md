지훈 씨는 모델 팀에 온 지 11주째입니다. 팀에는 동영상 광고의 완주율(영상을 끝까지 본 비율)을 피처(모델이 점수를 매길 때 입력으로 받는 값)로 쓰는 모델이 있었는데, 정작 그 피처 값이 언제 적힌 값인지는 아무도 몰랐습니다. 사용자가 영상을 재생하거나 멈출 때마다 앱이 보내는 재생 이벤트가 나간 뒤 모델이 바뀐 값을 읽기까지 몇 초가 걸리느냐고 물어도 돌아오는 답은 「거의 바로」뿐이었습니다.

선배는 같은 구조를 노트북에 띄워 놓고 이벤트를 직접 보내 보라고 권했습니다. 지훈 씨는 사용자 u42 가 영상 v7 을 보는 동안 생기는 이벤트 다섯 건을 한 건씩 보내면서 이벤트가 지나가는 자리마다 돌아온 응답을 기록했습니다.

**앱에서 나간 이벤트 한 건이 모델이 읽는 피처 값이 되기까지, 어디를 지나며 얼마나 걸릴까요?**

이벤트가 피처 값이 되기까지 지나는 이 길을 실시간 피처 파이프라인이라고 부릅니다. 길은 API(앱이 보낸 요청을 받는 서버)가 이벤트를 받는 데서 시작합니다. 이벤트는 받은 순서대로 쌓아 두는 Kafka 와 그 이벤트를 읽어 값을 더하는 처리기를 차례로 거쳐 더한 값을 두는 Redis 에 닿습니다. 피처 값이 늦게 바뀌면 모델이 읽는 값에는 방금 광고를 끝까지 본 기록이 아직 들어 있지 않아서 그 사용자에게 같은 광고가 또 나갑니다. 장애가 났을 때 처리를 다시 돌릴지 버릴지도 피처가 몇 초 늦는지와 처리기가 멈췄을 때 값이 사라지는지를 알아야 정할 수 있습니다.

> **한 줄 요약:** 앱이 보낸 이벤트 한 건은 API 와 Kafka 를 몇 ms(밀리초) 만에 지나는데, 처리기가 도착 순서가 뒤바뀐 이벤트를 바로잡으려고 읽은 이벤트를 2초 들고 있다가 적용하므로 Redis 의 값은 보낸 지 2,035ms 뒤에야 바뀝니다. 처리기를 12초 멈춘 동안에도 이벤트는 Kafka 에 남아 있어서 아직 처리하지 않은 메시지 수(lag)가 늘기만 했을 뿐 다시 켜자 쌓인 메시지가 한꺼번에 적용되어 잃은 이벤트가 없었습니다. 이렇게 써 둔 피처를 읽어 추천 점수를 내는 요청은 5.2ms 가 걸리고 그중 4.0ms 가 모델 서버(모델을 띄워 점수를 계산해 주는 서버)를 한 번 다녀오는 시간입니다.

> **골라 읽는 법** — 절이 7개이고 절마다 표나 코드나 기록 재생 그림이 하나씩 들어 있어서 그 표와 코드와 그림만 보고 넘어가도 됩니다.
>
> - 이벤트 한 건이 지나는 다섯 자리와 자리마다 걸린 시간 → 1절
> - Kafka 가 이벤트에 준 자리, partition 과 offset → 2절
> - 처리기가 이벤트를 2초 들고 있는 까닭과 그 규칙을 옮긴 파이썬 코드 → 3절
> - 이벤트를 적용한 뒤 Redis 에 남는 값 → 4절
> - 처리기가 멈춘 동안 늘어나는 lag → 5절
> - 피처를 읽어 점수를 내는 요청의 5.2ms → 6절
> - 담장 안(앱과 광고 서버와 로그를 한 회사가 모두 가진 곳)과 열린 RTB(광고를 싣는 매체와 광고 서버가 서로 다른 회사이고 거래소의 실시간 경매로 광고를 고르는 시장)의 차이 → 7절

이 글의 숫자는 설명을 위해 지어낸 값이 아니라 노트북 한 대에 Kafka 브로커(Kafka 를 이루는 서버) 하나와 Redis, 처리기, API, 모델 서버를 함께 띄우고 직접 측정한 값입니다. 운영 서버에서 측정하면 ms 의 크기는 이 값과 다르지만 어느 자리가 시간을 많이 쓰는지는 같습니다. 글에 넣은 그림 3개는 그때 기록해 둔 응답을 받은 시간 순서대로 다시 그려 보여 줍니다.

## 1. 이벤트 한 건이 지나는 다섯 자리와 걸린 시간

**재생을 멈춘 이벤트(PAUSE) 한 건은 API, Kafka, 처리기, Redis 를 지나 다시 API 로 읽히며 다섯 자리 가운데 처리기만 시간을 씁니다.**

「거의 바로」라는 답으로는 피처가 몇 초 늦은 값인지 알 수 없으므로, 지훈 씨가 보낸 이벤트 한 건을 자리마다 따라가 시간이 어디서 드는지부터 봅니다.

사용자가 재생을 멈추는 순간 앱은 이벤트 하나를 만듭니다. 이벤트에는 누가(user_id), 어떤 영상에서(video_id), 무엇을 했는지(action), 언제(ts)가 적혀 있습니다. action 에는 시작, 재생, 멈춤, 끝을 뜻하는 START, PLAY, PAUSE, END 같은 값이 들어갑니다. 앱은 이 이벤트를 JSON(이름과 값을 짝지어 적는 글자 형식)으로 적어 HTTP 요청 하나에 담아 API 로 보냅니다. API 는 받은 이벤트를 들고 있지 않고 곧바로 Kafka 에 넘기는데, Kafka 브로커가 「받았다」고 답하기까지 1.2ms 가 걸렸습니다.

Kafka 에 넘어간 이벤트는 받은 순서대로 쌓입니다. 이렇게 쌓인 이벤트를 읽어 피처 값을 더하는 프로그램이 처리기인데, 이 실습 환경의 처리기는 읽은 이벤트를 바로 적용하지 않고 2초 동안 들고 있다가 적용합니다. 처리기가 이벤트를 적용하기 전에 들고 있는 이 시간을 hold 라고 부릅니다. 처리기는 hold 동안 모인 이벤트를 이벤트 시각 순서로 정렬해 적용합니다. 왜 정렬하는지는 3절에서 봅니다. hold 때문에 다섯 자리가 쓰는 시간은 고르지 않아서 앞의 두 자리인 API 와 Kafka 는 1ms 남짓에 끝나지만 셋째 자리인 처리기는 2초를 씁니다.

아래 표는 사용자 u42 가 영상 v7 을 12초 동안 보다가 멈춘 PAUSE 한 건을 다섯 자리에서 따라간 기록입니다. 시간은 이벤트를 API 로 보낸 순간을 0 으로 놓고 측정했으므로 자리마다 보낸 뒤 그 자리가 하는 일을 마치기까지 걸린 시간이 적혀 있습니다. 2번 자리에 적힌 topic, partition, offset 은 Kafka 가 이벤트를 둔 자리를 나타내는 값(topic 은 이벤트 종류, partition 은 topic 을 나눈 줄, offset 은 줄 안의 자리 번호)이며 2절에서 자세히 풉니다. 4번 자리에 나오는 Hash 는 키 하나 안에 필드 여러 개를 두는 Redis 자료형이고 playtime_sec 은 그 Hash 에서 누적 재생 초를 담는 필드입니다.

| 자리 | 하는 일 | 보낸 뒤 걸린 시간 |
|---|---|---|
| 1. API | 이벤트를 받아 Kafka 에 넘긴다 | 0ms |
| 2. Kafka | topic play_events 의 partition 3, offset 710 에 둔다 | 1.2ms |
| 3. 처리기 | 2초 들고 있다가 이벤트 시각 순서로 정렬해 적용한다. 12초를 더한다 | 2,035ms |
| 4. Redis | Hash 의 playtime_sec 이 0 에서 12 로 바뀐다 | 2,123ms 에 확인 |
| 5. API | 그 Hash 를 읽어 돌려준다 | 2,127ms |

표에서 Kafka 가 답한 1.2ms 와 처리기가 적용한 2,035ms 를 나란히 놓으면 보낸 뒤 적용까지 걸린 시간 가운데 API 와 Kafka 의 몫은 1.2ms 뿐이고 나머지는 거의 모두 처리기가 이벤트를 들고 있던 hold 2초입니다. Redis 의 값은 3번에서 처리기가 이벤트를 적용한 그 순간에 바뀌었습니다. 표 4번의 2,123ms 는 기록할 때 0.25초마다 Redis 를 읽다가 바뀐 값을 처음 본 시각이라 값이 실제로 바뀐 2,035ms 보다 조금 늦습니다. 다섯 건 모두 보낸 뒤 적용되기까지 2,029ms 에서 2,042ms 사이가 걸려 다른 네 건도 PAUSE 와 비슷했습니다. 아래 그림에서 다섯 건 가운데 하나를 고르면 그 이벤트가 자리마다 남긴 기록을 시간 순서대로 다시 볼 수 있습니다.

## 2. Kafka 가 이벤트에 주는 자리, topic 과 partition 과 offset

**Kafka 는 PAUSE 한 건을 받고 「partition 3 의 710번 자리」라고 답했습니다. API 가 이벤트에 붙여 보내는 key 가 같으면 이벤트는 늘 같은 partition 에 차례로 들어갑니다.**

1절 표의 2번 자리에 적힌 값은 Kafka 가 이 자리를 어떻게 정하는지 알아야 읽을 수 있는데, 그 방식에 따라 처리기가 한 사용자의 이벤트를 어떤 순서로 읽을지도 달라집니다.

Kafka 는 이벤트를 종류마다 이름을 붙여 나눠 두고 이 이름을 topic 이라고 부릅니다. 이 실습 환경의 재생 이벤트는 모두 topic play_events 로 들어갑니다. topic 하나는 다시 partition 이라는 줄 여러 개로 나뉘는데 play_events 는 partition 이 4개입니다. Kafka 안에서는 이벤트 한 건을 메시지 하나라고 부릅니다. partition 안의 메시지는 들어온 차례대로 0 부터 하나씩 늘어나는 자리 번호를 받고 이 번호를 offset 이라고 부릅니다.

이벤트가 partition 4개 가운데 어디로 갈지는 key 가 정합니다. key 는 메시지마다 붙여 보내는 값인데, 이 실습의 API 는 이벤트의 user_id 를 key 로 붙여 보냅니다. Kafka 는 key 를 해시해(정해진 계산으로 숫자로 바꿔) 그 값을 partition 수로 나눈 나머지를 partition 번호로 씁니다. 같은 key 는 언제 해시해도 같은 숫자가 나오므로 key 가 같은 이벤트는 늘 같은 partition 으로 갑니다. u42 를 해시한 값을 partition 수 4 로 나눈 나머지가 3 이었으므로 u42 의 이벤트 다섯 건은 모두 partition 3 에 들어가 708, 709, 710, 711, 712번 자리를 차례로 받았습니다.

Kafka 가 이 자리에 실제로 무엇을 두었는지 보려고 다섯 건 가운데 PAUSE 한 건을 Kafka 에서 다시 읽어 왔습니다.

```json
{
  "partition": 3,
  "offset": 710,
  "timestamp_ms": 1793436831018,
  "key": "u42",
  "value": {
    "event_id": "u42-v7-1793436831-PAUSE-5afe",
    "user_id": "u42",
    "video_id": "v7",
    "action": "PAUSE",
    "ts": 1793436831,
    "sent_at": 1793436831.018
  }
}
```

value 바깥에 있는 partition 3 과 offset 710 은 1절 표의 2번 자리에 적힌 값입니다. key 에는 API 가 붙인 u42 가 들어 있고 value 에는 앱이 보낸 이벤트가 들어 있습니다. value 의 ts 1793436831 은 사용자가 재생을 멈춘 초 단위 시각으로 3절의 처리기가 이벤트를 정렬할 때 쓰는 값입니다. event_id 는 이벤트마다 다르게 붙는 식별자로 4절에서 같은 이벤트가 두 번 들어왔는지 확인할 때 쓰입니다.

Kafka 는 partition 하나 안에서는 메시지가 들어온 순서를 지켜 주지만 partition 이 다르면 순서를 지켜 주지 않으므로, 한 사용자의 이벤트를 같은 partition 에 모아야 처리기가 그 사용자의 이벤트를 들어온 순서대로 읽습니다. 만약 한 사용자의 START, PLAY, PAUSE 가 서로 다른 partition 에 흩어져 있다면 처리기가 PAUSE 를 PLAY 보다 먼저 읽을 수 있습니다.

처리기는 consumer group playtime-agg 라는 이름으로 Kafka 를 읽습니다. consumer group 은 같은 topic 을 나눠 읽는 처리기들을 한 이름으로 부르는 단위입니다. 처리기는 그룹 이름으로 partition 마다 「어디까지 읽었나」를 Kafka 에 적어 두는데, 이렇게 적어 둔 자리를 커밋한 offset 이라고 부릅니다. 처리기가 꺼졌다가 다시 켜지면 커밋한 offset 부터 이어 읽습니다. 처리기가 읽어 간 메시지도 Kafka 에서 지워지지 않고 보관 기간(Kafka 가 메시지를 남겨 두는 기간) 동안 남아 있습니다. 이어 읽을 자리가 Kafka 에 적혀 있고 그 뒤의 메시지도 남아 있으므로 5절에서처럼 처리기를 멈췄다가 다시 켜도 멈춘 동안 들어온 이벤트를 이어서 읽을 수 있습니다.

partition 수는 한 그룹에서 처리기를 몇 개까지 늘려 쓸 수 있는지도 정합니다. 한 그룹 안에서 partition 하나는 처리기 하나만 읽으므로, partition 이 4개인 play_events 를 처리기 5개가 읽으면 4개가 partition 을 하나씩 맡고 다섯째 처리기는 받을 partition 이 없어 아무것도 읽지 않습니다. 다음 절에서는 처리기가 이렇게 읽은 이벤트를 왜 바로 적용하지 않고 2초 동안 들고 있는지를 봅니다.

## 3. 도착 순서를 바로잡는 2초 hold

**처리기는 읽은 이벤트를 2초 들고 있다가 그동안 모인 이벤트를 이벤트 시각(ts) 순서로 정렬해 적용하므로, PAUSE 가 PLAY 보다 먼저 도착해도 2초 안에 PLAY 가 도착하면 재생 초를 12초로 맞게 셉니다.**

2절의 partition 이 지켜 주는 순서대로 이벤트를 받자마자 적용해도 재생 초를 잃을 수 있습니다.

처리기는 재생 초를 다음 규칙으로 셉니다. PLAY 가 오면 재생 구간을 열어 PLAY 의 시각을 적어 둡니다. PAUSE 나 END 가 오면 열린 구간을 닫고 그 이벤트의 시각에서 열린 시각을 뺀 초를 누적 재생 초에 더합니다. 열린 구간이 없을 때 온 PAUSE 는 뺄 시각이 없으므로 아무것도 더하지 않고 무시합니다. 이 뺄셈은 PLAY 가 PAUSE 보다 먼저 적용되어야 맞는 값이 나오므로 규칙 전체가 이벤트를 적용하는 순서에 달려 있습니다.

그런데 같은 partition 이 지켜 주는 순서는 사용자가 버튼을 누른 순서가 아니라 이벤트가 Kafka 에 도착한 순서입니다. 지하철에서 휴대폰이 PLAY 를 늦게 보내거나 PLAY 를 보낸 첫 요청이 실패해 다시 보내면 PAUSE 가 PLAY 보다 먼저 도착해 처리기도 PAUSE 를 먼저 읽습니다. 그래서 처리기는 읽은 이벤트를 바로 적용하지 않고 2초 동안 들고 있다가 그동안 모인 이벤트를 이벤트가 찍힌 시각(ts) 순서로 정렬한 뒤 적용합니다. 1절에서 hold 라고 부른 시간이 이 2초입니다.

hold 가 정말 재생 초를 지키는지 보려고 아래 코드는 처리기의 규칙을 함수 count 로 옮긴 뒤, 순서가 뒤바뀌어 도착한 두 이벤트를 한 번은 도착한 순서대로 세고 한 번은 시각 순서로 정렬해 셉니다. 두 이벤트는 1절의 기록과 같은 값인 3초에 누른 PLAY 와 15초에 누른 PAUSE 입니다. 코드는 PAUSE 가 먼저 도착했다고 가정합니다.

```python
# 하는 일: 순서가 뒤바뀌어 도착한 PLAY 와 PAUSE 로 누적 재생 초를 도착 순서와 시각 순서로 한 번씩 센다.
# 1단계: 도착한 이벤트를 둔다
# 3초에 누른 PLAY 와 15초에 누른 PAUSE 가 있다. PAUSE 가 먼저 도착했다고 가정한다.
arrived = [('PAUSE', 15), ('PLAY', 3)]

# 2단계: 처리기의 규칙을 함수로 둔다
# PLAY 는 구간을 연다. PAUSE 는 열린 구간이 있으면 닫고 시각의 차이를 더한다. 없으면 무시한다.
def count(events):
    open_ts, total, notes = None, 0, []
    for action, ts in events:
        if action == 'PLAY':
            open_ts = ts
            notes.append(f'{action}@{ts} 구간 열림')
        elif open_ts is not None:
            total += ts - open_ts
            notes.append(f'{action}@{ts} {ts - open_ts}초 더함')
            open_ts = None
        else:
            notes.append(f'{action}@{ts} 열린 구간이 없어 무시')
    return total, notes

# 3단계: 도착 순서 그대로 센다
# hold 가 0 초인 처리기다.
total, notes = count(arrived)
print(f'도착 순서: 누적 {total}초 | ' + ', '.join(notes))

# 4단계: 시각 순서로 정렬해 센다
# hold 동안 모인 것을 ts 로 정렬한 뒤 적용하는 처리기다.
total, notes = count(sorted(arrived, key=lambda e: e[1]))
print(f'시각 순서: 누적 {total}초 | ' + ', '.join(notes))

# 출력:
# 3단계 뜻: 도착한 대로 적용하면 PAUSE 가 버려지고 PLAY 는 열린 채 남아 12초를 잃는다.
# 도착 순서: 누적 0초 | PAUSE@15 열린 구간이 없어 무시, PLAY@3 구간 열림
# 4단계 뜻: 시각 순서로 정렬하면 1절 기록과 같은 12초가 나온다.
# 시각 순서: 누적 12초 | PLAY@3 구간 열림, PAUSE@15 12초 더함
```

3단계는 hold 가 0초인 처리기처럼 도착한 대로 적용해 「도착 순서: 누적 0초」를 찍었습니다. 먼저 온 PAUSE@15 는 열린 구간이 없어 무시되고 뒤에 온 PLAY@3 은 구간을 연 채로 남아 12초를 잃었습니다. 4단계는 같은 두 이벤트를 ts 로 정렬해 PLAY@3 을 먼저 적용하므로 PAUSE@15 가 열린 구간을 닫으면서 15 에서 3 을 뺀 12초를 더합니다. 그래서 4단계의 출력은 1절 기록과 같은 「시각 순서: 누적 12초」입니다.

hold 를 두면 피처가 2초 늦어지는 대신 순서가 뒤바뀐 이벤트도 맞게 셀 수 있는데, 바로잡는 범위는 2초 안에 도착한 뒤바뀜까지입니다. 그보다 늦게 온 이벤트는 함께 정렬되었어야 할 이벤트가 hold 2초를 마치고 이미 적용된 뒤에 도착하므로 바로잡을 수 없습니다. 이 처리기는 그런 이벤트의 시각이 그 사용자와 영상에서 마지막으로 적용한 이벤트의 시각보다 과거이면 버리고 버린 수를 따로 셉니다. 늦게 온 이벤트까지 모두 받으려면 hold 를 늘려야 하는데 hold 를 늘린 만큼 모든 피처가 늦어집니다.

그래서 hold 는 모든 피처에 같은 길이로 두지 않고 피처마다 다르게 둡니다. 재생 초나 완주율처럼 두 이벤트의 시각을 빼서 세는 피처는 순서가 바뀌면 값이 틀리므로 hold 를 둡니다. 반면 클릭 수처럼 값을 더하기만 하는 피처는 이벤트가 어떤 순서로 와도 합이 같으므로 hold 를 두지 않고 들어오는 대로 셉니다. 다음 절에서는 이렇게 센 값이 Redis 에 어떤 모양으로 남는지 봅니다.

## 4. 다시 만들 수 있는 값만 두는 Redis

**처리기는 이벤트 한 건을 적용할 때 Redis 에 있는 Hash 의 필드 몇 개만 고칩니다. PAUSE 한 건으로 누적 재생 초 playtime_sec 은 0 에서 12 로, 적용한 이벤트 수 events 는 2 에서 3 으로 바뀌었습니다.**

처리기가 고친 값은 모델 서버 앞의 API 가 요청마다 읽어 가므로 빨리 읽혀야 하는데, Redis 는 빠른 대신 꺼지면 값이 사라질 수 있어 어떤 값을 Redis 에 둘지 미리 정해 두어야 합니다.

Redis 는 키 하나에 값 하나를 짝지어 메모리에 두는 키-값 저장소입니다. 이 실습 환경은 사용자와 영상 한 쌍마다 키를 하나씩 만듭니다. u42 와 v7 의 키는 feat:user:u42:video:v7 입니다. 그 값의 자료형은 1절에서 본 Hash 라서 키 안의 필드 하나만 골라 따로 고칠 수 있습니다.

아래 표는 PAUSE 한 건을 보내기 바로 전과 처리기가 적용한 뒤에 같은 키를 읽어 나란히 놓은 값입니다. Redis 는 값을 모두 글자(문자열)로 저장하므로 표의 숫자도 Redis 안에서는 글자입니다.

| 필드 | 뜻 | 보내기 전 | 적용한 뒤 |
|---|---|---|---|
| playtime_sec | 누적 재생 초 | 0 | 12 |
| completed | 완주. 1 이면 END 까지 봄 | 0 | 0 |
| open_play_ts | 열린 PLAY 의 시각 | 1793436819 | (빈 값) |
| last_ts | 마지막으로 적용한 이벤트 시각 | 1793436819 | 1793436831 |
| events | 적용한 이벤트 수 | 2 | 3 |

표의 값으로 처리기가 PAUSE 를 적용한 계산을 한 단계씩 따라갈 수 있습니다. 보내기 전 open_play_ts 에는 열린 PLAY 의 시각 1793436819 가 적혀 있었습니다. PAUSE 의 시각 1793436831 에서 이 값을 빼면 12 이므로 playtime_sec 은 0 에서 12 로 바뀌었습니다. 구간이 닫히면서 open_play_ts 는 빈 값이 되었고 last_ts 는 방금 적용한 PAUSE 의 시각 1793436831 로, events 는 2 에서 3 으로 바뀌었습니다. completed 는 END 가 아직 오지 않아 0 그대로입니다.

같은 PAUSE 한 건으로 바뀌는 키는 이 Hash 말고도 3개가 더 있습니다. viewers:v7 은 영상 v7 을 본 사용자를 모은 Set(같은 값을 한 번씩만 담는 집합)입니다. rank:videos 는 영상마다 누적 재생 초를 점수로 매겨 순위를 두는 ZSet(값마다 점수를 붙여 점수 순으로 정렬해 두는 집합)입니다. dedupe: 로 시작하는 키는 그 event_id 를 이미 처리했다는 표시를 String(글자 값 하나)으로 적어 둔 중복 표시입니다. 이 키의 TTL(키를 만든 뒤 저절로 지워지기까지의 시간)은 300초입니다. 앱이 같은 event_id 를 다시 보내면 처리기는 이 표시를 보고 그 이벤트를 버리므로 같은 이벤트가 두 번 더해지지 않습니다. END 까지 다섯 건을 모두 적용한 뒤 u42 의 누적 재생 초는 30, completed 는 1 이었습니다.

API 가 이 Hash 를 읽는 데는 0.2ms 가 걸렸습니다. 요청 하나에 쓸 수 있는 시간을 예산이라고 합니다. 모델 서버 앞의 API 는 요청 하나마다 피처를 수십 개씩 읽어야 해서 한 번 읽는 데 1ms 를 넘기면 예산이 모자라므로 이렇게 빨리 읽히는 Redis 에 피처를 둡니다. 대신 Redis 는 값을 메모리에 두므로 Redis 가 꺼지면 값이 사라질 수 있습니다.

그래서 Redis 에는 값이 사라져도 Kafka 에 남은 이벤트로 다시 만들 수 있는 값만 둡니다. 커밋한 offset 을 처음으로 되돌려 처리기가 보관 기간 안의 이벤트를 다시 읽게 하면 Redis 가 같은 값으로 다시 채워집니다. 보관 기간을 넘겨 Kafka 에서 지워진 이벤트는 데이터 레이크(원본 데이터를 오래 쌓아 두는 큰 저장소)에서 가져와야 하므로, Redis 를 잃었을 때 복구에 걸리는 시간은 값을 이렇게 다시 만드는 데 걸리는 시간과 같습니다. 다음 절에서는 Redis 가 아니라 처리기가 멈췄을 때를 봅니다.

## 5. 처리기가 멈춘 동안 늘어나는 lag 과 따라잡기

**lag 은 partition 의 끝 offset(다음 메시지가 들어갈 자리)에서 처리기가 커밋한 offset 을 뺀 수입니다. 처리기를 12초 멈추자 lag 은 80 에서 552 로 늘었고 다시 켜고 2초 뒤 80 으로 돌아왔습니다.**

글 첫머리에서 장애 때 처리를 다시 돌릴지 버릴지 정하려면 처리기가 멈췄을 때 값이 사라지는지를 알아야 한다고 했습니다. 이 실습은 처리기를 일부러 멈췄다가 다시 켜면서 그동안 Kafka 에 쌓이는 메시지 수를 지켜봅니다.

lag(consumer lag)은 Kafka 에 들어왔지만 처리기가 아직 처리하지 않은 메시지 수입니다. partition 마다 끝 offset 에서 커밋한 offset 을 빼면 그 partition 의 lag 이 나옵니다. play_events 전체의 lag 은 partition 4개의 lag 을 더한 값입니다.

이 실습에서는 사용자 40명이 영상 5편을 보는 이벤트를 초당 40건씩 28초 동안 보내면서 6초에 처리기를 멈췄다가 18초에 다시 켰으므로, 처리기는 18 에서 6 을 뺀 12초 동안 멈춰 있었습니다. 이벤트를 보내는 동안 0.5초 간격으로 lag 과 영상 v11 의 누적 재생 초를 읽어 기록해 두었습니다. 아래 표는 그 기록 가운데 6개 시각의 값입니다.

| 기록 시각 | 처리기 | lag | v11 누적 재생 초 |
|---|---|---|---|
| 5초 | 도는 중 | 80 | 9 |
| 8초 | 멈춤 | 80 | 25 |
| 14초 | 멈춤 | 312 | 25 |
| 20초 | 다시 켠 직후 | 552 | 25 |
| 21초 | 도는 중 | 80 | 75 |
| 27.6초 | 도는 중 | 80 | 103 |

처리기는 이벤트를 적용한 뒤에 커밋하는데 읽은 이벤트를 2초 동안 들고 있으므로, 처리기가 멀쩡히 도는 5초에도 초당 40건 × 2초 = 80건은 아직 커밋 전이라 lag 이 0 이 아니라 80 입니다. 6초에 처리기를 멈춘 뒤에도 처음 2초 동안은 처리기가 이미 읽어 들고 있던 80건을 마저 적용했습니다. 이 2초 동안 새로 들어온 이벤트 수와 마저 적용해 커밋한 수가 같아 8초의 lag 은 그대로 80 입니다. 그 뒤로는 커밋이 멈춰 lag 이 늘어났고 표의 14초 값 312 에서 20초 값 552 까지는 6초 동안 1초에 40씩 늘었습니다. 그동안 v11 의 누적 재생 초는 8초부터 20초까지 25 에서 움직이지 않았습니다.

18초에 다시 켠 처리기는 커밋한 offset 부터 이어 읽으며 멈춘 동안 쌓인 메시지를 한꺼번에 가져왔습니다. 처리기는 이 메시지들도 2초 들고 있다가 적용했으므로 20초에도 552 이던 lag 은 21초에 80 으로 돌아왔고 v11 의 누적 재생 초도 25 에서 75 로 따라잡았습니다. 마지막 장면인 27.6초까지 보낸 이벤트는 1,096건이고 적용한 이벤트는 1,016건이라 두 수의 차이는 1,096 에서 1,016 을 뺀 80건입니다. 이 80건은 평소의 lag 과 같은 수로 그 순간 처리기가 hold 로 들고 있던 이벤트이므로 잃은 이벤트는 하나도 없습니다. 아래 그림에서 재생을 누르면 partition 4개의 막대와 lag, v11 누적 재생 초를 그린 두 선이 기록한 시각에 맞춰 함께 움직입니다.

## 6. ms 단위로 끝나는 읽는 길

**같은 실습 환경에서 Redis 의 피처를 읽어 추천 점수를 내는 요청 한 건은 5.2ms 가 걸렸습니다. 그중 CPU 가 계산한 시간은 0.85ms 뿐이고 나머지는 Redis 와 모델 서버의 답을 기다린 시간입니다.**

1절부터 5절까지 본 길은 이벤트가 Redis 의 피처 값이 되는 쓰는 길이었습니다. 이 절의 읽는 길은 추천 요청이 그 값을 읽어 점수를 내는 길이며 걸리는 시간이 초가 아니라 ms 단위입니다.

요청 한 건의 응답 시간은 세 가지 시간을 더한 값입니다. 요청이 서버에서 차례를 기다리며 줄에서 보낸 시간, CPU 가 계산한 시간, 그리고 차례로 기다린 I/O 시간입니다. I/O 는 다른 서버나 디스크에 무언가를 묻고 답을 기다리는 일인데, 여러 I/O 를 동시에 보냈다면 그 시간들을 더하지 않고 가장 오래 걸린 하나만 셉니다. 이 요청은 줄이 없는 상태에서 측정했으므로 줄에서 기다린 시간이 들어 있지 않습니다. 표의 값은 구간마다 50번 측정한 값의 가운데 값(크기순으로 놓았을 때 한가운데 오는 값)입니다.

요청은 아래 표의 순서대로 Redis 다섯 구간에서 캐시, 후보 순위, 후보마다의 피처, 내 통계, 영상 통계를 읽은 다음 피처 행렬과 모델에 보낼 JSON 을 만들고 모델 서버를 한 번 다녀와 받은 답으로 응답을 만듭니다.

| 구간 | 걸린 시간 | CPU | 기다림 |
|---|---|---|---|
| Redis 를 읽는 다섯 구간 (캐시, 후보 순위, 후보마다 피처, 내 통계, 영상 통계) | 0.89ms | 0.56ms | 0.33ms |
| 피처 행렬과 모델 입력 JSON 만들기 | 0.26ms | 0.25ms | 0.01ms |
| 모델 서버 왕복 | 3.99ms | 0ms | 3.99ms |
| 답을 풀고 정렬해 응답 만들기 | 0.04ms | 0.03ms | 0ms |

표에서 가장 큰 칸은 모델 서버 왕복의 3.99ms 입니다. 이 값을 요청 전체의 5.2ms 로 나누면 77% 라서 요청 한 건의 시간 대부분을 모델 서버 한 번이 씁니다. 모델 서버 왕복 안에는 네트워크를 한 번 오가는 시간과 모델 서버가 요청 여러 개를 모아 한 번에 계산하려고 기다리는 배칭 대기, 그리고 모델 서버의 계산 시간이 모두 들어 있습니다.

Redis 다섯 구간의 0.89ms 가운데 CPU 가 일한 시간은 0.56ms 로 기다린 시간 0.33ms 보다 깁니다. 같은 컴퓨터 안에서 Redis 를 한 번 다녀오는 왕복은 0.1ms 남짓인데 그 시간도 절반 넘게는 Redis 를 기다린 시간이 아니라 파이썬 코드가 쓴 CPU 시간입니다. 서버가 다른 기계에 있으면 왕복할 때마다 네트워크 시간이 더해집니다. 같은 데이터센터 안에서 한 번 왕복하는 데 보통 0.5ms 안팎이 걸리므로, Redis 다섯 구간이 쓰는 왕복 여섯 번에 0.5ms 씩 더하면 요청 시간이 3ms 쯤 늘어납니다.

아래 그림의 막대는 구간마다 걸린 시간을 CPU 가 일한 시간과 다른 서버의 답을 기다린 시간으로 나눠 보여 줍니다.

쓰는 길과 읽는 길은 서로를 기다리지 않습니다. 추천 요청은 처리기를 기다리지 않고 그 순간 Redis 에 들어 있는 값을 읽어 끝납니다. 처리기도 추천 요청과 상관없이 이벤트를 받은 지 2초 뒤에 그 값을 고칩니다. 그래서 두 길의 예산은 따로 세웁니다. 쓰는 길의 예산은 「몇 초 늦어도 되나」로, 읽는 길의 예산은 「몇 ms 안에 답하나」로 적습니다.

기다린 시간 대부분이 모델 서버 왕복의 3.99ms 에 있고 그 안의 배칭 대기는 설정 하나로 줄어들므로, 요청 시간을 줄이려면 Redis 왕복보다 모델 서버를 먼저 봅니다. 모델 서버는 최근에 들어온 요청을 보고 배칭 대기를 스스로 바꾸기 때문에 같은 환경에서도 모델 서버 구간이 2ms 아래로 내려가기도 하고 9ms 를 넘기도 했습니다.

## 7. 담장 안과 열린 RTB 의 차이, key 와 늦게 오는 이벤트

**다섯 자리의 구조는 담장 안과 열린 RTB 두 무대가 같습니다. 두 무대는 Kafka 의 key 로 쓸 식별자가 얼마나 안정적인지(같은 사람에게 늘 같은 값이 붙는지)와 이벤트가 얼마나 늦게 오는지에서 다릅니다.**

지금까지 본 실습은 user_id 를 key 로 쓰고 2초 hold 로 순서를 바로잡았는데, 이 두 가지가 그대로 통하는지는 이벤트가 어디서 어떤 길로 오는지에 따라 다릅니다.

### 로그인 ID 를 key 로 쓰는 담장 안 [무대: 닫힌 생태계]

담장 안 플랫폼은 앱과 광고 서버와 로그를 한 회사가 모두 가진 곳입니다. 재생 이벤트는 우리 앱이 우리 API 로 보냅니다. Kafka 의 key 로는 로그인한 회원 번호를 씁니다. 회원 번호는 같은 사람이 휴대폰에서 보든 다른 기기에서 보든 바뀌지 않으므로 한 사람의 이벤트는 기기와 상관없이 늘 같은 partition 에 들어가 그 안에서 도착한 순서대로 읽힙니다. 이벤트도 대부분 몇 초 안에 도착하므로 3절의 2초 hold 만으로 도착 순서가 뒤바뀐 경우를 대부분 바로잡습니다.

Kafka 의 보관 기간 안이라면 처리기 코드를 고친 뒤 커밋한 offset 을 되돌려 지난 이벤트를 다시 셀 수 있습니다. 피처 정의를 바꿨을 때 지난 일주일 치 이벤트를 새 정의로 다시 세는 일도 담장 안에서는 이 방법으로 할 수 있습니다.

### 남의 서버를 거쳐 늦게 오는 열린 RTB 의 이벤트 [무대: 열린 RTB]

DSP(광고주를 대신해 입찰하는 플랫폼)가 받는 노출, 클릭, 재생 이벤트는 매체(광고를 싣는 남의 페이지나 앱)에서 추적 요청으로 오거나 거래소(광고 경매를 여는 플랫폼)를 거쳐 들어옵니다. 추적 요청은 이벤트가 일어났음을 알리려고 매체의 페이지나 앱이 보내는 요청입니다. 여러 서버를 거쳐 오는 만큼 늦게 오거나 순서가 바뀌어 오는 이벤트가 많아서 2초 hold 로는 바로잡지 못하는 뒤바뀜도 많습니다. 같은 사용자의 이벤트라도 쿠키(브라우저에 저장해 두는 작은 식별 값)나 기기 ID 가 바뀌면 key 가 달라지므로, 2절의 규칙대로라면 다른 partition 으로 갈 수 있습니다.

그래서 열린 RTB 의 실시간 피처는 이벤트 순서에 덜 기대는 방식으로 만듭니다. PLAY 와 PAUSE 의 시각을 빼서 구간을 세는 재생 초 대신 재생이 어디까지 갔는지 알리는 진행 추적 이벤트를 세는 식입니다. 동영상 광고 표준인 VAST 는 재생이 25%, 50%, 75%, 완료 지점에 닿을 때마다 이벤트를 하나씩 보내는데, 이런 이벤트는 세기만 하면 되므로 3절의 클릭 수처럼 순서가 바뀌어 도착해도 센 개수가 같습니다. 3절의 처리기는 너무 늦게 온 이벤트를 버렸지만 여기서는 늦게 온 이벤트를 버리지 않고 다음 배치(쌓인 데이터를 정해진 때에 한꺼번에 처리하는 작업)에서 반영해 값을 고칩니다. 그래서 실시간 값은 빨리 내는 근삿값이고 정확한 값은 배치가 맞춥니다.

## 한눈 정리

| 자리 | 하는 일 | 이 실습에서 측정한 값 | 결정할 것 |
|---|---|---|---|
| API | 이벤트를 받아 Kafka 에 넘긴다 | Kafka 응답 1.2ms | key 로 무엇을 쓸지 |
| Kafka | partition 과 offset 을 주고 보관한다 | partition 넷, u42 는 모두 3번 | partition 수, 보관 기간 |
| 처리기 | hold 동안 모아 시각 순서로 적용한다 | 적용까지 2,029~2,042ms | 피처마다 hold 길이 |
| Redis | Hash 필드를 고친다 | 읽기 0.2ms | 다시 만들 수 있는 값만 둔다 |
| lag | 끝 offset 에서 커밋 offset 을 뺀 수 | 평소 80, 12초 멈춤에 552 | 알람 문턱 |
| 읽는 길 | 피처를 읽어 점수를 낸다 | 5.2ms, 모델 서버 77% | 모델 서버의 배칭 대기 |

## 헷갈리기 쉬운 점

- **Kafka 가 지켜 주는 순서는 사용자가 누른 순서가 아니라 Kafka 에 도착한 순서입니다.** 사용자가 누른 순서는 이벤트에 적힌 시각(ts)에 남아 있어서 처리기가 hold 동안 ts 로 정렬해 복원합니다.
- **처리기가 멀쩡해도 평소의 lag 은 0 이 아닙니다.** 처리기는 적용한 뒤에 커밋하므로 초당 건수 × hold 만큼은 늘 커밋 전으로 남습니다. 이 실습에서는 초당 40건에 hold 2초라 40 × 2 = 80 이었습니다.
- **처리기가 멈춰도 Kafka 에 들어온 이벤트는 사라지지 않습니다.** 이벤트는 Kafka 에 남아 있다가 처리기를 다시 켜면 커밋한 offset 부터 다시 읽힙니다. 보관 기간을 넘긴 이벤트만 Kafka 에서 지워집니다.
- **hold 는 모든 피처에 같은 길이로 두지 않습니다.** 재생 초처럼 두 이벤트의 시각을 빼서 세는 피처에만 hold 가 필요합니다. 클릭 수처럼 더하기만 하는 피처는 순서가 바뀌어도 합이 같으므로 hold 없이 셉니다.
- **피처의 신선도와 요청의 지연은 서로 다른 숫자입니다.** 신선도는 이벤트가 피처 값에 반영되기까지 걸린 시간으로 이 실습에서는 2초였습니다. 요청의 지연은 추천 요청 한 건이 점수를 받기까지 걸린 시간으로 5.2ms 였습니다. 두 길은 서로를 기다리지 않으므로 두 값을 한 예산에 넣지 않습니다.
- **Redis 는 왕복 한 번이 느린 것이 아니라 왕복 횟수가 문제입니다.** 왕복 한 번은 0.1ms 남짓으로 빠르지만 후보마다 따로 물으면 왕복이 후보 수만큼 늘어나므로 명령 여러 개를 묶어 한 번의 왕복에 보냅니다.
