입사 나흘째다. 메신저에 한 줄이 온다. "MMP 전환 API 붙여 주세요. 문서 링크 드릴게요."

전환을 대신 재 주는 외부 측정 회사를 MMP 라 부른다. 문서에는 주소 하나와 필드 열두 개가 적혀 있다. `POST /v1/conversions` 다. 요청을 만들어 보내는 코드는 30분이면 쓴다. 여기까지는 막히지 않는다.

막히는 것은 그다음이다. 타임아웃을 몇으로 잡나. 답이 안 오면 다시 보내나. 다시 보내면 전환이 두 번 잡히나. 인증키는 어디에 두나. 문서에는 이 넷의 답이 없다. 그런데 넷 중 하나만 틀려도 다음 날 리포트 숫자가 틀어진다.

이 글은 첫 주에 실제로 밟는 것들을 순서대로 본다. 출발점은 "API 붙여 주세요"를 받았을 때 가장 먼저 물어야 할 질문이다. 그 질문은 "무슨 언어로 짜나"가 아니다.

이 글의 숫자는 전부 설명을 위해 지어낸 값이다. 실제 제한시간·쿼터·유실률은 상대 회사마다 다르다.

> **한 줄 요약:** 같은 "API" 라도 부르는 쪽이 남의 기기냐 우리 서버냐에 따라 지켜야 할 것이 통째로 갈린다. 그 위에 얹히는 규약 중 첫 주에 가장 비싼 것은 멱등성이다.

**이 글에 나오는 말** — 낯선 이름만 먼저 풀어 둡니다. 본문에서 다시 설명하니 지금 외울 필요는 없습니다.

| 말 | 한 줄 뜻 |
|---|---|
| client to server | 앱·브라우저가 부른다. 부르는 쪽이 우리 통제 밖이다 |
| server to server | 우리 서버가 상대 서버를 부른다. 양쪽 다 통제된다 |
| 멱등성 (idempotency) | 같은 요청을 몇 번 보내도 결과가 한 번 보낸 것과 같은 성질 |
| 멱등키 | 요청마다 부르는 쪽이 붙이는 고유 값. 재시도해도 같은 값 |
| 지수 백오프 · 지터 (jitter) | 재시도 간격을 1초·2초·4초로 늘리고, 그 시각을 무작위로 흩는 것 |
| mTLS | 서버 둘이 서로의 인증서를 확인하는 연결 방식 |
| HMAC 서명 | 본문과 시각을 비밀키로 해시한 값. 한 글자만 고쳐도 달라진다 |

> **골라 읽는 법** — 절이 10개인 긴 글입니다. 처음부터 다 읽지 않아도 됩니다.
>
> - 두 종류가 왜 갈리는지 → 1~2절
> - REST · gRPC · GraphQL · webhook 중 무엇을 고르나 → 3절
> - 상태코드 · 에러 형식 · 페이지네이션 → 4~5절
> - 필드를 더하고 빼는 법과 버전 → 6절
> - 재시도가 전환을 부풀리는 자리 → 7절
> - 타임아웃 값과 백오프 → 8절
> - 인증 방식 다섯 → 9절
> - 지뢰 목록만 → 10절

## 1. 첫 질문은 "무슨 언어냐"가 아니다

**부르는 쪽이 사용자 기기냐 우리 서버냐. 이 하나가 지켜야 할 것을 통째로 가른다.**

API 는 주소와 형식의 묶음이다. 그런데 같은 주소라도 누가 부르느냐에 따라 전제가 뒤집힌다. 앱이 부르는 API 와 우리 서버가 부르는 API 는 이름만 같지 다른 물건이다. 앞엣것을 client to server 라 부른다. 뒤엣것은 server to server 다.

일곱 축으로 갈라 보면 겹치는 칸이 하나도 없다.

| 축 | client to server | server to server |
|---|---|---|
| 부르는 쪽 | 앱 · 브라우저 — 남의 기기 | 우리 서버 · 상대 서버 |
| 비밀키 | 둘 수 없다 | 둘 수 있다 |
| 인증 | 사용자 토큰(로그인) | 서비스 자격증명 · mTLS · 서명 |
| 요청에 실려 온 값 | 하나도 못 믿는다 | 계약 안이면 믿는다 |
| 트래픽 | 예측 불가 · 스파이크 | 대체로 예측 가능 |
| 버전 | 옛 앱이 몇 년 남는다 | 양쪽이 날짜를 잡고 같이 올린다 |
| 재시도 | 네트워크가 끊긴다는 전제 | 타임아웃 예산 안에서 |

**비밀키 줄부터 보자.** 앱에 넣은 문자열은 앱을 받은 사람 모두가 갖는다. 브라우저면 개발자 도구에서 그대로 보인다. 앱이면 파일을 풀어 문자열만 뽑으면 된다. 명령 한 줄이고, 9절에 그 한 줄을 적어 뒀다. 그래서 client to server 에는 "우리만 아는 값"을 둘 자리가 없다.

**요청 값 줄이 더 자주 사고를 낸다.** 앱이 보낸 본문을 그대로 쓰면 그 값은 사용자가 정한 값이다. 전환 금액을 앱이 보내게 만들었다고 하자. 프록시로 본문 한 글자를 고치면 `39000` 이 `3900000` 이 된다. 서버는 그것이 고쳐진 값인지 알 방법이 없다. 그래서 금액은 앱이 보낸 것을 쓰지 않고 우리 주문 테이블에서 다시 읽는다.

**버전 줄은 시간이 지나야 드러난다.** 서버끼리는 "다음 주 화요일에 같이 올립시다"가 된다. 앱은 안 된다. 앱을 안 올리는 사용자가 몇 년씩 남는다. 그래서 client to server 규약은 한 번 내보내면 되돌리기가 어렵다. 6절이 이 자리를 자세히 본다.

## 2. 광고 쪽 연동 셋을 그 표에 넣어 본다

**앱 SDK 수집 · 입찰 · 전환 포스트백. 셋 다 "API 연동"인데 하나만 client to server 다.**

말로만 두면 안 외워진다. 실제로 붙이게 되는 연동 셋을 1절 표의 칸에 넣어 보자. 우리가 만들어 앱에 심게 하는 라이브러리를 SDK 라 부른다. 아래 값은 전부 설명을 위해 지어낸 가상 수치다.

| 연동 | 부르는 쪽 | 종류 | 규모 · 예산 | 시크릿을 둘 수 있나 |
|---|---|---|---|---|
| 앱 SDK → 수집 서버 | 사용자 기기 | client to server | 초당 2,639건 · 스파이크 있음 | 안 된다 |
| bidder → 거래소 | 우리 서버 | server to server | 응답까지 12ms | 된다 |
| MMP → 전환 수집 API | 상대 서버 | server to server | 하루 1,000건 · 늦게 옴 | 된다 |

초당 2,639건은 하루 노출 로그 2억 2,800만 줄을 86,400초로 나눈 값이다. 이 숫자는 [로그가 Kafka 에 닿기까지](post.html?id=log-hops-to-kafka)와 같은 값을 쓴다. 12ms 는 매체가 입찰 응답을 기다려 주는 시간이고, [요청이 서비스까지 가는 길](post.html?id=gateway-ingress-router)에서 정한 값이다.

전환 포스트백만 규모가 다르다. 하루 1,000건은 광고주 한 곳, 캠페인 하나 기준이다. 노출은 초 단위로 쏟아지지만 전환은 광고주 한 곳 기준으로 하루 네 자리다. 규모가 작다고 쉬운 것은 아니다. 이 1,000건이 정산과 pCVR 라벨을 동시에 만든다.

같은 사고가 세 연동에서 어떻게 다르게 나타나는지 보면 칸이 왜 갈리는지가 분명해진다.

| 무슨 일이 나면 | 앱 SDK → 수집 | bidder → 거래소 | MMP → 전환 API |
|---|---|---|---|
| 응답이 늦다 | 앱이 큐에 쌓아 뒀다 나중에 보낸다 | 12ms 넘으면 그 건은 없던 일 | 상대가 몇 시간 뒤 다시 보낸다 |
| 필드를 하나 지운다 | 옛 앱이 몇 년 남아 계속 깨진다 | 날짜를 잡고 같이 올린다 | 상대 릴리스 일정에 맞춘다 |
| 인증 값이 샌다 | 앱 파일에서 뽑힌다 · 회수 불가 | 인증서 교체로 끝난다 | 키 재발급으로 끝난다 |
| 트래픽이 10배 | 푸시 발송 · 신규 앱 출시 | 계약된 QPS 안에서만 | 상대 배치가 밀렸다 몰아 온다 |

세 번째 줄이 특히 다르다. 서버끼리는 자격증명이 새도 한쪽에서 갈아 끼우면 끝난다. 앱은 그렇지 않다. 이미 배포된 앱 안의 값을 회수할 방법이 없다. 다음 버전에서 값을 바꿔도 옛 버전은 옛 값을 계속 보낸다.

네 번째 줄은 쿼터 설계에 바로 걸린다. 표에 나온 QPS 는 초당 요청 수를 줄여 쓴 말이다. 전환 포스트백은 평소 하루 1,000건이다. 그런데 상대 배치가 6시간 밀리면 그 6시간치가 한 번에 온다. 초당 5건을 상한으로 잡아 두면 정상 동작이 막힌다. 상대는 "너무 많다"는 뜻의 429 를 받는다. 도착 지연 분포를 미리 보고 상한을 잡아야 한다.

| 도착 지연 | 건수 | 누적 |
|---|---|---|
| 1시간 안 | 620 | 62.0% |
| 1~6시간 | 210 | 83.0% |
| 6~24시간 | 110 | 94.0% |
| 1~3일 | 48 | 98.8% |
| 3~7일 | 12 | 100.0% |
| **합계** | **1,000** | — |

이 분포는 지어낸 값이다. 여기서 읽을 것은 두 가지다. 절반 넘게는 한 시간 안에 온다. 그런데 꼬리가 7일까지 있다. 늦게 오는 전환을 어떻게 다룰지는 [지연 피드백](post.html?id=online-learning-delayed-feedback)에서 따로 다룬다. 이 글은 그 전환이 도착하는 순간의 규약만 본다.

## 3. 무엇으로 주고받나 — 규약 다섯

**REST · gRPC · GraphQL · webhook · 배치 파일. 고르는 기준은 취향이 아니라 부르는 쪽과 결과가 나오는 시점이다.**

"API 를 붙인다"는 말 뒤에는 다섯 가지 중 하나가 있다. 셋은 우리가 부르는 것이고, 하나는 상대가 우리를 부르는 것이고, 하나는 아예 파일이다.

| 규약 | 어디서 쓰나 | 브라우저에서 바로 되나 | 대표 모양 | 언제 고르나 |
|---|---|---|---|---|
| REST/HTTP + JSON | 양쪽 다 | 된다 | `POST /v1/conversions` | 기본값 · 상대가 누구든 붙는다 |
| gRPC | 서버 사이 | 안 된다 | `.proto` 스키마 | 우리 서비스끼리 · 초당 수만 건 |
| GraphQL | 주로 client to server | 된다 | 질의 하나로 필요한 필드만 | 화면마다 필요한 것이 다를 때 |
| webhook(콜백) | 서버 사이 | 안 된다 | 상대가 우리 주소를 부른다 | 결과가 언제 날지 모를 때 |
| 배치 파일 | 서버 사이 | 안 된다 | 저장소에 올린 gzip CSV | 하루치를 한 번에 · 정산 대사 |

**gRPC 가 왜 서버 사이에서만 흔한가.** gRPC 는 HTTP/2 위에서 돌면서 프레임과 트레일러를 직접 다룬다. 브라우저의 `fetch` 는 그 층을 건드리지 못한다. 그래서 브라우저에서 쓰려면 grpc-web 을 쓰고 앞에 변환 프록시를 하나 세워야 한다. 프록시를 세우는 순간 이점의 절반이 사라진다. 반대로 서버 사이에서는 스키마가 강제되고 본문이 작다는 이점이 그대로 남는다.

**GraphQL 은 화면이 많을 때 값을 낸다.** 화면 A 는 캠페인 이름만 필요하고 화면 B 는 예산·소진율·전환 수까지 필요하다고 하자. REST 로 하면 주소를 둘로 늘리거나 한쪽이 필요 없는 것까지 받는다. GraphQL 은 필요한 필드를 질의에 적는다. 대신 서버 쪽 복잡도가 올라가고 캐시가 어려워진다. 서버끼리 부르는 자리에서는 이 이점이 거의 없다.

**webhook 만 방향이 거꾸로다.** 나머지 넷은 우리가 상대를 부른다. webhook 은 상대가 우리를 부른다. 그래서 우리가 서버를 하나 열고 공개 주소를 상대에게 준다. 도입에 나온 전환 포스트백이 정확히 이것이다. 방향이 바뀌면 책임도 바뀐다. 인증·중복 제거·순서 뒤바뀜을 전부 받는 쪽이 감당한다. 이 글의 4~9절이 사실상 webhook 을 받는 쪽 이야기다.

**배치 파일은 규약이 아닌 것처럼 보이지만 규약이다.** 하루치 전환을 gzip CSV 한 장으로 받는다면 컬럼 순서·인코딩·타임존·파일 이름 규칙이 전부 계약이다. 실시간이 필요 없고 양이 많은 정산 대사에는 이쪽이 맞다. 실제 연동에서는 둘을 같이 쓰는 일이 흔하다. 실시간은 webhook 으로 받고, 하루가 끝나면 배치 파일로 대사해 빠진 것을 채운다.

우리 수집 API 를 REST 로 두는 이유도 여기서 나온다. 붙는 쪽이 iOS·안드로이드·웹·상대 서버로 제각각이다. 어디서나 되는 것이 첫 번째 조건이면 남는 답은 하나다.

## 4. 응답 맨 앞 세 자리를 실제로 어떻게 쓰나

**상태코드는 "누가 고쳐야 하나"와 "다시 보내도 되나"를 세 자리로 답한다. 200 안에 에러를 담으면 그 답이 사라진다.**

응답 맨 앞에 오는 세 자리 숫자를 HTTP 상태코드라 부른다. 상태코드는 셋으로 나뉜다. 2xx 는 처리됐다는 뜻이다. 4xx 는 부르는 쪽이 고쳐야 한다는 뜻이다. 5xx 는 받는 쪽이 고쳐야 한다는 뜻이다. 이 셋만 지켜도 재시도 규칙과 알람 규칙이 저절로 정해진다.

| 코드 | 뜻 | 누가 고쳐야 하나 | 다시 보내도 되나 |
|---|---|---|---|
| 200 OK | 처리했고 본문이 있다 | — | — |
| 201 Created | 새 자원을 만들었다 | — | — |
| 202 Accepted | 접수만 했다 · 결과는 나중에 | — | 멱등키가 있을 때만 |
| 204 No Content | 처리했고 돌려줄 본문이 없다 | — | — |
| 400 Bad Request | 요청 형식이 틀렸다 | 부르는 쪽 | 아니다 · 그대로 또 틀린다 |
| 401 Unauthorized | 자격증명이 없거나 틀렸다 | 부르는 쪽 | 토큰을 갱신한 뒤 한 번만 |
| 403 Forbidden | 자격은 맞는데 권한이 없다 | 부르는 쪽 | 아니다 |
| 404 Not Found | 그런 자원이 없다 | 부르는 쪽 | 아니다 |
| 409 Conflict | 같은 키로 다른 내용이 왔다 | 부르는 쪽 | 아니다 |
| 422 Unprocessable | 형식은 맞는데 값이 규칙 위반 | 부르는 쪽 | 아니다 |
| 429 Too Many Requests | 초당 허용을 넘겼다 | 부르는 쪽 | `Retry-After` 만큼 기다렸다가 |
| 500 · 502 · 503 · 504 | 받는 쪽이 터졌거나 밀렸다 | 받는 쪽 | 된다 · 백오프 필수 |

표 두 곳에 나온 "멱등키" 는 요청마다 붙는 고유 값이다. 부르는 쪽이 붙이고, 재시도할 때도 같은 값을 다시 쓴다. 그래서 받는 쪽이 "이건 아까 그 요청"이라고 알 수 있다. 7절이 이것만 따로 본다.

400 과 422 가 헷갈린다. 400 은 JSON 이 깨졌거나 필수 필드가 없는 경우다. 422 는 JSON 도 멀쩡하고 필드도 다 있는데 값이 규칙에 안 맞는 경우다. `value` 가 음수이거나 `click_id` 가 존재하지 않는 값일 때다. 둘을 굳이 안 가르는 API 도 많다. 가르지 않기로 했으면 문서에 그렇게 적으면 된다.

**"200 OK 안에 에러를 담지 마라"가 4절의 핵심이다.** 이런 응답을 실제로 자주 본다.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"result":"fail","message":"invalid click_id"}
```

이 한 줄 때문에 네 곳이 동시에 눈이 먼다. 부르는 쪽 라이브러리는 2xx 를 성공으로 처리하고 재시도 대상에서 뺀다. 우리 모니터링의 5xx 비율 그래프는 0% 로 평평하다. 앞단 로드밸런서는 이 서버를 정상으로 본다. 상대가 붙인 SDK 도 성공으로 세고 재전송하지 않는다. 실패가 났는데 실패로 세는 곳이 한 군데도 없다.

에러는 상태코드로 알리고, 본문에는 기계가 읽을 것과 사람이 읽을 것을 같이 담는다.

```json
{
  "error": {
    "code": "INVALID_CLICK_ID",
    "message": "click_id 'ck-77' was not found",
    "field": "click_id",
    "request_id": "r-8f21",
    "retryable": false
  }
}
```

다섯 필드가 각자 일한다. `code` 는 부르는 쪽이 분기에 쓴다. `message` 로 분기하면 문구를 다듬는 순간 상대 코드가 깨진다. `field` 는 어느 필드가 문제인지 짚는다. `request_id` 는 문의할 때 쓴다. 이 값이 없으면 상대는 "어제 저녁에 실패했어요"라고만 말하게 된다. 그러면 우리는 로그에서 그 건을 못 찾는다. `retryable` 은 상태코드로 이미 답한 것을 한 번 더 못 박는 값이다.

`request_id` 는 우리가 만들어 응답 헤더와 본문에 같이 넣는다. 이 글의 예에서는 `r-8f21` 이다. 같은 값이 우리 로그에도 남아야 쓸모가 있다. 요청 하나가 여러 서비스를 지나면 그 값을 그대로 물려 준다.

## 5. 목록을 어떻게 넘기나 — 페이지네이션

**offset 은 페이지를 넘기는 사이에 데이터가 움직이면 중복과 누락을 만든다. cursor 는 마지막으로 읽은 자리를 기억한다.**

전환 리포트를 하루치 내려받는다고 하자. 5만 행이고 한 번에 1,000행씩 받는다. 50번 부른다. 그동안 새 전환이 들어오고 취소가 지워진다. 이 "그동안"이 문제를 만든다.

offset 방식은 "앞에서 몇 개를 버리고 그다음 1,000개"라고 말한다. 최신순 정렬이면 새 행은 맨 앞에 끼어든다. 앞이 밀리니 이미 읽은 행이 다음 페이지에 다시 나온다.

```http
GET /v1/conversions?date=2026-08-14&offset=1000&limit=1000
```

cursor 방식은 "이 행 다음부터 1,000개"라고 말한다. 기준이 개수가 아니라 자리다. 앞에 무엇이 끼어들어도 읽던 자리는 안 밀린다.

```json
{
  "items": [{"order_id": "O-00042", "value": 39000, "ts": 1786002501}],
  "next_cursor": "cv_1786002501_O-00042",
  "has_more": true
}
```

50장을 넘기는 20분 동안 새 전환 12건이 들어오고 취소 3건이 지워졌다고 하자. 아래는 그때 두 방식이 내는 결과다. 지어낸 값이다.

| 방식 | 두 번 읽은 행 | 못 읽은 행 | 50번째 페이지 응답 | 첫 페이지로 돌아가기 |
|---|---|---|---|---|
| offset | 12 | 3 | 380ms | 쉽다 |
| cursor | 0 | 0 | 40ms | 커서를 따로 보관해야 한다 |

응답 시간이 열 배 가까이 갈리는 이유는 DB 가 하는 일이 다르기 때문이다. `offset=49000` 은 4만 9천 행을 세어 버린 다음 그다음 1,000행을 준다. 커서는 색인에서 그 자리를 바로 찾는다. 페이지가 뒤로 갈수록 offset 은 느려지고 커서는 그대로다.

그래서 규칙은 이렇게 정한다. 사람이 화면에서 페이지 번호를 누르는 목록은 offset 이 편하다. 기계가 전체를 훑어 가는 목록은 커서를 쓴다. 전환 리포트는 뒤엣것이다.

한 가지 더 있다. 목록 응답에는 `items` 를 배열로 그냥 던지지 말고 객체로 감싼다. 최상위가 배열이면 나중에 `has_more` 하나를 더할 자리가 없다. 6절의 "필드 추가는 호환"이 최상위가 객체일 때만 성립한다.

## 6. 필드를 더하는 것과 빼는 것

**응답에 필드를 더하는 것은 대체로 안전하고, 빼는 것은 안전한 적이 없다. 이 비대칭이 버전 규칙의 뿌리다.**

규약이 한 번 나가면 상대 코드가 그것을 전제로 짜인다. 그래서 바꿀 때마다 "옛 상대가 안 깨지나"를 먼저 본다. 바꾸는 종류마다 답이 다르다.

| 바꾸는 것 | 옛 상대에게 무슨 일이 | 호환인가 |
|---|---|---|
| 응답에 필드 추가 | 모르는 필드는 무시한다 | 대체로 호환 |
| 응답에서 필드 삭제 | 그 필드를 읽던 코드가 죽는다 | 아니다 |
| 응답 필드 타입 변경 | 파서가 죽거나 조용히 0이 된다 | 아니다 |
| enum 값 추가 | 미지 값 처리가 없으면 죽는다 | 조건부 |
| 요청에 선택 필드 추가 | 안 보내면 그만이다 | 호환 |
| 요청에 필수 필드 추가 | 옛 상대가 전부 400 을 받는다 | 아니다 |
| 기본값 변경 | 조용히 결과 개수가 달라진다 | 아니다 |

첫 줄의 "대체로"에 함정이 있다. 모르는 필드를 무시하는 것은 파서 설정에 달렸다. 엄격한 설정이면 모르는 필드 하나에 예외가 난다. 우리가 부르는 쪽일 때는 이 설정을 꺼 둔다. 상대가 필드를 더하는 것을 우리가 막을 수 없기 때문이다.

:::deep 더 깊이 — 그 설정의 실제 이름과 기본값
자바 Jackson 에서는 `FAIL_ON_UNKNOWN_PROPERTIES` 가 그 자리다. 이 값은 Jackson 자체에서는 켜져 있다. 스프링 부트가 그것을 꺼 준다. 그래서 같은 Jackson 을 써도 프레임워크에 따라 결과가 갈린다.

이름과 기본값은 언어와 도구마다 다르다. 어느 쪽이 켜져 있는지 외우지 말고 직접 확인한다. 확인하는 방법은 하나다. 모르는 필드가 하나 섞인 응답을 만들어 파서에 넣어 본다. 예외가 나면 켜져 있는 것이다.
:::

값을 정해진 몇 개 중 하나로 제한한 것을 enum 이라 한다. enum 이 조건부인 이유도 같다. `status` 가 `"paid"` 와 `"canceled"` 둘뿐이라고 짜인 코드가 있다. 거기에 `"refunded"` 가 오면 갈 곳이 없다. 그래서 처음부터 미지 값을 하나로 몰아 처리한다. 이것을 "모르는 값은 무시하고 기록만 남긴다"로 정해 두면 나중에 값이 늘어도 안 깨진다.

**필드를 지워야 할 때는 지우기 전에 세어 본다.** 앱 SDK 가 쓰는 필드 하나를 지운다고 하자. 아래는 지우기 직전에 본 앱 버전 분포다. 지어낸 값이다.

| 앱 버전 | 트래픽 비중 | 이 필드를 읽나 |
|---|---|---|
| 5.2 (최신) | 41% | 아니오 |
| 5.1 | 27% | 아니오 |
| 5.0 | 18% | 예 |
| 4.x | 11% | 예 |
| 3.x 이하 | 3% | 예 |
| **합계** | **100%** | 32% 가 읽는다 |

32% 를 초당 요청으로 바꾸면 2,639 × 0.32 = 약 844건이다. 지우는 순간 초당 844건이 깨진다. 그래서 순서를 뒤집는다. 먼저 새 필드를 더해 내보내고, 옛 필드는 값을 채운 채 남겨 둔다. 옛 필드를 읽는 비중이 충분히 떨어지면 그때 지운다. 서버끼리면 이 기간이 몇 주지만 앱이면 몇 분기다.

**버전은 두 자리 중 하나에 붙인다.** 하나는 경로다. `/v2/conversions` 를 새로 파는 방식이고, 옛 주소는 그대로 산다. 다른 하나는 헤더다. `x-api-version: 2` 를 보내는 쪽만 새 형식을 받는다. 경로는 눈에 보이고 로그에서 바로 갈린다. 헤더는 주소를 안 바꿔도 되니 상대에게 부탁할 일이 없다. 어느 쪽이든 **기본값은 가장 오래된 버전이 된다**는 점이 같다. 그것을 언제 걷을지는 따로 정해 둬야 한다. 이 갈림길의 실제 설정은 [요청이 서비스까지 가는 길](post.html?id=gateway-ingress-router) 4절에 있다.

## 7. 멱등성 — 재시도가 전환을 18% 부풀린다

**재시도는 반드시 하게 된다. 멱등키가 없으면 그 재시도가 전환 1,000건을 1,180건으로 만든다.**

멱등(idempotent)은 "몇 번을 해도 결과가 한 번 한 것과 같다"는 뜻이다. 메서드마다 답이 다르다.

| 요청 | 두 번 보내면 | 왜 그런가 |
|---|---|---|
| `GET /v1/conversions/O-00042` | 같은 것을 두 번 읽는다 | 상태를 안 바꾼다 |
| `PUT /v1/campaigns/9931` 예산 50,000 | 예산은 50,000 그대로 | 결과 상태를 통째로 지정한다 |
| `DELETE /v1/campaigns/9931` | 이미 없다 · 결과는 같다 | 지운 상태는 한 번 더 지워도 같다 |
| `POST /v1/conversions` | 전환이 두 줄 생긴다 | 부를 때마다 새 자원을 만든다 |
| `PATCH /v1/campaigns/9931` 예산 +10,000 | 예산이 20,000 늘어난다 | 상대적 변경이라 쌓인다 |

POST 와 PATCH 만 멱등이 아니다. 그런데 하필 전환 기록·결제·주문이 전부 POST 다. 값을 만드는 요청이 값을 못 만드는 요청보다 위험한 것은 당연하다.

**문제는 재시도를 안 할 수가 없다는 데 있다.** 응답이 안 왔을 때 부르는 쪽이 아는 것은 하나뿐이다. "답을 못 받았다." 서버가 못 받은 것인지, 받고 처리했는데 응답만 못 온 것인지 구분할 방법이 없다. 안 보내면 진짜 유실이 되고, 보내면 중복이 된다.

전환 포스트백 1,000건을 그대로 따라가 보자. 서버는 요청을 받으면 항상 기록에 성공한다고 두자. 다만 응답이 돌아오는 길에서 유실된다. 클라이언트는 답을 못 받으면 최대 3번 더 보낸다.

| 회차 | 보낸 건수 | 응답이 유실된 건수 | 서버가 기록한 누적 |
|---|---|---|---|
| 1차 | 1,000 | 150 | 1,000 |
| 2차 | 150 | 25 | 1,150 |
| 3차 | 25 | 5 | 1,175 |
| 4차 | 5 | 0 | 1,180 |
| **합계 요청** | **1,180** | 180 | **1,180** |

유실률은 15.0% · 16.7% · 20.0% 로 잡았다. 재시도가 몰리는 시각이라 뒤로 갈수록 조금 높게 뒀다. 전부 지어낸 값이다.

```python
# 재시도가 전환을 몇 건 부풀리나 — 멱등키가 없을 때와 있을 때.
# 광고주 한 곳이 하루에 보내는 전환 포스트백 1,000건을 그대로 따라간다.
# 서버는 요청을 받으면 항상 기록에 성공한다. 다만 응답이 돌아오는 길에서 유실된다.
# 클라이언트는 응답을 못 받으면 최대 3번까지 다시 보낸다.
# 모든 숫자는 설명을 위해 지어낸 값이다.
from unicodedata import east_asian_width

LOST = [150, 25, 5, 0]      # 회차별 '서버는 기록했는데 응답이 유실된' 건수
AD_SPEND = 5_000_000        # 이 광고주가 하루에 쓴 광고비(원)

pending = [f"O-{i:05d}" for i in range(1000)]   # 광고주 쪽 주문번호. 이것이 멱등키가 된다
naive_rows = []             # 멱등키를 안 보는 서버의 전환 테이블
idem_rows = []              # 멱등키를 보는 서버의 전환 테이블
idem_seen = {}              # 멱등키 → 첫 응답. 두 번째부터는 이것을 그대로 돌려준다
log = []

for attempt, lost in enumerate(LOST, start=1):
    sent = len(pending)
    for key in pending:
        naive_rows.append(key)          # 키를 안 보면 요청이 올 때마다 한 줄이 늘어난다
        if key not in idem_seen:        # 처음 보는 키일 때만 새 줄을 만든다
            idem_seen[key] = "201 Created"
            idem_rows.append(key)
    log.append((attempt, sent, lost, len(naive_rows), len(idem_rows)))
    pending = pending[:lost]            # 응답을 못 받은 건만 다시 보낸다

# 한글은 화면에서 두 칸을 먹는다. 칸수를 직접 세어 맞춘다
def w(s):
    return sum(2 if east_asian_width(c) in "WF" else 1 for c in s)

def row(cells, widths):
    out = ""
    for c, width in zip(cells, widths):
        out += " " * (width - w(str(c))) + str(c)
    print(out)

WID = [8, 12, 12, 16, 16]
row(["회차", "보낸 건수", "응답 유실", "키 없음 누적", "키 있음 누적"], WID)
for attempt, sent, lost, n, i in log:
    row([attempt, f"{sent:,}", f"{lost:,}", f"{n:,}", f"{i:,}"], WID)

real, counted = len(idem_rows), len(naive_rows)
print()
print(f"실제 전환 {real:,}건 → 리포트에 잡힌 전환 {counted:,}건 ({counted/real - 1:+.1%})")
print(f"진짜 CPA {AD_SPEND/real:,.0f}원 → 리포트 CPA {AD_SPEND/counted:,.0f}원"
      f" ({AD_SPEND/counted - AD_SPEND/real:,.0f}원)")
print(f"중복 요청 {counted - real}건은 전부 성공 응답을 받았다. 에러 로그에는 한 줄도 안 남는다.")

# 출력:
#     회차   보낸 건수   응답 유실    키 없음 누적    키 있음 누적
#        1       1,000         150           1,000           1,000
#        2         150          25           1,150           1,000
#        3          25           5           1,175           1,000
#        4           5           0           1,180           1,000
#
# 실제 전환 1,000건 → 리포트에 잡힌 전환 1,180건 (+18.0%)
# 진짜 CPA 5,000원 → 리포트 CPA 4,237원 (-763원)
# 중복 요청 180건은 전부 성공 응답을 받았다. 에러 로그에는 한 줄도 안 남는다.
```

마지막 세 줄이 이 절의 값이다. 전환 한 건을 얻는 데 든 광고비를 CPA 라 부른다. 광고비 500만 원을 쓴 광고주의 진짜 CPA 는 5,000원이다. 그런데 리포트에는 4,237원으로 뜬다. 763원이 낮다. 이 광고주는 성과가 좋다고 판단해 예산을 늘린다. 늘린 예산으로 산 전환도 같은 비율로 부풀어 있다.

더 나쁜 것은 이 180건이 에러가 아니라는 점이다. 전부 성공 응답을 받았고 로그에도 정상으로 남는다. 알람이 울릴 자리가 없다. pCVR 모델은 이 중복이 섞인 라벨로 학습한다. 같은 주문이 두 줄이면 그 유형의 전환율이 실제보다 높게 잡힌다. 이 문제의 모델 쪽 이야기는 [pCVR 모델링](post.html?id=pcvr-modeling) 2절에 있다.

**멱등키는 부르는 쪽이 만든다.** 받는 쪽이 만들면 두 번째 요청이 재시도인지 새 건인지 구분할 방법이 없다. 만드는 규칙은 넷이다.

- 자연키가 있으면 그것을 쓴다. 광고주 주문번호 `O-00042` 가 그 예다.
- 자연키가 없으면 UUID 를 하나 만든다. 그리고 재시도 내내 같은 값을 다시 쓴다.
- 재시도마다 새 UUID 를 만들면 키가 없는 것과 같다. 이 실수가 가장 흔하다.
- 본문 해시만으로 키를 만들지 않는다. 같은 금액의 진짜 두 번 결제를 하나로 먹는다.

마지막 줄은 실제로 갈리는 자리다. 같은 사람이 같은 상품을 39,000원에 두 번 살 수도 있다. 그것과 한 번 산 것이 두 번 도착한 것을 본문만으로는 못 가른다. 주문번호가 있어야 갈린다.

요청은 이렇게 생겼다. 키는 헤더에 둔다.

```http
POST /v1/conversions HTTP/1.1
Host: api.example.com
Content-Type: application/json
Idempotency-Key: O-00042
X-Signature: t=1786002501,v1=8f21c4a9

{"click_id":"ck-8f21","order_id":"O-00042","value":39000,"ts":1786002501}
```

**받는 쪽은 키를 저장한다.** 저장하는 것은 키 하나가 아니라 넷이다. 키, 처리 결과, 응답 상태코드, 만료 시각이다. 같은 키가 다시 오면 새로 처리하지 않고 저장해 둔 응답을 그대로 돌려준다. 그래서 두 번째 요청도 201 을 받는다. 부르는 쪽은 아무것도 몰라도 된다.

:::deep 더 깊이 — 멱등 저장소의 상태 셋과 경쟁 조건
키를 "있다 · 없다" 둘로만 두면 구멍이 하나 남는다. 첫 요청을 처리하는 **도중에** 재시도가 도착하는 경우다. 아직 저장이 안 끝났으니 두 번째 요청도 "없다"를 보고 같이 처리에 들어간다. 그래서 상태를 셋으로 둔다.

| 상태 | 언제 | 같은 키가 또 오면 |
|---|---|---|
| `in_progress` | 처리 시작 직후 기록 | 409 를 돌려준다 · 잠시 뒤 다시 오게 |
| `done` | 처리 끝 · 응답까지 저장 | 저장된 응답을 그대로 재생 |
| (없음) | 처음 보는 키 | `in_progress` 로 만들고 처리 시작 |

`in_progress` 를 만드는 순간이 경쟁 지점이다. "조회 → 없으면 삽입"을 코드로 나눠 쓰면 그 사이에 다른 요청이 끼어든다. 그래서 조회하지 말고 **유니크 제약이 걸린 삽입 한 번**으로 처리한다.

```sql
CREATE TABLE idempotency (
  key         VARCHAR(64) PRIMARY KEY,
  state       VARCHAR(16) NOT NULL,
  status_code INT,
  body        TEXT,
  expires_at  TIMESTAMP NOT NULL
);
-- 삽입이 성공하면 내가 첫 번째다. 유니크 위반이면 남이 먼저다.
INSERT INTO idempotency (key, state, expires_at)
VALUES ('O-00042', 'in_progress', NOW() + INTERVAL '24 hours');
```

만료를 두는 이유는 저장소가 무한히 커지지 않게 하려는 것만이 아니다. 만료 시간이 곧 **"재시도는 여기까지"라는 계약**이 된다. 24시간을 잡았으면 25시간 뒤에 온 같은 키는 새 건으로 처리된다. 상대의 재시도 정책이 7일이면 우리 만료도 7일이어야 한다. 이 값이 어긋나면 중복이 조용히 생긴다.

`in_progress` 로 남은 채 서버가 죽는 경우도 있다. 그 키는 만료 전까지 계속 409 를 받는다. 그래서 `in_progress` 에는 짧은 만료를 따로 둔다. 처리 시간 상한의 두 배 정도면 충분하다.
:::

값을 직접 움직여 보면 이 관계가 더 빨리 보인다. 아래 데모는 유실률·재시도 횟수·멱등키 여부를 바꿔 가며 최종 기록 건수를 보여 준다.

## 8. 타임아웃과 재시도 — 지터가 없으면 두 번째 장애가 난다

**타임아웃을 안 걸면 상대의 느림이 우리의 정지가 된다. 백오프에 지터가 없으면 재시도가 죽은 서버를 한 번 더 죽인다.**

타임아웃을 안 걸었을 때 무슨 일이 나는지는 곱셈 하나로 나온다. 동시에 물려 있는 커넥션 수는 초당 호출 수에 평균 응답 시간을 곱한 값이다. 우리 서비스가 상대를 초당 100번 부르고 커넥션 풀이 200개라고 하자.

| 상대 응답 시간 | 초당 호출 | 동시에 물리는 커넥션 | 풀 200개 |
|---|---|---|---|
| 39ms (평소) | 100 | 3.9 | 여유 |
| 400ms (우리 상한) | 100 | 40 | 여유 |
| 2초 | 100 | 200 | 딱 찬다 |
| 5초 | 100 | 500 | 300건이 대기한다 |
| 30초 (타임아웃 없음) | 100 | 3,000 | 전면 정지 |

마지막 줄이 중요하다. 상대는 죽지 않았다. 느려졌을 뿐이다. 그런데 우리 서비스는 커넥션을 다 써서 다른 일도 못 한다. 상대 API 와 상관없는 요청까지 같이 멈춘다. 타임아웃은 우리를 지키는 장치다.

타임아웃은 한 개가 아니라 셋이다. 연결이 맺어지기까지 기다리는 시간이 하나다. 응답 바이트를 기다리는 시간이 둘이다. 전체를 통틀어 기다리는 시간이 셋이다. 라이브러리 기본값이 무한인 경우가 아직도 많다. 셋 다 명시적으로 적어 둔다.

:::deep 더 깊이 — 그 값을 설정 파일에 적으면
아래는 타임아웃 셋과 재시도·멱등키를 한 파일에 모은 모양이다. 값은 이 절에서 정한 것을 그대로 옮겼다.

```yaml
# 전환 포스트백을 보내는 쪽 설정. 값은 이 절에서 정한 것이다.
conversion_client:
  endpoint: https://api.example.com/v1/conversions
  connect_timeout_ms: 200
  read_timeout_ms: 400
  total_timeout_ms: 700
  retry:
    max_attempts: 4
    backoff_base_ms: 1000
    jitter: full
    retry_on: [502, 503, 504, connect_timeout]
  idempotency:
    header: Idempotency-Key
    source: order_id
```

세 타임아웃 값은 200 · 400 · 700 이다. 앞의 둘을 더하면 600 이라 총합 700 안에 든다. 이 관계가 깨지면 총합이 먼저 끊는다.
:::

**재시도해도 되는 에러와 하면 안 되는 에러를 가르는 기준은 하나다.** "다시 보내면 결과가 달라질 수 있나." 400 은 다시 보내도 또 400 이다. 503 은 다시 보내면 성공할 수 있다.

| 실패 종류 | 서버가 처리했을 수 있나 | 재시도 |
|---|---|---|
| 연결 자체가 안 됨 | 아니다 | 안전하다 |
| 연결 뒤 응답 대기 중 타임아웃 | 그렇다 | 멱등키가 있을 때만 |
| 502 · 503 · 504 | 502 · 504 는 그럴 수 있다 | 멱등키가 있을 때만 |
| 429 | 아니다 | `Retry-After` 뒤에 |
| 400 · 403 · 404 · 422 | 아니다 | 하지 마라 |
| 409 | 이미 처리됐다 | 하지 마라 · 성공으로 본다 |

두 번째 줄이 7절과 이어진다. 응답 대기 중 끊긴 것은 서버가 이미 다 처리했을 수 있다. 그래서 멱등키 없이 재시도하면 1,180건이 된다. 멱등키가 있으면 이 줄이 "안전하다"로 바뀐다.

**백오프에 지터를 넣는 이유는 따로 있다.** 먼저 두 이름을 갈라 둔다. 재시도 간격을 1초·2초·4초로 늘리는 것이 지수 백오프다. 그 시각에 무작위 값을 섞어 흩는 것이 지터다. 상대 서버가 재시작하면 그 순간 물려 있던 요청이 한꺼번에 끊긴다. 전부 같은 시각에 실패했으니 전부 같은 시각에 재시도한다. 백오프를 넣어도 마찬가지다. 1초씩 미루면 1초 뒤에 다 같이 몰린다.

```python
# 지터가 없으면 재시도가 어떻게 죽은 서버를 한 번 더 죽이나.
# 상황: 상대 API 가 t=0 에 재시작한다. 그 순간 물려 있던 요청 500건이 한꺼번에 끊긴다.
#       서버는 3,000 ms 뒤에 살아나고, 살아난 뒤에도 100 ms 창당 60건까지만 받는다.
#       초과분은 503 이라 또 재시도로 돌아온다. 재시도는 최대 4회.
# 모든 숫자는 설명을 위해 지어낸 값이다.
import random
from unicodedata import east_asian_width

N, RECOVER_MS, CAP_PER_100MS, MAX_TRY, BASE = 500, 3000, 60, 4, 1000

def run(strategy):
    random.seed(7)
    load = {}                       # 100 ms 창 번호 → 그 창에 도착한 요청 수
    done = failed = 0
    for _ in range(N):
        t = 0.0
        for k in range(1, MAX_TRY + 1):
            if strategy == "fixed":       t += BASE
            elif strategy == "backoff":   t += BASE * 2 ** (k - 1)
            else:                         t += random.uniform(0, BASE * 2 ** (k - 1))
            bucket = int(t // 100)
            load[bucket] = load.get(bucket, 0) + 1
            alive = t >= RECOVER_MS                      # 서버가 살아났나
            room = load[bucket] <= CAP_PER_100MS         # 그 창에 자리가 있나
            if alive and room:
                done += 1
                break
        else:
            failed += 1                                  # 4회를 다 쓰고도 못 넣었다
    peak = max(load.values())
    last = max(b for b in load if b * 100 >= RECOVER_MS) * 100 / 1000
    return done, failed, peak, last

def w(s):
    return sum(2 if east_asian_width(c) in "WF" else 1 for c in s)

def row(cells, widths):
    print("".join(" " * (wd - w(str(c))) + str(c) for c, wd in zip(cells, widths)))

WID = [26, 10, 10, 16, 12]
row(["재시도 전략", "성공", "실패", "100ms 최대 부하", "마지막 도착"], WID)
for name, label in [("fixed", "고정 1초 간격"), ("backoff", "지수 백오프 (지터 없음)"),
                    ("jitter", "지수 백오프 + full jitter")]:
    done, failed, peak, last = run(name)
    row([label, f"{done}건", f"{failed}건", f"{peak}건", f"{last:.1f}s"], WID)

print()
print(f"창 하나가 받을 수 있는 양은 {CAP_PER_100MS}건이다. 그 위는 전부 503 으로 되돌아온다.")
print("지터는 재시도를 늦추는 장치가 아니라 같은 순간에 겹치는 것을 푸는 장치다.")

# 출력:
#                재시도 전략      성공      실패 100ms 최대 부하 마지막 도착
#              고정 1초 간격     120건     380건           500건        4.0s
#    지수 백오프 (지터 없음)     180건     320건           500건       15.0s
#  지수 백오프 + full jitter     472건      28건            92건       10.5s
#
# 창 하나가 받을 수 있는 양은 60건이다. 그 위는 전부 503 으로 되돌아온다.
# 지터는 재시도를 늦추는 장치가 아니라 같은 순간에 겹치는 것을 푸는 장치다.
```

세 줄을 나란히 놓으면 지터의 값이 보인다. 지터 없이 지수 백오프만 넣으면 성공이 180건이다. 지터를 넣으면 472건이다. 두 배 반이다. 최대 부하는 500건에서 92건으로 떨어진다. 서버가 100ms 창당 60건만 받는데 500건이 몰리면 440건은 그 자리에서 503 이다.

지수 백오프만 넣은 쪽이 고정 간격보다 마지막 도착이 훨씬 늦다는 것도 눈여겨볼 만하다. 15.0초와 4.0초다. 늦게 오는데 성공은 180건뿐이다. 몰리는 것을 안 풀면 미루는 것만으로는 아무것도 못 고친다.

**타임아웃 예산은 위에서 아래로 나눈다.** 우리가 400ms 안에 답하기로 했으면, 우리가 부르는 것들의 타임아웃 합이 400ms 를 넘으면 안 된다. 넘으면 상위가 먼저 끊고, 아래 작업은 아무도 안 기다리는 채로 계속 돈다.

## 9. 인증 — 무엇을 막고 무엇을 못 막나

**다섯 가지가 막는 것이 서로 다르다. 클라이언트에 시크릿을 박는 것은 그중 어느 것도 아니다.**

인증 방식 이름은 많지만 실무에서 만나는 것은 다섯이다. 각각 증명하는 것이 다르고, 못 막는 것도 다르다.

| 방식 | 무엇을 증명하나 | 무엇을 못 막나 | client to server 에 둘 수 있나 |
|---|---|---|---|
| API key | 이 키를 가진 쪽이라는 것 | 본문 위변조 · 재전송 | 안 된다 |
| OAuth2 client credentials | 서비스 신원 · 토큰을 받아 쓴다 | 토큰이 새면 만료까지 유효 | 안 된다 |
| JWT | 발급자가 서명했다는 것 | 만료 전 회수 · 탈취 | 사용자 토큰이면 된다 |
| mTLS | 양쪽이 서로의 인증서를 확인 | 본문 내용이 옳은지 | 사실상 안 된다 |
| HMAC 서명 | 본문이 안 바뀌었다는 것 | 재전송 · 시계가 틀리면 전량 실패 | 안 된다 |

API key 는 가장 단순하고 가장 약하다. 키만 있으면 누구나 우리인 척할 수 있다. 그래서 서버끼리만 쓴다. 그것도 TLS 위에서만 쓴다. 키는 주기적으로 갈아 끼운다. 갈아 끼우는 동안에는 옛 키와 새 키를 함께 인정하는 기간을 둔다.

표의 mTLS 는 양쪽이 서로 인증서를 내보이는 연결이다. 보통 TLS 는 서버 쪽 인증서만 확인한다. 그래서 mTLS 는 상대가 누구인지까지 증명한다. 대신 인증서를 만들고 갱신하는 일이 양쪽에 생긴다.

HMAC 서명은 성격이 다르다. 본문과 시각을 합쳐 비밀키로 해시를 만들어 헤더에 붙인다. 받는 쪽이 같은 계산을 해서 값이 같은지 본다. 본문을 한 글자만 고쳐도 값이 달라지니 위변조가 걸린다. 대신 같은 요청을 그대로 다시 보내는 것은 못 막는다. 그래서 서명 안에 시각을 넣고 허용 창을 둔다.

**허용 창을 두면 시계가 새 문제가 된다.** 창을 ±5분으로 잡았다고 하자.

| 우리 서버 시계 오차 | 결과 |
|---|---|
| +2초 | 통과 |
| +4분 50초 | 통과 · 여유 10초 |
| +6분 | 전량 401 |
| -12분 | 전량 401 |

시계가 어긋나면 코드는 한 글자도 안 틀렸는데 전부 401 이 된다. 그리고 그 401 은 "키가 틀렸다"처럼 보인다. 첫 주에 이걸로 반나절을 쓰는 사람이 많다. 시각 동기화가 켜져 있는지부터 본다.

**클라이언트에 시크릿을 박으면 안 되는 이유는 추상적이지 않다.** 안드로이드 앱 파일에서 키처럼 생긴 문자열을 뽑는 것은 명령 한 줄이다.

```bash
# 앱 파일을 풀어 문자열만 훑는다. 특별한 도구가 필요 없다.
unzip -p app.apk classes.dex | strings | grep -oE 'sk_live_[A-Za-z0-9]{8,}'
```

웹은 더 쉽다. 개발자 도구의 네트워크 탭에 요청 헤더가 그대로 보인다. 난독화는 이것을 어렵게 만들 뿐 막지 못한다. 앱 안에 있는 값은 앱을 받은 모두의 값이라고 생각하는 편이 정확하다.

그러면 앱은 어떻게 인증하나. 답은 셋이다. 첫째, 사용자가 로그인해서 받은 토큰을 쓴다. 이 토큰은 그 사용자만의 것이고 서버가 언제든 무효로 만들 수 있다. 둘째, 비밀이 필요한 호출은 우리 서버가 대신한다. 앱은 우리 서버만 부르고, 상대 API 키는 우리 서버에 둔다. 셋째, 수집 API 처럼 아무나 불러도 되는 것은 애초에 비밀이 필요 없게 설계한다. 대신 서버 쪽에서 쿼터와 값 검증을 건다.

토큰은 만료된다. 그래서 401 을 받으면 토큰을 갱신하고 딱 한 번만 다시 보낸다. 갱신 없이 무한 재시도를 걸면 401 폭풍이 된다. 갱신 요청 자체가 실패하면 그때는 재시도하지 않고 로그인으로 보낸다.

## 10. 첫 주에 밟는 지뢰 여덟

**여덟 가지다. 공통점은 배포가 성공하고 테스트도 통과한다는 것이다.**

**시크릿을 클라이언트에 박는다.** 앱 코드에 API 키를 넣고 배포한다. 동작은 완벽하다. 몇 달 뒤 그 키로 남이 우리 쿼터를 다 쓰거나, 우리 이름으로 요청을 만든다. 키를 바꾸려면 앱을 새로 내야 하고, 옛 앱을 쓰는 32% 는 그때부터 깨진다(6절).

**타임아웃을 안 건다.** 라이브러리 기본값이 무한이면 상대가 느려질 때 우리 커넥션이 다 물린다. 상대 API 와 무관한 요청까지 같이 멈춘다. 8절 표의 마지막 줄이 이 상태다. 지표에는 "우리 서비스가 느려졌다"로만 보여서 원인을 상대에게서 찾기까지 시간이 걸린다.

**200 안에 에러를 담는다.** 실패가 성공으로 세어진다. 알람이 안 울리고 재시도도 안 걸린다. 실패율 그래프가 평평하니 아무도 안 본다. 이 자리는 대개 상대 API 가 그렇게 생겨서 우리도 따라 하게 되는 경우다. 우리 쪽에서라도 상태코드를 제대로 매긴다(4절).

**재시도로 중복을 만든다.** 멱등키 없이 재시도를 켜면 전환이 18% 부푼다(7절). 에러가 아니라 성공으로 남으니 알람이 없다. CPA 가 낮게 보여 예산이 잘못 움직인다.

**상대 rate limit 을 무시한다.** 429 를 받고 곧바로 다시 보내면 429 를 또 받는다. 그 재시도가 다시 쿼터를 먹어 정상 요청까지 막는다. `Retry-After` 헤더를 읽고 그만큼 쉬어야 한다. 상대가 그 헤더를 안 주면 지수 백오프와 지터로 스스로 늦춘다(8절).

**시계가 어긋나 서명이 실패한다.** 시각 동기화가 꺼진 서버에서 HMAC 서명을 만들면 전량 401 이다. 키를 몇 번 재발급받아도 안 고쳐진다. 증상이 "인증 실패"라 원인을 시계에서 찾기까지 오래 걸린다(9절).

**응답 필드가 하나 늘어 파서가 깨진다.** 상대가 호환이라고 생각하고 필드를 더한다. 우리 파서가 엄격 모드면 그 순간 전부 예외가 난다. 우리가 부르는 쪽이면 모르는 필드를 무시하도록 먼저 열어 둔다(6절).

**테스트 자격증명으로 운영을 부른다.** 환경 변수 하나를 안 바꾸고 배포하면 두 방향으로 사고가 난다. 운영 키로 테스트를 돌려 진짜 전환을 만든다. 아니면 테스트 키로 운영을 돌려 하루치 전환을 통째로 잃는다. 주소와 키를 한 덩어리로 묶어 두면 절반은 막힌다. 응답에 `env` 필드를 넣어 부르는 쪽이 확인하게 하는 방법도 있다.

## 헷갈리기 쉬운 점

**"멱등성은 POST 를 GET 으로 바꾸는 것"이 아니다.** 멱등성은 메서드를 바꿔서 얻는 성질이 아니다. 같은 키가 두 번 오면 두 번째를 새로 처리하지 않겠다는 약속이다. POST 는 그대로 두고 키를 헤더에 얹는다. 그래야 새 자원을 만드는 요청도 재시도할 수 있다.

**"재시도를 끄면 중복이 없어진다"도 아니다.** 재시도를 끄면 중복 대신 유실이 생긴다. 응답을 못 받은 180건 중 상당수는 서버가 이미 기록한 건이다. 그런데 일부는 진짜로 안 들어간 건이다. 둘을 구분할 방법이 없으니 끄는 쪽도 답이 아니다. 켜고 키를 붙이는 것이 답이다.

**"타임아웃은 상대를 위한 배려"가 아니다.** 타임아웃은 우리를 지킨다. 상대는 우리가 기다리든 말든 자기 일을 계속한다. 끊는 쪽이 얻는 것은 커넥션과 스레드다. 그래서 상대가 느려도 우리 다른 기능은 산다.

**"200 이면 성공"이 아니다.** 상태코드가 200이어도 본문에 실패가 적혀 있을 수 있다. 상대 API 가 그렇게 생겼다면 우리 코드가 본문을 보고 판정해야 한다. 그 판정 결과를 우리 지표에는 실패로 기록한다. 상대의 나쁜 규약을 우리 지표까지 옮기지 않는다.

**"필드 추가는 항상 안전"도 아니다.** 안전한 것은 받는 쪽 파서가 관대할 때뿐이다. 그리고 응답 최상위가 배열이면 필드를 더할 자리 자체가 없다. 목록도 객체로 감싸 두는 이유가 이것이다(5절).

**"이건 내부 API 라 대충 해도 된다"가 가장 비싸다.** 내부라는 말은 상대가 우리 회사 안에 있다는 뜻일 뿐이다. 타임아웃도 멱등키도 똑같이 필요하다. 오히려 내부 호출은 홉이 길어서 실패 지점이 더 많다. 실제 홉 수는 [요청이 서비스까지 가는 길](post.html?id=gateway-ingress-router)에서 셀 수 있다.
