지훈은 피보나치 수를 구하는 함수를 재귀로 짰습니다. 피보나치 수는 0 과 1 에서 시작해 바로 앞의 두 수를 더한 값으로 다음 수를 만들어 가는 수열의 수입니다. 재귀는 함수가 더 작은 입력으로 자기 자신을 다시 불러 답을 구하는 방식입니다. 지훈의 함수는 본문이 두 줄뿐이었고 예제 입력에서도 맞는 답을 냈습니다. 그런데 n 을 30 으로 올리자 답이 나오기까지 0.3초가 걸렸고 40 으로 올리자 아예 끝나지 않았습니다.

이번에는 앞 편들에서처럼 리스트를 집합으로 바꾸거나 값을 정렬하면 풀리는 자료형 문제가 아니었습니다. 두 줄짜리 함수가 느렸던 까닭은 그 두 줄이 지나치게 많이 불렸다는 데 있었습니다.

**같은 계산을 몇 번이나 하고 있을까요?**

함수가 불린 횟수를 직접 세어 보면 이 질문의 답이 나옵니다. 이 글은 그렇게 세어 보는 데서 출발해 문제를 푸는 도구 세 가지로 넘어갑니다. **동적 계획법**(dynamic programming, DP)은 겹치는 작은 계산의 답을 적어 두었다가 다시 씁니다. **백트래킹**은 답을 한 단계씩 놓아 보다가 아니다 싶으면 바로 앞 단계로 되돌아옵니다. **그리디**는 뒤에 올 선택을 따지지 않고 매 단계에서 지금 가장 좋아 보이는 것만 고릅니다. 세 도구 모두 "모든 경우를 다 볼 수는 없다"는 같은 문제에 서로 다른 방식으로 답합니다.

> **한 줄 요약:** 피보나치 30 을 그냥 재귀로 구하면 같은 값을 거듭 구하느라 함수를 269만 번 부르지만 한 번 구한 답을 적어 두기만 해도 호출이 59번으로 줄어듭니다. 겹치는 계산이 없어 적어 둘 답이 없으면 하나씩 놓아 보고 막히면 되돌아오는 백트래킹으로 찾습니다. 지금 가장 좋아 보이는 것만 골라도 답이 되는 문제라면 그리디로 바로 고릅니다.

> **골라 읽는 법** — 이 글은 절 10개로 되어 있습니다.
>
> - 겹치는 계산을 세어 보고 없애는 방법 → 앞의 세 절
> - 점화식(앞에서 구한 값으로 다음 값을 구하는 식)을 세우는 순서와, 무게 한도 안에서 값을 가장 크게 담는 배낭 문제 → 넷째, 다섯째 절
> - 막히면 되돌아오는 백트래킹 → 여섯째, 일곱째 절
> - 그리디와 그리디가 틀리는 경우 → 여덟째, 아홉째 절

## 1. 같은 계산의 반복 횟수

**재귀가 느릴 때는 대개 같은 값을 여러 번 다시 구하고 있습니다. 함수가 불린 횟수를 세어 보면 바로 확인할 수 있습니다.**

지훈의 함수가 n 이 30 일 때 0.3초나 걸린 까닭을 찾으려면 먼저 함수가 같은 값을 몇 번이나 다시 구하는지 알아야 합니다. 피보나치 수는 `f(n) = f(n-1) + f(n-2)` 라는 식으로 정의되므로 지훈의 함수도 `f(n)` 을 구할 때 `f(n-1)` 과 `f(n-2)` 를 차례로 부릅니다. 그래서 `f(20)` 을 구하면 `f(19)` 와 `f(18)` 이 불리는데, `f(19)` 도 자기 답을 구하는 도중에 `f(18)` 을 또 부르므로 `f(18)` 은 서로 다른 두 갈래에서 두 번 계산됩니다. 이런 겹침이 n 이 작아질수록 몇 배로 늘어나는지는 짐작하기보다 세어 보는 편이 확실합니다.

같은 값을 몇 번씩 구하는지 보려고 함수가 불릴 때마다 그 n 의 횟수를 딕셔너리 `부른횟수` 에 1씩 올리는 재귀를 돌립니다. 2단계는 `f(20)` 을 한 번 구하며 n 마다 불린 횟수를 찍습니다. 3단계는 n 을 20, 25, 30 으로 키우며 걸린 시간(밀리초, ms)과 전체 호출 횟수를 측정합니다.

```python
# 하는 일: 피보나치를 그냥 재귀로 구하며 n 마다 함수를 몇 번 불렀는지 세고, n 이 20, 25, 30 일 때 걸린 시간과 부른 횟수를 찍는다.
import time

부른횟수 = {}

# 1단계: 부를 때마다 세는 재귀를 만든다
def 그냥(n):
    부른횟수[n] = 부른횟수.get(n, 0) + 1
    if n < 2: return n
    return 그냥(n-1) + 그냥(n-2)

# 2단계: f(20) 을 구하며 n 마다 부른 횟수를 센다
그냥(20)
print("피보나치 20 을 그냥 재귀로 구할 때, 각 n 을 몇 번 불렀나")
for n in (20, 18, 15, 10, 5, 2, 1):
    print(f"  n={n:<4}{부른횟수[n]:>7}번")
print(f"  전부 합치면 {sum(부른횟수.values()):,}번")

# 3단계: n 을 20, 25, 30 으로 키우며 시간과 횟수를 측정한다
print()
print(f"{'n':>5}{'그냥 재귀(ms)':>15}{'부른 횟수':>12}")
for n in (20, 25, 30):
    부른횟수.clear()
    t = time.perf_counter()
    그냥(n)
    ms = (time.perf_counter() - t) * 1000
    print(f"{n:>5}{ms:>15.1f}{sum(부른횟수.values()):>12,}")

# 출력 (시간은 돌릴 때마다 다르다):
# 2단계 뜻: 답이 늘 1 인 f(1) 을 6,765번 불렀다. 같은 계산을 그만큼 되풀이한 것이다.
# 피보나치 20 을 그냥 재귀로 구할 때, 각 n 을 몇 번 불렀나
#   n=20        1번
#   n=18        2번
#   n=15        8번
#   n=10       89번
#   n=5       987번
#   n=2      4181번
#   n=1      6765번
#   전부 합치면 21,891번
# 3단계 뜻: n 이 5 늘 때마다 부른 횟수가 11배쯤 는다. 밀리초는 기계마다 다르지만 부른 횟수는 어디서 돌려도 같다.
#
#     n      그냥 재귀(ms)       부른 횟수
#    20            2.2      21,891
#    25           24.5     242,785
#    30          265.7   2,692,537
```

2단계 출력을 보면 맨 위의 `f(20)` 은 한 번만 불렸지만 n 이 작아질수록 횟수가 늘어 `f(18)` 은 2번, `f(15)` 는 8번, `f(10)` 은 89번, `f(5)` 는 987번 불렸습니다. `f(1)` 은 계산할 것도 없이 언제나 1 을 돌려주는 호출인데도 6,765번이나 불렸습니다. 모든 n 의 호출을 합하면 21,891번입니다. 3단계의 걸린 시간은 기계마다 다르게 나오지만 부른 횟수는 어느 기계에서 돌려도 같은 값이 나옵니다.

3단계 표에서 부른 횟수는 n 이 20 일 때 21,891번, 25 일 때 242,785번, 30 일 때 2,692,537번으로 n 이 5 늘어날 때마다 11배쯤 커졌습니다. n 이 1씩 다섯 번 늘어 11배가 되려면 한 번 늘 때마다 대략 1.6배씩 커져야 합니다. **n 이 하나 늘 때마다 부른 횟수가 대략 1.6배씩 곱해지는 이런 증가를 지수 증가라고 합니다.** 앞 편들에서 다룬 O(n²) 는 시간이 n 의 제곱에 비례해 늘어나는데, 그 O(n²) 조차 이 지수 증가에 비하면 완만합니다. 표의 n=30 줄에 찍힌 265.7ms 가 지훈이 겪은 약 0.3초입니다.

## 2. 적어 두기(메모이제이션) — 위에서 아래로 내려가는 방식

**한 번 구한 답을 적어 두었다가 같은 값을 다시 물으면 계산하지 않고 적어 둔 답을 돌려줍니다. 코드에는 한 줄만 추가하면 됩니다.**

1절에서 호출이 그렇게 늘어난 까닭은 같은 값을 여러 갈래에서 다시 구한 데 있으므로, 한 번 구한 답을 적어 두었다가 같은 n 이 다시 오면 꺼내 주기만 해도 그 되풀이가 사라집니다. 이렇게 답을 적어 두었다가 다시 쓰는 방법을 **메모이제이션**(memoization)이라 합니다. 이 글의 코드와 출력에서는 같은 방법을 적어 두기라고 부릅니다. 이름은 어려워 보여도 실제로는 구한 값을 딕셔너리에 넣었다가 필요할 때 꺼낼 뿐입니다. 해시와 정렬 편에서 본 해시(키로 값을 둘 자리를 바로 계산하는 방식)가 여기서 그대로 쓰입니다.

세 방법의 답이 같은지와 걸린 시간, 부른 횟수가 얼마나 다른지 확인하려고 피보나치 30 을 그냥 재귀, 적어 두기, 아래에서 쌓기로 각각 구해 나란히 측정합니다. 아래에서 쌓기는 작은 n 부터 표를 채워 올라가는 방법으로, 3절에서 자세히 풀고 여기서는 결과만 함께 봅니다. `적어두기` 함수는 그냥 재귀와 같지만 `적어둔것` 딕셔너리에 n 이 이미 있으면 계산하지 않고 그 값을 바로 돌려줍니다.

```python
# 하는 일: 피보나치 30 을 그냥 재귀, 적어 두기, 아래에서 쌓기 세 방법으로 구해 답, 걸린 시간, 부른 횟수를 비교한다.
import time

# 1단계: 세 방법을 만든다
# 적어 두기는 그냥 재귀에 이미 구한 값을 딕셔너리에서 꺼내는 줄 하나를 더한 것이다. 아래에서 쌓기는 표의 앞 두 칸을 더해 채운다.
def 그냥(n):
    if n < 2: return n
    return 그냥(n-1) + 그냥(n-2)

적어둔것 = {}
불린횟수 = [0]
def 적어두기(n):
    불린횟수[0] += 1
    if n < 2: return n
    if n in 적어둔것: return 적어둔것[n]     # 이미 구한 것은 다시 안 구한다
    적어둔것[n] = 적어두기(n-1) + 적어두기(n-2)
    return 적어둔것[n]

def 아래에서(n):
    표 = [0, 1] + [0] * (n - 1)
    for i in range(2, n + 1):
        표[i] = 표[i-1] + 표[i-2]
    return 표[n]

# 2단계: 세 방법을 측정하고 답을 비교한다
N = 30
print(f"{'방법':<14}{'답':>10}{'시간(ms)':>12}{'부른 횟수':>12}")
t = time.perf_counter(); a = 그냥(N); ms = (time.perf_counter()-t)*1000
print(f"{'그냥 재귀':<14}{a:>10,}{ms:>12.1f}{'2,692,537':>12}")
t = time.perf_counter(); b = 적어두기(N); ms = (time.perf_counter()-t)*1000
print(f"{'적어 두기':<14}{b:>10,}{ms:>12.4f}{불린횟수[0]:>12,}")
t = time.perf_counter(); c = 아래에서(N); ms = (time.perf_counter()-t)*1000
print(f"{'아래에서 쌓기':<13}{c:>10,}{ms:>12.4f}{N-1:>12,}")
print(f"\n세 답이 같나 {a == b == c}")

# 출력 (시간은 돌릴 때마다 다르다):
# 2단계 뜻: 269만 번이 59번이 된다. 적어 두기는 f(2) 부터 f(30) 까지 29개만 한 번씩 계산하고 그때마다 두 번 부르니, 처음 부른 한 번까지 1 + 2 × 29 = 59번이다.
# 방법                     답      시간(ms)       부른 횟수
# 그냥 재귀            832,040       126.1   2,692,537
# 적어 두기            832,040      0.0116          59
# 아래에서 쌓기         832,040      0.0045          29
#
# 세 답이 같나 True
```

찍힌 표에서 세 방법의 답은 모두 832,040 이고 마지막 줄의 `세 답이 같나 True` 도 세 답이 같다고 확인해 줍니다. 부른 횟수는 그냥 재귀가 2,692,537번인 데 비해 적어 두기는 59번뿐이라 269만 번이 59번으로 줄었고 이번 실행에서 걸린 시간도 126.1ms 에서 0.0116ms 로 줄었습니다. 그렇게 줄이려고 코드에는 `if n in 적어둔것: return 적어둔것[n]` 한 줄만 추가했습니다.

59라는 횟수도 계산으로 맞춰 볼 수 있습니다. n 이 30 이므로 적어 두기가 실제로 계산하는 값은 `f(2)` 부터 `f(30)` 까지 29개이고 값마다 딱 한 번씩만 계산합니다. 하나를 계산할 때마다 `적어두기(n-1)` 과 `적어두기(n-2)` 를 한 번씩 부르니 29개를 계산하며 2 × 29 번을 부르고 맨 처음 부른 `적어두기(30)` 한 번까지 더하면 출력의 뜻 줄대로 1 + 2 × 29 = 59번입니다. 계산하지 않은 나머지 호출은 `f(0)` 과 `f(1)` 처럼 바로 값을 돌려주거나 적어 둔 값을 읽고 끝났습니다. **값마다 한 번씩만 구하면 계산 횟수가 n 에 비례하므로 시간은 O(n) 으로 줄어듭니다.**

파이썬에는 적어 두기를 대신 해 주는 도구도 있습니다. 함수 위에 `@lru_cache(maxsize=None)` 한 줄을 붙이면 파이썬이 인자마다 답을 적어 두므로 `적어둔것` 같은 딕셔너리를 직접 만들지 않아도 됩니다. `maxsize=None` 은 적어 둘 답의 개수에 한도를 두지 않는다는 뜻입니다. 다만 `@lru_cache` 도 인자를 딕셔너리의 키처럼 쓰기 때문에 해시와 정렬 편에서 본 "키로 쓸 수 있는 것" 조건이 그대로 적용되어 리스트처럼 내용이 바뀔 수 있는 값이 인자로 오면 쓸 수 없습니다.

## 3. 아래에서 쌓기(타뷸레이션) — 반복문으로 채우는 표

**적어 두기는 큰 n 에서 출발해 필요한 작은 n 으로 파고들며 답을 채웁니다. 순서를 뒤집어 작은 n 부터 채워 올라가면 재귀가 아예 필요 없어집니다.**

적어 두기는 호출을 59번으로 줄였어도 여전히 재귀라서 깊이에 한계가 있습니다. 재귀 깊이는 아직 끝나지 않은 채 기다리는 함수 호출이 몇 겹 쌓였는지를 뜻합니다. `적어두기(30)` 은 `적어두기(1)` 에 닿을 때까지 호출이 n 만큼 쌓입니다.

작은 값부터 표를 순서대로 채워 올라가는 방법을 **타뷸레이션**(tabulation)이라 합니다. 이 글에서는 아래에서 쌓기라고 부릅니다. 2절 코드의 `아래에서` 함수가 이 방법으로 짠 함수입니다. `아래에서` 는 표의 앞 두 칸을 `[0, 1]` 로 시작하므로 `f(0)` 과 `f(1)` 의 값을 처음부터 압니다. 그래서 `f(2)` 는 앞 두 칸을 더해 바로 구합니다. `f(3)` 을 구할 차례에는 필요한 `f(1)` 과 `f(2)` 가 이미 표에 들어 있습니다. 이렇게 i 를 2 부터 n 까지 하나씩 키우며 `표[i] = 표[i-1] + 표[i-2]` 로 한 칸씩 채우면 함수가 자기 자신을 부를 일이 없습니다.

두 방법은 같은 답을 내지만 코드의 모양, 계산하는 범위, 재귀 깊이, 짜는 방법이 다릅니다.

| | 적어 두기 (위에서) | 아래에서 쌓기 |
|---|---|---|
| 모양 | 재귀 + 딕셔너리 | 반복문 + 리스트 |
| 계산하는 범위 | 실제로 필요한 것만 | 0부터 n까지 전부 |
| 재귀 깊이 | n만큼 쌓인다 | 없다 |
| 짜기 | 원래 식을 그대로 옮기면 된다 | 채우는 순서를 정해야 한다 |

표의 「계산하는 범위」 줄처럼 적어 두기는 실제로 필요한 값만 계산하고 아래에서 쌓기는 0 부터 n 까지 모든 칸을 채우므로, **필요한 값이 전체의 일부뿐인 문제에서는 적어 두기가 유리합니다.** 반대로 어차피 모든 칸이 필요하고 n 이 아주 크다면 재귀 깊이 한계에 걸릴 수 있는 적어 두기보다 재귀 깊이가 없는 아래에서 쌓기가 안전합니다.

2절 출력의 부른 횟수 칸에서는 아래에서 쌓기가 29 로 가장 작았습니다. 이 29 는 코드가 `N-1` 로 찍은 값이라 함수 호출 수가 아니라 반복문이 `표[2]` 부터 `표[30]` 까지 한 칸씩 채운 횟수이며 값마다 정확히 한 번씩 계산했다는 뜻입니다. 적어 두기는 같은 값을 두 번씩 물어 59번이 되었습니다. 한 번은 그 값을 계산하려고 부르고 한 번은 적어 둔 값을 읽으려고 다시 부릅니다.

## 4. 점화식을 세우는 순서

**동적 계획법은 코드를 짜는 일보다 "표에 무엇을 적을지" 정하는 일이 더 어렵습니다.**

앞에서 구한 값들로 지금 값을 구하는 식을 **점화식**이라 합니다. 피보나치의 `f(n) = f(n-1) + f(n-2)` 가 점화식인데, 피보나치는 문제 자체가 이 식을 알려 주었지만 실제 문제는 식을 알려 주지 않습니다. 그래도 아래 네 단계를 차례로 밟으면 헤매지 않고 표와 식을 정할 수 있습니다.

**첫째, 칸 하나에 무엇을 적는지를 한 문장으로 씁니다.** 예를 들어 "표[i] = i번째까지 봤을 때의 최댓값" 같은 문장입니다. 이 한 문장이 나오지 않는다면 문제를 아직 이해하지 못했다는 뜻입니다.

**둘째, 마지막에 한 선택 하나만 생각합니다.** 지금 칸의 답에 이르기 바로 전에 어떤 선택을 했을 수 있는지, 그리고 선택마다 표의 어느 칸을 봐야 하는지를 묻습니다. 5절의 배낭 문제라면 마지막 물건을 넣었는지 넣지 않았는지가 이 선택입니다. 처음부터 끝까지 한꺼번에 그리려 하면 막히지만 마지막 한 걸음만 보면 대체로 풀립니다.

**셋째, 시작값을 정합니다.** `표[0]` 에 무엇을 둘지, 아무것도 고르지 않았을 때의 값이 0 인지 무한대인지를 정하는 단계입니다. 무한대는 어떤 수보다도 큰 값으로, 9절의 거스름돈 코드는 `float("inf")` 로 만든 `무한` 을 아직 만들 방법을 찾지 못한 금액의 칸에 넣습니다. 최솟값 문제에서 `표[0]` 뿐 아니라 나머지 칸까지 처음부터 0 으로 채우면 답이 전부 0 으로 나옵니다. 9절 코드처럼 `표[금-c] + 1` 이 지금 칸보다 작을 때만 칸을 고치는 코드라면 `표[금-c] + 1` 은 언제나 1 이상이라 0 보다 작아질 수 없어서 어느 칸도 처음의 0 에서 바뀌지 않습니다.

**넷째, 칸을 채우는 순서를 확인합니다.** `표[i]` 를 구하는 순간에는 그 계산에 필요한 칸이 이미 채워져 있어야 합니다. 3절의 아래에서 쌓기는 i 를 2 부터 키워 가므로 `표[i]` 를 구할 때 `표[i-1]` 과 `표[i-2]` 가 언제나 먼저 채워져 있습니다.

다음 절에서는 배낭 문제를 놓고 이 네 단계를 그대로 밟아 봅니다.

## 5. 배낭 문제 — 표를 채우고 거슬러 올라가는 풀이

**배낭 문제는 무게 한도가 있고 물건마다 무게와 값이 정해져 있을 때, 한도 안에서 물건을 골라 값의 합을 가장 크게 만드는 문제입니다.**

4절의 네 단계를 이 문제에 하나씩 적용하면 다음과 같습니다.

1. **칸의 뜻**: `표[i][w]` 는 앞에서부터 i개 물건만 쓸 수 있고 무게 한도가 w 일 때 얻을 수 있는 값의 최대 합입니다.
2. **마지막 선택**: i번째 물건은 넣거나 넣지 않거나 두 가지 가운데 하나입니다. 넣지 않으면 앞의 i-1개로 한도 w 를 채운 `표[i-1][w]` 가 그대로 답입니다. 넣으면 그 물건의 무게만큼 한도가 줄어드니 앞의 i-1개로 한도 `w-무게` 를 채운 값에 그 물건의 값을 더한 `표[i-1][w-무게] + 값` 이 답입니다. 칸에는 두 값 가운데 큰 값을 적습니다.
3. **시작값**: 물건을 하나도 쓰지 않으면 담은 것이 없어 값의 합도 0 이므로 첫 줄은 모두 0 입니다.
4. **순서**: 아래 줄을 구하려면 바로 위 줄이 있어야 하므로 물건 순서대로 한 줄씩 내려가며 채웁니다.

이 네 단계대로 물건 4개와 무게 한도 5 로 표를 채워 최대값을 구한 뒤 표를 거슬러 올라가 어떤 물건을 골랐는지까지 찾아봅니다. 물건은 노트북(무게 3, 값 9), 카메라(무게 2, 값 6), 책(무게 1, 값 2), 렌즈(무게 2, 값 5)입니다. 한도가 물건의 무게보다 작아 넣을 수 없는 칸에서는 코드가 `넣기` 를 -1 로 두어 `안넣기` 값이 뽑히게 합니다.

```python
# 하는 일: 물건 4개와 무게 한도 5 로 배낭 표를 채우고, 얻는 최대값과 고른 물건을 표를 거꾸로 따라가 찾는다.
물건 = [("노트북", 3, 9), ("카메라", 2, 6), ("책", 1, 2), ("렌즈", 2, 5)]
한도 = 5

# 1단계: 표를 채운다
# 표[i][w] 는 앞의 i 개 물건만 쓰고 무게 한도가 w 일 때의 최대값이다. i 번째 물건을 안 넣은 값과 넣은 값 가운데 큰 쪽을 적는다.
표 = [[0] * (한도 + 1) for _ in range(len(물건) + 1)]

for i, (이름, 무게, 값) in enumerate(물건, 1):
    for w in range(한도 + 1):
        안넣기 = 표[i-1][w]
        넣기 = 표[i-1][w-무게] + 값 if w >= 무게 else -1
        표[i][w] = max(안넣기, 넣기)

# 2단계: 표를 찍는다
print(f"{'':<8}" + "".join(f"{w:>5}" for w in range(한도 + 1)) + "   ← 남은 무게")
print(f"{'없음':<7}" + "".join(f"{x:>5}" for x in 표[0]))
for i, (이름, 무게, 값) in enumerate(물건, 1):
    print(f"{이름:<7}" + "".join(f"{x:>5}" for x in 표[i]) + f"   (무게 {무게}, 값 {값})")

print(f"\n무게 {한도} 까지 담아 얻는 최대값 {표[len(물건)][한도]}")

# 3단계: 표를 거꾸로 따라가 고른 물건을 찾는다
# 위 줄과 값이 다르면 그 물건을 넣었다는 뜻이다.
고른것, w = [], 한도
for i in range(len(물건), 0, -1):
    if 표[i][w] != 표[i-1][w]:          # 값이 달라졌다 = 이 물건을 넣었다
        이름, 무게, 값 = 물건[i-1]
        고른것.append(이름)
        w -= 무게
print("고른 것", 고른것[::-1])

# 출력:
# 2단계 뜻: 카메라 줄의 무게 5 칸의 15 는 노트북과 카메라를 둘 다 넣은 값이다. 렌즈 줄이 책 줄과 같은 것은 렌즈가 어느 무게에서도 도움이 안 됐다는 뜻이다.
#             0    1    2    3    4    5   ← 남은 무게
# 없음         0    0    0    0    0    0
# 노트북        0    0    0    9    9    9   (무게 3, 값 9)
# 카메라        0    0    6    9    9   15   (무게 2, 값 6)
# 책          0    2    6    9   11   15   (무게 1, 값 2)
# 렌즈         0    2    6    9   11   15   (무게 2, 값 5)
#
# 무게 5 까지 담아 얻는 최대값 15
# 3단계 뜻: 15 를 만든 물건은 노트북과 카메라다.
# 고른 것 ['노트북', '카메라']
```

출력의 `무게 5 까지 담아 얻는 최대값 15` 는 맨 아래 렌즈 줄의 무게 5 칸에 있는 값입니다. 표는 왼쪽 위에서 오른쪽 아래로 읽어 내려갑니다. 노트북 줄은 노트북의 무게가 3 이라 한도가 그보다 작은 무게 0, 1, 2 칸에는 넣을 자리가 없어 0 이고 무게 3 칸부터 노트북 하나를 넣은 9 가 적힙니다. 카메라 줄의 무게 5 칸 15 는 노트북(무게 3)과 카메라(무게 2)를 둘 다 넣은 값입니다. 이 칸에서 카메라를 넣지 않은 값은 위 줄 같은 칸의 9 이고 넣은 값은 한도 5 에서 카메라의 무게 2 를 뺀 위 줄 무게 3 칸의 9 에 카메라의 값 6 을 더한 15 라서 큰 값인 15 가 적힙니다. 책 줄을 카메라 줄과 비교하면 두 칸이 바뀌는데, 무게 1 칸은 책 하나를 넣은 2 가 되고 무게 4 칸은 노트북과 책을 함께 넣은 11 이 됩니다.

렌즈 줄은 책 줄과 칸마다 값이 똑같습니다. **렌즈는 어느 무게에서도 값을 늘리지 못했습니다.** 렌즈는 무게 2 에 값 5 인데 같은 무게의 카메라가 값 6 이라 렌즈와 카메라 가운데 하나만 고른다면 언제나 카메라가 낫습니다. 두 물건을 함께 담을 수 있는 무게 4 칸에서도 카메라와 렌즈를 넣은 11 은 노트북과 책을 넣은 11 과 같을 뿐이라 칸의 값이 늘지 않았습니다.

표에는 최대값만 남기 때문에 어느 물건을 골랐는지는 마지막 반복문이 표를 **거슬러 올라가며** 찾습니다. `표[i][w]` 는 i번째 물건을 넣지 않은 값 `표[i-1][w]` 와 넣은 값 가운데 큰 값이므로, 두 칸이 다르면 넣은 값이 더 커서 i번째 물건을 넣었다는 뜻입니다. 그래서 무게 5 에서 시작해 맨 아래 줄부터 한 줄씩 올라가며 위아래 두 칸을 비교합니다. 렌즈 줄과 책 줄의 무게 5 칸은 둘 다 15 이고 책 줄과 카메라 줄도 둘 다 15 라서 렌즈와 책은 넣지 않았습니다. 카메라 줄의 15 는 노트북 줄의 9 와 달라 카메라를 넣었고 남은 무게는 5 - 2 = 3 이 됩니다. 무게 3 칸에서는 노트북 줄의 9 가 없음 줄의 0 과 달라 노트북도 넣었으므로 출력에 `고른 것 ['노트북', '카메라']` 가 찍힙니다. 그래프 탐색 편의 BFS(너비 우선 탐색, 출발점에서 가까운 마디부터 한 층씩 넓혀 가는 탐색)에서 도착점부터 앞마디를 거슬러 올라가 경로를 찾던 것과 같은 방법입니다.

:::deep 표를 한 줄로 줄이는 방법과 반복 방향

위 표에서 `표[i]` 줄을 채울 때 읽는 줄은 바로 위의 `표[i-1]` 하나뿐이고 그보다 위의 줄들은 다시 읽지 않습니다. 그렇다면 줄 하나만 남겨 두고 물건 차례마다 그 줄을 덮어써도 되지 않을까요?

됩니다. 다만 무게를 도는 반복문을 **뒤에서 앞으로**, 큰 무게 칸부터 작은 무게 칸으로 돌려야 합니다. 한 줄로도 같은 답이 나오는지와 방향을 거꾸로 하면 무엇이 틀리는지 보려고 같은 물건 4개를 이번에는 무게 한도 6 으로 풀어 봅니다.

```python
# 하는 일: 같은 물건 4개로 무게 한도 6 의 배낭 문제를 한 줄짜리 표로 풀고, 무게를 앞에서 뒤로 돌면 왜 틀리는지 비교한다.
물건 = [("노트북", 3, 9), ("카메라", 2, 6), ("책", 1, 2), ("렌즈", 2, 5)]
한도 = 6

# 1단계: 한 줄을 뒤에서 앞으로 덮어쓴다
# 한줄[w] 를 고칠 때 읽는 한줄[w-무게] 는 이번 물건을 넣기 전 값이어야 한다. 뒤에서 앞으로 돌면 아직 안 건드린 자리라 안전하다.
한줄 = [0] * (한도 + 1)
print(f"{'넣은 물건':<8}" + "".join(f"{w:>5}" for w in range(한도 + 1)))
print(f"{'시작':<7}" + "".join(f"{x:>5}" for x in 한줄))
for 이름, 무게, 값 in 물건:
    for w in range(한도, 무게 - 1, -1):        # 뒤에서 앞으로
        한줄[w] = max(한줄[w], 한줄[w-무게] + 값)
    print(f"{이름:<7}" + "".join(f"{x:>5}" for x in 한줄))

# 2단계: 최대값과 들고 있는 칸 수를 찍는다
print(f"\n최대값 {한줄[한도]}, 들고 있는 칸 {len(한줄)}개 (표 전체는 {(len(물건)+1)*(한도+1)}칸)")

# 3단계: 앞에서 뒤로 돌려 본다
# 앞에서 뒤로 돌면 같은 물건을 여러 번 넣게 된다
틀린것 = [0] * (한도 + 1)
for 이름, 무게, 값 in 물건:
    for w in range(무게, 한도 + 1):            # 앞에서 뒤로 — 틀린 방향
        틀린것[w] = max(틀린것[w], 틀린것[w-무게] + 값)
print(f"앞에서 뒤로 돌면 {틀린것[한도]} — 같은 물건을 여러 번 담은 값이라 틀리다")

# 출력:
# 1단계 뜻: 물건을 하나 넣을 때마다 한 줄을 덮어쓴다. 마지막 줄의 무게 6 칸의 17 이 답이다.
# 넣은 물건       0    1    2    3    4    5    6
# 시작         0    0    0    0    0    0    0
# 노트북        0    0    0    9    9    9    9
# 카메라        0    0    6    9    9   15   15
# 책          0    2    6    9   11   15   17
# 렌즈         0    2    6    9   11   15   17
# 2단계 뜻: 표 전체 35칸 대신 7칸만 들고도 같은 최대값 17 을 낸다.
#
# 최대값 17, 들고 있는 칸 7개 (표 전체는 35칸)
# 3단계 뜻: 앞에서 뒤로 돌면 같은 물건을 여러 번 담아 18 이 나온다. 물건마다 하나씩만 담는 이 문제의 답이 아니다.
# 앞에서 뒤로 돌면 18 — 같은 물건을 여러 번 담은 값이라 틀리다
```

1단계 출력의 마지막 렌즈 줄 무게 6 칸에 최대값 17 이 나왔습니다. 2단계 줄대로 이 값을 내는 동안 들고 있던 칸은 7개뿐입니다. 표 전체를 들고 있었다면 시작 줄과 물건 4개의 줄을 합친 5줄에 무게 0 부터 6 까지 7칸씩이라 5 × 7 = 35칸이 필요했습니다. 무게 한도가 십만이고 물건이 천 개라면 표 전체는 천 줄에 십만 칸씩이지만 한 줄짜리 표는 십만 칸만 들고 있으면 되므로, 이 차이로 메모리 초과로 떨어질지 통과할지가 정해집니다.

반복 방향이 답을 바꾸는 까닭은 `한줄[w]` 를 고칠 때 읽는 `한줄[w-무게]` 에 있습니다. 이 값은 **이번 물건을 반영하기 전의 값**이어야 합니다. 큰 무게 칸부터 고쳐 내려가면 `w-무게` 칸은 이번 물건 차례에 아직 고치지 않은 칸이라 앞 물건까지의 값이 그대로 남아 있어 안전합니다. 노트북(무게 3, 값 9) 차례라면 무게 6 칸을 먼저 고치는데, 이때 읽는 무게 3 칸은 아직 0 이라 무게 6 칸은 9 가 됩니다. 작은 무게 칸부터 고쳐 올라가면 반대로 이번 물건을 넣어 이미 고친 칸을 다시 읽어서 같은 물건을 두 번 담습니다. 노트북 차례에 무게 3 칸을 먼저 9 로 고친 뒤 무게 6 칸이 그 9 를 읽으면 9 + 9 = 18 로 노트북 두 개를 담은 값이 나옵니다. 3단계가 찍은 18 은 이렇게 같은 물건을 여러 번 담아 나온 값이라 물건마다 하나씩만 담는 이 문제의 답이 아닙니다.

거꾸로 보면 **앞에서 뒤로 도는 반복문은 다른 문제의 정답입니다.** 같은 물건을 몇 개든 담아도 되는 문제라면 이번 물건을 넣은 값을 다시 읽어 한 번 더 담는 계산이 오히려 맞습니다. 반복 방향 하나로 "물건마다 한 번씩"인 문제와 "몇 개든 무제한"인 문제가 나뉩니다.
:::

## 6. 백트래킹 — 놓아 보고 막히면 물러서는 탐색

**표에 적어 둘 만큼 겹치는 계산이 없는 문제는 결국 경우를 하나씩 다 해 봐야 하지만 백트래킹은 아니다 싶은 순간 바로 되돌아옵니다.**

동적 계획법은 작은 문제의 답이 겹칠 때 쓰는데, 답이 겹치지 않는 문제도 많습니다. 체스의 퀸은 가로, 세로, 대각선 방향에 있는 다른 말을 공격할 수 있습니다. "퀸 8개를 서로 공격하지 못하게 판에 놓아라" 같은 문제가 겹치지 않는 문제의 예입니다. 이런 문제에서는 퀸을 하나씩 놓아 보고 안 되면 물러서며 답을 찾습니다.

이렇게 하나씩 놓아 보다가 막히면 바로 앞 단계로 물러서 다른 선택을 해 보는 방법이 **백트래킹**입니다. 그래프 탐색 편의 DFS(깊이 우선 탐색, 한 갈래를 끝까지 내려간 뒤 돌아와 다음 갈래로 가는 탐색)와 구조가 같은데, 갈래를 내려갔다가 올라올 때 **상태를 원래대로 되돌린다**는 점이 다릅니다. 퀸 문제에서 상태는 지금까지 퀸을 놓은 칸 번호의 목록인 `놓은자리` 입니다.

4 × 4 판에 퀸 4개를 서로 공격하지 못하게 놓는 방법을 모두 찾으면서 놓아 보다 막혀 되돌아가는 과정을 앞에서부터 16줄만 찍어 봅니다. 코드는 0줄부터 한 줄에 퀸을 하나씩 놓으므로 같은 줄은 따로 확인하지 않습니다. 앞서 놓은 퀸과 칸 번호가 같거나 대각선 위에 있는 칸만 막힌 칸으로 보고 건너뛰는데, 대각선은 두 퀸의 칸 번호 차이와 줄 번호 차이가 같은 경우라 코드에서는 `abs(칸 - c) != 줄 - r` 로 확인합니다.

```python
# 하는 일: 4 × 4 판에 퀸 4개를 서로 공격하지 못하게 놓는 방법을 백트래킹으로 모두 찾고, 놓아 보다 막혀 되돌아가는 과정의 앞 16줄을 찍는다.
N = 4
답 = []
시도횟수 = [0]

# 1단계: 한 줄씩 놓아 보고 막히면 되돌리는 함수를 만든다
# 내려갈 때 놓은자리에 넣고 올라올 때 뺀다. 이 짝이 백트래킹의 전부다.
def 놓기(줄, 놓은자리, 로그):
    시도횟수[0] += 1
    if 줄 == N:
        답.append(list(놓은자리)); 로그.append(f"{놓은자리} 완성")
        return
    for 칸 in range(N):
        안전 = all(칸 != c and abs(칸 - c) != 줄 - r for r, c in enumerate(놓은자리))
        if not 안전:
            로그.append(f"{'  '*줄}{줄}줄 {칸}칸 → 막힘, 되돌린다")
            continue
        로그.append(f"{'  '*줄}{줄}줄 {칸}칸 놓음")
        놓은자리.append(칸)
        놓기(줄 + 1, 놓은자리, 로그)
        놓은자리.pop()                      # 되돌린다
# 2단계: 0줄부터 놓아 보고 과정을 찍는다
로그 = []
놓기(0, [], 로그)
for 줄 in 로그[:16]:
    print(줄)
print("  ...")
print(f"\n답 {답}")
print(f"부른 횟수 {시도횟수[0]}회, 가지치기 없이 전부 놓으면 {N**N}회")

# 출력:
# 2단계 뜻: 들여쓰기가 깊어졌다 얕아졌다 하는 것이 되돌아오는 모양이다. 1줄 2칸에 놓았다가 2줄의 네 칸이 모두 막히자 1줄로 올라와 3칸을 놓는다.
# 0줄 0칸 놓음
#   1줄 0칸 → 막힘, 되돌린다
#   1줄 1칸 → 막힘, 되돌린다
#   1줄 2칸 놓음
#     2줄 0칸 → 막힘, 되돌린다
#     2줄 1칸 → 막힘, 되돌린다
#     2줄 2칸 → 막힘, 되돌린다
#     2줄 3칸 → 막힘, 되돌린다
#   1줄 3칸 놓음
#     2줄 0칸 → 막힘, 되돌린다
#     2줄 1칸 놓음
#       3줄 0칸 → 막힘, 되돌린다
#       3줄 1칸 → 막힘, 되돌린다
#       3줄 2칸 → 막힘, 되돌린다
#       3줄 3칸 → 막힘, 되돌린다
#     2줄 2칸 → 막힘, 되돌린다
#   ...
# 2단계 뜻: 답은 2가지이고 함수는 17회 불렀다. 막힌 갈래를 일찍 버려서 전부 놓는 256회보다 훨씬 적다.
#
# 답 [[1, 3, 0, 2], [2, 0, 3, 1]]
# 부른 횟수 17회, 가지치기 없이 전부 놓으면 256회
```

찍힌 답은 `[1, 3, 0, 2]` 와 `[2, 0, 3, 1]` 2가지입니다. 각 답은 0줄부터 3줄까지 퀸을 놓은 칸 번호를 차례로 적은 목록이라 첫 답은 0줄 1칸, 1줄 3칸, 2줄 0칸, 3줄 2칸에 퀸을 놓은 배치입니다. 찍힌 과정의 들여쓰기는 지금 몇 번째 줄을 놓는 중인지를 나타내므로 들여쓰기가 깊어졌다가 얕아지는 자리가 되돌아온 자리입니다. 처음에 0줄 0칸에 놓은 뒤 1줄 0칸은 0줄의 퀸과 칸 번호가 같고 1줄 1칸은 대각선이라 둘 다 막혀서 1줄 2칸에 놓았습니다. 그런데 2줄의 네 칸이 모두 막히자 1줄로 올라와 1줄 3칸을 놓았습니다.

`놓은자리.append(칸)` 과 `놓은자리.pop()` 은 짝으로 움직입니다. **아래 줄로 내려갈 때 넣고 다시 올라올 때 뺍니다.** 코드 주석의 말대로 이 짝이 백트래킹의 전부입니다. `pop()` 을 빼먹으면 1줄 2칸 갈래에서 돌아온 뒤에도 `놓은자리` 가 `[0, 2]` 로 남아 옆 갈래인 1줄 3칸을 확인할 때도 1줄 2칸의 퀸이 그대로 있는 것으로 계산되므로 답이 틀립니다.

## 7. 가지치기 — 안 될 갈래를 일찍 버리는 방법

**6절 출력의 마지막 줄에서 백트래킹이 얼마나 일을 덜어 주는지 보입니다. 퀸을 놓는 256가지를 다 만들어 보지 않고 함수 17번 호출로 끝났습니다.**

4 × 4 판에 퀸 4개를 한 줄에 하나씩 놓는 방법은 줄마다 네 칸 가운데 하나를 고르므로 4 × 4 × 4 × 4, 곧 4⁴ = 256가지입니다. 퀸을 다 놓은 뒤에 확인한다면 이 256가지 배치를 모두 만들어 하나씩 봐야 하지만 6절 코드는 한 줄 놓을 때마다 확인해서 함수를 17번만 불렀습니다.

두 방식의 차이는 **언제 확인하느냐**에서 나옵니다. 1줄에서 이미 막힌 칸이 나오면 그 아래 2줄과 3줄에 네 칸씩 놓는 4 × 4 = 16가지 갈래는 하나도 보지 않습니다. 6절 출력에서도 1줄 0칸과 1줄 1칸이 막히자 코드는 그 아래 2줄로 내려가지 않고 바로 다음 칸으로 넘어갔습니다.

이렇게 답이 될 수 없는 갈래를 일찍 잘라 버리는 일을 **가지치기**(pruning)라 합니다. 백트래킹 문제의 성능은 거의 전적으로 가지치기에서 정해집니다. **기본형 가지치기는 단계마다 "지금까지 만든 부분 답이 이미 조건을 어겼나"를 확인합니다.** 부분 답은 아직 끝까지 채우지 않은 중간 단계의 답으로, 퀸 문제에서는 몇 줄까지만 퀸을 놓은 `놓은자리` 가 부분 답입니다.

한 단계 더 나아간 가지치기도 있습니다. 최댓값을 찾는 문제에서 남은 선택을 모두 가장 좋게 골라도 지금까지의 최고 기록을 넘지 못한다면 그 갈래는 더 볼 필요가 없습니다. 이 판단이 정확할수록 탐색이 빨라집니다.

## 8. 그리디 — 지금 가장 좋아 보이는 것만 고르는 방법

**앞으로 올 선택을 따지지 않고 지금 가장 좋아 보이는 것만 골라도 답이 나오는 문제가 있습니다.**

회의실은 하나인데 회의 신청이 여러 건 들어왔습니다. 시간이 겹치지 않게 회의를 가장 많이 잡으려면 어떤 기준으로 골라야 할까요? 그럴듯한 기준으로는 시작이 빠른 순, 길이가 짧은 순, 끝이 빠른 순의 세 가지가 떠오릅니다.

세 기준이 실제로 몇 개씩 잡는지 비교하려고 회의 신청 6개를 기준마다 정렬해 차례로 잡아 봅니다. 신청은 A(9~16시), B(10~12시), C(11~13시), D(12~15시), E(13~14시), F(15~17시)입니다. 잡는 규칙은 세 기준이 모두 같습니다. 정렬된 순서대로 회의를 보며 시작 시각 `s` 가 마지막으로 잡은 회의가 끝난 시각 `끝난시각` 이상이면 그 회의를 잡습니다.

```python
# 하는 일: 회의 신청 6개를 세 가지 기준으로 정렬해 겹치지 않게 차례로 잡아 보고, 어느 기준이 가장 많이 잡는지 비교한다.
# (이름, 시작, 끝)
회의 = [("A", 9, 16), ("B", 10, 12), ("C", 11, 13), ("D", 12, 15), ("E", 13, 14), ("F", 15, 17)]

for 기준, 정렬키 in (("시작이 빠른 순", lambda m: m[1]),
                    ("길이가 짧은 순", lambda m: m[2] - m[1]),
                    ("끝이 빠른 순",  lambda m: m[2])):
    잡힌것, 끝난시각 = [], 0
    for 이름, s, e in sorted(회의, key=정렬키):
        if s >= 끝난시각:
            잡힌것.append(이름); 끝난시각 = e
    print(f"{기준:<14}{len(잡힌것)}개  {잡힌것}")

print("\n끝이 빠른 순이 가장 많이 잡는다 — 방을 가장 일찍 비워 주니 뒤에 남는 시간이 가장 많다.")

# 출력:
# 뜻: 셋 다 그리디인데 잡은 수가 1개, 2개, 3개로 다르다.
# 시작이 빠른 순      1개  ['A']
# 길이가 짧은 순      2개  ['E', 'F']
# 끝이 빠른 순       3개  ['B', 'E', 'F']
# 뜻: 끝나는 시각이 빠른 회의부터 잡으면 방이 가장 일찍 비어 뒤에 남는 시간이 가장 많다.
#
# 끝이 빠른 순이 가장 많이 잡는다 — 방을 가장 일찍 비워 주니 뒤에 남는 시간이 가장 많다.
```

출력을 보면 세 기준이 모두 그리디인데 잡은 회의 수가 서로 다릅니다. 시작이 빠른 순은 `['A']` 1개, 길이가 짧은 순은 `['E', 'F']` 2개, 끝이 빠른 순은 `['B', 'E', 'F']` 3개를 잡았습니다. **그리디에서는 코드보다 어떤 기준으로 고를지 정하는 일이 더 어렵습니다.**

시작이 빠른 순은 9시에 가장 먼저 시작하는 A 를 잡았습니다. 그런데 A 는 16시까지 이어지고 16시나 그 뒤에 시작하는 회의가 하나도 없어서 방을 A 하나에 다 내주고 끝났습니다. 길이가 짧은 순은 1시간짜리 E(13~14시)를 가장 먼저 잡았습니다. 이 반복문은 그 뒤로 E 가 끝난 14시보다 먼저 시작하는 회의를 받지 않으므로 E 와 시간이 겹치지 않는 B(10~12시)까지 건너뛰었습니다. `s >= 끝난시각` 은 마지막으로 잡은 회의 하나와만 비교하는데, 이 비교는 시작 시각 순이나 끝나는 시각 순으로 정렬해 잡은 회의가 시간 순서대로 쌓일 때만 맞습니다.

끝나는 시각으로 정렬하면 B(12시), C(13시), E(14시), D(15시), A(16시), F(17시) 차례가 됩니다. 가장 먼저 끝나는 B 를 잡은 뒤 C 는 B 가 끝나는 12시보다 이른 11시에 시작하므로 건너뛰고 13시에 시작하는 E 를 잡습니다. E 가 14시에 끝난 뒤로는 12시에 시작하는 D 와 9시에 시작하는 A 를 건너뛰고 15시에 시작하는 F 를 잡아 모두 B, E, F 3개가 됩니다.

끝이 빠른 순이 답을 내는 까닭은 말로 설명할 수 있습니다. **방을 가장 일찍 비워 주는 회의를 잡으면 그 뒤에 남는 시간이 가장 많으므로 그 회의를 잡아서 손해 볼 일이 없습니다.** 이번 신청에서는 B 가 12시로 가장 먼저 끝나므로 B 를 첫 회의로 잡으면 다른 어떤 회의를 첫 회의로 잡을 때보다 방이 일찍 비어 그만큼 뒤에 올 회의를 고를 시간이 많이 남습니다. 그리디는 이렇게 손해가 없다는 설명이 되는 기준을 찾았을 때만 믿을 수 있습니다.

## 9. 그리디가 틀리는 경우

**손해가 아닌 까닭을 설명할 수 없는 기준을 그럴듯해 보인다는 이유만으로 쓰면 오류도 없이 조용히 틀립니다.**

거스름돈 문제가 대표적인 예입니다. 동전 종류가 주어졌을 때 정해진 금액을 가장 적은 개수의 동전으로 만드는 문제인데, 언뜻 보면 큰 동전부터 쓰는 방법이 당연히 맞아 보입니다.

큰 것부터 쓰는 그리디가 정말 가장 적은 개수를 내는지 동전 두 벌로 확인합니다. 우리가 쓰는 500, 100, 50, 10 으로 1260원을 만들 때와 4, 3, 1 로 6원을 만들 때, 큰 것부터 쓰는 그리디와 모든 경우를 따지는 DP 가 각각 동전을 몇 개 쓰는지 찍습니다. DP 의 `표[금]` 은 금액 `금` 을 만드는 가장 적은 동전 수이고 동전 `c` 마다 `c` 를 마지막에 쓴 경우의 `표[금-c] + 1` 이 지금 칸보다 작으면 그 값으로 고칩니다. `고른[금]` 에는 그때 마지막으로 쓴 동전을 적어 두었다가 나중에 거꾸로 따라가며 쓴 동전 목록을 꺼냅니다.

```python
# 하는 일: 동전 두 벌로 금액을 가장 적은 수의 동전으로 만들며, 큰 것부터 쓰는 그리디와 전부 따지는 DP 의 답을 비교한다.
# 1단계: 큰 것부터 쓰는 그리디를 만든다
def 그리디(동전, 금액):
    남은, 쓴것 = 금액, []
    for c in sorted(동전, reverse=True):
        while 남은 >= c:
            남은 -= c; 쓴것.append(c)
    return (쓴것 if 남은 == 0 else None)

# 2단계: 금액마다 가장 적은 동전 수를 구하는 DP 를 만든다
# 표[금] 은 금을 만드는 가장 적은 동전 수다. 고른[금] 에 마지막으로 쓴 동전을 적어 두고, 거꾸로 따라가 쓴 동전을 꺼낸다.
def 최적(동전, 금액):
    무한 = float("inf")
    표 = [0] + [무한] * 금액
    고른 = [None] * (금액 + 1)
    for 금 in range(1, 금액 + 1):
        for c in 동전:
            if c <= 금 and 표[금-c] + 1 < 표[금]:
                표[금] = 표[금-c] + 1
                고른[금] = c
    if 표[금액] == 무한: return None
    쓴것, 남은 = [], 금액
    while 남은:
        쓴것.append(고른[남은]); 남은 -= 고른[남은]
    return 쓴것

# 3단계: 동전 두 벌로 비교한다
for 동전, 금액 in (([500, 100, 50, 10], 1260), ([4, 3, 1], 6)):
    g, o = 그리디(동전, 금액), 최적(동전, 금액)
    같나 = "같다" if (g and o and len(g) == len(o)) else "다르다"
    print(f"동전 {동전}, 금액 {금액}")
    print(f"  큰 것부터 (그리디)  {len(g)}개  {g}")
    print(f"  전부 따져 (DP)     {len(o)}개  {o}")
    print(f"  → {같나}\n")

# 출력:
# 3단계 뜻: 우리가 쓰는 동전에서는 그리디와 DP 가 같은 6개를 낸다.
# 동전 [500, 100, 50, 10], 금액 1260
#   큰 것부터 (그리디)  6개  [500, 500, 100, 100, 50, 10]
#   전부 따져 (DP)     6개  [500, 500, 100, 100, 50, 10]
#   → 같다
#
# 3단계 뜻: 동전이 4, 3, 1 이면 그리디는 4 를 먼저 써서 3개가 되지만, DP 는 3 두 개로 끝낸다.
# 동전 [4, 3, 1], 금액 6
#   큰 것부터 (그리디)  3개  [4, 1, 1]
#   전부 따져 (DP)     2개  [3, 3]
#   → 다르다
```

1260원에서는 그리디와 DP 가 똑같이 `[500, 500, 100, 100, 50, 10]` 6개를 냈습니다. 동전이 4, 3, 1 이면 그리디가 틀립니다. 6원을 만들 때 그리디는 가장 큰 4 를 먼저 쓰고 남은 2원을 1 두 개로 채워 `[4, 1, 1]` 3개를 내지만 DP 는 `[3, 3]` 2개로 끝냅니다. DP 가 2개를 찾는 과정은 6원에 마지막으로 쓸 동전을 세 가지 모두 따져 보면 알 수 있습니다. 마지막 동전이 4 면 2원을 만드는 최소 2개에 하나를 더해 3개, 3 이면 3원을 만드는 1개에 하나를 더해 2개, 1 이면 5원을 만드는 최소 2개에 하나를 더해 3개라서 DP 는 가장 적은 2개를 고릅니다.

**그리디가 위험한 까닭이 여기에 있습니다.** 그리디는 틀린 답을 낼 때도 오류를 내지 않고 예제 입력에서도 맞는 답을 냅니다. 실제로 쓰는 동전 체계가 대부분 그리디가 맞도록 설계돼 있어서 이 위험은 더 커집니다.

그래서 판단 기준을 미리 정해 두는 편이 낫습니다. **"이 선택이 왜 손해가 아닌가"를 한 문장으로 설명할 수 있으면 그리디를 쓰고 설명하지 못하면 DP 를 씁니다.** 8절의 회의실은 가장 일찍 끝나는 회의를 잡으면 뒤에 남는 시간이 가장 많다는 한 문장으로 설명이 됐습니다. 거스름돈은 큰 동전을 먼저 쓰는 선택이 왜 손해가 아닌지 설명할 수 없으며 실제로 6원에서는 동전이 하나 더 들었습니다.

시험장에서 그리디가 맞는지 확신이 서지 않으면 **작은 반례를 손으로 찾아보는 방법**이 가장 빠릅니다. 반례는 그 방법이 틀린 답을 내는 입력입니다. 4, 3, 1 로 6원을 만들 때 4 를 쓰면 어중간한 2원이 남듯이, 큰 동전을 쓰면 어중간한 나머지가 남는 조합을 만들어 보면 됩니다.

## 10. 세 도구를 고르는 기준

**세 도구는 "모든 경우를 다 볼 수 없다"는 같은 출발점에서 세 갈래로 나뉩니다.**

먼저 작은 문제의 답이 **겹치는지** 봅니다. 피보나치 20 이 `f(1)` 을 6,765번 부른 것처럼 같은 계산을 되풀이하고 있다면 동적 계획법을 씁니다. 지문에 "최대, 최소 몇 개", "몇 가지 방법", "최소 비용" 같은 말이 있고 선택이 단계별로 이어진다면 대체로 이 경우에 듭니다. 이 글의 배낭 문제와 거스름돈 문제도 `표[i-1][w-무게]` 와 `표[금-c]` 처럼 이미 구한 작은 문제의 답을 표에서 꺼내 쓰며 풀었습니다.

겹치는 계산이 없고 **모든 조합을 실제로 만들어 봐야 한다면** 백트래킹을 씁니다. 지문의 "가능한 모든 순서", "조건을 만족하는 배치" 같은 말이 그 신호입니다. 4 × 4 판의 퀸 문제가 이 경우로, 답 `[1, 3, 0, 2]` 는 퀸을 놓은 배치 그 자체입니다. 이때는 가지치기를 얼마나 일찍 하느냐가 시간 안에 통과하느냐를 정합니다.

**한 번의 선택이 뒤의 선택을 망치지 않는다고 설명할 수 있으면** 그리디를 씁니다. 8절의 회의실은 설명이 되는 경우이고 9절의 동전 4, 3, 1 은 설명이 되지 않는 경우입니다. 설명이 되지 않으면 그리디를 쓰지 않습니다. 그리디는 가장 빠르지만 9절처럼 오류 없이 틀릴 수 있어 가장 위험합니다.

입력 크기 n 으로도 쓸 도구가 나뉩니다. 모든 경우를 하나씩 다 해 보는 방법을 **완전탐색**이라 하는데, n 이 20 언저리면 2ⁿ(2 를 n 번 곱한 수)이 백만 정도라 완전탐색으로도 통과합니다. n 이 수천이면 O(n²) 인 DP 까지 쓸 수 있습니다. n 이 십만이면 시간이 n 에 비례하는 O(n) 이나 n 에 log n 을 곱한 만큼 늘어나는 O(n log n) 인 방법이어야 합니다. **문제를 받으면 먼저 지문에 적힌 n 이 어느 방법까지 허용하는지 계산합니다.**

## 한눈 정리

| 상황 | 쓸 것 | 왜 |
|---|---|---|
| 같은 계산이 반복된다 | 적어 두기 | 한 줄로 269만 번이 59번 |
| n이 크고 어차피 다 필요하다 | 아래에서 쌓기 | 재귀 깊이 걱정이 없다 |
| 필요한 부분이 일부뿐이다 | 적어 두기 | 안 쓰는 칸은 안 채운다 |
| 무엇을 골랐는지도 필요하다 | 표를 되짚는다 | 값이 달라진 칸이 고른 자리 |
| 모든 조합을 만들어야 한다 | 백트래킹 | 넣고 부르고 되돌린다 |
| 백트래킹이 느리다 | 가지치기를 위로 올린다 | 위에서 자를수록 많이 지워진다 |
| 선택이 뒤를 안 망친다고 설명된다 | 그리디 | 가장 빠르다 |
| 설명이 안 된다 | DP | 그리디는 조용히 틀린다 |
| n이 20 언저리 | 완전탐색 | 2ⁿ 이 백만 정도 |

## 헷갈리기 쉬운 점

- **표의 칸 하나가 무엇을 뜻하는지 한 문장으로 적을 수 없다면 아직 문제를 풀지 못한 상태입니다.** 코드부터 짜기 시작하면 거의 언제나 중간에 막힙니다.
- **시작값을 잘못 두면 답이 모두 틀립니다.** 최솟값 문제에서는 `표[0]` 을 0 이 아닌 무한으로 두는 실수와, 무한으로 채워야 할 나머지 칸을 0으로 두는 실수가 흔합니다.
- **백트래킹에서 `pop()` 을 빼먹으면 앞 갈래에서 넣은 값이 옆 갈래까지 남습니다.** 넣는 `append` 와 되돌리는 `pop` 은 언제나 짝으로 씁니다.
- **가지치기를 늦게 하면 하지 않은 것과 다름없습니다.** 퀸을 다 놓은 뒤에 확인하면 256번, 한 줄 놓을 때마다 확인하면 17번입니다.
- **그리디는 예제에서 맞는 답을 내도 틀린 방법일 수 있습니다.** 동전 4, 3, 1 로 6원을 만드는 경우가 그 예입니다. 오류가 나지 않으니 더 위험합니다.
- **`@lru_cache` 는 인자가 바뀔 수 있는 값이면 쓸 수 없습니다.** 리스트를 인자로 넘기면 오류가 나므로 튜플로 바꿔서 넘깁니다.
- **적어 두기도 재귀라서 깊이에 한계가 있습니다.** n 이 아주 크면 아래에서 쌓기로 바꿔 씁니다.
