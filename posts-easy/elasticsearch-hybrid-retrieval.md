지훈 씨가 모델 팀에 온 지 12주째입니다. 이번에 맡은 일은 검색 광고의 후보로, 사용자가 검색어를 넣으면 광고 상품 가운데 후보를 먼저 뽑아 두고 클릭 확률 모델은 그 후보에만 돌립니다. 그런데 「헤드셋」을 검색하면 헤드폰 상품이 후보에 하나도 없었는데, 헤드폰 상품 이름에 「헤드셋」이라는 글자가 없었기 때문입니다.

선배는 글자로 찾는 목록 옆에 뜻으로 찾는 목록을 하나 더 두고 두 목록을 합쳐 보라고 했습니다. 지훈 씨는 노트북 한 대에 검색 서버 두 대를 띄우고 상품 3만 건을 넣은 다음, 질의(검색 서버에 찾아 달라고 보내는 말로, 여기서는 사용자의 검색어) 3개를 보내 돌아온 응답을 기록했습니다.

**글자로 찾은 목록과 뜻으로 찾은 목록은 점수의 단위가 다른데, 어떻게 하나로 합칠까요?**

상품 이름에 질의와 같은 글자가 있는지로 찾는 방법을 BM25 라고 부릅니다. 질의와 상품 이름을 벡터(숫자를 정해 둔 순서로 늘어놓은 목록)로 바꿔 뜻이 가까운 상품을 찾는 방법은 kNN 벡터 검색이라고 부르는데, kNN 은 k-nearest neighbors 의 줄임말로 가장 가까운 k 개를 찾는다는 뜻입니다. 두 방법이 낸 목록을 점수 대신 순위로 합치는 방법은 RRF 입니다. BM25 와 kNN 과 RRF 를 함께 쓰는 검색을 하이브리드 검색이라고 합니다. 클릭 확률 모델은 후보에만 돌기 때문에 후보에 오르지 못한 상품은 모델이 아무리 좋아도 광고가 나가지 않고 그 매출은 후보마다 점수를 내는 랭킹 모델이 되찾지 못합니다.

> **한 줄 요약:** 글자로 찾는 BM25 는 질의와 같은 글자가 이름에 든 상품을, 뜻으로 찾는 kNN 은 뜻이 가까운 상품을 100개씩 찾습니다. 「헤드셋」은 그 글자가 든 상품 이름이 없어 BM25 가 0건이었고 kNN 은 헤드폰 100개를 찾았습니다. 두 목록은 점수의 단위가 달라서 RRF 는 점수를 버리고 순위만 보는데, 상품마다 목록별로 1 ÷ (60 + 순위) 를 구해 더한 값으로 두 목록을 하나로 합칩니다. 클릭률이나 입찰가처럼 날마다 바뀌는 피처(모델에 넣는 값)는 새 인덱스(검색 서버가 상품 문서를 담는 단위)를 만든 다음 별칭(검색이 읽는 이름)을 새 인덱스로 옮겨 바꿉니다. 새 인덱스를 만드는 시간을 빼고 별칭을 옮기는 교체 요청 자체는 22ms 에 끝났습니다.

> **골라 읽는 법** — 절이 8개입니다. 절마다 표나 코드나 기록 재생 그림(측정할 때 기록한 응답을 다시 그린 그림)이 있어서 그 부분만 보고 넘어가도 됩니다.
>
> - 질의 하나가 후보가 되기까지 지나는 5단계와 단계별 시간 → 1절
> - 글자로 찾는 BM25 와 상품 이름을 낱말 조각으로 자르는 분석기 → 2절
> - 뜻으로 찾는 kNN 과 문장을 벡터로 바꾸는 임베딩 → 3절
> - 두 목록을 순위로 합치는 RRF 의 계산과 파이썬 코드 → 4절
> - 광고가 꺼진 상품을 거르는 자리와 랭킹 모델로 보낼 후보 수 → 5절
> - 인덱스를 나눈 조각인 샤드와 그 복사본 replica → 6절
> - 날마다 새 인덱스를 만들어 바꾸는 법과 그동안의 검색 지연 → 7절
> - 한 회사가 검색창까지 가진 담장 안과 여러 회사가 경매로 광고를 사고파는 열린 RTB → 8절

이 글의 숫자는 지어낸 값이 아니라, 노트북 한 대에 Elasticsearch 9.5 노드 2개와 검색 API 를 띄우고 직접 측정한 값입니다. Elasticsearch 는 문서를 넣어 두고 질의로 찾아 주는 검색 엔진이고 노드는 그 서버 하나를 가리키는 말이라, 지훈 씨가 띄운 검색 서버 두 대가 이 노드 2개입니다. 검색 API 는 질의를 받아 Elasticsearch 에 묻는 서버로, 하는 일은 1절에서 봅니다. 상품 3만 건의 이름은 브랜드, 속성, 품목을 이어 만든 가짜이고 질의 벡터는 공개 모델 multilingual-e5-small 로 만들었습니다. 운영 서버라면 ms 로 적힌 시간의 크기는 다르지만 어느 단계가 시간을 많이 쓰는지는 같습니다. 글 속의 그림 3개는 측정할 때 기록한 응답을 그대로 다시 그립니다.

## 1. 질의 하나가 후보가 되기까지 지나는 5단계

**「캠핑 의자」를 한 번 검색하면 BM25 가 찾은 100개와 kNN 이 찾은 100개를 합치면서 두 목록에 다 있는 상품을 한 번만 세어 121개가 되는데, 여기서 광고가 꺼진 상품을 뺀 108개가 랭킹 모델로 갑니다. 이 5단계를 지나는 데 검색 API 안에서 27ms 가 걸렸습니다.**

하이브리드 검색에서는 검색 API 가 질의 하나를 받을 때마다 Elasticsearch 에 두 번 묻기 때문에, 질의가 후보가 되기까지 어떤 단계를 지나고 단계마다 시간이 얼마나 드는지부터 봅니다.

검색 API 는 질의를 받으면 Elasticsearch 에 한 번은 글자로(BM25), 한 번은 벡터로(kNN) 묻습니다. 두 번 묻는 사이에는 질의를 벡터로 바꾸는 계산이 있고 두 답을 받은 뒤에는 두 목록을 합치는 계산과 꺼진 상품을 거르는 계산이 있어서 아래 표처럼 모두 5단계가 됩니다. 표에 나오는 384차원 벡터는 숫자 384개로 된 벡터를 말합니다. 토큰은 상품 이름과 질의를 자른 낱말 조각이고 역색인은 토큰마다 그 토큰이 든 상품을 적어 둔 표인데, 둘 다 2절에서 자세히 봅니다.

| 단계 | 하는 일 | 건수 | 걸린 시간 |
|---|---|---|---|
| 1. BM25 | 질의의 토큰을 역색인에서 찾아 점수 순 100개 | 맞은 문서 1,885건 → 100건 | 6.9ms (Elasticsearch 안 4.5ms) |
| 2. 질의 벡터 | 질의를 384차원 벡터로 바꾼다 | 1건 | 5.7ms |
| 3. kNN | 벡터가 가까운 상품 100개 | 100건 | 13.6ms (Elasticsearch 안 10.0ms) |
| 4. RRF | 두 목록을 순위로 합친다 | 200건 → 121건 | 0.26ms |
| 5. 거르기 | 꺼진 상품을 뺀다 | 121건 → 108건 | 0.02ms |

표의 시간은 같은 질의를 10번 보내 얻은 시간 10개의 가운데 값(중앙값)입니다. 괄호 안의 값은 Elasticsearch 가 응답에 적어 주는 took 값으로 검색 서버 안에서 검색에 쓴 시간이고 검색 API 에서 측정한 시간과 이 값의 차이는 HTTP 로 요청과 응답을 주고받는 왕복과 응답 JSON(키와 값을 적는 텍스트 형식)을 푸는 데 쓴 시간입니다. 1번 BM25 라면 검색 API 가 측정한 6.9ms 가운데 4.5ms 를 검색 서버 안에서 썼고 나머지는 왕복과 JSON 을 푸는 데 썼습니다. 5단계 가운데 kNN 이 13.6ms 로 가장 오래 걸렸습니다. 반면 4번 RRF 의 0.26ms 와 5번 거르기의 0.02ms 는 둘 다 1ms 도 되지 않습니다.

이 실습 환경은 두 질의를 하나씩 차례로 보내므로 두 왕복의 시간이 더해집니다. 두 질의를 동시에 보내면 1번 BM25 가 2번 질의 벡터 계산, 3번 kNN 과 같은 시간에 도는데, 1번의 6.9ms 가 2번의 5.7ms 와 3번의 13.6ms 를 더한 시간보다 짧아서 kNN 쪽의 시간만 남습니다.

## 2. 질의의 토큰이 상품 이름에 있어야 찾는 BM25 와 분석기

**Elasticsearch 는 상품 이름을 토큰(검색에 쓰는 낱말 조각)으로 잘라 토큰마다 그 토큰이 든 상품을 적어 둔 역색인에 넣어 두므로, BM25 는 질의의 토큰이 이름에 든 상품만 찾습니다. 「헤드셋」이라는 토큰은 역색인 어디에도 없어서 BM25 의 결과가 0건이었습니다.**

지훈 씨가 「헤드셋」으로 헤드폰을 하나도 찾지 못한 까닭을 알려면, Elasticsearch 가 상품 이름과 질의를 어떤 단위로 잘라 맞춰 보는지부터 봐야 합니다.

상품 이름이나 질의 같은 문장을 토큰으로 자르는 프로그램이 분석기입니다. 한국어 상품 이름은 같은 말도 「캠핑의자」처럼 붙여 쓰거나 「캠핑 의자」처럼 띄어 써서 띄어쓰기가 일정하지 않으므로, 이 실습은 낱말을 형태소(뜻을 가진 가장 작은 말의 단위)로 쪼개는 형태소 분석기 nori 를 씁니다. 색인(상품을 검색할 수 있게 인덱스에 넣는 일)할 때 「캠핑의자」가 「캠핑」과 「의자」 두 토큰으로 나뉘어 들어가므로, 질의를 「캠핑 의자」로 띄어 쓰든 「캠핑의자」로 붙여 쓰든 같은 상품을 찾습니다.

아래는 이 실습 환경의 분석기에 상품 이름 하나와 질의 3개를 직접 넣어, 색인할 때와 검색할 때 각각 어떤 토큰이 나오는지 본 결과입니다.

```text
색인할 때 (분석기 ko)
  "베이직 접이식 그레이 캠핑의자"  →  베이직 | 접이식 | 그레이 | 캠핑 | 의자

검색할 때 (분석기 ko_search, 동의어 사전을 씀)
  "캠핑 의자"  →  캠핑 | 의자, 체어   (의자와 체어는 같은 자리)
  "스니커즈"   →  스니커즈, 운동화     (같은 자리)
  "헤드셋"     →  헤드셋
```

색인할 때 쓰는 분석기 ko 는 「베이직 접이식 그레이 캠핑의자」를 베이직, 접이식, 그레이, 캠핑, 의자로 잘랐습니다. 검색할 때 쓰는 분석기 ko_search 는 동의어 사전(같은 뜻의 낱말을 짝지어 적어 둔 목록)까지 써서 「의자」 자리에 「체어」를, 「스니커즈」 자리에 「운동화」를 함께 놓았습니다. 결과에 적힌 같은 자리는 두 토큰을 질의 안의 같은 위치에 놓았다는 뜻으로, 상품 이름에 두 토큰 가운데 어느 쪽이 있어도 그 자리의 토큰이 맞은 것으로 칩니다. 사전에 없는 「헤드셋」은 토큰 「헤드셋」 하나로 그대로 남았습니다.

역색인은 토큰마다 그 토큰이 든 문서의 목록을 적어 둔 표라서, 「의자」 토큰 아래에는 이름에 의자가 든 상품의 번호가 늘어서 있습니다. 문서는 Elasticsearch 에 넣어 둔 한 건을 말하고 이 글에서는 상품 하나가 문서 하나입니다. 검색할 때는 질의 토큰마다 이 목록을 꺼내 합치는데 기본 설정은 토큰 하나만 맞아도 맞은 문서로 치므로, 「캠핑 의자」는 이름에 캠핑이나 의자가 든 상품 1,885건이 모두 맞은 문서가 되었습니다.

맞은 문서마다 매기는 점수가 BM25 점수인데, 점수가 높은 문서일수록 질의와 잘 맞는다고 봅니다. BM25 점수는 질의 토큰이 이름에 많이 들수록, 그 토큰이 든 상품이 적은 드문 토큰일수록, 이름이 짧을수록 높아집니다. 그래서 「의자」보다 「캠핑」이 드문 토큰이라면 「캠핑」이 든 상품이 「의자」만 든 상품보다 앞섭니다. 「캠핑 의자」의 1위는 「캠핑」과 「의자」가 모두 든 「온 슬림 캠핑의자」였고 BM25 점수는 9.92 였습니다. BM25 는 이 점수가 높은 순서로 위 100건만 넘기므로, 1절 표의 1번 줄이 「맞은 문서 1,885건 → 100건」입니다.

「스니커즈」를 넣으면 검색용 분석기 ko_search 가 동의어 사전을 보고 「운동화」를 같은 자리에 함께 놓으므로 운동화 상품 37건이 맞았습니다. 동의어를 색인할 때 미리 풀어 넣으면 사전을 고칠 때마다 상품 3만 건을 다시 색인해야 하므로, 이 실습은 동의어를 검색할 때만 풉니다. 반면 「헤드셋」은 사전에 없는 말이라 질의가 토큰 「헤드셋」 하나로 남았는데, 역색인에는 「헤드셋」 토큰이 든 상품 이름이 하나도 없어서 BM25 가 0건을 돌려주었습니다.

「헤드셋」과 헤드폰을 짝지은 줄을 동의어 사전에 넣으면 BM25 도 「헤드셋」으로 헤드폰을 찾습니다. 그런데 사람들이 검색창에 쓰는 말을 사전에 다 적을 수는 없으므로, 사전이 따라가지 못하는 말은 다음 절의 kNN 이 메웁니다.

## 3. 질의와 상품을 벡터로 바꿔 가까운 것을 찾는 kNN

**kNN 은 상품 이름과 질의를 같은 임베딩 모델로 384차원 벡터로 바꾼 다음, 두 벡터의 방향이 얼마나 같은지를 나타내는 코사인 유사도가 높은 상품을 고릅니다. 「헤드셋」은 상품 이름에 그 글자가 없어도 헤드폰이 1위로 나왔습니다.**

사전에 없는 「헤드셋」은 글자로는 찾을 수 없으니, 선배가 말한 뜻으로 찾는 목록은 질의와 상품 이름을 숫자로 바꿔 서로 얼마나 가까운지를 계산합니다.

임베딩 모델은 문장을 받아 숫자 384개로 된 벡터를 내놓는 모델로, 뜻이 비슷한 문장일수록 벡터의 방향도 비슷하게 나오도록 학습되어 있습니다. 상품 3만 건은 색인할 때 이름과 카테고리를 이어 붙인 글을 한 번씩 벡터로 바꿔 넣어 두지만 질의는 검색할 때마다 벡터로 바꿉니다. 질의를 벡터로 바꾸는 계산이 1절 표의 2번 단계로, 「캠핑 의자」에서는 5.7ms 가 걸렸습니다.

코사인 유사도는 두 벡터의 방향이 얼마나 같은지를 나타내는 값으로, 방향이 같으면 1, 수직이면 0 이어서 클수록 두 문장의 뜻이 가깝습니다. Elasticsearch 는 코사인 유사도를 그대로 점수로 주지 않고 (1 + 코사인) ÷ 2 로 바꿔서 줍니다. 「헤드셋」의 1위 「아틀라이프(ATL) 와이드 헤드폰 AV505」는 점수가 0.911 이었는데, 코사인 0.822 에 1 을 더해 2 로 나누면 이 0.911 이 나옵니다.

질의 벡터를 상품 3만 건의 벡터와 하나씩 다 비교하면 느리므로, Elasticsearch 는 HNSW(Hierarchical Navigable Small World)라는 그래프를 써서 일부만 비교합니다. HNSW 는 벡터마다 가까운 벡터 몇 개를 선으로 이어 둔 그래프로, 검색은 그 선을 따라 질의 벡터에 더 가까운 벡터로 옮겨 가며 찾습니다. 이렇게 다 비교하지 않으니 진짜 가장 가까운 상품을 놓칠 수 있다는 뜻에서 이런 검색을 근사 검색이라고 부릅니다. 질의에 넣은 num_candidates 100 은 샤드(인덱스를 나눈 조각으로, 6절에서 자세히 봅니다)마다 후보를 100개까지 살펴보라는 설정입니다.

아래 표는 질의 3개마다 BM25 가 맞춘 수, 두 방법의 1위, 두 목록의 위 100개끼리 겹친 수를 나란히 놓았습니다.

| 질의 | BM25 가 맞춘 수 | BM25 1위 | kNN 1위 | 위 100개끼리 겹친 수 |
|---|---|---|---|---|
| 캠핑 의자 | 1,885 | 온 슬림 캠핑의자 | 하이라이프 와이드 브라운 캠핑의자 ML172 | 79 |
| 헤드셋 | 0 | 없음 | 아틀라이프(ATL) 와이드 헤드폰 AV505 | 0 |
| 스니커즈 | 37 | 별랩 와이드 운동화 | 윤라이프 방수 카키 선글라스 | 0 |

표에서 「헤드셋」은 BM25 가 0건이었는데도 kNN 1위가 헤드폰이었습니다. 「스니커즈」에서는 반대로 kNN 이 틀렸습니다. 이 실습에서 쓴 작은 모델은 스니커즈와 운동화를 가깝게 보지 못해 kNN 1위가 「윤라이프 방수 카키 선글라스」였고 위 100개에 운동화가 하나도 없었습니다. kNN 은 가까운 순서로 늘 100개를 채워 돌려주므로 0건은 나오지 않는데, 그 100개가 질의와 맞지 않는 상품일 수 있습니다.

BM25 는 글자가 맞으면 틀리지 않고 사전에 있는 말은 동의어 사전이 이어 주는데 kNN 은 사전에 없는 말을 메우므로, 하이브리드 검색은 두 방법을 같이 씁니다. 질의와 상품을 각각 벡터로 바꿔 벡터끼리 비교하는 이 구조는 [Two-Tower](post.html?id=two-tower-training) 편의 두 타워(두 쪽 입력을 따로 벡터로 바꾸는 신경망 2개)와 같은 갈래입니다. 이제 단위가 다른 BM25 점수와 kNN 점수로 상품을 어떻게 한 줄로 정렬할지가 남았습니다.

## 4. 점수 대신 순위를 더하는 RRF

**RRF 는 상품마다 BM25 목록과 kNN 목록에서 각각 1 ÷ (60 + 순위) 를 구해 더한 값으로 순위를 매기므로, 두 목록에 다 있는 상품이 한 목록의 1위보다 앞설 수 있습니다.**

BM25 점수와 kNN 점수는 크기가 달라서 그대로 더할 수 없습니다. 「캠핑 의자」의 BM25 점수는 1위가 9.92 인데 kNN 점수는 1위부터 10위까지가 모두 0.94 언저리라, 두 점수를 그대로 더하면 BM25 점수가 순서를 다 정하고 kNN 점수는 합계를 소수점 아래에서만 움직입니다. 두 점수를 모두 0 에서 1 사이로 맞춘 다음 더하는 방법도 있는데, 질의마다 점수의 범위가 달라서 어느 값을 0 과 1 로 맞출지 그 기준이 질의마다 흔들립니다.

RRF(Reciprocal Rank Fusion, 순위의 역수를 합치는 방법)는 두 점수를 버리고 각 목록에서의 순위만 씁니다. 상품마다 목록별로 「1 ÷ (k + 순위)」를 구해 더하는데, 어느 목록에 없는 상품은 그 목록의 몫으로 0 을 더합니다. RRF 의 k 는 순위에 더하는 상수로, 2009년에 이 방법을 처음 낸 논문이 쓴 값인 60 을 많이 씁니다. k 를 키울수록 분모에서 순위가 차지하는 몫이 작아져 1위와 10위가 받는 값의 차이가 줄어듭니다.

아래 코드는 「캠핑 의자」를 검색했을 때 기록한 BM25 순위와 kNN 순위를 그대로 넣어, 네 상품의 RRF 점수와 그 점수로 정렬한 순서를 봅니다.

```python
# 하는 일: 「캠핑 의자」에서 기록한 BM25 순위와 kNN 순위로 네 상품의 RRF 점수를 세어 순위를 매긴다.
# 1단계: 두 목록에서의 순위를 둔다
# 기록한 위 100개 목록의 순위다. 앞이 BM25, 뒤가 kNN 이다.
ranks = {
    '심플 슬림 캠핑의자': (3, 10),
    '베이직 접이식 그레이 캠핑의자': (9, 4),
    '온 슬림 캠핑의자': (1, 61),
    '온팩토리 와이드 그레이 캠핑의자 XR289': (60, 2),
}

# 2단계: 목록마다 1 / (60 + 순위) 를 더한다
K = 60
def rrf(pair):
    return sum(1 / (K + r) for r in pair)

# 3단계: 점수 순으로 찍는다
for name, (b, k) in sorted(ranks.items(), key=lambda kv: -rrf(kv[1])):
    print(f'{rrf((b, k)):.4f}  BM25 {b:>2}위  kNN {k:>2}위  {name}')

# 출력:
# 3단계 뜻: BM25 1위가 3위로 밀리고, 두 목록에서 모두 10위 안인 상품이 앞선다.
# 0.0302  BM25  3위  kNN 10위  심플 슬림 캠핑의자
# 0.0301  BM25  9위  kNN  4위  베이직 접이식 그레이 캠핑의자
# 0.0247  BM25  1위  kNN 61위  온 슬림 캠핑의자
# 0.0245  BM25 60위  kNN  2위  온팩토리 와이드 그레이 캠핑의자 XR289
```

찍힌 순서에서 BM25 1위였던 「온 슬림 캠핑의자」는 네 상품 가운데 3위로 밀렸습니다. 대신 BM25 3위와 kNN 10위인 「심플 슬림 캠핑의자」가 0.0302 로 1위, BM25 9위와 kNN 4위인 「베이직 접이식 그레이 캠핑의자」가 0.0301 로 2위입니다. RRF 점수는 클수록 앞에 놓이는데, 「심플 슬림 캠핑의자」의 0.0302 는 BM25 3위에서 받은 1 ÷ (60 + 3) 과 kNN 10위에서 받은 1 ÷ (60 + 10) 을 더한 값입니다. 「온 슬림 캠핑의자」는 BM25 1위라 1 ÷ (60 + 1) 을 받았지만 kNN 에서는 61위라 1 ÷ (60 + 61) 밖에 받지 못해 0.0247 에 그쳤습니다. 이 네 점수는 그림 1 의 셋째 목록, RRF 로 합친 목록에 찍힌 값과 같습니다.

RRF 는 두 목록이 모두 좋다고 한 상품에 높은 점수를 줍니다. 한 목록에만 있는 상품은 그 목록에서 1위여도 1 ÷ 61, 곧 0.0164 를 받는 데 그치는데, 두 목록에서 모두 10위 안에 든 상품은 「심플 슬림 캠핑의자」의 0.0302 처럼 그보다 두 배 가까이 받습니다.

순위만 보는 같은 성질이 한계도 만듭니다. 「스니커즈」는 두 목록이 하나도 겹치지 않아서 kNN 1위 선글라스와 BM25 1위 운동화가 둘 다 한 목록에서만 1위라 똑같이 0.0164 를 받았는데, RRF 는 순위만 보므로 kNN 이 선글라스를 얼마나 자신 없이 골랐는지는 알지 못합니다. 이 실습 환경은 점수가 같으면 문서 번호 순으로 정렬해서 「스니커즈」의 1위는 선글라스가 되었습니다.

Elasticsearch 에도 RRF 가 들어 있지만 유료 라이선스에서만 쓸 수 있는 기능이라, 무료 라이선스(basic)로 띄운 이 실습 환경에서 RRF 질의를 보내자 「license is non-compliant」라는 메시지와 함께 HTTP 403(요청 거부) 오류가 돌아왔습니다. 그래서 BM25 질의와 kNN 질의를 따로 보내고 검색 API 에서 위 코드처럼 합쳤습니다. 합친 목록에는 아직 광고가 꺼진 상품이 섞여 있습니다.

## 5. 서빙 때 거르는 꺼진 상품과 100개 안팎의 후보

**광고가 꺼진 상품을 RRF 로 합친 다음에 빼고 나니, 질의 3개 모두 100개 안팎의 후보가 남아 랭킹 모델로 갔습니다.**

광고주가 상품 광고를 켜고 끄는 일은 정해진 때 없이 아무 때나 일어납니다. 꺼진 상품도 인덱스에서 지우지 않고 문서의 status 필드(문서 안에서 상품의 상태를 담는 칸)에 켜짐인지 꺼짐인지 같은 상태를 적어 두었다가 검색할 때 그 필드를 보고 거르는데, 이렇게 하면 거르는 기준을 바꾸어도 인덱스를 다시 만들 일이 없습니다. 이 실습은 서빙(검색 요청이 올 때마다 후보를 만들어 내는 단계) 중에 RRF 로 합친 목록에서 꺼진 상품을 뺐습니다.

아래 표는 질의마다 두 목록의 크기와 합친 수, 꺼져서 뺀 수, 남은 후보 수를 보여 줍니다.

| 질의 | BM25 | kNN | 합친 수 | 꺼져서 뺀 수 | 남은 후보 |
|---|---|---|---|---|---|
| 캠핑 의자 | 100 | 100 | 121 | 13 | 108 |
| 헤드셋 | 0 | 100 | 100 | 8 | 92 |
| 스니커즈 | 37 | 100 | 137 | 9 | 128 |

「캠핑 의자」는 합친 121개 가운데 13개가 꺼져 있어 108개가 남았고 「스니커즈」는 137개에서 9개를 빼 128개가 남았습니다. 「헤드셋」은 BM25 가 0건이라 kNN 의 100개가 그대로 합친 목록이 되었는데, 여기서 8개를 빼 92개가 남았습니다.

꺼진 상품은 두 곳에서 거를 수 있습니다. 이 실습처럼 RRF 로 합친 뒤에 거르면 Elasticsearch 에 보내는 질의는 단순한 대신 꺼진 상품이 BM25 와 kNN 의 100개 안에 자리를 차지했다가 나중에 빠지므로 남는 후보가 그만큼 줄어듭니다. 「헤드셋」도 kNN 의 100개 가운데 꺼진 8개가 빠져 92개로 줄었습니다. 반대로 Elasticsearch 질의 안에 켜진 상품만 받는 조건을 넣으면 처음부터 켜진 상품 가운데 100개를 받는 대신, kNN 은 HNSW 그래프를 따라가며 조건에 맞는 상품만 세어야 해서 조건에 걸러지는 상품의 비율이 높을수록 느려집니다.

후보를 몇 개까지 랭킹 모델로 보낼지는 랭킹 모델에 주어진 시간이 정합니다. 랭킹 모델은 후보마다 피처를 모아 점수를 내므로 후보가 두 배면 그 일도 두 배가 되는데, [추론 서버](post.html?id=inference-server) 편의 모델 서버는 후보 800건을 한 텐서(여러 후보의 입력을 한 번에 담은 다차원 배열)로 넣어 3.0ms 에 점수를 냈습니다. 그 시간 예산이면 800건보다 훨씬 적은 100개 안팎은 넉넉하므로, BM25 와 kNN 이 가져오는 수를 늘릴 여유도 그만큼 있습니다.

다만 후보를 늘려 이득을 보는지는 늘린 만큼 지금까지 빠지던 상품이 새로 들어오는지로 판단합니다. 「스니커즈」는 kNN 의 위 100개에 운동화가 하나도 없었으니 이 질의에서 kNN 을 200개로 늘려도 얻을 것이 적습니다. 다음 절에서는 이 질의들이 Elasticsearch 안에서 어느 노드의 어느 샤드를 돌았는지 봅니다.

## 6. 샤드 2개로 나뉜 인덱스와 샤드마다 도는 질의

**상품 3만 건이 든 인덱스는 샤드 0 과 샤드 1 로 나뉘어 두 노드에 놓였는데, 샤드마다 원본인 primary 와 복사본인 replica 를 서로 다른 노드에 하나씩 두었습니다.**

1절에서 측정한 질의 시간과 노드 하나가 꺼졌을 때 검색이 이어지는지는 인덱스가 노드에 어떻게 나뉘어 놓였는지에 달려 있습니다.

인덱스는 Elasticsearch 가 문서를 담아 두는 단위로, 하나의 인덱스를 몇 개로 나눈 조각 하나하나를 샤드라고 부릅니다. Elasticsearch 는 문서마다 id 를 해시(정해 둔 규칙으로 값을 숫자로 바꾸는 계산)해서 어느 샤드에 넣을지 정하므로 문서가 거의 반반으로 나뉘어, 이 실습 환경의 인덱스는 샤드 0 에 15,042건, 샤드 1 에 14,958건을 담았습니다. 두 수를 더하면 상품 3만 건입니다.

질의를 받은 노드는 같은 질의를 샤드 0 과 샤드 1 에 보내 샤드마다 한 번씩 돌게 한 다음, 샤드마다 자기 문서 가운데 위 100개를 돌려받아 하나로 합칩니다. 그래서 질의 하나의 시간은 가장 늦게 답하는 샤드가 정합니다. 샤드를 늘리면 한 샤드가 살펴볼 문서는 줄지만 질의를 받은 노드가 질의를 보낼 곳과 합칠 목록은 늘어납니다.

그림 2 에서는 샤드 0 과 샤드 1 의 primary 와 replica 가 두 노드에 어떻게 나뉘어 놓였는지 보면 됩니다.

replica 는 primary 와 같은 문서를 다른 노드에 둔 샤드의 복사본이라, 노드 하나가 꺼져도 남은 노드에 샤드 0 과 샤드 1 이 모두 있어 검색이 이어집니다. 검색 같은 읽기 요청은 primary 와 replica 가운데 아무 쪽이나 받으므로 replica 를 늘리면 초당 받을 수 있는 질의도 늘어납니다. 반면 문서를 넣는 쓰기 요청은 primary 가 먼저 받은 뒤 replica 로 복사하므로, replica 가 늘면 쓰기 일도 함께 늘어납니다.

인덱스를 만들 때 정한 샤드 수는 그 인덱스에서는 바꿀 수 없습니다. 샤드를 늘리는 split 이나 줄이는 shrink 도 실제로는 새 인덱스를 만들어 문서를 옮기는 일입니다. 다음 절에서 볼 「새 인덱스로 교체」가 바로 그 일을 날마다 하는 방법이라, 이 방법을 쓰면 샤드 수를 고칠 기회도 날마다 생깁니다.

## 7. 날마다 바뀌는 피처와 새 인덱스로 옮기는 별칭 교체

**초당 50건의 검색을 받는 채로 상품 피처를 두 방법으로 바꿔 보니, 검색이 읽고 있는 운영 인덱스에 바로 넣은 방법은 8.8초 동안 검색 응답 시간의 p99(가장 느린 1% 를 뺀 나머지 검색이 모두 그 안에 끝나는 시간)가 221ms 까지 올랐고 새 인덱스를 만들어 바꾼 방법은 160ms 까지 올랐습니다. 새 인덱스로 넘어가는 별칭 교체 요청 자체는 22ms 에 끝났습니다.**

날마다 새로 계산하는 피처를 인덱스에 반영하는 동안에도 검색은 멈추지 않고 들어오므로, 두 방법으로 바꿔 보며 그동안 검색이 얼마나 느려지는지 측정했습니다.

피처 가운데 상품의 클릭률이나 입찰가는 날마다 새로 계산하는 값인데, 검색하면서 바로 쓰려고 인덱스에도 넣어 둡니다. 이 값을 바꾸는 방법은 두 가지로, (가)는 지금 검색이 읽고 있는 인덱스에 바뀐 문서를 바로 다시 넣고 (나)는 그 옆에 새 인덱스를 처음부터 만든 다음 다 되면 검색이 읽는 이름을 새 인덱스로 옮깁니다.

(나)에서 검색이 읽는 이름이 별칭(alias)인데, 인덱스에 붙여 두는 또 하나의 이름입니다. 검색 API 는 인덱스 이름 대신 kw_read 라는 별칭으로 질의하므로, 별칭이 어느 인덱스를 가리키는지에 따라 검색이 읽는 인덱스가 정해집니다. 아래는 별칭 kw_read 를 옛 인덱스에서 새 인덱스로 옮기는 요청입니다.

```json
POST _aliases
{
  "actions": [
    { "remove": { "index": "kw_20261031_120731", "alias": "kw_read" } },
    { "add":    { "index": "kw_20261031_175642", "alias": "kw_read" } }
  ]
}
```

요청의 actions 에는 옛 인덱스 kw_20261031_120731 에서 별칭을 떼는 remove 와 새 인덱스 kw_20261031_175642 에 별칭을 붙이는 add 가 함께 들어 있습니다. remove 와 add 가 한 요청 안에서 같이 일어나므로 별칭이 어느 인덱스도 가리키지 않는 순간이 없어 검색이 비는 순간도 없습니다.

아래 표는 초당 50건의 검색을 보내는 채로 (가)와 (나)를 차례로 해 본 기록입니다. 넣은 문서는 (가)가 상품의 절반인 1만 5천 건, (나)가 3만 건 전부입니다. 걸린 시간은 색인 프로그램이 단계마다 직접 측정했습니다. p99 평균과 p99 최대는 그 단계 동안 1초마다 낸 검색 p99 의 평균과 최댓값인데, 단계의 경계를 1초마다 상태를 읽어 정했기 때문에 (나)의 만들기 줄 p99 에는 다음 단계인 bulk(문서 여러 건을 요청 하나로 넣는 Elasticsearch API)의 첫 1초가 섞여 있습니다.

| 단계 | 걸린 시간 | p99 평균 | p99 최대 |
|---|---|---|---|
| (가) 운영 인덱스에 바로 bulk | 8.8초 | 118.7ms | 220.6ms |
| (나) 새 인덱스를 replica 0, refresh 끔으로 만들기 | 164ms | 130.1ms | 160.2ms |
| (나) 3만 건을 bulk | 4.2초 | 89.5ms | 141.7ms |
| (나) replica 켜고 refresh, green 기다리기 | 6.4초 | 33.5ms | 63.3ms |
| (나) force merge 로 세그먼트를 1개로 | 1.7초 | 32.0ms | 55.8ms |
| (나) 별칭 교체 | 22ms | - | - |
| 교체 뒤 30초 | - | 8.5ms | - |

p99 는 작을수록 검색이 빠른데, 표에서 (가)는 8.8초 동안 p99 평균이 118.7ms, 최대가 220.6ms 였고 (나)는 p99 가 가장 높았던 만들기 줄에서도 최대 160.2ms 였습니다. 굵은 요약의 221ms 와 160ms 는 이 두 최댓값을 반올림한 값입니다. 교체가 끝난 뒤 30초 동안의 p99 평균은 8.5ms 로 내려왔습니다.

(가)는 검색이 읽고 있는 인덱스의 문서를 지우고 다시 넣는 일이라, 바뀐 문서를 1초마다 새 세그먼트(샤드 안에서 문서를 나눠 담는 파일 단위)로 만드는 색인 일이 검색과 같은 노드의 CPU 와 디스크를 나눠 쓰면서 p99 가 올랐습니다. 이 실습 환경은 같은 노드 2개가 새 인덱스 만들기와 검색을 함께 하므로 (나)에서도 p99 가 올랐습니다. 그래도 (나)는 (가)보다 두 배 많은 문서를 넣으면서 (나) 전체의 p99 평균이 63.1ms 로, (가)의 p99 평균 118.7ms 의 절반쯤이었습니다.

(나)가 두 배 많은 문서를 더 빨리 넣은 데에는 새 인덱스의 설정이 큰 몫을 했습니다. (가)는 1만 5천 건에 8.8초가 걸렸는데 (나)의 bulk 줄은 3만 건에 4.2초였습니다. 새 인덱스는 처음에 replica 를 0 으로, refresh 를 끈 상태로 만들어 문서를 채웠습니다. refresh 는 넣은 문서를 검색할 수 있게 세그먼트로 만드는 일로 기본으로 1초마다 도는데, 새 인덱스는 아무도 읽지 않으므로 다 넣은 뒤 한 번만 하면 됩니다. replica 는 6절에서 본 대로 있으면 쓰기마다 replica 로 복사하는 일이 붙으므로 다 넣은 다음에 켰는데, 이때 다른 노드로 샤드 전체를 복사합니다. 표의 「replica 켜고 refresh, green 기다리기」 줄 6.4초는 이 복사와 refresh 를 마치고 모든 primary 와 replica 샤드가 노드에 자리를 잡은 green 상태가 되기를 기다린 시간입니다.

별칭 교체 바로 앞 단계인 force merge 는 세그먼트를 1개로 합치는 일로, 3만 건을 넣은 새 인덱스에서 1.7초가 걸렸습니다. Elasticsearch 는 문서를 지울 때 바로 없애지 않고 지웠다는 표시만 남기는데, force merge 로 합치고 나면 질의가 살펴볼 세그먼트가 줄고 지운 표시만 남아 있던 문서도 이때 정리됩니다. 다만 쓰기가 계속되는 인덱스에 force merge 를 하면 Elasticsearch 가 세그먼트를 스스로 골라 합치는 자동 병합이 합쳐진 큰 세그먼트를 다시 고르지 않아 지운 문서가 그 안에 오래 남으므로, force merge 는 쓰기가 끝난 새 인덱스에만 합니다.

## 8. 담장 안과 열린 RTB 에서 질의가 오는 곳

**글자와 뜻으로 찾아 순위로 합치는 방법은 담장 안과 열린 RTB 가 같지만 질의가 무엇인지와 찾는 데 쓸 수 있는 시간은 다릅니다.**

담장 안(닫힌 생태계)은 한 회사가 검색창 같은 서비스와 광고 상품을 다 가진 곳을, 열린 RTB(Real-Time Bidding, 실시간 입찰)는 여러 회사가 광고가 보일 자리를 실시간 경매로 사고파는 곳을 말합니다. 이 두 곳이 광고가 거래되는 두 무대입니다.

### 사용자의 검색어가 질의인 담장 안 [무대: 닫힌 생태계]

검색 광고를 파는 플랫폼은 검색창과 광고 상품을 다 가지므로, 사용자가 친 검색어가 그대로 질의가 되고 상품 이름과 상태와 피처도 우리 데이터베이스에서 옵니다. 데이터가 모두 우리 손에 있어서 날마다 새 인덱스를 만들어 별칭을 옮기는 일정도 우리가 정합니다. 광고주가 상품을 켜고 끄는 일은 하루 중 아무 때나 일어나므로, 그 상태만 작은 인덱스에 따로 받아 바로 반영하는 방법을 날마다의 인덱스 교체와 같이 씁니다.

동의어 사전과 임베딩 모델을 고칠 재료도 우리 검색 로그에서 나옵니다. 예를 들어 「헤드셋」을 친 사용자가 헤드폰 광고를 눌렀다는 기록이 쌓이면, 동의어 사전에 「헤드셋」과 헤드폰을 잇는 한 줄을 넣거나 그 검색어와 상품의 쌍으로 임베딩 모델을 다시 학습합니다.

### 질의 대신 지면의 내용이 오는 열린 RTB [무대: 열린 RTB]

열린 RTB 에서 광고주를 대신해 입찰하는 DSP(Demand-Side Platform)는 입찰 요청을 받는데, 입찰 요청은 광고가 보일 자리 하나를 경매에 내놓으며 DSP 들에게 값을 물어 오는 요청입니다. 이 입찰 요청에는 사용자의 검색어가 거의 없는 대신 그 자리인 지면의 주소, 카테고리, 앱 이름 같은 맥락이 옵니다. 그래서 질의는 검색어가 아닌 「이 지면의 글」이 되고 찾는 대상은 우리 광고주의 소재(광고로 보여 줄 이미지와 문구)입니다. 지면 글과 소재 글을 BM25 와 벡터로 비교해 순위로 합치는 방법은 담장 안에서와 똑같이 씁니다.

찾는 데 쓸 수 있는 시간은 더 빠듯합니다. 입찰 응답 전체를 100ms 안팎에 돌려줘야 하고 그 100ms 안에 거래소(지면을 경매에 내놓고 DSP 들의 입찰을 받는 곳)와의 네트워크 왕복까지 들어 있으므로, 지면마다 찾은 결과를 캐시(한 번 구한 결과를 저장해 두고 다시 쓰는 방법)해 두고 처음 보는 지면에만 검색을 돌리는 식으로 씁니다.

## 한눈 정리

| 단계 | 하는 일 | 이 실습에서 측정한 값 | 결정할 것 |
|---|---|---|---|
| 분석기 | 이름과 질의를 토큰으로 자른다 | 「헤드셋」은 토큰이 없어 0건 | 동의어를 검색 때 풀지 색인 때 풀지 |
| BM25 | 토큰이 맞는 문서를 점수 순으로 | 6.9ms 에 100건 | 가져올 수 |
| kNN | 벡터가 가까운 문서를 근사로 | 13.6ms 에 100건, 스니커즈 1위는 선글라스 | 모델, num_candidates |
| RRF | 순위로 1 ÷ (60 + 순위) 를 더한다 | 0.26ms, 200건이 121건으로 | k 값, 거르는 자리 |
| 샤드 | 인덱스를 나눠 노드에 둔다 | 샤드 둘, replica 하나, 노드 둘 | 샤드 수는 새 인덱스를 만들 때 |
| 교체 | 새 인덱스를 만들어 별칭을 옮긴다 | 교체 22ms, 바로 넣을 때 p99 최대 221ms | 옛 인덱스를 몇 개 남길지 |

## 헷갈리기 쉬운 점

- **BM25 0건은 장애가 아닙니다.** 질의의 토큰이 어느 상품 이름에도 없으면 0건이 정상이므로, 0건이 나오면 먼저 분석기에 질의와 상품 이름을 넣어 두 쪽의 토큰을 나란히 놓고 비교합니다.
- **kNN 은 늘 k 개를 돌려줍니다.** 이 글의 kNN 은 가까운 순서로 100개를 채워 돌려주므로 0건이 나오지 않는데, 0건이 없다고 해서 돌려준 상품이 질의와 맞는다는 뜻은 아닙니다. 「스니커즈」의 kNN 100개에는 운동화가 하나도 없었습니다.
- **RRF 점수는 확률이 아닙니다.** 「심플 슬림 캠핑의자」의 0.0302 는 그 질의 안에서 순위를 매기는 값일 뿐이라 다른 질의의 RRF 점수와 비교할 수 없습니다. 클릭 확률처럼 크기에 뜻이 있는 점수가 필요하면 그 점수는 랭킹 모델이 냅니다.
- **형태소 분석기는 사전에 없는 낱말을 엉뚱하게 자릅니다.** 이 글의 가짜 브랜드 「아틀라이프」는 「틀」과 「라이프」로 잘렸습니다. 이렇게 잘리지 않도록 브랜드 이름은 분석기의 사용자 사전(한 낱말로 보도록 직접 적어 두는 목록)에 넣어 둡니다.
- **force merge 는 운영 인덱스에 하지 않습니다.** 쓰기가 계속되는 인덱스에 하면 합친 큰 세그먼트를 자동 병합이 다시 고르지 않아 그 안에 지운 문서가 오래 남으므로, 쓰기가 끝난 인덱스에만 합니다.
- **별칭 교체가 빠르다고 새 인덱스를 만드는 일까지 빠르지는 않습니다.** 별칭 교체 요청은 22ms 였지만 새 인덱스를 만드는 데는 13초 넘게 걸렸는데, 그동안 생기는 부하는 검색을 받는 노드가 함께 받습니다.

- kNN 질의의 num_candidates 와 filter 는 [Elasticsearch 공식 문서의 kNN 검색](https://www.elastic.co/guide/en/elasticsearch/reference/current/knn-search.html)에, 별칭을 옮기는 요청은 [별칭 문서](https://www.elastic.co/guide/en/elasticsearch/reference/current/aliases.html)에 있습니다.
- 질의와 상품을 각각 벡터로 바꾸는 모델을 학습하는 법은 [Two-Tower](post.html?id=two-tower-training) 편입니다. 광고 서버가 캠페인 후보를 꺼내는 풀은 [후보풀 기초](post.html?id=candidate-pool-basics) 편이 그림 다섯 장으로 봅니다.
- 후보를 받아 점수를 내는 쪽의 예산은 [모델 API](post.html?id=model-api-from-training-script) 편 3절과 [추론 서버](post.html?id=inference-server) 편에 있습니다. 후보를 미리 뽑아 둘지 요청마다 뽑을지는 [배치 추론과 실시간 추론](post.html?id=batch-vs-realtime-inference) 편입니다.
- 이 글의 그림 셋은 [질의 하나 따라가기 기록](demo-search-replay.html) 데모 한 장에 모여 있습니다. 질의 셋을 바꿔 가며 세 목록을 다시 볼 수 있습니다.
