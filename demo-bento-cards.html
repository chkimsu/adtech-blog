BentoML 카드 다섯 장

모델 파일 하나가 HTTP API 서버가 되기까지 정해야 하는 것 하나가 카드 한 장입니다. 점이 흐르는 방향이 데이터가 가는 방향입니다. 숫자는 설명용 가상 값입니다.

파랑 = 저장된 것 (모델 파일, 모델 저장소, 이미지) 벽돌색 = 들어오는 요청과 비용이 드는 곳 먹색 = 서비스와 서버 회색 = 빌드와 배칭 같은 작업 점선 = 적어 둔 것 (설정, 태그) 점 = 지금 가고 있는 것

SEVEN BY HAND

직접 짜면 만들어야 하는 기능 일곱 가지

쉽게 말하면 모델을 호출하는 코드는 몇 줄입니다. 나머지는 요청을 받고, 서버 상태를 알리고, 모델 버전을 바꾸고, 지연을 재는 서빙 코드입니다.

일곱을 더하면 1,370줄 이고 설정 파일과 테스트까지 1,800줄입니다. 그중 모델마다 달라지는 것은 입력 변환 하나입니다.

ONE SERVICE FILE

서비스 파일 하나에 적는 것

쉽게 말하면 클래스 하나에 데코레이터 두 개를 붙입니다. @bentoml.service 가 서비스를, @bentoml.api 가 API 엔드포인트 하나를 만듭니다. 상태 확인과 메트릭 엔드포인트는 BentoML 이 같이 엽니다.

서비스 파일은 21줄 입니다. 앞 카드의 일곱 가운데 넷은 BentoML 이 만들어 주고, 입력 변환과 웜업은 직접 씁니다.

BUILD AND CONTAINERIZE

Bento 로 빌드하면 도커 이미지 한 장이 된다

쉽게 말하면 서비스 코드, 모델 파일, 의존 라이브러리 목록을 Bento 하나로 패키징하고, 그것을 도커 이미지로 바꿉니다. 이미지에는 그때의 코드와 모델이 그대로 들어 있습니다.

직접 짠 쪽은 1.1GB 에 모델이 이미지 밖이고, BentoML 쪽은 1.4GB 에 모델이 이미지 안입니다. 모델만 바꿔도 이미지를 다시 빌드해야 합니다.

WHEN BATCHING PAYS

동적 배칭이 이득인 경우

쉽게 말하면 여러 요청을 잠깐 모아 한 번에 추론합니다. 얻는 것은 건당 계산이 줄어드는 몫이고, 드는 것은 요청이 모이기를 기다리는 시간입니다.

요청 하나에 후보가 800건이면 묶어도 건당 계산이 3% 만 줄어듭니다. 요청 하나가 작고 자주 올 때는 78% 줄어듭니다.

MORE WORKERS

워커를 늘리면 무엇이 바뀌고 무엇이 그대로인가

쉽게 말하면 파이썬은 GIL 때문에 프로세스 하나로 코어 하나만 씁니다. 그래서 워커 프로세스를 여러 개 띄웁니다. 처리량은 늘지만 요청 한 건의 처리 시간은 그대로입니다.

워커 1개면 사용률이 1.04 라 대기열이 쌓이고, 4개면 대기가 0.04ms 로 거의 사라집니다. 그 뒤로는 늘려도 얻을 것이 없고, 한 건의 처리 시간 4.75ms 는 내내 같습니다.

현업에서는 이렇게 씁니다

  • 새 모델을 띄우자는 말이 나오면 세 가지를 먼저 묻습니다. 예산이 밀리초인가 초인가, 요청이 초당 몇 건인가, 이런 모델이 앞으로 몇 개 더 생기나.
  • 카드를 누르면 위 해설 칸에 그 자리에서 헷갈리는 것 하나가 더 나옵니다.
  • 글로 이어 읽으려면 BentoML 편에 이 카드들이 절마다 한 장씩 들어 있습니다. 직접 짜면 어떤 모양인지는 추론 서버 편입니다.
