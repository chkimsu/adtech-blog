지훈 씨가 둘째 주에 첫 연동을 맡았습니다. 광고주 한 곳이 하루에 쓰는 광고비가 ₩5,000,000입니다. 그 돈으로 산 전환 1,000건을 남의 회사 서버에서 받아 정산에 넣는 일이고, 요청을 주고받는 코드 자체는 30분이면 씁니다.

막히는 것은 그다음입니다. 답이 안 오면 다시 보내야 하는데, 그러면 그 전환이 한 건으로 남는지 두 건으로 남는지를 문서가 말해 주지 않습니다. 얼마나 기다렸다 끊을지도, 인증키를 어디에 둘지도 문서 밖의 일입니다.

**남의 회사 서버와 붙을 때 무엇을 미리 맞춰 둬야 할까요?**

이 글은 그 목록입니다. 무엇으로 주고받나, 응답의 세 자리 숫자, 5만 행을 나눠 받는 법, 필드를 더하고 빼는 것, 다시 보내기, 그리고 인증을 순서대로 봅니다.

> **한 줄 요약:** 같은 API 라도 부르는 쪽이 남의 기기냐 우리 서버냐에 따라 지켜야 할 것이 갈립니다. 그리고 가장 비싼 실수는 다시 보내기입니다. 요청마다 번호를 안 붙이고 재시도를 걸면 전환 1,000건이 1,180건으로 부풀어 예산이 잘못 움직입니다.

> **골라 읽는 법** — 절이 여섯 개입니다.
>
> - 연동을 시작할 때 먼저 물을 것 → 1절
> - 상태코드와 오류 응답 모양 → 2절
> - 5만 행짜리 목록을 나눠 받기 → 3절
> - 필드를 더하고 빼는 것, 버전 → 4절
> - 얼마나 기다리고 몇 번 다시 보내나 → 5절
> - 인증 셋과 앱에 키를 박으면 안 되는 이유 → 6절

이 글의 숫자는 전부 설명을 위해 지어낸 값입니다. 그리고 이 글에서 **우리**는 전환 수집 API 를 운영하는 쪽, 지훈 씨가 들어간 팀입니다. 역할이 뒤집히는 자리에서는 그때마다 밝힙니다.

앞 글인 [API 기초](post.html?id=api-basics) 편에서 메서드와 요청·응답을 봤습니다. 그것부터 낯설면 그 편을 먼저 읽는 편이 낫습니다.

## 1. 연동을 시작할 때 먼저 물을 것

**부르는 쪽이 남의 기기냐 우리 서버냐. 이 한 줄이 비밀키·인증·버전·재시도를 통째로 가릅니다.**

API 기초 편 2절에서 본 구분이 여기서 값을 냅니다. 앱이 부르는 것을 client to server, 우리 서버가 부르는 것을 server to server 라고 합니다. 같은 주소라도 이 구분 하나가 나머지 결정을 전부 정합니다.

| 축 | client to server | server to server |
|---|---|---|
| 부르는 쪽 | 앱 · 브라우저 — 남의 기기 | 우리 서버 · 상대 서버 |
| 비밀키 | 둘 수 없습니다 | 둘 수 있습니다 |
| 요청에 실려 온 값 | 하나도 못 믿습니다 | 계약 안이면 믿습니다 |
| 트래픽 | 예측 불가 · 갑자기 몰립니다 | 대체로 예측 가능합니다 |
| 버전 | 옛 앱이 몇 년 남습니다 | 날짜를 잡고 같이 올립니다 |
| 재시도 | 네트워크가 끊긴다는 전제 | 정해 둔 시간 예산 안에서 |

**비밀키 줄이 첫 갈림길입니다.** 앱에 넣은 문자열은 그 앱을 받은 사람 모두가 갖게 되고, 한 번 새면 회수할 방법이 없습니다. 그래서 아예 안 두는 쪽으로 설계합니다.

**요청 값 줄은 바로 매출에 닿습니다.** 전환 금액을 앱이 보내게 두면 중간에서 ₩39,000을 ₩3,900,000으로 고칠 수 있습니다. 그 매출로 예산이 움직이니, 금액은 앱이 보낸 값을 버리고 우리 주문 테이블에서 다시 읽습니다.

지훈 씨가 이번에 맡은 것은 오른쪽 줄입니다. 전환을 대신 재 주는 외부 측정 회사가 우리에게 결과를 보내 주고, 우리는 그것을 받습니다.

### 광고 쪽 연동 셋을 같은 축에 놓아 봅니다

실제로 붙이게 되는 연동 셋을 그 축에 얹어 보겠습니다. 남의 앱에 심게 하는 코드 묶음을 SDK, 전환을 대신 재 주는 외부 측정 회사를 MMP 라고 부릅니다.

| 물음 | 앱 SDK → 수집 서버 | bidder → 거래소 | MMP → 전환 수집 API |
|---|---|---|---|
| 부르는 쪽 | 사용자 기기 | 우리 서버 | 상대 서버 — 우리는 받습니다 |
| 종류 | client to server | server to server | server to server |
| 규모 | 초당 2,639건 | 응답까지 12ms | 하루 1,000건 |
| 비밀키를 둘 수 있나 | 안 됩니다 | 됩니다 | 됩니다 |
| 응답이 늦으면 | 앱이 쌓아 뒀다 나중에 | 12ms 넘으면 거래소가 버립니다 | 몇 시간 뒤 다시 보냅니다 |
| 인증 값이 새면 | 앱에서 뽑힙니다 · 회수 불가 | 인증서 교체로 끝납니다 | 키 재발급으로 끝납니다 |
| 필드를 하나 지우면 | 옛 앱이 몇 년 깨집니다 | 날짜 잡고 같이 올립니다 | 상대 일정에 맞춥니다 |

초당 2,639건은 하루 노출 로그 2억 2,800만 줄을 86,400초로 나눈 값입니다. 12ms 는 [로드밸런서·Ingress·API Gateway](post.html?id=gateway-ingress-router) 편에서 정한 응답 예산입니다.

**전환 포스트백만 규모가 다릅니다.** 하루 1,000건뿐인데, 이 줄들이 정산 매출과 pCVR 학습 라벨을 동시에 만듭니다. 건수가 적다고 대충 해도 되는 자리가 아니라, 오히려 한 건이 가장 비싼 자리입니다.

### 무엇으로 주고받나

"API 를 붙인다"는 말 뒤에는 넷 중 하나가 있습니다. **HTTP + JSON** 이 기본값이고 상대가 누구든 붙습니다. 우리 서비스끼리 초당 수만 건을 주고받을 때는 **gRPC** 를 쓰고, 하루치 정산을 한 번에 넘길 때는 **배치 파일**을 씁니다. 나머지 하나가 **webhook** 인데, 이것만 방향이 거꾸로입니다.

**webhook 에서부터 우리는 받는 쪽입니다.** 상대가 우리를 부르니 우리가 서버를 열고 공개 주소를 넘깁니다. 인증도 중복 제거도 순서 뒤바뀜도 전부 받는 쪽이 감당하는데, 이 글 2~6절이 바로 그 이야기입니다.

**배치 파일도 규약입니다.** 컬럼 순서·인코딩·타임존이 전부 계약입니다. 하루가 끝나면 이 파일로 매출을 맞춰 보는 것을 정산에서 대사라고 부릅니다.

그래서 우리 수집 API 는 HTTP + JSON 으로 갑니다. 붙는 쪽이 제각각이니 어디서나 되는 것이 첫 조건이고, gRPC 는 앞에 변환 프록시를 세워야 해서 운영 비용이 늘기 때문입니다.

## 2. 응답의 세 자리 숫자와 오류 모양

**상태코드는 "누가 고쳐야 하나"와 "다시 보내도 되나"를 세 자리로 답합니다. 200 안에 에러를 담으면 그 답이 사라집니다.**

응답 맨 앞 세 자리를 상태코드라고 합니다. 2xx 는 처리됐다, 4xx 는 부르는 쪽이 고쳐야 한다, 5xx 는 받는 쪽이 고쳐야 한다는 뜻입니다. 이 셋만 지켜도 재시도 규칙과 알람 규칙이 저절로 정해집니다.

| 코드 | 뜻 | 누가 고쳐야 하나 | 다시 보내도 되나 |
|---|---|---|---|
| 200 · 201 | 처리했습니다 | — | — |
| 202 | 접수만 했습니다 · 결과는 나중에 | — | 요청 번호가 있을 때만 |
| 400 | 요청 형식이 틀렸습니다 | 부르는 쪽 | 아니요 · 그대로 또 틀립니다 |
| 401 | 자격증명이 없거나 틀렸습니다 | 부르는 쪽 | 갱신한 뒤 한 번만 |
| 404 | 그런 자원이 없습니다 | 부르는 쪽 | 아니요 |
| 429 | 초당 허용을 넘겼습니다 | 부르는 쪽 | `Retry-After` 만큼 뒤에 |
| 500 · 502 · 503 · 504 | 받는 쪽이 터졌거나 밀렸습니다 | 받는 쪽 | 됩니다 · 간격을 늘려 가며 |

**"200 안에 에러를 담지 마세요"가 이 절의 핵심입니다.** 이런 응답을 실무에서 자주 봅니다.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"result":"fail","message":"invalid click_id"}
```

이 한 줄 때문에 네 곳이 동시에 눈이 멉니다. 라이브러리는 성공으로 보고 재시도에서 빼고, 실패율 그래프는 평평하고, 로드밸런서도 정상으로 봅니다. 정산 매출이 안 맞을 때까지 아무도 모르고, 그 사이 틀린 숫자로 예산이 움직입니다.

에러는 상태코드로 알리고, 본문에는 기계가 읽을 것과 사람이 읽을 것을 같이 담습니다.

```http
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{"error":{"code":"INVALID_CLICK_ID","message":"click_id 'ck-77' was not found","field":"click_id","request_id":"req-8f21","retryable":false}}
```

`code` 는 부르는 쪽이 분기에 씁니다. 사람이 읽는 문구로 분기하면 그 문구를 다듬는 순간 상대 코드가 깨집니다. 그리고 `request_id` 가 없으면 실패한 그 건을 나중에 로그에서 못 찾는데, API 기초 편 7절에서 본 그 번호가 여기서 살아납니다.

`retryable` 한 칸이 상대의 재시도 코드를 대신 정해 줍니다. 이 칸이 없으면 상대가 상태코드만 보고 짐작해야 하고, 짐작이 틀리면 5절의 사고로 이어집니다.

## 3. 5만 행을 나눠 받는 법

**한 번에 다 못 받으니 끊어 받는데, 끊는 기준을 자리로 잡느냐 개수로 잡느냐가 정산 매출을 가릅니다.**

전환 리포트 5만 행을 받아 와야 합니다. 1,000행씩 50번에 나눠 받으면 20분쯤 걸리는데, **그 20분 동안 새 전환이 들어오고 취소가 지워집니다.** 목록이 움직이는 동안 읽고 있는 셈입니다.

끊는 방법은 둘입니다. `offset` 은 "앞에서 몇 개를 버리고 그다음"이라고 말합니다. 그래서 새 행이 맨 앞에 끼어들면 이미 읽은 행이 한 칸씩 밀려 다시 나옵니다. 커서는 "이 행 다음부터"라고 말해서 기준이 개수가 아니라 자리라, 앞에 뭐가 끼어들어도 안 밀립니다.

그 20분 동안 실제로 세어 보면 차이가 이렇습니다. `offset` 으로 받으면 이미 읽은 행 12개를 두 번 읽고 3개를 아예 못 읽는데, 커서로 받으면 둘 다 0입니다. 50번째 요청의 응답 시간도 380ms 와 40ms 로 갈립니다.

응답 시간이 갈리는 이유는 DB 가 하는 일이 다르기 때문입니다. `offset=49000` 은 4만 9천 행을 세어 버린 다음 1,000행을 줍니다. 커서는 미리 적어 둔 목차에서 그 자리를 바로 집으니, 페이지가 뒤로 갈수록 이 차이가 벌어집니다.

**그래서 이렇게 정합니다.** 사람이 페이지 번호를 눌러 보는 화면은 `offset` 을 쓰고, 기계가 처음부터 끝까지 훑는 정산용 목록은 커서를 씁니다. 지훈 씨가 맡은 전환 리포트는 뒤쪽이라 커서입니다.

한 가지 더 있습니다. 목록 응답은 배열을 그대로 주지 말고 객체로 한 번 감쌉니다. 그래야 나중에 "다음 커서"나 "전체 건수" 같은 필드를 더할 자리가 생깁니다.

```json
{"items":[{"conversion_id":"cv-0001","value":39000}],"next_cursor":"cv-0001","has_more":true}
```

배열을 그대로 줬다가 나중에 필드를 더하려면 응답 모양을 통째로 바꿔야 하고, 그것이 다음 절이 말하는 "안전한 적이 없는 변경"입니다.

## 4. 필드를 더하는 것과 빼는 것

**응답에 필드를 더하는 것은 대체로 안전하고, 빼는 것은 안전한 적이 없습니다. 이 비대칭이 버전 규칙의 뿌리입니다.**

이 절은 우리가 API 를 내주는 쪽일 때 이야기입니다. 규약이 한 번 나가면 상대 코드가 그것을 전제로 짜이니, 잘못 고치면 상대 쪽 매출이 그날로 빕니다.

| 바꾸는 것 | 옛 상대에게 무슨 일이 | 호환인가 |
|---|---|---|
| 응답에 필드 추가 | 모르는 필드는 무시합니다 | 대체로 호환 |
| 응답에서 필드 삭제 | 그 필드를 읽던 코드가 죽습니다 | 아니요 |
| 응답 필드 타입 변경 | 값을 못 바꾸거나 조용히 0이 됩니다 | 아니요 |
| 요청에 선택 필드 추가 | 안 보내면 그만입니다 | 호환 |
| 요청에 필수 필드 추가 | 옛 상대가 전부 400 을 받습니다 | 아니요 |
| 기본값 변경 | 조용히 결과 개수가 달라집니다 | 아니요 |

첫 줄의 "대체로"에 함정이 있습니다. 받은 글자를 프로그램이 쓰는 값으로 바꾸는 부분을 파서라고 하는데, 모르는 필드를 무시할지는 이 파서 설정에 달렸습니다. 설정이 엄격하면 예외 하나로 연동이 통째로 멈춰 하루치 매출이 빕니다. **그래서 우리가 부르는 쪽이면 이 설정을 미리 확인해 둡니다.**

:::deep 더 깊이 — 그 설정을 어떻게 확인하나
자바 Jackson 에서는 `FAIL_ON_UNKNOWN_PROPERTIES` 가 그 자리입니다. Jackson 자체에서는 켜져 있고 스프링 부트가 그것을 꺼 주니, 이름과 기본값을 외우지 말고 직접 확인하는 편이 낫습니다. 모르는 필드가 섞인 응답을 파서에 넣어 보고 예외가 나면 켜져 있는 것입니다.
:::

**필드를 지울 때는 지우기 전에 세어 봅니다.** 아래는 앱 SDK 가 쓰는 필드 하나를 지우기 직전에 본 버전 분포입니다.

| 앱 버전 | 트래픽 비중 | 이 필드를 읽나 |
|---|---|---|
| 5.2 (최신) | 41% | 아니요 |
| 5.1 | 27% | 아니요 |
| 5.0 | 18% | 예 |
| 4.x | 11% | 예 |
| 3.x 이하 | 3% | 예 |
| **합계** | **100%** | 32% 가 읽습니다 |

옛 필드를 읽는 앱이 32% 이고, 초당 요청으로 바꾸면 약 844건입니다. 지우는 순간 초당 844건이 깨지고 그 사용자에게는 복구 수단이 없습니다. **그러니 결정은 하나입니다 — 새 필드를 먼저 내보내고, 지우는 것은 이 비중이 떨어진 뒤로 미룹니다.**

버전은 경로나 헤더에 붙입니다. `/v2/conversions` 를 새로 파면 로그에서 바로 갈리고, 헤더로 하면 상대에게 주소를 바꿔 달라고 부탁할 일이 없습니다. 어느 쪽이든 새 버전을 낼 때 같이 정할 것은 "옛 버전을 언제 중단하나" 하나입니다. 서버끼리면 몇 주, 앱이면 몇 분기이고, 날짜를 안 적어 두면 운영 비용이 계속 쌓입니다.

## 5. 얼마나 기다리고, 몇 번 다시 보내나

**다시 보내기는 반드시 하게 됩니다. 요청마다 번호를 안 붙이면 그 재시도가 전환 1,000건을 1,180건으로 만듭니다.**

먼저 얼마나 기다릴지부터입니다. 미리 열어 둔 연결 묶음을 커넥션 풀이라고 하는데, **동시에 물려 있는 연결 수는 초당 호출 수에 응답 시간을 곱한 값**입니다. 우리가 상대를 초당 100번 부르고 풀에 연결이 200개 있다고 하겠습니다.

평소 39ms 면 연결이 3.9개만 물려 있어 여유롭습니다. 상대가 2초로 느려지면 200개가 딱 차고, 5초면 500개가 필요해서 300건이 대기합니다. 상한을 아예 안 걸어 30초까지 가면 3,000개가 필요한데 풀에는 200개뿐이라 **전면 정지**입니다.

**마지막 경우가 중요합니다.** 상대는 죽지 않았고 느려졌을 뿐인데, 우리는 연결을 다 써서 무관한 요청까지 같이 멈춥니다. 기다리는 시간에 상한을 안 걸면 상대의 지연 하나가 우리 서비스 전면 중단이 됩니다.

이 상한을 우리 전환 API 는 400ms 로 잡았습니다. 그 400ms 를 안에서 이렇게 나눠 씁니다.

| 우리가 부르는 것 | 잡은 상한 | 평소 걸리는 시간 |
|---|---|---|
| 서명 · 시각 검증 | 20ms | 2ms |
| 같은 요청인지 조회 | 50ms | 3ms |
| 전환 테이블 쓰기 | 200ms | 28ms |
| Kafka 발행 | 100ms | 6ms |
| 남긴 여유 | 30ms | — |
| **합계** | **400ms** | **39ms** |

평소 39ms 인데 상한을 400ms 로 잡았으니 열 배입니다. 이 배수는 평소 값이 아니라 느린 쪽 꼬리를 보고 정합니다. 평소 값에 붙여 잡으면 멀쩡한 요청이 끊겨 매출이 빠지고, 너무 넉넉하게 잡으면 앞의 표처럼 연결이 물려 서비스가 멈춥니다.

### 다시 보내면 전환이 두 번 세어집니다

기다리다 끊었으면 다시 보내야 합니다. 그런데 여기서 지훈 씨가 처음 만나는 진짜 문제가 나옵니다.

**응답이 안 왔을 때 부르는 쪽이 아는 것은 "답을 못 받았다" 하나뿐입니다.** 요청이 닿기 전에 끊긴 것인지, 서버가 이미 기록해 놓고 응답만 끊긴 것인지 가를 방법이 없습니다.

그래서 어느 쪽을 골라도 손해가 납니다. 안 보내면 안 닿았던 건이 사라져 정산 매출에서 빠지고, 보내면 이미 기록된 건이 한 줄 더 생겨 전환이 부풉니다. 하루 1,000건에 응답 유실이 15%쯤 나는 상황을 그대로 따라가 보겠습니다.

| 회차 | 보낸 건수 | 응답 유실 | 번호 없을 때 누적 | 번호 있을 때 누적 |
|---|---|---|---|---|
| 1 | 1,000 | 150 | 1,000 | 1,000 |
| 2 | 150 | 25 | 1,150 | 1,000 |
| 3 | 25 | 5 | 1,175 | 1,000 |
| 4 | 5 | 0 | **1,180** | **1,000** |

가정은 셋입니다. 서버는 요청을 받으면 항상 기록에 성공하고, 다만 응답이 돌아오는 길에서 유실됩니다. 부르는 쪽은 응답을 못 받으면 최대 3번까지 다시 보냅니다.

**실제 전환 1,000건이 리포트에 1,180건으로 잡힙니다.** 전환 한 건에 든 광고비를 CPA 라고 하는데, 진짜 CPA 는 ₩5,000인데 리포트에는 ₩4,237로 뜹니다. 전환당 비용이 ₩763 싸 보이는 것입니다.

이 차이가 예산 결정을 뒤집습니다. 광고주는 성과가 좋다고 보고 예산을 늘리는데, 늘린 예산으로 산 전환도 같은 비율로 부풀어 있습니다. **더 나쁜 것은 이 180건이 에러가 아니라는 점입니다.** 전부 성공 응답을 받아서 알람이 울릴 자리가 없고, pCVR 모델은 이 중복이 섞인 라벨을 그대로 학습합니다([pCVR 모델링](post.html?id=pcvr-modeling) 2절).

**답은 "보내되 같은 건임을 받는 쪽이 알아보게 한다"입니다.** 부르는 쪽이 요청마다 고유한 번호를 붙이고 다시 보낼 때도 같은 번호를 씁니다. 그러면 받는 쪽이 "아까 그 요청"이라고 알아보고 새로 기록하지 않습니다.

```http
POST /v1/conversions HTTP/1.1
Host: api.example.com
Content-Type: application/json
Idempotency-Key: O-00042

{"click_id":"ck-8f21","order_id":"O-00042","value":39000,"ts":1786002501}
```

헤더 이름이 `Idempotency-Key` 인 것은 이 약속을 부르는 말이 멱등성이기 때문입니다. **이름은 몰라도 됩니다.** 하는 일은 위의 한 줄이 전부이고, 실무에서는 "요청 번호 붙였어요?"로 통합니다.

번호를 만드는 규칙은 셋입니다.

- 그 건에만 붙어 있는 번호가 있으면 그것을 씁니다. 주문번호 `O-00042` 가 그 예입니다.
- 그런 번호가 없으면 고유 문자열을 만들고, **다시 보내는 내내 같은 값을 씁니다.**
- 다시 보낼 때마다 새로 만들면 번호가 없는 것과 같습니다. 이 실수가 가장 흔합니다.

받는 쪽은 그 번호를 저장해 뒀다가, 같은 번호가 또 오면 저장해 둔 응답을 그대로 돌려줍니다. 두 번째 요청도 `201` 을 받고 정산 매출은 한 건으로 남습니다.

### 언제 다시 보내고, 언제 보내지 않나

기준은 하나입니다. **"다시 보내면 결과가 달라질 수 있나."** 400 은 다시 보내도 또 400 이라 비용만 버리지만, 503 은 성공할 수 있습니다.

| 실패 종류 | 서버가 처리했을 수 있나 | 다시 보내나 |
|---|---|---|
| 연결 자체가 안 됨 | 아니요 | 안전합니다 |
| 연결 뒤 응답 대기 중 끊김 | 그렇습니다 | 번호가 있을 때만 |
| 502 · 503 · 504 | 그럴 수 있습니다 | 번호가 있을 때만 |
| 429 | 아니요 | `Retry-After` 뒤에 |
| 400 · 403 · 404 · 422 | 아니요 | 하지 마세요 |

**한 가지가 더 남았습니다 — 언제 다시 보내느냐입니다.** 상대 서버가 재시작하면 물려 있던 요청이 한꺼번에 끊깁니다. 전부 같은 시각에 실패했으니, 다 같이 1초 뒤에 다시 보내면 살아난 서버가 그 순간 또 넘어집니다.

간격을 1초·2초·4초로 늘려도 마찬가지입니다. 다 같이 늘리니 여전히 같은 시각에 몰립니다. **다시 보내는 시각 자체를 무작위로 흩어야 풀립니다.**

500건이 한꺼번에 끊긴 상황을 세 방식으로 돌려 보면 이렇게 갈립니다. 서버는 3초 뒤에 살아나고, 살아난 뒤에도 짧은 창 하나에 60건까지만 받습니다.

| 다시 보내는 방식 | 성공 | 실패 | 한 창에 몰린 최대 |
|---|---|---|---|
| 1초 간격으로 똑같이 | 120건 | 380건 | 500건 |
| 간격을 1·2·4초로 늘림 | 180건 | 320건 | 500건 |
| **늘리고 + 시각을 흩음** | **472건** | **28건** | **92건** |

가운데 줄이 함정입니다. 간격을 늘렸는데도 최대 부하가 그대로 500건입니다. **모두가 똑같이 늘렸기 때문에 몰리는 것은 하나도 안 풀렸습니다.** 시각을 흩으면 같은 창에 92건만 들어와서 성공이 180건에서 472건으로 늡니다. 설정 한 줄 차이로 살아 돌아오는 요청이 두 배 반이 됩니다.

## 6. 인증 — 무엇을 막고 무엇을 못 막나

**셋이 막는 것이 서로 다릅니다. 그리고 앱에 비밀키를 박는 것은 그중 어느 것도 아닙니다.**

인증 방식 이름은 많지만 첫 연동에서 만나는 것은 셋입니다. 각각 증명하는 것이 다르고, 못 막는 것도 다릅니다.

| 방식 | 무엇을 증명하나 | 무엇을 못 막나 | 앱에 둘 수 있나 |
|---|---|---|---|
| API 키 | 이 키를 가진 쪽이라는 것 | 본문 위변조 · 같은 요청 재전송 | 안 됩니다 |
| 토큰 | 발급자가 내준 것이라는 것 | 만료 전에 새면 그때까지 유효 | 사용자 토큰이면 됩니다 |
| 서명 | 본문이 안 바뀌었다는 것 | 같은 요청 재전송 | 안 됩니다 |

**API 키는 가장 단순하고 가장 약합니다.** 키만 있으면 누구나 우리인 척할 수 있으니 서버끼리만 씁니다. 키를 갈아 끼울 때는 옛 키와 새 키를 함께 인정하는 기간을 두는데, 안 두면 하루치 매출이 통째로 중단됩니다.

**서명은 본문과 시각을 비밀키로 계산해 헤더에 붙이는 방식입니다.** 받는 쪽이 같은 계산을 해 보니 한 글자만 고쳐도 값이 달라져 위변조가 걸립니다. 대신 같은 요청을 그대로 다시 보내는 것은 못 막아서, 앞뒤 5분처럼 좁은 창을 둡니다.

창을 두면 시계가 새 문제가 됩니다. 서명하는 쪽과 검증하는 쪽 시계가 창만큼 벌어지면 **코드는 멀쩡한데 요청이 전량 401 이 되고, 그동안 전환이 통째로 중단됩니다.** 그래서 서명이 전부 실패하면 키 재발급 승인을 받으러 가기 전에 시각 동기화부터 봅니다. 이걸 모르면 하루를 엉뚱한 데서 씁니다.

**앱에 비밀키를 박으면 안 되는 이유는 추상적이지 않습니다.** 앱 파일에서 키처럼 생긴 문자열을 뽑는 것은 명령 한 줄입니다.

```bash
# 앱 파일을 풀어 문자열만 훑습니다. 특별한 도구가 필요 없습니다.
unzip -p app.apk classes.dex | strings | grep -oE 'sk_live_[A-Za-z0-9]{8,}'
```

웹은 더 쉬워서 개발자 도구 네트워크 탭에 헤더가 그대로 보입니다. 코드를 알아보기 어렵게 뒤섞는 난독화도 귀찮게 할 뿐 막지는 못합니다.

**그러면 앱은 어떻게 인증할까요.** 답은 셋입니다. 사용자가 로그인해 받은 토큰을 쓰거나, 비밀이 필요한 호출을 앱 대신 우리 백엔드가 하거나, 애초에 비밀이 필요 없게 설계합니다. 지훈 씨의 첫 연동은 서버끼리라 API 키에 서명을 얹는 쪽으로 정했습니다.

## 한눈 정리

| 질문 | 한 줄 답 |
|---|---|
| 연동을 맡으면 먼저 무엇을 묻나 | 부르는 쪽이 남의 기기냐 우리 서버냐 |
| 오류를 어떻게 알리나 | 상태코드로. 200 안에 실패를 담으면 네 곳이 눈이 멉니다 |
| 5만 행을 어떻게 받나 | 사람이 보는 화면은 offset, 기계가 훑으면 커서 |
| 필드를 지워도 되나 | 지우기 전에 옛 버전 비중부터 셉니다 |
| 얼마나 기다리나 | 상한을 꼭 겁니다. 안 걸면 상대의 느림이 우리 정지가 됩니다 |
| 다시 보내면 중복되지 않나 | 요청마다 번호를 붙이면 받는 쪽이 알아봅니다 |
| 다 같이 1초 뒤에 보내면 | 살아난 서버가 또 넘어집니다. 시각을 흩습니다 |
| 앱에 키를 넣어도 되나 | 안 됩니다. 명령 한 줄로 뽑힙니다 |

## 헷갈리기 쉬운 점

첫 연동에서 밟기 쉬운 것들입니다. 공통점은 **배포 승인이 나고 테스트도 통과한다**는 것입니다.

- **앱에 비밀키를 박습니다** — 남이 우리 쿼터를 쓰고, 키를 바꾸면 옛 앱이 깨집니다.
- **기다리는 상한을 안 겁니다** — 상대가 느려지면 연결이 다 물려 무관한 기능까지 멈춥니다.
- **성공 코드 안에 에러를 담습니다** — 실패가 성공으로 세어져 알람도 재시도도 안 걸립니다.
- **번호 없이 다시 보냅니다** — 전환이 부풀고 전환당 비용이 싸 보여 예산이 잘못 움직입니다.
- **다시 보낼 때마다 번호를 새로 만듭니다** — 번호를 안 붙인 것과 결과가 같습니다.
- **쿼터 초과를 무시합니다** — 곧바로 다시 보내면 그 재시도가 정상 요청까지 같이 막습니다.
- **시계가 어긋나 서명이 실패합니다** — 키를 재발급받아도 안 고쳐지고, 증상은 인증 실패로 보입니다.
- **응답 필드가 늘어 파서가 깨집니다** — 부르는 쪽이면 모르는 필드를 먼저 열어 둡니다.

**"다시 보내기를 끄면 중복이 없어진다"가 아닙니다.** 끄면 중복 대신 유실이 생겨 매출이 빕니다. 응답을 못 받은 건 중 일부는 서버가 이미 기록했고 일부는 진짜로 안 들어갔는데, 둘을 못 가르니 켜고 번호를 붙이는 것이 답입니다.

**"200 이면 성공"이 아닙니다.** 상대 API 가 200 안에 실패를 담는다면 우리 코드가 본문을 보고 판정하고, 그 결과를 지표에 실패로 기록합니다. 안 그러면 정산 매출이 틀어져도 못 잡습니다.

**"내부 API 라 대충 해도 된다"가 가장 비쌉니다.** 상한도 요청 번호도 똑같이 필요하고, 오히려 거치는 단계가 길어 실패 지점이 더 많습니다. 여기서 아낀 하루가 나중에 몇 주치 손해로 돌아옵니다.
