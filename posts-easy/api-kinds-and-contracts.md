둘째 주에 지훈 씨가 처음으로 외부 연동을 맡았습니다. 연동은 두 시스템이 미리 정한 방식으로 데이터를 주고받도록 서로 붙이는 일입니다. 광고주 한 곳이 하루에 광고비 ₩5,000,000을 쓰고 그 돈으로 전환(광고를 본 사람이 구매처럼 광고주가 바라던 행동을 한 일) 1,000건을 사는데, 지훈 씨는 이 전환 1,000건을 남의 회사 서버에서 받아 정산(광고비와 매출을 확정하는 계산)에 넣어야 합니다. 요청과 응답을 주고받는 코드만 놓고 보면 30분이면 다 씁니다.

지훈 씨가 막히는 자리는 코드를 다 쓴 다음에 나옵니다. 응답이 오지 않으면 요청을 다시 보내야 하는데, 다시 보낸 전환이 한 건으로 남는지 두 건으로 남는지를 연동 문서가 알려 주지 않습니다. 응답을 얼마나 기다렸다가 끊을지와 인증키(요청을 보낸 쪽이 누구인지 증명하는 문자열)를 어디에 둘지도 문서에 나와 있지 않습니다.

**남의 회사 서버와 붙을 때 무엇을 미리 맞춰 둬야 할까요?**

이 글은 그 질문에 답하는 확인 목록입니다. 주고받는 방식, 응답 맨 앞의 세 자리 숫자, 5만 행을 나눠 받는 방법, 필드 추가와 삭제, 다시 보내기, 인증을 차례로 봅니다.

> **한 줄 요약:** 같은 API(프로그램끼리 요청과 응답을 주고받도록 미리 정해 둔 약속)라도 부르는 쪽이 사용자의 앱 같은 남의 기기인지 우리 서버인지에 따라 비밀키, 인증, 버전, 재시도에서 지켜야 할 것이 달라집니다. 가장 비싼 실수는 응답을 못 받은 요청을 다시 보내는 재시도에서 나오는데, 요청마다 번호를 붙이지 않고 재시도를 걸면 받는 쪽이 같은 전환을 여러 번 기록해 실제 전환 1,000건이 1,180건으로 늘고 그 숫자를 보고 예산이 잘못 움직입니다.

> **골라 읽는 법** — 절이 6개입니다.
>
> - 연동을 시작할 때 먼저 확인할 부르는 쪽과 전송 방식 → 1절
> - 상태코드와 오류 응답의 형식 → 2절
> - 5만 행짜리 목록을 나눠 받는 방법 → 3절
> - 필드 추가와 삭제, 버전 → 4절
> - 응답을 기다리는 시간의 상한과 다시 보내는 횟수 → 5절
> - 인증 방식 3가지와 앱에 비밀키를 넣으면 안 되는 까닭 → 6절

이 글의 숫자는 모두 설명을 위해 지어낸 값입니다. 글에서 **우리**는 지훈 씨가 들어간 팀을 가리킵니다. 이 팀은 전환을 받아 모으는 전환 수집 API 를 운영합니다. 우리가 다른 서버를 부르는 쪽이 되는 것처럼 역할이 바뀌는 자리에서는 그때마다 밝혀 둡니다.

메서드(POST 처럼 요청이 서버에 시키는 일의 종류)와 요청, 응답은 앞 글인 [API 기초](post.html?id=api-basics) 편에서 다뤘으므로, 이 세 가지가 낯설면 그 편을 먼저 읽고 오는 편이 낫습니다.

## 1. 연동 첫 확인 사항 — client to server 와 server to server

**API 를 부르는 쪽이 남의 기기인지 우리 서버인지가 비밀키, 인증, 버전, 재시도를 모두 정합니다.**

인증키를 어디에 둘지, 응답이 없을 때 어떻게 다시 보낼지처럼 도입에서 지훈 씨를 막은 결정은 API 를 누가 부르느냐에 따라 답이 달라집니다. 사용자의 앱이나 브라우저가 서버를 부르는 것을 client to server, 서버가 다른 서버를 부르는 것을 server to server 라고 합니다. API 기초 편 2절에서 처음 본 이 구분이 이 글에서는 실제 결정으로 이어지는데, 같은 주소의 API 라도 두 경우 가운데 어느 쪽이냐에 따라 아래 표의 나머지 줄이 모두 정해집니다.

| 항목 | client to server | server to server |
|---|---|---|
| 부르는 쪽 | 앱, 브라우저 — 남의 기기 | 우리 서버, 상대 서버 |
| 비밀키 | 둘 수 없습니다 | 둘 수 있습니다 |
| 요청에 담겨 온 값 | 하나도 못 믿습니다 | 계약 안이면 믿습니다 |
| 트래픽 | 예측 불가, 갑자기 몰립니다 | 대체로 예측 가능합니다 |
| 버전 | 옛 앱이 몇 년 남습니다 | 날짜를 잡고 같이 올립니다 |
| 재시도 | 네트워크가 끊긴다는 전제 | 정해 둔 시간 예산 안에서 |

**표에서 가장 먼저 볼 줄은 비밀키입니다.** 비밀키는 요청을 보낸 쪽이 누구인지 증명하는 데 쓰는, 남에게 보이면 안 되는 문자열입니다. 앱에 넣은 문자열은 그 앱을 내려받은 사람 모두가 갖게 되고 한 번 새어 나가면 회수할 방법이 없으므로, client to server 에서는 비밀키를 아예 두지 않는 쪽으로 설계합니다.

**표의 「요청에 담겨 온 값」 줄은 매출과 바로 이어집니다.** 전환 금액을 앱이 보내게 두면 중간에서 누군가 ₩39,000을 ₩3,900,000으로 고칠 수 있는데, 고친 금액이 매출로 잡히면 그 매출을 보고 예산이 움직입니다. 그래서 금액은 앱이 보낸 값을 버리고 우리 주문 테이블에서 다시 읽습니다.

지훈 씨가 이번에 맡은 연동은 표의 오른쪽 열인 server to server 입니다. 전환을 대신 측정해 주는 외부 측정 회사의 서버가 측정 결과를 보내오면 우리 서버가 그 결과를 받습니다.

### 광고 연동 3가지 비교

광고 쪽에서 실제로 붙이게 되는 연동 3가지를 위 표의 기준에 놓아 보면 아래 표와 같습니다. 「앱 SDK → 수집 서버」 열에서 SDK 는 광고 쪽이 남의 앱 안에 넣어 쓰게 하는 코드 라이브러리이고 수집 서버는 SDK 가 보낸 로그를 받아 적는 서버입니다. 「bidder → 거래소」 열에서 bidder 는 광고 경매에 낼 입찰가를 계산하는 우리 서버이고 거래소는 여러 bidder 의 입찰을 받아 경매를 여는 곳입니다. 「MMP → 전환 수집 API」 열의 MMP 는 앞에서 말한 외부 측정 회사처럼 전환을 대신 측정해 주는 회사로, 측정한 전환을 우리 전환 수집 API 로 보냅니다.

| 물음 | 앱 SDK → 수집 서버 | bidder → 거래소 | MMP → 전환 수집 API |
|---|---|---|---|
| 부르는 쪽 | 사용자 기기 | 우리 서버 | 상대 서버 — 우리는 받습니다 |
| 종류 | client to server | server to server | server to server |
| 규모 | 초당 2,639건 | 응답까지 12ms | 하루 1,000건 |
| 비밀키를 둘 수 있나 | 안 됩니다 | 됩니다 | 됩니다 |
| 응답이 늦으면 | 앱이 쌓아 뒀다 나중에 | 12ms 넘으면 거래소가 버립니다 | 몇 시간 뒤 다시 보냅니다 |
| 인증 값이 새면 | 앱에서 뽑힙니다, 회수 불가 | 인증서 교체로 끝납니다 | 키 재발급으로 끝납니다 |
| 필드를 하나 지우면 | 옛 앱이 몇 년 깨집니다 | 날짜 잡고 같이 올립니다 | 상대 일정에 맞춥니다 |

표의 규모 줄에서 앱 SDK 의 초당 2,639건은 하루 노출 로그(광고가 화면에 보인 일을 적은 기록) 2억 2,800만 줄을 하루의 86,400초로 나눈 값입니다. bidder 의 12ms 는 [로드밸런서, Ingress, API Gateway](post.html?id=gateway-ingress-router) 편에서 정한 응답 예산, 다시 말해 응답이 오가기까지 쓸 수 있는 시간의 한도입니다.

**세 연동 가운데 전환 포스트백만 규모가 다릅니다.** 포스트백(postback)은 MMP 가 측정한 전환을 우리 서버로 보내 주는 호출이고 하루에 1,000건밖에 오지 않습니다. 그런데 이 1,000줄이 정산 매출과 pCVR(광고를 클릭한 사람이 전환할 확률을 모델이 예측한 값) 학습 라벨(모델이 정답으로 배우는 값)을 한꺼번에 만들기 때문에, 건수가 적다고 대충 다뤄도 되는 자리가 아니라 오히려 한 건의 값이 가장 비싼 자리입니다.

### 전송 방식 — HTTP + JSON, gRPC, 배치 파일, webhook

「API 를 붙인다」고 할 때 실제로 데이터를 주고받는 방식은 4가지 가운데 하나입니다. 기본값은 HTTP 요청의 본문에 JSON(이름과 값을 짝지어 적는 텍스트 형식)을 담아 보내는 **HTTP + JSON** 이며 상대가 누구든 이 방식으로 붙습니다. 우리 서비스끼리 초당 수만 건을 주고받을 때는 **gRPC** 를 쓰는데, gRPC 는 미리 정한 스키마(메시지에 들어갈 필드와 타입의 정의)에 맞춘 바이너리 메시지로 상대 서버의 함수를 부르는 방식입니다. 하루치 정산을 한 번에 넘길 때는 데이터를 파일 하나에 모아 넘기는 **배치 파일**을 씁니다. 마지막 **webhook** 은 상대 쪽에서 일이 생겼을 때 상대 서버가 우리가 미리 알려 준 주소로 요청을 보내 알려 주는 방식입니다. 상대가 우리를 부르므로 4가지 가운데 webhook 만 방향이 거꾸로입니다.

**webhook 에서는 우리가 받는 쪽이 됩니다.** 상대가 우리를 불러야 하므로 우리가 서버를 열어 두고 밖에서 접속할 수 있는 공개 주소를 상대에게 넘깁니다. 그러면 요청이 정말 그 상대가 보낸 것인지 확인하는 인증, 같은 요청이 두 번 왔을 때 한 번만 남기는 중복 제거, 보낸 순서와 도착 순서가 바뀌는 순서 뒤바뀜을 모두 받는 쪽이 감당해야 하는데, 이 글의 2~6절이 그 이야기입니다.

**배치 파일에도 지켜야 할 규약이 있습니다.** 파일 안 컬럼의 순서, 글자를 바이트로 적는 인코딩, 시각을 어느 시간대 기준으로 적었는지 정하는 타임존이 모두 양쪽이 맞춰야 하는 계약입니다. 하루가 끝나면 이 배치 파일로 매출을 맞춰 보는데, 정산에서는 이 일을 대사라고 부릅니다.

붙는 쪽이 제각각이라 어디서나 붙는 것이 첫 조건이었고 gRPC 로 열면 API 앞에 변환 프록시(받은 요청을 다른 형식으로 바꿔 넘겨 주는 중계 서버)를 따로 띄워야 해서 운영 비용이 늘어나므로, 우리 전환 수집 API 는 HTTP + JSON 으로 정했습니다.

## 2. 상태코드와 오류 응답 형식

**응답 맨 앞의 세 자리 숫자인 상태코드는 누가 고쳐야 하는지와 다시 보내도 되는지를 알려 주는데, 성공을 뜻하는 200 안에 에러를 담으면 그 두 가지 답이 모두 사라집니다.**

부르는 쪽 프로그램은 응답을 받으면 상태코드를 보고 다시 보낼지와 알람을 울릴지를 정합니다. 상태코드는 첫 자리 숫자로 뜻이 나뉘는데, 2로 시작하는 2xx 는 요청을 처리했다는 뜻이고 4로 시작하는 4xx 는 부르는 쪽이 요청을 고쳐야 한다는 뜻이며 5로 시작하는 5xx 는 받는 쪽이 고쳐야 한다는 뜻입니다. 받는 쪽이 이 3가지 뜻만 지켜서 응답해도 부르는 쪽의 재시도 규칙과 알람 규칙이 상태코드에서 저절로 정해집니다.

| 코드 | 뜻 | 누가 고쳐야 하나 | 다시 보내도 되나 |
|---|---|---|---|
| 200, 201 | 처리했습니다 | — | — |
| 202 | 접수만 했습니다, 결과는 나중에 | — | 요청 번호가 있을 때만 |
| 400 | 요청 형식이 틀렸습니다 | 부르는 쪽 | 아니요, 그대로 또 틀립니다 |
| 401 | 자격증명이 없거나 틀렸습니다 | 부르는 쪽 | 갱신한 뒤 한 번만 |
| 404 | 그런 자원이 없습니다 | 부르는 쪽 | 아니요 |
| 429 | 초당 허용을 넘겼습니다 | 부르는 쪽 | `Retry-After` 만큼 뒤에 |
| 500, 502, 503, 504 | 받는 쪽에서 오류가 났거나 요청이 밀렸습니다 | 받는 쪽 | 됩니다, 간격을 늘려 가며 |

표의 401 에 나오는 자격증명은 요청한 쪽이 누구인지 증명하는 키나 토큰(발급자가 기한을 정해 내준 인증 문자열)입니다. 429 의 `Retry-After` 는 받는 쪽이 응답 헤더에 적어 주는 값으로, 다시 보내기 전에 기다릴 시간을 알려 줍니다. 202 줄의 요청 번호는 같은 요청을 다시 보낼 때 받는 쪽이 알아볼 수 있도록 요청마다 붙이는 고유한 번호이며 5절에서 자세히 봅니다.

**200 응답 안에 에러를 담지 않습니다.** 실무에서는 아래처럼 상태코드는 200 OK 로 성공이라고 해 놓고 본문에만 실패라고 적은 응답을 자주 봅니다.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"result":"fail","message":"invalid click_id"}
```

본문에는 `"result":"fail"` 과 `invalid click_id` 가 적혀 있지만 상태코드가 200 이므로 상태코드로 성공과 실패를 판단하는 네 곳이 이 실패를 동시에 보지 못합니다.

- HTTP 라이브러리는 이 응답을 성공으로 판정합니다.
- 성공으로 판정된 요청은 재시도 대상에서 빠집니다.
- 실패율 그래프에는 실패가 하나도 늘지 않아 선이 평평합니다.
- 로드밸런서(들어오는 요청을 여러 서버에 나눠 보내는 장비)도 이 서버를 정상으로 봅니다.

그래서 정산 매출이 맞지 않는다는 것이 보일 때까지 아무도 실패를 알아채지 못합니다. 그동안 예산은 틀린 숫자를 근거로 움직입니다.

에러는 상태코드로 알리고 본문에는 프로그램이 읽을 값과 사람이 읽을 문장을 함께 담습니다. 아래 응답은 요청에 담긴 `click_id` 를 찾지 못했을 때의 예입니다. 상태코드 422 Unprocessable Entity 는 요청의 형식은 맞지만 담긴 값을 처리할 수 없다는 뜻입니다.

```http
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{"error":{"code":"INVALID_CLICK_ID","message":"click_id 'ck-77' was not found","field":"click_id","request_id":"req-8f21","retryable":false}}
```

본문의 필드(JSON 안에서 이름과 값이 짝을 이룬 항목)는 저마다 읽는 쪽이 다릅니다. `code` 의 `INVALID_CLICK_ID` 는 부르는 쪽 프로그램이 경우를 나누는 조건(분기)에 쓰는 값입니다. `message` 처럼 사람이 읽는 문구로 분기하면 우리가 그 문구를 다듬는 순간 상대 코드의 조건이 맞지 않아 깨지므로, 프로그램이 읽을 값은 문구와 따로 `code` 에 담습니다.

`request_id` 의 `req-8f21` 은 이 요청 하나에 붙인 고유한 번호입니다. 이 값이 없으면 실패한 그 한 건을 나중에 로그에서 찾을 수 없는데, API 기초 편 7절에서 본 그 `request_id` 가 여기서 쓰입니다. `field` 의 `click_id` 는 문제가 된 요청 필드의 이름입니다.

마지막 `retryable` 은 이 요청을 다시 보내도 되는지를 받는 쪽이 직접 알려 주는 필드로, 이 응답에서는 `false` 라서 다시 보내지 말라는 뜻입니다. 이 필드가 있으면 상대의 재시도 코드는 이 값을 따르기만 하면 됩니다. 필드가 없으면 상대는 상태코드만 보고 다시 보낼지 짐작해야 하는데, 짐작이 틀리면 5절에서 볼 재시도 사고로 이어집니다.

## 3. 페이지네이션 — 5만 행을 나눠 받는 방법

**5만 행은 한 번에 받을 수 없어 여러 번 끊어 받는데, 끊는 기준을 행의 자리로 잡는지 개수로 잡는지에 따라 정산 매출이 달라집니다.**

이번에는 전환 리포트 5만 행을 받아 와야 합니다. 긴 목록을 여러 번에 나눠 받는 방식을 페이지네이션(pagination)이라고 하고 한 번에 받는 부분을 페이지라고 합니다. 5만 행을 한 번에 1,000행씩 50번에 나눠 받으면 20분쯤 걸리는데, 그 20분 동안에도 **새 전환이 목록에 들어오고 취소된 전환은 목록에서 지워지므로** 지훈 씨는 계속 움직이는 목록을 나눠 읽게 됩니다.

목록을 끊는 방법은 2가지입니다. `offset` 은 「앞에서부터 몇 개를 버리고 그다음 행부터 달라」고 요청하는 방식이라 끊는 기준이 개수입니다. 첫 1,000행을 읽은 뒤에 새 전환이 목록 맨 앞에 끼어들면 이미 읽은 행이 모두 한 칸씩 뒤로 밀리므로, 두 번째 요청이 앞의 1,000개를 버리고 나면 방금 읽은 마지막 행이 다시 나옵니다.

커서(cursor)는 마지막으로 받은 행을 가리키는 값입니다. 커서 방식은 「이 행 다음부터 달라」고 요청하므로 끊는 기준이 개수가 아니라 행의 자리입니다. 그래서 앞에 무엇이 끼어들어도 다음 요청이 밀리지 않습니다.

20분 동안 두 방식으로 받으며 세어 보면 `offset` 으로 받았을 때는 이미 읽은 행 12개를 두 번 읽고 3개를 아예 읽지 못하는데, 커서로 받았을 때는 두 번 읽은 행도 못 읽은 행도 0개입니다. 50번째 요청의 응답 시간도 `offset` 이 380ms, 커서가 40ms 로 크게 차이 납니다.

응답 시간 차이는 두 요청을 받은 DB 가 하는 일이 달라서 생깁니다. 50번째 요청은 `offset=49000` 이라서 DB 가 앞의 4만 9천 행을 하나씩 세어 버린 다음에야 1,000행을 돌려줍니다. 커서로 보낸 요청은 DB 가 인덱스(값의 위치를 미리 정렬해 적어 둔 목차)에서 커서가 가리키는 자리를 바로 찾아 그다음 1,000행을 돌려주므로 세어 버리는 행이 없습니다. 페이지가 뒤로 갈수록 `offset` 이 세어 버려야 하는 행이 늘어나므로 두 방식의 응답 시간 차이도 그만큼 벌어집니다.

**그래서 두 방식을 쓰는 자리를 나눕니다.** 사람이 페이지 번호를 눌러 보는 화면에는 `offset` 을, 프로그램이 처음부터 끝까지 스캔하는 정산용 목록에는 커서를 씁니다. 지훈 씨가 맡은 전환 리포트는 정산용 목록이라 커서로 받습니다.

목록을 돌려주는 응답에는 규칙이 하나 더 있습니다. 행들의 배열을 응답 맨 바깥에 그대로 두지 말고 객체(중괄호로 감싸 이름과 값의 짝을 적는 JSON 값) 안에 한 번 넣어서 주는데, 그래야 나중에 다음 커서나 전체 건수 같은 필드를 그 객체에 추가할 자리가 생깁니다. 아래 응답은 행들을 `items` 배열에 담고 바깥 객체에 `next_cursor` 와 `has_more` 를 함께 둔 모양입니다.

```json
{"items":[{"conversion_id":"cv-0001","value":39000}],"next_cursor":"cv-0001","has_more":true}
```

`next_cursor` 는 이번 페이지의 마지막 행인 전환 `cv-0001` 을 가리키고 있어서 다음 요청에 이 값을 넣으면 `cv-0001` 다음 행부터 받습니다. `has_more` 가 `true` 이므로 아직 받을 행이 남아 있습니다.

처음부터 배열만 그대로 줬다면 나중에 다음 커서 같은 필드를 추가하려 할 때 응답 모양 전체를 바꿔야 하는데, 응답 모양을 이렇게 바꾸는 일이 다음 절에서 「안전한 적이 없다」고 하는 변경입니다.

## 4. 필드 추가와 삭제, API 버전

**응답에 필드를 추가하는 변경은 대체로 안전하지만 필드를 빼는 변경은 안전한 적이 없습니다. 버전 규칙은 이 차이에서 나옵니다.**

이 절에서는 우리가 API 를 만들어 상대에게 내주는 쪽입니다. 규약(요청과 응답의 모양을 정한 약속)을 한 번 내보내면 상대는 그 모양을 전제로 코드를 짜므로, 우리가 규약을 잘못 고치면 그날로 상대 쪽 매출이 빠집니다.

아래 표는 바꾸는 종류마다 옛 상대에게 생기는 일과 호환 여부를 보여 줍니다. 호환은 상대가 코드를 고치지 않아도 계속 동작한다는 뜻입니다.

| 바꾸는 것 | 옛 상대에게 무슨 일이 | 호환인가 |
|---|---|---|
| 응답에 필드 추가 | 모르는 필드는 무시합니다 | 대체로 호환 |
| 응답에서 필드 삭제 | 그 필드를 읽던 코드가 죽습니다 | 아니요 |
| 응답 필드 타입 변경 | 값을 못 바꾸거나 조용히 0이 됩니다 | 아니요 |
| 요청에 선택 필드 추가 | 안 보내면 그만입니다 | 호환 |
| 요청에 필수 필드 추가 | 옛 상대가 전부 400 을 받습니다 | 아니요 |
| 기본값 변경 | 조용히 결과 개수가 달라집니다 | 아니요 |

요청에 필수 필드를 추가하면 그 필드를 모르는 옛 상대의 요청에는 그 필드가 없으므로, 우리 서버는 옛 상대의 요청을 모두 2절 표의 400(요청 형식이 틀렸습니다)으로 돌려보냅니다.

표 첫 줄의 「대체로」에는 함정이 있습니다. 받은 응답의 글자를 프로그램이 쓰는 값으로 바꾸는 부분을 파서(parser)라고 하는데, 응답에 처음 보는 필드가 섞여 왔을 때 그 필드를 무시할지는 파서의 설정에 달려 있습니다. 설정이 엄격하면 상대가 응답에 필드 하나를 추가하기만 해도 파서가 예외를 내고 그 예외 하나로 연동이 전부 멈춰 하루치 매출이 빠지므로, **우리가 부르는 쪽일 때는 이 설정을 미리 확인해 둡니다.**

:::deep 더 깊이 — Jackson 의 모르는 필드 설정 확인 방법
자바의 JSON 라이브러리인 Jackson 에서는 `FAIL_ON_UNKNOWN_PROPERTIES` 설정이 모르는 필드를 만났을 때 예외를 낼지를 정합니다. Jackson 을 그대로 쓰면 이 설정이 켜져 있지만 스프링 부트(자바 애플리케이션 프레임워크)는 이 설정을 꺼서 Jackson 을 준비해 주므로, 같은 Jackson 이라도 어떻게 쓰느냐에 따라 기본값이 다릅니다. 그래서 설정 이름과 기본값을 외우기보다 직접 확인하는 편이 낫습니다. 모르는 필드가 섞인 응답을 파서에 넣어 보고 예외가 나면 이 설정이 켜져 있다는 뜻입니다.
:::

**필드를 지울 때는 지우기 전에 그 필드를 읽는 쪽이 얼마나 되는지부터 셉니다.** 아래 표는 앱 SDK 가 쓰는 필드 하나를 지우기 직전에 앱 버전마다 트래픽 비중과 그 필드를 읽는지를 함께 본 버전 분포입니다.

| 앱 버전 | 트래픽 비중 | 이 필드를 읽나 |
|---|---|---|
| 5.2 (최신) | 41% | 아니요 |
| 5.1 | 27% | 아니요 |
| 5.0 | 18% | 예 |
| 4.x | 11% | 예 |
| 3.x 이하 | 3% | 예 |
| **합계** | **100%** | 32% 가 읽습니다 |

이 필드를 읽는 버전은 5.0(18%), 4.x(11%), 3.x 이하(3%)이고 세 비중을 더하면 32% 입니다. 1절 표에서 본 앱 SDK 의 초당 2,639건에 32% 를 곱하면 약 844건이니, 이 필드를 지우는 순간 초당 844건의 요청이 깨집니다. 그 요청을 보낸 옛 앱의 사용자 쪽에는 복구할 수단이 없습니다. 1절 표의 「옛 앱이 몇 년 깨집니다」가 바로 이 경우입니다.

**그래서 새 필드를 먼저 내보내고 옛 필드를 지우는 일은 이 32% 가 떨어진 뒤로 미룹니다.**

버전은 주소의 경로나 요청 헤더에 붙입니다. 경로에 붙여 `/v2/conversions` 를 새로 만들면 로그만 보고도 어느 버전으로 온 요청인지 바로 구분됩니다. 헤더에 붙이면 주소가 그대로라 상대에게 주소를 바꿔 달라고 부탁할 일이 없습니다. 어느 쪽을 고르든 새 버전을 낼 때 옛 버전을 언제 중단할지를 함께 정합니다. 중단까지의 기간은 서버끼리라면 몇 주, 앱이라면 몇 분기입니다. 중단 날짜를 적어 두지 않으면 옛 버전을 운영하는 비용이 계속 쌓입니다.

## 5. 타임아웃과 재시도 횟수

**다시 보내기(재시도)는 반드시 하게 되는데, 요청마다 번호를 붙이지 않으면 그 재시도가 실제 전환 1,000건을 1,180건으로 만듭니다.**

다시 보낼지 정하기 전에 응답을 얼마나 기다렸다가 끊을지부터 정합니다. 기다리는 시간에 거는 상한을 타임아웃(timeout)이라고 하는데, 상한이 왜 필요한지는 커넥션 풀로 계산해 보면 알 수 있습니다. 커넥션 풀(connection pool)은 상대 서버와의 연결을 미리 여러 개 열어 두고 요청마다 하나씩 꺼내 쓴 뒤 돌려놓는 방식입니다. 요청 하나는 응답을 받을 때까지 연결 하나를 붙잡고 있으므로 **동시에 사용 중인 연결 수는 초당 호출 수에 응답 시간을 곱한 값**입니다. 이번에는 우리가 부르는 쪽입니다. 우리가 상대를 초당 100번 부르고 풀에 연결이 200개 있다고 해 보겠습니다.

응답이 평소처럼 39ms 에 오면 초당 100번에 39ms 를 곱한 3.9개만 사용 중이라 200개 가운데 대부분이 비어 있습니다. 상대가 느려져 응답에 2초가 걸리면 초당 100번에 2초를 곱한 200개가 필요해 풀이 딱 찹니다. 5초가 걸리면 500개가 필요한데 풀에는 200개뿐이라 나머지 300건이 연결을 얻지 못하고 대기합니다. 상한을 아예 걸지 않아 응답을 30초까지 기다리면 초당 100번에 30초를 곱한 3,000개가 필요하지만 풀에는 여전히 200개뿐이라 **전면 정지**입니다.

**마지막 경우에는 상대가 멈추지 않았는데도 우리 서비스가 멈춥니다.** 상대 서버는 죽지 않고 느려졌을 뿐인데 우리 쪽은 풀의 연결 200개를 모두 그 상대를 기다리는 데 써 버려서 그 상대와 상관없는 요청까지 연결을 얻지 못해 함께 멈춥니다. 기다리는 시간에 상한을 걸지 않으면 이렇게 상대 한 곳의 지연이 우리 서비스 전체의 중단으로 이어집니다.

우리 전환 수집 API 는 이 상한을 400ms 로 잡았습니다. 아래 표는 그 400ms 를 API 안에서 부르는 단계마다 나눠 준 상한과 각 단계가 평소 걸리는 시간입니다.

| 우리가 부르는 것 | 잡은 상한 | 평소 걸리는 시간 |
|---|---|---|
| 서명, 시각 검증 | 20ms | 2ms |
| 같은 요청인지 조회 | 50ms | 3ms |
| 전환 테이블 쓰기 | 200ms | 28ms |
| Kafka 발행 | 100ms | 6ms |
| 남긴 여유 | 30ms | — |
| **합계** | **400ms** | **39ms** |

표의 서명, 시각 검증은 요청이 정말 그 상대가 보낸 것인지 확인하는 단계로 6절에서 다룹니다. 같은 요청인지 조회는 이미 받은 요청이 다시 온 것인지 확인하는 단계이며 이 절 뒤쪽에서 봅니다. Kafka 발행은 Kafka(이벤트를 쌓아 두고 여러 곳이 각자 읽어 가게 하는 시스템)로 메시지를 내보내는 단계입니다.

단계마다 평소 걸리는 시간을 더하면 2 + 3 + 28 + 6 = 39ms 인데 잡은 상한은 20 + 50 + 200 + 100 에 남긴 여유 30 을 더한 400ms 라서 상한이 평소의 열 배입니다. 이 배수는 평소 값이 아니라 느린 쪽 꼬리(드물게 오래 걸리는 요청들의 응답 시간)를 보고 정합니다. 상한을 평소 값에 바짝 붙여 잡으면 조금 늦었을 뿐인 멀쩡한 요청까지 끊겨 매출이 빠집니다. 반대로 너무 넉넉하게 잡으면 앞에서 본 것처럼 연결이 모두 사용 중이 되어 서비스가 멈춥니다.

### 재시도로 생기는 중복 전환

상한에 걸려 응답을 더 기다리지 않고 끊은 요청은 다시 보내야 하는데, 지훈 씨가 이 연동에서 처음 만나는 진짜 문제가 바로 이 다시 보내기에서 나옵니다.

**응답이 오지 않았을 때 부르는 쪽은 답을 받지 못했다는 사실 하나만 압니다.** 요청이 서버에 닿기도 전에 끊겼는지, 서버가 이미 기록해 놓고 돌려보낸 응답만 중간에 끊겼는지를 부르는 쪽에서는 구분할 방법이 없습니다.

그래서 다시 보내지 않아도, 다시 보내도 손해가 납니다. 다시 보내지 않으면 서버에 닿지 않았던 건이 사라져 정산 매출에서 빠집니다. 다시 보내면 서버가 이미 기록한 건이 한 줄 더 생겨 전환이 실제보다 많이 잡힙니다.

하루 1,000건 가운데 응답의 15%쯤이 유실되는 상황을 회차마다 따라가 보겠습니다. 아래 표는 세 가지를 가정합니다.

- 서버는 요청을 받으면 항상 기록에 성공합니다.
- 유실은 응답이 돌아오는 길에서만 일어납니다.
- 부르는 쪽은 응답을 받지 못하면 최대 3번까지 다시 보냅니다.

| 회차 | 보낸 건수 | 응답 유실 | 번호 없을 때 누적 | 번호 있을 때 누적 |
|---|---|---|---|---|
| 1 | 1,000 | 150 | 1,000 | 1,000 |
| 2 | 150 | 25 | 1,150 | 1,000 |
| 3 | 25 | 5 | 1,175 | 1,000 |
| 4 | 5 | 0 | **1,180** | **1,000** |

1회차에 보낸 1,000건은 모두 기록되지만 그 가운데 150건의 응답이 유실되어 부르는 쪽은 이 150건을 2회차에 다시 보냅니다. 번호가 없으면 받는 쪽은 다시 온 150건을 새 전환으로 보고 또 기록하므로 누적 기록이 1,150건이 됩니다. 2회차 응답 가운데 25건이 또 유실되어 3회차에 25건을 다시 보내면 1,175건, 그중 5건의 응답이 유실되어 4회차에 5건을 다시 보내면 1,180건이 됩니다. 4회차는 3번째 재시도이고 응답 유실도 0건이라 여기서 끝납니다. 번호가 있으면 받는 쪽이 다시 온 요청을 알아보고 새로 기록하지 않으므로 누적 기록은 4회차까지 1,000건 그대로입니다.

**그 결과 실제 전환 1,000건이 리포트에는 1,180건으로 잡힙니다.** 전환 한 건을 얻는 데 든 광고비를 CPA 라고 하는데, 광고비 ₩5,000,000을 실제 전환 1,000건으로 나눈 진짜 CPA 는 ₩5,000이지만 리포트의 1,180건으로 나누면 ₩4,237이 나와 전환당 비용이 ₩763 싸 보입니다.

₩763 의 차이는 예산 결정을 뒤집습니다. 광고주는 전환당 비용이 싸졌으니 성과가 좋다고 보고 예산을 늘리지만 늘린 예산으로 산 전환도 리포트에서는 같은 비율로 늘어 있습니다. **게다가 늘어난 180건은 에러로 잡히지 않습니다.** 180건 모두 성공 응답을 받았으므로 알람이 울릴 자리가 없습니다. pCVR 모델은 이 중복이 섞인 라벨을 그대로 학습합니다([pCVR 모델링](post.html?id=pcvr-modeling) 2절).

**그래서 다시 보내기는 하되 같은 요청이라는 것을 받는 쪽이 알아보게 합니다.** 부르는 쪽이 요청마다 고유한 번호를 붙이고 다시 보낼 때도 처음과 같은 번호를 쓰면, 받는 쪽은 그 번호로 「아까 그 요청」임을 알아보고 새로 기록하지 않습니다. 아래는 그 번호를 헤더에 담아 전환 한 건을 보내는 요청입니다.

```http
POST /v1/conversions HTTP/1.1
Host: api.example.com
Content-Type: application/json
Idempotency-Key: O-00042

{"click_id":"ck-8f21","order_id":"O-00042","value":39000,"ts":1786866501}
```

요청 헤더의 `Idempotency-Key: O-00042` 가 그 번호이고 본문의 `order_id` 도 같은 `O-00042` 라서 주문 하나에 번호 하나가 붙어 있습니다. 이 약속을 부르는 이름이 멱등성(idempotency)이라 헤더 이름이 `Idempotency-Key` 입니다. 멱등성은 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질을 말합니다. **멱등성이라는 이름은 몰라도 됩니다.** 하는 일은 위 요청의 헤더 한 줄이 전부입니다. 실무에서는 「요청 번호 붙였어요?」라는 말로 통합니다.

번호를 만드는 규칙은 3가지입니다.

- 보내는 건에만 붙어 있는 번호가 이미 있으면 그 번호를 씁니다. 위 요청의 주문번호 `O-00042` 가 그런 번호입니다.
- 그런 번호가 없으면 겹치지 않는 문자열을 새로 만들되, **다시 보내는 내내 처음 만든 값을 씁니다.**
- 다시 보낼 때마다 번호를 새로 만들면 받는 쪽은 매번 처음 보는 번호를 받아 새 요청으로 기록하므로 번호가 없는 것과 같습니다. 이 실수가 가장 흔합니다.

받는 쪽은 처음 받은 번호와 그때 돌려준 응답을 함께 저장해 두었다가, 같은 번호가 다시 오면 새로 기록하지 않고 저장해 둔 응답을 그대로 돌려줍니다. 그래서 다시 보낸 두 번째 요청도 처음과 같은 `201`(처리했다는 성공 코드)을 받고 정산 매출에는 한 건만 남습니다.

### 재시도할 실패와 재시도 시각

어떤 실패를 다시 보낼지는 **다시 보냈을 때 결과가 달라질 수 있는가** 하나로 정합니다. 400 은 요청 형식이 틀렸다는 뜻이라 그대로 다시 보내도 또 400 이 와서 비용만 버리지만 503 은 2절 표처럼 받는 쪽에서 오류가 났거나 요청이 밀린 경우라 다시 보내면 성공할 수 있습니다. 아래 표는 실패 종류마다 서버가 그 요청을 이미 처리했을 수 있는지와 다시 보내는지를 함께 적은 기준입니다.

| 실패 종류 | 서버가 처리했을 수 있나 | 다시 보내나 |
|---|---|---|
| 연결 자체가 안 됨 | 아니요 | 안전합니다 |
| 연결 뒤 응답 대기 중 끊김 | 그렇습니다 | 번호가 있을 때만 |
| 502, 503, 504 | 그럴 수 있습니다 | 번호가 있을 때만 |
| 429 | 아니요 | `Retry-After` 뒤에 |
| 400, 403, 404, 422 | 아니요 | 하지 마세요 |

연결 자체가 안 된 실패는 서버가 그 요청을 처리했을 리 없으므로 다시 보내도 안전합니다. 연결한 뒤 응답을 기다리다 끊긴 경우와 502, 503, 504 는 서버가 이미 처리했을 수 있으므로 앞에서 본 요청 번호가 있을 때만 다시 보냅니다. 429 는 서버가 처리하지 않은 요청이라 `Retry-After` 에 적힌 시간이 지난 뒤에 보냅니다. 400, 403, 404, 422 는 차례대로 요청 형식 오류, 권한 없음, 없는 자원, 처리할 수 없는 값을 뜻하는데, 서버가 처리하지 않았고 다시 보내도 결과가 같으므로 다시 보내지 않습니다.

**다시 보낼 시각도 정해야 합니다.** 상대 서버가 재시작하면 그 서버에 연결되어 응답을 기다리던 요청이 한꺼번에 끊기는데, 이 요청들은 모두 같은 시각에 실패했으므로 다 같이 1초 뒤에 다시 보내면 막 살아난 서버에 요청이 한꺼번에 몰려 서버가 그 순간 다시 멈춥니다.

다시 보내는 간격을 1초, 2초, 4초로 두 배씩 늘리는 방식을 지수 백오프(exponential backoff)라고 합니다. 그런데 간격을 이렇게 늘려도 다시 보내는 쪽이 모두 똑같은 간격으로 늘리므로 여전히 같은 시각에 몰립니다. **다시 보내는 시각 자체를 요청마다 무작위로 흩어야 몰림이 풀립니다.** 이렇게 다시 보내는 시각에 무작위 값을 섞는 방법을 지터(jitter)라고 합니다.

아래 표는 한꺼번에 끊긴 요청 500건을 세 가지 방식으로 다시 보내 본 결과입니다. 서버는 3초 뒤에 살아나는데 그 뒤에도 짧은 시간 구간인 창 하나에 60건까지만 받는다고 가정했습니다.

| 다시 보내는 방식 | 성공 | 실패 | 한 창에 몰린 최대 |
|---|---|---|---|
| 1초 간격으로 똑같이 | 120건 | 380건 | 500건 |
| 간격을 1, 2, 4초로 늘림 | 180건 | 320건 | 500건 |
| **늘리고 + 시각을 흩음** | **472건** | **28건** | **92건** |

표의 가운데 줄에 함정이 있습니다. 간격을 1, 2, 4초로 늘렸는데도 한 창에 몰린 최대 요청이 첫 줄과 같은 500건인데, **500건을 다시 보내는 쪽이 모두 똑같은 간격으로 늘렸기 때문에 같은 시각에 몰리는 문제는 하나도 풀리지 않았습니다.** 시각을 흩은 셋째 줄에서는 한 창에 몰린 요청이 가장 많을 때도 92건이라 성공이 180건에서 472건으로 늘고 실패는 320건에서 28건으로 줄어듭니다. 재시도 설정 한 줄 차이로 살아 돌아오는 요청이 두 배 반이 됩니다.

## 6. 인증 — API 키, 토큰, 서명이 막는 범위

**인증 방식 3가지는 저마다 막는 것이 다릅니다. 앱에 비밀키를 넣어 두는 방법은 그 3가지 가운데 어디에도 들지 않습니다.**

마지막으로 지훈 씨는 MMP 가 보낸 요청이 정말 그 MMP 가 보낸 것인지 확인할 방법을 정해야 합니다. 요청을 보낸 쪽이 누구인지 확인하는 일을 인증이라고 합니다. 인증 방식은 이름이 많지만 첫 연동에서 만나는 방식은 API 키, 토큰, 서명 3가지이고 방식마다 증명해 주는 것과 막지 못하는 것이 다릅니다.

| 방식 | 무엇을 증명하나 | 무엇을 못 막나 | 앱에 둘 수 있나 |
|---|---|---|---|
| API 키 | 이 키를 가진 쪽이라는 것 | 본문 위변조, 같은 요청 재전송 | 안 됩니다 |
| 토큰 | 발급자가 내준 것이라는 것 | 만료 전에 새면 그때까지 유효 | 사용자 토큰이면 됩니다 |
| 서명 | 본문이 안 바뀌었다는 것 | 같은 요청 재전송 | 안 됩니다 |

표에서 위변조는 요청 본문을 중간에서 몰래 고치는 공격이고 재전송은 남이 보낸 요청을 가로채 그대로 다시 보내는 공격입니다. 토큰은 2절에서 본 대로 발급자가 기한을 정해 내준 인증 문자열이라 만료 전에 새어 나가면 만료될 때까지 남이 그 토큰을 쓸 수 있습니다.

**API 키는 3가지 가운데 가장 단순하고 가장 약합니다.** API 키는 미리 발급받은 고정 문자열을 요청에 넣어 보내는 방식입니다. 키 문자열만 손에 넣으면 누구나 우리인 척할 수 있으므로 API 키는 서버끼리에서만 씁니다. 키를 새 키로 바꿀 때는 옛 키와 새 키를 둘 다 인정하는 기간을 두는데, 이 기간을 두지 않으면 옛 키로 온 요청이 모두 거부되어 하루치 매출이 전부 중단됩니다.

**서명은 요청 본문과 보낸 시각을 비밀키로 계산한 값을 헤더에 붙이는 방식입니다.** 받는 쪽도 같은 비밀키로 같은 계산을 해서 헤더의 값과 비교하므로 본문을 한 글자만 고쳐도 계산 결과가 달라져 위변조가 걸립니다. 하지만 본문을 고치지 않고 같은 요청을 그대로 다시 보내면 서명도 그대로 맞으므로 서명만으로는 재전송을 막지 못합니다. 그래서 서명에 넣은 시각이 받는 쪽 시각의 앞뒤 5분처럼 좁은 창 안에 있을 때만 요청을 받아 줍니다.

창을 두면 두 서버의 시계가 새 문제가 됩니다. 서명하는 쪽과 검증하는 쪽의 시계가 창의 크기만큼 벌어지면 서명에 적힌 시각이 늘 창 밖에 있게 되어 **코드에는 아무 문제가 없는데도 요청이 모두 401 을 받고 그동안 전환이 전부 중단됩니다.** 그래서 서명이 모두 실패하면 키 재발급 승인을 받으러 가기 전에 두 서버의 시각이 맞는지부터 확인합니다. 이 순서를 모르면 하루를 엉뚱한 곳에서 씁니다.

**앱에 비밀키를 넣으면 안 되는 까닭은 명령 한 줄로 확인됩니다.** 아래 명령은 앱 파일 `app.apk` 를 풀어 그 안의 문자열 가운데 키처럼 생긴 것만 뽑습니다.

```bash
# 앱 파일을 풀어 문자열만 스캔합니다. 특별한 도구가 필요 없습니다.
unzip -p app.apk classes.dex | strings | grep -oE 'sk_live_[A-Za-z0-9]{8,}'
```

명령에서 `unzip` 이 앱 파일을 풀면 `strings` 가 그 안의 글자만 꺼내고 `grep` 이 `sk_live_` 로 시작하는 키 모양의 문자열을 골라내는데, 주석에 적힌 대로 특별한 도구는 필요 없습니다. 웹은 더 쉬워서 브라우저의 개발자 도구에서 네트워크 탭을 열면 요청 헤더가 그대로 보입니다. 코드를 알아보기 어렵게 뒤섞는 난독화도 키를 찾는 일을 귀찮게 할 뿐 막지는 못합니다.

**그러면 앱은 어떻게 인증할까요?** 방법은 3가지입니다. 사용자가 로그인해서 받은 토큰을 쓰거나, 비밀키가 필요한 호출을 앱 대신 우리 백엔드 서버가 하거나, 처음부터 비밀키가 필요 없게 설계합니다. 지훈 씨의 첫 연동은 MMP 서버와 우리 서버 사이의 server to server 라서 API 키에 서명을 붙이는 방식으로 정했습니다.

## 한눈 정리

| 질문 | 한 줄 답 |
|---|---|
| 연동을 맡으면 먼저 무엇을 묻나 | 부르는 쪽이 남의 기기인지 우리 서버인지 |
| 오류를 어떻게 알리나 | 상태코드로 알립니다. 200 안에 실패를 담으면 네 곳이 실패를 보지 못합니다 |
| 5만 행을 어떻게 받나 | 사람이 보는 화면은 offset, 프로그램이 스캔하는 목록은 커서 |
| 필드를 지워도 되나 | 지우기 전에 그 필드를 읽는 옛 버전의 비중부터 셉니다 |
| 얼마나 기다리나 | 상한을 꼭 겁니다. 안 걸면 상대가 느려질 때 우리 서비스가 멈춥니다 |
| 다시 보내면 중복되지 않나 | 요청마다 번호를 붙이면 받는 쪽이 같은 요청을 알아봅니다 |
| 다 같이 1초 뒤에 보내면 | 살아난 서버가 다시 멈춥니다. 다시 보내는 시각을 흩습니다 |
| 앱에 키를 넣어도 되나 | 안 됩니다. 명령 한 줄로 뽑힙니다 |

## 헷갈리기 쉬운 점

아래는 첫 연동에서 저지르기 쉬운 실수입니다. 모두 **배포 승인이 나고 테스트도 통과한다**는 공통점이 있습니다.

- **앱에 비밀키를 넣습니다** — 앱에서 키를 뽑아 간 남이 우리 쿼터(정해 둔 기간에 보낼 수 있는 요청 수의 한도)를 대신 써 버리는데, 키를 바꾸면 옛 키가 든 옛 앱이 깨집니다.
- **기다리는 시간에 상한을 걸지 않습니다** — 상대가 느려지면 커넥션 풀의 연결이 모두 그 상대를 기다리는 데 쓰여 상관없는 기능까지 멈춥니다.
- **성공 코드 안에 에러를 담습니다** — 실패가 성공으로 세어지므로 알람도 울리지 않고 재시도도 일어나지 않습니다.
- **요청 번호 없이 다시 보냅니다** — 같은 전환이 여러 번 기록되어 전환 수가 늘고 전환당 비용이 싸 보이므로 예산이 잘못 움직입니다.
- **다시 보낼 때마다 번호를 새로 만듭니다** — 받는 쪽이 매번 새 요청으로 보므로 번호를 붙이지 않은 것과 결과가 같습니다.
- **쿼터 초과를 무시합니다** — 429 를 받은 뒤 `Retry-After` 를 기다리지 않고 곧바로 다시 보내면 그 재시도가 정상 요청까지 함께 막습니다.
- **두 서버의 시계가 맞지 않아 서명이 실패합니다** — 증상은 인증 실패로 보이지만 원인이 키가 아니라 시계라서 키를 재발급받아도 고쳐지지 않습니다.
- **상대 응답에 필드가 추가되어 파서가 깨집니다** — 우리가 부르는 쪽이라면 모르는 필드를 무시하도록 파서 설정을 미리 열어 둡니다.

**다시 보내기를 끈다고 문제가 해결되지는 않습니다.** 다시 보내기를 끄면 중복 대신 유실이 생겨 매출이 빠집니다. 응답을 받지 못한 건 가운데 일부는 서버가 이미 기록했고 일부는 정말로 들어가지 않았는데 부르는 쪽은 두 경우를 구분할 수 없으므로, 다시 보내기를 켜 두고 요청 번호를 붙입니다.

**상태코드가 200 이라고 늘 성공은 아닙니다.** 상대 API 가 200 응답 안에 실패를 담아 보낸다면 우리 코드가 본문을 직접 읽어 성공인지 판정하고 실패면 지표에도 실패로 기록합니다. 이렇게 하지 않으면 정산 매출이 틀어져도 알아챌 수 없습니다.

**「내부 API 라 대충 해도 된다」는 생각이 가장 비쌉니다.** 회사 안 서비스끼리 부르는 내부 API 에도 기다리는 시간의 상한과 요청 번호가 똑같이 필요합니다. 내부 호출은 오히려 거치는 단계가 길어서 실패할 수 있는 지점이 더 많습니다. 여기서 아낀 하루가 나중에 몇 주치 손해로 돌아옵니다.
