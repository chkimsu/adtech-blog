서빙 카드 다섯 장

학습이 끝난 모델이 요청 하나에 답하기까지, 시간과 메모리가 정해지는 자리 하나가 카드 한 장입니다. 예산은 100ms 이고 테이블은 수십 GB 입니다. 숫자는 각 글의 가상 데이터 값입니다.

파랑 = 놓여 있는 데이터 (테이블, 벡터, 카운터) 벽돌색 = 지금 오는 것 (요청, 실시간 값) 먹색 = 모델과 서버 회색 = 만드는 작업 (해시, 배치 묶기, 샤딩) 점 = 지금 가고 있는 데이터

RETRIEVAL

10만 개에서 수백 개로 추린다

쉽게 말하면 광고 후보 10만 개에 정밀한 모델을 다 돌리면 30초가 걸립니다. 예산은 0.1초입니다. 그래서 먼저 가벼운 방법으로 훑어 수백 개만 남기고, 거기에만 정밀 모델을 씁니다.

정밀 모델 전수는 30,000ms, 벡터 내적은 13.6ms입니다. 후보가 100만 개가 되면 내적도 128.8ms 라 2%만 훑는 ANN 이 3.4ms 로 받습니다.

TRAIN / SERVE SKEW

같은 피처 이름, 다른 값

쉽게 말하면 「지난 7일 클릭 수」라는 같은 이름의 피처를, 학습은 자정에 만든 표에서 읽고 서빙은 실시간 카운터에서 읽습니다. 이름이 같으니 아무도 모릅니다.

평균 3.366%p 어긋나고, 심한 유저는 pCTR 3.4%가 14.2%로, 입찰가가 34원에서 142원이 됩니다. 활발해진 유저를 늘 낮게 봅니다.

BATCHING

몇 건씩 묶어 한 번에

쉽게 말하면 요청을 한 건씩 처리하면 서버가 많이 필요하고, 여러 건 모아 한 번에 처리하면 서버는 줄지만 모이기를 기다리는 시간이 붙습니다.

배치 1이면 서버 41대, 32면 3대입니다. 128까지 키우면 p99 가 14.75ms 가 되어 10ms 예산에서 탈락합니다.

HASHING IDS

광고 ID 100만 개를 칸 26만 개에

쉽게 말하면 광고마다 칸을 하나씩 주면 표가 너무 커집니다. 그래서 ID 를 계산해 정해진 칸 수 안에 밀어 넣는데, 서로 다른 광고가 같은 칸을 쓰게 됩니다.

배치 하나 3.8GB 가 테이블 16MB가 됩니다. 머리끼리 부딪친 200쌍만 오차 19.0%라, 상위 1만 개에 전용 칸 0.6MB 를 주면 0%가 됩니다.

EMBEDDING TABLE

2억 줄을 서버에 나눠 담는다

쉽게 말하면 유저마다 숫자 묶음을 하나씩 들고 있는 큰 표가 있습니다. 서빙만 하면 서버 한 대에 들어가는데, 학습하면 3배로 불어 쪼개야 합니다.

서빙 23.8GB 가 학습에서 83.2GB가 됩니다. 배치 1,024건이 건드리는 줄은 0.0005%뿐이라, 갱신을 밀집으로 짜면 하루치에 6.6일이 걸립니다.

현업에서는 이렇게 씁니다

  • 서빙이 느리다는 말을 들으면 이 다섯 자리를 순서대로 봅니다. 후보를 너무 많이 넘겼나, 피처 조회가 느린가, 배치가 너무 큰가, 테이블 조회가 흩어졌나, 샤드가 모자란가.
  • 카드를 누르면 위 해설 칸에 그 자리에서 헷갈리는 것 하나가 더 나옵니다.
  • 먼저 볼 것은 학습 데이터 카드 여섯 장입니다. 여기 오는 모델이 무엇을 배웠는지를 다룹니다.
