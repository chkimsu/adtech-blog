모델 팀으로 옮긴 지 셋째 주인 지훈 씨는 첫 업무로 피처 하나를 추가하는 일을 맡았습니다. 피처(feature)는 모델이 예측할 때 입력으로 받는 값입니다. 추가할 피처는 광고별 최근 7일 클릭률(광고가 노출된 횟수 가운데 클릭된 횟수의 비율)입니다. 노트북에서 이 피처를 만들어 모델에 넣고 돌려 보니 코드는 잘 돌았고 모델이 낸 예측값도 그럴듯했습니다.

그래서 지훈 씨는 선배에게 「이제 이걸 서버에 올리려면 어떻게 하나요?」 하고 물었습니다. 선배는 「커밋해서 올리면 CI 가 이미지를 만들고 검사 세 가지를 통과한 것만 이미지 저장소에 올려요. 그 이미지가 서버 12대에 올라가요」라고 답했지만 지훈 씨는 CI 검사가 무엇인지도, 이미지가 무엇인지도 몰랐습니다.

지훈 씨는 그보다 노트북에서 돌아간 코드가 서버에서도 똑같이 돌아간다고 누가 보장하느냐가 더 마음에 걸렸습니다. 노트북은 한 대이지만 서버는 12대입니다. 서버마다 조금씩 다르면 같은 요청을 보내도 어느 서버가 받느냐에 따라 다른 예측값이 나옵니다.

**내 노트북에서 돌아가는 코드가 서버에서도 똑같이 돌아간다고 누가 보장할까요?**

이 보장은 컨테이너 이미지(container image)와 CI(지속적 통합, continuous integration)가 만듭니다. 컨테이너 이미지(이 글에서는 줄여서 이미지)는 코드와 그 코드 아래에 깔린 파이썬, 라이브러리, 리눅스까지 하나로 묶어 빌드한 파일입니다. 여기서 빌드는 정해진 순서대로 필요한 것을 모아 실행할 수 있는 결과물 하나로 만드는 작업을 말합니다. 커밋(commit)은 고친 코드를 코드 저장소에 한 번 기록한 단위입니다. CI 는 커밋이 올라올 때마다 이미지를 만들어 검사 3가지를 차례로 거치게 하는 자동 절차입니다.

이 글은 지훈 씨의 커밋 하나가 검사 3가지를 지나 이미지 저장소(만든 이미지를 올려 두는 곳)에 오르기까지를 카드 그림으로 따라갑니다. 이 흐름을 알고 나면 「내 노트북에서는 되는데」라는 말이 왜 나오는지와 그 말이 나왔을 때 어디를 봐야 하는지가 보입니다.

> **한 줄 요약:** 이미지는 기본 리눅스부터 코드까지 층(레이어)을 아래에서부터 쌓아 빌드한 파일 하나이고 서버 12대가 같은 이미지를 쓰므로 코드 아래 층까지 12대가 모두 같습니다. 커밋 하나는 CI 에서 6분 20초 동안 이미지로 빌드되고 검사 3가지(함수마다 답이 정해 둔 값과 같은지 보는 유닛 테스트, 응답의 모양과 속도를 보는 계약 테스트, 이미지 안의 위험한 라이브러리와 크기를 보는 이미지 검사)를 지나는데, 하나라도 걸리면 이미지는 저장소에 오르지 않습니다.

> **골라 읽는 법** — 이 글은 절 7개로 되어 있고 4절을 뺀 절마다 카드 한 장이나 표 하나가 들어 있으므로 카드나 표만 보고 다음 절로 넘어가도 됩니다.
>
> - 노트북과 서버의 예측값 차이와 원인 → 1절
> - 이미지 한 장의 층 구성 → 2절
> - 커밋에서 이미지 저장소까지의 CI 단계 → 3절
> - CI 검사 3가지(유닛 테스트, 계약 테스트, 이미지 검사) → 4~6절
> - 담장 안(한 회사가 앱부터 모델 서버까지 모두 가진 곳)과 열린 RTB(여러 회사가 광고 자리를 실시간 경매로 사고파는 시장)의 차이 → 7절

이 글에 나오는 이름, 파일 크기, 시간은 모두 설명을 위해 정한 가상 값입니다. [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편의 요청 원문에 나오는 예측값 0.0412 와 그 편의 모델 서버(모델로 예측값을 계산해 돌려주는 서버) 12대, 모델 호출 예산(모델 서버를 한 번 부를 때 응답을 기다리는 시간 한도) 8ms 는 이 글에서도 같은 값으로 씁니다. 피처 이름 `ad_ctr_7d` 는 [CTR 피처 엔지니어링](post.html?id=ctr-feature-engineering) 편의 표에 나오는 이름입니다.

카드 그림의 색은 4가지로, 파랑은 놓여 있는 것(파일, 이미지, 저장소), 벽돌색은 지금 오는 것(커밋, 요청), 먹색은 모델과 서버, 회색은 만드는 작업(빌드, 테스트, 검사)을 나타냅니다. 점선 상자는 설정이나 통과 조건처럼 적어 둔 것을 뜻합니다.

## 1. 노트북과 서버의 예측값 차이

**같은 코드와 같은 모델 파일로 노트북과 서버가 서로 다른 예측값을 냈는데 두 곳은 코드 아래에 깔린 라이브러리 버전 하나만 달랐습니다.**

코드는 혼자 돌지 않고 파이썬, 수를 곱하고 더하는 라이브러리, 그 아래의 리눅스가 있어야 돌아가므로 코드가 같아도 그 아래 층 가운데 하나가 다르면 값이 달라질 수 있습니다.

지훈 씨가 바로 이 일을 겪었습니다. 새 피처를 넣기 전에 먼저 지금 쓰는 모델 v418 로 요청 하나를 노트북에서 돌려 봤는데, 회원 u-3f9c 에게 광고 9931 을 보였을 때 클릭할 확률을 묻는 요청에 노트북은 0.0412 를 냈고 같은 요청을 서버에 보내니 0.0397 이 돌아왔습니다. 두 값의 차이를 노트북의 0.0412 로 나눈 비율로 보면 서버의 0.0397 은 3.6% 낮은 값입니다. 그런데 두 곳의 코드는 같은 커밋이었고 모델 파일도 같은 38MB 였습니다.

아래 카드는 같은 요청과 같은 모델 파일을 받은 노트북과 모델 서버가 코드 아래의 어느 층에서 다른지를 보여 줍니다.

그래서 이 일에서 나오는 결정은 한 가지입니다. 라이브러리 버전 하나만 달라도 값이 달라지니 코드만 같게 맞춰서는 부족하고 코드 아래 층까지 하나로 묶어 빌드해야 합니다. 그렇게 빌드한 결과물이 다음 절에서 볼 이미지입니다.

## 2. 이미지 한 장의 층 구성

**이미지는 기본 리눅스, 파이썬, 라이브러리, 코드를 아래에서부터 차례로 쌓은 파일 한 장이고 코드는 그 가운데 맨 위 한 층입니다. 모델 파일은 이미지에 넣지 않습니다.**

이미지는 코드가 돌아가는 데 필요한 모든 것을 층층이 쌓아 빌드한 파일이라 서버 12대가 같은 이미지를 받으면 12대의 층이 모두 같아지고 1절에서 노트북과 서버의 값을 다르게 만든 라이브러리 버전 차이도 여기서 사라집니다.

층(레이어)은 이미지를 이루는 단위이며 아래 층부터 차례로 쌓아 만듭니다. 이 팀의 추론 이미지(서버에서 예측값을 낼 때 쓰는 이미지)는 아래에서부터 기본 리눅스, 파이썬 3.11, 추론 런타임(모델 파일을 읽어 예측을 계산하는 라이브러리), 코드의 네 층입니다. 학습에는 GPU 라이브러리(GPU 로 계산하게 해 주는 라이브러리)와 학습 프레임워크(모델을 학습시키는 라이브러리)가 더 필요하므로 학습 이미지(모델을 학습시킬 때 쓰는 이미지)에는 다섯 층이 쌓입니다. 아래 표에서 보듯 학습 이미지에는 추론 런타임 층이 없고 추론 이미지에는 GPU 라이브러리와 학습 프레임워크 층이 없습니다.

층마다 크기가 다르며 아래 표의 층별 크기는 가정한 값입니다. 이미지 한 장의 크기는 그 이미지에 든 층의 크기를 더한 값이라, 추론 이미지는 코드 12MB, 추론 런타임 0.8GB, 파이썬 3.11 0.2GB, 기본 리눅스 0.1GB 를 더해 표의 합계 1.1GB 가 됩니다.

| 층 | 학습 이미지 | 추론 이미지 |
|---|---|---|
| 코드 (커밋 a3f9c21) | 12MB | 12MB |
| 학습 프레임워크 | 1.2GB | 없음 |
| GPU 라이브러리 | 3.1GB | 없음 |
| 추론 런타임 | 없음 | 0.8GB |
| 파이썬 3.11 | 0.2GB | 0.2GB |
| 기본 리눅스 | 0.1GB | 0.1GB |
| 합계 | 4.6GB | 1.1GB |

카드에는 두 이미지의 층이 아래부터 쌓인 순서와 이미지 밖에 따로 놓인 모델 파일이 함께 그려져 있습니다.

표에서는 두 가지를 읽을 수 있습니다. 첫째는 이미지의 크기를 정하는 층입니다. 코드는 12MB 로 가장 작은 층이라 이미지의 크기는 코드가 아니라 라이브러리가 정합니다. 두 이미지에서 코드 12MB, 파이썬 3.11 0.2GB, 기본 리눅스 0.1GB 는 같으므로 학습 이미지 4.6GB 와 추론 이미지 1.1GB 의 차이 3.5GB 는 모두 라이브러리 층에서 나옵니다. 학습 이미지에만 있는 학습 프레임워크 1.2GB 와 GPU 라이브러리 3.1GB 를 더한 값에서 추론 이미지에만 있는 추론 런타임 0.8GB 를 빼면 3.5GB 입니다.

둘째는 커밋마다 다시 만드는 범위입니다. 코드를 고치면 맨 위 코드 층 하나만 다시 만들고 그 아래 층은 이미 만든 것을 그대로 다시 씁니다. 학습 이미지로 보면 코드 아래 네 층을 그대로 쓰므로 커밋마다 4.6GB 를 새로 만들지 않고 12MB 층 하나만 새로 만듭니다.

이미지를 어떤 층으로 어떤 순서로 쌓을지는 Dockerfile 이라는 파일에 적습니다. 아래는 추론 이미지의 Dockerfile 을 줄여 옮긴 것으로, 위에서 아래로 읽는 순서가 그대로 층이 쌓이는 순서입니다.

```dockerfile
FROM python:3.11-slim                      # 기본 리눅스 + 파이썬 3.11 (0.3GB)
RUN pip install onnxruntime==1.18.0        # 추론 런타임 (0.8GB). 버전을 고정합니다
COPY src/ /app/src/                        # 코드 (12MB). 커밋마다 이 층만 새로
WORKDIR /app
CMD ["python", "-m", "src.server"]         # 서버를 켜는 명령
```

첫 줄 `FROM python:3.11-slim` 은 기본 리눅스와 파이썬 3.11 이 함께 든 이미지를 맨 아래 층으로 가져오므로 주석의 0.3GB 는 위 표의 기본 리눅스 0.1GB 와 파이썬 3.11 0.2GB 를 더한 값입니다. 둘째 줄이 1절 문제의 답입니다. 이 줄은 파이썬 라이브러리를 설치하는 명령 `pip install` 로 추론 런타임 `onnxruntime` 을 버전 `1.18.0` 으로 고정해 설치하므로, 이 이미지를 노트북에서 켜든 서버에서 켜든 같은 버전의 런타임이 들어 있습니다. 셋째 줄 `COPY` 는 코드 12MB 를 맨 위 층으로 넣는 줄이라 주석대로 커밋마다 이 층만 새로 만들어집니다. 넷째 줄 `WORKDIR /app` 은 그다음 명령이 실행될 폴더를 `/app` 으로 정합니다. 마지막 줄 `CMD` 는 이미지를 켤 때 서버를 띄우는 명령입니다.

모델은 매일 새벽 새로 만들어지는데 이미지는 코드가 바뀔 때만 만들기 때문에 모델 파일 38MB 는 이 Dockerfile 에 넣지 않습니다. 서버는 뜰 때(켜질 때) 모델 파일을 두는 저장소에서 모델을 따로 내려받는데, 그 순서는 [추론 서버](post.html?id=inference-server) 편에 있습니다.

## 3. 커밋에서 이미지 저장소까지의 CI 단계

**커밋이 올라오면 CI 가 이미지를 만들어 검사 3가지를 거치게 한 뒤 이미지 저장소에 올리며 여기까지 6분 20초가 걸립니다. 저장소에 오른 이미지의 이름에는 커밋 해시(커밋마다 붙는 고유한 문자열)가 붙습니다.**

이미지를 쓰기로 해도 사람이 노트북에서 이미지를 만들어 올리면 1절의 문제가 다시 생기므로 이미지를 만드는 자리도 한 곳으로 정합니다. 그 한 곳이 CI 로, 커밋이 올라오면 정해진 순서대로 이미지를 만들고 검사합니다.

지훈 씨가 커밋 `a3f9c21` 을 올리자 CI 가 이미지 만들기, 유닛 테스트, 계약 테스트, 이미지 검사의 4단계를 차례로 돌기 시작했습니다. 아래 표의 걸린 시간은 단계마다 든다고 가정한 시간입니다. 끝나는 시각은 CI 가 시작한 때부터 그 단계까지 걸린 시간을 모두 더한 값이라, 이미지 만들기 2분 10초에 유닛 테스트 48초를 더하면 2분 58초, 여기에 계약 테스트 2분 30초를 더하면 5분 28초, 마지막으로 이미지 검사 52초까지 더하면 6분 20초입니다.

| 단계 | 하는 일 | 걸린 시간 | 끝나는 시각 |
|---|---|---|---|
| 이미지 만들기 | 코드 층을 새로 쌓음 | 2분 10초 | 2:10 |
| 첫째 검사, 유닛 테스트 | 함수 214개의 답 확인 | 48초 | 2:58 |
| 둘째 검사, 계약 테스트 | 요청과 응답의 모양과 속도 확인 | 2분 30초 | 5:28 |
| 셋째 검사, 이미지 검사 | 위험한 라이브러리와 크기 확인 | 52초 | 6:20 |

카드 아래쪽 눈금에는 표의 끝나는 시각이 2:10 부터 6:20 까지 그대로 찍혀 있어 커밋 `a3f9c21` 이 4단계를 지나 이미지 저장소에 오르기까지를 한 줄로 따라갈 수 있습니다.

6분 20초가 지나 이미지 저장소에 오른 한 장의 이름은 `pctr-serve:2026.09.17-a3f9c21` 입니다. 콜론 뒤의 태그(같은 이름의 이미지를 버전마다 구분하는 표시)에 날짜 2026.09.17 과 커밋 해시 `a3f9c21` 이 들어 있으므로 서버에 오른 이미지가 어느 코드로 만든 것인지 이름만 보고 알 수 있어 사고가 났을 때 「지금 서버에 있는 코드가 무엇인가」를 찾는 데 1초면 됩니다.

CI 가 어떤 순서로 무엇을 돌릴지는 CI 설정 파일에 적어 둡니다. 이 파일은 코드와 같은 저장소에 들어 있어 커밋이 올라올 때마다 CI 가 읽습니다. 아래는 그 설정을 줄여 옮긴 것으로, 표의 4단계는 `steps` 아래에 한 줄씩 들어 있습니다.

```yaml
on:
  push:
    branches: [main]
jobs:
  build-and-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t pctr-serve:${DATE}-${SHA} .     # 이미지 만들기
      - run: python -m unittest discover tests/unit          # 첫째 검사
      - run: python -m unittest discover tests/contract      # 둘째 검사
      - run: image-scan pctr-serve:${DATE}-${SHA}            # 셋째 검사
      - run: docker push registry.example.com/pctr-serve:${DATE}-${SHA}
```

맨 위의 `on: push` 와 `branches: [main]` 은 main 브랜치(저장소 안에서 커밋이 이어지는 갈래 하나)에 커밋이 올라올 때마다 이 설정을 실행하라는 뜻입니다. `steps` 아래에서는 `docker build` 줄이 이미지를 만들고 `tests/unit` 과 `tests/contract` 를 돌리는 두 줄이 첫째 검사와 둘째 검사를, `image-scan` 줄이 셋째 검사를 맡습니다. 이미지 이름의 `${DATE}-${SHA}` 자리에는 날짜와 커밋 해시가 들어가 위의 `pctr-serve:2026.09.17-a3f9c21` 같은 이름이 됩니다.

마지막 줄의 `docker push` 가 이미지를 이미지 저장소에 올리는 명령인데, 그 앞의 검사 세 줄 가운데 하나라도 실패하면 CI 가 거기서 멈춰 마지막 줄이 실행되지 않습니다. 그래서 검사에서 실패한 커밋은 저장소에 오르지 못하고 서버로 배포되지도 않습니다. 배포(deploy)는 이미지를 서버에 올려 실제 요청을 받게 하는 일입니다. 세 검사가 각각 무엇을 확인하는지는 다음 세 절에서 하나씩 다룹니다.

## 4. 첫째 검사: 유닛 테스트 214개

**유닛 테스트(unit test)는 함수 하나에 입력 하나를 넣어 나온 답이 미리 정해 둔 값과 같은지 보는 검사입니다. 214개가 48초에 끝나며 하나라도 답이 다르면 이미지는 여기서 멈춥니다.**

유닛 테스트에는 「이 함수에 이것을 넣으면 저것이 나와야 한다」가 코드로 적혀 있어 사람이 매번 손으로 확인하지 않아도 CI 가 커밋마다 대신 확인합니다.

지훈 씨의 피처 함수 `ad_ctr_7d` 로 예를 들어 보겠습니다. 이 함수는 로그(광고 노출 한 건마다 날짜, 광고 번호, 클릭 여부를 남긴 기록)를 받아 광고 하나의 최근 7일 클릭률을 냅니다. 이때 지킬 규칙은 세 가지입니다. 첫째, 7일 윈도우(오늘을 뺀 앞 7일, D-7 부터 D-1 까지) 안의 로그만 세고 윈도우 밖의 로그는 세지 않습니다. 둘째, 윈도우 안이라도 다른 광고의 로그는 세지 않습니다. 셋째, 윈도우 안에 노출이 없으면 노출 수 0 으로 나눌 수 없으니 나눗셈 없이 0 을 돌려줍니다. 아래 코드는 규칙 하나를 테스트 하나가 확인하도록 테스트 3개를 파이썬 표준 라이브러리의 `unittest` 만으로 만들어 돌립니다.

```python
# 하는 일: 광고별 최근 7일 클릭률 피처를 만들고, 그 유닛 테스트 셋을 돌린다.
import unittest

# 1단계: 피처 함수를 만든다
# 다른 광고의 로그와 윈도우 밖의 로그는 세지 않는다.
def ad_ctr_7d(logs, ad_id, today):
    """today 를 뺀 앞 7일(D-7 ~ D-1) 로그로 광고 하나의 클릭률을 낸다. 노출이 없으면 0."""
    imp = clk = 0
    for day, aid, is_click in logs:
        if aid != ad_id or not (today - 7 <= day <= today - 1):
            continue                       # 다른 광고이거나 윈도우 밖이면 세지 않는다
        imp += 1
        clk += is_click
    return clk / imp if imp else 0.0

# 2단계: 가상 로그를 만든다
# 로그 값은 전부 가상이다.
LOGS = [(day, 9931, 0) for day in range(1, 11)]   # 광고 9931: 1~10일 노출 10건
LOGS += [(3, 9931, 1), (9, 9931, 1)]             # 그중 3일과 9일에 클릭 (노출 12건, 클릭 2)
LOGS += [(5, 7720, 1)]                            # 다른 광고 7720 의 클릭 하나

# 3단계: 테스트 셋을 만들어 돌린다
# CI 는 이런 테스트 214개를 커밋마다 돌린다. 하나라도 틀리면 이미지가 저장소에 오르지 않는다.
class TestAdCtr7d(unittest.TestCase):
    def test_window_only(self):
        # today=10 이면 윈도우는 3~9일. 그 안의 9931 노출 9건, 클릭 2건 → 2/9
        self.assertAlmostEqual(ad_ctr_7d(LOGS, 9931, today=10), 2 / 9)
    def test_other_ad_excluded(self):
        # 9931 의 로그가 7720 의 값에 섞이면 안 된다 (노출 1건, 클릭 1건 → 1.0)
        self.assertAlmostEqual(ad_ctr_7d(LOGS, 7720, today=10), 1.0)
    def test_no_impression(self):
        # 윈도우 안에 노출이 없으면 나누지 않고 0
        self.assertEqual(ad_ctr_7d(LOGS, 9931, today=30), 0.0)

unittest.main(argv=["x"], verbosity=2, exit=False)

# 출력 (시간은 돌릴 때마다 다르다):
# 3단계 뜻: 세 테스트가 모두 ok 이고, 마지막 줄의 OK 가 테스트 셋 전체가 통과했다는 뜻이다.
# test_no_impression (__main__.TestAdCtr7d) ... ok
# test_other_ad_excluded (__main__.TestAdCtr7d) ... ok
# test_window_only (__main__.TestAdCtr7d) ... ok
#
# ----------------------------------------------------------------------
# Ran 3 tests in 0.000s
#
# OK
```

출력에서 세 테스트가 모두 `ok` 로 찍히고 마지막 줄이 `OK` 이므로 테스트 3개가 전부 통과했습니다. `Ran 3 tests in 0.000s` 에 찍히는 시간은 돌릴 때마다 다릅니다.

첫째 `test_window_only` 는 이 피처를 정의하는 7일 윈도우를 그대로 확인합니다. 오늘(`today`)이 10일이면 윈도우는 D-7 인 3일부터 D-1 인 9일까지라, 광고 9931 의 노출 12건 가운데 오늘 노출인 10일 1건과 윈도우 밖인 1일과 2일의 노출 2건을 빼면 9건이 남고 그 9건에 3일과 9일의 클릭 2건이 들어 있으므로 클릭률은 2/9 입니다. 5일에 있는 7720 의 클릭은 윈도우 안이지만 다른 광고의 것이라 9931 의 분자(클릭 수)에 넣지 않습니다. 윈도우를 잘못 잡아 오늘인 10일을 넣으면 값이 2/9 에서 달라지므로 이 테스트가 걸립니다.

둘째 `test_other_ad_excluded` 는 광고 번호로 로그를 제대로 거르는지 봅니다. 다른 광고 7720 의 로그는 5일의 클릭 1건뿐이라 7720 의 클릭률은 노출 1건에 클릭 1건인 1.0 이어야 하는데, 광고 번호로 거르지 못하면 9931 의 로그까지 섞여 값이 1.0 에서 달라지므로 이 테스트가 걸립니다. 셋째 `test_no_impression` 은 `today=30` 처럼 윈도우 안에 로그가 하나도 없을 때 나눗셈을 하지 않고 0.0 을 돌려주는지 확인합니다.

윈도우를 잘못 잡은 피처는 오프라인(지난 데이터로 평가할 때)에서 AUC 가 0.89 로 나와도 실서빙(실제 요청을 받는 서비스)에서는 0.78 이 됩니다. AUC 는 클릭된 노출 하나와 클릭되지 않은 노출 하나를 골랐을 때 모델이 클릭된 노출에 더 높은 점수를 줄 확률로, 1 에 가까울수록 좋은 지표입니다. 이 사례는 [CTR 피처 엔지니어링](post.html?id=ctr-feature-engineering) 편 6절에 있습니다.

지훈 씨의 커밋은 48초 만에 유닛 테스트 214개를 모두 통과했습니다. 다만 유닛 테스트는 함수를 하나씩 따로 볼 뿐이라 서버 전체가 요청을 받아 응답을 돌려주는 모양까지는 확인하지 않습니다. 그 모양은 다음 절의 둘째 검사가 봅니다.

## 5. 둘째 검사: 계약 테스트

**계약 테스트는 새 이미지로 서버를 실제로 켜고 요청을 보내 응답의 모양과 속도가 약속대로인지 봅니다. 응답의 필드(이름이 붙은 값 하나) 12개가 맞아야 하고 요청 1,000건을 보냈을 때 8ms 를 넘긴 요청의 비율(8ms 초과율)이 6% 이하여야 통과합니다.**

API 서버(모델 서버에 요청을 보내 예측값을 받아 쓰는 서버)와 모델 서버 사이의 「이 필드를 보내면 이 필드가 돌아온다, 그리고 8ms 안에 온다」라는 약속을 [API 연동 실무](post.html?id=api-kinds-and-contracts) 편에서는 계약(contract)이라고 불렀습니다. 계약 테스트는 새 이미지가 이 계약을 지키는지 확인합니다.

다음 카드에는 검사 3가지의 통과 조건 아래에 지훈 씨의 커밋이 받은 결과(214개 통과, 초과율 4.8% 로 통과, 1.1GB 로 통과)가 함께 적혀 있습니다.

계약 테스트는 모양과 속도의 두 부분으로 나뉩니다. 첫째인 모양 부분은 새 이미지로 서버를 켜고 요청 하나를 보내 응답의 필드 12개가 이름과 자료형(숫자인지 문자열인지 같은 값의 종류)까지 맞는지 봅니다. API 서버는 응답에 `pctr`(모델이 예측한 클릭 확률)이 있다고 믿고 순위를 매기므로 지훈 씨가 피처를 하나 추가했어도 응답 모양은 그대로여야 합니다.

둘째인 속도 부분은 요청을 많이 보내 응답 속도를 보는 부하 시험으로, 요청 1,000건의 8ms 초과율(낮을수록 좋습니다)을 셉니다. 새 피처는 조회(피처 값을 읽어 오는 일)를 한 번 더 하므로 요청마다 시간이 조금 더 드는데, 그 조금이 얼마인지에 따라 통과와 탈락이 정해집니다.

아래 코드는 이 부하 시험을 흉내 내어 새 피처의 조회가 요청마다 더하는 시간을 0 부터 1.0ms 까지 바꿔 가며 8ms 초과율이 기준 6% 를 넘는지를 봅니다. 요청 하나의 추론 시간은 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편과 같은 값을 쓴 로그정규 분포(시간에 로그를 취하면 정규분포가 되는 분포)에서 뽑습니다. 중앙값 3.0ms 는 요청의 절반이 3.0ms 안에 끝난다는 뜻이고 흩어진 정도 0.55 는 시간에 로그를 취한 값의 표준편차입니다. 함수 `exceed_rate` 는 요청 1,000건 하나하나에 뽑은 추론 시간과 `extra_ms` 를 더해 예산 8ms 를 넘으면 `over` 를 1 늘리며 1,000건을 다 돈 뒤에는 `over` 를 1,000 으로 나눈 값에 100 을 곱해 초과율(%)을 돌려줍니다.

```python
# 하는 일: 계약 테스트의 부하 부분으로 요청 1,000건의 8ms 초과율을 세고, 새 피처가 더하는 시간마다 기준 6% 를 넘는지 본다.
import random, math

# 1단계: 예산과 통과 기준을 둔다
# 통과 기준은 6% 이하다. 전부 가상 값이다.
BUDGET_MS = 8.0
LIMIT_PCT = 6.0
N = 1000

# 2단계: 초과율을 세는 함수를 만든다
# 추론 시간은 로그정규(중앙값 3.0ms, 흩어짐 0.55)로 잡는다.
def exceed_rate(extra_ms, seed=20260917):
    """요청 N 건 중 예산 8ms 를 넘긴 비율(%). extra_ms 는 새 피처가 더하는 시간."""
    rnd = random.Random(seed)
    mu = math.log(3.0)
    over = 0
    for _ in range(N):
        t = rnd.lognormvariate(mu, 0.55) + extra_ms
        over += t > BUDGET_MS
    return 100 * over / N

# 3단계: 더하는 시간을 바꿔 가며 판정한다
# 새 피처의 조회가 요청마다 더하는 시간을 0 부터 1.0ms 까지 바꿔 본다.
print(f"{'새 피처가 더하는 시간':>14}  {'8ms 초과율':>8}  판정 (기준 {LIMIT_PCT}% 이하)")
for extra in (0.0, 0.2, 0.5, 1.0):
    rate = exceed_rate(extra)
    verdict = "통과" if rate <= LIMIT_PCT else "탈락"
    print(f"{extra:>12.1f}ms  {rate:>7.1f}%  {verdict}")

# 출력:
# 3단계 뜻: 새 피처가 0.5ms 를 더하면 초과율이 3.2% 에서 4.8% 로 올라도 통과하고, 1.0ms 를 더하면 6.3% 로 기준을 넘어 탈락한다.
#   새 피처가 더하는 시간   8ms 초과율  판정 (기준 6.0% 이하)
#          0.0ms      3.2%  통과
#          0.2ms      3.6%  통과
#          0.5ms      4.8%  통과
#          1.0ms      6.3%  탈락
```

출력의 0.0ms 줄은 새 피처가 시간을 더하지 않을 때로, 이때도 요청의 3.2% 는 8ms 를 넘습니다. 더하는 시간이 0.2ms 면 초과율은 3.6% 입니다. 지훈 씨의 피처는 조회 한 번에 0.5ms 를 더해 초과율을 3.2% 에서 4.8% 로 올렸지만 4.8% 는 기준 6% 아래라 통과했습니다. 그런데 마지막 1.0ms 줄의 초과율은 6.3% 로 기준 6% 를 넘어 탈락이므로, 조회를 두 번 해서 0.5ms 의 두 배인 1.0ms 를 더하는 피처였다면 이미지는 여기서 멈췄습니다.

이 부하 시험은 「코드는 맞는데 서비스가 느려지는 커밋」을 잡는데, 그런 커밋은 유닛 테스트 214개를 전부 통과해도 여기서 걸립니다. 이 초과율은 서버 한 대에 요청 1,000건을 보낸 값입니다. 실제 서버에서 12대가 요청을 나눠 받을 때 초과율이 어떻게 달라지는지는 서빙 지연 편의 5절에서 다룹니다.

정확도를 0.001 올리는 피처라도 초과율을 기준 6% 위로 올리면 그 피처는 서버에 오를 수 없으므로 피처를 추가할 때는 조회 시간도 같이 측정합니다. 이미지가 서버에 오르기 전에 거치는 마지막 검사는 다음 절에서 봅니다.

## 6. 셋째 검사: 이미지 검사

**이미지 검사는 코드가 아니라 이미지 자체를 보는 검사로, 층 안에 알려진 위험이 있는 라이브러리가 없는지와 이미지 크기가 1.5GB 를 넘지 않는지를 확인합니다.**

코드가 맞아도 그 아래 층에 문제가 있을 수 있으므로, 앞의 두 검사가 「이 코드가 일을 제대로 하나」를 본 뒤에도 이미지 검사가 「이 이미지를 서버 12대에 올려도 되나」를 따로 확인합니다.

이미지 검사는 두 가지를 봅니다. 첫째는 취약점(라이브러리에 이미 알려진 보안 문제)입니다. 이미지 안에 든 라이브러리의 목록을 뽑아 알려진 문제가 있는 버전이 섞여 있는지 확인하고 심각한 취약점이 하나라도 있으면 탈락시킵니다. 둘째는 크기입니다. 이 팀은 이미지 크기의 상한을 1.5GB 로 두는데, 지훈 씨의 이미지는 2절 표의 추론 이미지 합계와 같은 1.1GB 로 상한보다 작아 통과했습니다.

크기를 보는 데에도 까닭이 있습니다. 서버는 뜰 때 이미지를 내려받으므로 이미지가 커지면 내려받는 시간이 늘어납니다. 배포 때는 서버 12대 가운데 2대씩 바꾸는 동안 나머지 10대가 요청을 모두 받으므로 내려받는 시간이 길수록 10대만으로 요청을 받는 시간도 길어져 위험합니다. 이 배포 장면은 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편 8절에서 다룹니다.

세 검사가 확인하는 대상, 통과 조건, 걸리는 시간, 여기서 걸리는 커밋을 한 표로 모으면 아래와 같습니다.

| 검사 | 확인 대상 | 통과 조건 | 걸리는 시간 | 여기서 걸리는 커밋 |
|---|---|---|---|---|
| 첫째, 유닛 테스트 | 함수 하나하나의 답 | 214개 전부 통과 | 48초 | 계산이 틀린 코드 |
| 둘째, 계약 테스트 | 요청 응답의 모양과 속도 | 필드 12개 일치, 8ms 초과율 6% 이하 | 2분 30초 | 모양을 바꾸거나 느려진 코드 |
| 셋째, 이미지 검사 | 이미지 층의 위험과 크기 | 심각 취약점 0, 1.5GB 이하 | 52초 | 위험한 라이브러리, 커진 이미지 |

세 검사 가운데 맨 앞에는 48초로 가장 싼 유닛 테스트가 놓였습니다. 계약 테스트는 서버를 켜야 해서 가장 비싼데, 유닛 테스트에서 걸린 커밋은 계약 테스트까지 가지 않으므로 그만큼 CI 시간이 줄어듭니다. 후보 광고를 거를 때 싼 필터를 먼저 쓰는 것과 같은 까닭입니다.

지훈 씨의 커밋은 세 검사를 모두 지나 이미지 `pctr-serve:2026.09.17-a3f9c21` 로 저장소에 올라갔습니다. 이 이미지를 서버 12대에 올리는 일은 CI 와 다른 절차인 배포이고 [모델 배포와 롤백](post.html?id=model-deployment-rollback) 편에서 다룹니다. 그 전에 다음 절에서는 세 검사가 두 무대(담장 안과 열린 RTB)에서 어떻게 다른지를 봅니다.

## 7. 요청을 보내는 곳에 따른 CI 검사의 차이

**담장 안에서는 이미지 하나가 우리 게이트웨이(바깥 요청이 처음 들어오는 입구) 뒤의 서버 12대로 가지만 열린 RTB 에서는 입찰 서버(입찰가를 내는 서버)가 여러 거래소(광고 자리를 경매에 부치는 곳)의 형식에 맞춰야 해서 계약 테스트가 거래소 수만큼 늘어납니다.**

검사 3가지는 두 무대에 모두 있지만 둘째 검사가 확인하는 계약을 누가 정하느냐는 두 무대가 다릅니다.

### 담장 안: 우리 팀이 정하는 계약 [무대: 닫힌 생태계]

한 회사가 앱, API 서버, 모델 서버를 모두 가진 담장 안에서는 요청과 응답의 모양을 우리 팀이 정합니다. 응답에 어떤 필드 12개를 넣을지, 예산을 8ms 로 할지도 우리가 정합니다. 계약 테스트도 한 벌(테스트 한 세트)뿐이고 그 상대는 우리 API 팀 하나입니다. 이 블로그의 저자가 일하는 곳이 이 무대입니다. 이 글의 카드 그림도 모두 이 상태를 보여 줍니다. 배포할 곳도 게이트웨이 뒤 한 군데라 이미지 하나가 서버 12대로 갑니다.

### 열린 RTB: 거래소가 정하는 계약 [무대: 열린 RTB]

열린 RTB 의 입찰 서버는 다른 회사의 거래소가 보내는 요청에 답하는데, 요청 형식은 거래소가 정한 OpenRTB(거래소와 입찰 서버가 주고받는 요청과 응답의 표준 형식) 버전을 따르고 응답 시간도 거래소가 정합니다. 응답 시간은 보통 100ms 안쪽이고 거래소마다 조금씩 다릅니다.

거래소 다섯 곳에 연결돼 있으면 둘째 검사인 계약 테스트도 거래소마다 한 벌씩 다섯 벌이 되고 그중 한 거래소가 형식을 바꾸면 그 거래소의 벌만 걸립니다. 그래서 열린 RTB 의 CI 에서는 계약 테스트가 가장 크고 가장 자주 바뀝니다. 거래소가 무엇이고 요청이 어떻게 오는지는 [DSP, SSP, 광고 거래소](post.html?id=dsp-ssp-exchange) 편에서 다룹니다.

| 항목 | 담장 안 | 열린 RTB |
|---|---|---|
| 요청과 응답의 모양을 정하는 곳 | 우리 팀 | 거래소마다 |
| 계약 테스트 벌 수 | 하나 | 연결된 거래소 수만큼 |
| 응답 예산을 정하는 곳 | 우리 (모델 호출 8ms) | 거래소 (보통 100ms 안쪽) |
| 요청이 들어오는 곳 | 우리 게이트웨이 하나 | 거래소마다 연결 하나 |

## 한눈 정리

| 질문 | 한 줄 답 |
|---|---|
| 노트북과 서버가 왜 다른 값을 내나 | 코드 아래 층(라이브러리 버전)이 다르기 때문입니다 |
| 이미지가 무엇인가 | 기본 리눅스부터 코드까지 층을 쌓아 빌드한 파일 하나입니다 |
| 이미지에 무엇이 안 들어가나 | 모델 파일입니다. 매일 바뀌니 서버가 뜰 때 따로 내려받습니다 |
| 이미지 크기는 무엇이 정하나 | 라이브러리 층입니다. 코드는 12MB 로 가장 작습니다 |
| CI 가 무엇인가 | 커밋마다 이미지를 만들고 검사 3가지를 거치게 하는 자동 절차입니다 |
| 검사 3가지는 무엇인가 | 유닛 테스트, 계약 테스트, 이미지 검사입니다 |
| 하나라도 걸리면 | 이미지가 저장소에 오르지 않습니다. 6분 20초를 다 돌지 않고 걸린 단계에서 멈춥니다 |
| 이미지 이름은 왜 그렇게 긴가 | 날짜와 커밋 해시가 들어 있어 어느 코드인지 이름으로 압니다 |

## 헷갈리기 쉬운 점

- **이미지는 코드가 아닙니다.** 코드는 이미지의 맨 위 한 층일 뿐이지만 「내 노트북에서는 되는데」라는 말은 그 아래 나머지 층이 노트북과 서버에서 달라서 나옵니다.
- **모델 파일은 이미지에 없습니다.** 이미지는 코드가 바뀔 때만 새로 만들지만 모델은 매일 바뀌므로 바뀌는 주기가 다른 이미지와 모델을 따로 둡니다.
- **유닛 테스트를 다 통과해도 서비스는 느려질 수 있습니다.** 느려지는 커밋은 계약 테스트의 부하 시험이 잡습니다.
- **계약 테스트의 초과율은 서버 한 대의 값입니다.** 서버 12대가 요청을 나눠 받는 실제 상황의 초과율과는 다른 값입니다.
- **CI 가 통과했다고 서버에 올라간 것이 아닙니다.** CI 는 이미지를 저장소에 올리는 데서 끝나며 서버에 올리는 배포는 모델 배포와 롤백 편에서 다룹니다.
