지훈이 입사 나흘째에 첫 연동을 맡았다. 광고주 한 곳이 하루에 쓰는 광고비가 ₩5,000,000이다. 그 돈으로 산 전환 1,000건을 받아 정산에 넣는 일이고, 요청을 보내는 코드는 30분이면 쓴다.

막히는 것은 그다음이다. 답이 안 오면 다시 보내야 하는데, 그러면 그 전환이 한 건으로 남는지 두 건으로 남는지를 문서가 말해 주지 않는다. 타임아웃도 인증키도 문서 밖의 일이다.

**같은 요청을 두 번 보내면 전환은 한 건인가 두 건인가?**

두 번 보내도 한 건으로 남게 미리 맞춰 두는 약속을 **멱등성**이라 부른다. 안 맞춰 두면 전환당 비용이 실제보다 싸게 리포트에 찍히고, 그 숫자를 본 광고주는 예산을 더 붓는다. 코드는 멀쩡한데 돈이 잘못 움직인다.

> **한 줄 요약:** 같은 API 라도 부르는 쪽이 남의 기기냐 우리 서버냐에 따라 지켜야 할 것이 갈린다. 첫 주에 가장 비싼 약속이 멱등성이고, 빼먹으면 전환 1,000건이 1,180건으로 부풀어 예산이 잘못 움직인다.

이 글의 숫자는 전부 설명을 위해 지어낸 값이다. 그리고 이 글에서 **우리**는 전환 수집 API 를 운영하는 쪽이다. 역할이 뒤집히는 자리에서는 그때마다 밝힌다.

이 글은 HTTP 메서드와 상태코드를 이미 아는 사람을 본다. 그것부터 낯설면 [API 기초](post.html?id=api-basics) 편을 먼저 보면 된다.

## 1. "API 붙여 주세요" 를 받으면 먼저 물을 것

**부르는 쪽이 남의 기기냐 우리 서버냐. 이 한 줄이 비밀키·인증·버전·재시도를 통째로 가른다.**

API 는 주소와 형식을 미리 맞춰 둔 묶음이다. 앱이 부르는 것을 client to server, 우리 서버가 부르는 것을 server to server 라 한다. 같은 주소라도 이 구분 하나가 나머지 결정을 전부 정한다.

| 축 | client to server | server to server |
|---|---|---|
| 부르는 쪽 | 앱 · 브라우저 — 남의 기기 | 우리 서버 · 상대 서버 |
| 비밀키 | 둘 수 없다 | 둘 수 있다 |
| 인증 | 사용자 토큰(로그인) | 서비스 자격증명 · 인증서 · 서명 |
| 요청에 실려 온 값 | 하나도 못 믿는다 | 계약 안이면 믿는다 |
| 트래픽 | 예측 불가 · 갑자기 몰린다 | 대체로 예측 가능 |
| 버전 | 옛 앱이 몇 년 남는다 | 날짜를 잡고 같이 올린다 |
| 재시도 | 네트워크가 끊긴다는 전제 | 정해 둔 시간 예산 안에서 |

**비밀키 줄이 첫 갈림길이다.** 앱에 넣은 문자열은 그 앱을 받은 사람 모두가 갖는다. 한 번 새면 회수 비용이 무한이라, 아예 안 두는 쪽으로 설계한다.

**요청 값 줄은 바로 매출에 닿는다.** 전환 금액을 앱이 보내게 두면 중간에서 ₩39,000을 ₩3,900,000으로 고칠 수 있다. 매출이 부풀고 그 매출로 예산이 움직이니, 금액은 우리 주문 테이블에서 다시 읽는다.

**버전 줄은 몇 달 뒤에 드러난다.** 앱은 안 올리는 사용자가 몇 년씩 남아, 되돌리는 비용을 3절에서 숫자로 잰다.

### 광고 쪽 연동 셋을 같은 축에 놓아 본다

실제로 붙이게 되는 연동 셋을 그 축에 얹어 보자. 남의 앱에 심게 하는 코드 묶음을 SDK, 전환을 대신 재 주는 외부 측정 회사를 MMP 라 부른다.

| 물음 | 앱 SDK → 수집 서버 | bidder → 거래소 | MMP → 전환 수집 API |
|---|---|---|---|
| 부르는 쪽 | 사용자 기기 | 우리 서버 | 상대 서버 — 우리는 받는다 |
| 종류 | client to server | server to server | server to server |
| 규모 | 초당 2,639건 | 응답까지 12ms | 하루 1,000건 |
| 비밀키를 둘 수 있나 | 안 된다 | 된다 | 된다 |
| 응답이 늦으면 | 앱이 쌓아 뒀다 나중에 | 12ms 넘으면 거래소가 버린다 | MMP 가 몇 시간 뒤 다시 보낸다 |
| 인증 값이 새면 | 앱에서 뽑힌다 · 회수 불가 | 인증서 교체로 끝난다 | 키 재발급으로 끝난다 |
| 필드를 하나 지우면 | 옛 앱이 몇 년 깨진다 | 날짜 잡고 같이 올린다 | 상대 일정에 맞춘다 |

초당 2,639건은 하루 노출 로그 2억 2,800만 줄을 86,400초로 나눈 값이다. 12ms 는 [요청이 서비스까지 가는 길](post.html?id=gateway-ingress-router)에서 정한 응답 예산이다.

전환 포스트백만 규모가 다르다. 하루 1,000건뿐이지만 이 줄들이 정산 매출과 pCVR 학습 라벨을 동시에 만든다. 인증 값이 새도 서버끼리는 재발급 비용이 하루면 끝나는데, 배포된 앱 안의 값은 회수할 수단이 없다.

### 무엇으로 주고받나 — 규약 다섯

"API 를 붙인다"는 말 뒤에는 다섯 중 하나가 있다. 넷은 우리가 부르는 쪽이거나 우리가 API 를 내주는 쪽이고, 하나만 방향이 거꾸로다.

| 규약 | 어디서 쓰나 | 브라우저에서 바로 되나 | 언제 고르나 |
|---|---|---|---|
| REST/HTTP + JSON | 양쪽 다 | 된다 | 기본값 · 상대가 누구든 붙는다 |
| gRPC | 서버 사이 | 안 된다 | 우리 서비스끼리 · 초당 수만 건 |
| GraphQL | 주로 client to server | 된다 | 화면마다 필요한 것이 다를 때 |
| webhook(콜백) | 서버 사이 | 안 된다 | 결과가 언제 날지 모를 때 |
| 배치 파일 | 서버 사이 | 안 된다 | 하루치를 한 번에 · 정산 |

**webhook 만 방향이 거꾸로다. 여기서부터 우리는 받는 쪽이다.** 상대가 우리를 부르니 우리가 서버를 열고 공개 주소를 넘긴다. 인증·중복 제거·순서 뒤바뀜을 전부 받는 쪽이 감당하고, 이 글 2~6절이 그 이야기다.

**배치 파일도 규약이다.** 컬럼 순서·인코딩·타임존이 전부 계약이다. 하루가 끝나면 이 파일로 매출을 맞춰 보는 것을 정산에서 대사라 부른다.

우리 수집 API 를 REST 로 두는 결정도 여기서 나온다. 붙는 쪽이 제각각이면 어디서나 되는 것이 첫 조건이고, gRPC 는 앞에 변환 프록시를 세워야 해 운영 비용이 는다.

## 2. 응답이 답해야 하는 것 — 세 자리 숫자와 목록

**상태코드는 "누가 고쳐야 하나"와 "다시 보내도 되나"를 세 자리로 답한다. 200 안에 에러를 담으면 그 답이 사라진다.**

응답 맨 앞 세 자리를 HTTP 상태코드라 부른다. 2xx 는 처리됐다, 4xx 는 부르는 쪽이 고쳐야 한다, 5xx 는 받는 쪽이 고쳐야 한다는 뜻이다. 이 셋만 지켜도 재시도 규칙과 알람 규칙이 정해져 장애 대응 비용이 준다.

| 코드 | 뜻 | 누가 고쳐야 하나 | 다시 보내도 되나 |
|---|---|---|---|
| 200 OK | 처리했고 본문이 있다 | — | — |
| 201 Created | 새 자원을 만들었다 | — | — |
| 202 Accepted | 접수만 했다 · 결과는 나중에 | — | 멱등키가 있을 때만 |
| 400 Bad Request | 요청 형식이 틀렸다 | 부르는 쪽 | 아니다 · 그대로 또 틀린다 |
| 401 Unauthorized | 자격증명이 없거나 틀렸다 | 부르는 쪽 | 갱신한 뒤 한 번만 |
| 404 Not Found | 그런 자원이 없다 | 부르는 쪽 | 아니다 |
| 409 Conflict | 같은 키로 다른 내용이 왔다 | 부르는 쪽 | 아니다 |
| 422 Unprocessable | 형식은 맞는데 값이 규칙 위반 | 부르는 쪽 | 아니다 |
| 429 Too Many Requests | 초당 허용을 넘겼다 | 부르는 쪽 | `Retry-After` 만큼 뒤에 |
| 500 · 502 · 503 · 504 | 받는 쪽이 터졌거나 밀렸다 | 받는 쪽 | 된다 · 간격을 늘려 가며 |

400 은 JSON 이 깨졌거나 필수 필드가 없는 경우이고, 422 는 형식은 멀쩡한데 값이 규칙에 안 맞는 경우다. 둘을 안 가르기로 결정했으면 문서에 그렇게 적으면 된다.

**"200 안에 에러를 담지 마라"가 이 절의 핵심이다.** 이런 응답을 실제로 자주 본다.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"result":"fail","message":"invalid click_id"}
```

이 한 줄 때문에 네 곳이 동시에 눈이 먼다. 라이브러리는 성공으로 보고 재시도에서 빼고, 실패율 그래프는 평평하고, 로드밸런서도 정상으로 본다. 정산 매출이 안 맞을 때까지 아무도 모르고, 그 사이 틀린 숫자로 예산이 움직인다.

에러는 상태코드로 알리고, 본문에는 기계가 읽을 것과 사람이 읽을 것을 같이 담는다.

```json
{
  "error": {
    "code": "INVALID_CLICK_ID",
    "message": "click_id 'ck-77' was not found",
    "field": "click_id",
    "request_id": "req-8f21",
    "retryable": false
  }
}
```

`code` 는 부르는 쪽이 분기에 쓴다. 사람이 읽는 문구로 분기하면 그 문구를 다듬는 순간 상대 코드가 깨지고, 요청 번호가 없으면 실패한 그 건을 로그에서 못 찾는다.

목록을 몇 개씩 끊어 넘기는 방식을 페이지네이션이라 부른다. 전환 리포트 5만 행을 1,000행씩 50번에 나눠 받는 20분 동안 새 전환이 들어오고 취소가 지워지는데, 그 사이 정산 매출이 어긋난다.

offset 은 "앞에서 몇 개를 버리고 그다음"이라 말해서, 새 행이 맨 앞에 끼어들면 이미 읽은 행이 다시 나온다. cursor 는 "이 행 다음부터"라 말해 기준이 자리라서 안 밀린다.

| 방식 | 두 번 읽은 행 | 못 읽은 행 | 50번째 페이지 응답 | 첫 페이지로 돌아가기 |
|---|---|---|---|---|
| offset | 12 | 3 | 380ms | 쉽다 |
| cursor | 0 | 0 | 40ms | 커서를 따로 보관해야 한다 |

응답 시간이 갈리는 이유는 DB 가 하는 일이 다르기 때문이다. `offset=49000` 은 4만 9천 행을 세어 버린 다음 1,000행을 준다. 커서는 미리 적어 둔 목차에서 그 자리를 바로 집고, 페이지가 뒤로 갈수록 이 비용 차이가 벌어진다.

그래서 이렇게 결정한다. 사람이 페이지 번호를 누르는 목록은 offset, 기계가 훑는 정산용 목록은 커서다. 목록 응답은 객체로 감싸야 나중에 필드를 더할 자리가 생긴다.

## 3. 필드를 더하는 것과 빼는 것

**응답에 필드를 더하는 것은 대체로 안전하고, 빼는 것은 안전한 적이 없다. 이 비대칭이 버전 규칙의 뿌리다.**

이 절은 우리가 API 를 내주는 쪽일 때다. 반대로 우리가 부르는 쪽일 때 할 일은 표 아래에 따로 적는다.

규약이 한 번 나가면 상대 코드가 그것을 전제로 짜인다. 잘못 고치면 상대 쪽 매출이 그날로 비니, 바꿀 때마다 "옛 상대가 안 깨지나"를 먼저 본다.

| 바꾸는 것 | 옛 상대에게 무슨 일이 | 호환인가 |
|---|---|---|
| 응답에 필드 추가 | 모르는 필드는 무시한다 | 대체로 호환 |
| 응답에서 필드 삭제 | 그 필드를 읽던 코드가 죽는다 | 아니다 |
| 응답 필드 타입 변경 | 값을 못 바꾸거나 조용히 0이 된다 | 아니다 |
| 정해진 값 목록에 하나 추가 | 미지 값 처리가 없으면 죽는다 | 조건부 |
| 요청에 선택 필드 추가 | 안 보내면 그만이다 | 호환 |
| 요청에 필수 필드 추가 | 옛 상대가 전부 400 을 받는다 | 아니다 |
| 기본값 변경 | 조용히 결과 개수가 달라진다 | 아니다 |

첫 줄의 "대체로"에 함정이 있다. 받은 글자를 프로그램이 쓰는 값으로 바꾸는 부분을 파서라 한다. 모르는 필드를 무시할지는 이 파서 설정에 달렸고, 엄격하면 예외 하나로 연동이 중단돼 하루치 매출이 빈다. 우리가 부르는 쪽이면 이 설정을 미리 꺼 둔다.

:::deep 더 깊이 — 그 설정의 실제 이름과 기본값
자바 Jackson 에서는 `FAIL_ON_UNKNOWN_PROPERTIES` 가 그 자리다. Jackson 자체에서는 켜져 있고 스프링 부트가 그것을 꺼 주니, 이름과 기본값은 외우지 말고 직접 확인한다. 모르는 필드가 섞인 응답을 파서에 넣어 보고, 예외가 나면 켜져 있는 것이다.
:::

값을 정해진 몇 개로 제한한 목록을 enum 이라 한다. 두 값만 있다고 짜인 코드에 세 번째 값이 오면 갈 곳이 없으니, "모르는 값은 무시하고 기록만 남긴다"로 미리 정해 둔다.

**필드를 지울 때는 지우기 전에 세어 본다.** 아래는 앱 SDK 가 쓰는 필드 하나를 지우기 직전에 본 버전 분포다.

| 앱 버전 | 트래픽 비중 | 이 필드를 읽나 |
|---|---|---|
| 5.2 (최신) | 41% | 아니오 |
| 5.1 | 27% | 아니오 |
| 5.0 | 18% | 예 |
| 4.x | 11% | 예 |
| 3.x 이하 | 3% | 예 |
| **합계** | **100%** | 32% 가 읽는다 |

옛 필드를 읽는 앱이 32% 이고, 초당 요청으로 바꾸면 약 844건이다. 지우는 순간 초당 844건이 깨지고 그 사용자에게는 복구 수단이 없으니, 새 필드를 먼저 내보내고 지우는 결정은 비중이 떨어진 뒤로 미룬다.

**버전은 경로나 헤더에 붙인다.** `/v2/conversions` 를 새로 파면 로그에서 바로 갈리고, 헤더로 하면 상대에게 주소를 바꿔 달라 부탁할 일이 없다. 어느 쪽이든 기본값은 가장 오래된 버전이 된다.

그래서 새 버전을 낼 때 같이 결정할 것은 "옛 버전을 언제 중단하나" 하나다. 서버끼리면 몇 주, 앱이면 몇 분기다. 날짜를 안 적어 두면 운영 비용이 계속 쌓인다.

## 4. 멱등성 — 재시도가 전환 1,000건을 1,180건으로 만든다

**재시도는 반드시 하게 된다. 요청마다 고유한 값을 안 붙이면 그 재시도가 전환 1,000건을 1,180건으로 만든다.**

멱등은 "몇 번을 해도 결과가 한 번 한 것과 같다"는 뜻이다. 요청 방식마다 그 성질이 있는 것과 없는 것이 갈린다.

| 요청 | 두 번 보내면 | 왜 그런가 |
|---|---|---|
| `GET` 전환 한 건 읽기 | 같은 것을 두 번 읽는다 | 상태를 안 바꾼다 |
| `PUT` 캠페인 예산을 50,000 으로 | 예산은 50,000 그대로 | 결과 상태를 통째로 지정한다 |
| `DELETE` 캠페인 지우기 | 이미 없다 · 결과는 같다 | 지운 상태는 또 지워도 같다 |
| `POST` 전환 기록하기 | 전환이 두 줄 생긴다 | 부를 때마다 새 자원을 만든다 |
| `PATCH` 캠페인 예산 +10,000 | 예산이 20,000 늘어난다 | 상대적 변경이라 쌓인다 |

`POST` 와 `PATCH` 만 멱등이 아니다. 하필 전환 기록·결제·주문이 전부 `POST` 라서, 매출이 걸린 요청만 골라 위험한 쪽에 서 있다.

**문제는 재시도를 안 할 수가 없다는 데 있다.** 응답이 안 왔을 때 부르는 쪽이 아는 것은 "답을 못 받았다" 하나뿐이다. 요청이 닿기 전에 끊긴 것인지, 서버가 이미 기록해 놓고 응답만 끊긴 것인지 가를 방법이 없다.

그래서 어느 쪽을 골라도 손해가 난다. 안 보내면 안 닿았던 건이 사라져 정산 매출에서 빠지고, 보내면 이미 기록된 건이 한 줄 더 생겨 전환이 부푼다. 답은 "보내되 같은 건임을 받는 쪽이 알아보게 한다"다.

알아보게 하는 값이 멱등키다. 부르는 쪽이 요청마다 고유한 값을 붙이고 재시도에도 같은 값을 쓰면, 받는 쪽이 "아까 그 요청"이라고 판정해 새로 기록하지 않는다. 안 붙였을 때 얼마나 벌어지는지 전환 1,000건으로 따라가 보자.

```python
# 재시도가 전환을 몇 건 부풀리나 — 멱등키가 없을 때와 있을 때.
# 광고주 한 곳이 하루에 보내는 전환 포스트백 1,000건을 그대로 따라간다.
# 서버는 요청을 받으면 항상 기록에 성공한다. 다만 응답이 돌아오는 길에서 유실된다.
# 부르는 쪽은 응답을 못 받으면 최대 3번까지 다시 보낸다.
# 모든 숫자는 설명을 위해 지어낸 값이다.
from unicodedata import east_asian_width

LOST = [150, 25, 5, 0]      # 회차별 '서버는 기록했는데 응답이 유실된' 건수
AD_SPEND = 5_000_000        # 이 광고주가 하루에 쓴 광고비(원)

pending = [f"O-{i:05d}" for i in range(1000)]   # 광고주 쪽 주문번호. 이것이 멱등키가 된다
naive_rows = []             # 멱등키를 안 보는 서버의 전환 테이블
idem_rows = []              # 멱등키를 보는 서버의 전환 테이블
idem_seen = {}              # 멱등키 → 첫 응답. 두 번째부터는 이것을 그대로 돌려준다
log = []

for attempt, lost in enumerate(LOST, start=1):
    sent = len(pending)
    for key in pending:
        naive_rows.append(key)          # 키를 안 보면 요청이 올 때마다 한 줄이 늘어난다
        if key not in idem_seen:        # 처음 보는 키일 때만 새 줄을 만든다
            idem_seen[key] = "201 Created"
            idem_rows.append(key)
    log.append((attempt, sent, lost, len(naive_rows), len(idem_rows)))
    pending = pending[:lost]            # 응답을 못 받은 건만 다시 보낸다

# 한글은 화면에서 두 칸을 먹는다. 칸수를 직접 세어 맞춘다
def w(s):
    return sum(2 if east_asian_width(c) in "WF" else 1 for c in s)

def row(cells, widths):
    out = ""
    for c, width in zip(cells, widths):
        out += " " * (width - w(str(c))) + str(c)
    print(out)

WID = [8, 12, 12, 16, 16]
row(["회차", "보낸 건수", "응답 유실", "키 없음 누적", "키 있음 누적"], WID)
for attempt, sent, lost, n, i in log:
    row([attempt, f"{sent:,}", f"{lost:,}", f"{n:,}", f"{i:,}"], WID)

real, counted = len(idem_rows), len(naive_rows)
print()
print(f"실제 전환 {real:,}건 → 리포트에 잡힌 전환 {counted:,}건 ({counted/real - 1:+.1%})")
print(f"진짜 CPA {AD_SPEND/real:,.0f}원 → 리포트 CPA {AD_SPEND/counted:,.0f}원"
      f" ({AD_SPEND/counted - AD_SPEND/real:,.0f}원)")
print(f"중복 요청 {counted - real}건은 전부 성공 응답을 받았다. 에러 로그에는 한 줄도 안 남는다.")

# 출력:
#     회차   보낸 건수   응답 유실    키 없음 누적    키 있음 누적
#        1       1,000         150           1,000           1,000
#        2         150          25           1,150           1,000
#        3          25           5           1,175           1,000
#        4           5           0           1,180           1,000
#
# 실제 전환 1,000건 → 리포트에 잡힌 전환 1,180건 (+18.0%)
# 진짜 CPA 5,000원 → 리포트 CPA 4,237원 (-763원)
# 중복 요청 180건은 전부 성공 응답을 받았다. 에러 로그에는 한 줄도 안 남는다.
```

전환 한 건에 든 광고비를 CPA 라 부른다. 진짜 CPA 는 ₩5,000인데 리포트에는 ₩4,237로 떠서, 전환당 비용이 ₩763 싸 보인다. 이 차이가 예산 결정을 뒤집는다.

광고주는 성과가 좋다고 보고 예산을 늘리는데, 늘린 예산으로 산 전환도 같은 비율로 부풀어 있다. 반대로 중복을 뒤늦게 걷어 내면 멀쩡한 캠페인을 중단하는 결정이 나오기도 한다.

더 나쁜 것은 이 180건이 에러가 아니라는 점이다. 전부 성공 응답을 받아 알람이 울릴 자리가 없고, pCVR 모델은 이 중복이 섞인 라벨을 그대로 학습한다([pCVR 모델링](post.html?id=pcvr-modeling) 2절).

**멱등키는 부르는 쪽이 만든다.** 받는 쪽이 만들면 두 번째 요청이 재시도인지 새 건인지 못 가른다. 만드는 규칙은 넷이다.

- 그 건에만 붙어 있는 번호가 있으면 그것을 쓴다. 주문번호 `O-00042` 가 그 예다.
- 그런 번호가 없으면 고유 문자열을 만들고, 재시도 내내 같은 값을 쓴다.
- 재시도마다 새로 만들면 키가 없는 것과 같다. 이 실수가 가장 흔하다.
- 본문 해시만으로 만들지 않는다. 같은 금액의 진짜 두 번 결제를 하나로 먹는다.

마지막 줄이 갈리는 자리다. 같은 사람이 ₩39,000짜리를 두 번 살 수도 있는데, 한 번 산 것이 두 번 도착한 것과 본문만으로는 구분되지 않는다.

```http
POST /v1/conversions HTTP/1.1
Host: api.example.com
Content-Type: application/json
Idempotency-Key: O-00042

{"click_id":"ck-8f21","order_id":"O-00042","value":39000,"ts":1786002501}
```

**받는 쪽은 키를 저장한다.** 저장할 것은 키·처리 결과·응답 상태코드·만료 시각 넷이다. 같은 키가 다시 오면 저장해 둔 응답을 그대로 돌려주니, 두 번째 요청도 201 을 받고 정산 매출은 한 건으로 남는다.

여기까지 해도 구멍이 하나 남는다. 첫 요청을 처리하는 **도중에** 재시도가 오면, 두 번째도 "그런 키 없음"을 보고 같이 처리에 들어간다. 둘이 동시에 들어와 서로를 못 보는 이 상태를 경쟁 조건이라 부르고, 이때는 키를 붙였는데도 전환이 두 줄 생긴다.

막는 방법은 키를 "처리 중·처리 끝·없음" 셋으로 두는 것이다. 처리를 시작하는 순간 "처리 중"을 먼저 적으면 두 번째 요청이 물러난다. 그 적어 두기를 조회와 삽입 둘로 나누면 사이가 다시 벌어지니, 조회 없이 삽입 한 번으로 끝낸다.

:::deep 더 깊이 — 멱등 저장소의 상태 셋과 만료
같은 키가 또 왔을 때 무엇을 돌려줄지가 상태마다 다르다.

| 상태 | 언제 | 같은 키가 또 오면 |
|---|---|---|
| `in_progress` | 처리 시작 직후 기록 | 409 를 돌려준다 · 잠시 뒤 다시 오게 |
| `done` | 처리 끝 · 응답까지 저장 | 저장된 응답을 그대로 재생 |
| (없음) | 처음 보는 키 | `in_progress` 로 만들고 처리 시작 |

조회하지 말고, 같은 값이 이미 있으면 실패하도록 걸어 둔 열에 삽입 한 번만 시도한다.

```sql
CREATE TABLE idempotency (
  key         VARCHAR(64) PRIMARY KEY,
  state       VARCHAR(16) NOT NULL,
  status_code INT,
  body        TEXT,
  expires_at  TIMESTAMP NOT NULL
);
-- 삽입이 성공하면 이 요청이 첫 번째다. key 가 이미 있어 실패하면 다른 요청이 먼저다.
INSERT INTO idempotency (key, state, expires_at)
VALUES ('O-00042', 'in_progress', NOW() + INTERVAL '24 hours');
```

만료 시간이 곧 "재시도는 여기까지"라는 계약이다. 상대 재시도 정책이 7일이면 받는 쪽 키 만료도 7일이어야 하고, 어긋나면 중복이 조용히 생긴다.
:::

## 5. 타임아웃과 재시도 — 지터가 없으면 두 번째 장애가 난다

**타임아웃을 안 걸면 상대의 느림이 우리의 정지가 된다. 재시도 시각을 흩지 않으면 그 재시도가 죽은 서버를 한 번 더 죽인다.**

미리 열어 둔 연결 묶음을 커넥션 풀이라 한다. 동시에 물려 있는 연결 수는 초당 호출 수에 평균 응답 시간을 곱한 값이고, 이 곱이 풀 크기를 넘는 순간 서비스가 멈춘다. 우리가 상대를 초당 100번 부르고 풀에 연결이 200개 있다고 하자.

| 상대 응답 시간 | 초당 호출 | 동시에 물리는 연결 | 풀 200개 |
|---|---|---|---|
| 39ms (평소) | 100 | 3.9 | 여유 |
| 400ms (상대에게 건 상한) | 100 | 40 | 여유 |
| 2초 | 100 | 200 | 딱 찬다 |
| 5초 | 100 | 500 | 300건이 대기한다 |
| 30초 (타임아웃 없음) | 100 | 3,000 | 전면 정지 |

마지막 줄이 중요하다. 상대는 죽지 않았고 느려졌을 뿐인데, 우리는 연결을 다 써서 무관한 요청까지 같이 멈춘다. 타임아웃을 안 걸면 상대의 지연 하나가 우리 서비스 전면 중단이 된다.

타임아웃은 한 개가 아니라 셋이다. 연결까지, 응답 바이트까지, 전체를 통틀어 기다리는 시간을 각각 잡는다. 우리 전환 HTTP 클라이언트는 200ms · 400ms · 700ms 로 결정했고, 앞의 둘을 더한 값이 예산 안에 든다.

**재시도해도 되는 실패를 가르는 기준은 하나다.** "다시 보내면 결과가 달라질 수 있나"이다. 400 은 다시 보내도 또 400 이라 재시도 비용만 버리지만, 503 은 성공할 수 있다.

| 실패 종류 | 서버가 처리했을 수 있나 | 재시도 |
|---|---|---|
| 연결 자체가 안 됨 | 아니다 | 안전하다 |
| 연결 뒤 응답 대기 중 타임아웃 | 그렇다 | 멱등키가 있을 때만 |
| 502 · 503 · 504 | 502 · 504 는 그럴 수 있다 | 멱등키가 있을 때만 |
| 429 | 아니다 | `Retry-After` 뒤에 |
| 400 · 403 · 404 · 422 | 아니다 | 하지 마라 |
| 409 | 이미 처리됐다 | 하지 마라 · 성공으로 본다 |

두 번째 줄이 4절과 이어진다. 응답을 기다리다 끊긴 것은 서버가 이미 처리했을 수 있다. 멱등키 없이 재시도하면 1,180건이 되고, 있으면 이 줄이 "안전하다"로 바뀐다.

**재시도 시각을 흩는 데는 따로 이유가 있다.** 간격을 1초·2초·4초로 늘리는 것이 지수 백오프, 그 시각을 무작위로 흩는 것이 지터다. 상대가 재시작하면 물려 있던 요청이 한꺼번에 끊기고, 전부 같은 시각에 실패했으니 백오프만으로는 다시 같은 시각에 몰린다.

```python
# 지터가 없으면 재시도가 어떻게 죽은 서버를 한 번 더 죽이나.
# 상황: 상대 API 가 t=0 에 재시작한다. 그 순간 물려 있던 요청 500건이 한꺼번에 끊긴다.
#       서버는 3,000 ms 뒤에 살아나고, 살아난 뒤에도 100 ms 창당 60건까지만 받는다.
#       초과분은 503 이라 또 재시도로 돌아온다. 재시도는 최대 4회.
# 모든 숫자는 설명을 위해 지어낸 값이다.
import random
from unicodedata import east_asian_width

N, RECOVER_MS, CAP_PER_100MS, MAX_TRY, BASE = 500, 3000, 60, 4, 1000

def run(strategy):
    random.seed(7)
    load = {}                       # 100 ms 창 번호 → 그 창에 도착한 요청 수
    done = failed = 0
    for _ in range(N):
        t = 0.0
        for k in range(1, MAX_TRY + 1):
            if strategy == "fixed":       t += BASE
            elif strategy == "backoff":   t += BASE * 2 ** (k - 1)
            else:                         t += random.uniform(0, BASE * 2 ** (k - 1))
            bucket = int(t // 100)
            load[bucket] = load.get(bucket, 0) + 1
            alive = t >= RECOVER_MS                      # 서버가 살아났나
            room = load[bucket] <= CAP_PER_100MS         # 그 창에 자리가 있나
            if alive and room:
                done += 1
                break
        else:
            failed += 1                                  # 4회를 다 쓰고도 못 넣었다
    peak = max(load.values())
    last = max(b for b in load if b * 100 >= RECOVER_MS) * 100 / 1000
    return done, failed, peak, last

def w(s):
    return sum(2 if east_asian_width(c) in "WF" else 1 for c in s)

def row(cells, widths):
    print("".join(" " * (wd - w(str(c))) + str(c) for c, wd in zip(cells, widths)))

WID = [26, 10, 10, 16, 12]
row(["재시도 전략", "성공", "실패", "100ms 최대 부하", "마지막 도착"], WID)
for name, label in [("fixed", "고정 1초 간격"), ("backoff", "지수 백오프 (지터 없음)"),
                    ("jitter", "지수 백오프 + full jitter")]:
    done, failed, peak, last = run(name)
    row([label, f"{done}건", f"{failed}건", f"{peak}건", f"{last:.1f}s"], WID)

print()
print(f"창 하나가 받을 수 있는 양은 {CAP_PER_100MS}건이다. 그 위는 전부 503 으로 되돌아온다.")
print("지터는 재시도를 늦추는 장치가 아니라 같은 순간에 겹치는 것을 푸는 장치다.")

# 출력:
#                재시도 전략      성공      실패 100ms 최대 부하 마지막 도착
#              고정 1초 간격     120건     380건           500건        4.0s
#    지수 백오프 (지터 없음)     180건     320건           500건       15.0s
#  지수 백오프 + full jitter     472건      28건            92건       10.5s
#
# 창 하나가 받을 수 있는 양은 60건이다. 그 위는 전부 503 으로 되돌아온다.
# 지터는 재시도를 늦추는 장치가 아니라 같은 순간에 겹치는 것을 푸는 장치다.
```

지터 없이 지수 백오프만 넣으면 성공이 180건이고, 지터를 넣으면 472건이다. 설정 한 줄 차이로 살아 돌아오는 요청이 두 배 반이 되니, 장애 복구 비용도 그만큼 줄어든다.

최대 부하 칸을 보면 이유가 드러난다. 짧은 창 하나가 받는 양은 정해져 있는데 그 몇 배가 같은 순간에 도착하고, 넘친 요청은 그 자리에서 503 을 받아 대기열로 되돌아간다.

지수 백오프만 넣은 쪽은 마지막 도착이 15.0초로 고정 간격의 4.0초보다 늦은데도 성공은 180건뿐이다. 몰리는 것을 안 풀면 복구 비용만 커진다.

**타임아웃 예산은 부르는 쪽에서 부르는 쪽으로 나눠 내려간다.** 우리를 부르는 쪽에 400ms 안에 답하기로 계약했다고 하자. 그러면 우리가 부르는 쪽들의 타임아웃 합이 그 400ms 를 넘으면 안 된다. 넘으면 우리를 부르는 쪽이 먼저 끊고, 우리가 부르는 쪽은 아무도 안 기다리는 채로 연결만 먹는다.

앞 표의 400ms 와 이름만 같고 방향이 반대다. 앞은 우리가 상대에게 건 상한이고, 여기는 우리가 지켜야 할 응답 시간이다.

| 우리가 부르는 것 | 잡은 타임아웃 | 평소 걸리는 시간 |
|---|---|---|
| 서명 · 시각 검증 | 20ms | 2ms |
| 멱등키 조회 | 50ms | 3ms |
| 전환 테이블 쓰기 | 200ms | 28ms |
| Kafka 발행 | 100ms | 6ms |
| 남긴 여유 | 30ms | — |
| **합계** | **400ms** | **39ms** |

평소 39ms 인데 상한을 400ms 로 잡은 것은 열 배다. 이 배수는 평소 값이 아니라 느린 쪽 꼬리를 보고 결정한다. 평소 값에 붙여 잡으면 멀쩡한 요청이 끊겨 매출이 빠지고, 너무 넉넉하면 앞의 표처럼 연결이 물려 서비스가 중단된다.

## 6. 인증 — 무엇을 막고 무엇을 못 막나

**다섯 가지가 막는 것이 서로 다르다. 앱에 비밀키를 박는 것은 그중 어느 것도 아니다.**

인증 방식 이름은 많지만 실무에서 만나는 것은 다섯이다. 각각 증명하는 것이 다르고, 못 막는 것도 다르다.

| 방식 | 무엇을 증명하나 | 무엇을 못 막나 | client to server 에 둘 수 있나 |
|---|---|---|---|
| API key | 이 키를 가진 쪽이라는 것 | 본문 위변조 · 재전송 | 안 된다 |
| OAuth2 client credentials | 서비스 신원 · 토큰을 받아 쓴다 | 토큰이 새면 만료까지 유효 | 안 된다 |
| JWT | 발급자가 서명했다는 것 | 만료 전 회수 · 탈취 | 사용자 토큰이면 된다 |
| mTLS | 양쪽이 서로의 인증서를 확인 | 본문 내용이 옳은지 | 사실상 안 된다 |
| HMAC 서명 | 본문이 안 바뀌었다는 것 | 재전송 · 시계가 틀리면 전량 실패 | 안 된다 |

API key 는 가장 단순하고 가장 약하다. 키만 있으면 누구나 우리인 척할 수 있으니 서버끼리만 쓴다. 키를 갈아 끼울 때는 옛 키와 새 키를 함께 인정하는 기간을 두는데, 안 두면 하루치 매출이 통째로 중단된다.

mTLS 는 양쪽이 서로 인증서를 내보이는 연결이라, 부르는 쪽이 누구인지까지 증명한다. 대신 인증서를 만들고 갱신하는 운영 비용이 양쪽에 생긴다.

HMAC 서명은 본문과 시각을 비밀키로 해시해 헤더에 붙이고, 받는 쪽이 같은 계산을 해 본다. 한 글자만 고쳐도 값이 달라지니 위변조가 걸린다. 대신 같은 요청을 그대로 다시 보내는 것은 못 막아 앞뒤 5분처럼 좁은 창을 둔다.

창을 두면 시계가 새 문제가 된다. 서명하는 쪽과 검증하는 쪽 시계가 창만큼 벌어지면 코드는 멀쩡한데 요청이 전량 401 이 되고, 그동안 전환이 통째로 중단된다. 서명이 전부 실패하면 키 재발급 승인을 받으러 가기 전에 시각 동기화부터 본다.

**앱에 비밀키를 박으면 안 되는 이유는 추상적이지 않다.** 앱 파일에서 키처럼 생긴 문자열을 뽑는 것은 명령 한 줄이다.

```bash
# 앱 파일을 풀어 문자열만 훑는다. 특별한 도구가 필요 없다.
unzip -p app.apk classes.dex | strings | grep -oE 'sk_live_[A-Za-z0-9]{8,}'
```

웹은 더 쉬워서 개발자 도구 네트워크 탭에 헤더가 그대로 보인다. 코드를 알아보기 어렵게 뒤섞는 난독화도 귀찮게 할 뿐 막지는 못한다.

그러면 앱은 어떻게 인증하나. 답은 셋이다. 사용자가 로그인해 받은 토큰을 쓰거나, 비밀이 필요한 호출을 앱 대신 우리 백엔드가 하거나, 애초에 비밀이 필요 없게 설계한다. 여기까지가 첫 주에 내려야 할 결정이다.

## 헷갈리기 쉬운 점

먼저 첫 주에 밟는 지뢰 여덟이다. 공통점은 배포 승인이 나고 테스트도 통과한다는 것이다.

- **앱에 비밀키를 박는다** — 남이 우리 쿼터를 쓰고, 키를 바꾸면 옛 앱이 깨진다.
- **타임아웃을 안 건다** — 상대가 느려지면 연결이 다 물려 무관한 기능까지 중단된다.
- **성공 코드 안에 에러를 담는다** — 실패가 성공으로 세어져 알람도 재시도도 안 걸린다.
- **멱등키 없이 재시도한다** — 전환이 부풀고 전환당 비용이 싸 보여 예산이 잘못 움직인다.
- **쿼터 초과를 무시한다** — 곧바로 다시 보내면 그 재시도가 정상 요청까지 같이 막는다.
- **시계가 어긋나 서명이 실패한다** — 키를 재발급받아도 안 고쳐지고 증상은 인증 실패다.
- **응답 필드가 늘어 파서가 깨진다** — 부르는 쪽이면 모르는 필드를 먼저 열어 둔다.
- **테스트 자격증명으로 운영을 부른다** — 진짜 전환을 만들거나 하루치 매출을 잃는다.

**"멱등성은 요청 방식을 바꾸는 것"이 아니다.** 같은 키가 두 번 오면 두 번째를 새로 처리하지 않겠다는 약속이다. `POST` 는 그대로 두고 키를 헤더에 얹어야, 새 자원을 만드는 요청도 안심하고 재시도할 수 있다.

**"재시도를 끄면 중복이 없어진다"도 아니다.** 끄면 중복 대신 유실이 생겨 매출이 빈다. 응답을 못 받은 건 중 일부는 서버가 이미 기록했고 일부는 진짜로 안 들어갔는데, 둘을 못 가르니 켜고 키를 붙이는 것이 답이다.

**"200 이면 성공"이 아니다.** 상대 API 가 200 안에 실패를 담는다면 우리 코드가 본문을 보고 판정하고, 그 결과를 지표에 실패로 기록한다. 안 그러면 정산 매출이 틀어져도 못 잡는다.

**"내부 API 라 대충 해도 된다"가 가장 비싸다.** 타임아웃도 멱등키도 똑같이 필요하고, 오히려 거치는 단계가 길어 실패 지점이 더 많다. 여기서 아낀 하루가 나중에 몇 주치 손해로 돌아온다.
