지훈 씨가 팀에 들어온 첫 주에 이런 말을 들었습니다. "회원가입은 POST 로 보내고, 목록은 GET 으로 받아 오면 돼요."

알겠다고 답했는데 다음 날 코드를 보다 막혔습니다. 검색 기능이 `POST /v1/search` 로 되어 있었고, 그런데 그 요청에서 **검색 결과가 돌아오고 있었습니다.** POST 는 뭔가를 고치거나 만드는 것이라고 배웠는데, 왜 여기서는 데이터를 받아 오고 있을까요.

**POST 로 보냈는데 왜 데이터가 돌아올까요?**

이 질문에는 오해가 두 겹 들어 있습니다. 하나는 POST 의 뜻이고, 다른 하나는 **요청과 응답이 별개**라는 사실입니다. 이 글은 그 둘을 풀고, 주소 짓기·공개 범위·로그·대량 전송까지 처음 API 를 다룰 때 필요한 것을 한 바퀴 돕니다.

> **한 줄 요약:** POST 는 "수정"이 아니라 "이걸 처리해 주세요"입니다. 그리고 HTTP 는 **요청 하나에 응답 하나가 반드시 짝**이라, 메서드가 무엇이든 답은 옵니다. 메서드는 내가 시키는 일이고 응답은 그 결과라서 서로 다른 이야기입니다.

> **골라 읽는 법** — 절이 열한 개인 글입니다.
>
> - POST 오해만 풀고 싶으면 → 3·4절
> - 주소 짓기와 공개 범위 → 5·6절
> - 로그에 무엇을 남기고, 그 로그가 어디에 남나 → 7·8절
> - 앱이 센 수와 서버가 센 수가 다를 때 → 9절
> - 대량 전송 → 10절
> - 광고 클릭 API 를 실제로 만들어 보기 → 11절

이 글의 숫자는 전부 설명을 위해 지어낸 값입니다. 다만 로그 줄과 요청·응답의 **형식**은 nginx 와 HTTP 가 실제로 내는 모양 그대로입니다. 그리고 이 글에서 **우리**는 API 를 만들어 내주는 쪽, 지훈 씨가 들어간 팀입니다.

## 1. API 는 미리 맞춰 둔 창구입니다

**API 는 "이 주소로 이런 모양으로 물으면 이런 모양으로 답한다"를 미리 맞춰 둔 것입니다.**

사람이 웹사이트를 볼 때는 화면을 보지만, 프로그램끼리는 화면이 필요 없으니 **데이터만** 주고받습니다. 그러려면 어떤 모양으로 주고받을지를 미리 정해 둬야 하는데, 그 약속이 바로 API 입니다. 그래서 API 를 만든다는 것은 코드를 짜는 일이기 전에 **모양을 정하는 일**입니다.

정할 모양은 요청 쪽 네 조각과 응답 쪽 세 조각입니다. 요청 한 번은 이렇게 되어 있습니다.

| 조각 | 무엇인가 | 예 |
|---|---|---|
| 메서드 | 무엇을 시키나 | `GET`, `POST` |
| 주소 | 무엇에 대해 | `/v1/posts/12` |
| 헤더 | 곁들이는 정보 | 누구인지, 본문이 무슨 형식인지 |
| 본문 | 딸려 보내는 데이터 | `{"title": "첫 글"}` |

응답 쪽 세 조각은 **상태 코드**(숫자 세 자리)와 **헤더**와 **본문**입니다.

여기서 이 글 전체를 관통하는 규칙이 하나 나옵니다. **요청을 하나 보내면 응답이 하나 오고, 예외가 없습니다.** 서버가 아무 데이터도 줄 게 없어도 "줄 게 없다"는 응답은 옵니다.

그러니 "POST 로 보냈는데 답이 왔다"는 이상한 일이 아니고, 오히려 답이 안 오는 쪽이 고장입니다. 왜 이게 그렇게 헷갈리는지는 4절에서 다시 봅니다.

## 2. 누가 부르나 — 남의 기기냐 우리 서버냐

**세 번째 줄이 실무에서 제일 자주 사고를 냅니다.** 브라우저가 보낸 `{"price": 0}` 을 그대로 믿고 주문을 만들면, 누군가 요청을 고쳐 보내는 순간 공짜로 물건이 나갑니다. 화면에서 막았다는 것은 아무 보장이 아닙니다. 화면을 안 거치고 요청만 직접 보낼 수 있기 때문입니다.

지훈 씨가 이번 주에 맡을 API 는 앱이 부르는 쪽입니다. 그러니 위쪽 줄이 전부 지훈 씨 이야기입니다.

## 3. 메서드 다섯이 시키는 일

**메서드는 "이 주소에 대해 무엇을 시키는가"입니다. 여기에 POST 오해의 절반이 들어 있습니다.**

| 메서드 | 뜻 | 예 |
|---|---|---|
| `GET` | 주세요 | 글 목록을 주세요 |
| `POST` | **이걸 처리해 주세요** | 이 내용으로 글을 새로 써 주세요 |
| `PUT` | 이 자리를 이 내용으로 통째로 바꿔 주세요 | 12번 글을 이 내용으로 교체 |
| `PATCH` | 이 자리에서 이 부분만 바꿔 주세요 | 12번 글의 제목만 교체 |
| `DELETE` | 지워 주세요 | 12번 글을 지워 주세요 |

**"수정"에 가장 가까운 것은 `PUT` 과 `PATCH` 입니다.** `POST` 는 수정이 아니라 **제출**에 가깝습니다. 무언가를 서버에 넘기면서 "알아서 처리해 주세요"라고 말하는 것입니다.

그래서 `POST` 의 결과는 상황마다 다릅니다. 글을 새로 만들기도 하고, 로그인을 시켜 주기도 하고, 결제를 걸기도 합니다. **공통점은 "서버 쪽에서 무슨 일이 일어난다"는 것뿐입니다.**

`GET` 은 반대입니다. **`GET` 은 아무것도 바꾸지 않아야 합니다.** 이것을 지키면 좋은 일이 생깁니다. 브라우저는 마음대로 미리 불러 둬도 되고, 부르는 코드는 실패하면 그냥 다시 부르면 됩니다. 사람은 그 주소를 그대로 공유해도 됩니다.

`GET /v1/posts/12/delete` 같은 주소를 만들면 안 되는 이유가 이것입니다. 검색 로봇이 그 주소를 한 번 훑는 것만으로 글이 다 지워집니다.

그래서 메서드를 고르는 기준은 한 줄로 정리됩니다. **서버 쪽에 무언가 바뀌면 `POST`·`PUT`·`PATCH`·`DELETE` 중 하나이고, 아무것도 안 바뀌면 `GET` 입니다.** 이 한 줄로 대부분 정해지는데, 다음 절이 바로 그 "대부분"에 안 들어가는 경우입니다.

## 4. POST 로 보냈는데 왜 데이터가 돌아오나

**메서드는 "내가 시키는 일"이고, 응답은 "그 결과"입니다. 둘은 서로 다른 이야기입니다.**

지훈 씨가 헷갈린 지점이 여기입니다. "POST = 데이터를 보내는 것"이라고 외우면, 보내기만 하고 받는 것은 없다고 생각하게 됩니다. 그런데 HTTP 는 **요청 하나마다 응답 하나가 반드시 따라옵니다.**

세 가지를 실제로 주고받는 모양 그대로 놓아 보겠습니다. 위가 보낸 것, 아래가 받은 것입니다.

**① 글 목록 조회 — 보낸 본문이 없습니다**

```http
GET /v1/posts?page=2 HTTP/1.1
Host: api.example.com

HTTP/1.1 200 OK
Content-Type: application/json

{"page":2,"items":[{"id":11,"title":"첫 글"},{"id":12,"title":"둘째 글"}]}
```

**② 글 새로 쓰기 — 보낸 본문도 받은 본문도 있습니다**

```http
POST /v1/posts HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"title":"셋째 글"}

HTTP/1.1 201 Created
Content-Type: application/json

{"id":13,"title":"셋째 글","status":"created"}
```

**③ 조건이 긴 검색 — 아무것도 안 만드는데 POST 입니다**

```http
POST /v1/search HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"filters":[{"field":"title","value":"글"},{"field":"author","value":"jihun"}]}

HTTP/1.1 200 OK
Content-Type: application/json

{"matched":2,"items":[{"id":11,"title":"첫 글"}]}
```

셋을 나란히 놓으면 오해가 풀립니다. ①은 보낸 본문이 없는데 받은 본문에는 글이 두 건 들어 있고, ②는 보낸 본문도 받은 본문도 있으면서 서버에 글이 하나 새로 생겼습니다. ③은 보낸 본문도 받은 본문도 있는데 서버에는 아무것도 안 생겼습니다.

**보낼 때 본문이 있느냐, 받을 때 본문이 있느냐, 서버에 뭔가 생겼느냐는 서로 상관이 없는 세 가지입니다.** 그래서 메서드 하나만 보고 나머지 둘을 짐작할 수 없습니다.

마지막 것이 지훈 씨가 본 코드입니다. 검색인데 왜 `POST` 를 썼을까요.

**조건이 주소에 안 들어가서입니다.** `GET` 은 조건을 주소 뒤에 붙이는데(`?title=글&author=jihun`), 조건이 스무 개쯤 되거나 값이 길면 주소가 감당을 못 합니다. 서버나 중간 장비가 주소 길이를 제한하는 경우도 많습니다. 그래서 조건을 본문에 담아 `POST` 로 보냅니다.

이것은 원칙을 어긴 것이 맞습니다. **원칙대로면 조회는 `GET` 입니다.** 다만 현실적인 이유로 `POST` 를 쓰는 것이고, 그럴 때는 주소에 `search` 처럼 "이건 조회다"를 남겨 둡니다. 그러니 판단 기준은 하나입니다. 조건이 주소에 들어가면 `GET` 을 쓰고, 안 들어갈 때만 `POST` 로 넘어가되 그 사실이 주소에 보이게 짓습니다.

:::deep 상태 코드 세 자리를 다 외워야 하나

안 외워도 됩니다. **첫 자리만 알면 대부분 읽힙니다.** 전부 서버가 하는 말입니다. 2xx 는 "됐습니다", 3xx 는 "다른 데로 가세요"라는 뜻입니다. 4xx 는 "그쪽이 잘못 보냈습니다", 5xx 는 "제가 처리를 못 했습니다"입니다.

이 중 4xx 와 5xx 를 가르는 것이 실무에서 가장 중요합니다. 부르는 쪽이면 4xx 가 뜰 때 요청을 고치고, 5xx 가 뜰 때 서버 담당자에게 알립니다. **같은 실패라도 할 일이 정반대입니다.**

자주 보는 것은 일곱 개쯤이고 나머지는 필요할 때 찾아보면 됩니다.

| 코드 | 뜻 | 누가 고치나 |
|---|---|---|
| `200` | 됐습니다 | — |
| `201` | 새로 만들었습니다 | — |
| `400` | 요청 모양이 틀렸습니다 | 부르는 쪽 |
| `401` | 누군지 모르겠습니다 | 부르는 쪽 |
| `403` | 누군지는 알겠는데 권한이 없습니다 | 부르는 쪽 |
| `404` | 그런 것 없습니다 | 부르는 쪽 |
| `500` | 서버가 터졌습니다 | 받는 쪽 |

`401` 과 `403` 을 헷갈리기 쉬운데, **로그인을 안 한 것이 401 이고 로그인은 했지만 남의 글을 지우려는 것이 403** 입니다.

한 가지 절대 하지 말아야 할 것이 있습니다. **`200` 을 보내 놓고 본문에 "실패했습니다"를 담는 것.** 부르는 쪽 코드는 상태 코드만 보고 성공으로 처리하고, 감시 도구도 오류로 안 셉니다. 실패가 조용히 묻힙니다.
:::

## 5. 주소를 어떻게 짓나

**주소에는 "무엇"만 넣고 "무엇을 하는지"는 메서드에 맡깁니다.**

주소 짓기에 정답은 없지만 널리 쓰는 관례가 있고, 그것만 따라도 남이 읽기 쉬워집니다.

| 규칙 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 동사를 넣지 않습니다 | `/getPost`, `/createUser` | `GET /posts/12`, `POST /users` |
| 복수형 명사를 씁니다 | `/post/12` | `/posts/12` |
| 소속은 경로로 나타냅니다 | `/comments?postId=12` | `/posts/12/comments` |
| 소문자와 하이픈을 씁니다 | `/userProfile`, `/user_profile` | `/user-profiles` |
| 버전을 앞에 붙입니다 | `/posts` | `/v1/posts` |

**첫 줄이 핵심입니다.** 동사를 주소에 넣으면 메서드와 뜻이 겹칩니다. `POST /createUser` 는 "만들어라"를 두 번 말하는 셈이고, 그러다 보면 `POST /deleteUser` 같은 것도 생깁니다.

주소가 명사면 같은 주소에 메서드만 바꿔 여러 일을 시킬 수 있습니다. `/v1/posts` 하나에 `GET` 을 붙이면 목록이고 `POST` 를 붙이면 새 글입니다. `/v1/posts/12` 에 `PATCH` 를 붙이면 일부 수정이고 `DELETE` 를 붙이면 삭제입니다. 이름 여섯 개를 따로 짓는 것보다 훨씬 외우기 쉽고, **처음 보는 사람도 `/v1/posts/12/likes` 가 무엇일지 짐작할 수 있습니다.**

버전을 앞에 붙이는 이유는 나중에 응답 모양을 바꿔야 할 때가 오기 때문입니다. `/v1` 을 살려 둔 채 `/v2` 를 새로 열면, 옛 앱은 계속 `/v1` 을 쓰고 새 앱만 `/v2` 로 옮겨 갑니다. 2절에서 본 "앱을 안 지운 사람이 있는 한 옛 버전을 못 끈다"가 여기서 살아납니다. 그래서 주소를 지을 때 가장 되돌리기 어려운 결정이 버전 자리이고, 나머지는 나중에 고칠 여지가 있습니다.

## 6. 어디까지 열어 두나 — 내부·파트너·공개

**"API 를 연다"는 것은 주소를 알려 주는 일이 아니라 등급을 정하는 일입니다.**

같은 서버 안에 있는 API 라도 누가 부를 수 있게 할지가 다릅니다. 크게 세 등급으로 나눕니다.

| 등급 | 누가 부르나 | 어떻게 막나 | 바꿀 때 |
|---|---|---|---|
| 내부용 | 사내 서버끼리 | 망 자체를 분리 | 양쪽 배포만 맞추면 됩니다 |
| 파트너용 | 계약한 회사 | 회사마다 키를 따로 발급 | 미리 알리고 유예 기간을 둡니다 |
| 공개용 | 아무나 | 가입하면 키를 줍니다 | 함부로 못 바꿉니다 |

**아래로 갈수록 바꾸기 어려워집니다.** 이것이 등급을 나누는 진짜 이유입니다. 내부용은 오늘 고쳐서 오늘 배포해도 되지만, 공개용은 누가 쓰는지도 모르니 한 번 연 모양을 오래 지켜야 합니다.

그래서 실무에서 자주 하는 실수가 **"일단 다 열어 두고 나중에 정리하자"** 입니다. 열어 둔 것을 나중에 닫으려면 쓰는 쪽을 전부 찾아 설득해야 합니다. **처음에 좁게 열고 필요할 때 넓히는 쪽이 언제나 쌉니다.**

등급을 정했으면 그다음 셋을 정합니다. 첫째는 누구인지 확인하는 방법입니다. 내부용은 망 분리로 충분하고, 파트너·공개용은 키나 토큰을 줍니다. 어떤 방식이 무엇을 막고 무엇을 못 막는지는 [API 연동 실무](post.html?id=api-kinds-and-contracts) 편에 정리돼 있습니다.

둘째는 얼마나 자주 부를 수 있는지입니다. 한 키가 초당 몇 번까지 부를 수 있는지를 정해 두지 않으면, 한 곳이 실수로 반복 호출을 걸었을 때 다른 모두가 같이 느려집니다.

셋째는 무엇을 문서로 남길지입니다. 주소·요청 모양·응답 모양·오류 목록 넷은 최소한입니다. 이게 없으면 부르는 쪽이 매번 물어보거나, 더 나쁘게는 추측해서 짭니다.

## 7. 로그 한 줄에 무엇을 넣고 무엇을 가리나

**요청 하나가 지나갈 때마다 한 줄을 남깁니다. 무엇을 넣고 무엇을 가릴지가 전부입니다.**

장애가 났을 때 "그 요청이 언제 들어왔고 뭐라고 답했나"를 못 찾으면 원인을 못 찾습니다. 그런데 아무거나 다 남기면 비밀번호와 카드번호가 로그에 그대로 박힙니다.

지훈 씨가 로그인 요청 한 건을 그대로 남겨 봤더니 이렇게 나왔습니다.

```json
{"ts":"2026-08-16T10:22:03.114Z","path":"/v1/users/login","body":{"email":"jihun@example.com","password":"hunter2","card":"4111-1111-1111-1234"}}
```

비밀번호 `hunter2` 와 카드번호가 그대로 보입니다. 로그는 보통 여러 사람이 검색할 수 있는 곳에 쌓이니, 이 줄 하나가 사고입니다. 가리고 남기면 이렇게 됩니다.

```json
{"ts":"2026-08-16T10:22:03.114Z","request_id":"req-8f21c0","method":"POST","path":"/v1/users/login","status":401,"took_ms":37,"body":{"email":"jihun@example.com","password":"***","card":"***"},"headers":{"Authorization":"***","User-Agent":"app/3.2.1"}}
```

늘어난 칸마다 정해야 할 것이 하나씩 있습니다. 세 가지를 짚어야 합니다.

**첫째, `request_id` 가 가장 중요한 칸입니다.** 요청이 들어올 때 고유한 값을 하나 붙이고, 그 요청을 처리하며 남기는 모든 줄에 같은 값을 넣습니다. 그러면 나중에 그 값 하나로 관련된 줄을 전부 모을 수 있습니다. 응답 헤더로 돌려주면 사용자가 "이 번호로 문의드립니다"라고 말할 수 있어 더 좋습니다.

**둘째, 가릴 때 통째로 빼지 않습니다.** `password` 칸을 아예 지우면 나중에 "비밀번호를 보내긴 했나"를 못 따집니다. 값만 `***` 로 바꾸고 칸은 남기는 쪽을 고릅니다. `status` 와 `took_ms` 도 같은 이유로 꼭 넣는데, 상태 코드만 있으면 "성공은 했는데 3초 걸렸다"를 못 보기 때문입니다.

**셋째, 모든 요청의 본문을 다 남기면 로그가 원본 데이터보다 커집니다.** 그래서 본문을 남길지는 취향이 아니라 초당 건수로 정합니다. 초당 수천 건이 들어오는 API 라면 본문은 오류가 났을 때만 남기거나, 일부만 골라 남깁니다.

## 8. 그 로그는 어디에 남나 — 서버가 저절로 남기는 줄, 앱이 보내야 남는 줄

**요청 하나에 서버 쪽 줄이 둘 남습니다. 하나는 코드를 안 짜도 남고, 하나는 앱이 보내 줘야만 남습니다.**

지훈 씨가 앱 팀 코드를 보다가 이상한 것을 찾았습니다. 광고를 누르면 앱이 `POST /v1/events` 로 "눌렀다"를 보냅니다. 그런데 그 요청이 도착하면 서버는 어차피 7절의 그 한 줄을 남깁니다. **왜 앱이 굳이 한 번 더 알려 주는 걸까요.**

**서버는 자기한테 온 것만 알기 때문입니다.**

```json
{"req_id":"r-8f21","event":"click","ad_id":9931,"slot":"main_top","event_ts":1786002501234,"app_ver":"3.2.1"}
```

| | ① 접속 로그 | ② 이벤트 로그 |
|---|---|---|

| 무엇이 적히나 | 요청이 왔다는 사실 — 주소·상태·걸린 시간 | 본문 내용 — 어느 광고, 어느 자리, 언제 |

| 앱이 본문을 안 담아 보내면 | 그래도 남습니다 | 아무것도 안 남습니다 |
| 어디에 쓰나 | 장애 조사 | 과금·리포트·학습 데이터 |

**웹 픽셀이 가장 노골적입니다.** 1×1 짜리 투명 이미지 주소를 부르기만 합니다. 보낼 본문도 없고 받은 답을 쓰지도 않습니다. 대신 광고 번호를 주소 뒤에 붙입니다(`/p.gif?ad=9931`). 그 요청이 남긴 접속 로그 한 줄이 곧 기록입니다.

**클릭은 지나가게 해서 남기기도 합니다.** 광고를 누르면 광고주 페이지로 바로 안 갑니다. 트래킹 서버 주소를 한 번 거칩니다. 그 서버가 클릭을 적고 진짜 주소로 넘깁니다. 이 경로는 [광고가 유저에게 도달하는 전체 과정](post.html?id=ad-serving-flow) 편 11절에 있습니다.

**부르는 쪽이 서버면 얘기가 다릅니다.** 자기 디스크에 쓰면 되니 남기려고 남을 부를 일이 없습니다. 보낼 데가 없는 것은 브라우저와 앱입니다.

그러니 지훈 씨의 질문에 대한 답은 이렇습니다. **일반적입니다.** 부르는 쪽이 남의 기기에 있으면 그 방법밖에 없습니다.

## 9. 앱이 센 수와 서버가 센 수가 다를 때

**8절의 두 줄은 둘 다 서버에 남는 줄이었습니다. 이번엔 다른 짝입니다 — 앱 안에 남는 기록과 서버에 남는 기록.**

지훈 씨가 앱 팀에게 어제 클릭 건수를 물었더니 1,000건이라고 했습니다. 그런데 서버 로그에는 985건뿐입니다. **15건은 어디로 갔을까요.**

둘이 재는 것부터 다릅니다. 앱은 요청을 보낸 순간부터 답이 다 올 때까지를 잽니다. 서버는 자기가 처리한 시간만 잽니다. 그 차이가 오가는 데 걸린 시간입니다.

더 중요한 것이 있습니다. **서버에 도착도 못 한 요청은 서버 로그에 없습니다.** 네 가지 상황을 놓고 보면 바로 보입니다.

| 상황 | 앱 쪽 기록 | 서버 쪽 기록 | 실제로는 |
|---|---|---|---|
| 정상 | 성공 `200` | `200` 한 줄 | 양쪽이 맞습니다 |
| 서버가 터졌습니다 | 실패 `500` | `500` 한 줄 | 양쪽 다 압니다 |
| 서버가 안 떠 있었습니다 | 연결 실패 | **줄이 없습니다** | 클릭은 있었는데 아무 데도 안 남았습니다 |
| 답이 늦어 앱이 포기했습니다 | 타임아웃 | **`200` 한 줄** | 서버는 저장했는데 앱은 실패로 압니다 |

**셋째 줄이 그 15건의 정체입니다.** 서버가 배포 중이라 잠깐 멈춘 사이 앱이 보낸 15건은 서버에 닿지 못했고, 그래서 서버 로그에는 아무 줄도 안 남았습니다. 1,000건에서 이 15건을 빼면 서버가 센 985건이 됩니다.

**넷째 줄은 반대 방향으로 어긋납니다.** 서버는 저장을 끝냈는데 답이 늦어 앱이 실패로 알았으니, 앱은 같은 클릭을 다시 보냅니다. 그러면 서버에 같은 클릭이 두 줄 남습니다. **모자란 것과 겹친 것이 한 로그 안에 같이 있는 셈입니다.** 셋째와 넷째가 같은 날 섞이면 총계만 보고는 어느 쪽인지 알 수 없습니다.

그래서 "어느 쪽이 맞나"를 따지는 대신 **무엇을 잴 때 어느 쪽을 보는지**를 정해 둡니다. 이 결정이 나중에 정산 회의에서 말이 갈리는 것을 막습니다.

**돈에 닿는 숫자는 서버 쪽이 정본입니다.** 과금·정산·리포트에 쓰는 건수는 서버가 센 985건을 씁니다. 남의 기기가 보낸 숫자는 고쳐 보낼 수 있어서인데, 2절 세 번째 줄과 같은 이유입니다.

**반대로 "얼마나 실패했나"는 앱 쪽 기록으로만 보입니다.** 도착 못 한 요청은 서버가 셀 수 없으니, 1,000건과 985건의 차이인 15건은 앱 쪽에서만 보입니다. 서버 그래프는 평평한데 사용자만 안 되는 일이 그래서 생깁니다.

두 줄을 이으려면 요청 번호를 양쪽이 같이 써야 합니다. 앱이 `X-Request-Id` 헤더에 값을 만들어 보내고, 서버가 그 값을 그대로 자기 줄에 적습니다. 헤더가 없으면 서버가 만듭니다. 7절의 `request_id` 가 여기서 살아납니다.

여기서 8절의 함정이 되살아납니다. 앱 쪽 기록도 결국 요청으로 보내야 서버에 닿는데, **그 전송도 실패할 수 있습니다.** 신호가 끊긴 곳에서는 실패 기록조차 못 보냅니다. 그래서 앱은 실패 기록을 모아 뒀다가 되는 대로 다시 보냅니다.

중간에 게이트웨이나 프록시가 있으면 그것도 자기 줄을 남깁니다. 그러면 한 요청에 줄이 셋입니다. 무엇이 어디에 끼는지는 [로드밸런서·Ingress·API Gateway](post.html?id=gateway-ingress-router) 편에 있습니다.

## 10. 100만 줄을 API 로 넘기려면

**API 로 대량 데이터를 주고받을 수는 있습니다. 다만 한 번의 요청에 다 담지 않습니다.**

클릭 로그 100만 줄을 넘겨야 한다고 하겠습니다. 한 줄이 이렇게 생겼고 평균 90바이트입니다.

```json
{"click_id":"c-0000001","ts":"2026-08-16T16:48:21Z","ad_id":9931,"user":"u-482913"}
```

90바이트 곱하기 100만 줄이면 **86MB** 입니다. 나누는 크기와 압축 여부에 따라 요청 하나가 이만큼 달라집니다.

| 보내는 방법 | 요청 수 | 한 번에 보내는 크기 |
|---|---|---|
| 한 번에 다 | 1 | 86 MB |
| 1,000줄씩 나눠 | 1,000 | 88 KB |
| 10,000줄씩 나눠 | 100 | 879 KB |
| 10,000줄씩 나눠 + gzip | 100 | 131 KB |

압축이 이만큼 듣는 이유는 로그의 성질에 있습니다. 줄마다 값은 다르지만 `click_id`·`ts`·`ad_id` 같은 **열쇠 이름이 100만 번 반복**됩니다. gzip 이 그 반복을 지우면 원본의 14.9% 가 됩니다.

맨 위 줄이 문제입니다. 86MB 를 한 요청에 담으면 세 가지가 한꺼번에 나빠집니다. 받는 쪽이 다 받을 때까지 아무것도 못 하고, 중간에 끊기면 처음부터 다시 보내야 하고, 서버가 그 전부를 메모리에 올려야 합니다.

나눠 보내면 셋 다 풀립니다. **10,000줄씩 100번 나누면 요청 하나가 879KB 라, 끊겨도 그 묶음만 다시 보냅니다.** 압축을 걸면 131KB 까지 줍니다.

그러니 이 표에서 고를 것은 하나입니다. **10,000줄씩 나누고 압축을 켜는 것이 기본값이고**, 여기서 벗어나는 경우가 둘 있습니다. 보낼 것이 수십 GB 로 아주 크면 요청에 담지 않고 파일로 올려 둔 뒤 그 위치만 알려 줍니다. 반대로 우리가 받아 오는 쪽이면 조금씩 나눠 받고 다음 위치를 응답이 알려 주게 합니다.

**한 가지가 더 있는데, 처음에는 잘 안 떠오르는 방식입니다.** 한 달치 정산 자료처럼 만드는 데 몇 분씩 걸리는 것은 그 자리에서 못 줍니다. 그래서 `POST /v1/reports` 로 "만들어 주세요"라고 요청하면 서버는 `202` 와 함께 접수 번호만 줍니다. 부르는 쪽은 `GET /v1/reports/{번호}` 로 가끔 확인하다가 다 됐을 때 받아 갑니다.

받아 올 목록을 서버가 어떻게 끊어 주는지는 [API 연동 실무](post.html?id=api-kinds-and-contracts) 편에 성능 비교까지 있습니다.

## 11. 광고 클릭 API 하나를 만들어 봅니다

**앞의 열 절이 실제 API 하나에 어떻게 한꺼번에 들어가는지 보겠습니다.**

지훈 씨가 첫 API 를 맡았습니다. 광고를 클릭하면 그 사실을 서버에 알리는 API 입니다. 앞 절들이 정한 것을 순서대로 얹으면 이 API 하나가 완성됩니다.

**맨 먼저 정하는 것은 누가 부르느냐입니다.** 사용자 기기가 부르니 2절의 왼쪽 줄이고, 그래서 비밀키를 못 싣고 앱이 보낸 값은 전부 다시 검사합니다. 서버에 기록이 생기는 일이니 메서드는 `POST` 이고, 주소에는 동사를 빼고 `POST /v1/events` 로 짓습니다. 아무나 부를 수 있게 열되 값을 안 믿는 쪽을 고릅니다.

**응답을 무엇으로 줄지가 광고에서 특히 중요합니다.** 클릭을 눌렀는데 화면이 멈추면 안 되니, 기록이 다 끝날 때까지 기다리지 않고 `202` 와 접수 번호만 먼저 답합니다. 실제 저장은 서버가 응답을 보낸 뒤 이어서 합니다. 4절에서 본 "요청 하나에 응답 하나"는 여기서도 그대로라, 저장을 안 기다린다고 답이 없어지지는 않습니다.

**그다음이 8·9절에서 본 그것입니다.** 앱이 못 보낸 클릭은 서버 로그에 아예 없으니, 앱이 자기 쪽 실패 건수를 따로 세어 보내야 합니다. 그것마저 못 보내면 아무 데도 안 남습니다. 그리고 클릭 하나마다 요청을 보내면 지하철에서 신호가 약할 때 다 실패합니다. 그래서 앱이 클릭 몇 개를 모아 뒀다가 한 번에 보내고, 실패하면 그 묶음만 다시 보냅니다.

**처음 API 를 만들 때의 순서도 이와 같습니다.** 누가 부르는지부터 정하고, 그다음 메서드와 주소를 정하고, 그다음 응답 모양과 공개 범위를 정하고, 마지막에 로그와 대량 처리를 얹습니다. 순서를 뒤집어 코드부터 짜면 대체로 처음 세 가지를 다시 정하게 됩니다.

그리고 이 API 가 받은 클릭 한 건은 여기서 끝나지 않습니다. 8절에서 남긴 그 두 줄이 어디로 흘러가는지가 이 트랙의 뒷부분입니다.

## 한눈 정리

| 질문 | 한 줄 답 |
|---|---|
| POST 는 수정하라는 뜻인가 | 아닙니다. "이걸 처리해 주세요"입니다. 수정은 PUT·PATCH |
| POST 인데 왜 데이터가 오나 | 요청 하나에 응답 하나가 항상 짝입니다. 메서드와 응답은 별개 |
| 조회인데 POST 를 써도 되나 | 조건이 주소에 안 들어갈 때만. 주소에 `search` 를 남깁니다 |
| GET 으로 데이터를 바꿔도 되나 | 안 됩니다. 검색 로봇이 훑는 것만으로 사고가 납니다 |
| client·server 구분이 왜 중요한가 | 남의 기기에는 비밀키를 못 싣고 보낸 값을 못 믿습니다 |
| 주소를 어떻게 짓나 | 동사 빼고 복수형 명사. 소속은 경로로, 버전은 앞에 |
| API 를 어디까지 여나 | 내부·파트너·공개 세 등급. 좁게 열고 넓히는 쪽이 쌉니다 |
| 로그에 무엇을 남기나 | 요청 번호·상태·걸린 시간. 민감한 칸은 값만 `***` |
| 그 로그가 어디에 남나 | 접속 로그는 코드 없이, 이벤트 로그는 앱이 보내야 |
| 앱과 서버 숫자가 다르면 | 돈은 서버 쪽, 실패율은 앱 쪽이 정본입니다 |
| 대량 데이터를 보낼 수 있나 | 나눠 보냅니다. 크면 파일로, 오래 걸리면 접수 번호로 |

## 헷갈리기 쉬운 점

- **POST 를 "데이터를 보내는 것"으로만 외우지 마세요.** 보내는 것과 받는 것은 상관이 없습니다. 4절의 셋 다 답이 옵니다.
- **GET 은 아무것도 바꾸지 않아야 합니다.** `GET /posts/12/delete` 같은 주소는 검색 로봇 한 번에 사고가 납니다.
- **주소에 동사를 넣지 마세요.** 메서드가 이미 동사입니다. `POST /createUser` 는 같은 말을 두 번 합니다.
- **화면에서 막았다고 막힌 것이 아닙니다.** 화면을 안 거치고 요청만 직접 보낼 수 있습니다.
- **`200` 안에 실패를 담지 마세요.** 부르는 쪽도 감시 도구도 성공으로 셉니다.
- **`401` 과 `403` 은 다릅니다.** 로그인을 안 한 것이 401, 했지만 권한이 없는 것이 403.
- **로그에서 민감한 칸을 통째로 빼지 마세요.** 값만 가리고 칸은 남겨야 나중에 따질 수 있습니다.
- **접속 로그만 보고 "어느 광고였나"를 찾지 마세요.** 주소는 전부 `/v1/events` 로 똑같습니다.
- **서버 로그만 보고 "장애 없음"이라고 하지 마세요.** 도착 못 한 요청은 거기 없습니다.
- **일단 다 열어 두지 마세요.** 여는 것은 하루, 닫는 것은 몇 달입니다.
