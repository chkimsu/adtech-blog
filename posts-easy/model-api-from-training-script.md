지훈 씨의 열째 주입니다. 지난주에 분석 팀의 실험용 pCVR(광고가 구매 같은 전환으로 이어질 확률의 예측값) 모델을 BentoML(학습한 모델을 요청에 답하는 서버로 띄워 주는 도구)로 띄웠습니다. 이번에는 광고 소재(광고에 쓰는 이미지와 문구)의 품질 점수를 내는 새 모델을 광고를 고르는 경로에 올리게 됐습니다. 이 경로는 모델 호출에 쓸 수 있는 시간이 8ms(ms 는 1,000분의 1초)라서 지훈 씨는 BentoML 을 쓰지 않고 추론 서버(모델이 요청을 받아 점수를 돌려주는 서버)를 직접 짜기로 했습니다.

지훈 씨는 학습 스크립트를 여러 번 짰습니다. 도커 이미지(코드와 실행 환경을 하나로 묶은 것)를 만들어 쿠버네티스(서버 여러 대를 띄우고 관리하는 플랫폼)에 올렸고 고친 코드가 CI 검사(코드를 고칠 때마다 자동으로 도는 검사)를 지나는 것도 봤습니다. 그런데 요청을 받아 답하는 서버 코드는 처음부터 짜 본 적이 없었습니다. 선배의 서버 코드를 읽기는 했는데 어디가 어려운 부분인지 감이 없었습니다.

선배에게 물었습니다. 「학습 스크립트는 짤 수 있는데, 서버는 무엇이 다릅니까?」 선배는 이렇게 답했습니다. 「끝나는 대신 기다립니다. 그것 말고 새로 배울 것은 셋뿐입니다.」 이어서 세 가지를 꼽았습니다. 「요청을 받는 함수의 모양, 여러 요청을 동시에 받는 법, 그리고 늦거나 실패했을 때 무엇을 돌려줄지입니다.」

**학습 스크립트를 짤 줄 아는 사람이 API 서버를 처음 짤 때, 새로 배워야 하는 것이 정말 세 가지뿐일까요?**

API 는 서버가 밖에 내놓는 주소와, 그 주소로 보내는 요청과 돌려받는 응답의 모양을 정해 둔 약속입니다. 추론 서버처럼 학습한 모델로 실제 요청에 답하는 일은 서빙이라고 부릅니다. 이 글은 학습 스크립트와 추론 서버의 코드를 나란히 놓고 같은 곳과 다른 곳을 찾은 뒤, 「사용자가 많다」는 말이 서버 한 대가 1초에 받는 요청 수로 어떻게 바뀌는지 계산합니다. 이 두 가지를 알고 나면 선배의 서버 코드에서 어디부터 읽을지, 서버 대수를 어떻게 계산하는지, 늦은 요청에 무엇을 돌려줄지가 보입니다.

> **한 줄 요약:** 학습 스크립트는 한 번 돌고 끝나지만 서버 코드는 끝나지 않고 다음 요청을 기다립니다. 기다리는 부분은 서버 라이브러리가 대신 하고 직접 쓰는 코드는 요청이 오면 부를 함수 하나입니다. 서버 대수는 사용자 수가 아니라 요청이 가장 몰리는 때(피크)의 초당 요청 수(QPS)에서 나오는데, 이 글의 가정으로는 피크 7,917 QPS 를 받는 데 서버 10대가 필요하고 장애와 배포 교체에 대비한 2대를 더해 12대입니다. 피처(모델에 넣는 입력 값)를 가져오는 피처 조회가 2ms 를 넘기면 더 기다리지 않고 기본 피처(받지 못한 피처 대신 넣는 정해 둔 값)로 점수를 내서 요청 하나의 응답 시간을 12ms 안에 지킵니다.

> **골라 읽는 법** — 번호가 붙은 절이 9개인 글입니다. 절마다 표나 코드가 하나씩 있어서 표나 코드만 보고 넘어가도 됩니다.
>
> - 학습 스크립트와 서버 코드의 여섯 가지 차이 → 1절
> - 표준 라이브러리만으로 API 를 띄우고 요청 하나를 보내는 코드 → 2절
> - 요청 하나의 예산 12ms 를 구간마다 나눈 표 → 3절
> - 사용자 수에서 서버 대수까지의 계산 → 4절
> - 늦은 요청에 돌려주는 응답 → 5절
> - 트래픽을 나눠 받는 세 층과 쿠버네티스 설정 항목의 서빙 이름 → 6~7절
> - 담장 안과 열린 RTB 에서 요청량과 예산을 정하는 곳 → 8절
> - 이 블로그의 API 와 서빙 글 8편을 읽는 순서 → 9절

이 글의 시간과 서버 대수는 모두 설명을 위해 정한 가상 값이며 그중 몇 가지는 다른 편과 같은 값을 씁니다. 모델 서버 12대, 모델 호출 예산(모델을 불러 점수를 받기까지 쓸 수 있는 시간) 8ms, 후보(이 사용자에게 보여 줄 수 있는 광고) 800건을 한 텐서(모델에 한 번에 넣는 숫자 배열)로 넣었을 때 걸리는 3.0ms 는 [추론 서버](post.html?id=inference-server) 편의 값입니다. 요청 전체 예산 12ms 는 [게이트웨이와 Ingress](post.html?id=gateway-ingress-router) 편에서 정했습니다. 하루 노출(광고가 화면에 보인 횟수) 2억 2,800만 건과 초당 2,639건은 [엔지니어링 기초 트랙](post.html?id=api-basics)의 표준값입니다. 요청 하나의 CPU 시간 6ms 와 피처 조회 2ms 는 이 글이 새로 둔 가정입니다.

## 1. 학습 스크립트와 서버 코드의 여섯 가지 차이

**학습 스크립트와 서버 코드는 둘 다 모델 파일을 열어 predict(입력을 받아 점수를 계산하는 함수)를 부르는 파이썬 프로그램입니다. 두 프로그램은 언제 시작하고 언제 끝나는지와 입력을 어디서 받고 출력을 어디로 보내는지가 다릅니다.**

지훈 씨는 선배의 서버 코드를 읽고도 어디가 어려운 부분인지 감이 없었는데, 학습 스크립트와 서버 코드를 나란히 놓으면 두 프로그램이 다른 자리는 여섯 군데로 좁혀집니다. 지훈 씨가 짜 온 학습 스크립트는 한 번 실행되면 데이터를 읽고 학습해 파일을 저장한 뒤 종료합니다. 서버 코드는 한 번 실행된 뒤 종료하지 않는 대신 모델 파일을 메모리에 올려 둔 채 요청이 올 때마다 predict 를 불러 답하고 다시 다음 요청을 기다립니다. 아래 표는 두 프로그램을 시작, 모델, 입력, 출력, 끝, 새로 쓰는 코드의 항목마다 나란히 비교합니다.

| 항목 | 학습 스크립트, train.py | 추론 서버, serve.py |
|---|---|---|
| 시작 | 명령 한 번으로 실행합니다 | 명령 한 번으로 실행하고, 그 뒤 계속 떠 있습니다 |
| 모델 | 끝에 파일로 저장합니다 | 시작할 때 파일을 열어 메모리에 올려 둡니다 |
| 입력 | 테이블이나 파일 전체를 읽습니다 | 요청 하나가 올 때마다 그 안의 JSON 을 읽습니다 |
| 출력 | 테이블이나 파일에 씁니다 | 응답 JSON 으로 바로 돌려줍니다 |
| 끝 | 다 돌면 종료합니다 | 종료하지 않습니다. 다음 요청을 기다립니다 |
| 새로 쓰는 코드 | 없습니다 | 「이 주소로 요청이 오면 이 함수를 불러라」 하나와, 그 함수의 입력 모양입니다 |

표의 여섯 줄 가운데 다섯 줄은 서버 라이브러리(서버가 하는 일을 미리 짜 둔 코드)가 맡습니다. 프로그램이 계속 떠 있는 것, 요청을 기다리는 것, 요청 본문을 읽어 함수에 넘기는 것, 응답을 보내는 것, 다음 요청으로 넘어가는 것이 모두 라이브러리의 몫입니다. 표의 JSON 은 키와 값을 글자로 적는 데이터 형식이고 요청 본문과 응답이 이 형식으로 오갑니다. 파이썬 표준 라이브러리(파이썬을 설치하면 함께 들어 있는 라이브러리)의 http.server 도, 웹 프레임워크(서버의 뼈대를 갖춰 두고 필요한 함수만 채우게 하는 라이브러리) FastAPI 와 그 앱을 띄우는 서버 uvicorn 도, 지난주에 쓴 BentoML 도 이 일을 똑같이 합니다. 지훈 씨가 직접 쓰는 코드는 표의 마지막 줄에 적힌 대로 요청이 오면 부를 함수 하나와 그 함수가 받는 입력의 모양뿐입니다.

그 함수 안에서 하는 일은 피처를 모아 텐서로 만든 뒤 predict 를 부르는 것으로 학습 때와 같습니다. 학습 스크립트에서 피처 테이블 한 벌을 텐서로 바꾸던 코드가 서버에서는 요청 하나에 담긴 후보 800건을 텐서로 바꾸는 코드가 되는데, [추론 서버](post.html?id=inference-server) 편에서 본 입력 변환이 이 코드입니다. 두 코드의 모양이 같아서 학습 코드를 그대로 옮겨 쓰는 팀이 많습니다.

함수 안의 일이 학습 때와 같으므로 서버 코드를 처음 짤 때 어려운 곳은 모델 쪽이 아닙니다. 한 번도 본 적 없는 「기다리는 부분」이 낯설어 어렵게 느껴질 뿐인데, 그 부분은 라이브러리가 하므로 직접 들여다볼 것이 거의 없습니다. 다음 절에서는 표준 라이브러리만 써서 기다리는 부분까지 포함한 서버 하나를 처음부터 끝까지 띄웁니다.

## 2. 표준 라이브러리만으로 띄운 API 서버

**아래 코드는 모델 하나를 API 로 띄우고 요청 하나를 보내 응답을 받은 뒤 서버를 내립니다. 지훈 씨는 그 가운데 핸들러 클래스(요청이 오면 라이브러리가 부를 메서드를 적어 두는 클래스)의 메서드 하나와 predict 함수만 직접 씁니다.**

프레임워크 없이 표준 라이브러리로 짜면 1절에서 라이브러리가 맡는다고 한 다섯 가지와 지훈 씨가 직접 쓰는 한 가지가 한 화면에 다 보여서 이 절의 코드는 표준 라이브러리만 씁니다. 실무에서는 FastAPI 나 BentoML 을 쓰지만 그 도구들이 하는 일도 같습니다. 가중치(학습이 정해 준 모델의 숫자)와 피처는 설명을 위해 정한 가상 값입니다. 피처 스토어(서빙할 때 피처를 꺼내 주는 저장소) 자리에는 파이썬 딕셔너리(키로 값을 찾는 자료형)를 두었습니다.

아래 코드는 요청 하나가 서버에 들어와 점수로 돌아오기까지의 순서와, 응답을 보낸 뒤에도 서버가 종료하지 않고 떠 있다는 점을 보려고 돌립니다. 3단계에서 서버는 다른 스레드(한 프로그램 안에서 따로 도는 실행 흐름)에서 기다리고 원래 스레드가 그 서버로 요청을 보내므로 프로그램 하나가 서버와 요청을 보내는 클라이언트를 함께 맡습니다.

```python
# 하는 일: 표준 라이브러리만으로 pCTR 점수 API 를 띄우고, 요청 하나를 보내 응답을 받은 뒤 서버를 내린다.
# 1단계: 모델과 피처를 둔다
# 학습이 남긴 가중치 대신 가상 가중치 셋을 두고, 피처 스토어 대신 딕셔너리를 둔다. predict 는 학습 때 쓰던 함수와 같은 모양이다.
import json, math, threading
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.request import Request, urlopen

WEIGHTS = {"bias": -4.0, "recent_ctr": 20.0, "is_video": 0.3}        # 가상 가중치
FEATURES = {"ad-101": {"recent_ctr": 0.030, "is_video": 1},           # 피처 스토어 대신 둔 표
            "ad-102": {"recent_ctr": 0.012, "is_video": 0},
            "ad-103": {"recent_ctr": 0.051, "is_video": 1}}

def predict(rows):
    scores = []
    for f in rows:
        z = WEIGHTS["bias"] + WEIGHTS["recent_ctr"] * f["recent_ctr"] + WEIGHTS["is_video"] * f["is_video"]
        scores.append(round(1 / (1 + math.exp(-z)), 4))
    return scores

# 2단계: 요청이 오면 부를 함수를 적는다
# 서버 틀은 라이브러리가 준다. 직접 적는 것은 「POST 가 오면 이렇게 답하라」 하나다. 후보 셋을 모아 predict 를 한 번만 부른다.
class ScoreHandler(BaseHTTPRequestHandler):
    def do_POST(self):
        body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        rows = [FEATURES[cid] for cid in body["candidate_ids"]]      # 피처 조회
        scores = predict(rows)                                       # 후보 셋을 한 번에
        reply = json.dumps({"scores": dict(zip(body["candidate_ids"], scores))}).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(reply)))
        self.end_headers()
        self.wfile.write(reply)
    def log_message(self, *args):                                    # 접근 로그는 끈다
        pass

# 3단계: 서버를 띄우고 요청 하나를 보낸다
# 포트 0 은 빈 포트를 하나 고르라는 뜻이다. 서버는 다른 스레드에서 기다리고, 이 스레드가 요청을 보낸다.
server = HTTPServer(("127.0.0.1", 0), ScoreHandler)
threading.Thread(target=server.serve_forever, daemon=True).start()
payload = {"user_id": "u-7", "candidate_ids": ["ad-101", "ad-102", "ad-103"]}
req = Request(f"http://127.0.0.1:{server.server_port}/score", method="POST",
              data=json.dumps(payload).encode(), headers={"Content-Type": "application/json"})
with urlopen(req, timeout=2) as resp:
    print("상태", resp.status, resp.headers["Content-Type"])
    print("응답", resp.read().decode())
server.shutdown()
print("서버를 내렸다. 학습 스크립트였다면 여기까지 오기 전에 이미 끝났다.")

# 출력:
# 3단계 뜻: 요청 하나가 들어와 상태 200 과 점수 셋이 JSON 으로 돌아왔다. 서버는 그 뒤에도 떠 있다가 shutdown 으로 내려간다.
# 상태 200 application/json
# 응답 {"scores": {"ad-101": 0.0431, "ad-102": 0.0228, "ad-103": 0.0642}}
# 서버를 내렸다. 학습 스크립트였다면 여기까지 오기 전에 이미 끝났다.
```

찍힌 값을 보면 요청 하나에 상태 200(웹의 요청과 응답 규약인 HTTP 에서 요청이 성공했다는 응답 코드)과 application/json(응답 본문이 JSON 이라는 표시)이 돌아왔고 응답 본문에는 후보 3개의 점수가 JSON 으로 들어 있습니다. 세 점수는 predict 가 학습 때와 같은 식으로 계산한 값입니다. ad-101 의 점수 0.0431 은 bias(피처와 상관없이 늘 더하는 값) -4.0 에 recent_ctr(최근 클릭률) 0.030 과 가중치 20.0 의 곱, is_video(동영상 여부) 1 과 가중치 0.3 의 곱을 더한 z 를 시그모이드(어떤 값이든 0 과 1 사이로 바꾸는 함수)에 넣고 소수 넷째 자리까지 반올림한 값입니다. 세 후보 가운데 recent_ctr 가 0.051 로 가장 높은 동영상 광고 ad-103 이 0.0642 로 가장 높은 점수를 받았고 recent_ctr 가 0.012 로 가장 낮은 데다 동영상도 아닌 ad-102 는 0.0228 로 가장 낮았습니다.

응답을 보낸 뒤에도 서버는 종료하지 않고 떠 있다가 3단계 끝에서 server.shutdown() 을 부른 뒤에야 내려갑니다. 마지막 줄이 적은 대로 학습 스크립트였다면 이 줄에 오기 전에 이미 끝났습니다.

코드를 위에서 아래로 따라가면 요청 하나가 처리되는 순서가 보입니다. 서버는 포트(한 컴퓨터 안에서 요청을 받을 프로그램을 정하는 번호)에서 기다리는데, 코드처럼 포트 번호로 0 을 주면 비어 있는 포트를 하나 골라 씁니다. 요청 본문이 오면 서버는 JSON 으로 읽은 뒤 본문의 후보 ID 3개로 피처를 조회하고 후보 3개를 모아 predict 를 한 번만 부릅니다. 점수를 JSON 으로 만들어 돌려준 다음에는 다시 다음 요청을 기다립니다. 이 순서 가운데 지훈 씨가 do_POST 안에 직접 쓴 줄은 피처 조회, predict 호출, 응답 조립의 3줄입니다. do_POST 는 POST 요청(본문에 데이터를 담아 보내는 요청)이 올 때 라이브러리가 부르는 메서드입니다.

이 코드에는 학습 스크립트와 다른 자리가 3곳 있는데 선배가 꼽은 세 가지가 바로 이 3곳입니다.

- **함수의 모양.** 입력이 파일이 아니라 요청 본문이고 출력도 파일이 아니라 응답입니다.
- **동시성(여러 요청을 동시에 받아 처리하는 방법).** 이 코드는 요청을 한 번에 하나씩 처리하므로 요청 2개가 겹치면 뒤에 온 요청이 앞 요청이 끝날 때까지 기다립니다. 실무에서는 프로세스(따로 실행되는 프로그램 하나)를 여러 개 띄워 요청을 나눠 받는데, 몇 개를 띄울지는 4절에서 계산합니다.
- **실패 처리.** 이 코드에는 늦거나 실패했을 때 할 일이 적혀 있지 않아서 피처 조회가 늦거나 후보 ID 가 피처 표에 없으면 그대로 멈춥니다. 5절에서 그 자리를 채웁니다.

세 가지 가운데 함수 모양은 반나절이면 익히지만 동시성과 실패 처리는 프로세스를 몇 개 띄울지, 몇 ms 까지 기다릴지 같은 숫자를 정하는 일이라 하나에 하루씩 듭니다. 다음 절부터 그 숫자를 계산하는데, 먼저 요청 하나에 쓸 수 있는 시간부터 나눕니다.

## 3. 요청 하나의 12ms 예산 배분

**요청 전체 예산이 12ms 이면 그 12ms 를 구간마다 나눠 적어 둡니다. 모델 호출 8ms, 피처 조회 2ms, 후보 조회 1ms, 게이트웨이(요청을 처음 받아 서버 한 대에 넘기는 곳)와 응답 조립 1ms 입니다. 구간마다 예산이 있어야 어느 구간이 예산을 넘겼는지 알 수 있습니다.**

[게이트웨이와 Ingress](post.html?id=gateway-ingress-router) 편에서는 입찰 요청(광고 자리 하나에 어떤 광고를 낼지 정해 달라는 요청) 하나의 예산을 12ms 로 정했습니다. 이 12ms 는 서버 코드 한 곳이 다 쓰는 시간이 아니라 [Ad Serving Flow](post.html?id=ad-serving-flow) 편의 여덟 단계가 나눠 쓰는 시간이어서 전체 예산만 정해 두면 요청이 늦었을 때 어느 구간이 늦었는지 알 수 없습니다. 이 팀은 12ms 를 아래 표처럼 다섯 구간에 나눴는데, 모델 호출 8ms 는 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편의 값이고 나머지 구간의 예산은 이 글의 가정입니다.

| 구간 | 예산 | 하는 일 | 넘기면 (예산을 넘겼을 때 하는 일) |
|---|---|---|---|
| 게이트웨이 | 0.5ms | 요청을 받아 서버 한 대에 넘깁니다 | 다른 서버로 보냅니다 |
| 후보 조회 | 1ms | 이 사용자에게 보여도 되는 광고 800건을 꺼냅니다 | 어제 만들어 둔 후보 목록을 씁니다 |
| 피처 조회 | 2ms | 사용자 한 줄과 광고 800줄을 피처 스토어에서 가져옵니다 | 기본 피처로 점수를 냅니다 |
| 모델 호출 | 8ms | 후보 800건을 한 텐서로 넣어 점수를 냅니다. 보통 3.0ms 입니다 | 인기도 점수로 순위를 매깁니다 |
| 응답 조립 | 0.5ms | 점수를 JSON 으로 만들어 돌려줍니다 | 넘길 일이 거의 없습니다 |

표의 예산을 더하면 게이트웨이 0.5ms, 후보 조회 1ms, 피처 조회 2ms, 모델 호출 8ms, 응답 조립 0.5ms 로 12ms 입니다. 보통 때 실제로 쓰는 시간은 예산보다 짧은데, 모델 호출은 예산이 8ms 이지만 보통 3.0ms 에 끝나므로 8ms 에서 3.0ms 를 뺀 5ms 는 느린 요청이 쓰도록 남겨 둔 몫입니다. 요청 100건을 빠른 것부터 늘어놓았을 때 99번째 요청이 쓴 시간을 p99 라고 부릅니다. 평균이 멀쩡해 보여도 하루 1,053만 건이 예산을 넘기는 일이 생기므로 예산은 평균이 아니라 p99 에 맞춥니다. 하루 1,053만 건이 나오는 계산은 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편 3절에 있습니다.

구간마다 예산을 넘겼을 때 무엇을 할지 적혀 있어야 한 구간이 느려져도 요청 전체가 실패하지 않으므로 이 표에서는 「넘기면」 열을 가장 눈여겨봅니다. 표대로 피처 조회가 늦으면 기본 피처로 점수를 내고 모델 호출이 늦으면 인기도 점수로 순위를 매기는데, 광고가 안 나가는 것보다 덜 정확한 광고라도 나가는 편이 낫기 때문입니다. 5절에서 이 결정을 코드로 옮깁니다.

예산 표는 선배의 서버 코드에서 어디부터 읽을지도 정해 줍니다. 구간마다 시작과 끝에 시각을 기록하는 줄이 있을 것이고 그 줄이 남긴 값이 대시보드(서버 지표를 그래프로 보여 주는 화면)의 p99 가 되는데, 구간이 어디서 끊기는지가 그 줄에 적혀 있으므로 지훈 씨는 predict 보다 그 시각 기록 줄을 먼저 찾습니다.

## 4. 사용자 수에서 서버 대수까지의 계산

**서버 설계의 입력은 「사용자가 많다」는 말이 아니라 초당 요청 수(QPS)입니다. 하루 노출 2억 2,800만 건을 초로 나누면 평균 2,639 QPS 이고 피크는 7,917 QPS 입니다. 그 피크를 8코어 서버가 안전선(CPU 를 이 비율까지만 쓰기로 정한 선) 60% 로 받으면 10대가 필요하고 예비까지 12대입니다.**

지훈 씨는 사용자 전부의 요청을 자기 서버가 받아야 한다고 생각해서 이 대목을 가장 걱정했습니다. 그런데 계산해 보면 그 걱정은 숫자 4개, 곧 하루 요청 수, 피크 배수(피크가 평균의 몇 배인지), 요청 하나의 CPU 시간(CPU 가 그 요청을 계산하는 데 쓴 시간), 서버 한 대의 코어(CPU 안에서 계산을 하나씩 맡아 돌리는 단위) 수로 줄어듭니다. 아래 코드는 이 숫자들에서 출발해 평균과 피크의 QPS, 피크에 동시에 처리 중인 요청 수, 서버 대수를 차례로 계산해 보려고 돌립니다. 하루 노출 수는 [엔지니어링 기초 트랙](post.html?id=api-basics)의 표준값이고 나머지는 이 글의 가정입니다.

```python
# 하는 일: 하루 노출 수에서 피크 초당 요청 수, 동시 요청 수, 서버 대수를 차례로 센다.
# 1단계: 숫자 넷을 둔다
# 하루 노출 2억 2,800만 건은 엔지니어링 기초 트랙의 값이다. 피크는 평균의 3배, 요청 하나의 CPU 시간은 6ms, 요청 하나의 지연은 7ms 로 둔다(가상 값). 서버는 8코어이고 CPU 는 60% 까지만 쓴다.
import math
DAILY, PEAK_RATIO = 228_000_000, 3
CPU_MS, LATENCY_MS = 6.0, 7.0
CORES, SAFE_RATIO = 8, 0.60
# 2단계: 평균과 피크 QPS 를 센다
# 하루는 86,400초다.
avg_qps = DAILY / 86_400
peak_qps = avg_qps * PEAK_RATIO
print(f"평균 {avg_qps:,.0f} QPS, 피크 {peak_qps:,.0f} QPS")
# 3단계: 동시에 처리 중인 요청 수를 센다
# 동시 요청 수 = 초당 요청 수 × 요청 하나의 지연(초). 이 수만큼 워커가 있어야 줄이 안 선다.
concurrent = peak_qps * LATENCY_MS / 1000
print(f"피크에 동시에 처리 중인 요청 {concurrent:.0f}건")
# 4단계: 서버 한 대의 처리량과 대수를 센다
# 코어 하나는 1초에 1,000ms 를 쓴다. 요청 하나가 6ms 면 코어당 초당 요청 수가 나온다. 60% 만 쓰는 이유는 100% 로 돌리면 p99 가 길어지기 때문이다.
per_core = 1000 / CPU_MS
per_server = per_core * CORES * SAFE_RATIO
need = math.ceil(peak_qps / per_server)
print(f"코어당 {per_core:.0f} QPS, 8코어 서버 한 대 {per_server:,.0f} QPS (60% 만 쓸 때)")
print(f"피크를 받는 데 {need}대, 장애와 배포 교체 몫 2대를 더해 {need + 2}대")
print(f"평균 때 서버 한 대가 받는 요청 초당 {avg_qps / (need + 2):.0f}건")

# 출력:
# 2단계 뜻: 하루 2억 2,800만 건은 평균 2,639 QPS 이고 피크는 7,917 QPS 다.
# 평균 2,639 QPS, 피크 7,917 QPS
# 3단계 뜻: 피크에 서버들 안에 동시에 55건이 있다. 12대로 나누면 한 대에 5건이 안 된다.
# 피크에 동시에 처리 중인 요청 55건
# 4단계 뜻: 코어당 167 QPS, 한 대 800 QPS 라 10대가 필요하고 예비 2대를 더해 12대다. 평균 때는 한 대가 초당 220건을 받는다.
# 코어당 167 QPS, 8코어 서버 한 대 800 QPS (60% 만 쓸 때)
# 피크를 받는 데 10대, 장애와 배포 교체 몫 2대를 더해 12대
# 평균 때 서버 한 대가 받는 요청 초당 220건
```

찍힌 값을 단계마다 따라가면 이렇습니다. 2단계에서 하루 2억 2,800만 건을 하루의 초 수 86,400 으로 나누면 평균 2,639 QPS 입니다. 저녁 시간대에 요청이 몰리는 피크를 평균의 3배로 보면 피크는 2,639 의 3배인 7,917 QPS 입니다.

3단계의 동시에 처리 중인 요청 수는 초당 요청 수에 요청 하나가 서버 안에 머무는 시간(지연)을 곱한 값입니다. 피크 7,917 QPS 에 지연 7ms 를 1,000 으로 나눠 초로 바꾼 값을 곱하면 피크에 서버들 안에 동시에 들어 있는 요청은 55건입니다. 이 55건을 서버 12대로 나누면 한 대에 5건이 안 되므로 8코어 서버에 워커(요청을 하나씩 맡아 처리하는 프로세스) 8개를 두면 요청이 대기열에서 기다리지 않습니다.

4단계에서 서버 대수가 나옵니다. 코어 하나는 1초에 1,000ms 를 계산에 쓸 수 있으므로 요청 하나에 CPU 6ms 가 들면 1,000 을 6 으로 나눈 167건을 1초에 처리합니다. 8코어면 1,000 을 6 으로 나눈 값의 8배인 1,333건인데, CPU 를 100% 로 돌리면 p99 가 길어지므로 안전선 60% 까지만 쓰기로 하면 서버 한 대는 1,333 의 60% 인 800 QPS 를 받습니다. 피크 7,917 QPS 를 800 으로 나눈 값을 올림하면 10대입니다. 서버 한 대가 죽어도 피크를 받아야 하고 배포 중에는 2대씩 빠지므로 여기에 2대를 더해 12대를 둡니다. 평균 때는 2,639 QPS 를 12대가 나눠 받아 서버 한 대가 초당 220건을 받는데, [추론 서버](post.html?id=inference-server) 편의 서버 12대와 서버 한 대가 평균 때 받는 초당 220건이 이 계산에서 나온 값입니다.

이 계산에서 결정 2가지가 나옵니다. 첫째로 서버 대수 12 를 쿠버네티스 설정의 복제본 수(같은 서버를 몇 개 띄울지 적는 값)에 적습니다. 둘째로 요청 하나의 CPU 시간 6ms 를 줄입니다. CPU 시간이 6ms 에서 3ms 로 줄면 코어 하나가 1초에 1,000 을 3 으로 나눈 333건을 처리해 코어당 처리량이 2배가 되므로 피크를 받는 데 필요한 서버도 10대에서 5대로 줄어듭니다. CPU 시간을 줄이는 데는 후보 800건을 하나씩 모델에 넣지 않고 한 텐서로 모아 한 번에 넣는 일이 가장 큰 몫을 하는데, [추론 서버](post.html?id=inference-server) 편 4절이 두 방식의 차이를 한 텐서로 넣을 때 3.0ms, 하나씩 넣을 때 96ms 로 측정했습니다.

사용자가 10배가 되면 이 계산에서는 첫 줄의 하루 노출 수만 바뀌고 서버 대수가 10배가 됩니다. 모델 서버가 상태(요청과 요청 사이에 서버가 기억해 두는 데이터)를 들고 있지 않아서 서버 대수를 10배로 늘리는 것만으로 늘어난 요청을 받을 수 있습니다.

## 5. 늦은 요청에 돌려주는 응답

**피처 조회가 2ms 를 넘기면 더 기다리지 않고 기본 피처로 점수를 냅니다. 기다리는 상한(타임아웃)이 없으면 요청 10건 중 2건이 12ms 를 넘기지만 타임아웃과 대신 돌려주는 값(폴백)을 넣으면 넘기는 요청이 0건이 되는 대신 2건이 덜 정확한 점수로 나갑니다.**

2절의 코드는 피처 조회가 늦으면 그대로 멈췄는데, 그 자리를 채우는 실패 처리에서는 얼마나 기다릴지와 기다리기를 멈추면 무엇을 돌려줄지의 두 가지를 정합니다. 기다리는 상한을 타임아웃(timeout), 기다리기를 멈췄을 때 대신 돌려주는 값을 폴백(fallback)이라고 부릅니다.

아래 코드는 피처 조회 시간이 들쭉날쭉한 요청 10건을 두고 타임아웃 없이 끝까지 기다릴 때와 2ms 에서 끊을 때를 비교해 예산을 넘기는 요청과 폴백으로 나가는 요청이 각각 몇 건인지 세어 보려고 돌립니다. 조회 시간은 가상 값이며 넷째와 일곱째 요청의 8.2ms 와 11.0ms 는 피처 스토어가 느려진 순간에 들어온 요청의 값입니다. 다른 구간은 게이트웨이 0.5ms, 후보 조회 1ms, 모델 호출 3ms, 응답 조립 0.5ms 로 늘 같다고 두었으므로 요청 하나의 시간은 이 네 구간의 합 5ms 에 조회 시간을 더한 값입니다.

```python
# 하는 일: 피처 조회가 늦은 요청에 타임아웃과 폴백을 넣으면 예산을 넘기는 요청 수가 어떻게 바뀌는지 센다.
# 1단계: 요청 10건의 피처 조회 시간을 둔다
# 조회 시간은 가상 값이다. 넷째와 일곱째 요청은 피처 스토어가 느려진 순간에 들어온 것이다. 다른 구간은 게이트웨이 0.5ms, 후보 조회 1ms, 모델 호출 3ms, 응답 조립 0.5ms 로 늘 같다고 둔다.
lookups_ms = [1.1, 0.9, 1.4, 8.2, 1.0, 1.2, 11.0, 1.3, 0.8, 1.1]
OTHER_MS = 0.5 + 1.0 + 3.0 + 0.5
BUDGET_MS, TIMEOUT_MS = 12.0, 2.0
# 2단계: 타임아웃 없이 끝까지 기다린다
# 요청 하나의 시간은 다른 구간 5ms 에 조회 시간을 더한 값이다.
no_timeout = [OTHER_MS + lk for lk in lookups_ms]
over = [t for t in no_timeout if t > BUDGET_MS]
print(f"타임아웃 없이: 가장 느린 요청 {max(no_timeout):.1f}ms, 예산 12ms 를 넘긴 요청 {len(over)}건")
# 3단계: 2ms 에서 끊고 기본 피처로 점수를 낸다
# 조회가 2ms 를 넘기면 그때까지 기다린 2ms 만 쓰고 기본 피처로 모델을 부른다. 그 요청은 점수가 덜 정확하다.
with_timeout = [OTHER_MS + min(lk, TIMEOUT_MS) for lk in lookups_ms]
fallbacks = [lk for lk in lookups_ms if lk > TIMEOUT_MS]
print(f"타임아웃 2ms: 가장 느린 요청 {max(with_timeout):.1f}ms, 예산을 넘긴 요청 {sum(t > BUDGET_MS for t in with_timeout)}건")
print(f"대신 기본 피처로 점수를 낸 요청 {len(fallbacks)}건 (조회에 {fallbacks[0]:.1f}ms, {fallbacks[1]:.1f}ms 걸리던 것)")

# 출력:
# 2단계 뜻: 끝까지 기다리면 느려진 순간의 요청 2건이 예산 12ms 를 넘긴다. 가장 느린 것은 16.0ms 다.
# 타임아웃 없이: 가장 느린 요청 16.0ms, 예산 12ms 를 넘긴 요청 2건
# 3단계 뜻: 2ms 에서 끊으면 가장 느린 요청도 7.0ms 라 넘기는 요청이 0건이다. 대신 2건은 기본 피처로 낸 점수를 받는다.
# 타임아웃 2ms: 가장 느린 요청 7.0ms, 예산을 넘긴 요청 0건
# 대신 기본 피처로 점수를 낸 요청 2건 (조회에 8.2ms, 11.0ms 걸리던 것)
```

찍힌 값을 보면 타임아웃 없이 끝까지 기다릴 때는 가장 느린 요청이 16.0ms 이고 예산 12ms 를 넘긴 요청이 2건입니다. 넷째 요청은 5ms 에 조회 8.2ms 를 더한 13.2ms, 일곱째 요청은 5ms 에 11.0ms 를 더한 16.0ms 가 되어 둘 다 12ms 를 넘기는데, 예산을 넘긴 요청은 게이트웨이가 버리므로 이 두 요청의 사용자는 광고를 보지 못합니다.

타임아웃을 2ms 에 걸면 같은 2건은 조회를 2ms 까지만 기다린 뒤 기본 피처로 모델을 부르므로 5ms 에 2ms 를 더한 7.0ms 에 끝나고 10건 가운데 예산을 넘기는 요청은 0건이 됩니다. 대신 그 2건은 그 사용자의 최근 행동 피처 없이 기본 피처로 낸 점수를 받아 덜 정확한 광고가 나갑니다.

광고가 안 나가는 비용과 덜 정확한 광고가 나가는 비용을 비교해 타임아웃 값을 정하는 저울질이 실패 처리의 전부입니다. 피처 조회는 보통 1ms 안팎이라 타임아웃 2ms 는 보통 요청은 자르지 않고 느려진 순간의 요청만 자릅니다. 위 10건에서도 보통 요청 8건은 조회 시간이 0.8ms 에서 1.4ms 사이라 하나도 잘리지 않았고 8.2ms 와 11.0ms 가 걸린 2건만 잘렸습니다. 모델 호출에도 같은 방식으로 타임아웃을 걸고 넘기면 인기도 점수로 순위를 매깁니다. 3절 표의 「넘기면」 열이 이렇게 타임아웃과 폴백이 되어 코드로 들어갑니다.

지훈 씨는 선배의 서버 코드에서 시각 기록 줄 다음으로 피처 스토어를 부르는 줄을 찾아 타임아웃 값을 적은 줄과 넘겼을 때 돌려줄 값을 적은 줄이 있는지 봅니다. 이 두 줄이 없으면 피처 스토어가 느려지는 날 서버 12대가 모두 예산을 넘기므로, 두 줄은 한 구간의 지연이 요청 전체의 장애로 이어지지 않게 막아 줍니다.

## 6. 트래픽을 나눠 받는 세 층

**사용자 전부의 요청을 모델 서버 혼자 받는 구조는 없습니다. 플랫폼이 요청을 나누고 서버 수를 조절하며 앞단 서버가 피처를 모아 모델 서버를 부릅니다. 모델 서버는 받은 배치(모델에 한 번에 넣도록 모은 입력)를 점수로 바꾸는 한 층입니다.**

4절에서 계산한 12대가 요청이 지나는 길의 어디에 놓이는지 알면 지훈 씨가 맡는 범위도 보입니다. 아래 표는 요청이 지나는 세 층을 층마다 트래픽에서 하는 일, 누가 만들고 운영하는지, 모델 엔지니어(모델을 만드는 엔지니어)가 그 층에 적어 주어야 하는 것으로 나눠 보여 줍니다.

| 층 | 트래픽에서 하는 일 | 누가 만들고 운영하나 | 모델 엔지니어가 적어 주는 것 |
|---|---|---|---|
| 플랫폼 | 로드밸런서가 요청을 서버 12대에 나눕니다. 오토스케일이 서버 수를 늘리고 줄입니다. 대시보드와 알람이 붙어 있습니다 | 플랫폼 팀. 쿠버네티스와 게이트웨이 | 서버 한 대가 받는 QPS, 요청 하나의 CPU 와 메모리, 늘리는 기준 |
| 앞단 서버 | 요청을 받아 후보와 피처를 모으고 모델 서버를 부릅니다. 타임아웃과 폴백을 겁니다. 예측 로그를 남깁니다 | 서빙 엔지니어. 작은 팀이면 모델 엔지니어가 같이 | 입력과 출력의 모양, 구간별 예산, 폴백 점수 |
| 모델 서버 | 받은 배치를 점수로 바꿉니다. 상태를 들고 있지 않아 몇 대를 띄워도 같습니다 | 모델 엔지니어 | 요청 하나의 비용, 메모리, 웜업, 부하 시험으로 측정한 서버 한 대의 QPS |

모델 엔지니어는 셋째 층인 모델 서버의 효율과 숫자를 책임집니다. 요청 하나의 CPU 시간을 6ms 에서 3ms 로 줄이고 모델을 메모리에 한 번만 올려 둡니다. 그리고 서버 한 대가 몇 QPS 를 받는지 부하 시험(일부러 요청을 많이 보내 서버가 받아 내는 양을 측정하는 시험)으로 측정해 첫째 층에 적어 줍니다. 표의 셋째 줄에 있는 웜업(서버가 실제 요청을 받기 전에 시험용 요청을 먼저 처리해 첫 계산의 준비를 끝내 두는 단계)은 7절에서 다시 나옵니다.

첫째 층인 플랫폼은 로드밸런서(요청을 여러 서버에 나눠 보내는 장치)로 요청을 서버 12대에 나누고 오토스케일(부하에 따라 서버 수를 자동으로 늘리고 줄이는 기능)로 서버 수를 조절합니다. 대시보드와 알람(지표가 기준을 넘으면 담당자에게 알리는 기능)도 이 층에 붙어 있습니다. 로드밸런서를 만들거나 오토스케일 규칙을 짜거나 클러스터(함께 운영하는 서버 여러 대의 모음)를 운영하는 일은 첫째 층의 몫이며 회사마다 이미 있습니다.

둘째 층인 앞단 서버는 요청을 받아 후보와 피처를 모으고 모델 서버를 부르며 타임아웃과 폴백을 걸고 예측 로그(어떤 요청에 어떤 점수를 냈는지 남기는 기록)를 남기는데, 이 층을 누가 맡는지는 팀 크기에 따라 다릅니다. 서빙 엔지니어가 따로 있는 팀에서는 모델 엔지니어가 입력과 출력의 모양과 폴백 점수만 정하지만 작은 팀에서는 모델 엔지니어가 둘째 층의 코드도 씁니다. 지훈 씨의 팀은 둘째 층과 셋째 층을 한 서버 코드에 함께 두어서 선배의 서버 코드에도 피처 조회와 타임아웃이 같이 들어 있었습니다. 3절과 5절에서 찾기로 한 시각 기록 줄과 피처 스토어를 부르는 줄이 그 코드의 둘째 층 부분입니다.

세 층으로 나눠 보면 「엄청 잘 설계해야 하는 자리」가 어디인지도 보입니다. 모델 서버는 상태가 없어서 대수만 늘리면 되지만 피처 스토어와 캐시(자주 쓰는 값을 빨리 읽도록 따로 복사해 두는 저장소)는 여러 서버가 같이 쓰는 자리라서 설계가 어렵습니다. 이 자리는 둘째 층과 첫째 층이 같이 보며 [Feature Store](post.html?id=feature-store-serving) 편이 다룹니다.

## 7. 쿠버네티스 설정 항목과 서빙 용어의 짝

**지훈 씨가 이미 써 본 쿠버네티스 설정의 값들은 이 글의 숫자와 하나씩 짝을 이룹니다. 복제본 수가 서버 대수이고 HPA(HorizontalPodAutoscaler)가 오토스케일이며 readiness probe(요청을 받을 준비가 됐는지 확인하는 검사)가 웜업이 끝났다는 신호입니다.**

도커 이미지를 만들어 쿠버네티스에 올려 본 사람은 이름만 다를 뿐 서빙 용어의 절반을 이미 압니다. 아래 표의 왼쪽 열은 [Docker 와 CI](post.html?id=container-ci-pipeline) 편과 [쿠버네티스 네트워킹](post.html?id=kubernetes-networking) 편에서 본 설정 항목이고 가운데 열은 서빙에서 부르는 이름, 오른쪽 열은 이 글에서 그 항목에 적는 값입니다.

| 이미 아는 것 | 서빙에서의 이름 | 이 글에서 적는 값 |
|---|---|---|
| 도커 이미지 | 모델 서버 한 벌 | 모델 파일 38MB, 서버 코드, 런타임. 학습 이미지와 다른 것은 시작 명령뿐입니다 |
| Deployment 의 replicas | 서버 대수 | 4절의 12 |
| resources 의 cpu | 코어 수 | 4절의 8코어. 코어당 167 QPS 를 곱하면 서버 한 대의 처리량입니다 |
| HPA | 오토스케일 | CPU 60% 를 넘으면 늘립니다. 늘어나는 데 41초가 걸리니 급증은 폴백이 먼저 받습니다 |
| Service 와 Ingress | 로드밸런서 | 요청을 12대에 나눕니다. 6절의 첫째 층입니다 |
| readiness probe | 웜업이 끝났다는 신호 | 모델을 올리고 웜업 200건이 끝나기 전에 요청이 오면 2.5배 느립니다. 그 전에는 트래픽을 받지 않게 하는 장치입니다 |
| liveness probe | 죽은 서버 교체 | 응답이 없으면 서버를 다시 띄웁니다 |
| ConfigMap 과 환경 변수 | 타임아웃과 모델 버전 | 5절의 2ms 와 3절의 8ms, 어느 모델 파일을 읽을지 |
| CI 의 이미지 빌드와 배포 | 모델 배포와 롤백 | 롤백은 이전 이미지 태그로 되돌리는 일입니다 |
| 롤링 업데이트와 카나리 | 새 모델 1% 트래픽 | 새 버전 서버를 일부만 띄워 p99 와 CTR 을 보고 늘립니다 |

표의 Deployment 는 같은 서버를 몇 개(replicas) 어떤 자원(resources)으로 띄울지 적는 쿠버네티스 설정입니다. ConfigMap 에는 코드를 고치지 않고도 바꿀 수 있게 설정 값을 코드 밖에 따로 적어 둡니다. 롤링 업데이트는 서버를 몇 대씩 차례로 새 버전으로 바꿔 나가는 배포 방식입니다. resources 의 cpu 줄이 말하는 서버 한 대의 처리량은 4절에서 계산한 대로 CPU 를 다 쓰면 1,333 QPS 가 되고 안전선 60% 까지만 쓰면 800 QPS 가 됩니다.

readiness probe 는 서버에게 요청을 받을 준비가 됐는지 묻는 검사로, 준비가 됐다고 답한 서버에만 요청이 갑니다. [추론 서버](post.html?id=inference-server) 편 3절과 6절에 따르면 새 서버는 뜨고 41초가 지나야 요청을 받을 준비가 되는데, 그 전에 요청을 받기 시작하면 서버 2대를 바꿀 때마다 폴백이 5,637건 더 나갑니다. 그래서 서빙에는 readiness probe 가 꼭 필요하고 쿠버네티스 설정의 readinessProbe 한 블록이 그 41초 동안 새 서버에 요청이 가지 않게 지켜 줍니다. HPA 가 서버를 늘릴 때도 새 서버는 같은 41초를 기다려야 해서 트래픽이 갑자기 늘면 오토스케일로 늘어난 서버보다 5절의 폴백이 먼저 늘어난 요청을 받습니다.

롤백(새 버전을 이전 버전으로 되돌리는 일)도 이미 아는 방식으로 합니다. [모델 배포와 롤백](post.html?id=model-deployment-rollback) 편에서 새 모델을 트래픽 1% 로 시작해 15분 안에 되돌리는 순서는 카나리 배포(새 버전을 일부 트래픽에만 먼저 내보내는 배포)와 이미지 태그(이미지마다 붙인 버전 이름) 되돌리기로 이루어집니다. 모델 서버에서는 모델 버전과 피처 버전을 짝으로 기록하는 일 하나가 새로 생깁니다. 모델만 바꾸고 피처 변환(원본 데이터를 모델 입력 피처로 바꾸는 처리)을 그대로 두면 오류 없이 조용히 틀린 점수가 나오는데, 이 문제가 [Feature Store](post.html?id=feature-store-serving) 편의 주제입니다.

## 8. 무대에 따른 숫자의 출처

**4절의 계산은 두 무대에서 같고 첫 줄의 숫자를 누가 주느냐만 다릅니다. 담장 안(한 회사가 앱과 서버를 다 가진 환경)에서는 우리가 요청량을 알지만 열린 RTB(Real-Time Bidding, 거래소가 광고 자리를 실시간 경매에 부치는 환경)에서는 거래소가 예산과 트래픽을 정합니다.**

### 담장 안: 우리 로그에서 오는 요청량 [무대: 닫힌 생태계]

담장 안에서는 하루 노출 2억 2,800만 건과 저녁 피크가 우리 로그에 남아 있으므로 4절 계산의 첫 줄에 어제 값을 적어 내일 필요한 대수를 계산합니다. 피처도 회원 ID 로 미리 만들어 두므로 피처 조회는 보통 2ms 안에 끝납니다. 요청 전체 예산 12ms 도 우리 게이트웨이가 정한 값이어서 3절의 구간 배분을 우리가 바꿀 수 있습니다. 이 블로그의 저자가 일하는 무대도 담장 안입니다. 이 글의 표와 코드는 모두 이 무대의 상태를 적었습니다.

### 열린 RTB: 거래소가 정하는 요청량과 예산 [무대: 열린 RTB]

열린 RTB 의 입찰 서버(입찰 요청에 답하는 서버)는 남의 거래소(광고 자리를 경매에 부치는 플랫폼)가 보내는 요청을 받습니다. 요청량이 거래소 사정에 따라 갑자기 크게 늘었다 줄었다 하므로 4절의 피크 배수 3 을 우리가 정할 수 없습니다. 예산도 거래소가 정하는데 그 안에 네트워크 왕복 시간(요청이 거래소와 우리 서버 사이를 오가는 시간)이 들어 있어서 서버가 쓸 수 있는 시간은 더 짧습니다. 요청에는 회원 ID 대신 쿠키(브라우저에 남겨 둔 식별 값)가 담겨 오므로 피처를 미리 만들어 둘 수 없고 피처 조회 대신 그 자리에서 계산하는 몫이 붙습니다. 그래서 열린 RTB 에서도 4절과 같은 계산을 하되 첫 줄에는 거래소별 로그의 피크를 적고 폴백도 담장 안보다 더 자주 나갑니다.

| 무엇 | 담장 안 | 열린 RTB |
|---|---|---|
| 하루 요청 수와 피크 | 우리 로그에서 읽습니다 | 거래소별 로그를 합쳐 읽고 급증하는 때에 맞춥니다 |
| 요청 전체 예산 | 우리 게이트웨이가 정한 12ms | 거래소마다 다르고 가장 짧은 곳에 맞춥니다 |
| 피처 조회 | 회원 ID 로 미리 만든 값을 2ms 안에 | 쿠키라 그 자리에서 계산하는 몫이 붙습니다 |
| 폴백이 나가는 빈도 | 피처 스토어가 느려진 순간뿐 | 트래픽이 급증할 때마다 더 자주 |

## 9. API 와 서빙 글 8편을 읽는 순서

**이 블로그에는 API 와 서빙 글이 8편 있습니다. 모델을 만들던 사람이 서버를 처음 짤 때는 아래 순서가 맞으며 요청 하나가 모델을 지나 돌아오는 길만 따라가면 됩니다.**

이 순서는 백엔드 개발자(서버 쪽 프로그램을 만드는 개발자)가 API 를 배우는 순서와 다릅니다. HTTP 전체를 먼저 보지 않고 이 글의 세 가지인 함수 모양, 동시성, 실패 처리를 채우는 글부터 읽습니다. 표의 순서 열이 읽는 차례이고 오른쪽 열은 그 글에서 가져갈 것 하나입니다.

| 순서 | 글 | 거기서 가져갈 것 |
|---|---|---|
| 1 | [API 기초](post.html?id=api-basics) | 요청과 응답이 반드시 짝이라는 것, 메서드 5가지, 로그가 남는 두 자리 |
| 2 | [추론 서버](post.html?id=inference-server) | 모델 파일이 서버가 되는 41초, 후보 800건을 한 텐서로 넣는 이유 |
| 3 | [서빙 지연, 처리량과 Grafana](post.html?id=serving-latency-throughput) | latency, throughput, QPS 의 뜻과 p99 를 어디서 측정하는가 |
| 4 | [API 연동 실무](post.html?id=api-kinds-and-contracts) | 타임아웃과 재시도, 다시 보내기가 가장 비싼 실수인 이유 |
| 5 | [BentoML](post.html?id=bentoml-model-serving) | 서버 기능 7가지 중 4가지를 도구가 대신 만들어 주는 것과 그 비용 |

## 한눈 정리

| 질문 | 한 줄 답 |
|---|---|
| 학습 스크립트와 서버 코드는 무엇이 다른가 | 끝나는가, 기다리는가입니다. 기다리는 부분은 라이브러리가 합니다 |
| 직접 쓰는 것은 | 요청이 오면 부를 함수 하나와 그 입력 모양입니다 |
| 새로 배우는 것은 | 함수 모양, 동시성, 실패 처리 세 가지입니다 |
| 요청 하나의 예산은 | 12ms. 모델 호출 8, 피처 조회 2, 후보 조회 1, 게이트웨이와 조립 1 |
| 사용자 수는 어떻게 숫자가 되나 | 하루 2억 2,800만 건이 평균 2,639 QPS, 피크 7,917 QPS 입니다 |
| 서버는 몇 대인가 | 요청당 CPU 6ms, 8코어, 60% 로 10대. 예비 2대를 더해 12대 |
| 늦은 요청에는 | 피처 조회 2ms 에서 끊고 기본 피처로 점수를 냅니다 |
| 트래픽은 누가 받나 | 플랫폼, 앞단 서버, 모델 서버 세 층입니다. 모델 서버는 그중 하나 |
| 쿠버네티스 설정과의 짝은 | replicas 가 대수, HPA 가 오토스케일, readiness probe 가 웜업 끝 신호 |

## 헷갈리기 쉬운 점

- **API 서버는 어려워서가 아니라 「기다리는 부분」을 본 적이 없어서 낯섭니다.** 기다리는 부분은 라이브러리가 맡고 2절 코드에서 지훈 씨가 직접 쓴 줄은 피처 조회, predict 호출, 응답 조립의 3줄입니다.
- **서버 설계의 입력은 사용자 수가 아니라 초당 요청 수입니다.** 초당 요청 수도 평균이 아니라 피크를 넣습니다. 사용자 1,000만 명이 서버 10여 대로 끝나는 정도가 보통의 자릿수입니다.
- **서버 대수는 지연이 아니라 CPU 시간이 정합니다.** 4절에서 지연 7ms 는 피크에 동시에 처리 중인 요청 수 55건을 정했고 CPU 시간 6ms 는 코어당 처리량 167 QPS 와 서버 대수 10대를 정했습니다.
- **타임아웃은 요청을 버리지 않고 기다리기를 멈춘 뒤 폴백으로 답합니다.** 예산을 넘긴 요청은 그 요청을 받은 게이트웨이가 버립니다.
- **오토스케일로는 갑자기 늘어난 요청을 받지 못합니다.** 새 서버가 떠서 요청을 받기까지 41초가 걸리므로 그 41초 동안은 폴백과 남겨 둔 예산(3절처럼 보통 때 다 쓰지 않고 남긴 시간)이 늘어난 요청을 받습니다.
- **모델 서버는 늘리기 쉽고 피처 스토어는 늘리기 어렵습니다.** 모델 서버는 상태가 없고 피처 스토어는 상태가 있어서 생기는 차이입니다. 늘리기 어려운 피처 스토어는 첫째 층과 둘째 층이 같이 봅니다.

- 2절의 코드를 실무 도구로 다시 짜려면 [FastAPI 공식 자습서의 한국어 판](https://fastapi.tiangolo.com/ko/tutorial/)에서 첫걸음부터 요청 본문까지 네 장이면 됩니다. 요청과 응답 자체가 낯설면 [MDN 의 HTTP 개요](https://developer.mozilla.org/ko/docs/Web/HTTP/Overview)에서 「HTTP 흐름」과 「HTTP 메시지」 두 절을 먼저 봅니다.
- 동시성을 눈으로 보려면 서버를 띄우고 [hey](https://github.com/rakyll/hey) 같은 부하 도구로 30초 동안 50 동시 접속을 겁니다. 워커 1개와 4개의 p99 차이가 4절의 동시 요청 수가 뜻하는 것입니다.

- 7절의 readiness probe 와 HPA 설정은 [쿠버네티스 공식 문서의 probe 설정](https://kubernetes.io/ko/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)과 [HorizontalPodAutoscaler 문서](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/)에 있습니다.
- 추천과 검색 서빙의 큰 그림은 Eugene Yan 의 [System Design for Recommendations and Search](https://eugeneyan.com/writing/system-design-for-discovery/)가 오프라인과 온라인, 후보 추출과 랭킹의 2×2 로 정리했습니다. 6절의 세 층을 그 그림에 겹쳐 보면 모델 서버가 어느 칸인지 보입니다.
- 서버 2대가 빠진 배포 중 몇 분 동안 지연이 어떻게 변하는지는 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편 8절입니다. 새 모델을 1% 로 열어 되돌리는 순서는 [모델 배포와 롤백](post.html?id=model-deployment-rollback) 편입니다.
