지훈 씨는 여덟째 주에 피처(모델이 입력으로 받는 값)를 하나 추가했습니다. 유저가 지난주에 본 광고 카테고리입니다. 그런데 모델이 받는 입력의 모양이 바뀌면 모델은 처음부터 다시 배워야 해서 이 피처는 어제 모델 위에 이어 붙일 수 없었습니다.

그래서 지훈 씨는 30일 전체로 재학습을 걸어 놓고 자리에 앉았습니다. 매일 새벽에 도는 학습은 55분이면 끝났는데 이번에는 남은 시간이 6시간 20분으로 떴습니다. 04:00 에 시작하면 10:20 에 끝나는데, 10:20 이면 그날 새 모델을 배포에 태우는 시각이 이미 지난 뒤입니다.

**GPU 를 네 장 쓰면 네 배 빨라질까요?**

학습을 GPU 여러 장에 나눠 맡기는 방식을 분산 학습(distributed training)이라고 부릅니다. 이 글의 재학습은 GPU 네 장이면 3.5배까지 빨라지는데, 네 배에 못 미치는 까닭은 글의 앞부분에서 봅니다. 광고 모델에는 따져 볼 것이 하나 더 있습니다. 광고 모델은 몇 층짜리 신경망과 함께 임베딩 표(유저와 광고마다 숫자 여러 개로 된 벡터를 한 줄씩 달아 둔 표)를 학습하는데, 임베딩 표가 커서 신경망과는 다른 방법으로 나눕니다. 이 차이를 모르면 GPU 장수(쓰는 GPU 의 개수)를 늘려도 학습이 아예 시작되지 않습니다.

> **한 줄 요약:** 30일치를 처음부터 다시 배우는 재학습은 GPU 한 장으로 6시간 20분이 걸립니다. 같은 모델을 GPU 4장에 한 벌씩 두고 학습 데이터를 4등분해 함께 배우면 1시간 50분으로 줄어듭니다. 다만 GPU 마다 낸 기울기(모델의 숫자를 고칠 방향과 크기)를 합치는 시간과 가장 늦게 계산을 끝내는 GPU 를 기다리는 시간이 장수에 비례해 붙으므로, 장수를 두 배로 늘려도 시간은 절반까지 줄지 않습니다. 광고 모델은 임베딩 표가 학습 때 83.2GB 가 되어 GPU 한 장에 들어가지 않으므로 신경망만 GPU 마다 복제하고 임베딩 표는 파라미터 서버(임베딩 표만 들고 있는 서버) 2대에 쪼개 둡니다.

> **골라 읽는 법** — 이 글은 절이 6개입니다. 절마다 카드 한 장이나 표 하나가 있어 카드나 표만 보고 넘어가도 됩니다.
>
> - 6시간 20분이 나온 계산 → 1절
> - 데이터는 4등분하고 모델은 복제하는 방식 → 2절
> - 기울기를 합치는 시점, 기다림과 낡음 → 3절
> - 임베딩 표만 따로 쪼개는 까닭 → 4절
> - GPU 장수에 따라 줄어드는 학습 시간 → 5절
> - 담장 안과 열린 RTB 에서 쪼개는 자리가 달라지는 까닭 → 6절

이 글의 시간, 행 수, GPU 장수는 모두 설명을 위해 만든 가상 값입니다. 하루 학습 행 2,485만 건과 매일 학습에 걸리는 55분은 [학습 파이프라인](post.html?id=training-pipeline-dag) 편에서 쓴 값과 같습니다. 임베딩 표 27.7GB 와 학습 때의 83.2GB 는 [임베딩 테이블 운영](post.html?id=embedding-table-ops) 편에서 곱셈으로 구한 값을 가져왔습니다.

## 1. GPU 한 장으로 6시간 20분이 걸리는 30일 전체 재학습

**학습 시간은 배울 행이 몇 개인지와 행 하나를 배우는 데 드는 계산으로 정해집니다. 하루치 2,485만 행을 배우는 매일 학습은 55분, 30일치 7억 4,550만 행을 처음부터 배우는 재학습은 GPU 한 장으로 6시간 20분이 걸립니다.**

6시간 20분을 줄이려면 먼저 학습 시간이 무엇으로 정해지는지 알아야 합니다. 학습이 오래 걸리는 까닭은 배울 행이 많거나 행 하나를 배우는 데 오래 걸리거나 두 가지뿐입니다. 30일 전체를 다시 배우면 이 가운데 배울 행이 하루치의 30배로 늘어납니다.

매일 새벽의 학습은 어제 모델을 그대로 불러와 어제 로그 2,485만 행만 추가로 배우므로 55분이면 끝납니다. 이렇게 어제 모델에서 이어 배우는 방식을 이어 학습이라고 부릅니다. 이어 학습에서는 모델을 처음부터 다시 만들지 않고 하루씩 갱신합니다. 학습 파이프라인 편의 새벽 파이프라인에서는 네 번째 태스크(파이프라인 안의 작업 하나)가 이 이어 학습을 맡습니다.

이번 주에는 이어 학습을 쓸 수 없었습니다. 새 피처가 들어가면 모델이 받는 입력의 모양이 달라집니다. 그런데 어제 모델에서 입력을 처음 받는 첫 층은 예전 입력 모양에 맞춰져 있어 새 피처 값을 받을 자리가 없습니다. 그래서 학습 창(학습에 쓰는 데이터의 기간)에 든 30일치를 전부 꺼내 처음부터 다시 배우는데, 배울 행은 하루 2,485만 행에 30을 곱한 7억 4,550만 행입니다.

남은 하나는 행 하나를 배우는 데 드는 계산입니다. 이 글은 행 하나의 계산을 GPU 한 장이 1초에 학습을 마치고 넘기는 행의 수(초당 넘기는 행, 클수록 빠릅니다)로 나타냅니다. GPU 에 한 번에 함께 올려 계산하는 여러 행을 배치라고 부르는데, 배치 크기(한 배치에 든 행의 수)가 이 속도를 크게 바꿉니다. 매일 학습은 배치 1,024 로 돌아 초당 7,530행을 넘깁니다. 배치가 작으면 GPU 안의 계산 장치 상당수가 놀지만 배치를 키우면 한 번에 곱하는 행이 늘어 노는 시간이 줄어들므로, 재학습은 배치를 4,096 으로 키워 초당 32,700행을 넘깁니다.

다만 배치를 끝없이 키울 수는 없습니다. 배울 행 수가 같은데 배치가 커지면 모델을 고치는 횟수(갱신 횟수)가 줄어 모델이 덜 배우므로, 재학습은 4,096 까지는 안전하다고 보아 배치를 4,096 에서 멈췄습니다. GPU 를 여러 장 쓸 때도 같은 일이 생기는데, GPU 4장이 각자 배치 4,096 으로 낸 기울기를 평균 내 함께 갱신하면(2절) 한 번의 갱신이 16,384행을 봅니다. 그래서 GPU 장수를 늘릴 때는 학습률(모델을 한 번 고칠 때 얼마나 크게 고칠지 정하는 값) 같은 설정을 다시 맞추고 정확도를 확인해야 합니다.

GPU 한 장이 배치 4,096 으로 초당 32,700행을 넘긴다고 가정하면 재학습 시간은 7억 4,550만 행을 초당 32,700행으로 나눈 22,798초이고 시간으로 바꾸면 6시간 20분입니다. 같은 식으로 매일 학습을 세면 2,485만 행을 초당 7,530행으로 나눠 55분이 나옵니다.

| 무엇 | 매일 이어 학습 | 30일 전체 재학습 |
|---|---|---|
| 배우는 행 | 어제 2,485만 행 | 30일 7억 4,550만 행 |
| 시작하는 자리 | 어제 모델 | 처음부터 |
| 한 번에 올리는 행(배치) | 1,024 | 4,096 |
| GPU 한 장이 초당 넘기는 행 | 7,530 | 32,700 |
| 걸리는 시간 | 55분 | 6시간 20분 |

6시간 20분이 왜 문제인지는 하루 일정의 시각으로 보면 분명합니다. 새 모델을 배포에 태워 달라고 요청하는 시각은 06:09 인데, 04:00 에 시작한 재학습은 10:20 에 끝나 이 요청 시각을 네 시간 넘깁니다. 그렇다고 일정을 하루 미루면 새 피처가 붙은 모델이 하루 늦게 나갑니다.

시간을 줄이는 방법은 배울 행을 줄이거나 행 하나의 계산을 GPU 여러 장에 나누는 것, 두 가지뿐입니다. 배울 행은 학습 기간을 30일에서 14일로 줄이는 식으로 줄일 수 있는데, 학습 기간이 짧아지면 드물게 나오는 광고는 학습 데이터가 모자라 모델이 나빠집니다. 그래서 30일치 행은 그대로 두고 계산을 GPU 여러 장에 나눕니다. 어떻게 나누는지는 다음 절에서 봅니다.

## 2. 데이터는 4등분하고 모델은 복제하는 데이터 병렬

**데이터 병렬은 같은 모델을 GPU 4장에 한 벌씩 복제하고 학습 데이터만 4등분해 나눠 줍니다. 네 장이 각자 낸 기울기를 평균 내 그 평균으로 함께 갱신하므로 네 장의 모델은 계속 같은 값을 유지합니다. 한 장으로 6시간 20분이던 재학습은 1시간 50분으로 줄어듭니다.**

계산을 GPU 4장에 나누면 네 장이 각자 다른 데이터를 배웁니다. 네 장이 따로 배우기만 하면 서로 다른 모델 4개가 생겨 나중에 어느 모델을 배포할지 정할 수 없으므로, 계산은 나누더라도 네 장이 늘 같은 모델을 들고 있게 해야 합니다.

데이터 병렬(data parallelism)에서는 학습 데이터를 나누고 모델을 복제합니다. 학습 데이터 7억 4,550만 행은 4등분해 한 장이 1억 8,640만 행쯤을 맡습니다. 모델은 나누지 않고 네 장이 똑같은 가중치(모델이 학습하며 고쳐 가는 숫자)를 한 벌씩 들고 시작합니다.

학습은 스텝을 되풀이하며 진행되는데, 스텝 하나는 배치 하나로 기울기를 내고 가중치를 한 번 고치는 과정입니다. 데이터 병렬에서 한 스텝은 이렇게 진행됩니다. 네 장이 각자 배치 4,096 행을 받아 예측을 내고 정답과 비교해 기울기를 냅니다. 기울기는 가중치를 어느 쪽으로 얼마나 고쳐야 하는지를 적은 벡터입니다. 여기까지 네 장이 따로 계산한 다음 네 장의 기울기를 모아 평균을 내고 그 평균으로 네 장이 똑같이 가중치를 갱신합니다. 기울기를 모아 평균 내는 일을 기울기 합치기(allreduce)라고 부릅니다.

한 장이 낸 기울기는 원래 배치에 든 행마다 구한 기울기의 평균이므로 네 장의 기울기를 합칠 때도 평균을 냅니다. 행 4,096개씩 든 배치 4개의 기울기를 평균 내면 4,096 × 4 = 16,384행의 기울기를 한 번에 평균 낸 값과 같아지므로, 네 장으로 도는 학습은 배치 16,384 짜리 학습과 같은 갱신을 합니다.

기울기는 가중치마다 값이 하나씩 있으므로 합칠 때 오가는 값의 크기는 신경망 가중치의 크기와 같습니다. 이 모델의 신경망은 38MB 라서 스텝마다 네 장이 38MB 규모의 숫자를 주고받습니다. 임베딩 표 27.7GB 가 이 주고받는 값에서 빠지는 까닭은 4절에서 다룹니다.

| 무엇 | 넷이 어떻게 갖나 | 크기 |
|---|---|---|
| 학습 행 | 나눈다. 한 장이 1억 8,640만 행 | 7억 4,550만 행 |
| 신경망 가중치 | 복제한다. 넷이 같은 값 | 38MB |
| 스텝마다 합치는 기울기 | 넷의 평균으로 되돌린다 | 38MB 규모 |
| 임베딩 표 | 나누지도 복제하지도 않는다 | 27.7GB |

카드 속 색은 4가지입니다. 파랑은 놓여 있는 데이터(학습 행, 임베딩 표), 벽돌색은 지금 문제가 되는 것(기다림, 안 들어가는 크기), 먹색은 GPU 와 파라미터 서버, 회색은 만드는 작업이고 점선 상자는 적어 둔 내용입니다. 아래 카드는 같은 모델을 GPU 4장에 한 벌씩 두고 학습 데이터만 4등분하는 데이터 병렬의 구성을 보여 줍니다.

재학습은 우선 GPU 4장으로 시작합니다. 장수를 더 늘릴지 판단하려면 방금 붙은 15분이 어디서 오는지 알아야 하는데, 그 15분은 기울기를 언제 합치느냐가 정합니다.

## 3. 기울기를 합치는 시점, 동기와 비동기

**스텝마다 네 장이 모두 기울기를 낼 때까지 기다렸다 합치는 동기 방식은 가장 늦은 장 하나를 나머지 세 장이 기다려야 하므로, 같은 스텝 수를 한 장이 혼자 돌 때보다 13% 오래 걸립니다. 기다리지 않는 비동기 방식은 기다림이 없는 대신 한 장이 기울기를 계산하는 사이 다른 장들이 가중치를 평균 3번 고쳐 놓아 기울기가 평균 3스텝 낡습니다.**

스텝마다 네 장이 서로를 기다렸다가 기울기를 합칠지, 기다리지 않고 각자 다음 스텝으로 갈지를 정해야 합니다. 기다리면 학습이 느려지고 기다리지 않으면 낡은 값으로 배웁니다.

동기(synchronous) 방식에서는 스텝마다 네 장이 모두 기울기를 낼 때까지 어느 장도 다음 스텝으로 넘어가지 못합니다. 스텝마다 네 장이 모두 도착해야 열리는 벽(barrier)을 하나씩 두는 방식입니다. 그런데 배치마다 건드리는 임베딩 줄(임베딩 표에서 유저나 광고 하나에 해당하는 한 행)의 수가 다르고 파라미터 서버에서 값을 받아 오는 시간이 흔들리며 같은 장비에서 다른 일이 돌기도 하므로, 네 장이 한 스텝에 걸리는 시간은 매번 조금씩 다릅니다. 그래서 한 스텝의 실제 길이는 네 장 가운데 가장 늦은 장이 정합니다.

아래 코드는 GPU 4장이 2,000스텝을 동기와 비동기로 도는 상황을 만들어 동기에서 기다리는 시간과 비동기에서 기울기가 낡는 정도를 비교합니다. 스텝 하나에 걸리는 시간의 중앙값(크기순으로 늘어놓았을 때 가운데 값)은 배치 4,096행을 초당 32,700행으로 나눈 0.125초로 두었습니다. 장마다 스텝마다 걸리는 시간은 배치가 건드리는 임베딩 줄 수와 서버 상태가 달라 흔들리므로, 코드는 이 중앙값을 가운데에 두고 로그정규 분포(값이 늘 0 보다 크고 큰 값 방향으로 꼬리가 긴 분포)에서 시간을 뽑습니다.

```python
# 하는 일: GPU 4장이 2,000스텝을 동기와 비동기로 돈다고 놓고, 동기가 기다리는 시간과 비동기에서 기울기가 낡는 정도를 비교한다.
import random, math

# 1단계: 장마다 스텝마다 걸린 시간을 뽑는다
# 스텝 하나의 중앙값은 4,096행 ÷ 초당 32,700행 = 0.125초이고, 흔들림은 로그정규로 준다. 전부 가상 값이다.
random.seed(7)
GPUS, STEPS = 4, 2_000
MED, SIGMA = 0.125, 0.12
mu = math.log(MED)

# 장마다 스텝마다 걸린 시간. 배치가 건드리는 임베딩 줄 수와 서버 상태가 달라 흔들린다.
times = [[random.lognormvariate(mu, SIGMA) for _ in range(STEPS)] for _ in range(GPUS)]

# 2단계: 동기로 돌린 시간을 센다
# 스텝마다 넷이 기울기를 합치므로 그 스텝의 가장 늦은 장에 맞춰진다.
alone = sum(times[0])
sync = sum(max(times[g][s] for g in range(GPUS)) for s in range(STEPS))
print(f"한 장이 혼자 {STEPS:,}스텝을 돌면 {alone:.1f}초")
print(f"동기 네 장은 스텝마다 늦은 장을 기다려 {sync:.1f}초, 혼자보다 {sync / alone - 1:.1%} 깁니다")
waited = sync - alone
print(f"기다린 {waited:.1f}초는 네 장 모두에게 붙어 {GPUS * waited:.0f}초의 GPU 시간이 됩니다")

# 3단계: 비동기로 돌려 기울기가 몇 스텝 낡는지 센다
# 각자 제 속도로 간다. 내가 기울기를 보내는 사이 남이 몇 번 갱신했나가 낡음이다.
ends = []
for g in range(GPUS):
    t = 0.0
    for s in range(STEPS):
        t += times[g][s]
        ends.append((t, g))
ends.sort()                      # 네 장의 갱신을 시각순으로 정렬한다

last, stale = {}, []
for i, (t, g) in enumerate(ends):
    if g in last:
        stale.append(i - last[g] - 1)    # 내 직전 갱신과 이번 갱신 사이에 끼어든 남의 갱신 수
    last[g] = i
print(f"비동기 네 장은 기다림이 0초입니다. 대신 기울기가 평균 {sum(stale) / len(stale):.1f}스텝 낡습니다"
      f" (최대 {max(stale)}스텝)")

# 출력:
# 2단계 뜻: 동기는 스텝마다 가장 늦은 장에 맞춰져 혼자보다 13.0% 길다. 기다린 32.5초 동안 나머지 셋도 쉬어서 GPU 시간 130초가 버려진다.
# 한 장이 혼자 2,000스텝을 돌면 250.6초
# 동기 네 장은 스텝마다 늦은 장을 기다려 283.1초, 혼자보다 13.0% 깁니다
# 기다린 32.5초는 네 장 모두에게 붙어 130초의 GPU 시간이 됩니다
# 3단계 뜻: 비동기는 기다리지 않는 대신, 기울기를 보내는 사이 다른 장이 평균 3.0번 갱신해 그만큼 낡은 기울기로 배운다.
# 비동기 네 장은 기다림이 0초입니다. 대신 기울기가 평균 3.0스텝 낡습니다 (최대 6스텝)
```

2단계가 찍은 값을 보면 한 장이 혼자 2,000스텝을 돌 때 250.6초 걸리는 구간이 동기 네 장으로는 283.1초가 걸립니다. 스텝마다 가장 늦은 장에 맞춰지므로 혼자 돌 때보다 32.5초, 비율로 13.0% 깁니다. 늦은 장을 기다리는 동안 나머지 장도 아무것도 하지 않으므로 이 32.5초는 한 장이 아니라 네 장 모두에 붙습니다. 그래서 GPU 시간(장마다 쓴 시간을 모두 더한 값)으로 세면 32.5초의 4배인 130초를 버립니다. GPU 는 값을 치르고 빌린 장비라서 버린 130초는 그대로 돈입니다.

비동기(asynchronous) 방식은 이 벽을 없앱니다. 각 장은 기울기를 내는 대로 파라미터 서버에 보내고 최신 가중치를 받아 바로 다음 스텝으로 가므로 기다림이 0초가 됩니다. 대신 한 장이 기울기를 계산하는 동안 다른 장들이 이미 가중치를 고쳐 놓습니다. 3단계는 한 장이 직전에 갱신한 때부터 이번에 갱신할 때까지 다른 장이 끼어들어 갱신한 횟수를 세는데, 그 횟수가 평균 3.0번이었고 많을 때는 6번이었습니다. 한 장이 평균 3스텝 전의 가중치를 보고 낸 방향으로 지금의 가중치를 고칩니다. 이렇게 몇 스텝 전의 가중치로 계산한 기울기를 낡은 기울기(stale gradient)라고 부릅니다.

낡은 기울기가 늘 나쁘지는 않습니다. 가중치가 조금씩만 움직이는 구간에서는 3스텝 차이가 결과를 거의 바꾸지 않지만 학습 초반처럼 가중치가 크게 흔들리는 때에는 낡은 기울기가 가중치를 엉뚱한 방향으로 밀어 손해가 큽니다. 그래서 실무에서는 두 방식을 섞습니다. 신경망 가중치는 모든 스텝이 모든 가중치를 건드려 낡으면 바로 표가 나므로 동기로 합쳐 정확하게 학습합니다. 임베딩은 한 배치가 건드리는 임베딩 줄이 극히 적어 두 장이 같은 줄을 동시에 고치는 일이 거의 없으므로 비동기로 풀어 기다림을 없앱니다.

아래 카드의 왼쪽은 동기이고 오른쪽은 비동기입니다. 왼쪽 막대 끝의 빈 칸이 늦은 장을 기다린 시간이고 오른쪽 막대의 눈금은 각 장의 스텝 경계입니다.

## 4. 임베딩 표만 따로 두는 파라미터 서버

**신경망 가중치는 38MB 로 작아 GPU 4장이 한 벌씩 복제해도 됩니다. 임베딩 표는 27.7GB 이고 학습 때는 83.2GB 로 늘어 GPU 한 장의 메모리 80GB 에 들어가지 않으므로, 임베딩 표만 파라미터 서버 2대에 쪼개 둡니다.**

2절의 데이터 병렬에서는 네 장이 모델 전체를 한 벌씩 들고 있어야 하는데, 광고 모델의 임베딩 표는 GPU 한 장에 들어가지 않습니다. 그래서 신경망은 GPU 안에 두고 임베딩 표만 따로 서버 2대에 나눠 둔 뒤, GPU 는 그때 쓰는 줄만 받아 옵니다.

이미지나 문장을 다루는 모델은 신경망 가중치가 크고 표가 작지만 광고 모델은 반대입니다. 광고 모델의 신경망은 몇 층뿐이라 38MB 인데, 유저와 광고마다 벡터를 한 줄씩 달아 둔 임베딩 표는 수십 GB 입니다.

임베딩 표의 크기는 곱셈으로 구합니다. 같은 표라도 서빙(학습을 마친 모델로 실제 요청에 점수를 내는 일) 때와 학습 때 크기가 다릅니다. 값 하나를 4바이트로 저장하면 유저 표는 유저 2억 줄 × 32차원(줄마다 숫자 32개) × 4바이트로 23.8GB 입니다. 여기에 광고 표, 지면 표, 카테고리 표를 더한 임베딩 표 4개의 합은 27.7GB 입니다. 학습에 쓰는 옵티마이저(기울기로 가중치를 고치는 규칙)를 Adam 으로 가정하면 값마다 숫자 2개가 더 저장됩니다. 하나는 기울기의 이동 평균인 1차 모멘트이고 다른 하나는 기울기 제곱의 이동 평균인 2차 모멘트입니다. 그래서 학습 때는 값 하나가 숫자 3개가 되어 임베딩 표가 27.7GB 의 반올림 전 값에 3을 곱한 83.2GB 가 됩니다.

| 조각 | 서빙 때 크기 | 학습 때 크기 | 어디에 두나 |
|---|---|---|---|
| 신경망 가중치 | 38MB | 114MB | GPU 넷이 복제 |
| 임베딩 표 넷 | 27.7GB | 83.2GB | 파라미터 서버 2대 |
| 그중 유저 표 | 23.8GB | 71.5GB | 같은 서버에 함께 |

표의 신경망 가중치도 같은 까닭으로 학습 때는 38MB 의 3배인 114MB 가 됩니다. GPU 한 장의 메모리는 80GB 라서 학습 때의 임베딩 표 83.2GB 만으로도 이미 넘치는데, 학습 중간에 쌓이는 값까지 함께 올려야 하므로 실제로는 더 모자랍니다. 데이터 병렬에서는 데이터를 아무리 잘게 나눠도 네 장이 모두 임베딩 표 전체를 들고 있어야 하므로, 데이터만 나누는 방식으로는 이 문제가 풀리지 않습니다. 임베딩 표는 GPU 4장에 나눌 대상이 아니라 GPU 밖으로 내보낼 대상입니다.

그래서 GPU 밖에 임베딩 표만 들고 있는 서버를 따로 두는데, 이 서버를 파라미터 서버(parameter server)라고 부릅니다. 서버 한 대가 임베딩에 내줄 수 있는 메모리를 64GB 로 보면 83.2GB 는 한 대에 들어가지 않으므로 파라미터 서버가 2대 필요합니다. 2대에 나누면 한 대가 83.2GB 의 절반인 41.6GB 씩 맡습니다.

GPU 는 임베딩 표에서 줄 하나 단위로 값을 조회하므로 표를 서버 2대에 쪼갤 때도 줄 단위로 나눕니다. 줄 번호 순서대로 덩어리째 나누면 최근 광고가 한 대에 몰리므로, 번호의 해시값(번호를 고르게 흩어진 다른 숫자로 바꾼 값)을 서버 수로 나눈 나머지로 줄마다 서버를 정해 흩어 둡니다. 이 규칙은 [임베딩 테이블 운영](post.html?id=embedding-table-ops) 편에서 쓴 규칙과 같습니다.

아래 카드에는 GPU 한 장에 신경망만 두고 임베딩 표는 파라미터 서버 2대에 41.6GB 씩 나눠 둔 구성이 그려져 있습니다.

임베딩 표가 GPU 밖에 있으면 스텝마다 값이 오가느라 학습이 느려지지 않을까 걱정이 되는데, 광고 모델은 한 배치가 건드리는 줄이 표의 아주 작은 부분이라 이 걱정을 덜 수 있습니다. 배치가 1,024행이면 한 배치에 든 유저는 많아야 1,024명이므로 건드리는 유저 줄도 많아야 1,024줄로 유저 2억 줄 가운데 0.0005% 입니다. 배치를 4,096 으로 키워도 4,096줄로 0.002% 입니다. 이번 배치가 건드리지 않은 나머지 줄은 기울기가 0 이라 보낼 것도 받을 것도 없습니다.

그래서 스텝마다 오가는 양은 생각보다 적습니다. 배치 4,096 으로 유저 줄 4,096개를 받아 오면 4,096 × 32차원 × 4바이트로 512KB 인데, 신경망 기울기를 합칠 때 오가는 38MB 보다 한참 작습니다. 임베딩 표가 27.7GB 인데도 스텝마다 오가는 양이 512KB 뿐인 데에는 모순이 없습니다. 27.7GB 는 임베딩 표 전체가 어딘가에 놓여 있어야 하는 크기이고 512KB 는 한 스텝에 실제로 건드리는 크기입니다.

임베딩 표는 파라미터 서버 2대에 두고 GPU 4장은 신경망만 복제해 갖기로 정합니다. 여기까지 정하면 GPU 장수는 자유롭게 고를 수 있습니다. 다음 절은 8장으로 늘렸을 때 얼마나 빨라지는지를 셉니다.

## 5. GPU 장수와 학습 시간, 효율

**GPU 장수를 늘리면 계산 시간은 장수만큼 나뉘지만 기울기를 합치고 늦은 장을 기다리는 시간은 장수에 비례해 붙습니다. 그래서 4장이면 한 장일 때보다 3.5배 빨라 효율이 86%, 8장이면 5.8배로 효율이 73% 입니다.**

장이 늘 때마다 합치기와 기다림이 붙으므로 GPU 를 두 배로 늘려도 학습 시간은 절반이 되지 않고 효율이 내려갑니다. 그래서 장을 늘릴 때 시간이 얼마나 줄어드는지 알아야 어디서 멈출지 정할 수 있습니다.

2~4절에서 본 것을 식 하나로 적으면, 학습 시간은 한 장의 계산 시간을 장수로 나눈 값에 장이 늘어난 만큼 붙는 몫을 곱한 값입니다. 붙는 몫은 장이 하나 늘 때마다 5.3% 로 가정합니다. 이 5.3% 에는 기울기를 합치며 오가는 통신, 늦은 장을 기다리는 시간, 파라미터 서버를 오가는 왕복이 함께 들어 있습니다. 세 가지 모두 장이 늘수록 커지며 계산처럼 장수로 나뉘지 않습니다. 4장이면 한 장보다 3장이 늘었으므로 장수로 나눈 계산 시간에 5.3% 가 3번 붙습니다.

아래 코드는 이 식으로 GPU 를 1장에서 32장까지 늘릴 때 30일치 학습 시간이 얼마나 주는지 세어 봅니다.

```python
# 하는 일: GPU 를 1장에서 32장까지 늘릴 때 30일치 학습 시간이 얼마나 주는지 센다.
# 1단계: 학습 시간 식을 만든다
# 계산은 장수만큼 나뉘지만, 기울기를 합치고 늦은 장을 기다리는 시간은 장수에 비례해 붙는다. 전부 가상 값이다.
ROWS = 745_500_000        # 30일 학습 행 (하루 2,485만 행 × 30일)
ROWS_PER_SEC = 32_700     # GPU 한 장이 초당 넘기는 행
OVERHEAD = 0.053          # 장이 하나 늘 때마다 스텝마다 더 붙는 몫

def train_time(gpus):
    compute = ROWS / ROWS_PER_SEC / gpus          # 계산은 장수만큼 나뉜다
    return compute * (1 + OVERHEAD * (gpus - 1))  # 합치기와 기다림은 장수에 비례해 붙는다

def hm(sec):
    m = round(sec / 60)
    return f"{m // 60}시간 {m % 60:02d}분" if m >= 60 else f"{m}분"

# 2단계: 장수마다 학습 시간, 배속, 효율, 줄어드는 시간을 찍는다
base = train_time(1)
print("GPU   학습 시간      배속   효율   줄어드는 시간")
prev = base
for g in (1, 2, 4, 8, 16, 32):
    t = train_time(g)
    saved = "%d분" % (round(prev / 60) - round(t / 60)) if g > 1 else "-"
    print("%3d장 %10s %6.1f배 %5.0f%% %10s" % (g, hm(t), base / t, 100 * base / t / g, saved))
    prev = t

# 3단계: 붙은 시간이 어디서 왔는지 나눠 본다
print()
for g in (4, 8):                                  # 붙은 시간이 어디서 왔는지 나눠 본다
    comp = ROWS / ROWS_PER_SEC / g
    print("%d장: 계산 %s + 합치기와 기다림 %s = %s"
          % (g, hm(comp), hm(train_time(g) - comp), hm(train_time(g))))

# 출력:
# 2단계 뜻: 장수를 두 배로 늘려도 학습 시간은 절반까지 줄지 않는다. 효율이 2장 95% 에서 32장 38% 까지 떨어지고, 줄어드는 시간도 180분에서 12분으로 준다.
# GPU   학습 시간      배속   효율   줄어드는 시간
#   1장    6시간 20분    1.0배   100%          -
#   2장    3시간 20분    1.9배    95%       180분
#   4장    1시간 50분    3.5배    86%        90분
#   8장    1시간 05분    5.8배    73%        45분
#  16장        43분    8.9배    56%        22분
#  32장        31분   12.1배    38%        12분
# 3단계 뜻: 4장에서 8장으로 가면 계산은 1시간 35분에서 47분으로 절반이 되지만, 합치기와 기다림은 15분에서 18분으로 는다.
#
# 4장: 계산 1시간 35분 + 합치기와 기다림 15분 = 1시간 50분
# 8장: 계산 47분 + 합치기와 기다림 18분 = 1시간 05분
```

2단계가 찍은 표에서 학습 시간은 2장 3시간 20분, 4장 1시간 50분, 8장 1시간 05분, 16장 43분, 32장 31분으로 줄어들지만 효율은 2장의 95% 에서 32장의 38% 까지 떨어집니다. 장수를 두 배로 늘릴 때마다 줄어드는 시간(표의 마지막 칸)도 180분에서 12분으로 작아집니다.

3단계가 찍은 마지막 두 줄에 이 절의 내용이 다 담겨 있습니다. 4장에서는 계산 1시간 35분에 5.3% 가 3번 붙어 합치기와 기다림이 15분입니다. 8장으로 늘리면 계산은 1시간 35분에서 47분으로 절반이 되지만 늘어난 장이 7장이라 5.3% 가 7번 붙어 합치기와 기다림은 15분에서 18분으로 오히려 늘어납니다. 장수로 나뉘는 계산과 장수에 따라 늘어나는 합치기와 기다림이 함께 있으므로 합계는 1시간 50분에서 1시간 5분으로 줄어도 절반까지 가지 못합니다. 장수를 키울수록 학습 시간에서 합치기와 기다림이 차지하는 몫이 커집니다.

줄어드는 시간 칸을 보면 어디서 멈출지가 보입니다. 장수를 두 배로 늘릴 때 버는 시간은 1장에서 2장으로 180분, 2장에서 4장으로 90분, 4장에서 8장으로 45분, 8장에서 16장으로 22분으로 두 배마다 절반씩 줄어듭니다. 16장은 8장보다 22분 빠르지만 GPU 를 두 배 쓰므로 GPU 시간은 8장의 521분에서 16장의 682분으로 늘어납니다. 16장은 22분을 벌려고 GPU 시간을 682분에서 521분을 뺀 161분만큼 더 씁니다.

재학습은 GPU 4장으로 돌립니다. 다만 지금까지는 유저 임베딩 표가 큰 무대(광고 시스템이 놓인 환경)를 전제로 했는데, 이 전제가 달라지면 나누는 방법도 달라집니다.

## 6. 담장 안과 열린 RTB 에서 쪼개는 자리

**한 회사가 앱과 광고 서버를 다 가진 담장 안에서는 유저 표가 임베딩 표 전체의 86% 라서 GPU 밖으로 쪼개 내보내는 대상이 유저 표입니다. 남의 매체에 입찰하는 열린 RTB 에서는 유저 줄이 한 번 쓰이고 버려져 임베딩이 작으므로, 파라미터 서버 없이 데이터 병렬만으로 학습이 끝납니다.**

어느 표가 가장 큰지가 무대마다 다르므로 무엇을 GPU 밖으로 내보낼지도 무대마다 달라집니다.

### 담장 안: 가장 큰 유저 표 [무대: 닫힌 생태계]

담장 안에서는 유저를 로그인 계정으로 알아보는데, 계정 번호는 몇 년 동안 바뀌지 않습니다. 그래서 유저 줄마다 숫자 32개를 달아 두면 그만한 값을 합니다. 한 유저가 한 달에 수백 번 등장하므로 그 유저 줄의 숫자 32개가 그 사람의 취향을 실제로 담습니다.

대신 유저 표가 커집니다. 유저 2억 줄이 23.8GB 로 임베딩 표 전체 27.7GB 의 86% 를 차지합니다. 광고 표, 지면 표, 카테고리 표는 다 합쳐도 27.7GB 에서 23.8GB 를 뺀 3.9GB 라 세 표만이면 GPU 한 장에 들어가므로, 이 글의 파라미터 서버 2대는 사실상 유저 표를 담으려고 띄운 서버입니다.

### 열린 RTB: 작은 임베딩 [무대: 열린 RTB]

열린 RTB(Real-Time Bidding)는 노출마다 실시간 경매로 광고를 고르는 방식입니다. 이 경매에서 남의 매체에 입찰하는 DSP(광고주 편에서 입찰하는 플랫폼)는 유저를 쿠키(브라우저에 저장해 두는 작은 식별 값)로 알아보는데, 쿠키는 브라우저마다 다르고 며칠이면 바뀝니다. 한두 번 등장하는 쿠키 번호에 숫자 32개를 배정해도 그 숫자는 학습에서 거의 움직이지 않으며 서빙 때는 그 줄을 찾을 키가 이미 없습니다. 그래서 임베딩 표의 메모리는 오래 쓰이는 도메인(광고가 실리는 사이트), 슬롯 위치(지면에서 광고가 놓이는 자리), 광고 소재(광고에 쓰는 이미지와 문구)의 줄에 배정합니다.

그러면 임베딩이 몇 GB 로 줄어 모델 전체가 GPU 한 장에 들어가므로 파라미터 서버 없이 2절의 데이터 병렬만으로 학습이 끝납니다. 기울기 합치기도 신경망 하나만 보면 되므로 3절의 동기 방식으로 두면 됩니다. 이 무대에서 어려운 부분은 나누는 자리에 있지 않고 학습 데이터 자체에 있습니다. 경매에서 이긴(낙찰된) 요청만 결과가 남고 진 요청은 결과를 모르는 문제인데, 이 문제는 [Bid Shading 과 낙찰가 미관측](post.html?id=bid-shading-censored) 편에서 다룹니다.

| 무엇 | 담장 안 | 열린 RTB |
|---|---|---|
| 가장 큰 표 | 유저 2억 줄, 23.8GB | 광고 소재와 지면 |
| 학습 때 임베딩 | 83.2GB, GPU 한 장에 안 들어감 | 몇 GB, 한 장에 들어감 |
| 나누는 방법 | 데이터 병렬 + 파라미터 서버 2대 | 데이터 병렬만 |
| 기울기 합치기 | 신경망은 동기, 임베딩은 비동기 | 신경망만 동기 |

두 무대 모두 분산 학습이라고 부르지만 띄우는 장비는 다릅니다. 담장 안의 설계를 DSP 에 그대로 옮기면 쓰지 않는 파라미터 서버 2대를 띄웁니다. 반대로 DSP 의 설계를 담장 안에 가져오면 학습 때 83.2GB 인 임베딩 표가 GPU 한 장의 80GB 에 들어가지 않아 학습이 메모리 부족으로 시작조차 못 합니다.

지훈 씨의 여덟 주가 여기서 끝납니다. 지훈 씨는 새벽 알람 한 줄에서 시작해 파이프라인, 버전, 이미지, 서버, 배포, 스트림, 배치 추론을 지나 학습을 나누는 자리까지 왔습니다. 여덟 편을 관통한 질문은 「만든 모델을 매일 같은 품질로 다시 내놓으려면 무엇을 적어 두고 무엇을 자동으로 돌려야 하는가」 하나였습니다.

## 한눈 정리

| 자리 | 무엇을 하나 | 숫자 |
|---|---|---|
| 30일 전체 재학습 | 피처가 바뀌면 처음부터 다시 배운다 | 7억 4,550만 행, 한 장 6시간 20분 |
| 데이터 병렬 | 데이터를 넷으로 나누고 모델은 복제한다 | 한 장 1억 8,640만 행, 1시간 50분 |
| 기울기 합치기 | 스텝마다 넷의 기울기를 평균 낸다 | 신경망 38MB 규모를 주고받는다 |
| 동기 | 스텝마다 늦은 장을 기다린다 | 혼자보다 13% 길다 |
| 비동기 | 기다리지 않는다 | 기울기가 평균 3스텝 낡는다 |
| 임베딩 표 | GPU 에 안 들어가 밖으로 뺀다 | 27.7GB, Adam 이면 83.2GB |
| 파라미터 서버 | 임베딩만 들고 건드린 줄만 준다 | 2대, 41.6GB 씩 |
| 한 스텝의 임베딩 통신 | 건드린 줄만 오간다 | 4,096줄이면 512KB |
| 장수와 효율 | 계산은 나뉘고 합치기는 안 나뉜다 | 4장 86%, 8장 73%, 16장 56% |

## 헷갈리기 쉬운 점

- **데이터 병렬은 모델을 나누지 않습니다.** 모델은 GPU 4장이 똑같이 한 벌씩 갖고 학습 데이터만 4등분합니다. 모델에서 쪼개는 부분은 임베딩 표뿐인데, 임베딩 표도 계산을 나누려는 것이 아니라 GPU 메모리에 들어가지 않아서 파라미터 서버 2대에 나눠 둡니다.
- **효율 86% 는 GPU 가 14% 놀았다는 뜻이 아닙니다.** 4장이 장수만큼 4배 빨라졌다면 효율이 100% 인데 실제로는 3.5배에 그쳤다는 뜻입니다. 4배에 못 미친 만큼을 기울기 합치기와 늦은 장 기다림이 차지합니다.
- **파라미터 서버는 GPU 가 아닙니다.** 학습 계산은 하지 않고 임베딩 표만 들고 있다가 GPU 가 필요한 줄을 물으면 그 줄만 내주고 GPU 가 보낸 갱신값을 받아 표에 씁니다.
- **배치를 키우면 빨라지지만 끝없이 키울 수는 없습니다.** 배울 행 수가 같을 때 배치가 커지면 갱신 횟수가 줄어 모델이 덜 배웁니다. 재학습은 4,096 까지는 안전하다고 보고 배치를 1,024 에서 4,096 으로 키웠습니다. GPU 4장으로 돌리면 네 장의 기울기를 평균 내 한 번의 갱신이 16,384행을 보므로 GPU 장수를 늘릴 때도 학습률 같은 설정을 다시 맞추고 정확도를 확인해야 합니다.
- **동기와 비동기는 정확도와 시간을 맞바꾸는 선택입니다.** 어느 한쪽이 늘 옳은 것이 아니라 값에 따라 고릅니다. 신경망 가중치처럼 모든 스텝이 건드리는 값은 동기로 합치고 임베딩처럼 두 장이 같은 줄을 고치는 일이 드문 값은 비동기로 둡니다.
