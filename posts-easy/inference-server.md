모델 팀으로 옮긴 지 넷째 주인 지훈 씨는 다음 주에 첫 배포를 맡게 되어서 그 전에 지금 서버가 모델을 어떻게 올리고 있는지부터 살펴보기로 했습니다. 학습 폴더를 열어 보니 파일이 2개 있었는데 하나는 작고 하나는 컸습니다.

지훈 씨가 선배에게 「학습이 끝나면 이 파일이 나오는데, 이게 어떻게 요청에 답하는 서버가 되나요?」 하고 묻자 선배는 이렇게 답했습니다. 「작은 쪽은 서빙 포맷으로 바꿔서 서버가 뜰 때 내려받아요. 큰 쪽은 따로 있는 서비스에 올려요. 서버가 뜨고 41초 뒤부터 요청을 받아요.」

지훈 씨는 그 41초 동안 서버 안에서 무슨 일이 일어나는지도, 서버가 왜 켜지자마자 답하지 않는지도 몰랐습니다. 요청 하나에 후보가 수백 건씩 담겨 오는데 서버가 그 후보들을 하나씩 계산하는지 한꺼번에 계산하는지도 알지 못했습니다.

**학습이 남긴 파일은 어디로 가고 서버는 그 파일을 어떻게 올리며 첫 요청은 언제부터 받을까요?**

학습이 남긴 파일을 받아 요청에 답하는 서버를 추론 서버(inference server)라고 부릅니다. 추론 서버는 그 파일을 열어 메모리에 올려 두었다가 요청이 오면 그 요청에 담겨 온 후보마다 점수를 매겨 돌려줍니다. 이 글은 추론 서버가 파일을 올리고 첫 요청을 받기까지를 카드 그림 네 장으로 따라갑니다. 이 과정을 알고 나면 배포 때 서버가 왜 30초 동안 느려지는지와 두 버전을 왜 한 서버에 같이 올려 두는지가 보입니다.

> **한 줄 요약:** 학습이 끝나면 클릭 확률을 계산하는 데 쓰는 신경망 가중치(38MB)와 ID 마다 벡터(숫자 목록) 하나를 적은 임베딩 표(27.7GB)가 남습니다. 작은 신경망 가중치는 학습 프레임워크와 모델 코드 없이 열리는 서빙 포맷(ONNX)으로 바꿔 서버마다 올립니다. 큰 임베딩 표는 임베딩 서비스 한 곳에 따로 둡니다. 새 서버는 켜진 뒤 모델 파일을 내려받아 메모리에 올리고 웜업까지 마친 41초에야 readiness probe(요청을 받을 준비가 됐는지 확인하는 검사)를 통과해 요청을 받습니다. 웜업은 더미 요청(시험용 요청)을 서버 자신에게 먼저 보내 첫 계산의 준비를 끝내 두는 단계입니다. 요청 하나에 담긴 후보 800건은 한 텐서(모델에 한 번에 넣는 숫자 배열)로 모아 모델을 한 번만 불러야 모델 호출에 주어진 시간 안에 계산이 끝납니다. 운영 중인 버전과 새 버전을 한 서버에 같이 올려 두면 바꾸기와 되돌리기가 설정 한 줄로 끝나는 대신 임베딩 서비스의 메모리가 임베딩 표 하나만큼(27.7GB) 더 듭니다.

> **골라 읽는 법** — 번호가 붙은 절이 7개인 글입니다. 절마다 카드 한 장이나 표 하나가 있어서 카드나 표만 보고 넘어가도 됩니다.
>
> - 학습이 남긴 파일 2개와 각 파일이 가는 곳 → 1~2절
> - 서버가 뜨는 41초와 readiness probe → 3절
> - 후보 800건을 한 텐서로 한 번에 넣는 까닭 → 4절
> - 두 버전을 한 서버에 같이 올려 두는 비용 → 5절
> - 웜업 없이 서버를 열면 생기는 일 → 6절
> - 담장 안과 열린 RTB 에서 미리 계산해 둘 수 있는 것의 차이 → 7절

이 글의 파일 크기와 시간은 모두 설명을 위해 정한 가상 값이며 그중 몇 가지는 다른 편과 같은 값을 씁니다. 임베딩 표 27.7GB 는 [대규모 임베딩 테이블 운영](post.html?id=embedding-table-ops) 편에서 계산한 크기입니다. 모델 서버 12대, 모델 호출 예산(서버가 모델을 불러 점수를 받기까지 쓸 수 있는 시간) 8ms, 새 서버가 처음 30초 동안 2.5배 느리다는 값은 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편과 같습니다. 요청 하나에 담기는 후보 800건은 [Ad Serving Flow](post.html?id=ad-serving-flow) 편의 값입니다.

## 1. 학습이 남긴 파일 2개

**학습이 끝나면 신경망 가중치 38MB 와 임베딩 표 27.7GB, 크기가 700배 다른 파일 2개가 남습니다. 임베딩 표는 서버 한 대에 올릴 크기가 아니어서 신경망 가중치와 다른 곳으로 갑니다.**

모델은 파일 하나가 아니라 두 부분으로 나뉘는데 지훈 씨가 학습 폴더에서 본 작은 파일과 큰 파일이 그 두 부분입니다. 큰 파일인 임베딩 표(embedding table)는 「어떤 ID 가 어떤 벡터인가」를 적은 표로, 회원 ID 와 광고 ID 마다 벡터 하나가 한 줄씩 들어 있습니다. 벡터는 숫자 여러 개를 순서대로 늘어놓은 목록입니다. 이 글의 광고 벡터에는 숫자가 32개(32차원) 들어 있습니다. 작은 파일인 신경망 가중치는 신경망이 그 벡터들을 받아 클릭 확률을 계산할 때 쓰는 숫자들입니다.

임베딩 표의 크기는 임베딩 편에서 계산한 값 그대로입니다. 줄이 2억 개인 표에 줄마다 32차원 벡터가 있고 숫자 하나가 4바이트라서 이 표만 2억 × 32 × 4바이트를 차지하며 여기에 다른 표들의 크기를 더하면 27.7GB 가 됩니다. 두 파일의 크기와 가는 곳, 바뀌는 주기는 아래 표와 같다고 가정합니다.

| 파일 | 무엇 | 크기 | 어디로 가나 | 얼마나 자주 바뀌나 |
|---|---|---|---|---|
| 신경망 가중치 | 벡터를 받아 클릭 확률을 내는 계산 | 38MB | 서버 12대 각각 | 매일 새벽 |
| 임베딩 표 | 회원 ID, 광고 ID 마다 벡터 하나 | 27.7GB | 임베딩 서비스 한 곳 | 매일 새벽, 줄 일부만 |

서버 12대가 임베딩 표를 각각 들고 있으면 27.7GB 씩 12대라 332GB 가 듭니다. 그래서 임베딩 표는 임베딩 서비스 한 곳에만 둡니다. 서버는 요청이 올 때마다 그 요청에 필요한 줄만 임베딩 서비스에서 가져오는데, 요청 하나에 필요한 줄은 회원 한 줄과 광고 800줄입니다. 임베딩 서비스가 어떤 서비스이고 27.7GB 를 어떻게 쪼개 담는지는 [대규모 임베딩 테이블 운영](post.html?id=embedding-table-ops) 편에 있습니다. 이 글에서는 서버 12대에 하나씩 올라가는 신경망 가중치 38MB 를 따라갑니다.

바뀌는 방식에서도 두 파일은 서로 다릅니다. 신경망 가중치는 매일 새벽 파일 전체가 새 파일로 바뀌므로 서버가 뜰 때 새 파일을 내려받으면 됩니다. 임베딩 표는 새로 생긴 ID 의 줄이 추가되고 죽은 ID 의 줄이 빠지는 식으로 일부 줄만 바뀌므로 임베딩 서비스를 켜 둔 채로 그 줄들만 고칩니다. 신경망 가중치 38MB 를 서버에 올릴 때는 먼저 파일 형식을 서빙 포맷으로 바꿉니다.

## 2. 서빙 포맷(ONNX) 변환

**학습 형식 그대로인 파일은 학습 프레임워크와 모델의 파이썬 코드가 서버에 있어야 열립니다. ONNX 로 바꾸면 계산 순서(그래프)와 가중치만 남아 작은 실행 프로그램(런타임) 하나로 열립니다.**

선배는 작은 파일을 「서빙 포맷으로 바꿔서」 내려받는다고 했습니다. 서버 이미지는 기본 리눅스부터 서버 코드까지 쌓아 빌드한 파일 하나로, 서버는 뜰 때 이 이미지로 켜집니다. 학습이 남긴 파일을 그대로 올리면 그 파일을 여는 데 필요한 학습 프레임워크와 모델 코드까지 서버 이미지에 넣어야 하고 파일을 메모리에 올리는 시간도 길어서 서빙 포맷으로 바꿉니다.

학습 형식의 파일에는 「이 클래스의 객체를 이렇게 복원하라」는 지시가 적혀 있습니다. 클래스는 모델의 구조를 정의한 파이썬 코드입니다. 학습 프레임워크는 그 코드로 모델을 만들고 학습시키는 라이브러리입니다. 서버가 파일의 지시대로 모델을 되살리려면 클래스 코드와 학습 프레임워크가 서버에 같이 있어야 합니다. 반면 ONNX 파일에는 계산 순서(그래프)와 그 계산에 쓰는 숫자(가중치)만 적혀 있으므로 서버에는 모델 코드 없이 이 파일과 추론 런타임만 있으면 됩니다. 추론 런타임은 ONNX 파일을 읽어 그래프에 적힌 순서대로 계산을 실행하는 프로그램입니다.

카드는 색으로 역할을 구분합니다. 파랑은 놓여 있는 것(모델 파일, 임베딩 표, 설정), 벽돌색은 지금 오는 것(요청, 후보), 먹색은 모델과 서버, 회색은 만드는 작업(변환, 웜업, 추론)이며 점선 상자는 적어 둔 것(설정, readiness probe 의 조건)입니다. 첫 번째 카드에서는 같은 가중치 38MB 를 학습 형식 그대로 올릴 때와 ONNX 로 바꿔 올릴 때 서버에 함께 있어야 하는 것이 어떻게 달라지는지를 보면 됩니다.

카드에 적힌 숫자로 보면 학습 형식 그대로 올릴 때는 학습 프레임워크 1.2GB 와 모델 클래스의 파이썬 코드가 서버 이미지에 들어가야 하지만 ONNX 로 바꾸면 추론 런타임 0.8GB 만 넣으면 됩니다. 앞 편 [Docker 와 CI](post.html?id=container-ci-pipeline) 의 추론 이미지는 학습 프레임워크 대신 이 런타임을 넣었기 때문에 1.1GB 로 작았습니다. 파일을 읽어 메모리에 올리는 적재(load) 시간도 줄어서 이 팀에서는 학습 형식이 9초, ONNX 가 3초입니다. 3절에서 볼 41초 안의 적재 3초가 이 ONNX 의 적재 시간입니다.

서버 코드가 모델에 무엇을 넣고 무엇을 돌려받는지는 ONNX 파일의 서명(signature)에 적혀 있습니다. 서명은 모델이 받는 입력과 내놓는 출력의 이름, 자료형, 모양을 적은 목록입니다. 바꾼 파일을 서버가 열면 아래처럼 입력 3개와 출력 1개가 나옵니다. 모양의 첫 숫자 800 은 요청 하나에 담긴 후보 수입니다.

```text
model: pctr-v418.onnx (38MB)
inputs
  ids     int64   [800, 6]     # 후보마다 해시된 ID 피처 여섯 (광고, 지면, 카테고리 등)
  emb     float32 [800, 32]    # 임베딩 서비스에서 가져온 광고 줄 800개
  dense   float32 [800, 12]    # 집계 피처 12개 (7일 클릭률 등)
outputs
  pctr    float32 [800]        # 후보마다 클릭 확률 하나
```

서명을 위에서부터 읽으면 서버는 후보 800건마다 광고와 지면과 카테고리 같은 ID 를 해시한 피처 6개(`ids`), 임베딩 서비스에서 가져온 광고 벡터 32차원(`emb`), 7일 클릭률 같은 집계 피처 12개(`dense`)를 넣습니다. 모델은 후보마다 클릭 확률 하나(`pctr`)를 돌려줍니다. 지훈 씨가 추가한 7일 클릭률도 `dense` 에 든 집계 피처 12개 가운데 하나입니다. 앞 편의 계약 테스트(새 이미지로 서버를 켜고 요청을 보내 응답의 모양과 속도가 약속대로인지 보는 검사)가 응답 필드 12개의 모양을 봤다면 이 서명은 서버 코드와 모델 파일 사이의 모양입니다. 서버 코드가 넣는 입력 3개의 이름과 자료형과 차원 수가 서명과 맞아야 합니다. 서버에 올릴 파일이 준비됐으니 이제 서버가 켜져서 첫 요청을 받기까지의 41초를 봅니다.

## 3. 서버가 뜨는 41초와 readiness probe

**새 서버는 켜지자마자 답하지 않고 이미지 시작 12초, 모델 내려받기 6초, 적재 3초, 웜업 20초를 지나 41초에 readiness probe 를 통과합니다. 게이트웨이(요청을 어느 서버로 보낼지 정하는 장치)는 이 검사를 통과한 서버에만 요청을 보냅니다.**

모델 파일을 메모리에 올린 서버는 이미 답할 수 있지만 곧바로 요청을 받지는 않습니다. 그 상태로 실제 요청을 받으면 처음 30초 동안 2.5배 느리게 답하므로 readiness probe 로 준비가 다 끝났는지 먼저 확인한 뒤에 요청을 보냅니다. readiness probe 는 서버에게 요청을 받을 준비가 됐는지를 일정한 간격으로 묻는 검사입니다. 서버는 미리 정해 둔 조건을 모두 채웠을 때만 「나 준비됐다」고 답합니다. 이 글의 서버는 그 조건에 웜업을 넣었습니다.

아래 카드에서는 41초가 이미지 시작, 내려받기, 적재, 웜업의 4단계로 나뉜 막대와 웜업 200건이 끝나야 readiness probe 를 통과한다는 조건을 보면 됩니다.

41초를 단계별로 보면 처음 12초는 앞 편에서 만든 1.1GB 이미지가 켜지면서 파이썬과 추론 런타임이 올라오는 시간입니다. 다음 6초에는 모델 파일 38MB 를 저장소에서 가져옵니다. 이미지에 모델 파일을 넣지 않았으므로 서버가 뜰 때마다 여기서 내려받습니다. 그다음 3초는 내려받은 파일을 메모리에 올리는 적재입니다. 12초, 6초, 3초를 더한 21초에 모델은 이미 답할 수 있는 상태가 되지만 서버는 아직 요청을 받지 않습니다.

마지막 20초는 웜업(warm-up)입니다. 웜업은 서버가 더미 요청(실제 사용자가 보내지 않은 시험용 요청) 200건을 자기 자신에게 보내 답하게 하는 단계입니다. 추론 런타임은 계산 순서를 최적화하고 계산에 쓸 메모리를 잡는 일을 첫 요청이 들어왔을 때 하므로 처음 몇 번의 계산이 느립니다. 이 몫을 실제 요청이 치르게 두면 첫 30초가 느려지므로 서버는 더미 요청 200건으로 그 몫을 미리 치르고 200건이 다 끝나야 readiness probe 를 통과합니다. 21초에 웜업 20초를 더한 41초가 선배가 말한 「41초 뒤」입니다.

readiness probe 는 서버가 도는 Pod 의 설정에 적어 둡니다. Pod 는 쿠버네티스(Kubernetes)가 앱을 실행하는 가장 작은 단위입니다. Pod 와 그 앞에서 요청을 나눠 주는 Service 는 [쿠버네티스 네트워킹](post.html?id=kubernetes-networking) 편에 있습니다. 아래는 Pod 설정에 들어가는 readiness probe 부분입니다. 언제부터 몇 초마다 묻는지와 몇 번 실패하면 이 서버에 요청을 보내지 않는지가 적혀 있습니다.

```yaml
readinessProbe:
  httpGet:
    path: /ready            # 모델이 올라오고 웜업 200건이 끝나면 200 을 돌려주는 주소
    port: 8080
  initialDelaySeconds: 20   # 켜지고 20초는 묻지 않습니다
  periodSeconds: 3          # 그 뒤 3초마다 묻습니다
  failureThreshold: 10      # 열 번 연속 실패면 이 서버에는 안 보냅니다
```

설정의 숫자를 읽으면 readiness probe 는 서버가 켜지고 20초 동안은 묻지 않다가(`initialDelaySeconds: 20`) 그 뒤로 3초마다 `/ready` 에 묻습니다(`periodSeconds: 3`). 10번 연속 실패하면 이 서버에는 요청을 보내지 않습니다(`failureThreshold: 10`). `/ready` 는 모델 파일 내려받기, 메모리 적재, 웜업 200건이 모두 끝났을 때만 200(정상이라는 HTTP 응답 코드)을 돌려줍니다. 이 3가지 조건이 모두 참이 된 서버만 게이트웨이가 요청을 보내는 목록에 들어가므로 41초 전에는 새 서버로 요청이 가지 않습니다. 웜업을 기다리지 않고 서버를 열면 무슨 일이 생기는지는 6절에서 세어 봅니다. 그 전에 다음 절에서는 준비를 마친 서버가 요청 하나를 어떻게 처리하는지 봅니다.

## 4. 한 텐서로 넣는 후보 800건

**요청 하나에 담겨 온 후보 800건을 하나씩 800번 모델에 넣으면 96ms 가 걸리고 800줄을 한 텐서로 모아 한 번에 넣으면 3.0ms 가 걸립니다. 모델 호출 예산 8ms 안에는 한 번에 넣는 방식만 들어갑니다.**

요청 하나에 담긴 후보 수백 건을 하나씩 계산하는지 한꺼번에 계산하는지는 지훈 씨가 몰랐던 세 번째 물음이었습니다. 어느 방식을 쓰느냐에 따라 모델 호출이 예산 안에 드는지가 정해집니다.

모델을 한 번 부를 때마다 실제 계산과는 상관없는 오버헤드(overhead)가 붙습니다. 오버헤드는 입력을 받아 모델에 넘기고 결과를 꺼내는 일에 드는 시간이라 후보 수와 상관없이 호출 한 번마다 생깁니다. 그래서 후보 800건을 하나씩 부르면 오버헤드가 800번 붙지만 800건을 한 텐서로 모아 한 번 부르면 오버헤드는 한 번만 붙습니다. 텐서(tensor)는 모델에 넣는 숫자 배열입니다. 2절 서명의 `dense` 가 `[800, 12]` 였던 것처럼 후보 하나가 한 줄인 표 모양이라 후보 800건을 800줄짜리 텐서 하나로 만들어 한 번에 넣을 수 있습니다.

카드에서는 하나씩 부를 때 호출마다 오버헤드가 다시 붙어 96ms 까지 쌓인 막대와 한 번에 넣을 때의 3.0ms 막대를 예산 8ms 선과 비교하면 됩니다.

호출 한 번의 오버헤드와 후보 한 건의 계산 비용은 측정값 2개로 구할 수 있습니다. 이 팀의 서버에서 후보 800건을 한 텐서로 넣으면 3.0ms, 후보 한 건만 넣으면 0.12ms 가 걸립니다(가상 값). 모델을 한 번 부르는 시간을 「오버헤드 + 후보 수 × 건당 계산 비용」으로 두면 이 두 측정값에서 미지수 2개가 풀립니다. 아래 코드는 먼저 두 미지수를 구한 다음 후보 수를 1건, 100건, 800건, 2,000건으로 바꿔 가며 두 방식의 시간을 예산 8ms 와 비교합니다.

```python
# 하는 일: 측정 두 개로 호출 오버헤드와 후보 한 건의 계산 비용을 풀고, 후보를 한 텐서로 넣을 때와 하나씩 부를 때의 시간을 비교한다.
# 1단계: 측정 둘에서 오버헤드와 건당 비용을 푼다
# 측정값(가상)은 한 텐서 800건 3.0ms, 후보 1건 한 번 0.12ms 다. 시간 = 오버헤드 + 후보 수 × 건당 비용 이라고 두면 미지수 둘이 풀린다.
BUDGET = 8.0
T_800, T_1 = 3.0, 0.12
per_row = (T_800 - T_1) / 799          # 후보 한 건의 계산 비용
fixed = T_1 - per_row                   # 호출 한 번의 오버헤드
print(f"호출 오버헤드 {fixed:.4f}ms, 건당 계산 {per_row:.4f}ms")
# 2단계: 후보 수마다 두 방식의 시간을 예산과 비교한다
# 모델 호출 예산은 8ms 다.
print(f"{'후보 수':>7}  {'한 텐서':>8}  {'하나씩':>9}   판정 (예산 {BUDGET:.0f}ms)")
for n in (1, 100, 800, 2000):
    one = fixed + n * per_row           # 한 번 부르고 n 줄 계산
    each = n * (fixed + per_row)        # n 번 부르고 매번 1줄 계산
    v1 = "통과" if one <= BUDGET else "초과"
    v2 = "통과" if each <= BUDGET else "초과"
    print(f"{n:>7,}  {one:>7.2f}ms  {each:>8.2f}ms   한 텐서 {v1}, 하나씩 {v2}")

# 출력:
# 1단계 뜻: 호출 한 번의 오버헤드 0.1164ms 가 후보 한 건의 계산 0.0036ms 보다 훨씬 크다.
# 호출 오버헤드 0.1164ms, 건당 계산 0.0036ms
# 2단계 뜻: 하나씩 부르면 오버헤드가 후보마다 붙어 100건에서 이미 12.00ms 로 예산을 넘는다. 한 텐서로 넣으면 2,000건도 7.33ms 로 통과한다.
#    후보 수      한 텐서        하나씩   판정 (예산 8ms)
#       1     0.12ms      0.12ms   한 텐서 통과, 하나씩 통과
#     100     0.48ms     12.00ms   한 텐서 통과, 하나씩 초과
#     800     3.00ms     96.00ms   한 텐서 통과, 하나씩 초과
#   2,000     7.33ms    240.00ms   한 텐서 통과, 하나씩 초과
```

1단계 줄에 찍힌 값은 호출 한 번의 오버헤드 0.1164ms 와 후보 한 건의 계산 0.0036ms 입니다. 800건일 때의 3.0ms 와 1건일 때의 0.12ms 의 차이는 후보 799건만큼의 계산 시간이므로 그 차이를 799 로 나눈 0.0036ms 가 후보 한 건의 계산 비용입니다. 1건일 때의 0.12ms 에서 이 0.0036ms 를 빼면 호출 한 번의 오버헤드 0.1164ms 가 남습니다.

후보가 1건이면 두 방식 모두 0.12ms 로 같지만 오버헤드가 건당 계산의 32배라서 후보가 늘수록 두 방식의 시간이 크게 벌어집니다. 하나씩 부르는 방식은 호출마다 오버헤드를 다시 치러 후보 한 건에 0.12ms 씩 쌓이므로 100건에서 이미 12.00ms 로 예산 8ms 를 넘기고 800건이면 96.00ms 입니다. 한 텐서로 넣는 방식은 오버헤드를 한 번만 치르고 후보 한 건에 0.0036ms 씩만 늘어나서 800건이 3.00ms, 2,000건도 7.33ms 로 예산 안에 듭니다. 후보를 800건에서 2,000건으로 늘려도 예산 안에 든다는 여유가 이 계산에서 나옵니다.

그래서 서버 코드는 요청에 담긴 후보를 모아 한 텐서로 만든 뒤 모델을 한 번만 부릅니다. 이 결정 때문에 2절의 서명도 입력을 후보 800건이 쌓인 `[800, …]` 모양으로 받습니다. 요청 하나 안의 후보가 아니라 요청 여럿을 모아 더 큰 텐서로 만드는 방법(배치)도 있지만 그 방법을 쓰면 요청이 모이기를 기다리는 시간이 붙습니다. 요청을 얼마나 모을지 따지는 내용은 [광고 모델 서빙 아키텍처](post.html?id=model-serving-architecture) 편의 배치 카드에 있습니다.

## 5. 한 서버에 같이 올려 두는 두 버전

**운영 중인 v417 과 새 v418 을 한 서버에 같이 올려 두고 어느 버전이 답할지는 설정 한 줄로 정합니다. 바꾸기도 되돌리기도 그 한 줄만 고치면 되므로 몇 초면 끝납니다.**

새 모델로 바꿀 때 서버를 새로 띄우면 3절의 41초가 서버 12대 모두에 듭니다. 두 버전을 한 서버에 같이 올려 두면 바꾸는 순간에도 서버를 껐다 켜지 않아도 되므로 그 41초를 기다리지 않습니다. 서버는 두 버전의 파일을 모두 메모리에 올려 둔 채 설정이 가리키는 버전만 바꾸고 문제가 생기면 가리키는 곳을 도로 돌립니다.

카드 위쪽에는 서버 한 대 안에 v417 과 v418 이 함께 올라가 있고 `active` 한 줄이 그중 답할 버전을 가리킵니다. 아래쪽에서는 버전마다 따로 있어야 하는 임베딩 표 때문에 임베딩 서비스가 55.4GB 로 늘어나는 비용을 보면 됩니다.

서버 안의 설정에서는 `active` 한 줄이 어느 버전이 답할지 정합니다. `loaded` 에는 메모리에 올려 둔 두 버전이 적혀 있습니다.

```yaml
active: v417        # 지금 답하는 버전. v418 로 바꾸면 다음 요청부터 v418 이 답합니다
loaded: [v417, v418]
```

`active` 를 v418 로 바꾸면 서버는 켜진 그대로 메모리에 이미 올라와 있는 v418 파일을 가리키기만 하므로 다음 요청부터 v418 이 답합니다. 되돌리기도 같은 방식이라 새 모델이 이상하면 `active` 를 v417 로 돌리면 됩니다. [시스템 설계 면접](post.html?id=interview-system-design) 편의 「되돌리는 데 30분이 걸리면 그 30분 동안 사고가 계속된다」는 문장이 여기에 해당합니다.

두 버전을 같이 올려 두는 비용은 메모리입니다. 버전마다 신경망 가중치 38MB 와 임베딩 표 27.7GB 가 하나씩 든다고 가정하면 두 버전을 다 올려 둘 때는 둘 다 두 배가 됩니다.

| 무엇 | v417 만 | v417 과 v418 | 더 드는 비용 |
|---|---|---|---|
| 서버 12대의 신경망 | 38MB 씩 | 76MB 씩 | 거의 안 듭니다 |
| 임베딩 서비스의 표 | 27.7GB | 55.4GB | 27.7GB 를 더 듭니다 |
| 전환에 걸리는 시간 | 없음 | 설정 한 줄, 몇 초 | |
| 되돌리기 | 없음 | 같은 한 줄 | |

표의 첫 줄을 보면 서버마다 신경망 가중치는 38MB × 2 = 76MB 로 늘어날 뿐이라 비용이 거의 들지 않습니다. 비용은 둘째 줄의 임베딩 서비스에서 듭니다. v418 은 v417 과 다른 임베딩을 학습했으므로 v418 의 임베딩 표가 따로 있어야 합니다. 그래서 임베딩 서비스의 표는 27.7GB × 2 = 55.4GB 로 늘어나 27.7GB 가 더 듭니다. 이 비용 때문에 두 버전을 같이 두는 기간을 미리 정해 두고 새 버전이 자리를 잡으면 옛 버전의 임베딩 표를 내립니다. 그 기간을 정하는 절차는 다음 편 [모델 배포와 롤백](post.html?id=model-deployment-rollback) 에서 다룹니다.

## 6. 웜업 없이 열면 생기는 일

**웜업 없이 서버를 열면 첫 30초 동안 요청이 2.5배 느려집니다. 그동안 예산을 넘겨 모델 답 대신 기본값(폴백)으로 나가는 요청이 서버 2대를 바꿀 때마다 5,637건, 12대를 다 바꾸면 33,821건 더 나갑니다.**

3절의 웜업 20초를 아끼려고 서버를 바로 열면 추론 런타임이 첫 요청들에서 하는 준비 작업의 몫을 실제 요청이 치릅니다. 모델 호출 예산 8ms 를 넘긴 요청은 모델이 매긴 점수 대신 기본값으로 나가는데, 이 기본값을 폴백(fallback)이라고 부릅니다. 웜업을 뺐을 때 폴백이 평소보다 몇 건 더 나가는지 세어 봅니다.

새 서버가 느린 장면은 [서빙 지연과 처리량](post.html?id=serving-latency-throughput) 편 8절에 나옵니다. 서버 12대 가운데 2대를 새로 올리면 새 2대가 첫 30초 동안 2.5배 느려서 그동안 서버 12대 전체의 8ms 초과율이 4.62% 에서 11.74% 로 오릅니다. 8ms 초과율은 예산 8ms 를 넘긴 요청의 비율이고 낮을수록 좋습니다. 아래 코드는 이 두 초과율로 폴백이 평소보다 몇 건 더 나가는지 셉니다.

```python
# 하는 일: 웜업 없이 새 서버 2대를 열면 첫 30초 동안 폴백이 평소보다 몇 건 더 나가는지 센다.
# 1단계: 서버 수와 초과율을 둔다
# 서버 12대가 초당 2,639건을 나눠 받는다. 새 2대가 첫 30초 동안 2.5배 느리면 서버 12대 전체의 8ms 초과율이 4.62% 에서 11.74% 가 된다(서빙 지연과 처리량 편 8절 값).
QPS, SERVERS, COLD_SEC = 2639, 12, 30
NORMAL, COLD = 0.0462, 0.1174
# 2단계: 새 2대가 느린 30초 동안 12대 전체에서 더 넘긴 요청을 센다
# 초과율이 12대 전체의 값이라 12대가 받은 요청 전부에 곱한다. 배포는 2대씩 여섯 번 한다.
per_server = QPS / SERVERS                      # 서버 한 대가 받는 초당 요청
cold_reqs = QPS * COLD_SEC                      # 새 2대가 느린 30초 동안 12대 전체가 받는 요청
extra = cold_reqs * (COLD - NORMAL)             # 평소보다 더 넘긴 요청
print(f"서버 한 대 초당 {per_server:.0f}건. 새 2대가 느린 첫 30초 동안 12대 전체가 받는 요청 {cold_reqs:,.0f}건")
print(f"그중 예산을 넘겨 폴백으로 나간 요청이 평소보다 {extra:,.0f}건 더 (2대 한 번 바꿀 때)")
print(f"12대를 2대씩 여섯 번 바꾸면 {extra * 6:,.0f}건. 웜업 200건을 먼저 보내면 0건")

# 출력:
# 2단계 뜻: 새 2대를 한 번 열 때마다 폴백이 5,637건 더 나가고, 12대를 다 바꾸는 여섯 번이면 33,821건이다. 웜업 요청 200건을 먼저 보내면 0건이 된다.
# 서버 한 대 초당 220건. 새 2대가 느린 첫 30초 동안 12대 전체가 받는 요청 79,170건
# 그중 예산을 넘겨 폴백으로 나간 요청이 평소보다 5,637건 더 (2대 한 번 바꿀 때)
# 12대를 2대씩 여섯 번 바꾸면 33,821건. 웜업 200건을 먼저 보내면 0건
```

코드가 찍은 첫 줄을 보면 서버 12대가 초당 2,639건을 나눠 받으므로 서버 한 대는 초당 약 220건을 받습니다. 11.74% 는 새 2대만의 값이 아니라 서버 12대 전체의 초과율이라서 코드는 새 2대가 느린 30초 동안 12대 전체가 받는 요청 79,170건(초당 2,639건 × 30초)에 곱합니다. 둘째 줄의 5,637건은 이 79,170건에 11.74% 와 4.62% 의 차이를 곱한 값으로, 평소보다 예산을 더 넘겨 폴백으로 나간 요청 수입니다. 12대를 2대씩 여섯 번 바꾸는 배포 한 번 전체로는 셋째 줄의 33,821건이 더 나갑니다. 웜업 200건을 먼저 보내면 더 나가는 폴백은 0건입니다.

배포 한 번에 33,821건이면 하루 요청 2억 2,800만 건에 비해 작아 보이지만 이 33,821건은 모두 배포 직후 몇 분 안에 몰려 있습니다. 그 시각에 광고를 본 사람들은 폴백 때문에 순위가 틀린 광고를 봅니다. 게다가 모델이 매일 바뀌므로 배포도 매일 일어납니다.

서버 한 대가 초당 220건을 받으므로 웜업 200건은 실제 요청으로 치면 1초 분량입니다. readiness probe 의 조건에 웜업을 넣어 이 1초 분량의 계산을 더미 요청으로 20초 동안 먼저 치르면 아래 표의 아랫줄처럼 첫 30초 초과율이 평소와 같은 4.62% 이고 더 나가는 폴백은 0건입니다. 다음 편의 카나리 배포(새 버전을 트래픽 일부에만 먼저 열어 보는 배포)도 새 서버 2대를 띄울 때 이 41초를 그대로 기다립니다.

| 열 때 | 첫 30초 초과율 | 2대 한 번에 폴백 | 12대 전부 |
|---|---|---|---|
| 웜업 없이 바로 | 11.74% | 5,637건 더 | 33,821건 더 |
| 웜업 200건 뒤 | 4.62% (평소와 같음) | 0건 | 0건 |

## 7. 미리 계산해 둘 수 있는 범위의 차이

**담장 안(한 회사가 앱과 서버를 다 가진 곳)에서는 요청량과 회원을 알므로 웜업 요청을 실제 분포대로 만들고 유저 벡터(회원 한 사람의 임베딩)를 미리 계산해 둡니다. 열린 RTB(남의 거래소가 보내는 입찰 요청을 받는 곳)에서는 요청량이 갑자기 크게 바뀌고 쿠키가 매번 달라서 웜업 표본을 거래소별 로그에서 섞어 뽑고 유저 벡터는 그때그때 계산합니다.**

서버가 뜨는 41초와 후보를 한 텐서로 넣는 계산은 두 무대(담장 안과 열린 RTB)에서 똑같습니다. 다만 두 무대는 요청이 오기 전에 미리 해 둘 수 있는 일의 범위가 다릅니다. 그 범위에 따라 웜업 요청 200건을 어디서 뽑는지와 유저 벡터를 언제 계산하는지가 달라집니다.

### 담장 안: 실제 요청과 같은 웜업 [무대: 닫힌 생태계]

한 회사가 앱과 서버를 다 가진 담장 안에서는 요청이 얼마나 오고 어떤 회원이 오는지를 압니다. 그래서 웜업 요청 200건을 어제 로그에서 뽑으면 실제 요청과 같은 모양이 됩니다. 회원 ID 마다 임베딩 줄(유저 벡터)을 미리 만들어 두므로 서버는 요청이 오면 그 회원의 줄을 조회하기만 합니다. [Two-Tower Retrieval](post.html?id=two-tower-retrieval) 편이 「유저 벡터를 미리 계산해 둘 수 있다」고 쓴 상황이 담장 안입니다. 이 블로그의 저자가 일하는 자리도 여기입니다. 이 글의 카드 네 장은 이 상태를 그렸습니다.

### 열린 RTB: 요청 때 계산하는 유저 벡터 [무대: 열린 RTB]

열린 RTB(Real-Time Bidding, 실시간 입찰)에서는 입찰 서버가 남의 거래소(광고 지면을 경매에 부쳐 응찰을 받는 곳)가 보내는 요청을 받습니다. 요청량은 거래소 사정에 따라 갑자기 크게 바뀝니다. 요청에는 회원 ID 대신 쿠키(브라우저에 저장해 두는 식별 값)가 담겨 오는데 쿠키는 매번 달라서 그 사람의 임베딩 줄을 미리 만들어 둘 수 없습니다. 유저 벡터를 요청이 온 그때 계산해야 하므로 4절의 한 텐서 계산에 유저 벡터를 계산하는 몫이 더 붙습니다. 웜업 표본도 어느 거래소의 요청이 올지 몰라서 거래소별 로그에서 섞어 뽑습니다. [광고 모델 서빙 아키텍처](post.html?id=model-serving-architecture) 편 9절은 이 차이를 「남의 트래픽은 튀고 캐시는 안 맞는다」는 한 문장으로 적었습니다.

| 무엇 | 담장 안 | 열린 RTB |
|---|---|---|
| 웜업 요청 200건의 출처 | 어제 우리 로그 | 거래소별 로그를 섞어서 |
| 유저 쪽 임베딩 | 회원 ID 로 미리 계산해 둠 | 쿠키라 요청 때 계산 |
| 요청량 | 우리가 압니다 | 거래소 사정에 따라 튑니다 |
| 한 텐서 계산에 붙는 것 | 조회뿐 | 유저 쪽 계산이 더 붙습니다 |

## 한눈 정리

| 질문 | 한 줄 답 |
|---|---|
| 학습이 남기는 파일은 | 2개입니다. 신경망 38MB 와 임베딩 표 27.7GB 입니다 |
| 두 파일은 어디로 가나 | 신경망은 서버 12대 각각, 임베딩은 임베딩 서비스 한 곳입니다 |
| 왜 포맷을 바꾸나 | ONNX 면 프레임워크와 코드 없이 런타임 0.8GB 로 열립니다 |
| 서버가 뜨는 데 얼마나 걸리나 | 41초입니다. 이미지 12초, 내려받기 6초, 적재 3초, 웜업 20초 |
| readiness probe 가 무엇인가 | 내려받기, 적재, 웜업 3가지가 다 끝났는지 확인하는 검사입니다. 게이트웨이는 통과한 서버에만 보냅니다 |
| 후보 800건은 어떻게 넣나 | 한 텐서로 한 번에 3.0ms 입니다. 하나씩이면 96ms 입니다 |
| 두 버전을 왜 같이 올려 두나 | 전환과 되돌리기가 설정 한 줄, 몇 초가 됩니다 |
| 그 비용은 | 임베딩 표 27.7GB 가 하나 더 듭니다 |
| 웜업을 빼면 | 2대 바꿀 때 폴백 5,637건, 12대면 33,821건이 더 나갑니다 |

## 헷갈리기 쉬운 점

- **모델 파일은 하나가 아니라 2개입니다.** 신경망 가중치 38MB 는 서버 12대에 하나씩 올라갑니다. 임베딩 표 27.7GB 는 서버마다 올리면 332GB 가 들어서 임베딩 서비스 한 곳에만 둡니다.
- **ONNX 로 바꿔도 가중치는 38MB 그대로입니다.** 서버 이미지에서는 학습 프레임워크 1.2GB 와 모델 코드가 빠지고 그 자리에 추론 런타임 0.8GB 가 들어갑니다.
- **적재가 끝났다고 준비가 끝난 상태는 아닙니다.** 모델은 적재가 끝난 21초부터 답할 수 있지만 readiness probe 는 더미 요청 200건으로 하는 웜업까지 마친 41초에 통과합니다.
- **한 텐서는 요청 하나에 담긴 후보를 모은 숫자 배열입니다.** 요청 여럿을 모아 더 큰 텐서로 만드는 배치와는 다릅니다. 배치에는 요청이 모이기를 기다리는 시간이 붙습니다.
- **두 버전을 같이 올려 두는 비용은 신경망 가중치가 아니라 임베딩 표에서 듭니다.** 서버마다 신경망 가중치는 76MB 로 작지만 임베딩 서비스의 표는 55.4GB 가 되어 27.7GB 가 더 듭니다.
