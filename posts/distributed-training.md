지훈 씨는 여덟째 주에 피처를 하나 더했습니다. 유저가 지난주에 본 광고 카테고리입니다. 이 피처는 어제 모델 위에 이어 붙일 수가 없었습니다. 모델이 받는 입력의 모양이 바뀌면 처음부터 다시 배워야 하기 때문입니다.

그래서 30일 전체로 재학습을 걸어 놓고 자리에 앉았습니다. 매일 새벽에 도는 학습은 55분이면 끝났습니다. 이번에는 남은 시간이 6시간 20분으로 떴습니다. 04:00 에 시작하면 10:20 에 끝납니다. 그날 새 모델을 배포에 태우는 시각은 이미 지난 뒤입니다.

**GPU 를 네 장 쓰면 네 배 빨라지나요?**

여러 장에 나눠 학습하는 것을 분산 학습(distributed training)이라고 부릅니다. 네 장이면 3.5배까지 갑니다. 네 배가 아닌 이유가 이 글의 앞쪽 내용입니다. 광고 모델에는 한 가지가 더 붙습니다. 임베딩 표가 커서 나누는 방법이 신경망과 다릅니다. 이것을 모르면 장수를 늘려도 학습이 아예 시작되지 않습니다.

> **한 줄 요약:** 30일 전체 재학습은 GPU 한 장에서 6시간 20분입니다. 데이터를 넷으로 나눠 같은 모델 넷이 함께 배우면 1시간 50분이 되고 여덟 장이면 1시간 5분이 됩니다. 장수를 두 배로 해도 시간이 절반이 안 되는 것은, 기울기를 합치고 늦은 장을 기다리는 시간이 장수에 비례해 붙기 때문입니다. 광고 모델이 다른 점은 임베딩 표입니다. 27.7GB 가 학습 때 83.2GB 가 되어 GPU 한 장에 안 들어갑니다. 그래서 신경망만 넷이 복제해 갖고 임베딩은 파라미터 서버 두 대에 쪼개 둡니다.

> **골라 읽는 법** — 절이 여섯 개인 글입니다. 절마다 카드 한 장이나 표 하나가 있어 그것만 보고 넘어가도 됩니다.
>
> - 6시간 20분이 어디서 나온 숫자인지 → 1절
> - 데이터를 넷으로 나누는 방식 → 2절
> - 기울기를 언제 합치나 → 3절
> - 임베딩만 따로 쪼개는 이유 → 4절
> - 장수를 늘리면 시간이 얼마나 주나 → 5절
> - 담장 안과 열린 RTB 에서 무엇이 달라지나 → 6절

이 글의 시간, 행 수, 장수는 전부 설명을 위한 가상 값입니다. 하루 학습 행 2,485만 건과 학습 55분은 [학습 파이프라인](post.html?id=training-pipeline-dag) 편과 같은 값입니다. 임베딩 표 27.7GB 와 학습 때의 83.2GB 는 [임베딩 테이블 운영](post.html?id=embedding-table-ops) 편에서 곱해 본 값입니다. 카드 속 색은 넷입니다. 파랑은 놓여 있는 데이터(학습 행, 임베딩 표)이고 벽돌색은 지금 문제가 되는 것(기다림, 안 들어가는 크기)입니다. 먹색은 GPU 와 파라미터 서버이고 회색은 만드는 작업입니다. 점선 상자는 적어 둔 것입니다.

## 1. 30일 전체를 다시 학습하면 6시간 20분입니다

**학습 시간은 배울 행의 수와 행 하나에 드는 계산으로 정해집니다. 하루치 2,485만 행은 55분이고, 30일 7억 4,550만 행은 6시간 20분입니다.**

쉽게 말하면 학습이 오래 걸리는 이유는 둘뿐입니다. 배울 행이 많거나, 행 하나를 배우는 데 오래 걸리거나입니다. 30일 전체를 다시 배우면 앞의 것이 서른 배가 됩니다.

매일 새벽에 도는 학습이 55분인 것은 어제 하루치만 배우기 때문입니다. 어제 모델을 그대로 불러와 어제 로그 2,485만 행을 한 번 더 얹습니다. 이것을 이어 학습이라고 부릅니다. 모델은 처음부터 다시 만들어지는 것이 아니라 하루씩 갱신됩니다. 앞 편의 새벽 파이프라인에서 네 번째 칸이 하는 일이 이것입니다.

이번 주는 그 방법을 쓸 수 없었습니다. 새 피처가 들어가면 모델이 받는 입력의 모양이 달라집니다. 어제 모델의 첫 층은 예전 모양에 맞춰져 있어 새 입력을 받을 자리가 없습니다. 그래서 학습 창에 있는 30일을 전부 꺼내 처음부터 다시 배웁니다. 하루 2,485만 행에 30을 곱하면 7억 4,550만 행입니다.

남은 것은 행 하나에 드는 계산입니다. GPU 한 장이 초당 몇 행을 넘기느냐로 나타냅니다. 한 번에 올리는 행의 묶음을 배치라고 부르는데, 이 값이 속도를 크게 바꿉니다. 매일 학습은 배치 1,024 로 돌고 초당 7,530행입니다. 재학습은 배치를 4,096 으로 키워 초당 32,700행입니다. 배치가 작으면 GPU 안의 계산 장치 상당수가 놀고, 키우면 한 번에 곱하는 행이 늘어 노는 시간이 줍니다.

가정은 GPU 한 장이 배치 4,096 으로 초당 32,700행을 넘긴다는 것입니다. 계산식은 7억 4,550만 행 ÷ 초당 32,700행 = 22,798초, 곧 6시간 20분입니다.

| 무엇 | 매일 이어 학습 | 30일 전체 재학습 |
|---|---|---|
| 배우는 행 | 어제 2,485만 행 | 30일 7억 4,550만 행 |
| 시작하는 자리 | 어제 모델 | 처음부터 |
| 한 번에 올리는 행(배치) | 1,024 | 4,096 |
| GPU 한 장이 초당 넘기는 행 | 7,530 | 32,700 |
| 걸리는 시간 | 55분 | 6시간 20분 |

이 6시간 20분이 왜 문제인지는 시각으로 보면 분명합니다. 04:00 에 시작하면 10:20 에 끝납니다. 새 모델을 배포에 태워 달라고 요청하는 시각은 06:09 입니다. 여섯 시간짜리 학습은 그 시각을 네 시간 넘깁니다. 하루를 통째로 미루면 새 피처가 붙은 모델이 하루 늦게 나갑니다.

시간을 줄이는 길은 둘뿐입니다. 배울 행을 줄이거나, 행 하나의 계산을 여러 장에 나누는 것입니다. 앞의 것은 30일을 14일로 줄이는 방식인데, 학습 창이 짧아지면 드물게 나오는 광고의 데이터가 모자라 모델이 나빠집니다. 그래서 행은 그대로 두고 나누는 쪽을 봅니다. 나누는 방법이 다음 절입니다.

## 2. 데이터를 넷으로 나누고 모델은 넷이 같이 갖습니다

**데이터 병렬은 같은 모델을 GPU 넷에 복제하고 데이터만 사등분합니다. 넷이 각자 낸 기울기를 평균 내 같은 모델로 되돌립니다. 6시간 20분이 1시간 50분이 됩니다.**

쉽게 말하면 GPU 마다 같은 모델을 한 벌씩 두고 학습 데이터만 넷으로 나눠 줍니다. 각자 낸 기울기를 평균 내 넷이 같은 모델을 유지합니다.

먼저 나누는 것과 복제하는 것을 구분해야 합니다. 나누는 것은 학습 데이터입니다. 7억 4,550만 행을 넷으로 나눠 한 장이 1억 8,640만 행쯤을 맡습니다. 복제하는 것은 모델입니다. 네 장이 똑같은 가중치를 하나씩 들고 시작합니다. 이 방식을 데이터 병렬(data parallelism)이라고 부릅니다.

한 걸음의 순서는 이렇습니다. 네 장이 각자 배치 4,096 을 받아 예측을 내고 정답과 비교해 기울기를 냅니다. 기울기는 가중치를 어느 쪽으로 얼마나 고쳐야 하는지를 적은 숫자 묶음입니다. 여기까지는 넷이 따로 합니다. 그 다음이 중요합니다. 넷의 기울기를 모아 평균을 내고, 그 평균으로 넷이 같은 갱신을 합니다. 이 합치는 일을 기울기 합치기(allreduce)라고 부릅니다.

평균을 내는 이유는 계산이 그렇게 맞기 때문입니다. 기울기는 원래 배치 안 행들의 평균입니다. 같은 크기의 배치 넷을 평균 내면 16,384행을 한 번에 본 것과 같습니다. 그래서 네 장으로 도는 학습은 배치 16,384 짜리 학습과 같은 갱신을 합니다. 합치기를 빼면 네 장이 서로 다른 모델 넷이 되어 버리고, 나중에 어느 것을 배포할지 정할 수 없습니다.

합칠 때 오가는 값의 크기는 신경망 가중치의 크기입니다. 이 모델의 신경망은 38MB 입니다. 스텝마다 네 장이 38MB 규모의 숫자를 주고받습니다. 임베딩 표 27.7GB 는 여기에 들어가지 않습니다. 임베딩이 왜 빠지는지는 4절에서 봅니다.

| 무엇 | 넷이 어떻게 갖나 | 크기 |
|---|---|---|
| 학습 행 | 나눈다. 한 장이 1억 8,640만 행 | 7억 4,550만 행 |
| 신경망 가중치 | 복제한다. 넷이 같은 값 | 38MB |
| 스텝마다 합치는 기울기 | 넷의 평균으로 되돌린다 | 38MB 규모 |
| 임베딩 표 | 나누지도 복제하지도 않는다 | 27.7GB |

네 장으로 시작하는 것이 이 절의 결정입니다. 그런데 방금 붙은 15분의 정체를 알아야 장수를 더 늘릴지 판단할 수 있습니다. 기울기를 언제 합치느냐가 그 15분을 정합니다.

## 3. 기울기를 언제 합치나 — 기다리느냐 낡느냐

**동기는 스텝마다 넷이 기울기를 합칩니다. 가장 늦은 장 하나가 셋을 세워 혼자 돌 때보다 13% 깁니다. 비동기는 기다리지 않는 대신 기울기가 평균 3스텝 낡습니다.**

쉽게 말하면 스텝마다 넷이 서로를 기다렸다 합칠지, 기다리지 않고 각자 갈지를 고르는 일입니다. 기다리면 느려지고 안 기다리면 낡은 값으로 배웁니다.

동기(synchronous)는 스텝마다 벽을 하나 세우는 방식입니다. 네 장이 모두 기울기를 낼 때까지 아무도 다음 스텝으로 못 갑니다. 문제는 네 장의 스텝 시간이 매번 조금씩 다르다는 데 있습니다. 배치마다 건드리는 임베딩 줄의 수가 다르고, 파라미터 서버에서 값을 받아 오는 시간이 흔들리고, 다른 일이 같은 장비에 얹히기도 합니다. 그래서 한 스텝의 실제 길이는 넷 중 가장 늦은 장이 정합니다.

이것이 얼마나 되는지는 세어 보면 나옵니다. 스텝 하나의 중앙값을 0.125초로 둡니다. 배치 4,096행을 초당 32,700행으로 나눈 값입니다. 여기에 로그정규로 흔들림을 주고 2,000스텝을 돌립니다.

```python
# 동기와 비동기를 2,000 스텝만 돌려 견준다. 스텝 하나의 중앙값은
# 4,096행 ÷ 초당 32,700행 = 0.125초이고, 흔들림은 로그정규로 준다. 전부 가상 값이다.
import random, math

random.seed(7)
GPUS, STEPS = 4, 2_000
MED, SIGMA = 0.125, 0.12
mu = math.log(MED)

# 장마다 스텝마다 걸린 시간. 배치가 건드리는 임베딩 줄 수와 서버 상태가 달라 흔들린다.
times = [[random.lognormvariate(mu, SIGMA) for _ in range(STEPS)] for _ in range(GPUS)]

alone = sum(times[0])
# 동기: 스텝마다 넷이 기울기를 합치므로 그 스텝의 가장 늦은 장에 맞춰진다.
sync = sum(max(times[g][s] for g in range(GPUS)) for s in range(STEPS))
print(f"한 장이 혼자 {STEPS:,}스텝을 돌면 {alone:.1f}초")
print(f"동기 네 장은 스텝마다 늦은 장을 기다려 {sync:.1f}초, 혼자보다 {sync / alone - 1:.1%} 깁니다")
waited = sync - alone
print(f"기다린 {waited:.1f}초는 네 장 모두에게 붙어 {GPUS * waited:.0f}초의 GPU 시간이 됩니다")

# 비동기: 각자 제 속도로 간다. 내가 기울기를 보내는 사이 남이 몇 번 갱신했나가 낡음이다.
ends = []
for g in range(GPUS):
    t = 0.0
    for s in range(STEPS):
        t += times[g][s]
        ends.append((t, g))
ends.sort()                      # 네 장의 갱신을 시각순으로 한 줄에 세운다

last, stale = {}, []
for i, (t, g) in enumerate(ends):
    if g in last:
        stale.append(i - last[g] - 1)    # 내 직전 갱신과 이번 갱신 사이에 끼어든 남의 갱신 수
    last[g] = i
print(f"비동기 네 장은 기다림이 0초입니다. 대신 기울기가 평균 {sum(stale) / len(stale):.1f}스텝 낡습니다"
      f" (최대 {max(stale)}스텝)")

# 출력:
# 한 장이 혼자 2,000스텝을 돌면 250.6초
# 동기 네 장은 스텝마다 늦은 장을 기다려 283.1초, 혼자보다 13.0% 깁니다
# 기다린 32.5초는 네 장 모두에게 붙어 130초의 GPU 시간이 됩니다
# 비동기 네 장은 기다림이 0초입니다. 대신 기울기가 평균 3.0스텝 낡습니다 (최대 6스텝)
```

혼자 돌면 250.6초인 구간이 동기로는 283.1초입니다. 13% 가 기다림입니다. 그리고 그 32.5초는 한 장이 아니라 네 장 모두에게 붙습니다. 늦은 장을 기다리는 동안 나머지 셋도 아무것도 안 하기 때문입니다. GPU 시간으로 세면 130초를 버린 셈입니다. 값을 치르고 빌린 장비이니 이 낭비는 그대로 돈입니다.

비동기(asynchronous)는 벽을 치웁니다. 각 장이 기울기를 내는 대로 파라미터 서버에 보내고 최신 가중치를 받아 다음 스텝으로 갑니다. 기다림이 0초가 되는 대신 다른 것을 잃습니다. 내가 기울기를 계산하는 동안 남들이 이미 가중치를 고쳐 놓습니다. 위 계산에서 그 사이에 끼어든 갱신이 평균 3.0번, 많을 때는 6번이었습니다. 3스텝 전의 값을 보고 낸 방향으로 지금 값을 고치는 것입니다. 이것을 낡은 기울기라고 부릅니다.

낡은 기울기가 늘 나쁜 것은 아닙니다. 값이 조금씩만 움직이는 구간에서는 3스텝 차이가 결과를 거의 바꾸지 않습니다. 반대로 학습 초반처럼 값이 크게 흔들릴 때는 엉뚱한 방향으로 밀어 손해가 큽니다. 그래서 실무에서는 둘을 섞습니다. 신경망 가중치는 동기로 합쳐 정확하게 가고, 임베딩은 비동기로 풀어 기다림을 없앱니다.

임베딩을 비동기로 풀어도 되는 이유가 따로 있습니다. 한 배치가 건드리는 임베딩 줄이 극히 적어서 두 장이 같은 줄을 동시에 고치는 일이 거의 없기 때문입니다. 신경망은 반대입니다. 모든 스텝이 모든 가중치를 건드리니 낡으면 바로 표가 납니다.

신경망은 동기로 두고 임베딩만 비동기로 푸는 것이 이 절의 결정입니다. 그런데 임베딩을 이렇게 따로 다루려면 임베딩이 GPU 밖에 있어야 합니다. 왜 밖에 두는지가 다음 절입니다.

## 4. 임베딩만 파라미터 서버로 따로 뺍니다

**신경망 가중치는 38MB 라 넷이 복제해도 됩니다. 임베딩 표는 27.7GB 이고 학습 때 83.2GB 가 되어 GPU 한 장의 80GB 에 안 들어갑니다. 그래서 임베딩만 파라미터 서버 두 대에 쪼갭니다.**

쉽게 말하면 신경망은 작아서 GPU 안에 들어가는데 임베딩 표는 GPU 한 장보다 큽니다. 그래서 표만 따로 서버 두 대에 나눠 두고 GPU 는 그때 쓰는 줄만 받아 옵니다.

광고 모델이 다른 모델과 달라지는 자리가 여기입니다. 이미지나 문장을 다루는 모델은 가중치가 크고 표가 작습니다. 광고 모델은 반대입니다. 신경망은 몇 층에 불과해 38MB 인데, 유저와 광고에 번호를 붙여 숫자 묶음을 하나씩 달아 둔 표가 수십 GB 입니다. 그 표를 임베딩 표라고 부릅니다.

크기는 곱셈으로 나옵니다. 가정은 값 하나가 4바이트이고 Adam 이 값마다 상태 둘을 더 든다는 것입니다. 계산식은 유저 2억 줄 × 32차원 × 4바이트 = 23.8GB 이고, 광고와 지면과 카테고리 표를 더하면 27.7GB 입니다. 학습 때는 여기에 3을 곱해 83.2GB 가 됩니다. Adam 은 값마다 1차와 2차 모멘트를 따로 저장해서 값 하나가 숫자 세 개가 되기 때문입니다.

| 조각 | 서빙 때 크기 | 학습 때 크기 | 어디에 두나 |
|---|---|---|---|
| 신경망 가중치 | 38MB | 114MB | GPU 넷이 복제 |
| 임베딩 표 넷 | 27.7GB | 83.2GB | 파라미터 서버 2대 |
| 그중 유저 표 | 23.8GB | 71.4GB | 같은 서버에 함께 |

GPU 한 장의 메모리는 80GB 입니다. 83.2GB 는 그 자체로 이미 넘고, 학습 중간에 쌓이는 값까지 올려야 하니 실제로는 더 모자랍니다. 데이터만 넷으로 나누는 방식으로는 이 문제가 풀리지 않습니다. 데이터를 아무리 잘게 나눠도 네 장이 모두 표 전체를 들고 있어야 하기 때문입니다. 표는 나누는 대상이 아니라 GPU 밖으로 내보내는 대상입니다.

그래서 임베딩만 들고 있는 서버를 따로 둡니다. 이것을 파라미터 서버라고 부릅니다. 한 대가 임베딩에 내줄 수 있는 몫을 64GB 로 보면 83.2GB 에 두 대가 필요하고, 한 대가 41.6GB 씩 맡습니다. 쪼개는 기준은 줄입니다. 조회 단위가 줄 하나이기 때문입니다. 번호순으로 뭉텅뭉텅 나누면 최근 광고가 한 대에 몰리므로, 번호를 해시한 나머지로 흩뿌립니다. 이 규칙은 [임베딩 테이블 운영](post.html?id=embedding-table-ops) 편과 같습니다.

표가 GPU 밖에 있으면 스텝마다 오가느라 느려지지 않을까 걱정됩니다. 여기서 광고 모델의 성질이 도움이 됩니다. 한 배치가 건드리는 줄이 표의 아주 작은 부분입니다. 배치 1,024 면 유저 줄은 많아야 1,024줄이고 2억 줄 가운데 0.0005% 입니다. 배치를 4,096 으로 키워도 0.002% 입니다. 나머지 줄은 기울기가 0 이라 보낼 것도 받을 것도 없습니다.

그래서 오가는 양이 생각보다 작습니다. 유저 줄 4,096개를 받아 오면 4,096 × 32차원 × 4바이트로 512KB 입니다. 신경망을 합칠 때 오가는 38MB 보다 한참 작습니다. 표가 27.7GB 라는 사실과 스텝마다 오가는 양이 512KB 라는 사실은 어긋나지 않습니다. 앞의 것은 어딘가에 놓여 있어야 할 크기이고 뒤의 것은 한 걸음에 실제로 건드리는 크기입니다.

임베딩은 파라미터 서버 둘에 두고 신경망만 GPU 넷이 복제하는 것이 이 절의 결정입니다. 여기까지 정하면 장수는 자유롭게 고를 수 있습니다. 여덟 장으로 늘리면 얼마나 빨라지는지가 다음 절입니다.

## 5. 장을 늘려도 시간은 장수만큼 줄지 않습니다

**계산은 장수만큼 나뉘지만 합치기와 기다림은 장수에 비례해 붙습니다. 네 장이면 3.5배로 효율 86%, 여덟 장이면 5.8배로 효율 73%입니다.**

쉽게 말하면 GPU 를 두 배로 늘려도 시간은 절반이 되지 않습니다. 장이 늘 때마다 합치기와 기다림이 붙어 효율이 내려갑니다.

앞 세 절에서 나온 것을 한 줄의 식으로 적을 수 있습니다. 학습 시간은 계산 시간을 장수로 나눈 값에, 장이 늘어난 만큼 붙는 몫을 곱한 것입니다. 붙는 몫은 장이 하나 늘 때마다 5.3% 로 둡니다. 이 5.3% 안에는 세 가지가 들어 있습니다. 기울기를 합치며 오가는 통신, 늦은 장을 기다리는 시간, 파라미터 서버를 오가는 왕복입니다. 셋 다 장이 늘수록 커지고 계산처럼 나뉘지 않습니다.

```python
# GPU 를 늘리면 학습 시간이 얼마나 주나. 계산은 장수만큼 나뉘지만
# 기울기를 합치고 늦은 장을 기다리는 시간은 장수에 비례해 붙는다. 전부 가상 값이다.
ROWS = 745_500_000        # 30일 학습 행 (하루 2,485만 행 × 30일)
ROWS_PER_SEC = 32_700     # GPU 한 장이 초당 넘기는 행
OVERHEAD = 0.053          # 장이 하나 늘 때마다 스텝마다 더 붙는 몫

def train_time(gpus):
    compute = ROWS / ROWS_PER_SEC / gpus          # 계산은 장수만큼 나뉜다
    return compute * (1 + OVERHEAD * (gpus - 1))  # 합치기와 기다림은 장수에 비례해 붙는다

def hm(sec):
    m = round(sec / 60)
    return f"{m // 60}시간 {m % 60:02d}분" if m >= 60 else f"{m}분"

base = train_time(1)
print("GPU   학습 시간      배속   효율   줄어드는 시간")
prev = base
for g in (1, 2, 4, 8, 16, 32):
    t = train_time(g)
    saved = "%d분" % int((prev - t) // 60) if g > 1 else "-"
    print("%3d장 %10s %6.1f배 %5.0f%% %10s" % (g, hm(t), base / t, 100 * base / t / g, saved))
    prev = t

print()
for g in (4, 8):                                  # 붙은 시간이 어디서 왔는지 나눠 본다
    comp = ROWS / ROWS_PER_SEC / g
    print("%d장: 계산 %s + 합치기와 기다림 %s = %s"
          % (g, hm(comp), hm(train_time(g) - comp), hm(train_time(g))))

# 출력:
# GPU   학습 시간      배속   효율   줄어드는 시간
#   1장    6시간 20분    1.0배   100%          -
#   2장    3시간 20분    1.9배    95%       179분
#   4장    1시간 50분    3.5배    86%        89분
#   8장    1시간 05분    5.8배    73%        44분
#  16장        43분    8.9배    56%        22분
#  32장        31분   12.1배    38%        11분
#
# 4장: 계산 1시간 35분 + 합치기와 기다림 15분 = 1시간 50분
# 8장: 계산 47분 + 합치기와 기다림 18분 = 1시간 05분
```

마지막 두 줄이 이 절의 내용을 다 담고 있습니다. 네 장에서 여덟 장으로 늘리면 계산은 1시간 35분에서 47분으로 절반이 됩니다. 그런데 합치기와 기다림은 15분에서 18분으로 오히려 늘었습니다. 나뉘는 부분과 늘어나는 부분이 같이 있으니 합계는 절반이 되지 않습니다. 장수를 키울수록 뒤의 몫이 앞을 잡아먹습니다.

줄어드는 시간 칸을 보면 어디서 멈출지가 보입니다. 두 장을 더해 179분을 벌고, 그 다음 두 배에 89분, 그 다음에 44분, 그 다음에 22분입니다. 장수를 두 배로 할 때마다 버는 시간이 절반씩 줄어듭니다. 열여섯 장은 여덟 장보다 22분 빠르지만 장비를 두 배 씁니다. GPU 시간으로 보면 여덟 장이 521분, 열여섯 장이 682분입니다. 22분을 벌자고 GPU 시간 161분을 더 쓰는 셈입니다.

그래서 장수는 성능이 아니라 마감으로 고릅니다. 이 재학습의 마감은 06:09 입니다. 그 시각에 배포 요청이 나가야 새 모델이 그날 카나리에 오릅니다. 04:00 에 시작해 네 장으로 돌리면 05:50 에 끝나 마감 안에 들어옵니다. 여덟 장이면 05:05 로 45분 이르지만 GPU 값이 두 배입니다. 마감을 이미 지켰으니 그 45분에는 값을 치를 이유가 없습니다.

네 장으로 돌린다가 이 절의 결정입니다. 다만 지금까지의 이야기는 유저 임베딩이 큰 무대를 전제로 했습니다. 그 전제가 달라지면 나누는 방법도 달라집니다.

## 6. 담장 안과 열린 RTB 는 쪼개는 자리가 다릅니다

**담장 안에서는 유저 표가 전체의 86%라 쪼개는 쪽이 유저 표입니다. 열린 RTB 에서는 유저 줄이 한 번 쓰고 버려져 임베딩이 작고, 파라미터 서버 없이 데이터 병렬만으로 끝납니다.**

쉽게 말하면 어느 표가 큰지가 무대마다 다릅니다. 그래서 무엇을 GPU 밖으로 내보낼지도 달라집니다.

### 담장 안에서는 유저 표가 가장 큽니다 [무대: 닫힌 생태계]

한 회사가 앱과 광고 서버를 다 가진 담장 안에서는 유저를 로그인 계정으로 알아봅니다. 그 번호는 몇 년을 삽니다. 그래서 유저 줄에 숫자 32개를 달아 두는 것이 값을 합니다. 한 달에 수백 번 등장하니 그 숫자가 실제로 그 사람의 취향을 담습니다.

대신 표가 커집니다. 유저 2억 줄이 23.8GB 이고 전체 27.7GB 의 86%를 차지합니다. 이 글의 파라미터 서버 두 대는 사실상 유저 표를 담으려고 세운 것입니다. 광고와 지면과 카테고리 표를 다 합쳐도 3.9GB 라 그것만이면 GPU 한 장에 들어갑니다. 전체 재학습이 여섯 시간대로 커지는 것도 유저 줄이 많아 갱신할 것이 많기 때문입니다.

### 열린 RTB 에서는 임베딩이 작습니다 [무대: 열린 RTB]

남의 매체에 입찰하는 DSP 는 유저를 쿠키로 봅니다. 브라우저마다 다르고 며칠이면 바뀝니다. 한두 번 등장하는 번호에 숫자 32개를 배정하면 학습에서 거의 안 움직이고, 서빙에서는 그 줄을 찾을 열쇠가 이미 없습니다. 그래서 표의 예산이 오래 사는 쪽으로 갑니다. 도메인과 슬롯 위치와 광고 소재입니다.

그러면 임베딩이 몇 GB 로 줄어 모델 전체가 GPU 한 장에 들어갑니다. 파라미터 서버가 필요 없고 데이터 병렬만으로 끝납니다. 기울기 합치기도 신경망 하나만 보면 되니 동기로 두면 됩니다. 이 무대의 어려움은 나누는 자리가 아니라 학습 데이터 자체에 있습니다. 낙찰된 요청만 남아 진 요청의 결과를 모른다는 문제인데, 그것은 [Bid Shading 과 낙찰가 미관측](post.html?id=bid-shading-censored) 편의 이야기입니다.

| 무엇 | 담장 안 | 열린 RTB |
|---|---|---|
| 가장 큰 표 | 유저 2억 줄, 23.8GB | 광고 소재와 지면 |
| 학습 때 임베딩 | 83.2GB, GPU 한 장에 안 들어감 | 몇 GB, 한 장에 들어감 |
| 나누는 방법 | 데이터 병렬 + 파라미터 서버 2대 | 데이터 병렬만 |
| 기울기 합치기 | 신경망은 동기, 임베딩은 비동기 | 신경망만 동기 |

같은 분산 학습이라는 말을 써도 두 무대가 세우는 장비가 다릅니다. 담장 안의 설계를 DSP 에 그대로 옮기면 쓰지 않는 파라미터 서버를 두 대 띄우게 됩니다. 반대로 DSP 의 설계를 담장 안에 가져오면 학습이 메모리 부족으로 시작조차 못 합니다.

여덟 주가 여기서 끝납니다. 지훈 씨는 새벽 알람 한 줄에서 시작해 파이프라인, 버전, 이미지, 서버, 배포, 스트림, 배치 추론을 지나 학습을 나누는 자리까지 왔습니다. 여덟 편을 관통하는 질문은 하나였습니다. 만든 모델을 매일 같은 품질로 다시 내놓으려면 무엇을 적어 두고 무엇을 자동으로 돌려야 하는가입니다.

## 한눈 정리

| 자리 | 무엇을 하나 | 숫자 |
|---|---|---|
| 30일 전체 재학습 | 피처가 바뀌면 처음부터 다시 배운다 | 7억 4,550만 행, 한 장 6시간 20분 |
| 데이터 병렬 | 데이터를 넷으로 나누고 모델은 복제한다 | 한 장 1억 8,640만 행, 1시간 50분 |
| 기울기 합치기 | 스텝마다 넷의 기울기를 평균 낸다 | 신경망 38MB 규모를 주고받는다 |
| 동기 | 스텝마다 늦은 장을 기다린다 | 혼자보다 13% 길다 |
| 비동기 | 기다리지 않는다 | 기울기가 평균 3스텝 낡는다 |
| 임베딩 표 | GPU 에 안 들어가 밖으로 뺀다 | 27.7GB, Adam 이면 83.2GB |
| 파라미터 서버 | 임베딩만 들고 건드린 줄만 준다 | 2대, 41.6GB 씩 |
| 한 스텝의 임베딩 통신 | 건드린 줄만 오간다 | 4,096줄이면 512KB |
| 장수와 효율 | 계산은 나뉘고 합치기는 안 나뉜다 | 4장 86%, 8장 73%, 16장 56% |

## 헷갈리기 쉬운 점

- **데이터 병렬은 모델을 나누는 것이 아닙니다.** 모델은 네 장이 똑같이 갖고 데이터만 나눕니다. 나누는 것은 임베딩 표뿐이고, 그것도 계산을 나누려는 것이 아니라 메모리에 안 들어가서입니다.
- **효율 86% 는 GPU 가 14% 놀았다는 뜻이 아닙니다.** 장수만큼 빨라졌으면 100% 인데 3.5배에 그쳤다는 뜻입니다. 그 차이가 합치기와 기다림입니다.
- **파라미터 서버는 GPU 가 아닙니다.** 계산은 하지 않고 표만 들고 있는 서버입니다. GPU 가 필요한 줄을 물으면 그 줄만 내주고, 갱신값을 받아 표에 씁니다.
- **배치를 키우면 빨라지지만 끝없이 키울 수는 없습니다.** 같은 행 수에 갱신 횟수가 줄어 모델이 덜 배웁니다. 1,024 에서 4,096 으로 키운 것도 여기까지가 안전하다고 본 것입니다.
- **동기와 비동기는 정확도와 시간을 맞바꾸는 선택입니다.** 어느 한쪽이 옳은 것이 아니라, 신경망처럼 모든 스텝이 건드리는 값은 동기로, 임베딩처럼 드물게 겹치는 값은 비동기로 둡니다.
