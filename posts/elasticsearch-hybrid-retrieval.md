# Elasticsearch 하이브리드 검색: 글자와 뜻으로 찾고 순위로 합치기

지훈 씨가 모델 팀에 온 지 12주째입니다. 이번 일은 검색 광고의 후보입니다. 사용자가 검색어를 넣으면 광고 상품 가운데 후보를 먼저 뽑고, 그 후보에만 클릭 확률 모델을 돌립니다. 그런데 「헤드셋」을 검색하면 헤드폰 상품이 후보에 하나도 없었습니다.

상품 이름에 「헤드셋」이라는 글자가 없어서였습니다. 선배는 글자로 찾는 목록 옆에 뜻으로 찾는 목록을 하나 더 두고 둘을 합쳐 보라고 했습니다. 지훈 씨는 노트북에 검색 서버 두 대를 띄우고 상품 3만 건을 넣어 질의 셋의 응답을 기록했습니다.

**글자로 찾은 목록과 뜻으로 찾은 목록은 점수의 단위가 다른데, 어떻게 하나로 합칠까요?**

글자로 찾는 방법을 BM25, 뜻으로 찾는 방법을 kNN 벡터 검색이라고 부릅니다. 두 목록을 순위로 합치는 방법이 RRF 이고, 셋을 같이 쓰는 것을 하이브리드 검색이라고 합니다. 후보에 오르지 못한 상품은 모델이 아무리 좋아도 광고가 나가지 않고, 그 매출은 랭킹 모델이 되찾지 못합니다.

> **한 줄 요약:** BM25 는 질의와 글자가 같은 상품을, kNN 은 뜻이 가까운 상품을 100개씩 찾습니다. 「헤드셋」은 BM25 가 0건이었고 kNN 이 헤드폰 100개를 찾았습니다. RRF 는 점수 대신 순위를 보고 1 ÷ (60 + 순위) 를 더해 두 목록을 합칩니다. 날마다 바뀌는 피처는 새 인덱스를 만들어 별칭을 옮기고, 그 교체 요청 자체는 22ms 에 끝났습니다.

> **골라 읽는 법** — 절이 여덟인 글입니다. 절마다 표나 코드나 기록 재생 그림이 하나 있어서 그것만 보고 넘어가도 됩니다.
>
> - 질의 하나가 지나는 다섯 단계와 걸린 시간 → 1절
> - BM25 와 분석기 → 2절
> - kNN 과 임베딩 → 3절
> - RRF 계산과 파이썬 → 4절
> - 거르기와 후보 수 → 5절
> - 샤드와 replica → 6절
> - 날마다 인덱스를 바꾸는 법 → 7절
> - 담장 안과 열린 RTB → 8절

이 글의 숫자는 지어낸 값이 아닙니다. 노트북 한 대에 Elasticsearch 9.5 노드 둘과 검색 API 를 띄우고 직접 재 본 값입니다. 상품 3만 건의 이름은 브랜드, 속성, 품목을 이어 만든 가짜입니다. 질의 벡터는 공개 모델 multilingual-e5-small 로 만들었습니다. 운영 서버라면 ms 의 크기는 다르지만 어느 자리가 큰지는 같습니다. 글 속의 그림 셋은 그때 기록한 응답을 다시 그립니다.

## 1. 질의 하나는 다섯 단계를 지나 후보가 됩니다

**「캠핑 의자」 한 번은 BM25 100개와 kNN 100개를 거쳐 겹친 것을 합친 121개가 됩니다. 꺼진 상품을 뺀 108개가 랭킹 모델로 갑니다. 다섯 단계를 지나는 데 API 안에서 27ms 가 걸렸습니다.**

검색 API 는 질의를 받으면 Elasticsearch 에 두 번 묻습니다. 한 번은 글자로, 한 번은 벡터로 묻습니다. 그 사이에 질의를 벡터로 바꾸는 계산이 있고, 두 답을 받은 뒤에는 합치고 거르는 계산이 있습니다. 이 실습 환경은 두 질의를 차례로 보내서 두 왕복의 시간이 더해집니다. 동시에 보내면 1번이 2번, 3번과 겹쳐 kNN 쪽의 시간만 남습니다.

| 단계 | 하는 일 | 건수 | 걸린 시간 |
|---|---|---|---|
| 1. BM25 | 질의의 토큰을 역색인에서 찾아 점수 순 100개 | 맞은 문서 1,885건 → 100건 | 6.9ms (Elasticsearch 안 4.5ms) |
| 2. 질의 벡터 | 질의를 384차원 벡터로 바꾼다 | 1건 | 5.7ms |
| 3. kNN | 벡터가 가까운 상품 100개 | 100건 | 13.6ms (Elasticsearch 안 10.0ms) |
| 4. RRF | 두 목록을 순위로 합친다 | 200건 → 121건 | 0.26ms |
| 5. 거르기 | 꺼진 상품을 뺀다 | 121건 → 108건 | 0.02ms |

시간은 같은 질의를 10번 보내 가운데 값을 냈습니다. 괄호 안은 Elasticsearch 가 응답에 적어 준 took 값으로, 검색 서버 안에서 쓴 시간입니다. API 에서 잰 시간과의 차이는 HTTP 왕복과 응답 JSON 을 푸는 시간입니다. 가장 긴 단계는 kNN 이고, RRF 와 거르기는 1ms 도 안 됩니다.

## 2. BM25 는 질의의 토큰이 상품 이름에 있어야 찾습니다

**Elasticsearch 는 상품 이름을 토큰으로 잘라 역색인에 둡니다. 「헤드셋」은 어느 상품 이름의 토큰에도 없어서 BM25 가 0건입니다.**

문장을 토큰으로 자르는 프로그램을 분석기라고 부릅니다. 한국어 상품 이름은 띄어쓰기가 일정하지 않아서, 형태소 분석기 nori 로 낱말을 쪼갭니다. 색인할 때 「캠핑의자」는 「캠핑」과 「의자」로 나뉩니다. 그래서 「캠핑 의자」로 띄어 검색해도, 「캠핑의자」로 붙여 검색해도 같은 상품을 찾습니다. 아래는 이 실습 환경의 분석기에 직접 넣어 본 결과입니다.

```text
색인할 때 (분석기 ko)
  "베이직 접이식 그레이 캠핑의자"  →  베이직 | 접이식 | 그레이 | 캠핑 | 의자

검색할 때 (분석기 ko_search, 동의어 사전을 씀)
  "캠핑 의자"  →  캠핑 | 의자, 체어   (의자와 체어는 같은 자리)
  "스니커즈"   →  스니커즈, 운동화     (같은 자리)
  "헤드셋"     →  헤드셋
```

역색인은 토큰마다 그 토큰이 든 문서의 목록을 둔 표입니다. 「의자」 토큰 아래에는 의자가 든 상품 번호가 줄지어 있습니다. 질의 토큰들의 목록을 꺼내 합치면 맞은 문서가 나옵니다. 「캠핑 의자」는 캠핑이나 의자가 든 상품이라 1,885건이 맞았습니다. 기본 설정은 토큰 하나만 맞아도 맞은 것으로 칩니다.

맞은 문서에 매기는 점수가 BM25 이고, 질의 토큰이 이름에 많이 들수록, 드문 토큰일수록, 이름이 짧을수록 높습니다. 「의자」보다 「캠핑」이 드물면 캠핑이 든 상품이 앞섭니다. 이 질의의 1위 「온 슬림 캠핑의자」는 9.92점이었습니다.

「스니커즈」를 넣으면 분석기가 검색할 때 「운동화」를 같은 자리에 더해서, 운동화 상품 37건이 맞았습니다. 동의어를 색인할 때 풀지 않는 이유는 사전을 고칠 때마다 3만 건을 다시 색인하지 않으려는 것입니다. 「헤드셋」은 사전에 없는 말이라 그대로 남았고, 상품 이름에는 헤드셋이라는 토큰이 없어 0건입니다.

사전에 하나씩 넣으면 BM25 도 헤드셋을 찾습니다. 그런데 사람들이 쓰는 말을 다 적을 수는 없습니다. 사전이 못 따라가는 말을 메우는 것이 다음 절의 kNN 입니다.

## 3. kNN 은 질의와 상품을 벡터로 바꿔 가까운 것을 찾습니다

**상품 이름과 질의를 같은 모델로 384차원 벡터로 바꾸고, 코사인 유사도가 높은 상품을 고릅니다. 「헤드셋」은 글자가 없어도 헤드폰이 1위로 나왔습니다.**

임베딩 모델은 문장을 받아 숫자 384개로 된 벡터를 내놓습니다. 뜻이 비슷한 문장은 벡터의 방향도 비슷하게 나오도록 학습된 모델입니다. 상품 3만 건은 색인할 때 이름과 카테고리를 이어 한 번씩 벡터로 바꿔 둡니다. 질의는 검색할 때마다 벡터로 바꾸며, 1절의 2번 단계가 그 계산입니다.

두 벡터의 방향이 얼마나 같은지를 코사인 유사도라고 부르고, 같으면 1, 수직이면 0 입니다. Elasticsearch 는 이것을 (1 + 코사인) ÷ 2 로 바꿔 점수로 줍니다. 「헤드셋」의 1위 「아틀라이프(ATL) 와이드 헤드폰 AV505」는 0.911점이었는데, 코사인으로는 0.822 입니다.

3만 건과 하나씩 다 비교하면 느려서 HNSW 라는 그래프를 씁니다. 벡터마다 가까운 벡터 몇 개를 이어 둔 그래프이고, 질의는 그 이음선을 따라 가까운 쪽으로 옮겨 가며 찾습니다. 다 비교하지 않으므로 진짜 가장 가까운 것을 놓칠 수 있어 근사 검색이라고 부릅니다. num_candidates 100 은 샤드마다 후보를 100개까지 살펴보라는 설정입니다.

| 질의 | BM25 가 맞춘 수 | BM25 1위 | kNN 1위 | 위 100개끼리 겹친 수 |
|---|---|---|---|---|
| 캠핑 의자 | 1,885 | 온 슬림 캠핑의자 | 하이라이프 와이드 브라운 캠핑의자 ML172 | 79 |
| 헤드셋 | 0 | 없음 | 아틀라이프(ATL) 와이드 헤드폰 AV505 | 0 |
| 스니커즈 | 37 | 별랩 와이드 운동화 | 윤라이프 방수 카키 선글라스 | 0 |

「스니커즈」의 kNN 1위는 선글라스였고, 위 100개에 운동화가 하나도 없었습니다. 이 실습에서 쓴 작은 모델은 스니커즈와 운동화를 가깝게 보지 못했습니다. kNN 은 늘 100개를 돌려주므로 0건은 없지만, 그 100개가 틀릴 수 있습니다.

그래서 둘을 같이 씁니다. BM25 는 글자가 맞으면 틀리지 않고 사전에 있는 말은 사전이 이어 주며, kNN 은 사전에 없는 말을 메웁니다. 질의와 상품을 각각 벡터로 바꾸는 이 구조는 [Two-Tower](post.html?id=two-tower-training) 편의 두 타워와 같은 갈래입니다. 남은 문제는 단위가 다른 두 점수를 어떻게 함께 정렬하느냐입니다.

## 4. RRF 는 점수 대신 순위를 더합니다

**RRF 는 상품마다 목록별로 1 ÷ (60 + 순위) 를 더한 값으로 순위를 매깁니다. 두 목록에 다 있는 상품이 한 목록의 1위보다 앞설 수 있습니다.**

두 점수를 그대로 더할 수 없는 것은 크기가 달라서입니다. 「캠핑 의자」의 BM25 점수는 1위가 9.92 이고, kNN 점수는 1위부터 10위까지가 0.94 언저리입니다. 그대로 더하면 BM25 가 순서를 다 정하고 kNN 은 소수점 아래에서만 움직입니다. 점수를 0 에서 1 로 맞추는 방법도 있지만, 질의마다 점수의 범위가 달라 맞추는 기준이 흔들립니다.

RRF 는 원어로 Reciprocal Rank Fusion 이고, 점수를 버리고 순위만 씁니다. 목록마다 「1 ÷ (k + 순위)」를 구해 더하고, 목록에 없으면 0 을 더합니다. k 는 60 을 많이 쓰는데, 2009년에 이 방법을 낸 논문이 쓴 값입니다. k 가 크면 1위와 10위의 차이가 줄어듭니다. 아래 코드는 「캠핑 의자」에서 기록한 순위 그대로 네 상품의 RRF 점수를 셉니다.

```python
# 하는 일: 「캠핑 의자」에서 기록한 BM25 순위와 kNN 순위로 네 상품의 RRF 점수를 세어 순위를 매긴다.
# 1단계: 두 목록에서의 순위를 둔다
# 기록한 위 100개 목록의 순위다. 앞이 BM25, 뒤가 kNN 이다.
ranks = {
    '심플 슬림 캠핑의자': (3, 10),
    '베이직 접이식 그레이 캠핑의자': (9, 4),
    '온 슬림 캠핑의자': (1, 61),
    '온팩토리 와이드 그레이 캠핑의자 XR289': (60, 2),
}

# 2단계: 목록마다 1 / (60 + 순위) 를 더한다
K = 60
def rrf(pair):
    return sum(1 / (K + r) for r in pair)

# 3단계: 점수 순으로 찍는다
for name, (b, k) in sorted(ranks.items(), key=lambda kv: -rrf(kv[1])):
    print(f'{rrf((b, k)):.4f}  BM25 {b:>2}위  kNN {k:>2}위  {name}')

# 출력:
# 3단계 뜻: BM25 1위가 3위로 밀리고, 두 목록에서 모두 10위 안인 상품이 앞선다.
# 0.0302  BM25  3위  kNN 10위  심플 슬림 캠핑의자
# 0.0301  BM25  9위  kNN  4위  베이직 접이식 그레이 캠핑의자
# 0.0247  BM25  1위  kNN 61위  온 슬림 캠핑의자
# 0.0245  BM25 60위  kNN  2위  온팩토리 와이드 그레이 캠핑의자 XR289
```

이 네 점수는 그림 1의 셋째 목록에 찍힌 값과 같습니다. RRF 가 상을 주는 것은 「두 목록이 다 좋다고 한 상품」입니다. 한쪽에서만 1위인 상품은 1 ÷ 61, 곧 0.0164 를 받는데, 두 목록에서 10위 안이면 그보다 두 배 가까이 받습니다.

한계도 같은 성질에서 나옵니다. 「스니커즈」는 두 목록이 하나도 안 겹쳐서 kNN 1위 선글라스와 BM25 1위 운동화가 똑같이 0.0164 를 받았습니다. 순위만 보므로 kNN 이 선글라스를 얼마나 자신 없이 골랐는지는 모릅니다. 점수가 같으면 이 실습 환경은 문서 번호 순으로 정렬해서 선글라스가 1위가 됐습니다.

Elasticsearch 에도 RRF 가 들어 있지만 유료 라이선스 기능입니다. 무료 라이선스(basic)로 띄운 이 실습 환경에서는 그 질의에 「license is non-compliant」라는 403 이 돌아왔습니다. 그래서 두 질의를 따로 보내고 API 에서 위 코드처럼 합쳤습니다. 합친 다음에는 아직 고를 것이 하나 남아 있습니다.

## 5. 꺼진 상품은 서빙 때 거르고, 남은 100개 안팎이 랭킹 모델로 갑니다

**상태가 꺼짐인 상품은 RRF 다음에 뺐습니다. 세 질의 모두 100개 안팎이 남아 랭킹 모델로 갔습니다.**

광고주는 상품 광고를 아무 때나 켜고 끕니다. 꺼진 상품도 색인에서 지우지 않고 status 필드에 상태를 적어 두고, 검색할 때 그 필드로 거릅니다. 거르는 기준을 바꿔도 색인을 다시 만들 일이 없습니다.

| 질의 | BM25 | kNN | 합친 수 | 꺼져서 뺀 수 | 남은 후보 |
|---|---|---|---|---|---|
| 캠핑 의자 | 100 | 100 | 121 | 13 | 108 |
| 헤드셋 | 0 | 100 | 100 | 8 | 92 |
| 스니커즈 | 37 | 100 | 137 | 9 | 128 |

거르는 자리는 두 곳이 될 수 있습니다. 이 실습처럼 합친 뒤에 거르면 질의가 단순하지만, 꺼진 상품이 100개 안의 자리를 차지했다가 빠지므로 남는 수가 줄어듭니다. Elasticsearch 질의 안에 조건을 넣으면 처음부터 켜진 상품 가운데 100개를 받습니다. 대신 kNN 은 그래프를 따라가며 조건에 맞는 것만 세어야 해서, 걸러지는 비율이 높을수록 느려집니다.

후보 수는 랭킹 모델이 쓸 수 있는 시간이 정합니다. 랭킹 모델은 후보마다 피처를 모아 점수를 내므로, 후보가 두 배면 그 일도 두 배입니다. [추론 서버](post.html?id=inference-server) 편의 모델 서버는 후보 800건을 한 텐서로 넣어 3.0ms 에 점수를 냈습니다. 그 예산이면 100개 안팎은 넉넉하고, 그만큼 BM25 와 kNN 이 가져오는 수를 늘릴 여유도 있습니다.

후보를 늘리는 쪽이 이득인지는 빠지던 상품이 들어오는지로 봅니다. 위 표에서 「스니커즈」의 kNN 100개는 하나도 운동화가 아니었으니, 이 질의에서 kNN 을 200개로 늘려도 얻을 것이 적습니다. 다음 절은 이 질의들이 Elasticsearch 안에서 어디를 돌았는지입니다.

## 6. 인덱스 하나는 샤드 둘로 나뉘고, 질의는 샤드마다 돕니다

**상품 3만 건이 든 인덱스는 샤드 둘로 나뉘어 노드 둘에 놓였습니다. 샤드마다 primary 와 replica 가 다른 노드에 하나씩 있습니다.**

인덱스는 Elasticsearch 에서 문서를 담는 단위이고, 샤드는 그 인덱스를 나눈 조각입니다. 이 실습 환경의 인덱스는 샤드 0 에 15,042건, 샤드 1 에 14,958건을 담았습니다. 문서마다 id 를 해시해 어느 샤드에 넣을지 정해서 거의 반반으로 나뉩니다.

질의 하나는 샤드마다 한 번씩 돕니다. 질의를 받은 노드가 샤드 0 과 샤드 1 에 같은 질의를 보내고, 샤드마다 자기 문서 가운데 위 100개를 돌려받아 합칩니다. 그래서 질의의 시간은 가장 늦은 샤드가 정합니다. 샤드를 늘리면 한 샤드가 볼 문서는 줄지만 보낼 곳과 합칠 목록이 늘어납니다.

replica 는 primary 와 같은 문서를 다른 노드에 둔 샤드의 복사본입니다. 노드 하나가 꺼져도 남은 노드에 샤드 0 과 1 이 다 있어 검색이 이어집니다. 읽기는 primary 와 replica 가운데 아무 쪽이나 받으므로 replica 를 늘리면 초당 받을 수 있는 질의도 늘어납니다. 쓰기는 primary 가 먼저 받고 replica 로 복사하므로 replica 가 늘면 쓰기 일도 늘어납니다.

샤드 수는 인덱스를 만들 때 정하는 값이라 그 인덱스에서는 바꾸지 못합니다. split 이나 shrink 로 바꾸는 것도 새 인덱스를 만들어 옮기는 일입니다. 다음 절에서 볼 「새 인덱스로 교체」가 그 일을 날마다 하는 방법이라, 샤드 수를 고칠 기회도 날마다 생깁니다.

## 7. 날마다 바뀌는 피처는 새 인덱스를 만들어 별칭을 옮깁니다

**초당 50건의 검색을 받으면서 상품 피처를 두 방법으로 바꿨습니다. 운영 인덱스에 바로 넣으니 8.8초 동안 p99 가 221ms 까지 올랐습니다. 새 인덱스를 만들어 바꾸니 160ms 까지 올랐고, 교체 자체는 22ms 에 끝났습니다.**

상품의 클릭률이나 입찰가처럼 날마다 새로 계산하는 값은 검색하면서 바로 쓰려고 색인에도 넣어 둡니다. 그 값을 바꾸는 방법이 둘입니다. (가)는 지금 검색이 읽고 있는 인덱스에 바뀐 문서를 바로 다시 넣습니다. (나)는 옆에 새 인덱스를 처음부터 만들고, 다 되면 검색이 읽는 이름을 새 인덱스로 옮깁니다.

검색이 읽는 이름을 별칭(alias)이라고 부릅니다. 검색 API 는 인덱스 이름 대신 kw_read 라는 별칭으로 질의합니다. 별칭을 옮기는 요청은 아래 하나이고, 빼기와 더하기가 한 요청 안에서 같이 일어나서 검색이 비는 순간이 없습니다.

```json
POST _aliases
{
  "actions": [
    { "remove": { "index": "kw_20261031_120731", "alias": "kw_read" } },
    { "add":    { "index": "kw_20261031_175642", "alias": "kw_read" } }
  ]
}
```

아래는 (가)와 (나)를 차례로 해 본 기록입니다. (가)는 상품 절반인 1만 5천 건, (나)는 3만 건 전부를 넣었습니다. 걸린 시간은 색인 프로그램이 단계마다 잰 값이고, p99 는 그동안 1초마다 낸 검색 p99 의 평균과 최대입니다. 단계의 경계는 1초마다 상태를 읽어 정해서, 만들기 줄의 p99 에는 bulk 의 첫 1초가 섞여 있습니다.

| 단계 | 걸린 시간 | p99 평균 | p99 최대 |
|---|---|---|---|
| (가) 운영 인덱스에 바로 bulk | 8.8초 | 118.7ms | 220.6ms |
| (나) 새 인덱스를 replica 0, refresh 끔으로 만들기 | 164ms | 130.1ms | 160.2ms |
| (나) 3만 건을 bulk | 4.2초 | 89.5ms | 141.7ms |
| (나) replica 켜고 refresh, green 기다리기 | 6.4초 | 33.5ms | 63.3ms |
| (나) force merge 로 세그먼트를 1개로 | 1.7초 | 32.0ms | 55.8ms |
| (나) 별칭 교체 | 22ms | - | - |
| 교체 뒤 30초 | - | 8.5ms | - |

(가)는 검색이 읽는 인덱스의 문서를 지우고 다시 넣는 일입니다. 바꾼 문서를 1초마다 새 세그먼트로 만들고, 그 색인 일이 검색과 같은 노드의 CPU 와 디스크를 나눠 씁니다. (나)도 p99 가 올랐는데, 이 실습 환경은 노드 둘이 새 인덱스 만들기와 검색을 같이 하기 때문입니다. 그래도 문서를 두 배 넣으면서 (나) 전체의 p99 평균은 63.1ms 로 (가)의 절반쯤이었습니다.

(나)가 두 배 많은 문서를 더 빨리 넣은 데에는 설정이 큽니다. 새 인덱스는 replica 없이, refresh 를 끈 채로 채웠습니다. refresh 는 넣은 문서를 검색할 수 있게 세그먼트로 만드는 일인데, 기본으로 1초마다 돕니다. 아무도 읽지 않는 새 인덱스라 다 넣은 뒤 한 번만 하면 됩니다. 다 넣고 나서 replica 를 켜면 다른 노드로 샤드를 통째로 복사합니다.

force merge 는 세그먼트를 하나로 합치는 일입니다. 질의가 볼 세그먼트가 줄고, 지운 표시만 남은 문서가 이때 정리됩니다. 쓰기가 계속되는 인덱스에 하면 합쳐진 큰 세그먼트를 자동 병합이 다시 고르지 않아, 지운 문서가 그 안에 오래 남습니다. 그래서 쓰기가 끝난 새 인덱스에만 합니다.

옛 인덱스는 지우지 않고 두었다가, 새 피처에 문제가 보이면 별칭을 옛 인덱스로 되돌리는 요청 하나로 롤백합니다. 이 실습 환경은 최근 셋을 남기고 그보다 오래된 것을 지웁니다. 남겨 둔 만큼 디스크를 더 쓰지만, 롤백이 다시 색인하는 시간이 아니라 요청 한 번의 시간이 됩니다.

## 8. 담장 안과 열린 RTB 는 질의가 어디서 오는지가 다릅니다

**글자와 뜻으로 찾아 순위로 합치는 방법은 두 무대가 같습니다. 다른 것은 질의의 정체와, 찾는 데 쓸 수 있는 시간입니다.**

### 담장 안에서는 사용자의 검색어가 질의입니다 [무대: 닫힌 생태계]

검색 광고를 파는 플랫폼은 검색창과 광고 상품을 다 가집니다. 사용자가 친 검색어가 그대로 질의가 되고, 상품 이름과 상태와 피처도 우리 데이터베이스에서 옵니다. 그래서 날마다 새 인덱스를 만들어 별칭을 옮기는 일정을 우리가 정합니다. 광고주가 상품을 켜고 끄는 일은 하루 중 아무 때나 일어나므로, 그 상태만 작은 인덱스에 따로 받아 바로 반영하는 방법을 같이 씁니다.

동의어 사전과 임베딩 모델도 우리 검색 로그로 고칩니다. 「헤드셋」을 친 사용자가 헤드폰 광고를 눌렀다는 기록이 쌓이면, 사전에 한 줄을 넣거나 임베딩 모델을 그 쌍으로 다시 학습합니다.

### 열린 RTB 에서는 질의 대신 지면의 내용이 옵니다 [무대: 열린 RTB]

DSP 가 받는 입찰 요청에는 사용자의 검색어가 거의 없습니다. 대신 지면의 주소, 카테고리, 앱 이름 같은 맥락이 옵니다. 그래서 질의는 「이 지면의 글」이 되고, 찾는 대상은 우리 광고주의 소재입니다. 지면 글과 소재 글을 BM25 와 벡터로 비교하고 순위로 합치는 방법은 그대로 씁니다.

시간은 더 빠듯해서, 입찰 응답 전체를 100ms 안팎에 돌려줘야 하고 그 안에 거래소와의 네트워크 왕복이 들어 있습니다. 그래서 지면마다 찾은 결과를 캐시해 두고, 처음 보는 지면에만 검색을 돌리는 식으로 씁니다.

## 한눈 정리

| 단계 | 하는 일 | 이 실습에서 잰 값 | 결정할 것 |
|---|---|---|---|
| 분석기 | 이름과 질의를 토큰으로 자른다 | 「헤드셋」은 토큰이 없어 0건 | 동의어를 검색 때 풀지 색인 때 풀지 |
| BM25 | 토큰이 맞는 문서를 점수 순으로 | 6.9ms 에 100건 | 가져올 수 |
| kNN | 벡터가 가까운 문서를 근사로 | 13.6ms 에 100건, 스니커즈 1위는 선글라스 | 모델, num_candidates |
| RRF | 순위로 1 ÷ (60 + 순위) 를 더한다 | 0.26ms, 200건이 121건으로 | k 값, 거르는 자리 |
| 샤드 | 인덱스를 나눠 노드에 둔다 | 샤드 둘, replica 하나, 노드 둘 | 샤드 수는 새 인덱스를 만들 때 |
| 교체 | 새 인덱스를 만들어 별칭을 옮긴다 | 교체 22ms, 바로 넣을 때 p99 최대 221ms | 옛 인덱스를 몇 개 남길지 |

## 헷갈리기 쉬운 점

- **BM25 0건은 장애가 아닙니다.** 토큰이 없으면 0건이 정상입니다. 먼저 분석기에 질의와 상품 이름을 넣어 토큰을 나란히 봅니다.
- **kNN 은 늘 k 개를 돌려줍니다.** 0건이 없다는 것이 맞는다는 뜻은 아닙니다. 「스니커즈」의 100개에는 운동화가 하나도 없었습니다.
- **RRF 점수는 확률이 아닙니다.** 0.0302 는 순위를 매기는 값일 뿐이라 질의끼리 비교할 수 없습니다. 점수의 크기가 필요하면 랭킹 모델이 냅니다.
- **없는 낱말은 형태소 분석기가 엉뚱하게 자릅니다.** 가짜 브랜드 「아틀라이프」는 「틀」과 「라이프」로 잘렸습니다. 브랜드 이름은 사용자 사전에 넣어 둡니다.
- **force merge 는 운영 인덱스에 하지 않습니다.** 쓰기가 끝난 인덱스에만 합니다. 쓰기가 계속되면 합친 큰 세그먼트 안에 지운 문서가 오래 남습니다.
- **별칭 교체가 빠른 것과 새 인덱스를 만드는 것이 빠른 것은 다릅니다.** 교체는 22ms 였지만 만드는 데는 13초 넘게 걸렸고, 그동안의 부하는 노드가 받습니다.
